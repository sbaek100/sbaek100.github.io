> 지난 시간 도달 상태: 공격자 Kali 준비 완료(1-2 Kali VM 또는 [1-2 부록 WSL Kali](/posts/socbuild-02-opt-kali-wsl/)).
> 오늘의 목표: **표적 서버(`victim`)** 를 **별도의 물리 리눅스 서버**로 세우고 취약한 웹앱(Juice Shop)을 올린 뒤, Kali에서 **첫 공격**을 날려 방어 장치가 하나도 없을 때 공격이 그대로 통하는 것을 확인합니다.
> 오늘 준비: **물리 서버 1대(표적) + 공격자 Kali 1대**.
{: .prompt-info }

> **★ 표적은 이 과정에서 유일한 "진짜 컴퓨터"입니다.** 방화벽(OPNsense)·관제 서버(SIEM)는 뒤 단계에서 VirtualBox VM으로 세우지만, 표적 웹서버는 남는 PC나 미니 PC 한 대에 우분투를 직접 설치해 씁니다. 공격자와 표적이 **같은 네트워크(같은 스위치·공유기)** 에 유선으로 연결되어 있어야 서로 통합니다.
>
> **공격자는 표적과 같은 네트워크에 있어야 합니다.** [1-2 부록의 WSL Kali](/posts/socbuild-02-opt-kali-wsl/) 는 윈도우의 네트워크를 그대로 쓰므로 바로 가능합니다. 1-2의 Kali **VM**을 쓴다면, VirtualBox 내부 네트워크로는 물리 서버에 닿지 못하므로 그 VM의 어댑터를 **브리지(Bridged Adapter)** 로 바꿔 같은 네트워크에 올려야 합니다.
{: .prompt-warning }

## 0. 오늘의 그림

지금은 방화벽·WAF가 아직 없습니다. 공격자와 표적이 **같은 네트워크**에 나란히 있어, 공격이 아무 저항 없이 표적에 닿습니다.

```text
[ 공격자 Kali ]        (같은 물리 네트워크 · 방어장치 없음)
        │
        ▼
[ 물리 리눅스 서버 ]  192.168.59.20  ─ Juice Shop (취약 웹앱, 포트 3000)
```

이 **무방비 상태**가 앞으로 모든 방어 단계의 "before" 기준입니다. 2단계에서 방화벽을 끼우면 같은 공격이 어떻게 막히는지 비교하게 됩니다.

> **네트워크 대역 안내**: 이 강의는 기준표(1-1강)를 따라 표적 IP를 **192.168.59.20** 으로 씁니다. 여러분의 실습 네트워크(공유기)가 다른 대역(예: `192.168.0.x`)이라면, **표적과 공격자를 같은 대역**으로 맞추기만 하면 됩니다. 뒤에 나오는 `192.168.59.x`·게이트웨이 `192.168.59.1` 은 **여러분 네트워크의 실제 값**으로 바꿔 넣으세요.
{: .prompt-info }

## 3. 따라 하기: 표적 서버 고정 IP 지정 (netplan)

공격자가 매번 같은 주소로 표적을 겨냥할 수 있도록 **고정 IP** 를 줍니다. Ubuntu Server는 **netplan** 으로 IP를 설정합니다. 물리 서버는 랜카드 한 장으로 **실습 통신과 인터넷을 함께** 쓰므로, VM 때와 달리 **게이트웨이와 DNS까지** 지정해야 합니다.

> ### 따라 하기 3-1. 인터페이스 이름 확인
>
> **목적** 랜카드 이름을 찾습니다.
{: .prompt-tip }

**1단계.**

```bash
ip -brief address
```

출력 예시:

```text
lo               UNKNOWN   127.0.0.1/8
eno1             UP        192.168.59.50/24    ← 유선 랜카드. 이름을 기억해 둡니다
```

- `lo` 를 뺀 나머지 줄, 지금 `192.168.x.x` 주소가 붙어 있는 것이 **유선 랜카드**입니다. 이름(`eno1`·`enp1s0`·`enp2s0` 등, PC마다 다름)을 기억해 둡니다.

> 여기 잡힌 주소(예: `192.168.59.50`)는 공유기가 임시로 준 것입니다. 다음 단계에서 우리가 정한 고정 주소 **192.168.59.20** 으로 바꿉니다.
{: .prompt-info }

> ### 따라 하기 3-2. netplan 설정 파일 작성
>
> **목적** 랜카드에 고정 IP·게이트웨이·DNS를 부여합니다.
{: .prompt-tip }

> ⚠️ 아래 두 곳을 **여러분 값**으로 바꿔야 합니다.
> - `eno1` → **3-1에서 확인한 실제 랜카드 이름**
> - `192.168.59.1` → **여러분 공유기(게이트웨이) 주소** (공유기 관리자 주소. 흔히 `192.168.0.1`·`192.168.1.1` 등)
{: .prompt-warning }

**2단계.** 아래 명령을 **통째로 붙여 넣습니다.** 설정 파일을 자동으로 만들어 줍니다.

```bash
sudo tee /etc/netplan/99-soc.yaml >/dev/null <<'EOF'
network:
  version: 2
  ethernets:
    eno1:
      dhcp4: no
      addresses: [192.168.59.20/24]
      routes:
        - to: default
          via: 192.168.59.1
      nameservers:
        addresses: [8.8.8.8, 1.1.1.1]
EOF
```

- `routes`(기본 경로)와 `nameservers`(DNS)가 있어야 서버가 **인터넷까지** 나갈 수 있습니다. VM 때는 NAT 어댑터가 이 역할을 대신했지만, 물리 서버는 랜카드 한 장으로 모두 처리합니다.

**3단계.** 파일 권한을 정리하고 적용합니다.

```bash
sudo chmod 600 /etc/netplan/99-soc.yaml
sudo netplan apply
```

**4단계.** 고정 IP가 붙었는지 확인합니다. (`eno1` 은 실제 이름으로)

```bash
ip -brief address show eno1
```

`192.168.59.20/24` 가 보이면 성공입니다.

**5단계.** **인터넷과 DNS가 되는지** 확인합니다. 다음 두 줄이 모두 응답해야 4장(Docker 설치)이 됩니다.

```bash
ping -c 3 8.8.8.8
ping -c 3 archive.ubuntu.com
```

- 첫 줄만 되고 둘째 줄이 안 되면 **DNS 문제**입니다. netplan의 `nameservers` 를 확인하세요.
- 둘 다 안 되면 **게이트웨이(`via`) 주소가 틀린** 것입니다. 공유기 주소를 다시 확인해 3-2를 고칩니다.

> 📷 **화면 캡처 위치** — `ip -brief address` 에 192.168.59.20 이 보이고, `ping archive.ubuntu.com` 이 응답하는 화면.
{: .prompt-tip }

## 4. 따라 하기: Docker 설치 후 취약 웹앱(Juice Shop) 올리기

취약한 웹앱을 직접 설치하려면 복잡합니다. 대신 **Docker**(컨테이너)로 명령 한 줄에 띄웁니다. OWASP **Juice Shop** 은 교육용으로 만든 대표적인 취약 웹앱입니다.

> ### 따라 하기 4-1. Docker 설치
>
> **목적** 컨테이너 실행 환경을 준비합니다. (3장에서 인터넷 확인 필요)
{: .prompt-tip }

**1단계.**

```bash
sudo apt update
sudo apt install -y docker.io
```

**2단계.** Docker 서비스를 켜고 부팅 시 자동 실행되도록 합니다.

```bash
sudo systemctl enable --now docker
```

**3단계.** `student` 계정이 `sudo` 없이 docker를 쓸 수 있게 그룹에 추가합니다.

```bash
sudo usermod -aG docker student
```

> ⚠️ 위 그룹 변경은 **다시 로그인해야** 적용됩니다. 지금은 우선 `sudo`를 붙여 진행하고, 다음 로그인부터 `sudo` 없이 쓰면 됩니다.
{: .prompt-warning }

> ### 따라 하기 4-2. Juice Shop 컨테이너 실행
>
> **목적** 취약 웹앱을 포트 3000으로 띄웁니다.
{: .prompt-tip }

**4단계.** 다음 한 줄로 이미지를 내려받아 실행합니다.

```bash
sudo docker run -d --restart unless-stopped -p 3000:3000 --name juice-shop bkimminich/juice-shop
```

**5단계.** 정상 실행 여부를 확인합니다.

```bash
sudo docker ps
```

`juice-shop` 이 `Up ...` 상태로 보이면 성공입니다.

**6단계.** 서버 자신에게서 응답이 오는지 확인합니다.

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000
```

`200` 이 출력되면 웹앱이 살아 있는 것입니다.

> 📷 **화면 캡처 위치** — `sudo docker ps` 에 juice-shop 이 Up 상태로 보이고, curl 이 200 을 돌려주는 화면.
{: .prompt-tip }

> **DVWA로 하고 싶다면(선택)**: Juice Shop 대신 `sudo docker run -d --restart unless-stopped -p 80:80 --name dvwa vulnerables/web-dvwa` 로 올릴 수 있습니다. 본 강의는 Juice Shop(포트 3000) 기준으로 진행합니다.
{: .prompt-tip }

## 5. 따라 하기: Kali에서 첫 공격 — 무방비 확인

이제 공격자(Kali)로 돌아가, 방어 장치가 없는 표적을 공격해 봅니다. **공격자 Kali가 표적과 같은 네트워크에 있어야** 합니다(WSL Kali 또는 브리지 모드 Kali VM). 표적 서버는 켜 둔 상태여야 합니다.

> ### 따라 하기 5-1. 표적이 살아 있는지 확인 (ping)
>
> **목적** 공격자와 표적이 서로 통하는지 봅니다.
{: .prompt-tip }

**1단계.** Kali 터미널에서:

```bash
ping -c 3 192.168.59.20
```

응답이 오면 연결된 것입니다. (응답이 없으면 두 기기가 같은 네트워크·같은 대역에 있는지, 표적 IP가 192.168.59.20 인지 확인하세요.)

> ### 따라 하기 5-2. 포트 스캔 (nmap)
>
> **목적** 표적에 어떤 서비스가 열려 있는지 정찰합니다. 공격의 첫 단계입니다.
{: .prompt-tip }

**2단계.** Kali 터미널에서:

```bash
nmap -sV -T4 192.168.59.20
```

결과에 **22/tcp (ssh)** 와 **3000/tcp** 가 `open` 으로 보입니다. 방어 장치가 없으니 스캔이 **아무 방해 없이** 표적의 열린 문을 그대로 알려 줍니다.

```text
PORT     STATE SERVICE VERSION
22/tcp   open  ssh     OpenSSH 9.6p1 Ubuntu
3000/tcp open  ppp?
```

> **왜 3000이 `http` 가 아니라 `ppp?` 로 나올까 — 사실 3000은 HTTP가 맞습니다.**
>
> nmap의 `SERVICE` 칸은 대개 **포트 번호로 짐작한 이름**입니다. nmap의 포트 목록에 3000번은 관례상 `ppp` 로 등록돼 있어 그렇게 표시됩니다. `-sV` 로 실제 응답까지 받아 봤지만, Juice Shop(Node.js)이 nmap의 버전 지문 목록에 없어 "확실치 않다"는 뜻의 물음표(`?`)가 붙은 것입니다.
>
> 그런데 같은 화면 아래에 nmap이 받아 온 응답 원문(`SF-Port3000...` 으로 시작하는 긴 덩어리)을 보면 `HTTP/1.1 200 OK`, `Content-Type: text/html`, `OWASP Juice Shop` 같은 글자가 그대로 들어 있습니다. **즉 3000은 명백히 HTTP(웹 서버)이고**, nmap의 이름표만 애매했을 뿐입니다. 확실한 확인법은 브라우저로 `http://192.168.59.20:3000` 에 접속해 보는 것입니다(바로 다음 단계).
>
> 이 점은 뒤(2-3편 Suricata)에서 중요합니다. **Suricata는 포트 번호나 nmap의 이름표가 아니라 트래픽 내용으로 HTTP를 알아보므로**, 3000 포트로 들어오는 웹 공격도 그대로 검사합니다.
{: .prompt-info }

> ### 따라 하기 5-3. 웹앱 접속
>
> **목적** 표적 웹앱이 공격자에게 그대로 보이는지 확인합니다.
{: .prompt-tip }

**3단계.** 웹 브라우저를 열고 주소창에 입력합니다. (WSL Kali는 그래픽 브라우저가 없으므로 **윈도우 브라우저**로 접속합니다. Kali VM이면 Kali 안의 Firefox로 접속합니다.)

```text
http://192.168.59.20:3000
```

Juice Shop 쇼핑몰 화면이 뜹니다. 방화벽·WAF가 없으니 공격자가 표적 웹앱에 자유롭게 접근합니다.

> ### 따라 하기 5-4. SQL 인젝션으로 로그인 우회
>
> **목적** 대표적인 웹 공격이 실제로 통하는 것을 확인합니다.
{: .prompt-tip }

**4단계.** Juice Shop 화면 오른쪽 위 **Account → Login** 으로 이동합니다.

**5단계.** 로그인 칸에 다음을 입력합니다.

| 칸        | 입력값             |
| -------- | --------------- |
| Email    | `' OR 1=1;--`   |
| Password | 아무 값이나 (예: `x`) |

**6단계.** **Log in** 을 누르면, 비밀번호를 모르는데도 **관리자 계정으로 로그인**됩니다. 화면 위에 사용자 이메일이 표시됩니다.

> 방금 입력한 `' OR 1=1;--` 는 데이터베이스 질의문을 조작해 "항상 참"을 만드는 **SQL 인젝션(SQLi)** 공격입니다. 지금은 이 공격을 걸러 줄 장치가 하나도 없어 그대로 성공했습니다. **3단계(웹 방화벽)** 를 세우면 바로 이 요청이 403으로 차단됩니다.
{: .prompt-danger }

> 📷 **화면 캡처 위치** — `' OR 1=1;--` 로 관리자 로그인에 성공해 화면 위에 이메일이 표시된 Juice Shop 화면.
{: .prompt-tip }

## 6. 표적 서버 상태 보존하기

물리 서버에는 VirtualBox의 **스냅샷** 같은 "한 번에 되돌리기" 기능이 없습니다. 대신 다음을 기억해 두면 됩니다.

- **웹앱은 자동으로 되살아납니다.** Juice Shop 컨테이너를 `--restart unless-stopped` 로 띄웠으므로, 서버를 껐다 켜도 부팅과 함께 다시 뜹니다.
- **깨끗한 상태로 초기화**해야 하면, 컨테이너만 지웠다가 다시 올립니다.

```bash
sudo docker rm -f juice-shop
sudo docker run -d --restart unless-stopped -p 3000:3000 --name juice-shop bkimminich/juice-shop
```

- **운영체제까지 처음으로 되돌리려면** 1~2장을 따라 **USB로 재설치**합니다. (고급: Clonezilla 같은 도구로 디스크 이미지를 떠 두면 통째로 복원할 수 있지만, 이 과정에서는 필요하지 않습니다.)

> 종료가 필요하면 서버 터미널에서 `sudo poweroff` 를 씁니다.
{: .prompt-tip }

## 7. 1단계 정리와 점검

1단계를 마치면 다음 상태가 됩니다.

- **공격자 Kali**와 **물리 표적 서버**(192.168.59.20)가 같은 네트워크에 있음
- 표적에는 취약 웹앱(Juice Shop)이 돌고 있음
- 방어 장치가 **하나도 없어**, 포트 스캔·웹 접근·SQL 인젝션이 **모두 성공**

점검 목록:

- [ ] 물리 서버에 Ubuntu Server가 설치되고 IP가 **192.168.59.20** 으로 고정됐다
- [ ] 서버에서 `ping archive.ubuntu.com` 이 응답한다 (인터넷·DNS 정상)

- [ ] Kali에서 `ping 192.168.59.20` 이 응답한다
- [ ] `nmap` 으로 3000 포트가 `open` 으로 보인다
- [ ] Juice Shop에서 `' OR 1=1;--` 로 로그인 우회가 성공했다
