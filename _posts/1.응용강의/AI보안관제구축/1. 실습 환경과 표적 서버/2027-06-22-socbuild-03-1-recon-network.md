> **선행 강의 도달점** — [1-3. 표적 서버 만들기와 첫 공격](/posts/socbuild-03-victim-server-firstattack/) 에서 표적(Ubuntu + Juice Shop)을 구축하고, 방어 장치가 부재한 상태에서 공격이 아무런 저항 없이 관철됨을 확인하였다.
> **본 강의의 목표** — 방어 장치가 전무한 표적을 '네트워크 계층'에서 점검한다. 표적의 생존 여부를 확인하고(호스트 발견), 개방된 포트를 열거하며(포트 스캔), 각 포트에서 동작하는 서비스와 버전을 식별한다(서비스 탐지). 이를 종합하여 **공격면(attack surface), 즉 외부에서 접근 가능한 통로의 지도**를 작성한다. 
> **준비 사항** — 공격자 Kali(WSL) 1대와 표적 서버 1대. 방어 장치는 여전히 부재하다.
{: .prompt-info } 

## 0. 3부작의 위치 — 무방비 상태의 계층별 진단

2단계에서 방화벽(OPNsense)을 도입하기 **이전에**, 표적의 무방비 정도를 **세 계층으로 구분하여** 진단한다. 의료 검진이 혈액·영상·초음파로 구분되듯, 공격면 또한 계층별로 분리하여 관찰해야 누락이 발생하지 않는다.

| 편 | 계층 | 점검 대상 | 대표 도구 |
| --- | --- | --- | --- |
| **1-3-1 (본 강의)** | 네트워크 (L3/L4) | 개방된 포트, 동작 중인 서비스 | `ping`, `nmap` |
| [1-3-2](/posts/socbuild-03-2-recon-system/) | 시스템 (호스트·서비스) | SSH·서비스 버전의 결함, 노출된 관리 서비스 | `nmap NSE`, `hydra`, `searchsploit` |
| [1-3-3](/posts/socbuild-03-3-recon-web/) | 웹 애플리케이션 (L7) | Juice Shop의 SQLi·XSS·접근통제 결함 | `nikto`, `sqlmap`, 브라우저 |

> **점검 순서의 근거** — 공격자는 항상 외부에서 내부로 범위를 좁혀 들어간다. 먼저 "어느 지점에 통로가 존재하는가(네트워크)"를 파악하고, 그 통로의 "잠금장치가 견고한가(시스템)"를 검증한 뒤, 최종적으로 "통로 내부의 자산(웹 애플리케이션의 데이터)"을 노린다. 방어자 또한 동일한 순서로 점검하여야 공격자에 선행하여 결함을 제거할 수 있다.
{: .prompt-tip }

본 3부작을 관통하는 핵심 원칙은 다음과 같다. 각 공격 절차의 말미에서 반드시 다음 질문에 답한다.

> **"이 공격은 후속 단계에서 도입할 OPNsense 방화벽으로 차단할 수 있는가?"**

이 질문의 답을 편별로 표로 정리한다. 일부 공격은 방화벽만으로 완전히 차단되며(주로 네트워크 계층), 일부 공격은 방화벽으로 **결코 차단할 수 없다**(주로 웹 계층 — 이 때문에 3단계의 WAF가 요구된다). 이 구분을 무방비 단계에서 직접 확인해 두는 것이 5단계 폐루프 SOC 전체를 이해하는 핵심이다.

## 0-1. 실습 구성도

```text
[ 공격자 Kali (WSL) ]          (동일 물리 네트워크 · 방어장치 0개)
   192.168.0.10                     192.168.0.0/24
        │
        │   ①생존 확인  ②개방 포트  ③동작 서비스
        ▼
[ Ubuntu 미니 PC ]  192.168.0.30  ─ Juice Shop (Docker, 포트 3000) + SSH(22)
```

> **⚠ 실습 범위 및 윤리 — 필수 준수 사항.** 본 강의의 모든 스캔과 공격은 **학습자 본인이 소유한 실습망의 표적 서버(192.168.0.30)** 에 한하여 수행한다. 허가받지 않은 타인의 시스템·네트워크·공유기를 스캔하는 행위는 **정보통신망법 위반에 해당하는 불법 행위**이다. 카페·회사·학교 등 공용 네트워크에서 `nmap 192.168.0.0/24` 와 같은 대역 스캔을 수행하여서는 안 된다. 실습은 **독립된 사설 네트워크**에서만 진행한다.
{: .prompt-danger }

> **💡 WSL Kali의 주소 체계 이해.** Kali(WSL) 내부에서 `ip a` 를 실행하면 주소가 **172.x.x.x** 로 표시된다. 이는 WSL 내부 전용 주소이다. 그러나 WSL2는 윈도우의 네트워크를 경유하여 외부로 통신하므로, **표적(192.168.0.30)의 관점에서 공격은 "윈도우 호스트의 IP(192.168.0.10)"에서 발신된 것으로 관측된다.** 본 강의에서 "공격자 192.168.0.10"으로 지칭하는 것은 이 관점의 주소이다. Kali에서 표적을 향한 스캔·공격은 정상적으로 수행된다.
> 참고로 윈도우 11 최신 버전의 WSL **미러(mirrored) 네트워크 모드**를 사용하면 Kali가 192.168.0.10을 직접 보유할 수도 있다. 어느 방식이든 표적 단일 대상에 대한 실습 결과는 동일하다.
{: .prompt-info }

## 1. 실습 도구 준비

Kali의 기본(base) 이미지, 특히 WSL 배포판은 최소 구성으로 제공되어 일부 도구가 설치되어 있지 않을 수 있다. 본 3부작에서 사용할 도구와 사전(wordlist)을 미리 설치한다.

> ### 실습 1-0. 도구 및 사전 설치
>
> **목적** 3부작 전체에서 사용할 점검 도구와 워드리스트를 확보한다.
{: .prompt-tip }

```bash
sudo apt update
sudo apt install -y nmap hydra nikto sqlmap gobuster whatweb exploitdb dirb wordlists curl
```

| 패키지 | 제공 도구 | 사용 편 |
| --- | --- | --- |
| `nmap` | 포트·서비스 스캐너 | 1-3-1, 1-3-2 |
| `hydra` | 로그인 무차별 대입 | 1-3-2 |
| `exploitdb` | `searchsploit`(공개 취약점 검색) | 1-3-2 |
| `nikto`·`gobuster`·`whatweb` | 웹 취약점·경로·기술 스택 탐색 | 1-3-3 |
| `sqlmap` | SQL 인젝션 자동화 | 1-3-3 |
| `dirb`·`wordlists` | `/usr/share/wordlists` 사전(rockyou, dirb) | 1-3-2, 1-3-3 |

> 설치가 완료되면 `nmap --version`, `hydra -h`, `searchsploit -h` 등으로 각 도구가 정상 동작하는지 확인한다.
{: .prompt-info }

## 2. 실습: 표적과의 연결 확인 (호스트 발견)

공격의 첫 단계는 언제나 **"표적이 가동 중이며 도달 가능한가"** 를 확인하는 것이다. 이 단계를 **호스트 발견(Host Discovery)** 이라 한다.

> ### 실습 2-1. 표적의 생존 확인 (ping)
>
> **목적** 표적 서버가 네트워크에서 응답하는지, 그리고 몇 홉(hop) 거리에 위치하는지 확인한다.
{: .prompt-tip }

**1단계.** Kali 터미널을 실행한다.

**2단계.** 표적으로 ICMP Echo 요청을 4회 전송한다.

```bash
ping -c 4 192.168.0.30
```

정상적인 경우 다음과 같은 응답이 수신된다.

```text
64 bytes from 192.168.0.30: icmp_seq=1 ttl=64 time=0.512 ms
64 bytes from 192.168.0.30: icmp_seq=2 ttl=64 time=0.480 ms
...
--- 192.168.0.30 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss
```

### 이 절차를 수행하는 이유

`ping` 은 공격이라기보다 **정찰의 출발점**이다. 응답이 수신되면 표적이 가동 중이며 통신이 성립함을 의미한다. 다만 응답이 없다고 하여 표적이 부재하는 것은 아니다 — **방화벽이 ICMP를 차단하고 있을 가능성**이 있기 때문이다. 따라서 공격자는 `ping` 하나로 판단을 종결하지 않고 후속 단계인 포트 스캔으로 이행한다.

### 명령과 옵션의 해설

| 옵션 | 의미 |
| --- | --- |
| `ping` | ICMP Echo 요청을 전송하여 응답을 확인하는 명령 |
| `-c 4` | 4회 전송 후 종료(`count`). 이 옵션이 없으면 리눅스의 ping은 무한 반복한다 |
| `time=0.5 ms` | 왕복 시간(RTT). 동일 스위치에 연결된 경우 통상 1ms 미만이다 |
| `ttl=64` | 잔여 홉 수. 64에서 시작하면 리눅스 계열, 128이면 윈도우 계열일 가능성이 높다 |

### 공격자가 획득하는 정보

- 표적이 **가동 중이며 도달 가능**하다는 사실
- `ttl=64` 로부터 표적이 **리눅스 계열**일 것이라는 최초의 단서
- 응답 시간이 1ms 미만이라는 점에서 **경로 중간에 방화벽이 부재**하다는 정황

> ### 실습 2-2. 네트워크 대역의 활성 호스트 열거 (핑 스윕)
>
> **목적** 단일 표적이 아니라 **동일 네트워크 대역에서 활성화된 모든 호스트**를 일괄 탐색한다.
{: .prompt-tip }

```bash
sudo nmap -sn 192.168.0.0/24
```

출력 예시는 다음과 같다.

```text
Nmap scan report for 192.168.0.1     (공유기/게이트웨이)
Host is up (0.0010s latency).
Nmap scan report for 192.168.0.10    (윈도우 호스트)
Host is up.
Nmap scan report for 192.168.0.30    (표적 Juice Shop 서버)
Host is up (0.00050s latency).
Nmap done: 256 IP addresses (3 hosts up) scanned in 2.13 seconds
```

> **⚠ WSL(NAT) 환경에서의 유의점.** WSL2가 기본 NAT 모드로 동작하는 경우, Kali는 표적과 다른 사설 대역(172.x)에 위치하므로 ARP 기반 호스트 발견이 적용되지 않는다. 이때 대역 스윕은 ICMP·TCP 프로브에 의존하며, 그 결과가 부분적일 수 있다. **표적 IP(192.168.0.30)를 이미 알고 있는 본 실습에서는 대역 스윕에 의존하지 않고 표적 단일 대상 스캔에 집중하는 것으로 충분하다.** (미러 모드에서는 ARP 스윕이 정상 동작한다.)
{: .prompt-warning }

### 이 절차를 수행하는 이유

실제 침입에서 공격자가 표적의 IP를 사전에 아는 경우는 드물다. 네트워크에 침투한 후 **"이 네트워크에 어떤 장비가 존재하는가"** 를 우선 파악하며, 이를 *내부 정찰(internal reconnaissance)* 이라 한다. 핑 스윕은 대역 전체(`/24` = 254개 주소)의 활성 호스트를 지도화한다.

### 명령과 옵션의 해설

| 옵션 | 의미 |
| --- | --- |
| `nmap` | 네트워크 스캐너. 본 3부작에서 가장 빈번히 사용된다 |
| `-sn` | **포트 스캔을 생략**하고 활성 호스트만 탐색(`s`can, `n`o port scan) |
| `192.168.0.0/24` | 192.168.0.0 ~ 192.168.0.255 대역 전체 |
| `sudo` | 호스트 발견은 ARP·ICMP 원시 패킷을 사용하므로 관리자 권한이 필요하다 |

### 공격자가 획득하는 정보

- **네트워크 지도** — 게이트웨이(0.1)·호스트(0.10)·표적(0.30)의 위치
- 표적 외 추가 대상(NAS·프린터·IoT 등)의 존재 여부
- 이 정보를 근거로 **후속 정밀 점검 대상을 선정**

### 점검 항목 (호스트 발견)

- [ ] 표적 `192.168.0.30` 이 `Host is up` 으로 식별되는가?
- [ ] `ttl=64` 인가? (리눅스 계열로 추정)
- [ ] 대역 내 예상치 못한 장비가 존재하지 않는가?

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **부분적으로 가능하다.** 후속 단계에서 Kali는 방화벽의 외부(WAN)에, 표적은 내부(LAN)에 배치된다. 이때 OPNsense에서 **ICMP 통과를 차단하는 규칙**을 적용하면 ping 응답이 차단된다. 또한 표적이 방화벽 내부로 이동하면 외부에서 `nmap -sn 192.168.0.0/24` 를 수행하여도 **LAN 대역이 스윕 결과에 포함되지 않는다**(네트워크 분리 효과). 다만 ICMP를 차단하여도 `-Pn` 옵션을 통한 포트 스캔은 여전히 시도 가능하므로, "ICMP 차단 = 안전"이라는 등식은 성립하지 않는다.
{: .prompt-warning }

## 3. 실습: 개방 포트의 전수 탐색 (포트 스캔)

호스트의 생존을 확인하였으므로, 다음으로 **개방된 포트**를 탐색한다. 각 포트는 "외부에서 접근 가능한 서비스"를 의미하며, 곧 **공격 후보**가 된다.

> ### 실습 3-1. 표적의 전체 포트 스캔
>
> **목적** 65,535개 포트 중 **개방된 포트를 전수** 탐색한다.
{: .prompt-tip }

```bash
sudo nmap -sS -p- -T4 --open -Pn 192.168.0.30
```

이 명령은 전 포트를 대상으로 하므로 수십 초에서 수 분이 소요된다. 출력 예시는 다음과 같다.

```text
PORT     STATE SERVICE
22/tcp   open  ssh
3000/tcp open  ppp?
```

> 표적에는 위 두 포트(SSH·Juice Shop)만 식별될 가능성이 높다. 서버 구축 과정에서 다른 서비스를 활성화하였다면 추가로 식별될 수 있다. **실제로 식별된 포트를 그대로 기록한다** — 이 목록이 본 강의에서 작성하는 공격면 지도이다.
{: .prompt-info }

### 이 절차를 수행하는 이유

**개방된 포트는 곧 공격 통로이다.** 아무리 취약한 웹 애플리케이션이라도 포트가 폐쇄되어 있으면 외부에서 접근할 수 없다. 반대로 개방된 포트가 많을수록 공격면은 확대된다. 공격자는 포트 스캔을 통해 **"어느 지점을 공격할 수 있는가"** 를 최우선으로 확정한다.

### 명령과 옵션의 해설

| 옵션 | 의미 | 사용 이유 |
| --- | --- | --- |
| `-sS` | **SYN 스캔**(half-open). 연결을 완결하지 않고 SYN→SYN/ACK만으로 판단 | 신속하고 로그가 적게 남아 "스텔스 스캔"으로 불린다. 원시 소켓을 사용하므로 `sudo` 필요 |
| `-p-` | **전체 포트**(1~65535) 스캔 | 주요 포트만 검사하는 기본 스캔은 3000과 같은 비표준 포트를 누락할 수 있다 |
| `-T4` | 타이밍 템플릿 4(신속) | 실습망에서의 속도 확보. 은밀성을 요하는 공격자는 `-T1`(저속)로 탐지를 회피한다 |
| `--open` | **개방 포트만** 출력 | 폐쇄 포트 다수를 출력에서 제외한다 |
| `-Pn` | 사전 ping을 생략하고 **무조건 스캔** | 표적이 ICMP를 차단하여도 스캔을 진행(방화벽 내부 표적에 유효) |

> **`-sS` 가 "스텔스"로 불리는 이유.** 정상적인 TCP 연결은 SYN → SYN/ACK → ACK 의 3방향 핸드셰이크(3-way handshake)로 완결된다. SYN 스캔은 마지막 ACK를 전송하지 않고 연결을 RST로 종료한다. 연결이 완결되지 않으므로 일부 애플리케이션 로그에는 흔적이 적게 남는다. **그러나** Suricata와 같은 IDS는 패킷 단위로 관측하므로 SYN 스캔 또한 탐지한다(2단계에서 확인).
{: .prompt-tip }

### 공격자가 획득하는 정보

- 공격 가능한 서비스 후보 목록 — `22`(원격 접속)·`3000`(웹 애플리케이션)
- 이 목록에 근거한 후속 단계 결정 — SSH는 [1-3-2 시스템 편](/posts/socbuild-03-2-recon-system/), 웹 애플리케이션은 [1-3-3 웹 편](/posts/socbuild-03-3-recon-web/) 에서 각각 정밀 점검

### 점검 항목 (포트 스캔)

- [ ] `22/tcp`(SSH)가 개방되어 있는가? → 원격 접속 공격의 통로
- [ ] `3000/tcp`(Juice Shop)가 개방되어 있는가? → 웹 공격의 통로
- [ ] **예상 외의 포트**가 개방되어 있지 않은가? (예: `2375` Docker API, `3306` MySQL, `6379` Redis 등은 외부 노출 시 매우 위험)

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **가능하며, 이는 방화벽의 핵심 기능이다.** OPNsense를 도입하면 **"필요한 포트만 개방하고 나머지는 전면 차단(default deny)"** 하는 정책을 적용할 수 있다. 예컨대 웹 서비스만 공개하려면 `3000` 만 통과시키고 `22`(SSH)는 외부 접근을 차단한다. 그 결과 동일한 `nmap -sS -p-` 를 수행하여도 개방 포트가 **현저히 감소**한다. 포트 스캔 행위 자체는 Suricata IDS가 탐지하며, 5단계에서 AI가 스캐너 IP를 자동으로 차단한다.
{: .prompt-warning }

## 4. 실습: 서비스 및 버전 식별

개방된 포트를 확인하였으므로, 각 포트에서 **어떤 프로그램이 어떤 버전으로** 동작하는지 식별한다. 버전이 확인되면 **해당 버전에 알려진 취약점(CVE)** 을 즉시 조회할 수 있으므로, 이 단계는 공격의 성패를 좌우한다.

> ### 실습 4-1. 서비스·버전 탐지
>
> **목적** 개방된 포트에서 동작하는 서비스의 종류와 버전을 식별한다.
{: .prompt-tip }

```bash
sudo nmap -sV -p 22,3000 192.168.0.30
```

출력 예시는 다음과 같다.

```text
PORT     STATE SERVICE VERSION
22/tcp   open  ssh     OpenSSH 9.6p1 Ubuntu 3ubuntu13.5 (Ubuntu Linux; protocol 2.0)
3000/tcp open  ppp?
```

### 반드시 이해하여야 할 사항 — "포트 이름을 신뢰하지 말 것"

3000번 포트가 `ppp?` 로 식별된다. **이는 nmap의 오류가 아니라 "확정하지 못하였다"는 표시이다.** nmap은 3000번을 자체 사전상의 명칭에 근거하여 `ppp` 로 추정하였을 뿐, 실제로는 **Juice Shop 웹서버(HTTP)** 가 동작하고 있다. 물음표(`?`)는 "확신할 수 없음"을 의미한다.

**시사점** — 포트 스캐너가 부여한 서비스 명칭은 **추정값**이다. 실제 정체는 직접 검증하여야 한다. 따라서 웹 포트는 다음과 같이 **직접 요청을 전송하여** 확인한다.

> ### 실습 4-2. 웹 포트의 실제 정체 검증
>
> **목적** `ppp?` 로 식별된 3000번이 실제로 HTTP 웹서버인지 직접 검증한다.
{: .prompt-tip }

```bash
curl -I http://192.168.0.30:3000
```

출력 예시는 다음과 같다.

```text
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
X-Content-Type-Options: nosniff
X-Frame-Options: SAMEORIGIN
Feature-Policy: payment 'self'
Content-Type: text/html; charset=utf-8
...
```

`HTTP/1.1 200 OK` 가 수신되므로 3000번이 **HTTP 웹서버**임이 확정된다. (이 웹서버의 상세 취약점은 [1-3-3 웹 편](/posts/socbuild-03-3-recon-web/)에서 본격적으로 다룬다.)

### 명령과 옵션의 해설

| 옵션 | 의미 |
| --- | --- |
| `nmap -sV` | 서비스·버전 탐지(`V`ersion). 포트에 실제로 접속하여 배너·응답을 분석한다 |
| `-p 22,3000` | 앞서 식별한 개방 포트만 선별 검사(신속) |
| `curl -I` | HTTP **헤더만**(`-I` = HEAD 요청) 수신. 본문 없이 서버 정보를 신속히 확인한다 |

> **참고.** `nmap -sV -sC`(기본 스크립트 포함)는 다른 포트에는 유용하나, 3000번(비표준 HTTP)에서는 HTTP 관련 스크립트가 정상 실행되지 않아 결과가 부정확할 수 있다. 웹 포트의 상세 점검은 `nmap` 이 아니라 `curl`·`nikto`·브라우저로 수행하는 것이 정확하다(3편에서 진행).
{: .prompt-info }

### 공격자가 획득하는 정보

- **OpenSSH 9.6p1** 이라는 정확한 버전 → 해당 버전에 알려진 취약점을 조회하는 근거([1-3-2](/posts/socbuild-03-2-recon-system/)에서 `searchsploit` 로 확인)
- 3000번이 **HTTP 웹 애플리케이션**이라는 확정 → 웹 공격 대상 확정
- 서버 헤더에서 노출되는 부가 정보(`X-Frame-Options` 유무 등)

### 점검 항목 (서비스·버전)

- [ ] SSH 버전을 정확히 기록하였는가? (예: `OpenSSH 9.6p1`)
- [ ] 3000번이 HTTP임을 `curl` 로 직접 검증하였는가?
- [ ] 서비스가 **버전 정보를 불필요하게 노출**하고 있지 않은가? (버전 은닉은 방어의 기본이다)

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **버전 노출 자체는 방화벽으로 은닉할 수 없다** — 방화벽은 IP·포트(L3/L4)만 검사하며, 서비스가 송출하는 배너·헤더(응용 계층)는 관여하지 않는다. 그러나 **접근 자체를 차단하면** 버전을 조회할 수단이 사라진다. 즉 SSH(22)를 외부에서 차단하면 공격자는 SSH 버전을 파악할 방법을 잃는다. **배너를 실제로 수정하는 것은 서버 설정(예: SSH 배너 은닉)이나 3단계 WAF의 역할이다.** 이처럼 "방화벽으로 해결 가능한 것과 불가능한 것"을 구분하는 감각이 본 3부작의 핵심이다.
{: .prompt-warning }

## 5. (보강) 운영체제 및 UDP 정찰

여건이 되면 다음 두 가지를 추가로 확인한다. 결과 기록만으로 넘어가도 무방하다.

> ### 실습 5-1. 운영체제 추정
{: .prompt-tip }

```bash
sudo nmap -O 192.168.0.30
```

`-O`(대문자 O)는 TCP/IP 응답의 미세한 특성으로 **운영체제를 추정**한다. `Running: Linux 5.X` 와 같이 식별되면, 앞서 관측한 `ttl=64` 와 종합하여 표적이 **리눅스**임을 확정할 수 있다. 공격자는 이 정보에 근거하여 리눅스용 공격 기법에 집중한다. (WSL NAT 환경에서는 추정 정확도가 저하될 수 있다.)

> ### 실습 5-2. UDP 포트 탐색 (상위 20개)
{: .prompt-tip }

```bash
sudo nmap -sU --top-ports 20 192.168.0.30
```

지금까지의 포트 스캔(`-sS`)은 모두 **TCP** 를 대상으로 하였다. 그러나 DNS·SNMP 등 일부 서비스는 **UDP** 로 동작한다. `-sU`(UDP 스캔)는 저속이므로 `--top-ports 20`(최빈 20개)만 검사한다. 표적에 UDP 서비스가 없으면 대부분 `open|filtered`(불확정)로 식별되며, 이는 정상이다.

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **가능하다.** 운영체제 추정과 UDP 스캔은 모두 **표적으로 향하는 패킷**을 필요로 한다. OPNsense가 불필요한 포트·프로토콜을 차단하면 이러한 정찰의 재료 자체가 감소한다. 특히 잘못 개방된 UDP 서비스(예: SNMP 161)는 방화벽에서 차단하는 것이 정석이다.
{: .prompt-warning }

## 6. 결과 저장 — 증거 보존의 원칙

실무 취약점 점검은 반드시 **결과를 파일로 보존**한다. nmap은 저장 옵션을 제공한다.

```bash
sudo nmap -sS -sV -p- -T4 --open -Pn -oA scan_juice_20270622 192.168.0.30
```

| 옵션 | 의미 |
| --- | --- |
| `-oA 파일명` | 세 형식(`.nmap` 가독용, `.gnmap` grep용, `.xml` 도구연동용)으로 **일괄 저장** |

이렇게 보존한 결과는 2단계에서 방화벽 도입 후 **"before / after"** 비교에 그대로 활용된다. "무방비 상태의 개방 포트 N개 → 방화벽 도입 후 M개" 를 정량적으로 입증하게 된다.

## 7. 종합 — 네트워크 공격면 지도

> ### 🖼 필요 이미지 1
> Kali에서 `nmap -sV -p-` 결과가 표시된 터미널 전체 화면을 캡처하여 삽입한다. (개방 포트 목록이 본 강의의 핵심 산출물이다.)
{: .prompt-info }

본 강의에서 작성한 표적의 네트워크 공격면은 다음과 같다.

| 포트 | 서비스 | 실제 정체 | 후속 정밀 점검 |
| --- | --- | --- | --- |
| 22/tcp | ssh | OpenSSH (원격 접속) | [1-3-2 시스템 편](/posts/socbuild-03-2-recon-system/) |
| 3000/tcp | (ppp?) | 실제로는 HTTP = Juice Shop | [1-3-3 웹 편](/posts/socbuild-03-3-recon-web/) |

### 네트워크 계층 최종 점검표

- [ ] 표적이 가동 중이며 ICMP에 응답한다(무방비 = ICMP 미차단)
- [ ] 전 포트 스캔으로 개방 포트를 **누락 없이** 확인하였다
- [ ] 각 포트의 서비스·버전을 기록하였다
- [ ] 웹 포트(3000)의 정체를 `curl` 로 직접 검증하였다
- [ ] 스캔 결과를 파일(`-oA`)로 보존하였다

### 🛡 OPNsense를 통한 차단 가능성 — 네트워크 편 종합

| 정찰·공격 | 계층 | OPNsense 차단 | 방법 |
| --- | --- | --- | --- |
| ping(호스트 발견) | L3 | ✅ 가능 | ICMP 차단 규칙 |
| 핑 스윕(대역 탐색) | L3 | ✅ 가능 | 네트워크 분리(WAN↔LAN) |
| 포트 스캔 | L4 | ✅ **핵심 기능** | 필요 포트만 허용, 나머지 default deny |
| 서비스 버전 노출 | L7 | ⚠ 접근차단으로 우회 가능(배너 자체는 미은닉) | 포트 차단 + 서버 설정 |
| OS·UDP 정찰 | L3/L4 | ✅ 가능 | 불필요 프로토콜 차단 |

> **본 강의의 결론.** 네트워크 계층의 공격은 대부분 **방화벽(OPNsense)만으로도 상당 부분 차단할 수 있다.** 이것이 2단계에서 방화벽을 우선 도입하는 근거이다. 그러나 [1-3-3 웹 편](/posts/socbuild-03-3-recon-web/)에서 확인할 웹 계층 공격(SQLi·XSS)은 **방화벽으로 결코 차단할 수 없다.** 이 차이가 3단계(WAF)와 4·5단계(SIEM·AI)의 필요성을 규정한다.
{: .prompt-tip }
