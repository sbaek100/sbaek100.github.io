> **선행 강의 도달점** — [1-3-1 네트워크 편](/posts/socbuild-03-1-recon-network/) 에서 표적의 개방 포트를 전수 확인하였다. `22/tcp`(SSH)와 `3000/tcp`(Juice Shop, HTTP)가 개방되어 있음을 식별하였다.
> **본 강의의 목표** — 네트워크 편에서 식별한 **통로(포트) 이면의 잠금장치가 견고한지** 시스템 계층에서 점검한다. ① SSH의 인증 방식과 약한 비밀번호를 무차별 대입으로 관철하고, ② 서비스 버전에 결부된 알려진 취약점(CVE)을 조회하며, ③ 외부에 노출되어서는 안 될 관리 서비스가 존재하는지 확인한다.
> **준비 사항** — 공격자 Kali(WSL)와 표적 서버. 방어 장치는 여전히 부재하다.
{: .prompt-info }

> **⚠ 실습 범위 및 윤리.** 본 강의에서는 **비밀번호 무차별 대입(brute force)** 을 실습한다. 이는 **학습자 본인이 소유한 실습 표적(192.168.0.30)** 에 한하여 수행한다. 타인의 서버에 무차별 대입을 시도하는 행위는 명백한 **불법**이다. 실습 종료 후에는 표적 계정의 비밀번호를 견고한 것으로 변경하는 것이 바람직하다.
{: .prompt-danger }

> **💡 WSL Kali 주소 체계 복습.** Kali(WSL) 내부의 `ip a` 는 172.x로 표시되나, 표적의 관점에서 공격 발신지는 윈도우 호스트 IP(**192.168.0.10**)로 관측된다. 본 강의의 SSH 접속·무차별 대입은 모두 외부로 향하는 통신이므로 정상 동작한다. (상세 설명은 [1-3-1](/posts/socbuild-03-1-recon-network/) 참조.)
{: .prompt-info }

## 0. 실습 구성도

```text
[ 공격자 Kali (WSL) ]                     [ Ubuntu 미니 PC ] 192.168.0.30
   192.168.0.10                             ├─ 22/tcp  SSH   ← 본 강의의 주 공격 대상
        │  ①SSH 정찰 ②무차별 대입 ③CVE 조회    ├─ 3000/tcp HTTP (Juice Shop) ← 3편에서
        └──────────────────────────────────▶  └─ (노출된 관리 서비스가 존재하는가?)
```

> **"네트워크 = 어느 통로가 개방되었는가 / 시스템 = 그 통로의 잠금장치가 견고한가."** 본 강의에서는 개방된 통로(SSH)의 잠금장치를 직접 시험한다. 잠금장치가 취약하면(=약한 비밀번호) 공격자는 **서버 전체를 장악**한다. 웹 애플리케이션 하나가 아니라 서버 자체를 확보하는 것이므로, 시스템 취약점은 웹 취약점보다 한층 치명적이다.
{: .prompt-tip }

> **도구 확인.** 본 강의는 `hydra`·`searchsploit`(exploitdb)·워드리스트를 사용한다. [1-3-1의 실습 1-0](/posts/socbuild-03-1-recon-network/)에서 설치하지 않았다면 다음을 먼저 실행한다. (이미 설치된 경우 재실행하여도 무방하다.)
>
> ```bash
> sudo apt update && sudo apt install -y hydra exploitdb wordlists dirb nmap
> ```

## 1. 실습: SSH 심층 정찰

비밀번호를 시도하기에 앞서, SSH 서버가 **어떤 인증 방식**을 허용하는지 먼저 확인한다. 비밀번호 로그인이 비활성화되어 있다면 무차별 대입은 무의미하기 때문이다.

> ### 실습 1-1. SSH 호스트키·암호 알고리즘 확인
>
> **목적** SSH 서버의 종류·버전·지원 알고리즘을 파악한다.
{: .prompt-tip }

```bash
sudo nmap -p 22 --script ssh-hostkey,ssh2-enum-algos 192.168.0.30
```

출력 예시(요약)는 다음과 같다.

```text
22/tcp open  ssh
| ssh-hostkey:
|   256 aa:bb:cc:...  (ED25519)
|   3072 dd:ee:ff:... (RSA)
| ssh2-enum-algos:
|   kex_algorithms: (다수)
|   encryption_algorithms: (다수)
```

> ### 실습 1-2. 허용된 인증 방식 확인
>
> **목적** 해당 서버가 **비밀번호 로그인**을 허용하는지 확인한다.
{: .prompt-tip }

```bash
sudo nmap -p 22 --script ssh-auth-methods --script-args="ssh.user=student" 192.168.0.30
```

출력에 `password` 가 포함되면, **비밀번호 무차별 대입이 유효할 수 있음**을 의미한다.

```text
| ssh-auth-methods:
|   Supported authentication methods:
|     publickey
|     password        ← 이 항목이 존재하면 무차별 대입 가능
```

### 이 절차를 수행하는 이유

무차별 대입은 소음이 크고(다량의 로그를 생성하고) 시간을 요하는 공격이다. 따라서 공격자는 먼저 **성공 가능성**을 확인한다. `password` 인증이 활성화되어 있어야 시도할 가치가 있다. 만약 서버가 **공개키(publickey) 로그인만** 허용한다면 무차별 대입은 무의미하므로 다른 통로를 모색한다.

### 명령과 옵션의 해설

| 옵션 | 의미 |
| --- | --- |
| `--script ssh-hostkey` | 서버 호스트키 지문 수집 |
| `--script ssh2-enum-algos` | 지원 암호·키교환 알고리즘 열거(구식 취약 알고리즘의 활성화 여부 확인) |
| `--script ssh-auth-methods` | 허용된 인증 방식 확인 |
| `--script-args="ssh.user=student"` | 인증 방식 확인에 사용할 계정명 지정 |

### 공격자가 획득하는 정보

- **비밀번호 로그인 허용 여부** → 무차별 대입의 실행 결정
- 구식 취약 알고리즘의 사용 여부(중간자 공격 가능성 판단)
- SSH 버전(호스트키·배너)으로부터 **Ubuntu 릴리스** 추정

## 2. 실습: SSH 약한 비밀번호 무차별 대입 (hydra)

이제 실제로 잠금장치를 시험한다. **hydra** 는 Kali에 기본 포함된 로그인 무차별 대입 도구이다.

> ### 실습 2-1. 후보 비밀번호 목록 작성
>
> **목적** 시도할 비밀번호 사전(wordlist)을 준비한다.
{: .prompt-tip }

개념 확인을 위하여 **소규모 사전**을 직접 작성한다.

```bash
printf 'password\n123456\nubuntu\nadmin\nqwerty\nstudent1234\n' > pw.txt
cat pw.txt
```

> **`student1234` 를 포함한 이유.** 본 실습 표적은 [1-3](/posts/socbuild-03-victim-server-firstattack/) 에서 계정 `student` / 비밀번호 `student1234` 로 구성하였다. 즉 **의도적으로 취약하게 설정한 잠금장치**이다. 실제 공격자는 `student1234` 를 알 수 없으나, `rockyou.txt` 와 같은 수천만 개의 유출 비밀번호 사전으로 시도한다. 본 실습에서는 개념을 신속히 확인하기 위하여 소규모 사전을 사용한다.
{: .prompt-info }

실무에서 자주 사용되는 대형 사전은 Kali에 포함되어 있다(워드리스트 패키지 설치 시).

```bash
# rockyou.txt 는 압축되어 있어 최초 1회 해제하여야 한다(약 1,400만 개 비밀번호)
sudo gunzip -k /usr/share/wordlists/rockyou.txt.gz
wc -l /usr/share/wordlists/rockyou.txt
```

> `/usr/share/wordlists/rockyou.txt.gz` 가 존재하지 않으면 `sudo apt install -y wordlists` 를 먼저 실행한다.
{: .prompt-info }

> ### 실습 2-2. hydra를 이용한 SSH 무차별 대입
>
> **목적** `student` 계정의 비밀번호를 사전으로 순차 대입한다.
{: .prompt-tip }

```bash
hydra -l student -P pw.txt -t 4 -f -V ssh://192.168.0.30
```

성공 시 다음과 같이 **비밀번호가 식별**된다.

```text
[22][ssh] host: 192.168.0.30   login: student   password: student1234
[STATUS] attack finished for 192.168.0.30 (valid pair found)
```

### 이 공격을 수행하는 이유

SSH는 **서버로 진입하는 가장 직접적인 정문**이다. 웹 애플리케이션을 어렵게 관통하여 데이터 일부를 유출하는 것보다, SSH 로그인 하나가 성공하면 **서버 전체(파일·데이터베이스·타 서비스)** 를 일거에 확보한다. 이 때문에 약한 SSH 비밀번호는 실무에서 **가장 빈번하고 가장 치명적인** 침해 원인이다.

### 명령과 옵션의 해설

| 옵션 | 의미 |
| --- | --- |
| `hydra` | 네트워크 로그인 무차별 대입 도구 |
| `-l student` | 단일 계정명 지정(소문자 L). 다수 계정 시도는 `-L 파일` |
| `-P pw.txt` | 비밀번호 **목록 파일**(대문자 P). 단일 값은 `-p` |
| `-t 4` | 동시 시도 스레드 수 4(과도하면 서버가 연결을 차단한다) |
| `-f` | 유효한 쌍을 **최초 발견 시 즉시 종료**(fast) |
| `-V` | 시도하는 조합을 순차 표시(verbose) |
| `ssh://192.168.0.30` | 공격 대상 서비스와 IP(서비스 모듈 = ssh) |

### 공격자가 획득하는 정보

- **유효한 SSH 자격증명**(`student` / `student1234`)
- 이 자격증명을 통한 **서버 직접 로그인** → 서버 완전 장악의 발판

> ### 실습 2-3. 확보한 계정으로 실제 로그인 및 권한 확인
>
> **목적** 자격증명 하나가 왜 "서버 장악"에 해당하는지 직접 확인한다. (학습자 본인의 실습 표적에 한한다.)
{: .prompt-tip }

```bash
ssh student@192.168.0.30
# (비밀번호 student1234 입력)

# 로그인 후, 공격자가 통상 수행하는 확인 절차:
id                 # 자신의 권한 확인
sudo -l            # 관리자(root) 권한으로의 상승 가능 여부
cat /etc/passwd    # 계정 목록
sudo docker ps     # 동작 중인 컨테이너(Juice Shop) 확인
```

`sudo -l` 에서 `student` 가 `sudo` 를 사용할 수 있다면, 공격자는 **root(관리자)** 로 상승하여 서버를 완전히 지배한다. 웹 애플리케이션 데이터에 국한되지 않고 **로그 삭제, 백도어 설치, 타 장비로의 횡적 이동**까지 가능해진다.

### 점검 항목 (SSH)

- [ ] SSH가 **비밀번호 로그인**을 허용하는가? (허용 = 무차별 대입 위험)
- [ ] `root` 직접 로그인이 허용되어 있지 않은가? (`PermitRootLogin`)
- [ ] 계정 비밀번호가 사전에 존재할 만큼 취약하지 않은가?
- [ ] 로그인 실패 횟수 제한(fail2ban 등)이 부재하지 않은가?

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **네트워크 위치에 의하여 상당 부분 차단 가능하다.** 후속 단계에서 Kali는 방화벽의 외부(WAN)에 배치된다. 이때 OPNsense에서 **"외부에서 표적의 22번(SSH)으로 향하는 접속을 전면 차단"** 할 수 있다. 관리자는 내부(LAN)에서만 SSH를 사용하고, 외부 공격자는 SSH 포트에 도달하지 못한다. 무차별 대입 시도는 Suricata IDS가 "단시간 내 반복되는 SSH 접속 실패"로 탐지하며, 5단계에서 AI가 해당 IP를 자동 차단한다.
> **다만 유의할 점**은, 본 강의처럼 공격자와 표적이 **동일 LAN(방화벽 부재)** 에 위치하면 방화벽으로 차단할 수 없다는 것이다. 따라서 **약한 비밀번호를 견고하게 변경하고 공개키 인증만 허용**하는 서버 자체의 방어가 방화벽만큼 중요하다. ("방화벽으로 해결 가능한 것과 불가능한 것"의 구분!)
{: .prompt-warning }

## 3. 실습: 서비스 버전에 결부된 알려진 취약점(CVE) 조회

[1-3-1](/posts/socbuild-03-1-recon-network/) 에서 확보한 **정확한 버전**(예: `OpenSSH 9.6p1`)은 그 자체로 공격 재료이다. 공개된 취약점·공격코드(exploit)를 버전으로 조회할 수 있기 때문이다.

> ### 실습 3-1. searchsploit을 이용한 공개 취약점 조회
>
> **목적** 표적이 사용하는 서비스 버전에 알려진 공개 취약점·공격코드가 존재하는지 확인한다.
{: .prompt-tip }

```bash
# 로컬 취약점 DB 최신화(최초 1회)
searchsploit --update

# SSH 버전으로 조회
searchsploit openssh 9.6
searchsploit openssh
```

출력 형식은 다음과 같다.

```text
--------------------------------------------- ---------------------------------
 Exploit Title                               |  Path
--------------------------------------------- ---------------------------------
 OpenSSH <X.Y> - Username Enumeration        | linux/remote/xxxxx.py
 ...
--------------------------------------------- ---------------------------------
```

### 이 절차를 수행하는 이유

취약점을 **처음부터 고안할 필요가 없다.** 이미 공개된 CVE와 공격코드가 다수 존재한다. 공격자는 "표적 버전 = 공개 취약점"을 대응시켜 **가장 용이한 침투 경로**를 탐색한다. 이를 *알려진 취약점 악용(known-vulnerability exploitation)* 이라 한다.

### 명령과 옵션의 해설

| 명령                         | 의미                                               |
| -------------------------- | ------------------------------------------------ |
| `searchsploit`             | Exploit-DB의 공개 취약점·공격코드를 **오프라인**으로 조회하는 Kali 도구 |
| `searchsploit --update`    | 로컬 취약점 DB 최신화                                    |
| `searchsploit openssh 9.6` | 제목·버전에 "openssh 9.6"이 포함된 항목 조회                  |
| `searchsploit -x 경로`       | 조회된 공격코드의 내용 열람                                  |

> **중요 — 조회 결과가 곧 즉시 침투를 의미하지는 않는다.** searchsploit에 항목이 표시되어도 즉시 관통되는 것은 아니다. ① 버전이 정확히 일치하여야 하고, ② 취약점의 유형(원격 코드 실행인지, 단순 정보 노출인지)을 확인하여야 하며, ③ 다수의 공개 코드는 특정 조건에서만 동작한다. **방어자 관점의 핵심은 "자사 서비스 버전에 심각한 CVE가 존재하는가 → 존재 시 즉시 패치"** 이다.
{: .prompt-info }

### 공격자가 획득하는 정보

- 표적 버전에 **즉시 활용 가능한 공격코드**의 존재 여부
- 취약점 심각도에 따른 **원격 코드 실행(서버 장악)** 가능성 판단

### 점검 항목 (버전 취약점)

- [ ] 각 서비스(SSH·웹서버 등)의 정확한 버전을 확보하였는가?
- [ ] 해당 버전에 **심각도 높은 CVE**(원격 코드 실행 등)가 존재하는가?
- [ ] 표적 OS·서비스가 **최신 보안 패치** 상태인가? (`sudo apt update && sudo apt upgrade`)

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **간접적으로만 가능하다.** CVE는 "서비스 소프트웨어의 결함"이므로 근본 해결책은 **패치**이다(방화벽은 결함 있는 코드를 수정하지 못한다). 다만 OPNsense가 **해당 서비스로의 접근을 차단**하면 공격자가 취약점에 도달하지 못하게 할 수 있고, Suricata IDS는 잘 알려진 CVE 공격 패턴을 **시그니처로 탐지**한다. 즉 "패치(근본) + 방화벽 접근차단(범위 축소) + IDS 탐지"의 3중 방어이다.
{: .prompt-warning }

## 4. 실습: 노출된 관리 서비스 점검

실무 침해의 상당수는 정교한 공격이 아니라 **"개방하여서는 안 될 것을 개방한"** 설정 실수에서 비롯된다. 대표적으로 **Docker 원격 API** 와 노출된 **데이터베이스 포트**가 있다.

> ### 실습 4-1. 위험한 관리 포트의 개방 여부 확인
>
> **목적** 외부 노출 시 즉시 서버 장악으로 이어지는 포트들을 점검한다.
{: .prompt-tip }

```bash
sudo nmap -p 2375,2376,3306,5432,6379,27017 192.168.0.30
```

| 포트 | 서비스 | 노출 시 위험 |
| --- | --- | --- |
| 2375 | Docker API(비암호화) | **인증 없이 컨테이너·호스트 완전 장악** |
| 2376 | Docker API(TLS) | 인증서 부재 시 상동 |
| 3306 | MySQL/MariaDB | DB 직접 접근 |
| 5432 | PostgreSQL | DB 직접 접근 |
| 6379 | Redis | 인증 부재 시 데이터 탈취·RCE |
| 27017 | MongoDB | DB 직접 접근 |

본 실습 표적은 이 포트들이 **모두 폐쇄(closed/filtered)** 되어 있어야 정상이다.

> ### 실습 4-2. Docker API의 폐쇄 여부 직접 검증
{: .prompt-tip }

```bash
curl -s http://192.168.0.30:2375/version
```

연결이 거부되면(무응답/refused) **안전**하다. 만약 JSON 형식으로 Docker 버전이 수신된다면 이는 **심각한 사고**이다.

### 이 절차를 수행하는 이유 / 공격자가 획득하는 정보

본 실습 표적은 [1-3](/posts/socbuild-03-victim-server-firstattack/) 에서 Juice Shop을 다음과 같이 기동하였다.

```text
sudo docker run -d --restart unless-stopped -p 3000:3000 --name juice-shop bkimminich/juice-shop
```

여기서 `-p 3000:3000` 은 **3000번만** 외부로 개방한다. Docker 관리 API(2375)는 기본적으로 유닉스 소켓으로만 동작하며 외부에 노출되지 않으므로 **안전**하다. 본 점검은 "자사 설정의 안전성 확인"인 동시에, **관리 서비스 노출이 왜 위험한지**를 학습하는 단계이다. (공격자는 2375가 개방된 서버를 발견하면 인증 없이 새 컨테이너를 기동하여 호스트 파일시스템을 마운트하고 서버를 장악한다.)

### 점검 항목 (노출 서비스)

- [ ] Docker API(2375/2376)가 **폐쇄**되어 있는가?
- [ ] DB 포트(3306/5432/6379/27017)가 외부에 노출되지 않았는가?
- [ ] 웹 애플리케이션이 사용하는 포트(3000) **외에** 불필요한 포트가 개방되어 있지 않은가?

> ### 🛡 OPNsense를 통한 차단 가능성
>
> **가능하며, 매우 효과적이다.** 설령 서버 관리자가 실수로 Docker API나 DB 포트를 개방하더라도, OPNsense가 **"필요한 포트(3000)만 허용, 나머지 전면 차단"** 정책을 적용하고 있으면 외부 공격자는 해당 포트에 도달하지 못한다. 방화벽의 **default deny** 정책이 "설정 실수를 보완하는 안전망" 역할을 하는 대표적 사례이다. 물론 근본적으로는 **서버에서 해당 포트를 애초에 개방하지 않는 것**이 우선이다(다중 방어).
{: .prompt-warning }

## 5. (보강) 시스템이 자체적으로 노출하는 정보

공격자는 서비스가 무심코 송출하는 배너·헤더로부터도 정보를 수집한다.

```bash
# SSH 배너에는 Ubuntu 릴리스가 그대로 포함된다
sudo nmap -p 22 -sV 192.168.0.30 | grep -i ubuntu
```

`OpenSSH 9.6p1 Ubuntu 3ubuntu13.5` 와 같은 배너는 **정확한 Ubuntu 릴리스**를 노출한다. 공격자는 이 릴리스에 결부된 커널·라이브러리 CVE로 공격 범위를 좁힌다. 방어자는 **불필요한 버전 노출을 축소(하드닝)하고 최신 패치를 유지**하여야 한다.

## 6. 종합 — 시스템 공격면과 방어 대응

> ### 🖼 필요 이미지 1
> hydra가 `login: student   password: student1234` 를 식별한 터미널 화면을 캡처하여 삽입한다. (본 강의의 핵심 결과이다.)
{: .prompt-info }

### 시스템 계층 최종 점검표

- [ ] SSH 비밀번호 로그인 허용 여부와 강도를 점검하였다
- [ ] hydra로 약한 비밀번호가 실제로 관철되는 것을 확인하였다
- [ ] 서비스 버전에 결부된 CVE를 `searchsploit` 으로 조사하였다
- [ ] 노출되어서는 안 될 관리 포트(Docker/DB)가 폐쇄되어 있음을 확인하였다
- [ ] 표적이 최신 보안 패치 상태인지 확인하였다

### 🛡 OPNsense를 통한 차단 가능성 — 시스템 편 종합

| 공격 | 계층 | OPNsense 차단 | 방법 / 추가 요구사항 |
| --- | --- | --- | --- |
| SSH 무차별 대입 | L4(접근) + 인증 | ✅ 접근차단 / ⚠ 동일 LAN에서는 불가 | WAN→22 차단, IDS로 반복실패 탐지 **+ 강한 비밀번호·공개키(서버 방어)** |
| 알려진 CVE 악용 | 서비스 코드 | ⚠ 접근차단으로 범위 축소 | **패치가 근본**, IDS 시그니처 탐지 |
| 노출된 관리 서비스(Docker/DB) | L4 | ✅ 매우 효과적 | 필요 포트만 허용(default deny) |
| 버전·배너 정보 노출 | L7 | ✖ 방화벽은 미은닉 | 서버 하드닝(배너 은닉) |

> **본 강의의 결론.** 시스템 공격은 **"방화벽(접근 차단) + 서버 자체 방어(강한 인증·패치·하드닝)"** 가 병행되어야 차단된다. 방화벽 단독으로는 부족하다. 특히 무차별 대입은 동일 네트워크 내에서는 방화벽으로 차단할 수 없으므로, **약한 비밀번호의 제거**가 제1의 방어선이다. 다음 편에서는 방화벽이 **거의 관여하지 못하는** 웹 계층 공격으로 진입한다.
{: .prompt-tip }
