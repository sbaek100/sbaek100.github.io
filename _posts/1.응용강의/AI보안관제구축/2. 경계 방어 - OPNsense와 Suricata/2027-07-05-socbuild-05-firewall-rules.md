> 지난 시간 도달 상태: OPNsense가 Kali(57.10)와 victim(59.20) 사이에 놓였습니다. 다만 관리망(LAN)은 기본 허용이었고, 표적망(OPT1)에도 통신을 살리려고 **임시로 활짝 여는 규칙**을 넣어 둔 상태라 **공격이 여전히 통했습니다.**
> 오늘의 목표: 양쪽 모두 **"필요한 것만 허용, 나머지는 차단"** 으로 바꿔, 재실행하는 nmap에서 웹 포트(3000) 외에는 모두 막히는 것을 확인합니다.
> 오늘 켜는 VM: **OPNsense + Kali + victim**.
{: .prompt-info }

## 1. 이론: 최소 권한(화이트리스트) 원칙

방화벽 규칙에는 두 가지 철학이 있습니다.

| 방식 | 설명 | 안전성 |
| --- | --- | --- |
| 블랙리스트 | "위험한 것만 골라 막고 나머지는 허용" | 낮음 — 빠뜨린 위험은 다 통과 |
| **화이트리스트(최소 허용)** | "꼭 필요한 것만 허용하고 나머지는 전부 차단" | 높음 — 실무 표준 |

우리 표적 서버가 외부에 제공해야 하는 것은 **웹(포트 3000)** 하나뿐입니다. 그러므로 규칙은 이렇게 정합니다.

- 공격자망 → 표적 서버 **3000 포트만 허용**
- 그 외 표적 서버로 향하는 모든 접근(22/SSH, ping 등) **차단**
- 표적 서버가 **바깥으로 나가는 것**도 업데이트에 꼭 필요한 것만 남기고, 특히 **공격자망 쪽으로 되돌아가는 길은 차단**

> **규칙은 위에서 아래로, 첫 번째로 맞는 규칙이 적용됩니다.** 그래서 "허용" 규칙을 위에, "차단" 규칙을 그 아래 두는 순서가 중요합니다.
{: .prompt-tip }

> **나가는 방향까지 막는 이유** — 표적 서버가 뚫린 뒤, 공격자가 그 서버를 발판 삼아 **다른 망으로 옮겨 다니는 것**을 막기 위해서입니다. 이를 **피벗(pivoting)** 이라고 합니다. DMZ에 놓인 서버는 "들어오는 것"만큼이나 "나가는 것"을 좁게 두는 것이 실무 원칙입니다.
{: .prompt-info }

## 2. 따라 하기: 표적 서버 별칭(Alias) 만들기

IP·포트를 규칙마다 직접 쓰는 대신, **별칭(Alias)** 으로 이름을 붙여 두면 관리가 쉽습니다.

> ### 따라 하기 2-1. victim 별칭 등록
>
> **목적** 표적 서버 주소에 이름을 붙입니다.
{: .prompt-tip }

**1단계.** Kali 브라우저에서 OPNsense(`https://192.168.57.1`) 로그인 → 상단 메뉴 **Firewall → Aliases** → **+ Add**.

| 항목 | 값 |
| --- | --- |
| Name | **`victim_host`** |
| Type | Host(s) |
| Content | `192.168.59.20` |
| Description | 표적 서버 |
![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787620228849.png)


**2단계.** **Save** 를 누릅니다. 이어서 **+ Add** 로 포트 별칭도 만듭니다.

| 항목 | 값 |
| --- | --- |
| Name | **`web_ports`** |
| Type | Port(s) |
| Content | `3000` |
| Description | 표적 웹 포트 |
![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787620270882.png)

**3단계.** 한 번 더 **+ Add** 로, 표적 서버가 **나갈 때** 쓸 포트 별칭을 만듭니다.

| 항목 | 값 |
| --- | --- |
| Name | **`dmz_out_ports`** |
| Type | Port(s) |
| Content | `80`, `443` (한 줄에 하나씩) |
| Description | 표적 서버가 나갈 때 쓰는 포트 |
![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787620353534.png)

**4단계.** 목록 아래쪽 **`Apply`** 를 눌러 별칭을 적용합니다.

![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787620413411.png)

## 3. 따라 하기: LAN 규칙 다시 짜기

Kali는 OPNsense의 **LAN** 인터페이스(2-1 매핑표)에 있습니다. 여기에 규칙을 추가해 표적망(soc-dmz) 접근을 통제합니다.

> ### 따라 하기 3-1. 웹만 허용하는 규칙 (맨 위)
>
> **목적** 공격자망 → 표적 3000 포트만 통과시킵니다.
{: .prompt-tip }

**1단계.** **Firewall → Rules** 로 가서 왼쪽 위 드롭다운에서 **`LAN`** 을 고릅니다. `Interface rules` 묶음에 **LAN 기본 허용 규칙(IPv4·IPv6)** 이 이미 들어 있습니다 — 2-1에서 GUI 접속을 가능하게 해 준 그 규칙입니다. 목록 **오른쪽 아래 주황색 `+`** 를 누릅니다.

![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787620463109.png)

| 항목 | 값 |
| --- | --- |
| Action | **Pass** |
| Interface | LAN |
| Direction | in |
| Protocol | **TCP** |
| Source | LAN net |
| Destination | **`victim_host`** (별칭 이름을 입력하면 자동완성) |
| Destination Port | **`web_ports`** (별칭 이름을 입력하면 목록에 나타납니다) |
| Description | 표적 웹 허용 |

![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787620642871.png)

**Save** 를 누릅니다.

> **포트 칸 쓰는 법** — 이 칸은 **하나뿐**입니다. 드롭다운의 `Single port or range` 는 "직접 입력 모드"라는 뜻이고, 그 아래 칸에 값을 적으면 됩니다.
>
> | 넣고 싶은 것 | 입력 방법 |
> | --- | --- |
> | 포트 하나 | `53` — 숫자만 |
> | 포트 범위 | `8000-8100` — **하이픈**으로 시작-끝 |
> | 잘 알려진 서비스 | 드롭다운에 있는 `DNS`·`HTTP`·`HTTPS` 등을 선택 |
> | 별칭 | 만들어 둔 이름(`web_ports` 등)을 입력하면 목록에 나타남 |
>
> **여기서 별칭이 왜 필요한지가 드러납니다.** `80`과 `443`처럼 **떨어져 있는 포트 두 개는 범위로 쓸 수 없습니다.** `80-443` 이라고 적으면 그 사이 360여 개 포트가 전부 열려 버립니다. 그래서 별칭에 두 포트를 각각 넣어 두고, 규칙에는 별칭 이름 하나만 적는 것입니다.
{: .prompt-tip }

> ### 따라 하기 3-2. 나머지 표적 접근 차단 (그 아래)
>
> **목적** 3000을 제외한 모든 표적 접근을 막습니다.
{: .prompt-tip }

**2단계.** 다시 **+ Add** 로 규칙을 하나 더 만듭니다.

| 항목 | 값 |
| --- | --- |
| Action | **Block** |
| Interface | LAN |
| Direction | in |
| Protocol | any |
| Source | LAN net |
| Destination | **`victim_host`** |
| **Log** | **체크** (차단 기록을 남김) |
| Description | 표적 그 외 전부 차단 |

**3단계.** 순서를 맞춥니다. 새로 만든 규칙은 목록 **맨 아래**에 붙습니다. 그런데 그 위에는 2-1부터 있던 **LAN 기본 허용 규칙**이 있고, **먼저 맞는 규칙이 이기므로** 그대로 두면 우리 규칙은 한 번도 쓰이지 않습니다. 각 줄 왼쪽 손잡이를 **드래그**하거나 오른쪽 `Commands` 열의 **화살표 아이콘**으로 다음 순서를 만듭니다.

| 순서  | 규칙                       |
| --- | ------------------------ |
| 1   | **표적 웹 허용** (Pass, 3000) |
| 2   | **표적 그 외 전부 차단** (Block) |
| 3   | LAN 기본 허용 규칙 (그대로 둠)     |


![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787620991973.png)

**4단계.** 목록 아래쪽 주황색 **`Apply`** 버튼을 눌러 적용합니다.

> **여기가 오늘 실습에서 가장 자주 틀리는 곳입니다.** 규칙을 아무리 잘 만들어도 기본 허용 규칙 아래에 있으면 아무 일도 일어나지 않습니다. 적용 후 `ping` 이 여전히 되면 십중팔구 순서 문제입니다.
{: .prompt-warning }


> 맨 아래 기본 허용 규칙은 **지우지 않고 그대로 둡니다.** 덕분에 Kali의 인터넷·DNS·OPNsense 관리 접속이 계속 됩니다. 우리가 위에 얹은 두 규칙이 **표적으로 가는 트래픽만** 먼저 걸러 내는 구조입니다.
{: .prompt-info }

## 4. 따라 하기: 표적망(OPT1) 규칙 조이기

2-1에서는 표적망이 아예 통신을 못 하기에, OPT1에 **"전부 허용"** 규칙을 임시로 하나 넣어 두었습니다. 오늘 그것을 걷어내고 꼭 필요한 것만 남깁니다.

> ### 따라 하기 4-1. 되돌아가는 길 차단 (맨 위)
>
> **목적** 표적 서버가 뚫려도 공격자망 쪽으로 옮겨 가지 못하게 합니다.
{: .prompt-tip }

**1단계.** **Firewall → Rules** → 왼쪽 위 드롭다운에서 **`OPT1`** 선택 → 목록 오른쪽 아래 주황색 **`+`**:

| 항목 | 값 |
| --- | --- |
| Action | **Block** |
| Interface | OPT1 |
| Direction | in |
| Protocol | any |
| Source | **OPT1 net** |
| Destination | **LAN net** |
| **Log** | **체크** |
| Description | `disallow target->attacker` |
![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787621099015.png)


**Save** 를 누릅니다.

> **여기서 가장 헷갈리는 점** — 이 규칙을 넣어도 **Kali에서 웹 접속은 계속 됩니다.** 방화벽이 **상태 기반**(2-1 이론)이기 때문입니다. Kali가 먼저 보낸 요청은 하나의 "연결"로 기억되고, 그 **응답**은 새로운 접속이 아니라 기존 연결의 일부로 자동 허용됩니다. 이 규칙이 막는 것은 **표적 서버가 스스로 먼저 거는 접속**입니다.
{: .prompt-tip }

> ### 따라 하기 4-2. 이름 풀이와 업데이트만 열어 주기
>
> **목적** 표적 서버가 살아가는 데 꼭 필요한 두 가지만 남깁니다.
{: .prompt-tip }

**2단계.** **+ Add** 로 이름 풀이(DNS) 규칙을 만듭니다.

| 항목               | 값                                |
| ---------------- | -------------------------------- |
| Action           | Pass                             |
| Interface        | OPT1                             |
| Direction        | in                               |
| Protocol         | **TCP/UDP**                      |
| Source           | OPT1 net                         |
| Destination      | **This Firewall**                |
| Destination Port | **`53`** (또는 드롭다운에서 `DOMAIN` 선택) |
| Description      | `Resolve Target Name`            |

![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787621344413.png)

> 프로토콜을 `UDP` 가 아니라 **`TCP/UDP`** 로 두는 이유는, 응답이 길면 DNS가 TCP로 다시 물어보기 때문입니다. 목적지 **This Firewall** 은 방화벽 자신의 주소 전체를 뜻하며, 표적이 실제로 쓰는 것은 자기 게이트웨이인 **59.1** 입니다.
{: .prompt-tip }

**3단계.** **+ Add** 로, 표적이 **방화벽 자신을 건드리지 못하게** 막는 규칙을 만듭니다.

| 항목 | 값 |
| --- | --- |
| Action | **Block** |
| Interface | OPT1 |
| Direction | in |
| Protocol | any |
| Source | OPT1 net |
| Destination | **This Firewall** |
| **Log** | **체크** |
| Description | `Disallow from target to fw` |

> 바로 위 DNS 허용 규칙보다 **아래**에 두어야 합니다. 그래야 이름 풀이(53)는 통과하고, 나머지(특히 관리 화면 443)는 막힙니다. 이 규칙이 없으면 표적 서버에서 `https://192.168.59.1` 로 **방화벽 관리 화면에 접속할 수 있습니다.** 뚫린 DMZ 서버가 방화벽까지 손대는 일은 반드시 막아야 합니다.
{: .prompt-warning }

**4단계.** 마지막으로 **+ Add** 로 업데이트 규칙을 만듭니다.

| 항목 | 값 |
| --- | --- |
| Action | Pass |
| Interface | OPT1 |
| Direction | in |
| Protocol | TCP |
| Source | OPT1 net |
| Destination | any |
| Destination Port | **`dmz_out_ports`** (별칭) |
| Description | `update https/http` |

> **시간 맞추기(NTP, UDP 123)는 일부러 지금 열지 않습니다.** 4단계에서 SIEM이 여러 장비의 로그를 시각으로 엮을 때 필요해지므로, 그때 같은 방식으로 규칙을 한 줄 더 추가합니다. 지금은 "필요해질 때 하나씩 연다"는 원칙을 그대로 따라가는 것이 중요합니다.
{: .prompt-info }

> ### 따라 하기 4-3. 임시 규칙 걷어내기
>
> **목적** 2-1에서 넣은 "전부 허용"을 없앱니다.
{: .prompt-tip }

**5단계.** OPT1 목록에서 Description이 **`OPT1 default allow`** 인 규칙(2-1에서 임시로 넣은 "전부 허용")을 찾아 오른쪽 **🗑 휴지통 아이콘**으로 삭제합니다.

> **이 줄을 지우지 않으면 오늘 만든 규칙이 전부 무효입니다.** 출발지 OPT1 network → 목적지 `*` 를 통과시키는 규칙이 맨 위에 있으면, 방화벽은 거기서 판단을 끝내고 아래 네 줄을 읽지 않습니다. 지우기가 아깝다면 왼쪽 체크박스를 해제해 비활성으로 두어도 결과는 같습니다.
{: .prompt-warning }

**6단계.** 남은 네 규칙을 드래그해 아래 순서로 맞춘 뒤, 목록 아래쪽 주황색 **`Apply`** 를 누릅니다.

| 순서 | 규칙 | 하는 일 |
| --- | --- | --- |
| 1 | Block · OPT1 net → LAN net | 공격자망으로 되돌아가는 길 차단(피벗) |
| 2 | Pass · OPT1 net → This Firewall · 53 | 이름 풀이만 허용 |
| 3 | Block · OPT1 net → This Firewall | 방화벽 자신에 대한 나머지 접근 차단 |
| 4 | Pass · OPT1 net → any · 80/443 | 업데이트만 허용 |

> 2번이 3번보다 **위**에 있어야 DNS가 살아남습니다. 순서가 뒤바뀌면 `apt update` 부터 실패합니다.
{: .prompt-warning }


![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787621830847.png)



> ### 따라 하기 4-4. 표적 서버에서 확인
>
> **목적** 조인 결과를 표적 쪽에서 직접 봅니다.
{: .prompt-tip }

**7단계.** victim 터미널에서 2-1에는 되던 것을 해 봅니다.

```bash
ping -c 2 8.8.8.8
```

이제 **응답이 오지 않습니다.** ICMP는 우리가 열어 둔 목록(53·80·443)에 없기 때문입니다. "조인다"는 것이 이런 뜻입니다.

**8단계.** 반대로 꼭 필요한 것은 되는지 봅니다.

```bash
sudo apt update
```

목록을 정상적으로 받아 옵니다. **이름 풀이(53)와 내려받기(80·443)만** 열어 두었기 때문입니다.

![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787621931404.png)

**9단계.** 피벗 차단과 관리 화면 차단도 확인합니다.

```bash
ping -c 2 192.168.57.10
curl -sk --max-time 5 https://192.168.59.1 -o /dev/null -w "%{http_code}
"
```

![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787622012128.png)

첫 명령은 막히고(표적 서버에서 공격자망으로 넘어갈 수 없음), 둘째 명령도 응답 없이 끝납니다(표적 서버에서 방화벽 관리 화면에 닿을 수 없음). 두 시도 모두 **Log** 를 켜 두었으므로 방화벽 로그에 남습니다.

## 5. 따라 하기: 같은 공격 다시 실행 (차단 확인)

이제 1단계·2-1에서 통했던 공격을 다시 실행해 결과가 어떻게 달라지는지 봅니다. (ping이 막히므로 nmap에는 `-Pn` 을 붙입니다.)

> ### 따라 하기 5-1. ping — 이제 막힘
{: .prompt-tip }

**1단계.** Kali 터미널:

```bash
ping -c 3 192.168.59.20
```

응답이 **오지 않습니다**(100% packet loss). ICMP는 3000 포트가 아니므로 차단 규칙에 걸립니다.

> ### 따라 하기 5-2. nmap — 3000만 열림
{: .prompt-tip }

**2단계.** 포트 스캔을 다시 합니다. (`-Pn`은 ping이 막혀도 스캔하도록 하는 옵션입니다.)

```bash
nmap -Pn -p 22,3000 192.168.59.20
```

결과가 1단계와 달라집니다.

```text
PORT     STATE     SERVICE
22/tcp   filtered  ssh      ← 차단됨(응답 없음)
3000/tcp open      ppp      ← 허용된 웹(HTTP)만 열림
```

> `-sV` 없이 스캔하면 nmap은 포트 번호로 서비스 이름을 짐작만 하므로, 3000이 `ppp` 로 표시됩니다. 이름표일 뿐 실제로는 HTTP(Juice Shop)라는 점은 1단계에서 설명했습니다.
{: .prompt-info }

![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787622100807.png)


**3단계.** 웹은 여전히 되는지 확인합니다.

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.59.20:3000
```

`200` 이 나옵니다. **서비스는 정상, 나머지 문은 닫힘** — 방화벽이 제 역할을 합니다.

![](/assets/img/posts/2027-07-05-socbuild-05-firewall-rules-1787622140508.png)

## 7. before / after 비교

| 시도 | 1단계(무방비) | 2-1(방화벽만 통과) | 2-2(규칙 적용) |
| --- | --- | --- | --- |
| ping 59.20 | 응답 | 응답 | **차단** |
| nmap 22/ssh | open | open | **filtered(차단)** |
| nmap 3000/web | open | open | open(허용) |
| 웹 접속 | 성공 | 성공 | 성공 |
| victim → `ping 8.8.8.8` | 성공 | 성공 | **차단** |
| victim → `apt update` | 성공 | 성공 | 성공(필요해서 열어 둠) |
| victim → 공격자망(57.10) | 성공 | 성공 | **차단(피벗 차단)** |
| victim → 방화벽 관리화면(59.1:443) | — | 접속 가능 | **차단** |

방화벽 규칙으로 **공격 표면(열린 문)** 이 크게 줄었습니다. 하지만 아직 **허용된 3000 포트로 들어오는 웹 공격(SQLi 등)** 은 그대로 통합니다. 방화벽은 "포트"는 보지만 "내용"은 보지 않기 때문입니다. 이것이 다음 시간 Suricata(IDS)가 필요한 이유입니다.

## 8. 스냅샷과 점검

OPNsense 스냅샷을 `fw-rules` 로 저장합니다.

- [ ] `victim_host` · `web_ports` · `dmz_out_ports` 별칭을 만들었다
- [ ] LAN에 **웹 허용(위) → 그 외 차단(아래)** 순서로 규칙을 넣었다
- [ ] OPT1에서 "전부 허용" 임시 규칙을 지우고 **네 규칙(피벗 차단·DNS·방화벽 접근 차단·업데이트)** 을 순서대로 남겼다
- [ ] victim에서 `apt update` 는 되고 `ping 8.8.8.8` 과 `ping 192.168.57.10` 은 막힌다
- [ ] `ping 59.20` 이 차단된다
- [ ] `nmap` 에서 3000만 open, 22는 filtered 다
- [ ] `curl ...:3000` 은 여전히 200 이다
- [ ] Firewall Live View에서 차단 로그를 확인했다
