## 1. 채널(Channels)과 고객 관계(Customer Relationships)

### 1.1 왜 두 블록을 함께 보는가

채널은 "어떤 경로로 고객에게 가치를 전달할 것인가"를 묻고, 고객 관계는 "고객과 어떤 관계를 맺을 것인가"를 묻는다. 이 둘은 함께 생각하는 것이 자연스럽다 — 채널이 정해지면 가능한 관계 방식이 달라지고, 원하는 관계 방식이 있으면 적합한 채널이 달라지기 때문이다.

### 1.2 채널의 범위

채널은 "앱이냐 웹이냐"의 선택만을 뜻하지 않는다. 더 넓게 다음을 포함한다.

- 고객이 **처음 알게 되는** 경로 (예: 이메일 공지, 학교 게시판)
- 고객이 **실제로 사용하는** 경로 (예: 웹사이트, 학습 관리 시스템)
- 고객이 **도움을 받는** 경로 (예: 문의 채널)

채널을 고를 때는 다음 네 가지 질문이 유용하다.

1. 고객이 가장 자주 접근하는 곳은 어디인가?
2. 처음 접했을 때 진입 장벽이 낮은가?
3. 우리 팀이 실제로 구현 가능한 방식인가?
4. 사용 후 다시 돌아오게 만들 수 있는가?

예컨대 학생 대상 학습 서비스라면 웹은 접근이 쉽고, 학교 학습 관리 시스템(LMS)은 수업 연계성이 좋으며, 모바일 앱은 반복 방문 유도에 유리하지만 개발 부담이 크다. 즉 **채널 선택은 기술 선호가 아니라 고객 접근성과 구현 현실성의 문제**이다.

### 1.3 고객 관계의 유형

| 유형 | 예시 |
|---|---|
| 일회성 사용 | 특정 정보 조회 |
| 반복 사용 | 일정 관리, 학습 서비스 |
| 피드백 기반 | 퀴즈, 추천, 개인화 학습 |
| 지원 기반 | 상담, 멘토링, 관리자 응답 |

학습 서비스인데 한 번 사용 후 다시 돌아올 이유가 없다면 고객 관계 설계가 약한 것이다.

### 1.4 작성 예시 — 피싱 메일 판별 학습 서비스

| 블록 | 내용 | 근거 |
|---|---|---|
| 채널 | 웹 학습 페이지, 학교 LMS, 학교 포털 | 대학생의 접근성이 높고 구현 부담이 낮다 |
| 고객 관계 | 퀴즈 결과 피드백, 반복 학습, 학기별 교육 연계 | 보안 지식은 한 번 듣고 끝나는 것보다 반복 확인이 중요하다 |

### 실습 1.1

자신의 프로젝트에 대해 다음 세 줄을 작성하라.

```text
고객이 처음 이 서비스를 알게 되는 경로: {                      }
고객이 실제로 사용하는 경로:            {                      }
고객이 다시 돌아오게 되는 이유:          {                      }
```

## 2. 수익원(Revenue Streams)과 비용 구조(Cost Structure)

### 2.1 왜 이 두 블록이 필요한가

학생 팀은 "만들 수 있는가"에 집중하고 "**유지할 수 있는가**"를 놓치는 경우가 많다. 수익원과 비용 구조는 바로 그 지점 — 프로젝트의 **현실성과 지속 가능성** — 을 보게 하는 블록이다.

### 2.2 학생 프로젝트에서의 수익원 해석

수익원은 일반적으로 금전적 수익 구조를 뜻하지만, 학생 프로젝트에서는 **"무엇으로 이 활동을 지속할 것인가"**로 넓게 해석하는 것이 적절하다.

- 수업 과제·캡스톤으로 운영
- 학교 프로그램·학과 지원과 연계
- 공모전, 산학 프로젝트 참여
- 무료 운영 + 교육 목적 유지

"학생 프로젝트니까 수익은 필요 없다"라고 이 칸을 비워 두면, 지속 가능성에 대한 설명이 통째로 사라진다는 점에 유의한다.

### 2.3 비용은 돈만이 아니다

비용 구조에는 금전 외의 부담이 모두 포함된다.

- 개발 시간, 운영·유지보수 시간
- 서버·호스팅 비용
- 데이터 수집과 콘텐츠 제작 부담
- 팀원의 학습 부담

학생 프로젝트에서는 오히려 **시간 비용과 운영 부담**이 가장 큰 비용인 경우가 많다.

### 2.4 두 블록을 함께 보아야 하는 이유

수익만 보고 비용을 보지 않으면 지나치게 낙관적이 되고, 비용만 보면 실행 의지가 약해진다. 둘을 같이 볼 때 비로소 "이 프로젝트가 현실적인가"가 보인다. 다음 질문으로 점검한다.

1. 이 프로젝트는 무엇으로 유지되는가?
2. 누가 시간과 자원을 계속 투입하는가?
3. 가장 큰 부담은 무엇인가?
4. 지금 팀 규모에서 감당 가능한가?

### 2.5 작성 예시 — 피싱 메일 판별 학습 서비스

| 블록 | 내용 |
|---|---|
| 수익원(유지 자원) | 수업 과제 활용, 학교 보안 교육 프로그램 연계, 교수자 운영 |
| 비용 구조 | 사례 업데이트 시간, 웹 운영 부담, 콘텐츠 제작 노동 |

직접적인 유료 판매 없이도 유지 자원이 설명되고, 무엇이 실제 부담인지 드러난다. 이것이 "좋아 보이는 아이디어"와 "운영 가능한 아이디어"를 구분하는 방법이다.

### 실습 2.1

```text
이 프로젝트를 유지하게 해 주는 자원:      {                     }
이 프로젝트에서 가장 부담이 큰 비용:      {                     }
지금 팀이 감당 가능한 수준인가:          {                     }
```

## 3. 핵심 자원·핵심 활동·핵심 파트너

### 3.1 실행 구조를 만드는 세 블록

앞의 블록들이 "누구를 위해 왜 필요한가"를 설명했다면, 이 세 블록은 "**그것을 실제로 어떻게 굴릴 것인가**"를 설명한다. 좋은 아이디어를 가지고도 구현 단계에서 막히는 팀은 대부분 이 세 블록을 충분히 생각하지 않은 경우이다.

| 블록 | 질문 |
|---|---|
| **핵심 자원(Key Resources)** | 무엇이 있어야 하는가 |
| **핵심 활동(Key Activities)** | 무엇을 해야 하는가 |
| **핵심 파트너(Key Partners)** | 누구의 도움이 필요한가 |

### 3.2 핵심 자원 — 자원은 장비만이 아니다

자원을 "노트북"이나 "서버" 같은 기술 요소로만 생각하기 쉬우나, 실제로는 훨씬 넓다.

| 자원 유형 | 예시 |
|---|---|
| 사람 | 웹 구현이 가능한 팀원, 콘텐츠 작성자 |
| 기술 | 개발 도구, 서버, 데이터베이스 |
| 데이터 | 사례 데이터, 공개 데이터셋 |
| 시간 | 콘텐츠 제작 시간, 교수자의 피드백 시간 |
| 플랫폼 | 학교 LMS 접근 권한, 웹사이트 |

### 3.3 핵심 활동 — "할 수 있는 일"이 아니라 "반드시 해야 하는 일"

핵심 활동은 가치 제안을 실제로 만들기 위해 **반드시** 해야 하는 활동이다. 판별 기준은 간단하다 — **그 활동이 빠지면 가치 제안이 무너지는가?** 무너진다면 핵심 활동이다.

"로그인 만들기, 버튼 만들기" 같은 개발 작업 목록은 핵심 활동이 아니라 세부 작업이다. 핵심 활동은 "사례 수집", "학습 콘텐츠 제작", "퀴즈 설계"처럼 가치와 직접 연결된 수준으로 적는다.

### 3.4 핵심 파트너 — 혼자 다 하지 않는다

학생 프로젝트에도 협력 대상은 거의 항상 존재한다 — 자료를 제공해 줄 사람, 검토를 도와줄 사람, 접근 권한을 가진 사람. 파트너를 정리하면 **직접 해야 하는 일과 도움을 받아야 하는 일**을 구분할 수 있다.

### 3.5 작성 예시 — 피싱 메일 판별 학습 서비스

| 블록 | 내용 |
|---|---|
| 핵심 자원 | 피싱 사례 데이터, 콘텐츠 작성 시간, 웹 개발 역량 |
| 핵심 활동 | 사례 수집, 학습 콘텐츠 작성, 퀴즈 구현, 결과 피드백 |
| 핵심 파트너 | 교수자, 학교 전산팀, 보안 자료 제공처 |

이 예시에서 프로젝트의 실체가 "웹 페이지 제작"이 아니라 **콘텐츠와 데이터가 함께 필요한 교육 서비스**임이 드러난다. 실행 구조를 적어 보면 프로젝트의 본질이 보인다.

## 4. 자주 하는 실수 정리

| 블록 | 실수 | 개선 |
|---|---|---|
| 채널 | "앱"이라고만 적음 | 왜 그 채널이 적절한지 접근성·현실성으로 설명 |
| 고객 관계 | 반복 사용 이유를 고려하지 않음 | 다시 돌아오게 만드는 장치를 설계 |
| 수익원 | 비워 둠 / "광고 붙이면 된다" | 유지 자원 관점으로 현실적으로 작성 |
| 비용 | "서버는 그냥 쓰면 된다" | 시간·운영 부담까지 포함하여 작성 |
| 자원 | "노트북만 있으면 된다" | 데이터·시간·콘텐츠·권한까지 포함 |
| 파트너 | 비워 둠 | 자료 제공자·검토자·권한 보유자를 확인 |

## 핵심 용어 정리

| 용어 | 영문 | 설명 |
|---|---|---|
| 채널 | Channels | 고객에게 가치를 전달하는 경로 |
| 고객 관계 | Customer Relationships | 고객과 유지하는 관계의 유형 |
| 수익원 | Revenue Streams | 활동을 유지하게 하는 수익 또는 자원 |
| 비용 구조 | Cost Structure | 만들고 유지하는 데 드는 비용과 부담 |
| 핵심 자원 | Key Resources | 프로젝트 운영에 필요한 핵심 자산 |
| 핵심 활동 | Key Activities | 가치 창출을 위해 반드시 해야 하는 활동 |
| 핵심 파트너 | Key Partners | 협력이 필요한 사람이나 조직 |
