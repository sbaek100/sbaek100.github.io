> **학습 목표**
> 1. 비즈니스 모델 캔버스(BMC)의 9개 블록 구조를 설명할 수 있다.
> 2. 고객 세그먼트(Customer Segments)를 구체적으로 좁혀 정의할 수 있다.
> 3. 기능과 가치를 구분하고, 가치 제안(Value Proposition)을 한 문장으로 작성할 수 있다.
{: .prompt-info }

## 1. 비즈니스 모델 캔버스란

![](/assets/img/posts/2027-03-15-pwai-03-bmc-customer-value-1787452285608.png)

> **비즈니스 모델(Business Model)**이란 조직이 **어떻게 가치를 창출하고, 전달하고, 획득하는지**를 설명하는 틀이다. 쉽게 말해 "우리는 누구에게, 무엇을, 어떻게 제공하며, 그 활동을 무엇으로 유지하는가"에 대한 답이다.

**비즈니스 모델 캔버스(BMC, Business Model Canvas)**는 Alexander Osterwalder가 제안한 시각화 도구로, 비즈니스 전체 구조를 9개 블록으로 나누어 **한 장**에 표현한다. Strategyzer는 비즈니스 모델을 다음과 같이 정의한다.

> "A business model describes the rationale of how an organization creates, delivers, and captures value." — [Strategyzer](https://www.strategyzer.com/library/the-business-model-canvas)

학생 프로젝트는 흔히 "앱을 만들고 싶다", "AI를 넣으면 멋질 것 같다"에서 출발한다. 이런 출발 자체는 자연스러우나, 다음 질문에 답하지 못하면 프로젝트는 방향을 잃는다.

- 누가 정말 쓸 것인가?
- 그 사람은 어떤 상황에서 문제를 겪는가?
- 우리가 주는 가치가 실제로 의미가 있는가?
- 이 활동을 어떻게 유지할 것인가?

> "AI를 붙인다", "채팅 기능을 넣는다", "앱으로 만든다"는 **구현 방식**일 뿐, 아직 비즈니스 모델이 아니다.
{: .prompt-warning }

BMC가 학생 프로젝트에 필요한 이유는 네 가지이다.

1. **팀이 같은 방향을 보게 한다** — 아이디어가 막연할 때 팀원마다 떠올리는 그림이 다르다. BMC는 그 그림을 맞추는 도구이다.
2. **기능보다 가치 중심으로 생각하게 한다** — "무엇을 만들까"보다 "왜 필요한가"를 먼저 묻게 한다.
3. **요구사항 도출 전에 방향을 잡는다** — 코드를 작성하기 전에 고객·가치·전달 경로를 정리한다.
4. **설명 능력을 높인다** — 발표에서 "누구를 위해 왜 필요한가"를 명확히 말할 수 있게 된다.

## 2. 9개 블록의 전체 지도

| 블록 | 질문 | 쉬운 표현 |
|---|---|---|
| **고객 세그먼트(Customer Segments)** | 누구를 위한가? | 누가 쓰는가 |
| **가치 제안(Value Proposition)** | 왜 필요한가? | 왜 써야 하는가 |
| **채널(Channels)** | 어떻게 전달하는가? | 어디서 만나는가 |
| **고객 관계(Customer Relationships)** | 어떤 관계를 맺는가? | 한 번 쓰는가, 계속 쓰는가 |
| **수익원(Revenue Streams)** | 무엇으로 유지되는가? | 유지 자원은 어디서 오는가 |
| **핵심 자원(Key Resources)** | 무엇이 필요한가? | 무엇이 있어야 하는가 |
| **핵심 활동(Key Activities)** | 무엇을 해야 하는가? | 무엇을 해야 돌아가는가 |
| **핵심 파트너(Key Partners)** | 누구와 협력하는가? | 누구의 도움이 필요한가 |
| **비용 구조(Cost Structure)** | 무엇이 부담되는가? | 무엇이 비용인가 |

캔버스의 구조는 다음과 같이 읽는다. 왼쪽(인프라 영역)에서 핵심 파트너·활동·자원이 중앙의 **가치 제안**을 만들어 내고, 그 가치가 오른쪽(고객 영역)의 고객 관계·채널을 통해 고객 세그먼트로 전달된다. 하단에서는 왼쪽의 활동이 **비용**을 발생시키고, 오른쪽의 고객이 **수익**을 만들며, 수익이 비용보다 클 때 지속 가능해진다.

![](/assets/img/posts/2027-03-15-pwai-03-bmc-customer-value-1787452502365.png)

![](/assets/img/posts/2027-03-15-pwai-03-bmc-customer-value-1787452530476.png)

> **권장 이미지**: BMC 9블록 캔버스 전체 그림 1장. "비즈니스 모델 캔버스의 표준 9블록 레이아웃. 중앙에 '가치 제안', 오른쪽에 '고객 세그먼트'·'채널'·'고객 관계', 왼쪽에 '핵심 파트너'·'핵심 활동'·'핵심 자원', 하단에 '비용 구조'와 '수익원'. 각 블록에 한글 이름 표기, 화이트보드에 포스트잇을 붙인 느낌의 일러스트."
{: .prompt-tip }

9개 블록을 한 번에 채우려 하면 부담이 크다. 다음 순서가 자연스럽다.

```text
① 고객 세그먼트 → ② 가치 제안 → ③ 채널 → ④ 수익·비용 → ⑤ 자원·활동·파트너
```

고객이 보이지 않으면 가치가 흐려지고, 가치가 흐리면 전달 방식이 애매해지며, 유지 구조가 없으면 지속성이 약해진다.

## 3. 고객 세그먼트(Customer Segments) — 누구를 위한 프로젝트인가

### 3.1 왜 고객 정의가 먼저인가

고객을 정하면 문제의 맥락, 사용 시점, 불편의 강도, 기능의 우선순위, 전달 방식이 함께 정리되기 시작한다. 반대로 고객이 흐리면 다음의 연쇄가 일어난다.

```text
고객이 흐림 → 문제도 흐림 → 가치가 흐림 → 기능이 많아지고 우선순위가 꼬임
```

### 3.2 흔한 실수 — 고객을 너무 넓게 잡기

"모든 대학생", "누구나 쓸 수 있는 서비스", "전 국민"과 같은 정의는 실제 사람의 모습이 떠오르지 않는다는 점에서 실패한 정의이다. 좋은 고객 정의에는 최소한 다음 중 일부가 드러나야 한다 — 어떤 사람인가, 언제 이 문제를 겪는가, 왜 중요한가, 얼마나 자주 겪는가.

### 3.3 고객을 좁히는 세 가지 방법

| 방법 | 예시 (넓음 → 좁음) |
|---|---|
| **상황으로 좁히기** | 모든 대학생 → 팀 프로젝트를 자주 하는 대학생 → 학교 메일을 자주 확인하는 신입생 |
| **문제 강도로 좁히기** | 보안에 관심 있는 사람 → 실제로 의심스러운 링크를 클릭한 경험이 있는 학생 |
| **사용 빈도로 좁히기** | 가끔 필요한 사람 → 매주 반복해서 이 문제를 겪는 사람 |

고객을 좁히는 것은 사람을 배제하는 것이 아니라, **처음에 누구를 가장 잘 도와줄지 정하는 것**이다.

### 3.4 사용자와 도입 결정자의 구분

"쓰는 사람"과 "도입을 결정하는 사람"이 다른 경우가 많다. 예를 들어 학교에서 쓰는 보안 학습 서비스라면 사용자는 학생이지만, 도입을 결정하는 주체는 교수자나 학교이다. 이 구분을 놓치면 발표에서 설명이 꼬인다.

| 구분 | 예시 |
|---|---|
| 사용자 | 실제로 서비스를 사용하는 학생 |
| 고객·도입 주체 | 수업에 활용하는 교수자, 학교 조직 |
| 영향 주체 | 학교 전산팀, 보안 담당자 |

![](/assets/img/posts/2027-03-15-pwai-03-bmc-customer-value-1787452966506.png)



### 3.5 작성 예시 — 페르소나로 구체화하기

한 명의 구체적인 사람처럼 적어 보면 고객 정의가 선명해진다. 다음은 "피싱 메일 판별 학습 서비스"를 주제로 한 작성 예시이다.

```text
이름(가상): 민수
학년/역할: 1학년 대학생
주로 겪는 문제: 학교 메일과 외부 메일을 구분하지 못하고 링크를 쉽게 누른다
문제가 생기는 상황: 과제 공지, 장학금 공지, 학교 행사 안내 메일을 볼 때
왜 이 문제가 중요한가: 실수로 피싱 링크를 누르면 보안 사고로 이어질 수 있다
```

### 실습 3.1

다음 문장을 더 좋은 고객 정의로 개선하라. 개선할 때는 "어떤 사람인가, 언제 겪는가, 왜 중요한가"의 세 질문에 답해야 한다.

```text
원래 문장: 대학생을 위한 일정 관리 서비스

개선 예시: 팀 프로젝트를 두 개 이상 동시에 진행하여 마감일 관리가 어려운
          대학생을 위한 일정 관리 서비스

내 문장:  {                                                    }
```

## 4. 가치 제안(Value Proposition) — 왜 이 프로젝트가 필요한가

![](/assets/img/posts/2027-03-15-pwai-03-bmc-customer-value-1787452573783.png)

### 4.1 기능과 가치의 구분

가치 제안은 고객의 "왜 이걸 써야 하는가"에 대한 답이다. 여기서 결정적으로 중요한 것은 **가치 제안은 기능 목록이 아니라는 점**이다.

| 표현 | 성격 |
|---|---|
| 피싱 메일 예시를 보여준다 | 기능 |
| 학생이 위험한 메일을 더 잘 구분하도록 돕는다 | 가치 |

기능은 "무엇을 하는가"이고, 가치는 "그것이 왜 중요한가"이다. 다음 대비를 참고하라.

| 기능 중심 표현 | 가치 중심 표현 |
|---|---|
| AI 분석 기능 제공 | 사용자가 더 빠르게 위험 신호를 인식하도록 돕는다 |
| 퀴즈 기능 제공 | 학습자가 실수를 줄이도록 돕는다 |
| 알림 기능 제공 | 팀원이 마감일을 놓치지 않게 돕는다 |

### 4.2 고객 문제에서 가치 제안으로

가치 제안은 다음 흐름으로 도출한다.

```text
고객 → 문제 상황 → 불편·위험 → 원하는 결과 → 가치 제안
```

**작성 예시** — 피싱 메일 판별 학습 서비스

```text
고객:        이메일을 자주 쓰는 대학생
문제 상황:   학교 메일인지 피싱 메일인지 헷갈린다
불편·위험:   잘못 클릭할 수 있다
원하는 결과: 위험 신호를 빨리 알아차리고 싶다
가치 제안:   학생이 위험한 메일을 더 잘 구분하도록 돕는 학습 서비스
```

이 사고 과정을 더 세분화한 것이 Strategyzer의 Value Proposition Canvas이며, 핵심 질문은 세 가지이다 — 고객이 하려는 일은 무엇인가(Jobs), 무엇이 불편한가(Pains), 어떤 결과를 원하는가(Gains).

### 4.3 가치 제안 작성 공식

```text
[고객]이 [문제 상황]에서 [원하는 결과]를 얻도록 돕는 [서비스/활동]
```

**작성 예시**:

```text
학교 메일을 자주 사용하는 대학생이 피싱 메일의 위험 신호를
더 잘 구분하도록 돕는 학습 서비스
```

문장이 화려할 필요는 없으나, **고객·문제·결과** 세 가지는 반드시 드러나야 한다.

### 4.4 좋은 가치 제안과 약한 가치 제안

| 구분 | 예시 | 진단 |
|---|---|---|
| 약함 | "AI 기반 차세대 보안 플랫폼" | 고객·문제가 보이지 않고 기술 수식어만 있다 |
| 좋음 | "보안 경험이 적은 대학생이 학교 메일의 위험 신호를 쉽게 구분하도록 돕는 학습 서비스" | 고객·문제·가치가 모두 보인다 |

### 실습 4.1

다음 기능 설명을 가치 제안 문장으로 바꿔라.

```text
원래 문장: 사용자가 퀴즈를 풀 수 있는 웹 서비스를 만든다.

개선 예시: 보안 지식이 적은 대학생이 피싱 메일의 위험 신호를
          반복 학습으로 익히도록 돕는 웹 학습 서비스

내 문장:  {                                                    }
```

## 5. 학생이 흔히 하는 실수 정리

| 실수 | 예시 | 문제점 |
|---|---|---|
| 기능을 BMC라고 착각 | "AI 기능 추가", "로그인 구현" | 요구사항 후보일 뿐 비즈니스 모델이 아니다 |
| 고객을 너무 넓게 | "모든 대학생", "전 국민" | 누구를 위한 것인지 모호해진다 |
| 가치 대신 수식어 | "스마트 보안 플랫폼", "차세대 AI 서비스" | 고객과 문제를 설명하지 못한다 |
