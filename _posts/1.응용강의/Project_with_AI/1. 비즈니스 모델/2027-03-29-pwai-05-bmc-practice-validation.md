## 1. 공통 예제로 캔버스 완성하기

### 1.1 예제 주제

> **대학생을 위한 피싱 메일 판별 학습 서비스**

이 주제를 예제로 삼는 이유는 학생이 실제로 접할 수 있는 상황이고, 고객·가치·채널·운영 구조를 모두 떠올리기 쉽기 때문이다.

### 1.2 브레인스토밍 — 캔버스에 들어갈 재료 모으기

캔버스의 칸을 바로 채우기 전에, 생각나는 내용을 자유롭게 적는다. 이 단계는 정답을 적는 단계가 아니라 **재료를 모으는 단계**이다.

```text
- 학생들은 피싱 메일을 진짜 메일로 착각할 수 있다
- 위험 신호를 잘 모르고 클릭할 수 있다
- 사례 중심으로 배우면 더 잘 이해할 수 있다
- 퀴즈 형태면 참여가 쉽다
- 학교 LMS와 연결하면 수업에서 쓰기 좋다
- 콘텐츠를 계속 업데이트해야 할 수 있다
```

### 1.3 재료를 9개 블록으로 배치하기

| 블록 | 작성 내용 |
|---|---|
| 고객 세그먼트 | 이메일과 메시지를 자주 사용하는 대학생 |
| 가치 제안 | 피싱 메일의 위험 신호를 더 쉽게 구분하도록 돕는다 |
| 채널 | 웹 학습 페이지, 학교 LMS, 학교 포털 |
| 고객 관계 | 반복 퀴즈, 즉시 피드백, 학기별 학습 |
| 수익원(유지 자원) | 수업 연계 운영, 학교 보안 교육 프로그램 |
| 핵심 자원 | 사례 데이터, 콘텐츠, 웹 구현 역량 |
| 핵심 활동 | 사례 수집, 학습 콘텐츠 작성, 퀴즈 구현 |
| 핵심 파트너 | 교수자, 학교 전산팀, 자료 제공처 |
| 비용 구조 | 콘텐츠 업데이트 시간, 운영 부담 |

각 칸의 작성 근거는 다음과 같다.

- **고객**: "대학생"이 아니라 "이메일을 자주 사용하는 대학생"으로 구체화하였다 — 문제 상황이 선명해진다.
- **가치**: "보안 교육 서비스"가 아니라 "위험 신호를 더 쉽게 구분하도록 돕는다"로 적었다 — 학생이 얻는 가치가 보인다.
- **채널**: 학생이 실제 접근 가능한 웹·LMS·포털을 골랐다 — 앱보다 구현 부담이 낮고 현실적이다.
- **관계**: 보안 지식은 반복 학습이 중요하므로 퀴즈와 피드백을 설계하였다.

### 1.4 발표용 한 줄 정리

캔버스가 완성되었는지 확인하는 가장 간단한 방법은 다음 문장이 채워지는지 보는 것이다.

```text
우리 프로젝트는 [고객]이 [문제]를 해결하도록 돕는 [가치]를 제공하며,
[채널]을 통해 전달되고, [운영 방식]으로 유지된다.
```

**작성 예시**:

```text
우리 프로젝트는 대학생이 피싱 메일을 더 잘 구분하도록 돕는 학습 가치를 제공하며,
웹과 LMS를 통해 전달되고, 수업 연계형 교육 서비스로 운영된다.
```

이 한 줄이 써지지 않는다면, 아직 핵심 칸이 정리되지 않은 것이다.

### 실습 1.1 — 내 프로젝트에 적용

자신의 프로젝트로 아래 템플릿을 채워라. 순서는 고객 → 가치 → 채널 → 수익·비용 → 자원·활동·파트너를 권장한다. 초안은 불완전해도 좋다 — 중요한 것은 빈칸이 있더라도 우선 구조를 만드는 것이다.

```text
프로젝트 이름:
고객 세그먼트:
가치 제안:
채널:
고객 관계:
수익원(유지 자원):
핵심 자원:
핵심 활동:
핵심 파트너:
비용 구조:
```

## 2. 캔버스 검증 — 고객 인터뷰

### 2.1 왜 검증이 필요한가

캔버스를 적었다고 해서 그 내용이 사실이 되는 것은 아니다. 대부분의 칸은 아직 **가설**이다. Steve Blank는 고객 개발 방법론에서 다음 문장으로 이를 표현한다.

> "There are no facts inside the building." — [Steve Blank](https://steveblank.com/category/customer-development/)

회의실 안에서는 사실을 확인할 수 없으며, **실제 사람을 통해 확인해야 한다**는 뜻이다. 블록별 검증 질문은 다음과 같다.

| 블록 | 검증 질문 |
|---|---|
| 고객 세그먼트 | 우리가 정한 고객이 정말 이 문제를 겪는가 |
| 가치 제안 | 이 가치가 고객에게 실제로 의미 있는가 |
| 채널 | 이 경로가 실제로 접근하기 편한가 |
| 고객 관계 | 고객이 반복해서 돌아올 이유가 있는가 |
| 수익·비용 | 이 구조가 지속 가능한가 |

### 2.2 인터뷰 질문 만들기 — 경험을 묻고, 유도하지 않는다

좋은 인터뷰 질문은 **실제 경험**을 묻는다. 나쁜 질문은 답을 유도한다.

| 좋은 질문 (경험 중심) | 나쁜 질문 (유도 질문) |
|---|---|
| 최근에 이런 문제를 겪은 적이 있는가 | 이 서비스 좋지 않은가 |
| 그때 어떻게 해결했는가 | 이런 기능이 있으면 쓸 것인가 |
| 무엇이 가장 불편했는가 | 우리 아이디어 어떤가 |

유도 질문에는 누구나 예의상 긍정적으로 답한다. 그것은 검증이 아니라 **아이디어에 대한 예의 바른 동의**일 뿐이다. 인터뷰의 목적은 아이디어를 자랑하는 것이 아니라, **가설을 깨뜨리거나 보완하는 것**이다.

### 2.3 검증의 흐름

```text
캔버스 초안 작성 → 가설 표시 → 인터뷰 질문 작성 → 사용자 인터뷰
→ 배운 점 정리 → 캔버스 수정
```

이 흐름에서 알 수 있듯, BMC는 한 번 쓰고 끝나는 문서가 아니라 **계속 수정되는 작업 도구**이다.

### 2.4 작성 예시 — 피싱 학습 서비스의 검증 계획

```text
검증하고 싶은 가설:
- 대학생은 피싱 메일 구분에 실제로 어려움을 느낀다
- 퀴즈형 학습이 긴 설명보다 더 도움이 된다
- LMS나 웹 방식이 접근성이 좋다

인터뷰 질문:
1. 최근에 메일이나 메시지를 보고 의심스러웠던 경험이 있는가?
2. 그때 어떤 기준으로 판단했는가?
3. 보안 교육을 받았다면 어떤 방식이 가장 기억에 남았는가?
4. 긴 설명과 퀴즈형 학습 중 어느 쪽이 더 도움이 될 것 같은가?
```

### 2.5 검증에서 자주 하는 실수

1. **친구에게 설명하고 "좋다"는 말만 듣기** — 피드백일 수는 있으나 검증이 아니다.
2. **문제 경험보다 솔루션 반응만 묻기** — "이 서비스 어떤가"보다 "이 문제를 최근에 겪었는가"가 중요하다.
3. **인터뷰 결과를 캔버스에 반영하지 않기** — 검증은 기록보다 수정이 중요하다.

### 실습 2.1

자신의 프로젝트에 대해 다음 세 종류의 질문을 하나씩 작성하라.

```text
1. 고객이 실제 경험을 말하게 하는 질문: {                       }
2. 문제의 강도를 확인하는 질문:        {                       }
3. 현재의 해결 방식을 묻는 질문:       {                       }
```

## 3. 캔버스에서 요구사항으로

### 3.1 BMC와 요구사항의 관계

BMC는 "**왜** 이 프로젝트가 필요한가"를 설명하고, 요구사항은 "**무엇을** 만들어야 하는가"를 설명한다. 이 두 단계가 섞이면 아이디어도 흐려지고 기능도 흔들린다.

| 구분 | BMC | 요구사항 |
|---|---|---|
| 질문 | 왜 필요한가 | 무엇을 만들어야 하는가 |
| 대상 | 기획 방향 | 실제 기능·행동 |
| 형태 | 구조적 요약 | 기능 문장·조건 |

예를 들어 "피싱 메일을 더 잘 구분하도록 돕는다"는 BMC(가치 제안)이고, "사용자는 메일 사례를 보고 정상/피싱 여부를 판단해 볼 수 있어야 한다"는 요구사항이다.

### 3.2 블록별 연결 방법

| BMC 블록 | 요구사항으로 바뀌는 관점 |
|---|---|
| 고객 세그먼트 | 어떤 사용자를 고려한 설계가 필요한가 |
| 가치 제안 | 어떤 문제를 해결하는 기능이 필요한가 |
| 채널 | 웹·앱·LMS 중 무엇으로 제공할 것인가 |
| 고객 관계 | 반복 사용·피드백·알림이 필요한가 |
| 핵심 활동 | 실제로 구현해야 할 핵심 기능은 무엇인가 |

### 3.3 작성 예시 — 피싱 학습 서비스

| BMC 내용 | 도출된 요구사항 |
|---|---|
| 대학생이 주요 고객 | 사용자는 학생 눈높이의 쉬운 설명과 예시를 볼 수 있어야 한다 |
| 피싱 메일 구분을 돕는다 | 사용자는 사례를 보고 정상/피싱 여부를 판단해 볼 수 있어야 한다 |
| 웹·LMS로 제공 | 사용자는 웹 브라우저를 통해 학습 콘텐츠에 접근할 수 있어야 한다 |
| 반복 학습 관계 | 사용자는 퀴즈 결과와 피드백을 받을 수 있어야 한다 |

### 3.4 요구사항 문장의 기본형

```text
사용자는 ______ 할 수 있어야 한다.
시스템은 ______ 제공해야 한다.
```

### 3.5 연결 단계에서 자주 하는 실수

1. **가치 제안을 그대로 요구사항이라고 쓰기** — "피싱 메일을 더 잘 구분하도록 돕는다"는 방향 설명이지 기능 요구사항이 아니다.
2. **너무 이른 구현 상세** — "버튼 색은 파란색이어야 한다"는 이후 화면 설계 단계의 결정이다. 먼저 사용자 행동과 시스템 역할을 정리한다.
3. **고객을 잊은 기능 나열** — 고객과 가치가 보이지 않는 기능 목록은 방향을 잃는다.

### 실습 3.1

```text
BMC에서 정한 고객: {                                           }
BMC에서 정한 가치: {                                           }

이것을 바탕으로 도출한 요구사항:
1. 사용자는 {                                  } 할 수 있어야 한다.
2. 사용자는 {                                  } 할 수 있어야 한다.
3. 시스템은 {                                  } 제공해야 한다.
```

## 핵심 용어 정리

| 용어 | 영문 | 설명 |
|---|---|---|
| 가설 | Hypothesis | 아직 검증되지 않은, 사실로 가정한 내용 |
| 고객 인터뷰 | Customer Interview | 실제 사용자를 통해 가설을 확인하는 활동 |
| 유도 질문 | Leading Question | 답을 특정 방향으로 이끄는 질문 (피해야 함) |
| 요구사항 | Requirement | 시스템이 제공해야 할 기능·조건의 기술 |

## 다음 강의

6강부터는 도출된 요구사항을 **서비스 기획서**로 발전시킨다. 문제 진술문 작성법, 기능·비기능 요구사항의 구분, 우선순위 결정 기법(MoSCoW)을 다루며, 본 과정의 공통 구현 예제인 **통신 기록 분석 리포트(pcapeek)**가 이 단계부터 등장한다.
