> **학습 목표**
> 1. 작품 평가의 6개 요소를 이해하고, 각 요소를 무엇으로 입증할지 계획할 수 있다.
> 2. 평가 기준에 대응하는 발표 자료(슬라이드)를 구성할 수 있다.
> 3. 복장·어조·자세·시간 관리 등 발표 태도와 질의응답 기법을 갖춘다.
{: .prompt-info }

## 1. 평가자는 무엇을 보는가 — 6개 평가 요소

프로젝트 작품 발표는 다음 여섯 가지 요소로 평가된다. **발표 준비의 출발점은 "내 발표의 어느 부분이 어느 평가 요소에 대응하는가"를 확인하는 것**이다. 열심히 만들었더라도 평가 요소에 대응하는 근거를 보여주지 못하면 점수로 연결되지 않는다.

| 평가 요소 | 평가 내용 |
|---|---|
| **① 완성도** | 교육과정에 의한 종합적 응용능력의 표현 정도와 완성도 |
| **② 독창성** | 교육과정에 의한 적정 수준의 주제인지의 여부와 독창성 |
| **③ 실용성** | 주제의 표현 능력과 실용성 및 조화성 |
| **④ 난이도** | 프로젝트실습 작품의 난이도와 숙련도 |
| **⑤ 기획 및 참여도** | 프로젝트실습의 기획능력과 참여도(성실도, 적극성) |
| **⑥ 기타 사항** | 그 밖에 실습 과정에서 필요한 사항 |

### 1.1 각 요소를 무엇으로 입증하는가

평가 요소는 말로 주장하는 것이 아니라 **산출물과 시연으로 입증**한다. 본 과정에서 만든 산출물이 각 요소의 증거가 된다.

| 평가 요소 | 평가자가 던지는 질문 | 입증 수단 (본 과정의 산출물) |
|---|---|---|
| ① 완성도 | 실제로 동작하는가? 배운 것을 종합적으로 썼는가? | **라이브 시연**, 테스트 통과 화면(pytest), 예외 상황(잘못된 입력)에도 죽지 않는 모습 |
| ② 독창성 | 주제가 적정 수준이고 남과 다른 점이 있는가? | 기존 도구 대비 **차별점 1~2개**, 문제 진술문(왜 기존 것으로 안 되는가) |
| ③ 실용성 | 누가 실제로 쓸 수 있는가? 표현이 조화로운가? | **비즈니스 모델(고객·가치·채널)**, 사용자 인터뷰 결과, 일관된 화면 설계 |
| ④ 난이도 | 기술적으로 어느 수준인가? 숙련되게 다루는가? | **시스템 구조도**, 구현 과정에서 겪은 문제와 해결(ADR), 자동 검증 장치(훅) |
| ⑤ 기획 및 참여도 | 계획적으로 진행했는가? 전원이 성실히 참여했는가? | **기획 문서 전체**(BMC·PRD·와이어프레임), 스프린트 기록·커밋 이력, 팀원별 역할과 기여 |
| ⑥ 기타 | 윤리·출처·발표 태도 등 | 오픈소스·데이터 출처 명시, 시간 엄수, 복장과 태도 |

> **핵심 원리**: 평가표를 먼저 읽고 발표를 역산한다. 슬라이드를 다 만든 뒤 "평가 요소가 들어갔는지" 확인하는 것이 아니라, **여섯 요소 각각에 대응하는 슬라이드·시연·발언을 먼저 배정**한 뒤 자료를 만든다.
{: .prompt-tip }

## 2. 발표 자료 작성법

### 2.1 스토리라인 — 발표는 이야기의 순서다

발표 자료는 다음 순서를 따른다. 이 순서는 청중이 자연스럽게 이해하는 순서이자, 6개 평가 요소가 빠짐없이 배치되는 순서이다.

| 순서 | 슬라이드 | 내용 | 대응 평가 요소 |
|---|---|---|---|
| 1 | 표지 | 프로젝트명, 팀명, 팀원 | — |
| 2 | **문제 정의(Hook)** | 구체적 숫자·사례로 시작. "왜 이것이 문제인가" | ②③ |
| 3 | 솔루션 한 줄 | "X를 입력하면 Y를 보여주는 도구" + 대표 화면 1장 | ③ |
| 4 | 고객과 가치 | 누가 쓰는가, 무엇이 좋아지는가 (비즈니스 모델 요약) | ③⑤ |
| 5 | 시스템 구조도 | 데이터 흐름을 화살표로 표시한 그림 한 장 | ④ |
| 6 | 핵심 기술과 차별점 | 사용 기술 + 기존 도구와 다른 점 1~2개 | ②④ |
| 7~8 | **시연(데모)** | 핵심 기능 3가지 라이브 시연 | ①④ |
| 9 | 성과와 근거 수치 | 테스트 통과, 정확도·처리 시간 등 측정 결과 | ① |
| 10 | 개발 과정 | 스프린트 일정, 팀원별 역할과 기여, 겪은 문제와 해결 | ⑤ |
| 11 | 한계와 향후 계획 | 한계를 먼저 밝히고 개선 방향 제시 | ①⑥ |
| 12 | 마무리 | 한 줄 요약 + 출처·감사 | ⑥ |

10분 발표 기준 12장 내외가 적정하다. **1분에 1장**을 넘기면 청중이 따라오지 못한다.

### 2.2 슬라이드 디자인 원칙

| 원칙 | 설명 |
|---|---|
| **1슬라이드 1메시지** | 한 장에서 말하고 싶은 것은 하나만. 두 가지면 두 장으로 나눈다 |
| **글자는 적게, 크게** | 슬라이드는 대본이 아니다. 한 장에 6줄·한 줄에 6단어를 넘기지 않는다(6×6 원칙) |
| **숫자는 크게 강조** | "정확도 96%"는 문장 속에 묻지 말고 화면 중앙에 크게 배치한다 |
| **실물 화면을 보여준다** | 개념 설명보다 실제 동작 화면(스크린샷)이 설득력이 높다 |
| **디자인 통일** | 글꼴 2종 이내, 색 2~3종 이내. 장마다 배경·글꼴이 바뀌면 산만하다 |

**금지 목록** — 다음은 발표의 신뢰를 깎는다.

```text
- 슬라이드 전체를 문장으로 채우고 그대로 읽기
- 과도한 화면 전환 효과·애니메이션
- 출처 없는 이미지·통계
- 코드 전체 화면 붙여넣기 (핵심 부분만 확대하여 제시)
- 마지막 장 "감사합니다"만 크게 (마지막 장에는 한 줄 요약을 남긴다)
```

### 2.3 Hook — 처음 30초가 절반이다

발표의 처음 30초 안에 청중이 "들을 가치가 있다"고 판단하게 만들어야 한다.

| 유형 | 예시 |
|---|---|
| 충격적 수치 | "전 세계 피싱 공격은 3초에 1건 발생합니다" |
| 실제 사례 | 피해 뉴스 헤드라인 화면 1장 |
| 청중 질문 | "여러분의 통신 기록, 누가 훔쳐볼 수 있는지 아십니까?" |

기술 설명("저희는 Python을 썼고요…")으로 시작하는 것은 최악의 도입이다. **문제가 먼저, 기술은 나중이다.**

### 2.4 팀원별 역할 슬라이드 — ⑤를 입증하는 법

"다 같이 열심히 했습니다"는 참여도의 근거가 되지 못한다. 다음과 같이 **구체적으로** 적는다.

```text
| 이름  | 역할          | 주요 기여                              |
| A    | 팀장/기획      | BMC·기획서 총괄, 스프린트 관리, 발표      |
| B    | 구현          | 하네스 구성, 자동 실행·검증              |
| C    | 검증/문서      | 테스트 확인, 인터뷰 수행, 최종 보고서      |
```

단, 역할을 나누었더라도 **팀원 전원이 시스템 전체 구조를 설명할 수 있어야 한다**. 질의응답에서 "그 부분은 제가 안 해서 모릅니다"라는 답이 나오면 참여도 평가 전체가 흔들린다.

> **권장 이미지**: 6개 평가 요소와 발표 슬라이드의 대응 지도 1장. "왼쪽 열에 평가 요소 6개(완성도, 독창성, 실용성, 난이도, 기획·참여도, 기타), 오른쪽 열에 슬라이드 아이콘들(Hook, 구조도, 데모, 성과, 역할)을 배치하고 연결선으로 매핑한 다이어그램. 한글, 흰 배경, 플랫 스타일."
{: .prompt-tip }

## 3. 시연(데모) — 완성도를 입증하는 4분

### 3.1 데모 시나리오는 대본으로 만든다

즉흥 시연은 반드시 실패한다. 보여줄 기능 3가지를 정하고, 클릭 순서까지 대본으로 만든 뒤 그대로 연습한다.

**작성 예시 — pcapeek 데모 대본 (4분)**:

```text
0:00  "지금부터 실제로 동작하는 모습을 보여드리겠습니다"
0:10  터미널에서 명령 한 줄 실행 → 연습용 파일 생성
0:40  분석 명령 실행 → 브라우저에 리포트가 자동으로 열림
1:30  화면 위에서 아래로 설명: 요약 → 프로토콜 비율 → 경고 카드
2:30  (완성도 입증) 일부러 잘못된 파일을 넣어 오류 처리를 보여줌
      "죽지 않고 이유를 알려주고 정상 종료합니다"
3:10  (완성도 입증) 테스트 실행 → 전체 통과 화면
3:40  "설계한 화면 그대로, 검증까지 통과한 상태입니다"
```

**일부러 실패 상황을 보여주는 것**이 고급 기법이다 — 정상 동작만 보여주면 "잘 되는 경우만 골랐다"는 의심을 받지만, 잘못된 입력을 우아하게 처리하는 모습은 완성도의 강력한 증거가 된다.

### 3.2 데모 실패 대비 — 이중 안전장치

라이브 데모는 언제든 실패할 수 있다(네트워크, 프로젝터 해상도, 예상 못 한 오류). 다음 두 가지를 반드시 준비한다.

1. **백업 영상**: 데모 전 과정을 미리 화면 녹화해 둔다. 현장에서 실패하면 "준비한 영상으로 보여드리겠습니다"라고 즉시 전환한다.
2. **결과 스크린샷**: 핵심 화면(리포트, 테스트 통과)을 슬라이드 예비 장에 넣어 둔다.

데모가 실패했을 때 최악의 대응은 그 자리에서 5분간 디버깅하는 것이다. **한 번 재시도 후 즉시 백업으로 전환**한다 — 침착한 전환 자체가 준비성(⑤)의 증거가 된다.

## 4. 발표 태도 — 복장·어조·자세

### 4.1 복장

복장은 "내가 이 발표를 중요하게 여긴다"는 신호이며, 기타 사항(⑥) 평가에 반영된다.

| 항목 | 권장 | 피할 것 |
|---|---|---|
| 기본 원칙 | **단정한 비즈니스 캐주얼** — 깃 있는 셔츠·블라우스, 면바지·슬랙스, 깨끗한 신발 | 슬리퍼, 트레이닝복, 모자, 구겨진 옷 |
| 팀 통일 | 팀원 간 격식 수준을 맞춘다 (한 명만 정장, 한 명은 반바지 금지) | 격식 수준이 제각각인 팀 |
| 실용 | 마이크·포인터를 다룰 수 있게 주머니나 손이 자유로운 복장 | 소리 나는 장신구, 발표 중 만지작거리게 되는 소품 |

### 4.2 어조와 말하기

| 항목 | 지침 |
|---|---|
| **존댓말·평서형** | "~했습니다", "~입니다"로 통일한다. "~같아요", "~인 것 같습니다" 같은 자신 없는 표현은 줄인다 |
| **속도** | 긴장하면 빨라진다. 평소보다 의식적으로 느리게, 문장 사이에 한 박자 쉰다 |
| **군말 제거** | "어…", "음…", "약간", "뭔가"가 반복되면 신뢰가 깎인다. 말이 막히면 군말 대신 **침묵**한다 — 짧은 침묵은 생각하는 모습으로 보인다 |
| **대본 낭독 금지** | 대본을 통째로 외워 읽으면 시선이 죽는다. 슬라이드마다 **핵심 문장 1개**만 외우고 나머지는 말하듯 풀어낸다 |
| **단정적 표현** | 측정한 것은 단정적으로 말한다 — "빠른 것 같습니다"가 아니라 "5초 안에 처리합니다" |

### 4.3 시선과 자세

- 시선은 **청중(평가자)을 향한다**. 스크린을 보고 말하면 목소리가 뒤로 새고 등을 보이게 된다. 화면을 가리킬 때만 잠시 보고 다시 청중으로 돌아온다.
- 무게중심을 두 발에 고르게 두고 선다. 몸을 흔들거나 한쪽 다리에 기대지 않는다.
- 손은 포인터를 쥐거나 자연스럽게 둔다. 팔짱, 주머니에 손, 뒷짐은 피한다.
- 팀 발표에서 자기 차례가 아닐 때도 **자세를 유지한다** — 딴짓하는 팀원은 참여도(⑤) 감점 요인이 된다.

![](/assets/img/posts/2027-05-24-pwai-13-final-presentation-1787454563142.png)

### 4.4 시간 엄수

- 발표 시간을 초과하면 대개 강제로 중단되며, 준비한 결론과 성과를 말하지 못한 채 끝난다.
- 리허설에서 측정한 시간의 **110%를 실전 소요 시간으로 가정**한다(긴장하면 설명이 늘어진다).
- 시간이 부족해지면 건너뛸 장을 미리 정해 둔다(대개 개발 과정 상세). **결론과 성과는 절대 건너뛰지 않는다.**

## 5. 질의응답(Q&A) — 발표의 두 번째 절반

### 5.1 단골 질문과 대비

평가자의 질문은 대부분 6개 평가 요소에서 나온다. 예상 질문을 요소별로 미리 준비한다.

| 관련 요소 | 단골 질문 | 준비 방법 |
|---|---|---|
| ② 독창성 | "기존 도구와 무엇이 다른가?" | 차별점 1~2개를 수치·사례와 함께 준비 |
| ① 완성도 | "이 경우에는 어떻게 되는가?" (예외 상황) | PRD 사용자 시나리오의 "잘못될 수 있는 것" 목록이 그대로 답이 된다 |
| ④ 난이도 | "가장 어려웠던 부분은?" | 실제 겪은 문제와 해결 과정(ADR) 하나를 이야기로 준비 |
| ⑤ 참여도 | "본인은 무엇을 했는가?" (특정 팀원 지목) | 전원이 자기 기여 + 전체 구조를 설명할 수 있게 연습 |
| ③ 실용성 | "실제로 누가 쓰는가? 써 본 사람이 있는가?" | 인터뷰·사용 피드백 결과 인용 |

### 5.2 답변 원칙

1. **질문을 끝까지 듣는다.** 중간에 끊고 답하기 시작하면 질문을 오해하기 쉽다.
2. **결론부터 답한다.** "네, 됩니다. 이유는…" / "아니요, 현재는 안 됩니다. 대신…"
3. **모르면 모른다고 답한다.** 아는 척 얼버무리는 순간 발표 전체의 신뢰가 무너진다. 정직한 표준 답변은 다음과 같다 — "그 부분은 미처 확인하지 못했습니다. 확인해서 보완하겠습니다. 다만 관련하여 저희가 검토한 것은 ~입니다."
4. **한계는 발표에서 먼저 밝힌다.** 질의응답에서 지적당하기 전에 발표자가 먼저 한계를 말하면, 같은 내용이 약점이 아니라 성찰의 증거(①⑥)가 된다.
5. **공격적 질문에도 감사로 시작한다.** "좋은 지적 감사합니다"로 받으면 분위기가 방어전이 되지 않는다.

## 6. 발표 전 최종 점검표

```text
[자료]
[ ] 6개 평가 요소 각각에 대응하는 슬라이드·시연이 배정되어 있다
[ ] Hook이 숫자 또는 사례로 시작한다 (기술 설명으로 시작하지 않는다)
[ ] 시스템 구조도 그림이 한 장 들어 있다
[ ] 성과가 수치로 표현되어 있다
[ ] 한계와 향후 계획이 들어 있다
[ ] 팀원별 역할·기여가 구체적으로 적혀 있다
[ ] 오픈소스·데이터·이미지의 출처가 명시되어 있다

[시연]
[ ] 데모 대본이 있고, 3회 이상 통째로 리허설했다
[ ] 백업 영상과 결과 스크린샷이 준비되어 있다
[ ] 발표장 환경(프로젝터 해상도, 인터넷 유무)을 확인했다

[태도]
[ ] 복장이 단정하고 팀 간 격식이 맞다
[ ] 리허설 시간 × 1.1 이 제한 시간 안에 든다
[ ] 팀원 전원이 전체 구조와 자기 기여를 설명할 수 있다
[ ] 예상 질문 5개 이상에 대한 답이 준비되어 있다
```

---

## 실습

1. 자신의 프로젝트에 대해 1.1절의 표를 채워라 — 6개 평가 요소 각각에 대해 "무엇으로 입증할 것인가"를 한 줄씩 적는다.
2. 2.1절의 스토리라인에 따라 12장 분량의 슬라이드 목차(각 장의 제목과 핵심 메시지 한 줄)를 작성하라.
3. 데모 대본을 3.1절의 형식(시각 표기 포함)으로 작성하고, 실패 시 전환할 백업 계획을 한 줄로 명시하라.
4. 팀원별로 예상 질문 1개씩을 만들어 서로에게 던지고, 5.2절의 원칙(결론부터, 모르면 모른다고)에 따라 답하는 연습을 하라.

## 핵심 용어 정리

| 용어 | 설명 |
|---|---|
| 평가 요소 | 완성도·독창성·실용성·난이도·기획 및 참여도·기타의 6개 항목 |

## 과정을 마치며

본 강의로 14개 강의의 전 과정이 끝난다. 방법론(스프린트)에서 출발하여 비즈니스 모델과 PRD를 만들고, 하네스를 갖춘 바이브 코딩으로 소프트웨어를 완성했으며, 마지막으로 그 결과를 평가 기준에 맞춰 발표하는 방법까지 다루었다. **만들고(기획·구현), 증명하는(검증·발표)** 이 두 능력의 순환이 해커톤과 실무 프로젝트에서 반복하게 될 전체 주기이다.
