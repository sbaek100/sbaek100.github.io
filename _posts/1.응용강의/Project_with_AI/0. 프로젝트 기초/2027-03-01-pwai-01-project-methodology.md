## 0. 이 과정의 목표

본 과정의 최종 목표는 **AI 코딩 도구를 활용하여 하나의 소프트웨어 프로젝트를 스스로 완성하는 능력**을 기르는 것이다. 구체적으로는 다음 세 가지 역량을 목표로 한다.

| 역량            | 의미                                             |
| ------------- | ---------------------------------------------- |
| **기획 역량**     | 무엇을, 누구를 위해, 왜 만드는지를 글로 정리하는 능력                |
| **바이브 코딩 역량** | 코드를 직접 작성하지 않고, AI에게 정확한 지시를 내려 소프트웨어를 완성하는 능력 |
| **협업·발표 역량**  | 팀 단위로 일정을 관리하고, 결과물을 설득력 있게 발표하는 능력            |

이 세 가지가 갖추어지면 **해커톤**(제한된 시간 안에 팀을 이루어 소프트웨어를 완성하는 대회)에 참가할 수 있는 기초 체력이 완성된다. 12개 강의는 기획(비즈니스 모델·요구사항·화면 설계)에서 시작하여 구현(하네스 기반 바이브 코딩)으로 끝나며, 이 순서 자체가 실제 프로젝트의 진행 순서이다.

## 1. 프로젝트란 무엇인가

### 1.1 정의

> **프로젝트(Project)**란 명확한 목표를 달성하기 위해, 정해진 기간 동안, 한정된 자원을 활용하는 **일시적(temporary) 활동**이다.

프로젝트를 규정하는 핵심 요소는 네 가지이다.

| 요소 | 설명 |
|---|---|
| **목표(Goal)** | 달성해야 할 명확한 결과물이 존재한다 |
| **기간(Duration)** | 시작일과 종료일이 정해져 있다 |
| **자원(Resource)** | 사람·예산·도구가 제한되어 있다 |
| **일시성(Temporary)** | 반복되지 않는 고유한 활동이다 |

### 1.2 일반 업무(Operation)와의 차이

"매일 이메일을 확인한다"는 일반 업무이고, "한 학기 안에 통신 기록 분석 프로그램을 완성한다"는 프로젝트이다. 두 활동의 차이는 다음과 같다.

| 구분 | 프로젝트 | 일반 업무 |
|---|---|---|
| 목적 | 새로운 결과물 창출 | 기존 업무의 유지·반복 |
| 기간 | 한시적 (시작~종료) | 지속적 |
| 결과 | 고유한 산출물 | 표준화된 반복 산출물 |
| 위험 | 불확실성이 높다 | 상대적으로 예측 가능 |

학기 중 진행하는 팀 과제, 해커톤 출품작, 공모전 준비는 모두 프로젝트의 정의에 부합한다. 따라서 프로젝트를 관리하는 방법론을 알면 이런 활동 전부에 적용할 수 있다.

## 2. 폭포수 모델과 애자일

### 2.1 폭포수 모델(Waterfall Model)

전통적 개발 방식인 폭포수 모델은 요구사항 분석 → 설계 → 개발 → 테스트 → 배포를 **순차적으로 한 번씩** 진행한다.

```text
요구사항 분석 → 설계 → 개발 → 테스트 → 배포
     (앞 단계로 되돌아가기 어렵다)
```

이 방식의 문제는 **후반에 요구사항이 바뀌면 전체를 다시 해야 한다**는 점이다. 실제 프로젝트에서 요구사항은 거의 항상 바뀌므로, 비용과 시간 낭비가 크다.

### 2.2 애자일(Agile)

> **애자일(Agile)**이란 "민첩한"이라는 뜻으로, **짧은 반복 주기(iteration)를 통해 지속적으로 개선해 나가는** 소프트웨어 개발 방법론이다.

2001년 발표된 애자일 선언(Agile Manifesto)은 다음 네 가지 가치를 제시한다.

| 더 중요하게 여기는 것 | 상대적으로 덜 중요한 것 |
|---|---|
| 개인과 상호작용 | 프로세스와 도구 |
| 작동하는 소프트웨어 | 포괄적인 문서 |
| 고객과의 협력 | 계약 협상 |
| 변화에 대응 | 계획 준수 |

오른쪽 열이 불필요하다는 뜻이 아니라, 왼쪽 열이 **더** 중요하다는 뜻임에 유의한다. 

애자일을 구현하는 대표적 프레임워크로는 스크럼(Scrum), 칸반(Kanban), XP(Extreme Programming) 등이 있으며, 본 과정에서는 가장 널리 쓰이는 **스크럼**의 핵심 개념인 스프린트를 다룬다.

## 3. 스프린트(Sprint)

### 3.1 정의

> **스프린트(Sprint)**란 스크럼 방법론에서 **일정한 짧은 기간(보통 1~4주) 동안 정해진 작업을 완료하는 반복 개발 주기**이다.

스프린트의 전체 구조는 다음과 같다.

```text
프로덕트 백로그          스프린트 백로그          스프린트 결과물
(Product Backlog)   →   (Sprint Backlog)   →   (Increment)
전체 할 일 목록          이번 주기의 할 일         실제 동작하는 산출물

  ↑___________________ 피드백(Feedback) ___________________↓
```

### 3.2 프로덕트 백로그(Product Backlog)

프로젝트가 끝날 때까지 완성해야 할 **모든 기능과 요구사항의 우선순위 목록**이다. 팀원들과 브레인스토밍으로 "있으면 좋을 기능"을 전부 적은 뒤, 가장 중요한 순서대로 정렬한다.

**작성 예시** — 주제: 학교 매점 예약 앱

```text
1. 로그인 기능          (필수)
2. 상품 목록 보기        (필수)
3. 장바구니 담기         (중요)
4. 실시간 재고 알림      (나중에)
5. 리뷰 작성 기능        (선택)
```

### 3.3 스프린트 백로그(Sprint Backlog)

프로덕트 백로그 중 **이번 스프린트(예: 1~2주) 안에 완료하기로 약속한 항목**이다. 전체 목록에서 현실적으로 할 수 있는 양만큼만 가져온 뒤, 작업을 더 작게 쪼개어 담당자와 기한을 정한다.

**작성 예시** — 1주차 스프린트

```text
스프린트 목표: 사용자가 상품 목록을 볼 수 있게 만든다

할 일:
- A팀원: 상품 데이터베이스 만들기
- B팀원: 상품 목록 화면 설계하기
- C팀원: 클릭 시 상세 페이지 이동 기능 구현하기
```

### 3.4 스프린트 결과물(Increment)

스프린트가 끝났을 때 나오는 **실제로 동작하는 결과물**이다. 문서나 계획이 아니라 실행 가능한 코드 또는 동작하는 프로토타입이어야 한다. 예를 들어 결제 기능이 없더라도, 화면에서 상품 목록이 보이고 클릭이 되는 상태라면 유효한 결과물이다.

### 3.5 스프린트를 구성하는 네 가지 이벤트

| 이벤트 | 내용 | 시점 |
|---|---|---|
| **스프린트 계획(Sprint Planning)** | 이번 스프린트에서 할 일 결정 | 스프린트 시작 |
| **데일리 스크럼(Daily Scrum)** | 매일 15분, 진행 상황 공유 | 매일 |
| **스프린트 리뷰(Sprint Review)** | 결과물 시연 및 피드백 | 스프린트 종료 |
| **회고(Retrospective)** | 팀 개선점 논의 | 스프린트 종료 후 |

데일리 스크럼에서는 각자 세 가지만 말한다 — "어제 무엇을 했는가, 오늘 무엇을 할 것인가, 막힌 것이 있는가". 15분을 넘기지 않는 것이 원칙이다.

## 4. 스프린트 계획 수립

스프린트 계획은 다음 4단계로 수립한다.

```text
1단계: 목표 설정        → "이번 2주 동안 무엇을 완성할 것인가"
2단계: 백로그 항목 선택  → 프로덕트 백로그에서 우선순위 높은 항목 선택
3단계: 작업 분해        → 각 항목을 1~2일 단위의 세부 작업으로 분해
4단계: 역할 배정        → 팀원별 담당 작업 배정
```

### 학기 프로젝트의 스프린트 일정 예시 (12주 기준)

| 스프린트 | 기간 | 주요 활동 | 산출물 |
|---|---|---|---|
| Sprint 0 | 1~2주 | 주제 확정, 팀 구성, 비즈니스 모델 작성 | 프로젝트 제안서, BMC |
| Sprint 1 | 3~4주 | 문제 정의, 요구사항 도출 | 요구사항 목록, Use Case |
| Sprint 2 | 5~6주 | 화면 설계, 개발 환경 구축 | 와이어프레임, 개발 환경 |
| Sprint 3 | 7~8주 | 핵심 기능 1차 개발 | 동작하는 프로토타입 |
| Sprint 4 | 9~10주 | 핵심 기능 2차 개발 및 테스트 | 완성된 시스템 |
| Sprint 5 | 11~12주 | 문서화 및 최종 발표 준비 | 최종 보고서, 발표 자료 |

본 과정의 12개 강의 순서가 이 스프린트 일정과 대응된다. 즉 강의를 순서대로 따라가는 것 자체가 한 번의 프로젝트 수행 경험이 된다.

## 5. 유저 스토리(User Story)

백로그의 각 항목은 **사용자 관점의 문장**으로 적는 것이 좋다. 이를 유저 스토리라 한다.

> 형식: "나는 **[역할]**로서, **[목표]**를 위해 **[기능]**이 필요하다."

| 역할 | 유저 스토리 예시 |
|---|---|
| 일반 사용자 | 나는 사용자로서, 계정을 보호하기 위해 이중 인증 기능이 필요하다 |
| 관리자 | 나는 관리자로서, 문제 파악을 위해 사용자 행위 기록을 조회할 수 있어야 한다 |
| 학습자 | 나는 학습자로서, 복습을 위해 지난 퀴즈 결과를 다시 볼 수 있어야 한다 |

기능 이름("로그인 기능")만 적는 것보다, 유저 스토리로 적으면 **누가 왜 필요로 하는지**가 함께 남아 우선순위를 정하기 쉬워진다.

## 6. 팀 구성과 협업 도구

### 6.1 스크럼 팀의 역할

| 역할 | 책임 | 학생 팀에서의 대응 |
|---|---|---|
| **Product Owner(PO)** | 요구사항과 백로그의 우선순위 관리 | 팀장 |
| **Scrum Master** | 회의 진행, 진행을 막는 장애물 제거 | 부팀장 |
| **Developer** | 개발·테스트·문서 작성 | 팀원 전체 |

역할을 나누더라도 **팀원 전원이 프로젝트의 전체 구조를 설명할 수 있어야 한다**. 발표나 질의응답에서 "그 부분은 제가 안 해서 모릅니다"라는 답이 나오면 팀 전체의 평가가 낮아진다.

### 6.2 협업 도구

| 용도 | 도구 | 특징 |
|---|---|---|
| 코드 관리 | GitHub | 버전 관리, 코드 리뷰 |
| 이슈·백로그 | GitHub Projects | 무료, GitHub 연동 |
| 커뮤니케이션 | Discord / Slack | 채널 분리, 파일 공유 |
| 문서 작성 | Notion / Obsidian | 회의록, 지식 관리 |

## 실습

1. 자신이 참여했던 활동(과제, 동아리 행사 등) 중 하나를 골라, 그것이 프로젝트의 4요소(목표·기간·자원·일시성)를 만족하는지 표로 분석하라.
2. "학교 주변 맛집 추천 서비스"를 주제로 프로덕트 백로그 항목 5개를 작성하고 우선순위를 매겨라. 각 항목은 유저 스토리 형식으로 적는다.
3. 위 백로그에서 1주차 스프린트 백로그(2~3개 항목)를 선택하고, 3인 팀을 가정하여 역할을 배정하라.

| 용어 | 영문 | 설명 |
|---|---|---|

| 애자일 | Agile | 짧은 반복 주기로 개발하는 방법론 |
| 스크럼 | Scrum | 애자일의 대표적 프레임워크 |
| 스프린트 | Sprint | 1~4주 단위의 반복 개발 주기 |

| 데일리 스크럼 | Daily Scrum | 매일 15분간의 진행 상황 공유 회의 |

## 다음 강의

2강에서는 프로젝트의 첫 관문인 **주제 선정**을 다룬다. 좋은 주제의 조건, 주제를 고르는 절차, 그리고 제안서와 발표 자료에 반드시 들어가야 할 다섯 가지 요소를 학습한다.
