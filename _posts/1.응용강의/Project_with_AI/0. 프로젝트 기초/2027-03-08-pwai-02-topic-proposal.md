> **학습 목표**
> 1. 좋은 프로젝트 주제의 다섯 가지 조건을 설명할 수 있다.
> 2. 주제 선정 프로세스에 따라 자신의 주제를 검토할 수 있다.
> 3. 제안서(Proposal)와 발표 자료에 반드시 포함해야 할 다섯 가지 요소를 안다.
{: .prompt-info }

## 1. 좋은 주제의 조건

프로젝트의 성패는 주제 선정 단계에서 절반 이상 결정된다. 좋은 주제는 다음 다섯 가지 조건을 만족한다.

| 조건 | 설명 | 나쁜 예 | 좋은 예 |
|---|---|---|---|
| **문제 명확성** | 해결하려는 문제가 구체적이다 | "생활을 편리하게 한다" | "기숙사 세탁기 사용 가능 여부를 실시간으로 알려준다" |
| **실현 가능성** | 학기(또는 해커톤 기간) 내에 구현 가능하다 | "국가 단위 교통 관제 시스템" | "우리 학교 셔틀버스 도착 알림" |
| **측정 가능성** | 결과를 수치로 평가할 수 있다 | "사용성이 좋아진다" | "판별 정확도 90% 이상 달성" |
| **독창성** | 기존 도구의 단순 설치·모방이 아니다 | "유명 앱 따라 만들기" | "기존 앱에 없는 우리 학교 특화 기능 추가" |
| **자원 확보 가능성** | 필요한 데이터·도구를 실제로 구할 수 있다 | "은행 거래 데이터 분석" (구할 수 없음) | "공개 데이터셋 기반 분석" |

특히 마지막 조건이 자주 간과된다. "이런 것을 만들겠다"는 계획만 있고 **데이터를 어디서 구할지**에 대한 계획이 없으면, 구현 단계에서 반드시 막힌다. 공개 데이터 출처(Kaggle, 공공데이터포털, PhishTank 등)를 주제 선정 단계에서 미리 확인해 두어야 한다.

## 2. 주제 선정 프로세스

주제는 다음 4단계로 선정한다.

```text
1단계: 문제 발굴 (브레인스토밍)
   → 일상에서 겪는 불편, 뉴스, 공모전 주제 등에서 문제를 찾는다

2단계: 범위 설정 (Scoping)
   → 주어진 기간 내에 구현 가능한가?
   → 팀원 수와 기술 수준에 맞는가?

3단계: 타당성 검토 (Feasibility)
   → 필요한 도구·데이터·환경이 준비되는가?
   → 참고할 자료(문서, 오픈소스)가 있는가?

4단계: 주제 확정 및 문서화
   → 프로젝트 제안서(Proposal) 작성
```

> **범위에 관한 경험칙**: 처음 떠올린 아이디어는 대부분 실제 구현 가능한 범위의 3~5배 크기이다. "이 정도면 너무 작지 않을까" 싶을 만큼 줄인 것이 대개 적정 규모이다. 작지만 끝까지 완성하여 스스로 설명할 수 있는 주제가, 크지만 미완성인 주제보다 항상 높게 평가된다.
{: .prompt-warning }

## 3. 1학년이 도전할 만한 주제 예시

아래는 비전공 1학년 팀이 한 학기 안에 완성 가능한 수준의 주제 예시이다. 예시일 뿐이므로 자유롭게 변형해도 된다.

| 주제 | 한 줄 설명 | 데이터 확보 난이도 |
|---|---|---|
| 비밀번호 강도 시각화 | 비밀번호를 입력하면 해독에 걸리는 시간을 보여준다 | 매우 쉬움 (계산만 필요) |
| 피싱 URL 판별기 | URL을 넣으면 위험 점수를 게이지로 표시한다 | 쉬움 (무료 공개 데이터셋) |
| 통신 기록 분석 리포트 | 네트워크 기록 파일을 읽어 위험 통신을 경고한다 | 쉬움 (직접 생성 가능) |
| 학식 메뉴 알리미 | 오늘의 학식 메뉴와 혼잡도를 한 화면에 보여준다 | 보통 (직접 수집 필요) |
| 팀 일정 조율 도우미 | 팀원들의 공강 시간을 겹쳐서 회의 가능 시간을 찾아준다 | 쉬움 (직접 입력) |

이 중 "통신 기록 분석 리포트"는 본 과정의 후반부(하네스 실습)에서 실제로 함께 완성할 공통 예제이다.

## 4. 프로젝트 제안서(Proposal) 양식

주제가 확정되면 한 쪽 분량의 제안서로 문서화한다.

```text
## 프로젝트 제안서

1. 프로젝트 제목
   예: 통신 기록 분석 웹 리포트 생성기

2. 문제 정의 (Problem Statement)
   현재 어떤 문제가 존재하는가?

3. 해결 방안 (Proposed Solution)
   어떻게 해결할 것인가? (한 문장으로)

4. 기대 결과물 (Deliverables)
   - 소프트웨어:
   - 보고서:
   - 발표 자료:

5. 활용 기술 (Technology Stack)
   - 언어 / 도구:

6. 일정 (Schedule)
   | 주차 | 활동 |
   |------|------|

7. 팀 역할 분담
   | 이름 | 역할 |
   |------|------|
```

## 5. 발표에 반드시 들어가야 할 다섯 가지

제안서를 발표 자료(PPT)로 만들 때는 다음 다섯 가지 요소가 반드시 포함되어야 한다. 하나라도 빠지면 심사자를 설득하기 어렵다.

### ① 문제 정의(Hook) — 왜 만드는가

발표의 처음 30초 안에 청중을 사로잡아야 한다.

- 구체적인 숫자나 사례로 시작한다. 예: "전 세계 피싱 공격은 3초에 1건 발생한다"
- 실제 피해 사례나 뉴스 헤드라인 **1장**을 보여준다
- 기술 설명부터 시작하는 것은 최악의 시작이다 — 문제가 먼저, 기술은 나중이다

### ② 솔루션 한 줄 요약

- "우리는 **X를 입력하면 Y를 보여주는** 도구를 만든다"
- 한 문장 + 대표 화면(스크린샷 또는 목업) **1장**

### ③ 시스템 구조도(Architecture)

전체 시스템을 설명하는 **그림 한 장**이다.

```text
[데이터 입력]   →   [분석 엔진]   →   [결과 화면]
  기록 파일          자동 분석         웹 리포트
```

화살표로 데이터의 흐름을 표시한다. 구조도가 없으면 "감으로 만든 것"처럼 보이고, 구조도가 있으면 "시스템을 이해하고 있다"는 신호가 된다.

### ④ 핵심 기술과 차별점

- 사용 기술을 간결하게 정리한다 (예: Python, 표준 라이브러리)
- **기존 도구 대비 차별점 1~2개**를 명시한다 — 심사자의 단골 질문("기존 것과 뭐가 다른가")을 선제적으로 방어하는 것이다

### ⑤ 성능·근거 데이터

- 예: "판별 정확도 96%", "처리 시간 5초 이내"
- 숫자가 있어야 "그냥 만든 것"이 아니라 "검증한 것"이 된다
- 기획 단계 발표라면 목표 수치를 제시하고, 완성 후 실측치로 채운다

> **권장 이미지**: ③의 시스템 구조도 예시 1장. "3개의 둥근 사각형(데이터 입력, 분석 엔진, 결과 화면)이 화살표로 연결된 단순한 시스템 구조도. 각 상자 아래에 작은 설명 텍스트. 한글, 흰 배경, 단정한 다이어그램 스타일."
{: .prompt-tip }

### 발표 시간 배분 (10분 발표 기준)

| 구간 | 시간 | 내용 |
|---|---|---|
| 문제 정의(Hook) | 1분 | 해결하려는 문제 |
| 솔루션 한 줄 | 1분 | 무엇을 만드는가 |
| 구조도 + 기술 | 2분 | 어떻게 동작하는가 |
| 시연(데모) | 4분 | 실제 동작 (핵심 기능 3가지) |
| 결과 + 결론 | 2분 | 수치, 한계, 향후 계획 |

## 6. 발표에서 자주 하는 실수

| 실수 | 문제점 | 개선 |
|---|---|---|
| 기술 자랑부터 시작 | 왜 필요한지가 안 보인다 | 항상 문제(Hook)부터 |
| 구조도 없이 말로만 설명 | 이해했다는 근거가 없다 | 그림 한 장을 반드시 포함 |
| "잘 됩니다"라고만 말함 | 검증의 근거가 없다 | 수치로 표현 ("정확도 96%") |
| 한계를 숨김 | 질의응답에서 무너진다 | 한계를 먼저 밝히고 개선 계획 제시 |
| 너무 큰 주제 | 설명도 구현도 불가능 | 작지만 전부 설명 가능한 주제 |

---

## 실습

1. 3절의 주제 예시 중 하나를 골라(또는 자신의 아이디어로), 1절의 다섯 가지 조건을 만족하는지 표로 점검하라.
2. 그 주제로 4절의 제안서 양식을 채워라. 특히 "데이터를 어디서 구할 것인가"를 반드시 포함한다.
3. 자신의 제안서를 바탕으로, 5절의 다섯 요소 중 ①(Hook)과 ②(한 줄 요약)를 각각 한 문장으로 작성하라.

## 핵심 용어 정리

| 용어 | 영문 | 설명 |
|---|---|---|
| 제안서 | Proposal | 프로젝트의 목표·범위·방법을 정의한 문서 |
| 범위 설정 | Scoping | 구현 가능한 범위로 주제를 좁히는 일 |
| 타당성 검토 | Feasibility Study | 실현 가능성을 사전에 확인하는 일 |
| 시스템 구조도 | Architecture Diagram | 시스템 구성 요소와 데이터 흐름을 나타낸 그림 |
| 훅 | Hook | 발표 도입부에서 청중의 관심을 끄는 장치 |

## 다음 강의

3강부터는 **비즈니스 모델 캔버스(BMC)**를 다룬다. 좋은 주제를 골랐더라도 "누가, 왜 쓰는가"에 답하지 못하면 프로젝트는 방향을 잃는다. BMC는 그 답을 한 장으로 정리하는 도구이다.
