> 1. 기술 스택이 무엇인지 네 가지 질문으로 설명할 수 있다.
> 2. PRD의 제약사항에서 기술 스택 선택 기준을 도출할 수 있다.
> 3. 데이터베이스·웹 서버·Docker·클라우드 같은 환경 요소가 언제 필요한지 요구사항의 신호로 판단할 수 있다.
> 4. AI와 후보를 비교·검토하며 기술 스택을 확정하고, 결정 기록을 남길 수 있다.

## 1. 기술 스택이란

지금까지 무엇을 만들지(PRD)와 어떤 모양으로 보여줄지(화면 설계)를 정했다. 마지막으로 남은 질문은 **"무엇으로 만드는가"**이다.

> **기술 스택(Tech Stack)**이란 프로그램을 만들고 실행하는 데 쓰는 기술의 조합이다.

"스택"이라는 말이 거창하게 들리지만, 우리 규모의 프로젝트에서는 네 가지 질문에 답하는 것이 전부다.

| 질문                     | 뜻                     | 이미 정해진 것                  |
| ---------------------- | --------------------- | ------------------------- |
| ① 어떤 **언어**로 쓰는가       | 코드를 작성할 프로그래밍 언어      | 미정 — **본 강의에서 결정**        |
| ② 결과를 어떤 **형태**로 보여주는가 | 터미널 출력, 웹 페이지, 앱 화면 등 | 화면 설계에서 결정됨 (정적 HTML 리포트) |
| ③ 데이터를 **어디에** 두는가     | 파일, 데이터베이스, 클라우드 등    | 미정 — 본 강의에서 결정            |
| ④ **어디서** 실행되는가        | 내 컴퓨터, 서버, 스마트폰 등     | 미정 — 본 강의에서 결정            |

②가 이미 정해져 있다는 점에 주목한다. 화면 설계에서 "서버 없이 파일 하나로 완결되는 리포트"를 채택한 순간, 기술 스택의 큰 방향은 사실상 정해졌다. **기술 스택은 기획의 결론이지, 기획에 앞서는 취향의 문제가 아니다.**

## 2. 선택 기준 — 기능이 아니라 제약이 정한다

"어떤 언어가 제일 좋은가"라는 질문에는 답이 없다. 올바른 질문은 **"내 PRD의 제약사항 안에서 무엇이 가능한가"**이다. 우리 과정에서는 다음 네 기준으로 후보를 거른다.

| 기준 | 묻는 것 | 근거 |
|---|---|---|
| **제약 충족** | PRD의 제약사항(인터넷 없이, 설치 권한 없이 등)을 지킬 수 있는가 | 제약을 어기는 스택은 아무리 좋아도 탈락 |
| **배우는 비용** | 학기 안에 팀 전원이 다룰 수 있는가 | 시간 제약(12주)의 일부다 |
| **AI가 잘 아는가** | 널리 쓰여서 AI의 학습 자료가 많은 기술인가 | 바이브 코딩에서는 이것이 곧 개발 속도다 |
| **팀원 전원** | 일부만 아는 기술은 아닌가 | 발표·질의응답에서 전원이 설명해야 한다 |

세 번째 기준은 바이브 코딩 특유의 것이다. **AI는 세상에 코드가 많이 존재하는 대중적인 기술일수록 잘 다룬다.** 희귀한 언어나 갓 나온 프레임워크를 고르면, AI가 만드는 코드의 품질이 떨어지고 오류를 스스로 고치지 못하는 일이 잦아진다. 대중적인 선택이 곧 실용적인 선택이다.

이 기준은 감이 아니라 자료로 확인할 수 있다. 개발자 설문·사용 순위(예: Stack Overflow 연례 개발자 설문)에서 **순위가 높은 기술일수록 세상에 코드·문서·질문답변이 많고, AI도 바로 그 데이터로 학습했다.** 예전에는 "많이 쓰는 기술 = 물어볼 사람이 많은 기술"이 선택 이유였다면, 지금은 "많이 쓰는 기술 = AI가 잘 아는 기술"이라는 이유가 하나 더 붙은 것이다.

## 3. 환경까지 넓혀 보기 — 데이터베이스·서버·Docker는 언제 필요한가

후보 비교에 들어가기 전에, 실무의 기술 스택에 등장하는 **환경 요소**들을 알아 둘 필요가 있다. 채용 공고나 기술 소개에서 보는 스택에는 언어 외에 데이터베이스, 웹 서버, Docker, 클라우드 같은 이름이 줄줄이 붙는다. 이들이 무엇이고 언제 필요한지 모르면 두 가지 실수 중 하나를 하게 된다 — **필요 없는데 넣어서 배보다 배꼽이 커지거나(과잉), 필요한데 빼서 구현 도중에 갈아엎거나(과소).** 정확한 스택 전략은 이 요소들을 아는 데서 나온다.

### 3.1 환경 요소 지도

| 구성 요소 | 하는 일 | 필요해지는 신호 (요구사항에서 찾는다) |
|---|---|---|
| **데이터베이스(DB)** | 데이터를 엑셀 표처럼 구조화해 저장하고, 빠르게 찾고, 여러 명이 동시에 써도 꼬이지 않게 관리한다 | 프로그램을 꺼도 데이터가 남아야 한다 / 사용자들의 데이터가 계속 쌓인다 / 검색·정렬을 자주 한다 |
| **웹 서버** | 항상 켜진 채로 접속자의 요청을 받아 응답한다 | 나 아닌 다른 사람이 접속해서 쓴다 / 항상 켜져 있어야 한다 |
| **외부 API** | 남이 만들어 둔 기능(AI 모델 등)을 인터넷 요청으로 빌려 쓴다 | AI 생성·분석처럼 직접 만들 수 없는 기능이 Must에 있다 |
| **Docker (컨테이너)** | 프로그램과 실행 환경(언어 버전·라이브러리·설정)을 상자 하나로 포장해, 어느 컴퓨터에서든 똑같이 돌게 한다 | "내 컴퓨터에서는 되는데"가 반복된다 / 팀원마다 개발 환경이 다르다 / 서버에 올려 배포해야 한다 |
| **클라우드** | 남의 컴퓨터(AWS 등)를 빌려 프로그램을 실행한다 | 24시간 켜 둘 컴퓨터가 없다 / 외부에 공개해야 한다 |

판단 원칙은 앞 절의 과잉·과소를 가르는 한 문장으로 요약된다.

> **그 신호가 내 Must 요구사항에서 나오는가?** 나오면 스택에 넣는 것이 정당하고, 나오지 않으면 지금은 필요 없다.

신호는 처음부터 있는 것이 아니라 **요구사항이 바뀌는 순간 생기기도 한다.** 한 번 분석하고 끝나는 도구에는 DB 신호가 없지만, "지난 결과를 저장해 두고 다시 본다"는 요구가 추가되는 순간 신호가 생긴다. 그래서 환경 요소 판정은 한 번 하고 끝이 아니라, 요구사항이 바뀔 때마다 다시 한다.

> **외부 API를 쓰기로 판정했다면 반드시 따라오는 결정이 있다 — API 키 관리.** API 키는 서비스를 빌려 쓰기 위한 비밀 열쇠로, 유출되면 남이 내 계정 요금으로 API를 마음껏 쓴다. **키를 코드 안에 직접 적거나, 사용자에게 전달되는 화면 쪽 코드에 넣으면 안 된다.** "키를 어디에 보관할 것인가"(환경 변수, 별도 설정 파일 등)를 결정표에 함께 적고, 구현 단계에서 AI에게도 "키를 코드에 하드코딩하지 말 것"을 지시한다.
{: .prompt-warning }

### 3.2 같은 4질문, 다른 답 — 두 프로젝트 비교

환경 요소는 좋고 나쁨의 문제가 아니라 **프로젝트의 성격 문제**임을 두 서비스로 비교한다.

| 신호 질문 | pcapeek (로컬 분석 도구) | 팀 일정 공유 서비스 (가상 예) |
|---|---|---|
| 꺼도 데이터가 남아야 하는가 | 아니오 — 리포트 파일이면 충분 → **DB 불필요** | 예 — 일정이 핵심 데이터 → **DB 필요** |
| 다른 사람이 접속하는가 | 아니오 — 혼자 로컬에서 사용 → **웹 서버 불필요** | 예 — 팀원 전원이 접속 → **웹 서버 필요** |
| 어디서든 같은 환경이어야 하는가 | 아니오 — 내 터미널에서만 실행 → **Docker 불필요** | 예 — 서버에 배포 → **Docker 유용** |
| 24시간 켜져 있어야 하는가 | 아니오 → **클라우드 불필요** | 예 → **클라우드 필요** |

오른쪽 같은 프로젝트라면 DB·서버·클라우드는 과잉이 아니라 **Must에서 도출된 정당한 스택**이다. pcapeek이 이들을 쓰지 않는 것도 "초보라서 못 쓰는 것"이 아니라 신호가 없기 때문이다. 자신의 프로젝트가 오른쪽에 가깝다면, 뒤에 나올 후보 비교와 AI 토의를 환경 요소까지 포함해 진행하면 된다.

### 3.3 신호가 있어도 최소로 시작한다

신호가 있다고 곧장 가장 무거운 선택으로 갈 필요는 없다. **신호의 크기에 맞는 최소 선택**이 원칙이다.

| 신호 | 최소 선택 | 무거운 선택 (지금은 과잉) |
|---|---|---|
| 데이터가 남아야 한다 (사용자 소수) | 파일 저장, 또는 SQLite(파이썬에 기본 포함된 파일형 DB — 별도 설치 불필요) | MySQL·PostgreSQL 등 서버형 DB |
| 팀원 몇 명이 접속한다 | 교내망에서 노트북 한 대로 서버 실행 | 클라우드 상시 가동 |
| AI 기능이 필요하다 | 외부 AI API 호출 (모델은 남의 것을 빌려 쓴다) | AI 모델을 직접 학습·운영 |
| 문의 폼·댓글 같은 부가 기능이 필요하다 | 만들어져 있는 외부 서비스를 연결 | 백엔드를 직접 구현 |
| 환경을 맞춰야 한다 | 파이썬 버전과 라이브러리 목록을 문서로 명시 | Docker 도입 |

왼쪽으로 시작해도 요구사항은 충족되며, 서비스가 커져 신호가 강해지면 그때 오른쪽으로 옮기면 된다. 이 "옮길 수 있다"는 사실 자체가, 처음부터 무겁게 시작할 이유가 없음을 말해 준다.

### 실습 3.1

자신의 프로젝트에 대해 3.2절의 신호 질문 4개에 답하고, 각 환경 요소의 필요 여부를 판정하라. "필요"로 판정한 요소가 있다면 3.3절을 참고해 최소 선택을 함께 적는다.

```text
꺼도 데이터가 남아야 하는가:     {예/아니오} → DB {필요/불필요} {필요 시 최소 선택}
다른 사람이 접속하는가:         {예/아니오} → 웹 서버 {필요/불필요}
어디서든 같은 환경이어야 하는가: {예/아니오} → Docker {필요/불필요}
24시간 켜져 있어야 하는가:      {예/아니오} → 클라우드 {필요/불필요}
```

> **권장 이미지**: 두 프로젝트의 스택 비교 그림 1장. "좌우 2단 비교 다이어그램. 왼쪽은 '로컬 분석 도구' — 노트북 한 대 안에 언어·프로그램·리포트 파일만 있는 단순한 구성. 오른쪽은 '팀 웹 서비스' — 여러 사용자 아이콘이 웹 서버에 접속하고, 서버 뒤에 데이터베이스 원통, 전체가 클라우드 구름 안에 있는 구성. 가운데에 '요구사항의 신호가 스택을 정한다' 문구. 한글, 흰 배경, 플랫 다이어그램 스타일."
{: .prompt-tip }

## 4. 후보 비교 — 결정표 만들기

### 4.1 작성 예시 — pcapeek

네 가지 질문 각각에 대해 후보 2~3개를 놓고 위의 기준으로 비교한 뒤, **선택과 이유, 버린 후보와 이유**를 표로 남긴다.

**① 언어**:

| 후보 | 제약 충족 | 배우는 비용 | AI가 잘 아는가 | 판정 |
|---|---|---|---|---|
| **Python** | 실습실 PC에 기본 설치됨 | 팀 전원이 교양 수업에서 접함 | 매우 잘 안다 | **채택** |
| C | 컴파일러 설치 필요 | 포인터 등 학습 부담 큼 | 잘 안다 | 탈락 — 배우는 비용 |
| JavaScript | 브라우저만으로 가능 | 학습 부담 중간 | 매우 잘 안다 | 탈락 — 파일 읽기가 브라우저에서 제한됨 |

**②~④ 나머지 질문** (①만큼 후보가 많지 않아 판정만 기록):

```text
② 보여주는 형태: 정적 HTML 리포트 — 화면 설계에서 이미 결정.
   CSS는 파일 안에 포함(외부 자원 금지 원칙).
③ 데이터 저장: 없음 — 입력 파일(.pcap)을 읽기만 하고 아무것도 저장하지 않는다.
   데이터베이스는 3절의 신호가 하나도 없으므로 Out of Scope.
④ 실행 위치: 사용자 컴퓨터의 터미널 — 서버가 없으므로 자연히 결정된다.

추가 결정 — 외부 라이브러리를 쓰지 않고 Python 표준 라이브러리만 쓴다.
   이유: 실습실 PC에 설치 권한이 없다(PRD 제약사항).
```

> **표준 라이브러리(Standard Library)**란 언어를 설치하면 함께 딸려 오는 기본 부품 모음이다. 별도 설치 명령 없이 바로 쓸 수 있으므로, "설치 권한 없음" 제약 아래에서는 가장 안전한 선택이 된다.

### 4.2 작성 예시 — photosort (보조 예제)

```text
① 언어: Python — pcapeek과 같은 이유(기본 설치, 전원 경험, AI가 잘 앎)
② 형태: 정적 HTML 리포트 — 화면 설계에서 결정
③ 저장: 없음 — 사진 폴더를 읽기만 한다. 원본을 수정하지 않는다는
   요구사항 3번과도 맞물린다
④ 실행: 사용자 컴퓨터의 터미널

버린 후보와 이유:
- 스마트폰 앱 — 사진이 폰에 있어 매력적이지만, 앱 개발·배포는
  배우는 비용이 학기를 넘는다 → Out of Scope
- 엑셀 매크로 — 팀원 일부만 다룰 수 있고, 리포트 화면 설계를 살릴 수 없다
```

두 예제의 결론이 같은 것은 우연이 아니다 — **제약이 같으면(실습실·설치 권한·인터넷) 스택도 같은 곳으로 수렴한다.**

### 실습 4.1

자신의 프로젝트로 결정표를 작성하라. ①은 후보 2개 이상을 비교표로, ②~④는 판정과 이유로 적는다(③·④는 실습 3.1의 판정 결과를 옮긴다). "버린 후보와 이유"를 최소 1개 포함한다.

```text
① 언어:   {선택} — {이유}
   버린 후보: {무엇} — {왜}
② 형태:   {                                                }
③ 저장:   {                                                }
④ 실행:   {                                                }
```

## 5. AI와 토의하며 스택 정하기 — 실제 상호작용

후보를 고르기 어렵다면 AI에게 비교를 시킨다. 역할 분담은 지금까지와 같다 — **AI는 후보와 장단점을 내는 역할, 학생은 제약을 지키며 결정하는 역할**이다.

### 5.1 후보 요청 프롬프트

PRD의 제약사항을 반드시 함께 붙인다. 제약 없이 물으면 AI는 유행하는 기술을 나열한다.

```text
나는 1학년 학생이고, 아래 PRD대로 프로그램을 만들려고 해.

[PRD의 개요·요구사항·제약사항을 붙여 넣는다]
[화면 설계 문서의 "출력 원칙"을 붙여 넣는다]

이 조건에서 쓸 프로그래밍 언어 후보를 2~3개 제안하고,
각각을 "제약 충족 / 배우는 비용 / AI가 잘 아는 정도" 기준으로 비교해 줘.
하나를 추천하되, 추천 이유를 제약사항과 연결해서 설명해 줘.
아직 코드는 쓰지 마.
```

### 5.2 대화 예시 — pcapeek

여기서도 **AI의 제안을 제약을 근거로 거절하는 턴**이 나온다.

```text
AI:    Python을 추천합니다. 다만 패킷 분석에는 scapy, 그래프에는
       matplotlib 라이브러리를 함께 쓰면 훨씬 편합니다.

학생:  scapy와 matplotlib은 별도 설치가 필요한 외부 라이브러리 아니야?
       제약사항에 "설치 권한 없음"이 있는데.

AI:    맞습니다. 그 제약이라면 표준 라이브러리만으로 구성해야 합니다.
       파일 해석은 struct 모듈로 직접 할 수 있고, 그래프는 HTML/CSS의
       막대로 표현할 수 있습니다. 구현 난이도는 다소 올라갑니다.

학생:  좋아. "Python 표준 라이브러리만 사용"으로 확정하고,
       결정표의 버린 후보에 "scapy·matplotlib — 설치 권한 제약"을 기록해 줘.
```

AI의 첫 제안(scapy·matplotlib)은 일반적으로는 훌륭한 조언이다. 그러나 **내 제약사항과 대조하는 것은 학생의 몫**이며, 대조 없이 받아들였다면 실습실에서 프로그램이 돌지 않는 것을 구현 단계에 가서야 발견했을 것이다.

### 5.3 과잉 스택 경고 — 신호 없는 제안은 거절한다

AI는 묻지 않아도 화려한 구성을 제안하는 경향이 있다 — 웹 프레임워크, 데이터베이스, Docker, 사용자 로그인. 그때마다 판단 기준은 3절에서 세운 그대로다.

> **그 요소를 필요하게 만드는 신호가 내 Must 요구사항에 있는가?** 없으면 지금은 필요 없다.

| AI가 제안할 법한 것 | 신호가 있는가 (pcapeek) | 판정 |
|---|---|---|
| 웹 프레임워크(Flask 등) | 아니오 — 다른 사람이 접속하지 않는다 | 거절, Out of Scope |
| 데이터베이스 | 아니오 — 꺼도 남아야 할 데이터가 없다 | 거절, Out of Scope |
| Docker | 아니오 — 배포할 서버가 없고 내 터미널에서만 돈다 | 거절, Out of Scope |
| 로그인 기능 | 아니오 — 혼자 로컬에서 쓴다 | 거절, Out of Scope |

거절한 항목은 결정표의 "버린 후보"나 PRD의 Out of Scope에 이유와 함께 남긴다. 기록이 없으면 다음 대화에서 AI가 같은 제안을 반복할 때 다시 흔들린다. 반대로 실습 3.1에서 "필요"로 판정한 요소가 있는 프로젝트라면, 그 요소는 거절할 것이 아니라 3.3절의 최소 선택부터 후보 비교에 포함시킨다.

### 5.4 결정표 검토받기

결정표가 완성되면 마지막으로 한 번 검토를 받는다. 여기서는 "이 스택으로 정말 되는가"를 공격시킨다.

```text
다음은 내 프로젝트의 기술 스택 결정표야.

[결정표를 붙여 넣는다]
[PRD의 요구사항·제약사항을 붙여 넣는다]

이 스택으로 요구사항을 전부 구현할 수 있는지 검토해 줘.
특히 "될 것 같지만 실제로는 함정이 있는 부분"이 있으면 짚어 줘.
지적은 심각한 것부터 순서대로. 아직 코드는 쓰지 마.
```

**검토 예시 — pcapeek**: AI가 "브라우저 자동 열기는 일부 리눅스 환경에서 조용히 실패할 수 있다"고 지적했다면 — 사용자 시나리오의 "잘못될 수 있는 것"에 이미 "브라우저가 안 열리면 경로를 출력해 직접 열게 안내"가 있으므로, 스택을 바꿀 일이 아니라 "시나리오에서 처리됨"으로 답하고 넘어간다. **지적이 나올 때마다 스택을 갈아엎는 것이 아니라, 기존 문서(PRD·화면 설계)로 감당되는지 먼저 확인한다.** 멈추는 기준은 지금까지와 같다 — 치명적 지적이 없으면 확정한다.

### 실습 5.1

1. 5.1절의 프롬프트로 후보를 요청하고, AI의 제안 중 최소 하나를 **제약사항이나 신호 없음을 근거로 거절**하여 결정표에 기록하라.
2. 완성된 결정표에 5.4절의 검토를 적용하라. 받은 지적이 스택 변경 사유인지, 기존 문서로 감당되는지 구분하여 답하라.

## 6. 결정 기록 — 구현 단계로 넘어가는 마지막 산출물

본 강의의 산출물인 기술 스택 결정표는 다음 형식으로 정리해 둔다.

**완성 예시 — pcapeek**:

```text
[기술 스택 결정표]
① 언어:  Python (표준 라이브러리만)
         — 실습실 기본 설치, 전원 경험, AI가 가장 잘 다룸
② 형태:  정적 HTML 리포트, CSS 파일 내 포함
         — 화면 설계에서 결정, 외부 자원 금지 원칙
③ 저장:  없음 (입력 파일 읽기만)
④ 실행:  사용자 컴퓨터의 터미널

버린 후보:
- C — 컴파일러 설치 필요, 학습 부담
- JavaScript — 브라우저의 파일 접근 제한
- scapy·matplotlib — 외부 라이브러리, 설치 권한 제약
- 웹 프레임워크·데이터베이스·Docker — 필요 신호가 Must에 없음
```

이 표는 구현 단계에서 AI에게 주는 지시문에 **금지 조항의 형태로** 들어간다 — "Python 표준 라이브러리만 사용할 것", "외부 CSS 프레임워크를 불러오지 말 것". 결정표의 한 줄 한 줄이 AI의 이탈을 막는 울타리가 되는 것이다. 이로써 기획 챕터의 세 산출물 — **PRD, 화면 설계 문서, 기술 스택 결정표** — 가 모두 갖춰졌다.

> **권장 이미지**: 기획 3종 산출물이 구현 지시문으로 합쳐지는 그림 1장. "왼쪽에 문서 3장(PRD, 화면 설계, 기술 스택 결정표)이 세로로 놓여 있고, 화살표가 오른쪽의 'AI에게 주는 지시문' 문서 한 장으로 모이는 다이어그램. 지시문 문서 안에 '핵심 기능 / 안 만들 것 / 화면 모양 / 사용 기술' 네 줄이 보인다. 한글, 흰 배경, 단정한 플랫 스타일."
{: .prompt-tip }

### 실습 6.1

실습 3.1(환경 요소 판정)·4.1(후보 비교)·5.1(AI 토의)의 결과를 위 형식의 결정표 한 장으로 정리하라. 버린 후보에는 모두 이유가 붙어 있어야 한다.

| 용어 | 영문 | 설명 |
|---|---|---|
| 기술 스택 | Tech Stack | 프로그램을 만들고 실행하는 데 쓰는 기술의 조합 |

| 컨테이너 | Container (Docker) | 프로그램과 실행 환경을 함께 포장해 어디서든 같게 실행하는 기술 |
