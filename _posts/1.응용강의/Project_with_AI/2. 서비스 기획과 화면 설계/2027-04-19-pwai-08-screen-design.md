## 1. 왜 화면부터 설계하는가

프로젝트의 완성 여부는 코드가 아니라 **화면으로 확인**된다. PRD의 사용자 시나리오에서 "화면에 결과가 표시된다"까지는 정했지만, **정확히 어떤 모양으로** 표시되는지는 아직 정하지 않았다.

화면을 정하지 않으면 AI가 임의로 결정하며, 그 결정은 실행할 때마다 달라진다 — 어떤 실행에서는 표로, 어떤 실행에서는 목록으로, 순서도 매번 바뀐다. 화면을 먼저 그려 두면 AI는 정해진 모양대로 채우기만 하면 되므로 결과가 안정된다.

이번 강의의 공통 예제 pcapeek은 실행하면 결과를 담은 웹 페이지 파일(`report.html`)을 만들어 브라우저로 여는 방식이다. 두 가지 방식을 비교하면 다음과 같다.

| 방식 | 설명 | 채택 여부 |
|---|---|---|
| **정적 리포트 파일** | 실행할 때마다 HTML 파일 하나를 생성하고 브라우저로 연다 | 채택 — 서버·포트 개념 없이 파일 하나로 완결 |
| 웹 서버 방식 | 서버를 상시 가동하고 브라우저에서 접속한다 | 제외 — 서버 운영·업로드 처리 등 학습 부담이 크다 |

서버가 없어도 브라우저에서 렌더링되는 순간 HTML·CSS로 구성된 정식 웹 페이지이며, 파일 하나로 완결되므로 인터넷 연결 없이도 동작한다.

---

## 2. 좋은 웹 리포트의 다섯 가지 원칙

| 원칙 | 이유 | pcapeek 적용 |
|---|---|---|
| **정보 위계** — 요약 먼저, 세부 나중 | 끝까지 읽지 않아도 핵심을 알 수 있다 | 최상단 카드에 패킷 수·크기 요약 |
| **한 페이지 완결** | 파일 하나로 관리·공유가 쉽다 | 단일 report.html |
| **숫자에는 단위** | "22.3"만으로는 초인지 KB인지 알 수 없다 | `22.3 KB`, `65개` |
| **색은 아이콘과 함께** | 색만으로 표시하면 색각 이상 사용자가 인지하지 못한다 | 경고는 빨간 배경 + ⚠ 아이콘 병행 |
| **외부 자원 금지** | 외부 CDN·폰트를 부르면 인터넷이 없을 때 페이지가 깨진다 | CSS를 `<style>`로 파일 안에 포함 |

특히 마지막 원칙이 자주 깨진다. AI는 화면을 꾸미기 위해 외부 CSS 프레임워크나 웹폰트를 습관적으로 불러오는데, 인터넷이 제한된 실습 환경에서는 그 순간 페이지가 깨진다.

## 3. 벤치마킹 — 잘 만든 화면에서 배우기

빈 화면 앞에서 처음부터 배치를 생각해 내기는 어렵다. 다행히 우리가 만들려는 "검사 결과를 보여주는 리포트"는 이미 세상에 잘 만들어진 예가 많다. **벤치마킹(Benchmarking)**이란 비슷한 문제를 푼 화면을 관찰하여 그 **구조와 패턴**을 배우는 일이다. 디자인을 그대로 복제하는 것이 아니라, "정보를 어떤 순서로, 어떻게 강조해 보여주는가"를 배운다.

### 3.1 어디서 찾는가

내 프로젝트와 소재가 같은 서비스를 찾을 필요는 없다. **"화면의 성격"이 같은 것**을 찾는다. pcapeek과 photosort는 모두 "무언가를 검사해서 요약·경고를 보여주는 화면"이므로, 다음과 같은 곳이 좋은 관찰 대상이다.

| 관찰 대상 | 어디서 보는가 | 우리와 닮은 점 |
|---|---|---|
| 인터넷 속도 측정 결과 | fast.com, speedtest.net | 핵심 숫자 하나를 크게, 세부는 아래에 |
| 웹페이지 성능 리포트 | 브라우저 개발자 도구의 Lighthouse | 점수 요약 → 항목별 세부 → 경고 목록 |
| 백신 검사 결과 화면 | PC에 설치된 백신 프로그램 | "위협 N개 발견"을 색으로 강조 |
| 스마트폰 저장 공간 분석 | 휴대폰 설정 → 저장 공간 | 분류별 막대그래프, 정리 대상 안내 |
| 은행 앱의 월간 소비 리포트 | 본인이 쓰는 은행·카드 앱 | 월별 분류, 요약 카드 |

모두 무료로, 지금 가진 기기에서 바로 열어 볼 수 있는 것들이다.

### 3.2 무엇을 관찰하는가 — 다섯 가지 질문

화면을 열었으면 "예쁘다/안 예쁘다"가 아니라 다음 다섯 가지를 관찰하고 **기록**한다.

```text
1. 첫 3초에 무엇이 보이는가? (가장 크게, 가장 위에 있는 것)
2. 숫자를 어떻게 보여주는가? (단위, 크기, 색)
3. 위험·경고를 어떻게 강조하는가? (색, 아이콘, 위치)
4. 정보가 어떤 순서로 배치되어 있는가? (요약이 먼저인가, 세부가 먼저인가)
5. 한 화면에 영역(카드)이 몇 개인가?
```

**관찰 기록 예시 — Lighthouse 성능 리포트를 열어 본 결과 (pcapeek에 적용)**:

| 관찰한 것 | 우리 리포트에 적용 | 적용하지 않는 것 (이유) |
|---|---|---|
| 최상단에 종합 점수를 큰 원으로 표시 | 요약 카드를 최상단에 (숫자를 크게) | 점수화 자체 — 위험 개수를 점수로 환산하면 근거를 설명하기 어렵다 |
| 색을 3단계(빨강·주황·초록)로만 사용 | 경고는 빨강 하나로 통일 (우리는 판정이 위험/정상 둘뿐) | 3단계 색 — 중간 단계 판정 기준이 없다 |
| 문제 항목을 펼치면 상세가 나옴 | — | 접기/펼치기 — 여러 상태를 관리해야 해서 범위를 넘는다 |
| 항목마다 "왜 문제인가" 한 줄 설명 | 경고 카드에 "암호화되지 않아 제3자가 볼 수 있음" 한 줄 추가 | — |

이 표가 벤치마킹의 산출물이다. **"적용하지 않는 것"과 그 이유를 남기는 것**이 적용할 것 목록만큼 중요하다 — PRD의 Out of Scope와 같은 원리로, 나중에 "이것도 넣으면 어떤가"에 흔들리지 않기 위함이다.

### 3.3 AI에게 벤치마킹 분석 시키기

관찰한 화면을 AI에게 분석시킬 수도 있다. AI 코딩 도구는 **스크린샷 이미지를 붙여 넣으면 화면을 읽을 수 있다**.

```text
[관찰한 화면의 스크린샷을 붙여 넣는다]

이 화면은 인터넷 속도 측정 결과 화면이야.
나는 통신 기록 파일을 검사해서 요약과 경고를 보여주는
한 페이지짜리 웹 리포트를 만들려고 해.

1. 이 화면이 정보를 배치한 순서와 강조 방법을 분석해 줘.
2. 내 리포트에 적용할 만한 점 3가지, 적용하면 안 될 점 2가지를
   이유와 함께 골라 줘.
아직 코드는 쓰지 마.
```

"적용하면 안 될 점"까지 함께 묻는 것에 주목한다. 적용할 점만 물으면 AI는 화면의 모든 요소를 좋게 평가하며 다 가져오라고 하는 경향이 있다. 물론 최종 선별은 3.2절의 표에 학생이 직접 결정해 기록한다.

### 3.4 주의 — 배우는 것과 베끼는 것

벤치마킹으로 가져오는 것은 **구조와 패턴**(정보 순서, 강조 방법, 영역 구성)이다. 다음은 가져오면 안 된다.

- 로고·상표·아이콘 이미지 파일 자체
- 화면 문구를 그대로 복사한 것
- 특정 서비스와 혼동될 정도로 똑같은 배색·모양

"요약을 위에, 경고를 색으로" 같은 패턴은 누구의 소유도 아니지만, 남의 화면을 통째로 복제하면 표절이 된다.

### 실습 3.1

3.1절의 표에서 두 곳 이상을 직접 열어 보고, 3.2절의 다섯 질문에 따라 관찰 기록 표를 작성하라. "적용하지 않는 것"에는 반드시 이유를 붙인다.

```text
| 관찰한 것 | 우리 리포트에 적용 | 적용하지 않는 것 (이유) |
|---|---|---|
| {           } | {           } | {           } — {이유} |
```

> **권장 이미지**: 벤치마킹 3단계 흐름도 1장. "왼쪽에 여러 서비스 화면 축소판(속도 측정, 성능 리포트, 백신 검사)이 겹쳐 있고, 가운데 돋보기 아이콘과 '관찰 기록(5가지 질문)' 메모, 오른쪽에 내 와이어프레임으로 화살표가 이어지는 그림. 화살표 중간에 '구조만 가져온다, 디자인은 베끼지 않는다' 문구. 한글, 흰 배경, 플랫 일러스트 스타일."

## 4. 와이어프레임 — 손으로 먼저 그리기

> **와이어프레임(Wireframe)**이란 색·글꼴 등 시각 요소를 배제하고, 화면의 **영역 배치와 정보 순서**만을 선으로 표현한 설계도이다.

문자만으로도 충분히 그릴 수 있다. 박스 문자로 "여기가 하나의 영역(카드)"임을 표시한다.

**작성 예시 — pcapeek** (이후 구현 단계에서 이 배치 그대로 완성한다):

```text
┌─────────────────────────────────────────────┐
│  pcapeek 리포트 — sample.pcap                 │
├─────────────────────────────────────────────┤
│  요약                                         │
│  패킷 65개 · 22.3 KB · Ethernet · 4.2초        │
├─────────────────────────────────────────────┤
│  프로토콜 비율                                 │
│  TCP   ███████████░░░░░  66.7%               │
│  ICMP  ████░░░░░░░░░░░░  20.0%               │
│  UDP   ███░░░░░░░░░░░░░  13.3%               │
├─────────────────────────────────────────────┤
│  가장 많이 오간 상대·포트 (표, 상위 5)           │
├─────────────────────────────────────────────┤
│  ⚠ 경고 — 암호화되지 않은 통신 16개 발견          │
│    HTTP 12개 · Telnet 4개                     │
└─────────────────────────────────────────────┘
```

막대 문자(`█`, `░`)까지 정해 둔 것에 주목한다. "그래프로 보여준다"라고만 쓰면 AI가 어떤 그래프를 그릴지 알 수 없으나, 문자 하나까지 정해 두면 해석의 여지가 없다.

**작성 예시 — photosort** (보조 예제. 막막하면 이 틀을 그대로 베끼고 항목만 바꾼다):

```text
┌─────────────────────────────────────────────┐
│  photosort 리포트 — Pictures/                 │
├─────────────────────────────────────────────┤
│  요약: 전체 사진 482장 (3.1 GB)                │
├─────────────────────────────────────────────┤
│  월별 개수                                     │
│  2027-01  ████████░░░░  120장                 │
│  2027-02  █████░░░░░░░   62장                 │
│  2027-03  ██████████░░  180장                 │
├─────────────────────────────────────────────┤
│  ⚠ 경고 — 중복 의심 파일 3개 (합계 12MB)         │
└─────────────────────────────────────────────┘
```

두 예시의 뼈대는 동일하다 — **제목 → 요약 → 분류 막대그래프 → 경고**. 뼈대는 유지하고 무엇을 세는지만 바꾼 것이다. 벤치마킹 기록(3절)에서 "적용"으로 골라 둔 것이 있다면 이 단계에서 와이어프레임에 반영한다.

### 실습 4.1

자신의 프로젝트 화면을 위 두 예시 중 하나를 본떠 문자로 그려라. 영역 순서, 각 영역의 내용, 제목까지 실제 화면에 나올 모양 그대로 적는다.

## 5. 정보 위계 — 무엇을 먼저 보여줄 것인가

사용자가 화면을 열었을 때 **3초 안에 알아야 하는 것 하나**를 정하면, 나머지 배치는 자연스럽게 따라온다.

**작성 예시 — pcapeek**: 3초 안에 알아야 할 것은 "위험한 통신이 있는가"이다. 따라서 경고 카드를 빨간 배경 + ⚠ 아이콘으로 강조한다. 다만 화면 최상단이 아니라 하단에 배치하는데, 위쪽의 요약(패킷 수·프로토콜 비율)을 먼저 읽어야 경고가 나온 맥락이 이해되기 때문이다.

| 순서 | 내용 | 배치 이유 |
|---|---|---|
| 1 | 파일 이름·기본 정보 | 지금 무엇을 보고 있는지부터 확인 |
| 2 | 프로토콜 비율 | 전체 그림 파악 |
| 3 | 상위 통신 상대 | 세부 정보 |
| 4 | **경고** | 가장 중요한 결론을 색·아이콘으로 강조 |

**작성 예시 — photosort**: 3초 안에 알아야 할 것은 "용량을 차지하는 중복 파일이 있는가"이며, 하단에 빨간 카드 + ⚠ 아이콘으로 배치한다.

### 실습 5.1

```text
3초 안에 알아야 하는 것: {                                     }
배치 위치와 강조 방법:   {                                     }
```

## 6. "하지 말 것" 목록

AI에게 화면 구현을 맡길 때 자주 발생하는 실수를 미리 금지 목록으로 만들어 둔다.

```text
- 외부 CDN·폰트·이미지 불러오기  — 인터넷이 없으면 페이지가 깨진다
- 색에만 의존한 위험 표시        — 색각 이상 사용자가 인지하지 못한다 (아이콘 병행)
- 화려한 애니메이션·자동재생      — 정보 전달과 무관하고 페이지가 무거워진다
- 여러 페이지로 분할            — 파일 하나(report.html)로 완결해야 한다
```

**작성 예시 — photosort의 추가 항목**:

```text
- 사진 원본을 리포트에 삽입      — 파일이 무거워지고 개인정보 노출 우려가 있다.
                               파일 이름과 개수만 표시한다
- 개수를 "약 500장"으로 반올림   — 정확한 수치(482장)를 보여야 신뢰할 수 있다
```

### 실습 6.1

자신의 프로젝트에서 AI가 저지를 법한 실수를 1~2개 추가하라. 각 항목에는 금지 이유를 붙인다.

## 7. AI와 토의하며 화면 확정하기 — 실제 상호작용

혼자 그리기 막막하다면, 완성된 설계를 만들어 던지는 대신 **AI와 대화하며 함께 결정**할 수 있다. PRD를 완성할 때와 역할 분담은 같다 — **AI는 안을 내고 지적하는 역할, 학생은 고르고 결정하는 역할**이다. 흐름은 "제안 요청 → 선택 → 수정 요청 → 확정"이며, 확정 전에 검토·수정을 반복한다(7.2절).

### 7.1 제안받고 고르기

제안을 요청할 때 **벤치마킹 기록(3절)의 "적용" 목록을 함께 붙이면** AI의 안이 내 관찰에 근거하게 된다. 빈손으로 "예쁘게 제안해 달라"고 하면 AI가 흔히 만드는 정형화된 화면이 나온다.

**대화 예시 — photosort**:

```text
사용자: 사진 정리 결과를 웹 페이지(report.html)로 보여줄 것인데,
       레이아웃을 카드형으로 할지 표로 할지 정하지 못했다.
       월별 개수와 중복 파일 경고를 보여주고 싶다.
       벤치마킹에서 정한 것: 핵심 숫자는 크게 최상단에,
       경고는 빨간 카드 + 아이콘으로.
       레이아웃 안을 2~3개 제안하라. 아직 코드는 쓰지 마라.

AI:    세 가지 안을 제안합니다.
       안 A — 카드형: 상단 요약 카드 → 월별 막대그래프 → 하단 경고 카드
       안 B — 표 위주: 월별 표 하나 + 상단 경고 문구 (구현이 가장 단순)
       안 C — 대시보드형: 좌측 요약 사이드바 + 우측 그래프 (구조가 복잡)

사용자: 안 A로 하되, 경고 카드에 구분선을 넣어 더 강조하라.

AI:    수정한 와이어프레임입니다. [4절의 photosort 예시와 같은 배치]
```

두 가지에 유의한다.

1. **"아직 코드는 쓰지 마라"를 포함한다** — 지금은 설계 단계이다.
2. **"알아서 예쁘게 다 만들어 달라"는 지시는 피한다** — 최소한 "무엇을 먼저 보여줄지"(5절)와 "외부 자원 금지"(6절)는 직접 정한 뒤, 나머지 배치를 AI와 다듬는다.

### 7.2 와이어프레임 검토·수정 반복

레이아웃을 골랐으면, PRD 때와 마찬가지로 **완성된 와이어프레임을 AI에게 공격하게** 하고, 지적을 반영한 수정본으로 다시 검토받는다.

```text
다음은 내 리포트 화면의 와이어프레임이야.

[와이어프레임 전체를 붙여 넣는다]

아래 기준으로 검토자의 입장에서 비판해 줘.
1. 좋은 웹 리포트의 원칙(정보 위계·한 페이지·단위·색+아이콘·외부 자원 금지)에
   어긋난 곳이 있는지
2. 3초 안에 알아야 하는 것이 실제로 3초 안에 보이는지
3. "하지 말 것" 목록과 충돌하는 요소가 있는지
4. 사용자 시나리오의 "잘못될 수 있는 것" 상황일 때 이 화면이 어떻게 보일지
   (예: 경고가 0개일 때 경고 카드는 어떻게 되는가)
지적은 심각한 것부터 순서대로. 아직 코드는 쓰지 마라.
```

**검토·수정 반복 예시 — photosort**:

```text
[1차 검토] AI의 지적 2건
 ① 중복이 0개일 때 경고 카드가 어떻게 되는지 정해지지 않았다
 ② 월별 막대그래프에 달이 12개를 넘으면(여러 해) 화면이 길어진다

[학생의 수정 결정]
 ① 반영 — 경고가 없으면 빨간 카드 대신 "중복 없음 ✓" 초록 카드를 표시
 ② 반영 — 최근 12개월만 표시하고 "이전 N장"으로 합산 (와이어프레임에 추가)

[2차 검토] 수정본으로 재검토 → 새 지적은 표현 수준(제목 문구) → 반복 종료
```

①이 특히 중요하다. 와이어프레임은 보통 "결과가 있는 경우"만 그리게 되는데, **PRD 사용자 시나리오의 "잘못될 수 있는 것"들이 화면에서 어떻게 보일지**는 검토에서 자주 발견되는 구멍이다. 멈추는 기준은 PRD 때와 같다 — 새 지적이 사소해지면(2~3회면 충분) 확정한다.

### 실습 7.1

1. 실습 4.1의 와이어프레임(막혔다면 전체 레이아웃)에 대해 7.1절처럼 제안을 요청하라. 벤치마킹 기록의 "적용" 목록을 함께 붙인다. 받은 안 중 하나를 선택하거나 조합하라.
2. 확정 전에 7.2절의 검토 프롬프트를 적용하고, 수정본으로 재검토를 **최소 1회 이상** 진행하라. "결과가 0건일 때 화면"에 대한 지적이 나왔는지 확인하고, 나오지 않았다면 직접 물어보라.

## 8. 화면 설계 문서로 정리

본 강의의 산출물을 모으면 화면 설계 문서가 완성된다.

| 순서 | 항목 | 출처 |
|---|---|---|
| 1 | 출력 원칙 5가지 | 2절 |
| 2 | 벤치마킹 관찰 기록 (적용/비적용과 이유) | 3절 |
| 3 | 와이어프레임 (검토·수정을 거친 최종본) | 4절 + 7절 |
| 4 | 정보 위계 (3초 원칙) | 5절 |
| 5 | 하지 말 것 목록 | 6절 |

이 문서는 PRD(문제·요구사항·사용자 시나리오)와 함께, 구현 단계에서 AI에게 전달할 지시문의 재료가 된다. 특히 와이어프레임은 출력 형식 지침에 **그대로 붙여 넣어** 사용한다.
