## 1. Use Case란

> **Use Case**란 사용자(액터)가 목표를 이루기 위해 시스템과 주고받는 **구체적인 상호작용 시나리오**이다.

요구사항이 "무엇을 할 수 있어야 한다"라면, Use Case는 "실제로 어떤 순서로 쓰는가"를 그린 것이다.

| 구성 요소 | 의미 |
|---|---|
| **액터(Actor)** | 시나리오의 주인공 (사람 또는 다른 시스템) |
| **목표(Goal)** | 액터가 이루고자 하는 것 |
| **사전 조건(Precondition)** | 시나리오 시작 전에 갖춰져 있어야 하는 것 |
| **기본 흐름(Main Flow)** | 모든 것이 정상일 때 순서대로 일어나는 일 |
| **예외 흐름(Exception Flow)** | 중간에 무언가 잘못되었을 때 일어나는 일 |

## 2. 작성 예시 — pcapeek의 Use Case

| 항목 | 내용 |
|---|---|
| 액터 | 네트워크를 처음 배우는 1학년 |
| 목표 | 수집한 통신 기록 파일에 위험한 통신이 있는지 확인한다 |
| 사전 조건 | 분석할 `.pcap` 파일을 이미 가지고 있다 |

**기본 흐름**:

```text
1. 사용자가 터미널에 프로그램 명령과 파일 이름을 입력한다
2. 프로그램이 파일을 읽고 패킷을 분석한다
3. 프로그램이 분석 결과를 담은 report.html 파일을 만들고,
   기본 브라우저로 자동으로 연다
4. 웹 페이지에 패킷 수·프로토콜 비율·상위 통신 상대가 표시되고,
   암호화되지 않은 프로토콜(HTTP·Telnet)의 개수가 경고로 강조된다
5. 사용자가 경고를 보고 어떤 통신이 위험한지 이해한다
```

**예외 흐름**:

```text
2a. 파일이 존재하지 않는다
    → "파일을 찾을 수 없습니다"를 출력하고 오류 코드로 종료한다

2b. 파일이 올바른 형식이 아니다
    → "지원하는 형식이 아닙니다"를 출력하고 오류 코드로 종료한다

2c. 해석할 수 없는 패킷이 섞여 있다
    → 해당 패킷만 건너뛰고 "건너뜀 N개"로 알린다. 전체가 멈추지 않는다

3a. 브라우저가 자동으로 열리지 않는다
    → 출력된 report.html의 경로를 사용자가 직접 브라우저에서 연다
```

### 예외 흐름을 놓치면 안 되는 이유

정상 흐름만 설계하면, 사용자가 파일 이름을 잘못 입력하는 순간 프로그램이 이해할 수 없는 오류를 내며 멈춘다. 처음 쓰는 사용자는 "내가 무엇을 잘못했는가"를 알 수 없어 그대로 포기한다. **기본 흐름의 각 단계마다 "여기서 무엇이 잘못될 수 있는가"를 한 번씩 물어야** 한다. 이 질문에서 나온 답이 "잘못된 입력에도 죽지 않는다"는 비기능 요구사항의 근거가 된다.

### 작성 예시 — photosort의 Use Case (보조 예제)

```text
액터: 사진이 수천 장 쌓인 대학생
목표: 어떤 사진이 중복인지 확인하고 정리 대상을 파악한다
사전 조건: 사진이 들어 있는 폴더가 있다

기본 흐름:
1. 사용자가 폴더 경로를 지정하여 프로그램을 실행한다
2. 프로그램이 폴더를 훑어 사진 정보를 수집한다
3. 월별 개수와 중복 의심 파일 목록이 리포트로 표시된다

예외 흐름:
1a. 폴더가 존재하지 않는다 → 오류 메시지 출력 후 종료
2a. 사진이 아닌 파일이 섞여 있다 → 건너뛰고 개수만 보고
```

### 실습 2.1

자신의 프로젝트로 Use Case를 작성하라. 예외 흐름을 최소 2개 이상 포함한다.

```text
액터:       {                                               }
목표:       {                                               }
사전 조건:   {                                               }

기본 흐름:
1. {                                                        }
2. {                                                        }
3. {                                                        }

예외 흐름:
{N}a. {무엇이 잘못될 수 있는가}
    → {그때 시스템은 어떻게 반응하는가}
```

## 3. 서비스 기획서로 통합

### 3.1 기획서의 구성

지금까지 각 강의에서 작성한 산출물을 순서대로 모으면 그 자체가 서비스 기획서가 된다. 새로 쓸 것은 없으며, 다음 순서로 정리한다.

| 순서 | 항목 | 산출된 강의 |
|---|---|---|
| 1 | 비즈니스 모델 캔버스(9블록) | 비즈니스 모델 챕터 |
| 2 | 문제 진술문 | 6강 |
| 3 | 요구사항 (기능·비기능) | 6강 |
| 4 | 우선순위 (MoSCoW, Won't의 이유 포함) | 6강 |
| 5 | Use Case (기본·예외 흐름) | 7강(본 강의) |

이 기획서는 이후 구현 단계에서 AI에게 전달할 지시문의 재료가 된다. 특히 다음 대응 관계를 기억해 두면 좋다 — **Must 목록은 "핵심 기능"으로, Won't 목록은 "안 만들 것"으로, Use Case의 기본·예외 흐름은 "완료 기준"으로** 그대로 옮겨진다.

### 3.2 AI에게 기획서 검토받기

기획서 초안이 완성되면 AI 코딩 도구(Claude Code 등)에 검토를 요청한다. 다음 지시문을 사용한다.

```text
다음은 내가 만들 서비스의 기획서 초안이야.

[기획서 전문을 붙여 넣는다]

아래 관점에서 검토해 줘. 아직 코드는 쓰지 마.
1. 문제 진술문에 해결책이 섞여 있지는 않은지
2. Must 요구사항이 서로 겹치거나 빠진 것이 없는지
3. Use Case의 예외 흐름이 충분한지 (빠뜨린 경우가 있으면 짚어 줘)
4. Won't 항목에 이유가 모두 붙어 있는지
```

두 가지 원칙에 유의한다.

1. **"아직 코드는 쓰지 마"를 반드시 포함한다.** AI는 지시하지 않아도 코드부터 작성하려는 경향이 있다. 지금은 기획의 완성도를 확인하는 단계이지 구현 단계가 아니다.
2. **AI가 질문 없이 "네, 알겠습니다"라고만 답하면 오히려 의심한다.** 기획서가 이미 완벽하거나 AI가 대충 넘어간 것인데, 후자일 가능성이 높다. "정말 빠진 예외 흐름이 없는가? 세 가지만 더 짚어 봐라"라고 한 번 더 요구한다.

AI가 던지는 질문(예: "IPv6 패킷이 나오면 건너뛰는가, 오류 처리하는가?")에 답하는 과정에서 기획서의 빈틈이 메워진다. 답한 내용은 반드시 기획서 본문에 반영한다.

### 실습 3.1

1. 3.1절의 순서대로 자신의 기획서를 한 문서로 통합하라.
2. AI에게 위 지시문으로 검토를 요청하고, 받은 질문 중 두 가지 이상에 답하여 기획서에 반영하라.

## 핵심 용어 정리

| 용어 | 영문 | 설명 |
|---|---|---|
| 액터 | Actor | Use Case의 주체 (사용자 또는 외부 시스템) |
| 기본 흐름 | Main Flow | 정상 상황의 단계별 시나리오 |
| 예외 흐름 | Exception Flow | 오류·이탈 상황의 시나리오 |
| 사전 조건 | Precondition | 시나리오 시작 전 충족되어야 할 조건 |
| 기획서 | Service Plan | 문제·요구사항·시나리오를 통합한 문서 |
