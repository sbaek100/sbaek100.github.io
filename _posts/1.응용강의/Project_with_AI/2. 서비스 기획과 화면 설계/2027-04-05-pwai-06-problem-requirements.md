## 0. 공통 예제 소개 — pcapeek

이번 강의부터 과정 후반의 구현 실습까지 관통하는 공통 예제는 **pcapeek**이다.

> **pcapeek**: 컴퓨터가 주고받은 통신 기록 파일(`.pcap`)을 읽어, 무슨 통신이 오갔고 위험한 것은 없는지 **웹 리포트로 알려 주는 프로그램**. 암호화되지 않은 통신(HTTP·Telnet 등)은 제3자가 내용을 훔쳐볼 수 있으므로, 이를 찾아 경고하는 것이 핵심 기능이다.

비교용 보조 예제로 **photosort**(사진 폴더를 읽어 월별 개수와 중복 파일을 알려 주는 프로그램)를 함께 사용한다. 두 예제의 소재는 다르지만 기획의 틀은 같다는 것을 보이기 위함이다.

## 1. 문제 진술문 — 문제를 한 문단으로

### 1.1 작성 공식

기획의 출발점은 문제를 한 문단으로 압축하는 것이다.

```text
[사용자]는 [상황]에서 [문제]를 겪는다. 왜냐하면 [원인].
```

**작성 예시 — pcapeek**:

```text
네트워크를 처음 배우는 1학년은, 실습에서 수집한 통신 기록 파일을 열어 보아도
그 안에 위험한 통신이 있는지 스스로 판단하지 못한다.
왜냐하면 기존 분석 도구는 전문가용이라 정보량이 많고 용어가 낯설어,
초심자가 핵심(암호화되지 않은 통신)을 걸러내지 못하기 때문이다.
```

**작성 예시 — photosort**:

```text
사진을 자주 찍는 대학생은, 수천 장이 쌓인 사진 폴더에서
어떤 파일이 중복이고 언제 찍은 것인지 파악하지 못한다.
왜냐하면 파일 이름만으로는 내용을 알 수 없고,
하나하나 열어 보기에는 양이 너무 많기 때문이다.
```

### 1.2 가장 흔한 실수 — 해결책이 문제 안에 숨어 있다

| 구분 | 예시 | 진단 |
|---|---|---|
| 나쁜 진술문 | "학생은 위험한 통신을 **자동으로 알려주는 도구가 없어서** 곤란하다" | "자동으로 알려주는 도구"라는 해결책이 이미 문제 안에 들어 있다 |
| 좋은 진술문 | "학생은 통신 기록 안에 위험한 통신이 있는지 스스로 판단하지 못한다" | 순수하게 문제만 남아 있다 |

해결책이 문제 안에 들어가면 **다른 해결책을 떠올릴 여지가 사라진다**. 문제 진술 단계에서는 "무엇이 어렵다"만 남기고, 어떻게 풀지는 다음 단계로 미룬다.

### 1.3 점검 목록

- 문장 안에 "~할 수 있는 도구", "~해 주는 기능" 같은 해결책 표현이 없는가
- "왜냐하면" 뒤에 진짜 원인이 있는가 (단순히 "불편해서"가 아니라)

### 실습 1.1

자신의 프로젝트(또는 BMC 실습에서 다룬 주제)로 문제 진술문을 작성하라.

```text
{사용자}는 {상황}에서 {문제}를 겪는다.
왜냐하면 {원인}.
```

## 2. 해결 아이디어 발산 — 질보다 양

문제 하나를 푸는 방법은 하나가 아니다. 우선 최대한 많이 떠올린 뒤 선택한다. 이 단계에서는 **질보다 양**이며, 비현실적인 아이디어도 일단 기록한다.

**작성 예시 — pcapeek의 문제("위험한 통신을 스스로 판단하지 못한다")에 대한 아이디어**:

```text
1. 위험한 프로토콜(HTTP·Telnet 등)을 자동으로 찾아 경고로 보여준다   ← 채택
2. AI 챗봇에게 기록 파일을 통째로 물어본다                (범위가 너무 큼)
3. 조교가 실시간으로 화면을 봐 준다                       (자동화가 아님)
4. 분석 도구 사용법 동영상 강의를 만든다                   (도구가 아니라 교육)
5. 위험도를 색깔로 구분해 한눈에 보여준다                  ← 1과 합쳐서 채택
```

기각한 아이디어에도 기각 사유를 한 줄씩 남긴다. 이후 "이것도 해 보면 어떤가"라는 질문에 다시 흔들리지 않기 위함이다.

### 실습 2.1

작성한 문제 진술문에 대해 해결 아이디어를 5개 이상 나열하고, 채택·기각과 그 사유를 표시하라.

## 3. 요구사항 작성

### 3.1 기능 요구사항과 비기능 요구사항

| 종류 | 묻는 것 | pcapeek 예시 |
|---|---|---|
| **기능 요구사항** | 시스템이 **무엇을** 하는가 | 암호화되지 않은 프로토콜을 찾아 경고한다 |
| **비기능 요구사항** | 시스템이 **어떻게** 동작하는가 (성능·제약·사용성) | 파일 하나(10MB 이하)를 5초 안에 처리한다 |

두 종류가 모두 있어야 완전한 요구사항이다. 기능만 적으면 "얼마나 빨라야 하는지, 어떤 환경에서 돌아가야 하는지"가 빠지고, 비기능만 적으면 무엇을 만드는지 알 수 없다.

**작성 예시 — pcapeek의 비기능 요구사항**:

```text
- 인터넷 연결이 없어도 동작해야 한다 (실습실 네트워크가 제한될 수 있다)
- 별도 프로그램 설치 없이 동작해야 한다 (실습실 PC는 설치 권한이 없을 수 있다)
- 결과는 리포트 한 페이지 안에 보여야 한다
```

### 3.2 요구사항 문장 작성법 — 확인 가능하게

요구사항은 "[사용자]는 [행동]을 할 수 있어야 한다" 형식으로, **되었는지 안 되었는지 확인 가능한** 문장으로 작성한다.

| 모호한 표현 | 구체적 표현 |
|---|---|
| 위험을 알려준다 | 사용자는 암호화되지 않은 프로토콜(HTTP·Telnet)이 몇 개 있는지 화면에서 확인할 수 있어야 한다 |
| 통계를 보여준다 | 사용자는 가장 많이 오간 상대 주소·포트 상위 5개를 확인할 수 있어야 한다 |
| 쉽게 쓴다 | 사용자는 명령 하나로 리포트를 만들고, 브라우저로 열어 결과를 볼 수 있어야 한다 |

**작성 예시 — photosort**:

```text
1. 사용자는 폴더를 지정하면 월별 사진 개수를 확인할 수 있어야 한다
2. 사용자는 내용이 동일한 중복 파일의 목록과 총 용량을 확인할 수 있어야 한다
3. 시스템은 원본 파일을 삭제하거나 수정하지 않아야 한다
```

### 실습 3.1

2절에서 채택한 해결 아이디어를 요구사항 3~5개로 풀어 써라.

```text
1. {사용자}는 {구체적인 행동}을 할 수 있어야 한다
2. {사용자}는 {구체적인 행동}을 할 수 있어야 한다
3. 시스템은 {구체적인 조건}을 만족해야 한다
```

## 4. 우선순위 결정 — MoSCoW 기법

### 4.1 네 가지 등급

요구사항이 모두 같은 무게일 수는 없다. 시간은 유한하므로 무엇을 먼저 만들지 정해야 한다. **MoSCoW**는 널리 쓰이는 우선순위 결정 기법이다.

| 등급 | 의미 | pcapeek 예시 |
|---|---|---|
| **Must** (반드시) | 없으면 서비스가 성립하지 않는다 | 암호화 안 된 프로토콜을 찾아 경고한다 |
| **Should** (가능하면) | 있으면 훨씬 좋으나 없어도 동작한다 | 프로토콜 비율을 막대그래프로 보여준다 |
| **Could** (여유가 있다면) | 시간이 남을 때만 | 두 개의 기록 파일을 비교하는 기능 |
| **Won't** (이번에는 제외) | 이번 범위에서는 만들지 않는다 | 실시간 수집, 특수 파일 형식 지원 |

**Must만 모으면 그것이 곧 "핵심 기능"이며, 최소 기능 제품(MVP, Minimum Viable Product)의 범위가 된다.**

![](/assets/img/posts/2027-04-05-pwai-06-problem-requirements-1787453422430.png)
### 4.2 Won't에는 이유를 반드시 적는다

Won't 칸을 비워 두거나 항목만 나열하면, 개발 도중 "이것도 만들면 어떤가"라는 제안에 계속 흔들린다. **무엇을 안 만드는지와 왜 안 만드는지**를 함께 기록한다.

```text
나쁜 예: Won't — 실시간 수집
좋은 예: Won't — 실시간 수집. 저장된 파일만 다룬다.
         수집은 기존 표준 도구가 이미 잘하는 일이므로 중복 개발할 이유가 없다.
```

**작성 예시 — pcapeek의 Won't 목록**:

```text
- IPv6 해석      — 건너뛰고 개수만 센다
- 실시간 수집     — 저장된 파일만 다룬다. 수집은 표준 도구(tcpdump)가 한다
- 특수 파일 형식(pcapng 등) — 표준 pcap 형식만 지원한다
- 패킷 내용 표시  — 개인정보가 노출될 수 있다
```

이 형식(항목 + 이유)은 이후 AI에게 구현을 지시할 때 "안 만들 것" 목록으로 그대로 재사용된다. AI는 명시적으로 금지하지 않은 확장 기능을 계속 제안하는 경향이 있는데, 이유가 붙은 Won't 목록은 그 제안을 사전에 차단한다.

### 실습 4.1

작성한 요구사항을 MoSCoW 네 칸에 배치하라. Won't에는 반드시 이유를 붙인다.

```text
Must:   {                                                   }
Should: {                                                   }
Could:  {                                                   }
Won't:  {무엇} — {왜}
```

## 핵심 용어 정리

| 용어 | 영문 | 설명 |
|---|---|---|
| 문제 진술문 | Problem Statement | 사용자·상황·문제·원인을 담은 한 문단 |
| 기능 요구사항 | Functional Requirement | 시스템이 무엇을 하는지에 대한 요구 |
| 비기능 요구사항 | Non-functional Requirement | 성능·제약·사용성 등 동작 방식에 대한 요구 |
| MoSCoW | MoSCoW | Must/Should/Could/Won't로 우선순위를 나누는 기법 |
| MVP | Minimum Viable Product | 핵심 가치를 검증할 수 있는 최소 기능 제품 |
