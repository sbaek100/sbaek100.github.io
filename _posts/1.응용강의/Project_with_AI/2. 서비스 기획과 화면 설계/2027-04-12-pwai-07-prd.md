## 1. PRD란 무엇인가

지난 시간까지 문제 진술문·요구사항·MoSCoW 우선순위를 각각 따로 작성했다. 이 조각들은 아직 하나로 묶이지 않았다. AI 코딩 도구에게 프로젝트를 설명할 때마다 "저번에 정한 문제는 이거였고, 요구사항은..."을 매번 반복해야 한다면, 설명이 조금씩 달라지고 빠뜨리는 부분도 생긴다.

> **PRD(Product Requirements Document, 제품 요구사항 문서)**란 "무엇을, 누구를 위해, 왜, 어디까지 만드는가"를 하나의 문서로 정리한 합의 자료이다.

원래는 기획자가 개발팀에게 전달하기 위해 쓰던 업계 표준 문서다. 바이브 코딩에서는 이 문서를 **AI 코딩 도구에게 그대로 전달하는 지시문의 뼈대**로 재사용한다. 사람 개발팀이 PRD를 읽고 구현하듯, AI도 PRD를 읽고 구현한다. 차이가 있다면 AI는 문서에 없는 부분을 **임의로 지어서 채운다**는 점이며, 그래서 PRD의 빈틈이 사람 팀에서보다 더 위험하다.

### PRD가 있을 때와 없을 때

| 상황 | PRD 없이 | PRD로 |
|---|---|---|
| 여러 날에 걸쳐 개발 | 매번 맥락을 새로 설명해야 한다 | 문서를 그대로 붙여넣으면 된다 |
| 팀원 간 의견이 엇갈릴 때 | "내가 듣기로는 이랬는데"로 다툰다 | 문서가 최종 기준이 된다 |
| AI가 범위 밖 기능을 제안할 때 | 막을 근거가 없어 흔들린다 | "Out of Scope에 있다"고 근거를 댈 수 있다 |
| 시간이 지나 다시 열어볼 때 | 왜 이렇게 만들었는지 기억나지 않는다 | 문서에 이유가 그대로 남아 있다 |

**작성 예시 — pcapeek**: "암호화되지 않은 통신을 찾아 경고한다"는 요구사항 하나만 봐서는, 왜 IPv6는 다루지 않는지, 왜 실시간 수집은 하지 않는지 알 수 없다. PRD에는 이 결정들과 이유가 함께 남는다.

## 2. PRD의 필수 구성 요소

PRD는 백지에서 새로 쓰는 문서가 아니다. 절반 가까이는 **이미 6강에서 만들어 둔 것을 정해진 틀에 옮겨 담는 일**이다.

| 항목 | 묻는 질문 |
|---|---|
| 개요(Overview) | 무엇을, 왜 만드는가 |
| 목표와 성공 기준(Goals & Success Metrics) | 무엇이 되면 성공인가, 숫자로 확인할 수 있는가 |
| 대상 사용자(Target User) | 누구를 위한 것인가 |
| 문제 정의(Problem Statement) | 사용자가 겪는 문제는 무엇인가 |
| 범위(Scope: In / Out) | 무엇을 만들고 무엇을 안 만드는가 |
| 요구사항(Requirements) | 시스템이 무엇을, 어떻게 해야 하는가 |
| 사용자 시나리오(User Scenario) | 실제로 어떤 순서로 사용하는가 |
| 제약사항(Constraints) | 어떤 조건 안에서 만드는가 |
| 열린 질문(Open Questions) | 아직 결정하지 못한 것은 무엇인가 |

이번 강의는 3~7절에서 각 항목을 채운 뒤, **8절에서 AI와 대화하며 문서 전체를 완성**하는 순서로 진행한다.

> **권장 이미지**: PRD 한 장 구조 다이어그램. "종이 한 장 위에 9개의 칸(개요·목표와 성공기준·대상사용자·문제정의·범위·요구사항·사용자시나리오·제약사항·열린질문)이 표 형태로 배치된 그림. 각 칸에 항목 이름과 그 항목이 묻는 질문이 작은 글씨로 적혀 있다. 한글, 흰 배경, 단정한 다이어그램 스타일."
{: .prompt-tip }

## 3. 목표와 성공 기준 — 측정 가능하게 쓰기

### 3.1 목표만으로는 부족하다

"편리한 프로그램을 만든다"는 목표는 언제 달성되었는지 아무도 판단할 수 없다. 목표에는 반드시 **성공 기준**이 따라야 하며, 성공 기준은 숫자나 관찰 가능한 사실로 확인할 수 있어야 한다.

| 모호한 성공 기준 | 구체적인 성공 기준 |
|---|---|
| 사용자가 만족한다 | 실습 참가자 10명 중 8명 이상이 리포트만 보고 위험 통신 종류를 맞힌다 |
| 빠르게 동작한다 | 10MB 이하 파일을 5초 안에 처리한다 |
| 정리가 잘 된다 | 중복 파일 판정 정확도가 수동 확인 대비 95% 이상 일치한다 |

**작성 예시 — pcapeek**:

```text
목표: 네트워크를 처음 배우는 1학년이, 조교 도움 없이도
     통신 기록 파일에서 위험한 통신을 스스로 찾아낼 수 있게 한다.

성공 기준:
1. 실습 참가자 10명 중 8명 이상이 리포트만 보고
   "이 파일에 암호화되지 않은 통신이 있는가"를 정확히 답한다.
2. 파일 하나(10MB 이하)를 5초 안에 처리한다.
```

**작성 예시 — photosort**:

```text
목표: 사진이 많이 쌓인 대학생이, 폴더를 하나하나 열어 보지 않고도
     중복 파일과 월별 분포를 파악할 수 있게 한다.

성공 기준:
1. 사용자가 리포트를 30초 안에 훑어보고 중복 의심 파일의 개수를 답할 수 있다.
2. 500장 규모의 폴더를 10초 안에 처리한다.
```

### 실습 3.1

자신의 프로젝트의 목표와 성공 기준을 작성하라. 성공 기준은 최소 2개, 숫자나 확인 가능한 사실을 포함해야 한다.

```text
목표: {                                                        }

성공 기준:
1. {                                                            }
2. {                                                            }
```

## 4. 대상 사용자와 범위 정리

### 4.1 대상 사용자

대상 사용자는 새로 만드는 것이 아니라, 앞서 비즈니스 모델 단계에서 정리한 고객 세그먼트를 한 문장으로 옮기는 작업이다.

```text
pcapeek   — 네트워크 과목을 처음 듣는 1학년 학생
photosort — 사진이 수천 장 쌓인 대학생
```

### 4.2 범위 — MoSCoW를 In/Out으로 재배열

PRD의 범위(Scope) 항목은 6강에서 만든 MoSCoW 표를 옮기되, **Must·Should·Could는 "만드는 것(In Scope)"으로, Won't는 "만들지 않는 것(Out of Scope)"으로** 두 칸으로 압축한다. 근거는 이미 6강에서 다 정리되어 있으므로, 여기서는 옮기기만 하면 된다.

**작성 예시 — pcapeek**:

```text
In Scope  — 암호화 안 된 프로토콜 경고, 프로토콜 비율, 상위 통신 상대·포트
Out of Scope — IPv6 해석, 실시간 수집, 특수 파일 형식(pcapng 등), 패킷 내용 표시
              (각 항목의 이유는 6강에서 작성한 Won't 목록을 그대로 옮긴다)
```

### 실습 4.1

자신의 프로젝트의 대상 사용자를 한 문장으로, 범위를 In/Out 두 칸으로 정리하라.

```text
대상 사용자: {                                                  }

In Scope:     {                                                }
Out of Scope: {무엇} — {왜}
```

## 5. 사용자 시나리오 — 실제로 어떻게 쓰는가

요구사항이 "무엇을 할 수 있어야 한다"의 목록이라면, 사용자 시나리오는 **사용자가 프로그램을 켜서 끝낼 때까지의 순서**를 그린 것이다. 복잡한 형식은 필요 없다. 두 가지만 적는다 — **기본 흐름**(모든 것이 정상일 때의 단계)과 **잘못될 수 있는 것**(각 단계에서 생길 수 있는 문제와 그때의 반응).

**작성 예시 — pcapeek**:

```text
기본 흐름:
1. 사용자가 터미널에 프로그램 명령과 파일 이름을 입력한다
2. 프로그램이 파일을 읽고 패킷을 분석한다
3. 분석 결과를 담은 report.html이 만들어지고 브라우저로 자동으로 열린다
4. 화면에 패킷 수·프로토콜 비율·상위 통신 상대가 표시되고,
   암호화되지 않은 프로토콜(HTTP·Telnet)의 개수가 경고로 강조된다

잘못될 수 있는 것:
- 파일이 존재하지 않는다 → "파일을 찾을 수 없습니다"를 출력하고 종료
- 파일이 올바른 형식이 아니다 → "지원하는 형식이 아닙니다"를 출력하고 종료
- 해석할 수 없는 패킷이 섞여 있다 → 해당 패킷만 건너뛰고 "건너뜀 N개"로 알림
- 브라우저가 자동으로 안 열린다 → report.html 경로를 출력해 직접 열게 안내
```

**작성 예시 — photosort**:

```text
기본 흐름:
1. 사용자가 폴더 경로를 지정하여 프로그램을 실행한다
2. 프로그램이 폴더를 훑어 사진 정보를 수집한다
3. 월별 개수와 중복 의심 파일 목록이 리포트로 표시된다

잘못될 수 있는 것:
- 폴더가 존재하지 않는다 → 오류 메시지 출력 후 종료
- 사진이 아닌 파일이 섞여 있다 → 건너뛰고 개수만 보고
```

"잘못될 수 있는 것"을 생략하면, 사용자가 파일 이름을 잘못 입력하는 순간 프로그램이 이해할 수 없는 오류를 내며 멈춘다. **기본 흐름의 각 단계마다 "여기서 무엇이 잘못될 수 있는가"를 한 번씩 묻는다.** 이 목록은 이후 구현 단계에서 "완료 기준"(이 경우들을 모두 처리해야 완성)으로 그대로 옮겨진다.

### 실습 5.1

자신의 프로젝트의 사용자 시나리오를 작성하라. "잘못될 수 있는 것"을 최소 2개 이상 포함한다.

```text
기본 흐름:
1. {                                                            }
2. {                                                            }
3. {                                                            }

잘못될 수 있는 것:
- {무엇이 잘못될 수 있는가} → {그때 시스템은 어떻게 반응하는가}
- {                        } → {                              }
```

## 6. 제약사항 — 어떤 조건 안에서 만드는가

제약사항은 "하고 싶어도 할 수 없는 것"을 미리 적어 두는 항목이다. 시간·기술·환경 세 갈래로 나누면 빠뜨리기 어렵다.

| 갈래 | 묻는 것 | pcapeek 예시 |
|---|---|---|
| 시간 | 언제까지 완성해야 하는가 | 학기 중 12주 안에 완성 |
| 기술 | 무엇을 쓸 수 없는가 | 외부 라이브러리 설치 없이 동작해야 한다 |
| 환경 | 어떤 조건에서 동작해야 하는가 | 인터넷 연결 없이도 동작해야 한다(실습실 네트워크 제한) |

이 항목들 중 일부는 6강의 비기능 요구사항과 겹친다. 겹치는 것은 자연스러운 일이며, 그대로 옮겨 적으면 된다.

### 실습 6.1

자신의 프로젝트의 제약사항을 시간·기술·환경 세 갈래로 정리하라.

```text
시간: {                                                         }
기술: {                                                         }
환경: {                                                         }
```

## 7. 열린 질문 — 아직 정하지 못한 것을 숨기지 않는다

기획을 하다 보면 끝내 결정하지 못한 채 넘어가는 부분이 생긴다. 이를 조용히 덮어 두면 나중에 구현 도중 갑자기 문제로 터진다. **"아직 결정하지 못했다"는 사실 자체를 문서에 남겨 두는 편이 훨씬 안전하다.**

**작성 예시 — pcapeek**:

```text
- IPv6 패킷이 섞여 있을 때 개수만 셀지, 아예 건너뛸지 아직 미정
  → 8절의 AI 검토 단계에서 결정 예정
- 리포트를 한글이 아닌 환경(영문 OS)에서도 지원할지 미정
  → 이번 학기 범위에서는 보류, 필요시 추후 결정
```

열린 질문은 뒤에 나올 AI와의 대화에서 특히 중요한 역할을 한다. AI가 던지는 질문에 답하다 보면 이 목록이 하나씩 지워지고, 답을 못 하는 것은 여기 남는다.

### 실습 7.1

자신의 프로젝트에서 아직 결정하지 못한 것을 1개 이상 적어라. "언제 결정할 것인가"도 함께 남긴다.

```text
- {아직 결정하지 못한 것} → {언제, 어떻게 결정할 것인가}
```

## 8. AI와 함께 PRD 완성하기 — 실제 상호작용

여기까지 조각을 만들었으면, 이제 AI 코딩 도구(Claude Code 등)와 대화하며 하나의 PRD로 완성한다. 진행 방식은 세 가지가 있는데, 이 과정에서는 **인터뷰 방식**을 권장한다.

| 방식 | 진행 | 문제점 |
|---|---|---|
| 전부 직접 쓰기 | 학생이 혼자 9개 항목을 채운다 | 무엇을 빠뜨렸는지 스스로 알기 어렵다 |
| 전부 AI에게 맡기기 | "PRD 만들어 줘" 한 줄 | 그럴듯하지만 **내 결정이 하나도 없는 남의 문서**가 나온다 |
| **인터뷰 방식 (권장)** | 학생이 재료를 주고, AI가 질문하고, **학생이 결정**한다 | — |

인터뷰 방식의 핵심은 역할 분담이다. **AI는 빠진 곳을 찾아 질문하는 역할, 학생은 답하고 결정하는 역할**이다. 결정을 AI에게 넘기는 순간 그 문서는 내 기획이 아니게 된다.

전체 흐름은 **인터뷰 → 초안 → 검토 → 수정 → 재검토**의 순서이며, 뒤의 검토·수정은 한 번으로 끝나지 않고 문서가 안정될 때까지 반복한다(8.4절).

> **권장 이미지**: 학생과 AI의 역할 분담 그림 1장. "왼쪽에 학생 아이콘(말풍선: '재료 제공', '답변', '결정'), 오른쪽에 AI 아이콘(말풍선: '질문', '초안 작성', '지적'), 두 아이콘 사이에 양방향 화살표로 대화가 오가는 모습. 학생 쪽 말풍선 중 '결정'만 굵은 테두리로 강조. 한글, 흰 배경, 플랫 일러스트 스타일."
{: .prompt-tip }

### 8.1 인터뷰 시작 프롬프트

지금까지 만든 조각을 모두 붙여 넣고, 다음과 같이 인터뷰를 요청한다.

```text
나는 1학년 학생이고, 아래 자료로 내 프로젝트의 PRD를 만들려고 해.

[문제 진술문]
[요구사항 (기능·비기능)]
[MoSCoW 표]
[목표와 성공 기준 / 대상 사용자 / 사용자 시나리오 / 제약사항 / 열린 질문 초안]

PRD를 바로 쓰지 말고, 먼저 나를 인터뷰해 줘.
- 빠져 있거나 모호한 부분을 찾아 한 번에 하나씩 질문해 줘.
- 내가 답하면 다음 질문으로 넘어가 줘.
- 질문은 5개 이내로 하고, 끝나면 아래 항목 순서로 PRD 초안을 작성해 줘.
  개요 / 목표와 성공 기준 / 대상 사용자 / 문제 정의 / 범위(In/Out) /
  요구사항 / 사용자 시나리오 / 제약사항 / 열린 질문
- 아직 코드는 쓰지 마.
```

프롬프트의 장치 하나하나에 이유가 있다.

| 문구 | 없으면 생기는 일 |
|---|---|
| "PRD를 바로 쓰지 말고 먼저 인터뷰해 줘" | AI가 빈 곳을 지어내서 즉시 완성본을 내놓는다 |
| "한 번에 하나씩" | 질문 10개가 한꺼번에 쏟아져 성의 없이 답하게 된다 |
| "질문은 5개 이내" | 인터뷰가 끝없이 늘어진다 |
| "아직 코드는 쓰지 마" | 기획이 끝나기도 전에 코드부터 나온다 |

### 8.2 실제 대화 예시 — photosort

인터뷰가 실제로 어떻게 흘러가는지 photosort로 보인다. 특히 **학생이 AI의 제안을 받아들이는 턴과 거절하는 턴이 모두 있다**는 점에 주목한다.

```text
AI:  첫 번째 질문입니다. 성공 기준에 "사용자가 리포트를 훑어보고 중복 개수를
     답할 수 있다"고 하셨는데, 시간 제한이 없으면 확인하기 어렵습니다.
     "30초 안에"처럼 시간을 정하면 어떨까요?

학생: 좋아, 30초로 하자.                            ← 제안 수용

AI:  두 번째 질문입니다. 중복 파일은 무엇을 기준으로 판정합니까?
     파일 이름이 같으면 중복인가요, 내용이 같아야 중복인가요?

학생: 내용이 같아야 중복이야. 이름은 달라도 내용이 같은 경우를 찾고 싶은 거니까.
                                                    ← 모호함이 여기서 처음 드러남

AI:  세 번째 질문입니다. 중복 파일을 찾으면 자동으로 삭제하는 기능도
     넣을까요? 사용자에게 편리할 것 같습니다.

학생: 아니, 넣지 마. 원본을 건드리지 않는 게 요구사항 3번이야.
     그건 Out of Scope에 "자동 삭제 — 실수로 지우면 복구할 수 없다"로 추가해 줘.
                                                    ← 제안 거절 + 문서에 근거 남김

AI:  네 번째 질문입니다. 열린 질문에 "썸네일도 중복으로 셀지 미정"이
     있습니다. 내용 기준으로 판정한다면 썸네일은 원본과 내용이 다르므로
     중복이 아니게 됩니다. 이렇게 결정된 것으로 정리할까요?

학생: 맞네, 그렇게 정리하고 열린 질문에서는 지워 줘.  ← 열린 질문 하나 해소

AI:  질문을 마쳤습니다. PRD 초안을 작성합니다. [초안 출력]
```

이 짧은 대화에서 일어난 일을 정리하면 다음과 같다.

- 성공 기준이 측정 가능해졌다 ("훑어보고" → "30초 안에")
- 숨어 있던 모호함이 드러났다 (중복의 기준: 이름인가 내용인가)
- **범위 밖 기능 제안을 근거를 들어 거절**하고, 그 근거가 문서에 남았다
- 열린 질문 하나가 해소되어 본문으로 옮겨졌다

세 번째 턴이 가장 중요하다. AI는 그럴듯한 확장 기능(자동 삭제)을 친절하게 제안하지만, 받아들이면 요구사항("원본을 건드리지 않는다")과 정면으로 충돌한다. **AI의 제안이 내 문서와 충돌하는지 판단하는 것은 학생의 몫**이며, 이 판단을 하려면 자기 문서의 내용을 알고 있어야 한다. 전부 AI에게 맡긴 문서로는 이 판단이 불가능하다.

### 8.3 초안 검토받기 — 역할을 바꿔 공격시키기

인터뷰로 초안이 나왔다고 끝이 아니다. 이번에는 역할을 바꿔, **완성된 초안을 AI에게 공격하게** 한다.

```text
방금 작성한 PRD 초안을 이번에는 검토자의 입장에서 비판해 줘.
1. 문제 정의에 해결책이 섞여 있지는 않은지
2. 성공 기준이 숫자나 확인 가능한 사실로 되어 있는지
3. 요구사항이 서로 겹치거나 빠진 것이 없는지
4. 사용자 시나리오의 "잘못될 수 있는 것"에서 빠뜨린 경우가 있는지
5. Out of Scope 항목에 이유가 모두 붙어 있는지
지적은 심각한 것부터 순서대로 나열해 줘. 아직 코드는 쓰지 마.
```

검토 단계에서 유의할 것 두 가지다.

1. **AI가 "훌륭합니다, 문제 없습니다"라고만 답하면 오히려 의심한다.** 문서가 이미 완벽하거나 AI가 대충 넘어간 것인데, 후자일 가능성이 높다. "정말 빠진 경우가 없는가? 세 가지만 더 짚어 봐라"라고 한 번 더 요구한다.
2. **지적을 받아들일지 말지도 학생이 결정한다.** AI의 지적 중에는 타당한 것과 범위를 넘는 것이 섞여 있다. 타당하면 본문에 반영하고, 범위를 넘으면 "Out of Scope"라고 답하면 된다.

### 8.4 수정과 재검토의 반복 — 문서가 안정될 때까지

검토에서 받은 지적을 반영했으면, **수정한 문서로 다시 검토를 받는다.** 한 번의 검토로 끝내지 않는 이유는 두 가지다 — 수정 과정에서 새로운 문제가 생길 수 있고, 지난 지적이 제대로 해소되었는지도 확인해야 하기 때문이다. 재검토는 다음 프롬프트로 요청한다.

```text
지적을 반영해 수정한 PRD야.

[수정한 PRD 전문을 붙여 넣는다]

1. 지난번 지적이 모두 해소되었는지 하나씩 확인해 줘.
2. 수정하면서 새로 생긴 문제가 있는지 봐 줘.
지적은 심각한 것부터 순서대로. 아직 코드는 쓰지 마.
```

**반복 예시 — photosort의 검토·수정 2회전**:

```text
[1차 검토] AI의 지적 3건 (심각한 순서)
 ① 사용자 시나리오에 "폴더에 사진이 0장인 경우"가 빠져 있다
 ② "월별 개수"의 기준이 모호하다 — 촬영일 기준인가, 파일 수정일 기준인가
 ③ 리포트를 파일로 저장하는 기능도 있으면 좋겠다

[학생의 수정 결정]
 ① 반영 — "사진이 0장이다 → '사진이 없습니다'를 표시하고 정상 종료" 추가
 ② 반영 — 요구사항 1번에 "(촬영일 기준, 촬영일 정보가 없으면 파일 수정일)" 명시
 ③ 거절 — 리포트 표시가 핵심이므로 Out of Scope에
    "파일 저장 — 화면 표시로 충분하며, 필요하면 추후 확장" 추가

[2차 검토] 수정본으로 재검토 요청
 - 지난 지적 ①②: 해소 확인. ③: Out of Scope 처리 확인
 - 새 지적 1건: "촬영일 정보가 깨져 있는 사진의 처리가 미정" → 열린 질문에 추가

[종료 판단] 남은 지적이 열린 질문 1건뿐이고 치명적 문제가 없다 → 반복 종료
```

1차에서 3건이 나오고, 2차에서 지난 지적의 해소가 확인되고 새 지적이 사소해졌다. 이 시점이 멈출 때다.

**언제 멈추는가.** 주의할 점이 있다 — **AI는 요청하면 언제나 무언가를 더 지적한다.** 지적이 0건이 될 때까지 반복하면 끝나지 않는다. 목표는 "지적 없음"이 아니라 "치명적 지적 없음"이며, 다음 중 하나면 멈춘다.

| 종료 신호 | 의미 |
|---|---|
| 새 지적이 전부 사소하다 (표현·순서 수준) | 내용은 안정되었다 |
| 새 지적이 전부 Out of Scope나 열린 질문으로 정리된다 | 범위 판단이 끝났다 |
| 같은 지적이 다시 나온다 | AI가 더 볼 것이 없어 재탕하는 중이다 |

경험적으로 **2~3회면 충분**하다. 그 이상 반복하고 있다면 문서를 다듬는 것이 아니라 AI와 핑퐁을 하고 있는 것이다.

> **권장 이미지**: 초안-검토-수정 반복 사이클 다이어그램 1장. "원형 순환 화살표로 연결된 4단계 — '초안 작성' → 'AI 검토(지적)' → '학생이 반영/거절 결정' → '수정' → 다시 'AI 검토'로 순환. 순환 고리 옆에 '치명적 지적 없음?'이라는 마름모 분기가 있고, 예(Yes)면 'PRD 완성'으로 빠져나가는 출구 화살표. 순환 화살표 옆에 '2~3회' 표기. 한글, 흰 배경, 단정한 플로우차트 스타일."
{: .prompt-tip }

### 8.5 상호작용 원칙 정리

세 단계(인터뷰 → 검토 → 수정·재검토 반복)에서 지킨 원칙을 모으면 다음 일곱 가지다. 이 원칙은 PRD 작성만이 아니라 이후 구현 단계에서 AI와 일할 때도 똑같이 적용된다.

| 원칙 | 이유 |
|---|---|
| 재료는 내가 주고, 질문은 AI가 한다 | 빈손으로 시키면 AI가 지어낸 남의 문서가 나온다 |
| 한 번에 하나씩 묻게 한다 | 질문이 쏟아지면 성의 없는 답이 나온다 |
| 결정은 항상 학생이 한다 | AI의 제안은 그럴듯해도 내 요구사항과 충돌할 수 있다 |
| 결정하면 반드시 문서에 반영한다 | 대화에만 남은 결정은 다음 세션에서 사라진다 |
| 검토는 수정본으로 다시 받는다 | 지난 지적의 해소 확인과 새 문제 발견은 재검토에서만 가능하다 |
| "치명적 지적 없음"에서 멈춘다 (2~3회) | AI는 언제나 무언가를 더 지적하므로, 0건을 기다리면 끝나지 않는다 |
| "아직 코드는 쓰지 마"를 매번 붙인다 | 기획 단계에서 코드가 나오면 기획이 코드에 끌려간다 |

### 실습 8.1

1. 8.1절의 프롬프트에 자신의 재료를 채워 AI와 인터뷰를 진행하라. AI의 질문 중 최소 하나는 **거절하고 그 이유를 문서에 남겨라** (거절할 것이 없으면 "자동으로 ~해 주는 기능도 넣을까요?"류의 제안이 나올 때까지 진행한다).
2. 완성된 초안에 8.3절의 검토 프롬프트를 적용하고, 받은 지적마다 반영/거절/열린 질문 중 하나로 결정하라.
3. 수정본으로 8.4절의 재검토를 **최소 1회 이상** 진행하고, 어느 종료 신호에서 멈췄는지 한 줄로 기록하라.

## 9. PRD 완성본

인터뷰와 검토·수정의 반복을 거치면 PRD가 완성된다. 아래는 photosort로 채운 완성 예시이며, 그 아래 자신의 프로젝트용 빈 틀이 이어진다.

**완성 예시 — photosort** (8.2절 인터뷰와 8.4절 검토·수정 2회전의 결정이 모두 반영된 상태):

```text
[개요]
사진이 수천 장 쌓인 폴더를 정리하지 못하는 대학생을 위해,
월별 분포와 중복 파일을 자동으로 찾아 알려주는 프로그램을 만든다.

[목표와 성공 기준]
목표: 폴더를 하나하나 열어 보지 않고도 중복 파일과 월별 분포를 파악하게 한다.
성공 기준: (1) 리포트를 30초 안에 훑고 중복 의심 개수를 답할 수 있다.
          (2) 500장 규모를 10초 안에 처리한다.

[대상 사용자]
사진이 수천 장 쌓인 대학생

[문제 정의]
사진을 자주 찍는 대학생은, 수천 장이 쌓인 사진 폴더에서 어떤 파일이
중복이고 언제 찍은 것인지 파악하지 못한다. 파일 이름만으로는 내용을
알 수 없고, 하나하나 열어 보기에는 양이 너무 많기 때문이다.

[범위]
In Scope  — 월별 사진 개수, 내용 동일 중복 파일 목록과 총 용량
Out of Scope — 사진 원본 리포트 삽입 (개인정보 우려),
              중복 파일 자동 삭제 (실수로 지우면 복구할 수 없다),
              리포트 파일 저장 (화면 표시로 충분하며, 필요하면 추후 확장)

[요구사항]
1. 사용자는 폴더를 지정하면 월별 사진 개수를 확인할 수 있어야 한다.
   (촬영일 기준, 촬영일 정보가 없으면 파일 수정일)

   (중복 판정 기준: 파일 이름이 아니라 내용)
3. 시스템은 원본 파일을 삭제하거나 수정하지 않아야 한다.

[사용자 시나리오]
기본 흐름:
1. 사용자가 폴더 경로를 지정하여 프로그램을 실행한다
2. 프로그램이 폴더를 훑어 사진 정보를 수집한다
3. 월별 개수와 중복 의심 파일 목록이 리포트로 표시된다
잘못될 수 있는 것:
- 폴더가 존재하지 않는다 → 오류 메시지 출력 후 종료
- 사진이 아닌 파일이 섞여 있다 → 건너뛰고 개수만 보고
- 폴더에 사진이 0장이다 → "사진이 없습니다"를 표시하고 정상 종료

[제약사항]

  (썸네일 중복 여부는 "내용 기준 판정" 결정으로 해소되어 삭제됨)
```

### 실습 9.1

자신의 프로젝트로 PRD를 완성하라. 실습 8.1의 인터뷰·검토에서 결정된 내용이 모두 본문에 반영되어 있어야 한다.

```text
[개요]

[목표와 성공 기준]
{                                                                }

[대상 사용자]
{                                                                }

[문제 정의]
{6강에서 작성한 문제 진술문을 옮긴다}

Out of Scope: {무엇} — {왜}

[요구사항]
```

이 PRD는 이후 구현 단계에서 AI에게 전달할 지시문의 재료가 된다. 특히 다음 대응 관계를 기억해 두면 좋다 — **In Scope의 핵심(Must)은 "핵심 기능"으로, Out of Scope은 "안 만들 것"으로, 사용자 시나리오의 기본 흐름과 "잘못될 수 있는 것"은 "완료 기준"으로** 그대로 옮겨진다.

## 핵심 용어 정리

| 용어 | 영문 | 설명 |
|---|---|---|
| PRD | Product Requirements Document | 무엇을·누구를 위해·왜·어디까지 만드는지 정리한 합의 문서 |
| 성공 기준 | Success Metric | 목표 달성 여부를 숫자나 관찰 가능한 사실로 확인하는 기준 |
| 범위 | Scope | 만들 것(In Scope)과 만들지 않을 것(Out of Scope)의 경계 |
| 사용자 시나리오 | User Scenario | 기본 사용 흐름과 잘못될 수 있는 경우를 적은 항목 |
| 열린 질문 | Open Question | 아직 결정하지 못했음을 명시적으로 남긴 항목 |
| 인터뷰 방식 | — | AI가 질문하고 학생이 결정하며 문서를 완성하는 진행 방식 |
