# 5부. 프로젝트 실행
---
## 1. 스프린트 계획 수립

### 스프린트 계획의 목적

> 스프린트 계획(Sprint Planning)은 팀이 **이번 스프린트에서 무엇을 완성할지**를 결정하는 회의임.

  

### 스프린트 계획 수립 절차

```
[스프린트 계획 4단계]  
1단계: 목표 설정 (Sprint Goal)
  → "이번 2주 동안 무엇을 완성할 것인가?"
2단계: 백로그 아이템 선택
  → 프로덕트 백로그에서 우선순위 높은 항목 선택
3단계: 작업 분해 (Task Breakdown)
  → 각 항목을 1~2일 단위의 세부 작업으로 분해
4단계: 역할 배정 (Assignment)
  → 팀원별 담당 작업 배정
```

### 스프린트 계획서 양식  

| 항목          | 내용                           |
| ----------- | ---------------------------- |
| 스프린트 번호     | Sprint #1                    |
| 기간          | 2026-03-10 ~ 2026-03-23 (2주) |
| 스프린트 목표     | 로그인 인증 모듈 및 JWT 토큰 발급 기능 완성  |
| 참여 인원       | 팀원 4명                        |
| 선택한 백로그 아이템 | SR-F-001, SR-F-002, SR-F-003 |

### 프로젝트 전체 스프린트 일정 예시 (12주 과정)  

| 스프린트         | 기간     | 주요 활동              | 산출물            |
| ------------ | ------ | ------------------ | -------------- |
| **Sprint 0** | 1~2주   | 주제 확정, 팀 구성, 환경 구성 | 프로젝트 제안서, BMC  |
| **Sprint 1** | 3~4주   | 위협 분석, 요구사항 도출     | 위협 분석 보고서, SRS |
| **Sprint 2** | 5~6주   | 핵심 기능 1차 개발        | 기능 프로토타입       |
| **Sprint 3** | 7~8주   | 핵심 기능 2차 개발        | 동작하는 시스템       |
| **Sprint 4** | 9~10주  | 보안 테스트 및 취약점 수정    | 취약점 점검 보고서     |
| **Sprint 5** | 11~12주 | 문서화 및 최종 발표 준비     | 최종 보고서, 발표 자료  |

## 2. 백로그(Backlog) 관리

### 백로그의 종류

| 종류                            | 설명                      | 관리 주체 |
| ----------------------------- | ----------------------- | ----- |
| **프로덕트 백로그(Product Backlog)** | 전체 프로젝트에서 해야 할 모든 작업 목록 | 팀 전체  |
| **스프린트 백로그(Sprint Backlog)**  | 현재 스프린트에서 할 작업 목록       | 개발팀   |

### 유저 스토리(User Story) 작성법

> **유저 스토리(User Story)** 는 사용자 관점에서 기능을 기술하는 방법임.

**형식**: "나는 [역할]로서, [목표] 를 위해 [기능]이 필요하다."

| 역할     | 유저 스토리                                         | 관련 요구사항  |
| ------ | ---------------------------------------------- | -------- |
| 일반 사용자 | 나는 사용자로서, 계정을 보호하기 위해 2FA(이중인증) 기능이 필요하다       | SR-F-005 |
| 관리자    | 나는 관리자로서, 보안 감사를 위해 모든 사용자 행위 로그를 조회할 수 있어야 한다 | SR-F-012 |
| 보안 담당자 | 나는 보안 담당자로서, 실시간 위협을 감지하기 위해 이상 트래픽 알림이 필요하다   | SR-F-018 |

## 3. 팀 협업과 역할 분담


### 스크럼 팀의 구성

| 역할                | 원래 스크럼 역할 | 역할                  |
| ----------------- | --------- | ------------------- |
| **Product Owner** | 요구사항 관리   | 팀장, 요구사항 및 백로그 관리   |
| **Scrum Master**  | 프로세스 촉진   | 부팀장, 회의 진행 및 장애 제거  |
| **Developer**     | 개발        | 팀원 전체 (개발, 테스트, 문서) |

### 팀 역할 분담 예시 (4인 팀, 보안 모니터링 시스템)

| 역할          | 담당자 | 주요 책임               |
| ----------- | --- | ------------------- |
| **팀장/PO**   | 1명  | 전체 일정 관리, 발표, 최종 문서 |
| **백엔드/보안**  | 1명  | 인증 모듈, 위협 탐지 로직     |
| **프론트/UI**  | 1명  | 대시보드, 알람 인터페이스      |
| **인프라/테스트** | 1명  | 서버 구성, 취약점 테스트, 보고서 |

### 협업 도구 추천

| 용도         | 도구                | 특징            |
| ---------- | ----------------- | ------------- |
| **코드 관리**  | GitHub            | 버전 관리, 코드 리뷰  |
| **이슈/백로그** | GitHub Projects   | 무료, GitHub 연동 |
| **커뮤니케이션** | Discord / Slack   | 채널 분리, 파일 공유  |
| **문서 작성**  | Notion / Obsidian | 지식 관리, 회의록    |
| **다이어그램**  | draw.io / Mermaid | DFD, 시스템 구조도  |

## 4. 결과물(Deliverable) 산출 기준


### 프로젝트 최종 결과물 목록


| 결과물                  | 내용                     | 관련 강의 |
| -------------------- | ---------------------- | ----- |
| **프로젝트 제안서**         | 주제, 목표, BMC, 일정        | 2부    |
| **위협 분석 보고서**        | DFD, STRIDE 분석, 위험 평가  | 3부    |
| **보안 요구사항 명세서(SRS)** | 기능적/비기능적 요구사항          | 4부    |
| **시스템 구현 결과물**       | 동작하는 소프트웨어/시스템         | 5부    |
| **취약점 점검 보고서**       | 테스트 결과, 발견된 취약점, 조치 내용 | 5부    |
| **최종 보고서**           | 전체 프로젝트 종합 문서          | 5부    |
| **발표 자료**            | 10~15분 발표용 슬라이드        | 5부    |


### 취약점 점검 보고서 작성 방법


```markdown

## 취약점 점검 보고서

### 1. 개요
- 점검 대상: [시스템명]
- 점검 기간: [날짜]
- 점검 방법: 수동 점검 / 자동화 도구


### 2. 점검 도구
| 도구 | 용도 |
|------|------|
| OWASP ZAP | 웹 취약점 자동 스캔 |
| Burp Suite | 웹 요청 분석 및 조작 |
| Nmap | 포트 스캔, 서비스 열거 |

### 3. 발견된 취약점

#### [V-001] SQL 인젝션 (심각도: 높음)

- **위치**: /api/login 엔드포인트
- **설명**: username 파라미터에 SQL 구문 삽입 가능
- **재현 방법**: username=' OR 1=1-- 입력
- **영향**: 전체 사용자 데이터 유출 가능
- **조치 방안**: 매개변수화 쿼리 적용
- **조치 상태**: 완료 / 진행 중 / 미조치

### 4. 심각도 요약

| 심각도 | 개수 |
|-------|------|
| 심각(Critical) | 0 |
| 높음(High) | 1 |
| 중간(Medium) | 3 |
| 낮음(Low) | 5 |

```

### 최종 보고서 목차 구성

```

최종 보고서 목차

1. 프로젝트 개요

   1.1 배경 및 목적

7. 결론 및 향후 발전 방향

  

부록
```

## 5. 최종 발표 준비
  
### 발표 구성 (10분 발표 + 5분 질의응답)

| 섹션        | 시간  | 내용                 |
| --------- | --- | ------------------ |
| **인트로**   | 1분  | 팀 소개, 주제 한 줄 요약    |
| **문제 정의** | 1분  | 해결하려는 보안 문제        |
| **분석**    | 2분  | 위협 분석, 요구사항 핵심 내용  |
| **구현 데모** | 4분  | 시스템 시연 (핵심 기능 3가지) |
| **결과**    | 1분  | 취약점 점검 결과, 성과      |
| **결론**    | 1분  | 의의, 한계, 향후 계획      |

  

### 좋은 발표의 조건

| 조건            | 나쁜 예        | 좋은 예                          |
| ------------- | ----------- | ----------------------------- |
| **명확한 문제 제기** | "보안이 중요합니다" | "매년 1,200만 건 개인정보가 유출됩니다"     |
| **데모 중심**     | 슬라이드만 설명    | 실제 동작하는 시스템 시연                |
| **수치로 결과 표현** | "보안이 개선되었다" | "SQL 인젝션 100% 차단, 응답속도 200ms" |
| **한계점 솔직하게**  | 한계 없음       | "미탐지율 15%는 향후 ML 적용으로 개선 예정"  |

### 평가 기준 (예시)

| 평가 항목       | 배점   | 세부 기준              |
| ----------- | ---- | ------------------ |
| **주제 적합성**  | 10점  | 정보보안 프로젝트로서의 완성도   |
| **위협 분석**   | 20점  | STRIDE 분석의 정확성과 깊이 |
| **요구사항 도출** | 20점  | 위협과 요구사항의 연계성      |
| **구현 완성도**  | 30점  | 요구사항 충족률, 동작 여부    |
| **보안 테스트**  | 10점  | 취약점 점검 수행 및 조치     |
| **발표 및 문서** | 10점  | 발표 명확성, 문서 완성도     |
| **합계**      | 100점 |                    |
