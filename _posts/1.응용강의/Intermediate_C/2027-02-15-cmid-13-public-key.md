## 제1절. 공개키 암호란

### 1.1 열쇠가 둘입니다

> **공개키 암호**: 잠그는 열쇠와 여는 열쇠가 **다른** 방식.

| 열쇠 | 성질 |
|---|---|
| **공개키** | 누구에게나 알려도 된다 |
| **개인키** | 절대 알려서는 안 된다 |

**핵심은 "공개키에서 개인키를 알아낼 수 없다"** 는 것입니다. 수학적으로 어려운 문제에 기대고 있습니다.

### 1.2 두 가지 쓰임

| 쓰임 | 잠그는 쪽 | 푸는 쪽 |
|---|---|---|
| **비밀 전달** | **공개키**로 잠근다 | **개인키**로 푼다 |
| **전자서명** | **개인키**로 서명 | **공개키**로 검증 |

**방향이 반대**입니다. 이 대칭이 공개키 암호의 힘입니다.

### 1.3 알고리즘

| 계열 | 알고리즘 | 오늘날 |
|---|---|---|
| RSA | RSA-2048, RSA-4096 | 아직 널리 쓰인다. **크고 느리다** |
| **타원곡선** | **X25519**(키 교환), **Ed25519**(서명), ECDSA | **권장** |
| 후양자 | ML-KEM 등 | 도입이 시작되는 중 |

**이번 강의는 X25519와 Ed25519를 씁니다.** 키가 **32바이트**로 작고 빠르며, 잘못 쓰기 어렵게 설계되어 있습니다.

| | RSA-2048 | X25519 |
|---|---|---|
| 공개키 크기 | 256바이트 | **32바이트** |
| 안전성 | 112비트급 | **128비트급** |
| 매개변수 고를 일 | 많다 | **없다** |

## 제2절. 무엇에 쓰는가

### 2.1 자료를 직접 암호화하지 않습니다

**공개키로 큰 자료를 암호화하지 않습니다.**

| 이유 | |
|---|---|
| **느리다** | 대칭키의 수백~수천 분의 일(제8절) |
| **크기 제한** | RSA-2048은 한 번에 200바이트 남짓 |
| X25519는 아예 암호화 함수가 없다 | 키 교환 전용 |

### 2.2 실제 쓰임

| 쓰임 | 방법 |
|---|---|
| **공유 비밀 만들기** | 키 교환(제3절) |
| **상대 확인** | 전자서명(제5절) |
| 문서 서명 | 소프트웨어 서명, 전자 계약 |
| 인증서 | **14강** |

**"공개키로 대칭키를 정하고, 자료는 대칭키로 나른다."** 이것이 오늘날 모든 보안 통신의 뼈대입니다(제7절).

## 제3절. 키 교환

### 3.1 도청당하면서 비밀을 만든다

> **키 교환**: 두 사람이 **공개된 통로로만** 대화하면서, **도청자는 알 수 없는 비밀**에 함께 도달하는 방법.

처음 들으면 불가능해 보입니다. 그러나 됩니다.

| 앨리스 | 공개된 통로 | 밥 |
|---|---|---|
| 개인키 a 생성 | | 개인키 b 생성 |
| 공개키 A 계산 | **A →** | |
| | **← B** | 공개키 B 계산 |
| **비밀 = f(a, B)** | | **비밀 = f(b, A)** |

**두 비밀이 같습니다.** 그런데 도청자는 A와 B만 보았으므로 만들 수 없습니다.

### 3.2 코드

```c
/* gen_key: X25519 키 쌍을 만든다 */
static EVP_PKEY *gen_key(void)
{
    EVP_PKEY_CTX *ctx = EVP_PKEY_CTX_new_id(EVP_PKEY_X25519, NULL);
    EVP_PKEY *k = NULL;

    if (ctx == NULL)
        return NULL;
    if (EVP_PKEY_keygen_init(ctx) != 1 || EVP_PKEY_keygen(ctx, &k) != 1)
        k = NULL;
    EVP_PKEY_CTX_free(ctx);
    return k;
}
```

```c
/* derive: 내 개인키 + 상대 공개키 → 공유 비밀 */
static int derive(EVP_PKEY *mine, const unsigned char *peer_pub,
                  size_t peer_len, unsigned char *secret, size_t *slen)
{
    EVP_PKEY *peer = EVP_PKEY_new_raw_public_key(EVP_PKEY_X25519, NULL,
                                                 peer_pub, peer_len);
    ...
    if (EVP_PKEY_derive_init(ctx) == 1 &&
        EVP_PKEY_derive_set_peer(ctx, peer) == 1 &&
        EVP_PKEY_derive(ctx, secret, slen) == 1)
        rc = 0;
    ...
}
```

**공개키를 바이트로 꺼내는 것**이 중요합니다. 선으로 보내야 하기 때문입니다.

```c
EVP_PKEY_get_raw_public_key(k, out, len)
```

**두 비밀이 한 글자도 다르지 않습니다.** 그리고 이 값은 **선을 흐른 적이 없습니다.**

### 3.4 이 비밀을 그대로 쓰지 마십시오

```c
memcpy(key, secret, 32);            /* 권장하지 않는다 */
```

공유 비밀은 **고르게 분포하지 않을 수** 있습니다. **키 유도 함수를 한 번 거치는 것**이 표준입니다.

```c
/* HKDF 로 용도별 키를 뽑아낸다 */
EVP_KDF *kdf = EVP_KDF_fetch(NULL, "HKDF", NULL);
```

TLS도 이렇게 합니다. 한 번의 키 교환에서 **보내는 키, 받는 키, IV** 등을 각각 뽑아냅니다.

### 3.5 순방향 비밀성

**연결마다 새 키 쌍을 만들어 쓰고 버리면**, 나중에 장기 키가 새어 나가도 **지난 통신은 풀 수 없습니다.**

| | |
|---|---|
| **순방향 비밀성**(forward secrecy) | 오늘의 키 유출이 어제의 대화를 위협하지 않는다 |
| 조건 | **임시 키 쌍**을 쓰고 버린다 |

TLS 1.3은 **이것을 필수로** 만들었습니다. 임시 키 교환을 쓰지 않는 방식은 아예 제거되었습니다(14강).

## 제4절. 중간자 공격

**이 절이 이번 강의에서 가장 중요합니다.**

### 4.1 무엇이 빠졌는가

3.3절의 키 교환에는 치명적인 구멍이 있습니다.

> **앨리스는 받은 공개키가 정말 밥의 것인지 확인하지 않았습니다.**

### 4.2 공격

```c
        /* 말로리가 양쪽에 각각 다른 공개키를 건넨다 */
        mallory_a = gen_key();      /* 앨리스를 상대할 키 */
        mallory_b = gen_key();      /* 밥을 상대할 키 */
```

```text
   앨리스 ◀──▶ 말로리 ◀──▶ 밥

```

**말로리는 양쪽과 각각 키 교환을 합니다.** 앨리스는 밥과, 밥은 앨리스와 이야기한다고 믿습니다.

### 4.4 무엇이 일어난 것인가

| 관찰 | 뜻 |
|---|---|
| 말로리와 앨리스의 비밀이 **같다** | 말로리가 앨리스의 말을 **읽을 수 있다** |
| 말로리와 밥의 비밀도 **같다** | 밥의 말도 읽을 수 있다 |
| **앨리스와 밥의 비밀은 다르다** | 둘은 직접 통신한 적이 없다 |

**말로리는 앨리스의 말을 풀어 읽고, 원한다면 고쳐서, 다시 암호화해 밥에게 넘깁니다.** 양쪽 모두 정상적으로 통신하고 있다고 믿습니다.

> **12강에서 만든 암호 채널로도 막을 수 없습니다.**
> 암호화는 완벽하게 동작합니다. 다만 **엉뚱한 상대와 완벽하게** 암호화한 것입니다. 9강 8.6절에서 "인증이 없으면 엉뚱한 상대와 안전하게 통신하게 된다"고 한 말의 뜻이 이것입니다.
{: .prompt-danger }

### 4.5 어디서 일어나는가

| 자리 | 예 |
|---|---|
| 공용 무선망 | 가짜 접속점 |
| 공유기 | 감염된 장비 |
| DNS | 엉뚱한 주소로 유도 |
| 회사·국가 | 중간 검사 장비 |

**9강에서 만든 `wiretap.c`가 바로 이 자리에 있었습니다.** 그때는 읽기만 했지만, 키 교환에 끼어들면 암호화까지 무력화할 수 있습니다.

## 제5절. 전자서명

### 5.1 방향이 반대입니다

| | 잠그기 | 풀기 |
|---|---|---|
| 비밀 전달 | 공개키 | 개인키 |
| **서명** | **개인키** | **공개키** |

**개인키를 가진 사람만 서명할 수 있고, 공개키를 가진 누구나 검증할 수 있습니다.**

### 5.2 무엇을 보장하는가

| 보장 | 뜻 |
|---|---|
| **출처** | 개인키를 가진 사람이 만들었다 |
| **무결성** | 서명 이후 바뀌지 않았다 |
| 부인 방지 | 만든 사람이 부인하기 어렵다 |

### 5.3 코드

```c
/* do_sign: 개인키로 서명한다. 서명 길이를 돌려준다 */
static int do_sign(EVP_PKEY *key, const unsigned char *msg, size_t mlen,
                   unsigned char *sig, size_t *siglen)
{
    EVP_MD_CTX *ctx = EVP_MD_CTX_new();
    ...
    if (EVP_DigestSignInit(ctx, NULL, NULL, NULL, key) == 1 &&
        EVP_DigestSign(ctx, sig, siglen, msg, mlen) == 1)
        rc = 0;
    ...
}
```

```c
    if (EVP_DigestVerifyInit(ctx, NULL, NULL, NULL, key) == 1 &&
        EVP_DigestVerify(ctx, sig, siglen, msg, mlen) == 1)
        rc = 0;
```

**Ed25519는 해시 함수를 따로 지정하지 않습니다.** 알고리즘 안에 정해져 있어 `EVP_DigestSignInit`의 해시 인자가 `NULL`입니다. 잘못 고를 여지를 없앤 설계입니다.

### 5.5 서명과 인증 태그의 차이

12강의 GCM 태그도 변조를 잡아냈습니다. **무엇이 다릅니까?**

| | 인증 태그(GCM) | 전자서명 |
|---|---|---|
| 필요한 것 | **양쪽이 같은 키** | 서명은 개인키, 검증은 **공개키** |
| 누가 만들 수 있나 | **키를 아는 누구나** | **개인키 주인만** |
| 제삼자가 검증 | **불가** | **가능** |
| 속도 | 매우 빠르다 | 느리다 |

**"키를 아는 누구나 만들 수 있다"** 가 결정적 차이입니다. 대칭키로는 **상대가 만든 것인지, 내가 만든 것인지** 구분할 수 없습니다.

## 제6절. 서명으로 중간자 막기

### 6.1 방법

> **밥이 자기 교환용 공개키에 서명해서 보낸다.**

앨리스가 **밥의 서명 공개키를 미리 알고 있다면**, 받은 교환용 공개키가 진짜 밥의 것인지 확인할 수 있습니다.

```c
    if (sign_it(bob_sign, bob_pub, 32, sig, &slen) != 0) { ... }
```

```c
    printf("앨리스가 받은 공개키를 밥의 서명으로 검증합니다...\n");
    if (verify_it(bob_sign, offered, 32, sig, slen) == 0) {
        printf("  → 검증 통과. 이 공개키는 밥이 보낸 것이 맞습니다.\n");
```

### 6.2 실행

```bash

```

```text
앨리스가 받은 공개키를 밥의 서명으로 검증합니다...
  → 검증 통과. 이 공개키는 밥이 보낸 것이 맞습니다.
  → 키 교환을 진행합니다.
```

```bash
./signed_kex mitm
```

```text
말로리가 공개키를 자기 것으로 바꿔치기합니다.

앨리스가 받은 공개키를 밥의 서명으로 검증합니다...
  → 검증 실패! 밥이 보낸 공개키가 아닙니다.
  → 연결을 끊습니다. 중간자를 막았습니다.
```

**4.3절에서 성공했던 공격이 막혔습니다.**

### 6.3 왜 막히는가

| 말로리가 할 수 있는 것 | 할 수 없는 것 |
|---|---|
| 공개키를 바꿔치기 | **자기 공개키에 밥의 서명을 붙이기** |
| 서명을 그대로 전달 | 서명을 자기 키에 맞게 고치기 |
| 연결을 끊기 | **밥인 척하기** |

**밥의 개인 서명키가 없으면 밥의 서명을 만들 수 없습니다.**

> **말로리는 여전히 연결을 방해할 수는 있습니다.** 자료를 버리거나 끊을 수 있습니다. 그러나 **읽거나 바꿀 수는 없습니다.** 이것을 "가용성은 지킬 수 없지만 비밀성과 무결성은 지킨다"고 표현합니다.
{: .prompt-info }

### 6.4 그런데 전제가 있습니다

> **"앨리스는 밥의 서명 공개키를 미리 알고 있다"**

**이 전제가 12강의 "미리 나눈 문구"와 무엇이 다릅니까?**

| | 12강 | 오늘 |
|---|---|---|
| 미리 나누는 것 | **비밀 문구** | **공개키** |
| 새어 나가면 | **끝장** | **문제없다** |
| 여러 상대와 | 상대마다 다른 문구 | **하나로 충분** |
| 한 번 나누면 | 그 상대와만 | **누구나 검증 가능** |

**큰 진전입니다.** 비밀을 나눌 필요가 없어졌고, 공개키 하나로 여러 상대를 상대할 수 있습니다.

**그래도 "미리 알고 있어야" 하는 것은 그대로입니다.** 처음 보는 서버와는 어떻게 합니까? 그것이 14강의 인증서입니다.

## 제7절. 혼합 방식

### 7.1 오늘날의 표준 구조

```text
   ① 키 교환      — 공개키 (느리다, 한 번만)
   ② 신원 확인    — 전자서명 (느리다, 한 번만)
   ③ 자료 주고받기 — 대칭키 (빠르다, 계속)
```

| 단계 | 쓰는 것 | 횟수 |
|---|---|---|
| 연결 시작 | 공개키 연산 | **몇 번** |
| 그 뒤 | AES-GCM | **수백만 번** |

**느린 것은 처음 몇 번만** 쓰고, 그 뒤로는 빠른 것을 씁니다. 이것이 12강과 13강을 이어 붙이는 방식이며, **TLS가 하는 일 그 자체**입니다.

### 7.2 우리가 만든 것들이 모이면

| 우리가 만든 것 | TLS에서의 이름 |
|---|---|
| 11강 `proto.c` | 레코드 계층 |
| 12강 `securechan.c` | 레코드 보호(AEAD) |
| 13강 `kex.c` | 키 공유(key share) |
| 13강 `signed_kex.c` | CertificateVerify |
| **14강 인증서** | Certificate |

**14강에서 이 조각들이 하나의 이름으로 묶입니다.**

```text
aes-256-cbc    1243650.11k  1380456.51k  1463033.09k  1544592.38k  1559109.63k  1572519.94k
```


### 8.2 읽는 법

| 항목 | 값 |
|---|---|
| AES-256-CBC | 초당 약 **1.5 GB** 처리 |
| ECDSA P-256 서명 | 초당 **57,729회** |
| ECDSA P-256 검증 | 초당 **21,244회** |

**대칭키로는 초당 기가바이트를 처리하는데, 공개키 연산은 초당 수만 번**입니다. 자료 크기로 환산하면 수천 배 차이가 납니다.

> **그래서 혼합 방식을 씁니다.**
> 연결 하나에 공개키 연산이 몇 번뿐이라면 전혀 문제가 되지 않습니다. 그러나 **모든 메시지마다** 한다면 서버가 감당하지 못합니다.
{: .prompt-tip }

### 8.3 그래도 접속이 많으면 부담입니다

초당 2만 번의 검증이면 **접속이 초당 2만 건일 때 CPU 하나를 다 씁니다.** 그래서 실무에서는 다음을 씁니다.

| 방법 | 설명 |
|---|---|
| **세션 재개** | 이미 한 연결의 결과를 재사용(14강) |
| 연결 유지 | 한 연결로 여러 요청 |
| 하드웨어 가속 | 전용 장비 |

### 9.1 여기까지 온 길

| 강의 | 해결한 것 | 남은 것 |
|---|---|---|
| 9강 | — | 모든 것이 평문 |
| **12강** | 비밀성·무결성 | **키를 어떻게 나누나** |
| **13강** | 키 교환·**신원 확인** | **서명 공개키를 어떻게 믿나** |
| 14강 | **인증서** | |

### 9.2 마지막 고리

> **처음 보는 서버의 공개키를 어떻게 믿습니까?**

| 방법 | 문제 |
|---|---|
| 미리 받아 둔다 | 서버가 수억 개인데? |
| 처음 본 것을 기억한다(TOFU) | **처음에 중간자가 있었다면?** |
| 웹에서 내려받는다 | **그 웹은 어떻게 믿나** |

**답은 "믿을 수 있는 제삼자가 보증한다"** 입니다. 그 보증서가 **인증서**이고, 보증하는 곳이 **인증기관(CA)** 입니다.

**14강에서 인증서를 직접 만들고, 검증하고, TLS 핸드셰이크에서 어떻게 쓰이는지 패킷으로 확인합니다.**

### 9.3 SSH를 떠올려 보십시오

처음 접속할 때 이런 물음을 본 적이 있을 것입니다.

```text
The authenticity of host 'c-srv (192.168.56.60)' can't be established.
ED25519 key fingerprint is SHA256:...
Are you sure you want to continue connecting (yes/no)?
```

**SSH는 인증기관 없이 TOFU 방식을 씁니다.** 사용자에게 직접 묻고, 한 번 승낙하면 기억합니다. 그래서 **처음 접속할 때가 유일한 위험 지점**입니다.

1강 6.2절에서 SSH로 VM에 접속할 때 본 그 물음이 **오늘 배운 문제와 정확히 같은 것**이었습니다.

### 문제 3·4. 전자서명과 중간자 방어

### 문제 5. 키를 파일로 저장

키 쌍을 파일에 저장하고 다시 읽어 들이십시오. **권한에 주의**하십시오.

**정답 및 해설**

```c
    FILE *fp = fopen("private.pem", "w");

    PEM_write_PrivateKey(fp, key, NULL, NULL, 0, NULL, NULL);
    fclose(fp);
    chmod("private.pem", 0600);         /* 3강 4.5절 */
```

```c
    fp = fopen("public.pem", "w");
    PEM_write_PUBKEY(fp, key);
    fclose(fp);
```

```bash
ls -l private.pem public.pem
```

```text
-rw------- 1 student student  119 Feb 15 09:30 private.pem
-rw-r--r-- 1 student student  113 Feb 15 09:30 public.pem
```

- **개인키는 0600, 공개키는 0644**입니다. 3강 4.5절에서 "개인 키 파일은 반드시 0600"이라고 예고한 그것입니다.
- 파일을 만든 **뒤에** `chmod` 하면 그사이에 잠깐 열려 있습니다. `open`에 권한을 주어 만드는 편이 낫습니다(2강 2.5절).
- PEM 형식은 사람이 읽을 수 있는 텍스트입니다. `cat`으로 열어 보십시오.
- 개인키를 여는 서술자에 **`O_CLOEXEC`** 를 붙이는 것도 잊지 마십시오(2강 8.3절).

### 문제 6. HKDF로 키 유도

공유 비밀에서 **보내는 키와 받는 키를 따로** 뽑아내십시오.

**정답 및 해설**

```c
    EVP_KDF *kdf = EVP_KDF_fetch(NULL, "HKDF", NULL);
    EVP_KDF_CTX *kctx = EVP_KDF_CTX_new(kdf);
    OSSL_PARAM params[5], *p = params;

    *p++ = OSSL_PARAM_construct_utf8_string("digest", "SHA256", 0);
    *p++ = OSSL_PARAM_construct_octet_string("key", secret, 32);
    *p++ = OSSL_PARAM_construct_octet_string("info", "c2s", 3);  /* 용도 */
    *p   = OSSL_PARAM_construct_end();

    EVP_KDF_derive(kctx, key_c2s, 32, params);
```

- **`info`만 바꾸면 다른 키**가 나옵니다. `"c2s"`와 `"s2c"`로 방향별 키를 뽑습니다.
- 이러면 12강 6.6절처럼 IV로 방향을 나눌 필요가 없어집니다. **키 자체가 다르기 때문**입니다.
- TLS 1.3이 이 방식을 씁니다. 하나의 비밀에서 여러 키를 체계적으로 뽑아냅니다.

### 문제 8. 암호 채널에 키 교환 붙이기

12강의 `securechan.c`에서 **미리 나눈 문구를 없애고** 키 교환으로 대체하십시오.

**정답 및 해설**

```c
/* sc_handshake: 연결 직후 키를 정한다 */
int sc_handshake(struct schan *sc, int is_client)
{
    EVP_PKEY *mine = gen_key();
    unsigned char my_pub[32], peer_pub[32], secret[32];
    size_t pl = sizeof my_pub, sl = sizeof secret;

    if (mine == NULL)
        return -1;
    EVP_PKEY_get_raw_public_key(mine, my_pub, &pl);

    /* 공개키를 주고받는다 — 11강의 프레이밍 그대로 */
    if (msg_send(sc->fd, my_pub, 32) != 0) { ... }
    if (msg_recv(sc->fd, peer_pub, sizeof peer_pub) != 32) { ... }

    if (derive(mine, peer_pub, 32, secret, &sl) != 0) { ... }

    /* 비밀을 그대로 쓰지 않는다 */
    hkdf(secret, sl, "cmid13", sc->key, SC_KEYLEN);

    OPENSSL_cleanse(secret, sizeof secret);
    EVP_PKEY_free(mine);
    sc->is_client = is_client;
    return 0;
}
```

- **연결마다 새 키 쌍**을 만들면 순방향 비밀성을 얻습니다(3.5절).
- 문구도, `PBKDF2`도 필요 없어졌습니다. **미리 나눌 것이 없습니다.**
- **그러나 아직 중간자에 뚫립니다.** 서명 검증을 넣지 않았기 때문입니다. 문제 4를 여기에 얹어 보십시오.
- 그때도 **밥의 서명 공개키를 어떻게 미리 아는가**는 남습니다. 14강까지 기다려야 합니다.

### 문제 9. 순방향 비밀성 확인

장기 키가 유출되어도 **지난 통신은 풀리지 않는 것**을 설명하십시오.

**정답 및 해설**

| 방식 | 장기 키 유출 시 |
|---|---|
| 장기 키로 직접 암호화 | **지난 통신 전부 복호화 가능** |
| **임시 키 교환** | **지난 통신은 안전** |

- 임시 키 쌍은 **연결이 끝나면 버립니다.** 메모리에서 지우면 세상에 남지 않습니다.
- 장기 서명키가 유출되면 **앞으로의 통신에서 사칭**당할 수 있지만, **지난 대화는 읽을 수 없습니다.**
- 이 성질 때문에 TLS 1.3은 임시 키 교환을 **필수**로 만들었습니다(14강).
- `OPENSSL_cleanse`로 개인키와 비밀을 지우는 것까지 해야 완전합니다.

### 문제 10. `openssl` 명령으로 서명

명령행 도구로 서명하고 검증해, **우리 프로그램과 맞춰 보십시오.**

**정답 및 해설**

```bash
openssl genpkey -algorithm ED25519 -out priv.pem
openssl pkey -in priv.pem -pubout -out pub.pem
```

```bash
openssl pkeyutl -sign -inkey priv.pem -rawin -in msg.txt -out msg.sig
```

```bash
openssl pkeyutl -verify -pubin -inkey pub.pem -rawin -in msg.txt -sigfile msg.sig
```

```text
Signature Verified Successfully
```

- **`-rawin`이 필요합니다.** Ed25519는 미리 해시하지 않고 원본에 서명하기 때문입니다(5.3절).
- 파일을 한 글자 고치고 다시 검증하면 실패합니다.
- **우리 프로그램이 만든 서명을 `openssl`로 검증**할 수 있어야 합니다. 되지 않는다면 서명 대상이나 형식이 다른 것입니다. 1부 12강부터 써 온 "정답과 맞춰 보기" 검증입니다.

## 정리

| 구분 | 핵심 |
|---|---|
| 공개키 | 열쇠가 둘. **공개키에서 개인키를 알아낼 수 없다** |
| 두 쓰임 | 비밀 전달(공개키로 잠금) / **서명(개인키로 잠금)** |
| 권장 | **X25519**(교환)·**Ed25519**(서명) — 32바이트, 실수할 여지가 적다 |
| **키 교환** | 도청당하면서도 **같은 비밀**에 도달 |
| 비밀 사용 | 그대로 쓰지 말고 **HKDF** 를 거친다 |
| 순방향 비밀성 | **임시 키 쌍**을 쓰고 버린다 |
| **중간자 공격** | 인증이 없으면 **암호화가 무의미**하다 |
| 전자서명 | 출처 + 무결성. **제삼자도 검증 가능** |
| 태그와의 차이 | 태그는 **키를 아는 누구나** 만들 수 있다 |
| 막는 법 | **교환용 공개키에 서명**을 붙인다 |
| 혼합 방식 | 공개키로 **한 번**, 대칭키로 **계속** |
| 성능 | 대칭키 초당 1.5 GB vs 공개키 초당 수만 회 |
| **남은 문제** | **서명 공개키를 어떻게 믿는가** → 14강 |
