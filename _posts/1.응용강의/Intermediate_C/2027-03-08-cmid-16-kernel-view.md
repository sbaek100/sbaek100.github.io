### 1.1 프로그램마다 자기만의 주소

**모든 프로그램이 자기가 메모리 전체를 쓰는 것처럼 봅니다.**

```text
   프로그램 A 의 주소 0x1000  ──┐
                              ├──▶ [MMU] ──▶ 서로 다른 물리 주소
   프로그램 B 의 주소 0x1000  ──┘
```

| 얻는 것 | |
|---|---|
| **격리** | 남의 메모리를 건드릴 수 없다 |
| 단순함 | 주소가 겹칠 걱정이 없다 |
| **과다 약속** | 물리 메모리보다 많이 약속할 수 있다(제4절) |
| 공유 | 같은 물리 페이지를 여럿이(제6절) |

> **1부 10강에서 배운 신뢰 경계**가 하드웨어로 강제되는 지점입니다. 프로세스 사이의 벽은 규칙이 아니라 **MMU가 물리적으로 막는** 것입니다.

### 2.4 권한 문자를 읽으십시오

| 문자 | 뜻 |

| `rw-p` | 읽기 + 쓰기 — 데이터·힙·스택 |

{: .prompt-tip }

### 2.5 코드가 실행 파일에 연결되어 있습니다

`r-xp` 줄에 **파일 경로가 적혀 있습니다.** 코드는 메모리에 통째로 올라온 것이 아니라 **파일에서 필요할 때 읽어 옵니다**(6강의 `mmap`과 같은 방식). 이것이 제5절의 **단단한 페이지 폴트**입니다.

### 2.6 `[vdso]`

**커널이 프로그램 주소 공간에 심어 놓은 작은 코드**입니다. `gettimeofday` 같은 것을 **시스템 호출 없이** 처리하기 위한 지름길입니다.

**1강 3절에서 "시스템 호출은 비싸다"** 고 했습니다. 너무 자주 불리는 몇 가지는 이렇게 우회합니다.

```bash
strace -c ./memview 2>&1 | tail -5
```

시각을 얻는 호출이 목록에 없다면 vdso로 처리된 것입니다.

## 제3절. 주소 무작위화

### 3.1 매번 달라집니다

같은 프로그램을 두 번 실행합니다.

```text
1회차:  코드(main)  0x5c04a62102ff    스택  0x7ffde91b479c
2회차:  코드(main)  0x5ccf060782ff    스택  0x7fffefde982c
```

**주소가 전부 달라졌습니다.** 이것을 **ASLR**(주소 공간 배치 무작위화)이라 합니다.

### 3.2 왜 하는가

| 공격 | ASLR이 있으면 |
|---|---|
| 특정 주소로 되돌아가게 만들기 | **주소를 모른다** |
| 라이브러리 함수 호출 | **어디 있는지 모른다** |

**1부 10강의 버퍼 오버플로 대책**입니다. 취약점이 있어도 **악용을 훨씬 어렵게** 만듭니다.

### 3.3 끄는 법 — 디버깅할 때만

```bash
setarch $(uname -m) -R ./memview
```

```text
1회차:  코드(main)  0x5555555552ff    스택  0x7fffffffe7bc
2회차:  코드(main)  0x5555555552ff    스택  0x7fffffffe7bc
```

**두 번 다 같습니다.** 이러면 주소를 적어 두고 재현할 수 있습니다.

| 언제 쓰나 | |
|---|---|
| 주소가 나오는 버그 재현 | 1부 10강 |
| **TSan이 WSL에서 실패할 때** | **8강 문제 10에서 쓴 그 명령** |
| 강의 자료의 주소를 고정 | |

### 4.3 무슨 일이 일어난 것인가

| 시점 | VmSize | VmRSS |
|---|---|---|
| 시작 | 2,680 KB | 1,408 KB |
| **`malloc(512MB)` 직후** | **526,972 KB** | **1,408 KB** |
| 전부 건드린 뒤 | 526,972 KB | **525,696 KB** |

> **`malloc`은 물리 메모리를 주지 않았습니다.**
> **"쓰겠다고 약속한 자리"만 표시**했을 뿐입니다. 실제 물리 메모리는 **처음 건드리는 순간** 한 페이지씩 배정됩니다. 이것을 **게으른 할당**이라 합니다.
{: .prompt-info }

### 4.4 그래서 생기는 일

| 결과 | |
|---|---|
| `malloc`이 **거의 실패하지 않는다** | 약속만 하니까 |
| **`NULL` 검사만으로는 부족하다** | 성공했어도 나중에 메모리가 없을 수 있다 |
| **OOM 킬러** | 물리 메모리가 진짜 모자라면 커널이 프로세스를 죽인다 |
| `ps`의 VSZ가 크다고 놀라지 말 것 | RSS를 보아야 한다 |

```bash
cat /proc/sys/vm/overcommit_memory
```

| 값 | 뜻 |
|---|---|
| **0** | 적당히 판단(기본값) |
| 1 | 무조건 허락 |
| 2 | 엄격하게 제한 |

### 4.5 1부에서 배운 것과 이어집니다

1부 9강에서 **"`malloc`의 반환값을 반드시 검사하라"** 고 했습니다. 그것은 지금도 옳습니다. 다만 **검사를 통과했다고 메모리가 확보된 것은 아니라**는 것을 오늘 알았습니다.

**정말 확보해야 한다면** 잡은 직후에 전부 건드리거나(`memset`), `mlock`으로 고정합니다.

## 제5절. 페이지 폴트

### 5.1 두 가지

| 종류 | 언제 | 비용 |
|---|---|---|
| **부드러운**(minor) | 물리 페이지는 있는데 연결만 안 됨 | 싸다 |
| **단단한**(major) | **디스크에서 읽어야 함** | **비싸다** |

```c
static void faults(const char *when)
{
    struct rusage ru;

    getrusage(RUSAGE_SELF, &ru);
    printf("  %-14s 부드러운 폴트 %ld회, 단단한 폴트 %ld회\n",
           when, ru.ru_minflt, ru.ru_majflt);
}
```

### 5.2 숫자를 맞춰 보십시오

```text
  시작         부드러운 폴트 87회
  malloc 뒤    부드러운 폴트 88회        <- 1회만 늘었다
  건드린 뒤    부드러운 폴트 131159회

건드린 페이지 수: 131072 개
```

**131159 − 88 = 131071.** 건드린 페이지 수 **131072**와 거의 정확히 같습니다.

> **한 페이지를 처음 건드릴 때마다 폴트가 한 번씩 났습니다.**
> 이것이 게으른 할당의 실체입니다. `malloc`은 1회밖에 안 늘었는데(88), 실제로 쓰기 시작하자 13만 번 났습니다.
{: .prompt-tip }

### 5.3 단단한 폴트가 0인 이유

**메모리에서 공간을 만들어 준 것**이지 디스크에서 읽은 것이 아니기 때문입니다. 단단한 폴트는 이럴 때 납니다.

| 경우 | |
|---|---|
| 실행 파일의 코드를 처음 실행 | 2.5절 |
| `mmap`한 파일을 처음 읽음 | 6강 |
| 스왑에 나갔던 페이지 | |

**단단한 폴트가 많으면 성능 문제**입니다. 디스크를 기다리기 때문입니다.

```bash
/usr/bin/time -v ./lazymem 2>&1 | grep -i fault
```

## 제6절. fork는 복사하지 않는다

### 6.1 4강에서 미룬 이야기

4강에서 **"`fork`는 프로세스를 복사한다"** 고 했습니다. 그러면 256MB를 쓰는 프로그램이 `fork`하면 **512MB가 필요해야 합니다.** 정말 그럴까요?

### 6.2 RSS만으로는 알 수 없습니다

먼저 주의할 점이 있습니다.

> **`VmRSS`는 공유 페이지와 전용 페이지를 구분하지 않습니다.**
> 그래서 RSS만 보면 `fork` 뒤에도, 고쳐 쓴 뒤에도 **거의 변화가 없어 보입니다.** 실제로 이 실습을 RSS로 처음 해 보면 아무것도 관찰되지 않습니다.
>
> **`/proc/self/smaps_rollup`** 을 보아야 **공유/전용**이 갈라집니다.
{: .prompt-warning }

```c
/* rollup: /proc/self/smaps_rollup 에서 한 항목을 읽는다 */
static long rollup(const char *key)
{
    FILE *fp = fopen("/proc/self/smaps_rollup", "r");
    ...
}
```

```c
static void show(const char *who)
{
    printf("  %-18s Rss=%7ld KB  공유=%7ld KB  전용=%7ld KB\n",
           who, rollup("Rss:"),
           rollup("Shared_Clean:") + rollup("Shared_Dirty:"),
           rollup("Private_Clean:") + rollup("Private_Dirty:"));
}
```

### 6.3 실험

```c
    memset(p, 'A', (size_t) size);           /* 부모가 실제로 채운다 */

    printf("=== fork 전 ===\n");
    show("부모");
    fflush(stdout);                          /* fork 전에 반드시 비운다 (4강) */

    pid = fork();
```

```bash
./cowtest
```

```text
=== fork 전 ===
  부모             Rss= 263716 KB  공유=   1452 KB  전용= 262264 KB

=== fork 직후 (아직 아무것도 안 고침) ===
  자식             Rss= 263180 KB  공유= 263136 KB  전용=     44 KB

=== 자식이 64MB 를 고쳐 쓴 뒤 ===
  자식             Rss= 263180 KB  공유= 197600 KB  전용=  65580 KB

=== 자식이 128MB 를 고쳐 쓴 뒤 ===
  자식             Rss= 263180 KB  공유= 132064 KB  전용= 131116 KB
  자식이 안 건드린 곳 p[268435455] = A

=== 자식이 끝난 뒤 ===
  부모             Rss= 263908 KB  공유=   1644 KB  전용= 262264 KB
  부모의 p[0] = A  (자식이 'B' 로 바꿨지만 부모는 그대로)
```

### 6.4 숫자를 맞춰 보십시오

| 시점 | 공유 | 전용 |
|---|---|---|
| fork 직후 | **263,136 KB** | 44 KB |
| 64MB 고침 | 197,600 KB | 65,580 KB |
| 128MB 고침 | 132,064 KB | 131,116 KB |

| 계산 | 값 |
|---|---|
| 공유 감소 (263,136 → 197,600) | **65,536 KB = 64 MB** |
| 전용 증가 (44 → 65,580) | **65,536 KB = 64 MB** |
| 그다음 64MB도 | **정확히 65,536 KB씩** |

> **고쳐 쓴 만큼만, 정확히 그만큼만 복사되었습니다.**
> `fork` 직후에는 **256MB 전부가 공유**였습니다. 128MB를 고쳐 쓰자 **그 128MB만 전용**이 되었습니다. 나머지 128MB는 여전히 부모와 같은 물리 페이지를 봅니다.
{: .prompt-tip }

### 6.5 쓸 때 복사

> **쓸 때 복사**(copy-on-write): `fork` 직후에는 페이지를 공유하고 **읽기 전용**으로 표시해 둔다. 어느 쪽이든 **쓰려고 하면** 그때 폴트가 나고, 커널이 **그 페이지만** 복사해 준다.

```text
   fork 직후:   부모 ──┐
                     ├──▶ [같은 물리 페이지] (읽기 전용 표시)
                자식 ──┘

   자식이 쓰면: 부모 ────▶ [원본]
                자식 ────▶ [복사본]   ← 이 페이지만
```

| 그래서 | |
|---|---|
| `fork`가 **빠르다** | 페이지 표만 만든다 |
| **큰 프로그램도 fork 가능** | 8GB 프로그램이 fork해도 즉시 8GB가 필요하지 않다 |
| **`fork` + `exec`이 낭비가 아니다** | 어차피 `exec`이 다 버린다(4강 6절) |

### 6.6 부모는 그대로입니다

```text
  부모의 p[0] = A  (자식이 'B' 로 바꿨지만 부모는 그대로)
```

**격리는 지켜집니다.** 공유는 **커널 내부의 최적화**일 뿐, 프로그램에서는 각자 자기 사본을 가진 것과 똑같이 보입니다.

### 6.7 이 실습을 만들며 겪은 일

**자식의 출력이 통째로 사라졌습니다.**

```c
        printf("자식: ...");
        _exit(0);           /* 버퍼를 비우지 않는다 */
```

| 원인 | |
|---|---|
| 출력이 파이프로 가면 **블록 버퍼** | 1부 6강 |
| **`_exit`은 버퍼를 비우지 않는다** | 4강 5절 |

**그리고 `fork` 앞에서 비우지 않았더니 부모의 줄이 두 번 나왔습니다.** 버퍼가 통째로 복사되어 부모와 자식이 각각 출력했기 때문입니다.

```c
    fflush(stdout);                      /* fork 전에 반드시 비운다 (4강) */
    pid = fork();
```

```c
        fflush(stdout);                  /* _exit 는 버퍼를 비우지 않는다 */
        _exit(0);
```

> **4강에서 글로 배운 두 가지가 실제로 벌어졌습니다.**
> 이런 것은 겪어 보아야 몸에 남습니다. **여러분도 일부러 `fflush`를 빼고 실행해 보십시오.**
{: .prompt-tip }

## 제7절. `/proc`으로 들여다보기

### 7.1 실행 중인 프로그램 보기

```bash
sleep 30 &
```

```bash
grep -E "^(Name|State|Pid|PPid|Threads|VmSize|VmRSS)" /proc/416/status
```

```text
Name:	sleep
State:	S (sleeping)
Pid:	416
PPid:	282
VmSize:	    3124 kB
VmRSS:	    1664 kB
Threads:	1
```

| 항목 | 어디서 배웠나 |
|---|---|
| `State: S (sleeping)` | 4강 — 상태 |
| `PPid` | 4강 — 부모 |
| **`Threads`** | 7강 |
| `VmSize`/`VmRSS` | 제4절 |

### 7.2 열린 파일 서술자

```bash
ls -l /proc/416/fd
```

```text
lr-x------ 1 seungsoo seungsoo 64 Aug 22 14:18 0 -> /dev/null
l-wx------ 1 seungsoo seungsoo 64 Aug 22 14:18 1 -> pipe:[7574]
l-wx------ 1 seungsoo seungsoo 64 Aug 22 14:18 2 -> pipe:[7575]
```

> **2강에서 배운 서술자 0·1·2가 그대로 보입니다.**
> 그리고 1·2가 **`pipe:`** 로 되어 있습니다. 이 명령의 출력이 파이프로 연결되어 있기 때문입니다. **6강에서 만든 파이프**가 여기 나타납니다.
>
> `l-wx`는 **쓰기 전용**, `lr-x`는 **읽기 전용** 서술자라는 뜻입니다.
{: .prompt-tip }

### 7.3 그 밖에

```bash
ls -l /proc/416/exe
```

```text
/proc/416/exe -> /usr/bin/sleep
```

```bash
ls -l /proc/416/cwd
```

```text
/proc/416/cwd -> /home/seungsoo/cmid16
```

| 경로 | 내용 |
|---|---|
| `/proc/PID/maps` | 메모리 지도(2.3절) |
| `/proc/PID/status` | 요약 |
| `/proc/PID/fd/` | **열린 서술자** |
| `/proc/PID/exe` | 실행 파일 |
| `/proc/PID/cwd` | 작업 디렉터리(3강) |
| `/proc/PID/environ` | 환경 변수 |
| `/proc/PID/limits` | 자원 한계 |
| `/proc/PID/smaps_rollup` | **공유/전용 메모리**(6.2절) |

### 7.4 디버깅에 쓰는 법

| 증상 | 볼 곳 |
|---|---|
| 서술자가 샌다 | **`ls /proc/PID/fd \| wc -l`** — 계속 늘어나면 누수 |
| 메모리가 샌다 | `VmRSS`가 계속 증가 |
| 멈춰 있다 | `State`와 `/proc/PID/stack` |
| 어느 파일을 열었나 | `/proc/PID/fd` |

> **2강 문제 10에서 "서술자 누수를 어떻게 찾는가"** 라고 물었습니다. 답이 여기 있습니다. **실행 중에 `/proc/PID/fd`를 세어 보는 것**입니다.
{: .prompt-tip }

### 7.5 `/proc`은 진짜 파일이 아닙니다

**디스크에 없습니다.** 읽는 순간 커널이 만들어 냅니다.

```bash
ls -l /proc/self/status
```

크기가 **0**으로 나옵니다. 그런데 읽으면 내용이 있습니다. **3강에서 배운 파일의 상식이 통하지 않는 곳**입니다.

**그래도 `open`/`read`로 읽을 수 있습니다.** "모든 것이 파일"이라는 유닉스의 설계 덕분입니다(2강 1절).

## 제8절. 스케줄링과 한계

### 8.1 CPU는 몇 개인가

```bash
getconf _NPROCESSORS_ONLN
```

```text
8
```

**7강에서 스레드를 만들 때 이 숫자를 기준**으로 삼았습니다.

### 8.2 문맥 교환

```bash
grep -E "^(voluntary|nonvoluntary)_ctxt_switches" /proc/self/status
```

| 종류 | 언제 |
|---|---|
| **자발적**(voluntary) | 스스로 기다린다 — `read`, `sleep`, 잠금 대기 |
| **비자발적**(nonvoluntary) | **시간이 다 되어 뺏긴다** |

> **비자발적 교환이 많으면 CPU 경쟁**이 심한 것이고, **자발적 교환이 많으면 입출력 대기**가 많은 것입니다. 성능을 볼 때 유용한 구분입니다.
{: .prompt-tip }

### 8.3 왜 순서가 보장되지 않는가

4강에서 **"부모와 자식 중 누가 먼저 실행될지 모른다"**, 7강에서 **"스레드의 실행 순서는 보장되지 않는다"** 고 했습니다.

**스케줄러가 정하기 때문입니다.** 그리고 그 판단은 다음에 따라 달라집니다.

| 요소 | |
|---|---|
| 다른 프로그램들의 상태 | |
| CPU 개수와 부하 | |
| `nice` 값 | |
| 마지막에 얼마나 CPU를 썼는가 | |

**같은 프로그램도 실행할 때마다 다릅니다.** 그래서 8강에서 **"몇 번 돌려서 맞았다고 옳은 것이 아니다"** 라고 한 것입니다.

### 8.4 자원 한계

```bash
ulimit -a
```

```text
core file size              (blocks, -c) 0
data seg size               (kbytes, -d) unlimited
open files                          (-n) 10240
pipe size                (512 bytes, -p) 8
```

| 항목 | 어디서 만났나 |
|---|---|
| **`open files`** | **10강 — 서술자 한계** |
| `pipe size` | 6강 |
| `core file size` | **0이면 코어 덤프가 안 생긴다** |

**10강에서 `ulimit -n`으로 시험한 그 값**입니다. 프로그램 안에서는 이렇게 봅니다.

```c
struct rlimit rl;

getrlimit(RLIMIT_NOFILE, &rl);
printf("서술자: 현재 %ld, 최대 %ld\n", (long) rl.rlim_cur, (long) rl.rlim_max);
```

### 8.5 시스템 전체

```bash
head -4 /proc/meminfo
```

```text
MemTotal:       16122072 kB
MemFree:        15144296 kB
MemAvailable:   15463844 kB
Buffers:           47952 kB
```

| 항목 | 뜻 |
|---|---|
| `MemFree` | **아무도 안 쓰는** 메모리 |
| **`MemAvailable`** | **실제로 쓸 수 있는** 메모리(캐시 회수 포함) |

**`MemFree`가 적다고 걱정하지 마십시오.** 커널이 남는 메모리를 캐시로 쓰고 있을 뿐입니다. **`MemAvailable`을 보십시오.**

## 제9절. 모든 것이 만나는 자리

### 9.1 1부부터 배운 것이 커널에서는

| 배운 것 | 커널에서는 |
|---|---|
| 변수와 배열(1부) | 주소 공간의 한 자리(2.2절) |
| 포인터(1부 8강) | **가상 주소** |
| `malloc`(1부 9강) | **약속만**(제4절) |
| 지역 변수 | 스택 페이지 |
| 파일 서술자(2강) | 커널 표의 색인(7.2절) |
| 파일 오프셋(2강) | 열린 파일 표의 항목 |
| `fork`(4강) | **페이지 표 복사**(제6절) |
| `exec`(4강) | 주소 공간을 통째로 갈아 끼움 |
| 시그널(5강) | 실행 흐름에 끼어드는 커널 |
| 파이프(6강) | 커널 안의 원형 버퍼 |
| `mmap`(6강) | **페이지 표에 파일을 연결** |
| 스레드(7강) | **주소 공간을 공유**하는 실행 흐름 |
| 경쟁 상태(8강) | 스케줄러가 아무 데서나 끊는다 |
| 소켓(9강) | 커널의 프로토콜 처리 |
| `epoll`(10강) | 커널이 관리하는 관심 목록 |
| TLS(15강) | 응용 계층 — **커널은 바이트만 나른다** |

### 9.2 스레드가 왜 가벼운가

```text
   프로세스 = 주소 공간 + 실행 흐름
   스레드   =            실행 흐름   ← 주소 공간을 공유
```

**7강에서 "스레드는 메모리를 공유한다"** 고 한 것이, 커널에서는 **같은 페이지 표를 가리킨다**는 뜻입니다.

```bash
grep Threads /proc/self/status
```

리눅스에서는 **스레드도 프로세스와 같은 방식으로 스케줄**됩니다. 다만 주소 공간을 공유할 뿐입니다.

### 9.3 다음은 어디로

**이 과정 다음에 갈 수 있는 길**입니다.

| 방향 | 무엇을 |
|---|---|
| **커널 프로그래밍** | 모듈, 드라이버, 시스템 호출 추가 |
| **성능 분석** | `perf`, eBPF, 화염 그래프 |
| **컨테이너** | 네임스페이스, cgroup — **격리의 확장** |
| 보안 | seccomp, 능력(capability), SELinux |
| 분산 시스템 | 네트워크 위의 프로그램 |

**오늘 배운 `/proc`은 이 모든 길의 출입구**입니다.

> **1부 정리편에서 "다음은 시스템 프로그래밍"** 이라고 했습니다. 그 시스템 프로그래밍이 2부였고, **오늘 그 아래층까지 내려다보았습니다.**
{: .prompt-tip }

## 제10절. 자주 나오는 실수

| 증상 | 원인 | 해결 |

| 페이지 크기를 4096으로 고정 | 환경에 따라 다름 | `sysconf(_SC_PAGESIZE)` |

| `/proc` 파일 크기가 0 | 진짜 파일이 아님 | 그냥 읽으면 된다(7.5절) |
| 실행 환경에서 ASLR을 끔 | 잘못된 습관 | **절대 금지** |

### 문제 1·2·3. 주소 공간과 ASLR

주소 공간을 확인하고, `/proc/self/maps`를 읽고, ASLR을 확인하십시오.

**정답 및 해설**

제2·3절의 코드와 결과가 답입니다.

- **구역의 순서**(코드 < 데이터 < 힙 < 스택)를 확인하십시오.
- `r-xp`(코드)와 `rw-p`(데이터)를 구분하고, **`rwx`가 없다**는 것을 확인하십시오(2.4절).
- ASLR: 두 번 실행해 주소가 다른 것, `setarch -R`로 같아지는 것을 모두 보이십시오.
- **코드 구역에 쓰려고 하면** 어떻게 되는지 시험해 보십시오.

```c
char *p = (char *) main;
*p = 0;                 /* 세그멘테이션 오류 */
```

- 이것이 **1부 8강에서 본 세그멘테이션 오류의 정체**입니다. 페이지 권한을 어긴 것입니다.

### 문제 4·5. 게으른 할당과 페이지 폴트

512MB를 잡고 **VmSize와 VmRSS의 차이**를 보이고, 페이지 폴트를 세십시오.

**정답 및 해설**

4.2절의 결과가 답입니다.

| 시점 | VmSize | VmRSS | 부드러운 폴트 |
|---|---|---|---|
| `malloc` 직후 | 526,972 KB | **1,408 KB** | 88 |
| 전부 건드린 뒤 | 526,972 KB | 525,696 KB | **131,159** |

- **폴트 증가분(131,071)과 페이지 수(131,072)를 맞춰 보는 것**이 이 문제의 핵심입니다.
- `calloc`으로 바꾸면 어떻게 되는지 해 보십시오. 큰 크기는 커널이 **0으로 채워진 페이지**를 약속하므로 역시 즉시 할당되지 않습니다.
- `memset`으로 전부 채우면 `malloc` 직후에 RSS가 오릅니다. **정말 확보해야 할 때** 쓰는 방법입니다(4.5절).
- 4096이 아니라 **1바이트씩** 건드려 보십시오. 폴트 수는 같습니다. **페이지 단위**로 나기 때문입니다.

### 문제 6. 쓸 때 복사 측정

`fork` 뒤 자식이 일부만 고쳐 쓸 때, **공유와 전용이 어떻게 바뀌는지** 측정하십시오.

**정답 및 해설**

6.3절의 결과가 답입니다.

| 시점 | 공유 | 전용 |
|---|---|---|
| fork 직후 | 263,136 KB | 44 KB |
| 64MB 고침 | 197,600 KB | 65,580 KB |
| 128MB 고침 | 132,064 KB | 131,116 KB |

- **감소분과 증가분이 정확히 65,536 KB(=64MB)** 인 것을 확인하십시오.
- **먼저 `VmRSS`로 해 보십시오.** 아무 변화가 없습니다. **왜 그런지 설명할 수 있어야** 합니다(6.2절).
- `fflush`를 빼고 실행해, 출력이 사라지거나 두 번 나오는 것을 직접 보십시오(6.7절).
- 자식이 **읽기만** 하면 어떻게 되는지도 해 보십시오. 전용이 늘지 않습니다. **쓸 때만** 복사되기 때문입니다.

### 문제 7. 서술자 누수 찾기

일부러 서술자를 새게 만들고, `/proc`으로 찾아내십시오.

**정답 및 해설**

```c
    for (i = 0; i < 100; i++) {
        int fd = open("/etc/hostname", O_RDONLY);   /* close 를 안 한다 */

        printf("%d 번째, 서술자 %d\n", i, fd);
        sleep(1);
    }
```

```bash
ls /proc/$(pgrep leaky)/fd | wc -l
```

- **숫자가 계속 늘어나면 누수**입니다.
- 서술자 번호가 계속 커지는 것도 단서입니다. 2강 3절에서 배운 **"가장 작은 빈 번호"** 규칙 때문에, 닫지 않으면 번호가 단조 증가합니다.
- 한계에 닿으면 `EMFILE`이 납니다(10강).
- **실제 서버에서 가장 흔한 장애 원인의 하나**입니다.

### 문제 8·9. 자원 한계와 스택

한계를 확인하고, **스택이 자라는 것**을 보이십시오.

**정답 및 해설**

```c
static void recurse(int depth)
{
    char buf[1024];

    buf[0] = (char) depth;
    if (depth % 100 == 0)
        printf("깊이 %5d  스택 주소 %p\n", depth, (void *) buf);
    recurse(depth + 1);
}
```

- 주소가 **점점 작아집니다.** 스택은 **아래로** 자랍니다(2.2절).
- 결국 **스택 오버플로**로 죽습니다. `ulimit -s`가 한계입니다.
- `ulimit -s`를 바꿔 한계가 달라지는 것을 확인하십시오.
- **1부 8강의 재귀**가 왜 위험할 수 있는지 여기서 이해됩니다. 깊이가 깊으면 스택이 넘칩니다.

```bash
ulimit -c unlimited
```

- 코어 덤프를 켜면 죽은 뒤 상태를 `gdb`로 볼 수 있습니다(1부 10강).

## 정리

| 구분 | 핵심 |
|---|---|
| 가상 메모리 | 프로그램마다 자기 주소 공간. **격리는 하드웨어가 강제** |
| 페이지 | **4096바이트**. `sysconf(_SC_PAGESIZE)` |
| 주소 공간 | 코드 → 데이터 → **힙(위로)** … **스택(아래로)** |
| `maps` | 권한 문자. **`rwx`인 구역은 없다**(W^X) |
| ASLR | 매번 주소가 달라진다. **디버깅 때만** `setarch -R` |
| **게으른 할당** | **`malloc`은 약속만.** 건드릴 때 배정 |
| VmSize / VmRSS | **약속 / 현실** |
| 페이지 폴트 | 부드러운(싸다) / **단단한(디스크, 비싸다)** |
| 측정 확인 | 512MB → **13만 회의 부드러운 폴트** |
| **쓸 때 복사** | **`fork`는 복사하지 않는다.** 쓸 때 그 페이지만 |
| 측정 확인 | 128MB를 고치자 **정확히 128MB만** 전용으로 |
| **주의** | **RSS로는 COW가 안 보인다** → `smaps_rollup` |
| `/proc` | `maps`·`status`·**`fd`**·`smaps_rollup` |
| 서술자 누수 | **`ls /proc/PID/fd \| wc -l`** 이 계속 늘어나면 |
| 스케줄링 | 자발적(대기) / **비자발적(뺏김)** 교환 |
| 한계 | `ulimit -a` · `getrlimit` |
| **전체** | **1부부터 배운 모든 것이 커널의 몇 가지 장치로 설명된다** |
