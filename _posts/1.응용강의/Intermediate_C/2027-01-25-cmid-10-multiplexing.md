## 제1절. 지금 서버의 문제

### 1.1 한 명씩만

9강의 서버 구조입니다.

```c
for (;;) {
    conn_fd = accept(listen_fd, ...);
    while (read_line(conn_fd, ...) > 0) {   /* 이 손님이 끝날 때까지 */
        ...                                  /* 여기 갇혀 있다 */
    }
    close(conn_fd);
}
```

**`while` 안에 있는 동안 `accept`로 돌아가지 못합니다.** 다음 손님은 `listen`의 대기줄에서 기다립니다.

### 1.2 무엇이 문제인가

| 상황 | 결과 |
|---|---|
| 손님이 아무 말도 안 하고 있다 | **다른 모두가 기다린다** |
| 손님이 느린 회선을 쓴다 | 마찬가지 |
| 대기줄(backlog)이 찬다 | **새 접속이 거부된다** |

**한 명이 서비스 전체를 멈출 수 있습니다.** 악의가 없어도 그렇습니다.

### 1.3 핵심 질문

> **"여러 서술자를 동시에 지켜보려면 어떻게 하는가?"**

`read`는 **하나의 서술자**에서만 기다립니다. 서술자가 100개면 어디에 자료가 왔는지 알 방법이 없습니다.

이 문제를 **입출력 다중화**(I/O multiplexing)라 하며, 이번 강의의 주제입니다.

## 제2절. 네 가지 방법 개관

| 방법 | 방식 | 장점 | 한계 |
|---|---|---|---|
| **`fork`** | 접속마다 프로세스 | 단순·격리 | **비싸다**, 수천 개는 무리 |
| 스레드 | 접속마다 스레드 | `fork`보다 싸다 | 여전히 개수 한계(7강 3.3절) |
| **`select`** | 한 흐름이 여럿 감시 | 이식성 최고 | **`FD_SETSIZE` 한계**, 느리다 |
| **`poll`** | 같은 개념, 개수 제한 없음 | `select`보다 낫다 | 여전히 **전부 훑는다** |
| **`epoll`** | 커널이 준비된 것만 알려 줌 | **가장 빠르다** | **리눅스 전용** |

이번 강의에서는 **하나의 에코 서버를 다섯 가지 방식으로** 만들어 견줍니다.

```bash
./multiserv fork|select|poll|epoll|epollet [포트]
```

### 2.1 공통 부분

```c
static int make_listener(unsigned short port)
{
    int fd, on = 1;
    struct sockaddr_in addr;

    fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd == -1)
        die("socket");
    if (setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on) == -1)
        die("setsockopt");
    ...
}
```

```c
/* echo_once: 한 번 읽어 그대로 돌려준다.
   0 = 계속, -1 = 이 연결을 닫아라 */
static int echo_once(int fd)
{
    char buf[BUFSZ];
    ssize_t n;

    n = read(fd, buf, sizeof buf);
    if (n < 0) {
        if (errno == EINTR)
            return 0;
        if (errno == EAGAIN || errno == EWOULDBLOCK)
            return 0;               /* 더 읽을 것이 없다 */
        return -1;
    }
    if (n == 0)
        return -1;                  /* 상대가 닫았다 */
    ...
}
```

**하는 일은 다섯 방식이 모두 같습니다.** 달라지는 것은 **"누가 준비되었는지 알아내는 방법"** 뿐입니다.

## 제3절. `fork` 방식

### 3.1 9강 문제 9의 그것

```c
        pid = fork();
        if (pid == 0) {
            close(lfd);
            while (echo_once(cfd) == 0)
                ;
            close(cfd);
            _exit(0);
        }
        close(cfd);
```

**자식은 `listen_fd`를, 부모는 `conn_fd`를 닫습니다**(9강 문제 9).

### 3.2 언제 쓸 만한가

| 좋은 점 | 나쁜 점 |
|---|---|
| **격리** — 하나가 죽어도 나머지는 산다 | 프로세스 생성 비용 |
| 코드가 단순하다 | 메모리를 많이 쓴다 |
| 자료 공유 사고가 없다 | 손님끼리 자료를 나눌 수 없다 |
| **권한을 낮출 수 있다** | 문맥 전환이 잦다 |

7강 문제 10에서 잰 것처럼 `fork`는 스레드보다 세 배쯤 비쌉니다. 다만 **접속이 오래 유지되고 수가 적다면** 여전히 좋은 선택입니다.

> **"권한을 낮출 수 있다"** 가 보안에서 중요합니다. 자식이 손님을 맡기 전에 `setuid`로 권한을 떨어뜨리면, 그 손님이 프로그램을 장악해도 할 수 있는 일이 제한됩니다.

## 제4절. `select`

### 4.1 개념

> **"이 서술자들 중 준비된 것이 있으면 알려 달라."**

```c
#include <sys/select.h>

int select(int nfds, fd_set *readfds, fd_set *writefds,
           fd_set *exceptfds, struct timeval *timeout);
```

| 함수/매크로 | 하는 일 |
|---|---|
| `FD_ZERO(&set)` | 비운다 |
| `FD_SET(fd, &set)` | 넣는다 |
| `FD_CLR(fd, &set)` | 뺀다 |
| `FD_ISSET(fd, &set)` | 준비되었는지 확인 |

### 4.2 코드

```c
    for (;;) {
        int nready;

        rset = allset;              /* select 는 집합을 고쳐 놓으므로 복사 */
        nready = select(maxfd + 1, &rset, NULL, NULL, NULL);
        if (nready == -1) {
            if (errno == EINTR)
                continue;
            die("select");
        }

        if (FD_ISSET(lfd, &rset)) {
            int cfd = accept(lfd, NULL, NULL);
            ...
        }

        for (i = 0; i < FD_SETSIZE && nready > 0; i++) {
            int cfd = client[i];

            if (cfd < 0 || !FD_ISSET(cfd, &rset))
                continue;
            nready--;
            if (echo_once(cfd) < 0) {
                FD_CLR(cfd, &allset);
                close(cfd);
                client[i] = -1;
            }
        }
    }
```

### 4.3 세 가지 함정

**① 집합이 고쳐집니다.**

```c
rset = allset;      /* 반드시 복사해서 넘긴다 */
```

`select`는 넘긴 집합에서 **준비되지 않은 것을 지워 버립니다.** 원본을 그대로 넘기면 두 번째 호출부터 아무도 감시하지 못합니다.

**② 듣기 소켓도 함께 감시합니다.**

`listen_fd`가 "읽을 수 있다"는 것은 **새 손님이 왔다**는 뜻입니다.

**③ `nfds`는 개수가 아니라 최댓값 + 1입니다.**

```c
select(maxfd + 1, ...)
```

이름이 `nfds`여서 개수처럼 보이지만 **가장 큰 서술자 번호 + 1**입니다. 자주 틀리는 곳입니다.

### 4.4 치명적 한계 — `FD_SETSIZE`

```c
                if (cfd >= FD_SETSIZE) {        /* 한계! */
                    fprintf(stderr, "서술자 %d 는 FD_SETSIZE(%d) 를 넘습니다\n",
                            cfd, FD_SETSIZE);
                    close(cfd);
                }
```

**`fd_set`은 고정 크기 비트 배열**입니다. 리눅스에서 `FD_SETSIZE`는 **1024**입니다.

연결 1100개를 시도해 보았습니다.

```bash
./multiserv select 5450 &
./loadgen 127.0.0.1 5450 1100 1
```

```text
연결 1100개를 여는 데 3.054초
요청 1020건 성공, 80건 실패, 0.109초 (초당 9398건)
```

서버 쪽 기록입니다.

```text
[select] 포트 5450 에서 기다립니다 (FD_SETSIZE=1024)
서술자 1024 는 FD_SETSIZE(1024) 를 넘습니다
```

```bash
grep -c "FD_SETSIZE" sel.log
```

```text
81
```

**정확히 1024번 서술자부터 거부되었고, 80건이 실패했습니다.**

> **`ulimit -n`이 10240이어도 소용없습니다.**
> 서술자는 만들 수 있지만 **`fd_set`에 넣을 수 없습니다.** `FD_SETSIZE`를 늘려 다시 컴파일하는 방법이 있지만 권장되지 않습니다. 그런 경우에는 `poll`이나 `epoll`을 써야 합니다.
{: .prompt-danger }

### 4.5 그래도 배우는 이유

| 이유 | |
|---|---|
| **이식성이 가장 좋다** | 거의 모든 시스템에 있다 |
| 시간 제한을 걸기 쉽다 | 마지막 인자 |
| 옛 코드에 많다 | 읽을 줄 알아야 한다 |

## 제5절. `poll`

### 5.1 배열로 관리합니다

```c
#include <poll.h>

int poll(struct pollfd *fds, nfds_t nfds, int timeout);

struct pollfd {
    int   fd;         /* 감시할 서술자, 음수면 건너뛴다 */
    short events;     /* 무엇을 기다리나 */
    short revents;    /* 무슨 일이 일어났나 — 커널이 채워 준다 */
};
```

| `events`/`revents` | 뜻 |
|---|---|
| `POLLIN` | 읽을 것이 있다 |
| `POLLOUT` | 쓸 수 있다 |
| `POLLHUP` | 상대가 끊었다 |
| `POLLERR` | 오류 |

### 5.2 `select`보다 나은 점

| | `select` | `poll` |
|---|---|---|
| 개수 한계 | **`FD_SETSIZE`(1024)** | **없다** |
| 입력·출력 분리 | 넘긴 집합이 **고쳐진다** | `events`와 `revents`가 **따로** |
| 무엇을 기다릴지 | 세 집합으로 | **서술자마다 지정** |

**`revents`가 따로 있어 복사할 필요가 없습니다.** 4.3절 ①의 함정이 사라집니다.

### 5.3 코드

```c
    for (;;) {
        int nready = poll(pfd, (nfds_t) nfd, -1);
        ...
        if (pfd[0].revents & POLLIN) {
            int cfd = accept(lfd, NULL, NULL);
            ...
        }

        for (i = 1; i < nfd && nready > 0; i++) {
            if (pfd[i].fd < 0 || pfd[i].revents == 0)
                continue;
            nready--;
            if (echo_once(pfd[i].fd) < 0) {
                close(pfd[i].fd);
                pfd[i].fd = -1;
            }
        }
    }
```

**`pfd[i].fd = -1`로 비워 둡니다.** 음수 서술자는 `poll`이 건너뛰므로 배열을 다시 정리할 필요가 없습니다.

### 5.4 남은 문제

> **`select`와 `poll` 모두, 부를 때마다 **전체 목록을 커널에 넘기고** 돌아와서 **전부 훑어야** 합니다.**

| 연결 수 | 매번 하는 일 |
|---|---|
| 10개 | 10개 검사 |
| 1만 개 | **1만 개 검사** — 자료가 하나만 와도 |

**연결이 늘수록 비례해서 느려집니다.** 제9절에서 이것을 측정합니다.

## 제6절. `epoll`

### 6.1 발상의 전환

> **목록을 커널에 **미리 등록**해 두고, **준비된 것만** 돌려받는다.**

| | `select`/`poll` | `epoll` |
|---|---|---|
| 목록 전달 | **매번** | **한 번 등록** |
| 돌려받는 것 | 전체 목록 | **준비된 것만** |
| 비용 | 연결 수에 비례 | **준비된 수에 비례** |

### 6.2 세 함수

```c
#include <sys/epoll.h>

int epoll_create1(int flags);
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);
```

| `op` | 뜻 |
|---|---|
| `EPOLL_CTL_ADD` | 감시 목록에 넣는다 |
| `EPOLL_CTL_MOD` | 조건을 바꾼다 |
| `EPOLL_CTL_DEL` | 뺀다 |

**`epoll` 자체도 파일 서술자입니다.** `epoll_create1`이 돌려주는 것이 그것이며, 다 쓰면 `close` 해야 합니다.

### 6.3 코드

```c
    int ep = epoll_create1(0);
    struct epoll_event ev, events[MAXCONN];

    set_nonblock(lfd);
    ev.events  = EPOLLIN;
    ev.data.fd = lfd;
    if (epoll_ctl(ep, EPOLL_CTL_ADD, lfd, &ev) == -1)
        die("epoll_ctl(listen)");

    for (;;) {
        int n = epoll_wait(ep, events, MAXCONN, -1);
        ...
        for (i = 0; i < n; i++) {
            int fd = events[i].data.fd;
            ...
        }
    }
```

**`epoll_wait`가 돌려준 `n`개만 처리하면 됩니다.** 전체를 훑지 않습니다.

### 6.4 `accept`도 반복문으로

```c
            if (fd == lfd) {
                for (;;) {                      /* 한 번에 여러 명이 올 수 있다 */
                    int cfd = accept(lfd, NULL, NULL);

                    if (cfd == -1) {
                        if (errno == EAGAIN || errno == EWOULDBLOCK)
                            break;
                        if (errno == EINTR)
                            continue;
                        break;
                    }
                    set_nonblock(cfd);
                    ev.events  = edge ? (EPOLLIN | EPOLLET) : EPOLLIN;
                    ev.data.fd = cfd;
                    ...
                }
                continue;
            }
```

**알림 하나에 손님이 여럿 와 있을 수 있습니다.** `EAGAIN`이 날 때까지 `accept`를 되풀이해야 놓치지 않습니다.

### 6.5 `data` 항목

```c
union epoll_data {
    void    *ptr;
    int      fd;
    uint32_t u32;
    uint64_t u64;
};
```

**커널이 그대로 돌려주는 자리**입니다. 서술자만 넣어도 되지만, 실무에서는 **연결 정보 구조체의 주소**를 넣습니다.

```c
ev.data.ptr = conn;         /* 이 연결의 상태를 통째로 */
```

그러면 알림을 받았을 때 **버퍼·상태·상대 주소를 곧바로** 얻을 수 있습니다. 17강 종합 과제에서 이 방식을 씁니다.

## 제7절. 수준 방식과 가장자리 방식

### 7.1 두 가지 알림 방식

| 방식 | 언제 알려 주나 |
|---|---|
| **수준 방식**(level-triggered, 기본) | **자료가 남아 있는 동안 계속** |
| **가장자리 방식**(edge-triggered, `EPOLLET`) | **새로 들어온 순간 한 번만** |

```text
  자료 100바이트 도착, 30바이트만 읽었다면

  수준 방식  : 다음 epoll_wait 에서 또 알려 준다 (70바이트 남았으니까)
  가장자리 방식: 알려 주지 않는다 (새로 들어온 것이 없으니까)
```

### 7.2 가장자리 방식의 규칙

> **`EAGAIN`이 날 때까지 **모두 읽어야** 합니다.**

```c
            /* 가장자리 방식이면 EAGAIN 이 날 때까지 모두 읽어야 한다 */
            for (;;) {
                int r = echo_once(fd);

                if (r < 0) {
                    epoll_ctl(ep, EPOLL_CTL_DEL, fd, NULL);
                    close(fd);
                    break;
                }
                if (!edge)
                    break;                      /* 수준 방식은 한 번만 */
                ...
            }
```

**남겨 두면 영영 알림이 오지 않습니다.** 연결이 멈춘 것처럼 보이고, 원인을 찾기가 매우 어렵습니다.

### 7.3 비교

| | 수준 방식 | 가장자리 방식 |
|---|---|---|
| 기본값 | **그렇다** | `EPOLLET` 필요 |
| 반드시 다 읽어야 하나 | 아니다 | **그렇다** |
| 논블로킹 필수인가 | 권장 | **필수** |
| 알림 횟수 | 많다 | 적다 |
| 실수 여지 | 적다 | **많다** |

> **처음에는 수준 방식을 쓰십시오.**
> 가장자리 방식은 알림 횟수를 줄여 주지만, 실측해 보면 차이가 크지 않은 경우가 많습니다(제9절). **정확성을 먼저 얻고, 필요할 때 바꾸십시오.**
{: .prompt-tip }

### 7.4 가장자리 방식이 논블로킹을 요구하는 이유

가장자리 방식에서는 "모두 읽을 때까지" 반복합니다. 그런데 **막히는 소켓**이라면 마지막 `read`에서 **영원히 멈춥니다.** 더 올 자료가 없기 때문입니다.

**논블로킹이면** 그 순간 `EAGAIN`으로 돌아오므로 반복문을 빠져나올 수 있습니다.

## 제8절. 논블로킹과 `EAGAIN`

### 8.1 설정

```c
static void set_nonblock(int fd)
{
    int fl = fcntl(fd, F_GETFL, 0);

    if (fl == -1 || fcntl(fd, F_SETFL, fl | O_NONBLOCK) == -1)
        die("fcntl(O_NONBLOCK)");
}
```

**기존 플래그를 읽어 `|`로 더해야** 합니다. 그냥 `fcntl(fd, F_SETFL, O_NONBLOCK)`이라고 쓰면 다른 플래그가 지워집니다.

### 8.2 무엇이 달라지나

| 동작 | 막히는 소켓 | 논블로킹 소켓 |
|---|---|---|
| 읽을 것이 없는 `read` | **기다린다** | `-1` + **`EAGAIN`** |
| 버퍼가 찬 `write` | 기다린다 | **일부만 쓰거나** `EAGAIN` |
| 손님이 없는 `accept` | 기다린다 | `-1` + `EAGAIN` |
| `connect` | 완료까지 기다린다 | `-1` + `EINPROGRESS` |

**`EAGAIN`은 오류가 아닙니다.** "지금은 안 되니 나중에 다시"라는 뜻입니다. 1강 10.1절에서 이 `errno`를 처음 보았고, 6강 4.1절에서 파이프 용량을 잴 때 썼습니다.

```c
        if (errno == EAGAIN || errno == EWOULDBLOCK)
            return 0;               /* 더 읽을 것이 없다 */
```

> **`EAGAIN`과 `EWOULDBLOCK`은 리눅스에서 같은 값**이지만, 표준은 다를 수 있다고 규정합니다. **둘 다 검사하는 것**이 이식성 있는 방식입니다.
{: .prompt-info }

### 8.3 쓰기가 더 어렵습니다

읽기는 "읽을 것이 없으면 나중에"로 끝나지만, **쓰기는 보낼 자료를 들고 있어야** 합니다.

| 상황 | 해야 할 일 |
|---|---|
| `write`가 일부만 씀 | **나머지를 보관** |
| `EAGAIN` | 보관해 두고 **`EPOLLOUT`을 등록** |
| 쓸 수 있게 되면 | 알림을 받아 이어서 보낸다 |
| 다 보내면 | **`EPOLLOUT`을 해제** |

**이것이 진짜 서버가 복잡해지는 지점**입니다. 연결마다 **보낼 자료 버퍼**를 들고 있어야 합니다.

> `EPOLLOUT`을 등록해 두고 해제하지 않으면, **쓸 수 있다는 알림이 끝없이 옵니다.** CPU가 100%가 되는 흔한 사고입니다.
{: .prompt-danger }

이번 강의의 예제는 응답이 짧아 이 문제를 피해 갔습니다. 17강에서 제대로 다룹니다.

### 9.4 C10K 문제

> **1999년, "한 서버가 동시 접속 1만 개를 감당할 수 있는가"** 라는 물음이 제기되었습니다. 이를 **C10K 문제**라 합니다.

| 방식 | 1만 연결이면 |
|---|---|
| 접속마다 프로세스 | 프로세스 1만 개 — **불가능에 가깝다** |
| 접속마다 스레드 | 스택만 80 GiB(7강 3.3절) |
| `select` | **1024에서 막힌다** |
| `poll` | 매번 1만 개 검사 |
| **`epoll`** | **준비된 것만** — 가능 |

**오늘날 nginx·Redis·Node.js가 모두 `epoll` 계열을 씁니다.**

### 9.5 이식성

| 시스템 | 대응하는 기능 |
|---|---|
| 리눅스 | **`epoll`** |
| BSD·macOS | `kqueue` |
| Solaris | `/dev/poll`, 이벤트 포트 |
| 윈도우 | IOCP |

**개념은 같고 이름만 다릅니다.** `libevent`·`libuv` 같은 라이브러리가 이 차이를 감춰 줍니다.

### 9.6 측정할 때 주의할 점

| 주의 | 이유 |
|---|---|
| **같은 컴퓨터에서 재면 왜곡된다** | 부하 생성기가 CPU를 나눠 쓴다 |
| 한 번의 결과를 믿지 말 것 | 7강 문제 3의 원칙 |
| `ulimit -n`을 확인 | 연결 수의 상한 |
| 커널 설정도 영향 | 포트 범위·`TIME_WAIT` |

**두 VM으로 재면 훨씬 정확합니다.** 서버는 `c-srv`, 부하는 `c-cli`에서 돌리십시오.

### 문제 2. `FD_SETSIZE` 한계 확인

`select` 서버에 1024개가 넘는 연결을 시도해 무슨 일이 일어나는지 보이십시오.

### 문제 5. 가장자리 방식

`EPOLLET`를 적용하고, **다 읽지 않으면** 어떻게 되는지 확인하십시오.

**정답 및 해설**

7.2절의 코드가 답입니다. **일부러 고장 내 보는 것**이 이 문제의 핵심입니다.

```c
            /* 일부러 한 번만 읽어 본다 — 가장자리 방식에서는 위험 */
            echo_once(fd);
```

- 짧은 메시지에서는 잘 동작하는 것처럼 보입니다. **한 번에 여러 줄을 보내면** 뒷줄이 처리되지 않고 연결이 멈춥니다.

```bash
printf 'a\nb\nc\n' | nc -q1 127.0.0.1 5000
```

- **재현되지 않을 수도 있습니다.** 그것이 이 버그의 무서운 점입니다. 자료가 한 번에 도착해야 드러납니다.
- 측정해 보면 가장자리 방식이 수준 방식보다 **빠르지 않은 경우도 많습니다**(9.2절: 28497 vs 31866). 복잡도를 감수할 만한지 재어 보고 정하십시오.

### 문제 6. 논블로킹 확인

논블로킹 소켓에서 `read`가 `EAGAIN`을 돌려주는 것을 확인하십시오.

**정답 및 해설**

```c
    set_nonblock(fd);
    errno = 0;
    n = read(fd, buf, sizeof buf);
    printf("read = %zd, errno = %d (%s)\n", n, errno, strerror(errno));
```


- **11이 `EAGAIN`** 입니다. 1강 10.1절의 표에서 본 그 값입니다.
- 막히는 소켓이었다면 이 줄에서 프로그램이 멈춰 있었을 것입니다.
- `fcntl`로 플래그를 **읽어서 더한 것**을 확인하십시오(8.1절). `O_NONBLOCK`만 설정하면 `O_APPEND` 같은 다른 플래그가 지워집니다.

### 문제 8. 시간 제한 두기

아무 말 없이 30초가 지난 연결을 끊도록 고치십시오.

**정답 및 해설**

**마지막 활동 시각을 연결마다 기록**하고, 주기적으로 검사합니다.

```c
struct conn {
    int    fd;
    time_t last;                    /* 마지막으로 무언가 한 시각 */
};
```

```c
    n = epoll_wait(ep, events, MAXCONN, 1000);      /* 1초마다 깨어난다 */
    ...
    now = time(NULL);
    for (i = 0; i < nconn; i++) {
        if (conns[i].fd >= 0 && now - conns[i].last > 30) {
            epoll_ctl(ep, EPOLL_CTL_DEL, conns[i].fd, NULL);
            close(conns[i].fd);
            conns[i].fd = -1;
        }
    }
```

- **시간 제한을 `-1`이 아니라 유한한 값으로** 주는 것이 핵심입니다. 그래야 아무 일이 없어도 주기적으로 깨어나 검사할 수 있습니다.
- 이 처리가 없으면 **연결을 열어 두고 아무것도 하지 않는 것만으로** 서버 자원을 소진시킬 수 있습니다. 11강에서 이런 종류의 공격을 다룹니다.
- `EPOLL_CTL_DEL`을 `close`보다 **먼저** 해야 합니다(제10절 표).

---

### 문제 9. 접속 수 제한

동시 접속을 일정 수로 제한하고, 넘으면 정중히 거절하십시오.

**정답 및 해설**

```c
        if (nconn >= MAX_CLIENTS) {
            const char *msg = "서버가 혼잡합니다. 잠시 뒤 다시 시도하십시오\n";

            write_full(cfd, msg, strlen(msg));
            close(cfd);
            continue;
        }
```

- **`accept`는 하되 곧바로 닫는 것**이 요령입니다. `accept`를 안 하면 대기줄에 쌓여 상대는 아무 응답도 못 받습니다.
- 이유를 알려 주고 닫는 편이 낫습니다. 그냥 끊으면 클라이언트가 원인을 알 수 없습니다.
- 상한은 `ulimit -n`보다 충분히 작게 잡으십시오. 서술자를 다 쓰면 **`accept` 자체가 실패**하고 그때는 거절 메시지조차 보낼 수 없습니다.

### 문제 10. 방식 고르기

다음 각 상황에 어떤 방식이 알맞은지 고르고 이유를 쓰십시오.

1. 접속이 하루에 열 번, 각각 몇 시간씩 유지되는 관리 도구
2. 동시 접속 5만 개를 받는 채팅 서버
3. 신뢰할 수 없는 코드를 손님마다 실행해야 하는 서비스
4. 다른 UNIX 계열에도 그대로 옮겨야 하는 프로그램

**정답 및 해설**

| 상황 | 선택 | 이유 |
|---|---|---|
| 1. 접속이 드물고 길다 | **`fork`** | 단순함이 최고. 성능이 문제되지 않는다 |
| 2. 동시 5만 | **`epoll`** | 유일하게 감당 가능(9.4절) |
| 3. 신뢰할 수 없는 코드 | **`fork`** | **격리와 권한 낮추기**(3.2절) |
| 4. 이식성 | **`poll`** | `select`의 한계가 없고 POSIX 표준 |

- **성능만으로 고르는 것이 아닙니다.** 3번에서 `epoll`을 고르면 손님 하나가 서버 전체를 장악할 수 있습니다.
- 4번에서 `select`가 아니라 `poll`인 이유를 설명할 수 있어야 합니다. 둘 다 POSIX지만 `select`에는 `FD_SETSIZE` 한계가 있습니다.
- 실무에서는 **섞어 씁니다.** nginx는 프로세스를 몇 개 띄우고 각각이 `epoll`을 돌립니다. 7강 9.3절에서 말한 그 구조입니다.

## 정리

| 구분 | 핵심 |
|---|---|
| 문제 | `read`는 **하나만** 기다린다 → 다중화가 필요 |
| `fork` | 단순·**격리**. 수천 개는 무리 |
| `select` | 이식성 최고. **`FD_SETSIZE`(1024) 한계**, 집합이 고쳐진다 |
| `poll` | 개수 제한 없음, `revents` 분리. **여전히 전부 훑는다** |
| **`epoll`** | 미리 등록, **준비된 것만** 돌려받음. 리눅스 전용 |
| 수준 방식 | 기본. 남아 있으면 계속 알려 준다 |
| 가장자리 방식 | 한 번만. **`EAGAIN`까지 다 읽어야** 하고 **논블로킹 필수** |
| `EAGAIN` | 오류가 아니라 **"지금은 안 된다"** |
| 쓰기 | 못 보낸 자료를 **보관**하고 `EPOLLOUT` 등록·해제 |
| 측정 | 500연결에서 `select` 45% 감소, **`epoll` 16% 감소** |
| C10K | 오늘날 서버가 `epoll` 계열을 쓰는 이유 |
| 선택 | 성능만이 기준이 아니다 — **격리·이식성·단순함** |
