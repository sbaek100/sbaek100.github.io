## 제1절. 스레드란

### 1.1 한 프로세스 안의 여러 흐름

> **스레드는 같은 주소 공간을 함께 쓰는 실행 흐름입니다.**

```text
   프로세스 (주소 공간 하나)
   ┌──────────────────────────────────────────┐
   │  코드 · 전역 변수 · 힙 · 열린 파일        │  ← 모두 공유
   │                                          │
   │  ┌────────┐  ┌────────┐  ┌────────┐     │
   │  │ 스택 1 │  │ 스택 2 │  │ 스택 3 │     │  ← 각자 따로
   │  └────────┘  └────────┘  └────────┘     │
   │   스레드 1     스레드 2     스레드 3      │
   └──────────────────────────────────────────┘
```

### 1.2 `fork`와 비교

4강에서 배운 것과 나란히 놓아 보십시오.

| | `fork` (프로세스) | 스레드 |
|---|---|---|
| 주소 공간 | **따로**(복사) | **함께** |
| 전역 변수 | 각자의 복사본 | **공유** |
| 힙 | 각자의 복사본 | **공유** |
| 스택 | 각자 | **각자** |
| 열린 서술자 | 물려받되 위치 공유 | **완전히 공유** |
| 만드는 비용 | 비싸다 | **싸다** |
| 통신 | 파이프·공유 메모리 필요 | **그냥 변수로** |
| 하나가 죽으면 | 나머지는 산다 | **전부 죽는다** |
| 자료 보호 | 자동으로 격리 | **직접 해야 한다** |

**마지막 두 줄이 대가입니다.** 편한 만큼 위험합니다.

### 1.3 리눅스에서는 둘이 형제입니다

리눅스 커널은 프로세스와 스레드를 **같은 구조로** 다룹니다. 무엇을 공유할지만 다르게 정할 뿐입니다.

| 개념 | 커널이 부르는 이름 |
|---|---|
| 프로세스 | 태스크(task) |
| 스레드 | **같은 그룹에 속한 태스크** |

그래서 스레드에도 고유 번호가 있습니다. **TID**(thread id)라 하며, 주 스레드의 TID는 PID와 같습니다. 제2절에서 눈으로 확인합니다.

## 제2절. 만들고 거두기

### 2.1 두 함수

```c
#include <pthread.h>

int pthread_create(pthread_t *thread, const pthread_attr_t *attr,
                   void *(*start_routine)(void *), void *arg);
int pthread_join(pthread_t thread, void **retval);
```

| 함수 | 대응하는 프로세스 함수 |
|---|---|
| `pthread_create` | `fork` |
| `pthread_join` | `waitpid` |

**시작 함수의 모양이 정해져 있습니다.**

```c
void *이름(void *arg)
```

인자도 반환값도 `void *` 하나뿐입니다. 여러 값을 넘기려면 **구조체를 만들어 그 주소를 넘깁니다.**

### 2.2 오류를 알리는 방식이 다릅니다

> **pthread 함수는 `errno`를 쓰지 않습니다. 오류 번호를 그대로 돌려줍니다.**

```c
        rc = pthread_create(&th[i], NULL, worker, &tasks[i]);
        if (rc != 0) {                  /* errno 가 아니라 반환값으로 알린다 */
            fprintf(stderr, "pthread_create: %s\n", strerror(rc));
            return 1;
        }
```

| 지금까지의 시스템 호출 | pthread 함수 |
|---|---|
| 실패하면 `-1`, 이유는 `errno` | **실패하면 오류 번호를 반환**, 성공하면 0 |
| `perror`·`strerror(errno)` | **`strerror(rc)`** |

**이 차이를 놓치는 것이 가장 흔한 실수입니다.** `if (pthread_create(...) == -1)`이라고 쓰면 오류를 영영 못 잡습니다. 성공했을 때 0을 돌려주므로 `if (rc != 0)`으로 검사해야 합니다.

### 2.3 예제

```c
static void *worker(void *arg)
{
    struct task *t = arg;
    long i, sum = 0;

    for (i = 1; i <= t->count; i++)
        sum += i;

    printf("[스레드 %d] PID %d, TID %ld, 1부터 %ld 까지의 합 = %ld\n",
           t->id, (int) getpid(), (long) syscall(SYS_gettid), t->count, sum);

    /* 결과를 돌려준다. 스택 위의 값을 돌려주면 안 된다 */
    t->count = sum;
    return t;
}
```

```bash
gcc -Wall -Wextra -std=gnu17 -pthread thread1.c -o thread1
```

```bash
./thread1
```

```text
[주 스레드] PID 432, TID 432
[스레드 0] PID 432, TID 433, 1부터 100 까지의 합 = 5050
[스레드 1] PID 432, TID 434, 1부터 200 까지의 합 = 20100
[주 스레드] 0번이 돌려준 값 = 5050
[주 스레드] 1번이 돌려준 값 = 20100
[스레드 2] PID 432, TID 435, 1부터 300 까지의 합 = 45150
[주 스레드] 2번이 돌려준 값 = 45150
```

**세 가지를 확인하십시오.**

| 관찰 | 뜻 |
|---|---|
| **PID가 전부 432로 같다** | 프로세스는 하나다 |
| TID가 432·433·434·435로 다르다 | 실행 흐름은 넷이다 |
| **주 스레드의 TID = PID** | 1.3절의 그 규칙 |
| 출력 순서가 뒤섞였다 | **순서는 보장되지 않는다**(4강 2.4절과 같다) |

### 2.4 `-pthread` 옵션

```bash
gcc -Wall -Wextra -std=gnu17 -pthread thread1.c -o thread1
```

**`-pthread`를 붙이십시오.** 다만 요즘은 붙이지 않아도 링크가 됩니다.

```bash
ldd --version | head -1
```

```text
ldd (Ubuntu GLIBC 2.39-0ubuntu8.8) 2.39
```

**glibc 2.34부터 pthread 함수가 libc 안으로 들어왔기 때문**입니다. 예전에는 `-lpthread`가 없으면 `undefined reference to 'pthread_create'` 오류가 났습니다(1부 11강 3.1절의 그 오류).

그래도 붙여야 하는 이유가 있습니다.

```bash
diff <(gcc -dM -E -x c /dev/null) <(gcc -pthread -dM -E -x c /dev/null)
```

```text
101a102
> #define _REENTRANT 1
```

| 이유 | 설명 |
|---|---|
| `_REENTRANT`를 정의한다 | 라이브러리가 스레드 안전한 판을 고를 수 있다 |
| **이식성** | 오래된 시스템·다른 UNIX에서는 여전히 필요하다 |
| 뜻이 분명해진다 | "이 프로그램은 스레드를 쓴다" |

> **`-lpthread`가 아니라 `-pthread`입니다.** 앞의 것은 라이브러리만 링크하고, 뒤의 것은 **컴파일과 링크 양쪽을** 알맞게 설정합니다.

## 제3절. 무엇을 공유하는가

### 3.1 주소를 찍어 보면 답이 나옵니다

```c
static void *worker(void *arg)
{
    int local = 200;                /* 지역 — 스레드마다 따로 */
    long id = (long) arg;

    printf("[스레드 %ld] 지역변수 주소 %p, 전역 주소 %p, 힙 주소 %p\n",
           id, (void *) &local, (void *) &global, (void *) heap);

    if (id == 1) {                  /* 1번만 값을 바꾼다 */
        global = 111;
        *heap  = 333;
        local  = 222;
    }
    return NULL;
}
```

```bash
./thread_share
```

```text
[주 스레드] 지역변수 주소 0x7fffc4fab8f0, 전역 주소 0x5c4197991010, 힙 주소 0x5c41a0a842a0, fd 3
[스레드 1] 지역변수 주소 0x73fa1bffdeac, 전역 주소 0x5c4197991010, 힙 주소 0x5c41a0a842a0
[스레드 0] 지역변수 주소 0x73fa1c7feeac, 전역 주소 0x5c4197991010, 힙 주소 0x5c41a0a842a0
[주 스레드] 1번이 바꾼 뒤: global=111 heap=333 local=200
```

### 3.2 읽는 법

| 항목 | 주소가 | 결론 |
|---|---|---|
| 전역 `global` | **셋 다 `0x5c4197991010`** | **공유** |
| 힙 `heap` | **셋 다 `0x5c41a0a842a0`** | **공유** |
| 지역 `local` | 전부 다르다 | **각자의 스택** |

그리고 결과가 증명합니다. **1번 스레드가 바꾼 `global`과 `heap`이 주 스레드에도 보입니다.**

4강 3.2절의 `fork` 실험과 정반대입니다.

| | `fork` | 스레드 |
|---|---|---|
| 자식/스레드가 전역을 바꾸면 | 부모는 **100 그대로** | 주 스레드도 **111** |

### 3.3 스택은 얼마나 떨어져 있나

두 스레드의 지역변수 주소를 빼 보십시오.

```text
0x73fa1c7feeac − 0x73fa1bffdeac = 0x800000 = 8 MiB
```

**정확히 8 MiB 간격**입니다. 스레드마다 그만큼의 스택을 받기 때문입니다.

```c
    pthread_attr_t a;
    size_t sz = 0;

    pthread_attr_init(&a);
    pthread_attr_getstacksize(&a, &sz);
    printf("새 스레드 기본 스택 크기: %zu 바이트 (%zu MiB)\n", sz, sz / (1024*1024));
```

```text
주 스레드 스택 크기: 8384512 바이트 (7 MiB)
새 스레드 기본 스택 크기: 8388608 바이트 (8 MiB)
```

```bash
ulimit -s
```

```text
8192
```

**`ulimit -s`의 8192 KiB = 8 MiB와 같습니다.**

> **스레드를 수천 개 만들면 주소 공간이 모자랍니다.** 스레드 1000개면 스택만 8 GiB입니다. 실제로는 쓰는 만큼만 물리 메모리를 차지하지만, 주소 공간은 미리 잡힙니다. 그래서 스레드를 많이 쓰는 서버는 `pthread_attr_setstacksize`로 스택을 줄입니다.
{: .prompt-warning }

### 3.4 공유 목록

| 공유하는 것 | 각자 갖는 것 |
|---|---|
| 코드·전역 변수·`static` 변수 | **스택**(지역 변수) |
| 힙(`malloc`) | **`errno`**(제8절) |
| **열린 파일 서술자** | TID |
| 현재 작업 디렉터리 | 시그널 마스크 |
| 사용자·그룹 ID | 스케줄링 우선순위 |
| 시그널 **처리기** | |

**"시그널 처리기는 공유하지만 마스크는 각자"** 라는 점이 까다롭습니다. 다중 스레드 프로그램에서 시그널을 다루는 일은 특히 조심해야 하며, 8강에서 다시 다룹니다.

## 제4절. 인자와 반환값

### 4.1 가장 흔한 실수

```c
        if (bad)
            pthread_create(&th[i], NULL, show, &i);        /* 위험: i 는 하나뿐 */
        else
            slots[i] = i, pthread_create(&th[i], NULL, show, &slots[i]);
```

**반복문 변수의 주소를 넘기면 안 됩니다.** 모든 스레드가 **같은 변수 하나**를 가리키고, 그동안 `i`는 계속 바뀌기 때문입니다.

```bash
./argbug bad ; ./argbug bad ; ./argbug bad
```

```text
1 3 4 1 1 
bad  판이 출력한 값들입니다
3 4 3 3 4 
bad  판이 출력한 값들입니다
1 2 4 2 4 
bad  판이 출력한 값들입니다
```

```bash
./argbug good
```

```text
0 3 1 2 4 
good 판이 출력한 값들입니다
```

| 판 | 결과 |
|---|---|
| `bad` | **값이 빠지고 겹친다.** 실행할 때마다 다르다 |
| `good` | **0~4가 모두 한 번씩.** 순서만 뒤섞인다 |

**`good`도 순서는 뒤죽박죽입니다.** 그것은 정상입니다. 문제는 **값이 틀리는 것**입니다.

### 4.2 안전하게 넘기는 방법

| 방법 | 설명 |
|---|---|
| **스레드마다 다른 자리** | 배열의 각 칸(`&slots[i]`) |
| 구조체 배열 | 여러 값을 넘길 때 |
| 값을 그대로 | `(void *)(long) i` — 작은 정수만 |
| `malloc`으로 하나씩 | 스레드가 다 쓰고 `free` |

```c
pthread_create(&th[i], NULL, show, (void *) (long) i);   /* 값을 그대로 */
```

이 방법은 포인터를 정수로 쓰는 것이라 엄밀히는 이식성이 떨어지지만, 리눅스에서는 널리 쓰입니다. `intptr_t`를 쓰면 더 정확합니다.

### 4.3 반환값

```c
    t->count = sum;
    return t;                       /* 스택 위의 값을 돌려주면 안 된다 */
```

```c
        rc = pthread_join(th[i], &ret);
        ...
        printf("[주 스레드] %d번이 돌려준 값 = %ld\n",
               i, ((struct task *) ret)->count);
```

> **지역 변수의 주소를 돌려주지 마십시오.**
> 스레드가 끝나면 그 스택은 사라집니다. 1부 5강에서 "함수가 끝난 뒤 지역 변수의 주소는 쓸 수 없다"고 배운 것과 같습니다. **호출한 쪽이 준 자리**나 `malloc`한 자리에 결과를 넣으십시오.
{: .prompt-danger }

### 4.4 거두지 않으면

`pthread_join`을 부르지 않으면 **좀비와 비슷한 상태**가 됩니다. 스택 등 자원이 반환되지 않습니다.

| 방법 | 설명 |
|---|---|
| `pthread_join` | 끝나기를 기다리고 자원도 회수 |
| **`pthread_detach`** | **거둘 필요가 없다고 선언** — 끝나면 알아서 정리 |

```c
pthread_detach(th);         /* 결과가 필요 없을 때 */
```

4강 8절의 좀비와 같은 구조입니다. **결과가 필요 없으면 떼어 놓고, 필요하면 반드시 거두십시오.**

## 제5절. 경쟁 상태를 만들어 본다

**이 절이 이번 강의의 핵심입니다.**

### 5.1 문제의 코드

```c
static void *bump(void *arg)
{

    (void) arg;
    for (i = 0; i < rounds; i++) {
        if (use_mutex) {
```

## 제6절. 뮤텍스

### 6.1 한 번에 하나만

> **뮤텍스(mutex)는 "한 번에 하나만 들어가는 문"입니다.**

```c
#include <pthread.h>

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
```

| 함수 | 하는 일 |
|---|---|
| `lock` | 잠근다. 이미 잠겨 있으면 **기다린다** |
| `unlock` | 푼다 |
| `trylock` | 잠겨 있으면 **기다리지 않고** `EBUSY` |

### 6.2 고쳐 보기

```c
            pthread_mutex_lock(&lock);
            counter++;              /* 읽고, 더하고, 쓴다 */
            pthread_mutex_unlock(&lock);
```

```bash
for i in 1 2 3 4 5; do ./race 4 100000 mutex; done
```

```text
뮤텍스 있음 | 스레드  4 × 100000회 | 기대값   400000 | 실제값   400000 | 차이 0
뮤텍스 있음 | 스레드  4 × 100000회 | 기대값   400000 | 실제값   400000 | 차이 0
뮤텍스 있음 | 스레드  4 × 100000회 | 기대값   400000 | 실제값   400000 | 차이 0
뮤텍스 있음 | 스레드  4 × 100000회 | 기대값   400000 | 실제값   400000 | 차이 0
뮤텍스 있음 | 스레드  4 × 100000회 | 기대값   400000 | 실제값   400000 | 차이 0
```

**다섯 번 모두 정확합니다.**

### 6.3 규칙

| 규칙 | 이유 |
|---|---|
| **잠근 스레드가 푼다** | 남이 풀면 안 된다 |
| **임계 구역은 짧게** | 길면 다른 스레드가 계속 기다린다 |
| 임계 구역 안에서 **막히는 일을 하지 말 것** | `read`·`sleep`·`printf` 등 |
| **모든 경로에서 푼다** | 중간에 `return` 하면 영영 잠긴다 |
| 잠금 순서를 **정해 둔다** | 8강 교착 상태 |

> **`unlock`을 빠뜨리는 것이 가장 흔한 사고입니다.**
> 특히 오류 처리로 일찍 빠져나갈 때 잊기 쉽습니다. 1부 10강 6.3절에서 "실패 경로에서도 자원을 정리하라"고 한 것과 완전히 같은 문제입니다.
> ```c
> pthread_mutex_lock(&lock);
> if (뭔가 잘못) {
>     pthread_mutex_unlock(&lock);   /* 반드시! */
>     return NULL;
> }
> ```
{: .prompt-danger }

### 6.4 초기화 두 가지

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;       /* 정적 */
```

```c
pthread_mutex_t *lock = malloc(sizeof *lock);           /* 동적 */
pthread_mutex_init(lock, NULL);
...
pthread_mutex_destroy(lock);
free(lock);
```

전역 뮤텍스는 앞의 방법으로 충분합니다. **구조체 안에 넣거나 개수가 실행 중에 정해지면** 뒤의 방법을 씁니다.

### 6.5 대가

뮤텍스는 공짜가 아닙니다.

| 비용 | 설명 |
|---|---|
| 잠그고 푸는 시간 | 경합이 없으면 아주 싸다 |
| **기다리는 시간** | 경합이 심하면 병목이 된다 |
| 병렬성을 잃는다 | 임계 구역은 결국 **한 줄로 실행**된다 |

**뮤텍스로 감싼 부분은 더 이상 병렬이 아닙니다.** 스레드를 늘려도 그 구간은 빨라지지 않습니다.

직접 재어 보십시오.

```bash
time ./race 4 2000000 > /dev/null
time ./race 4 2000000 mutex > /dev/null
```

```text

real	0m0.029s
--- 뮤텍스 ---
real	0m0.359s
```

**약 12배 느립니다.** 잠그고 푸는 일이 800만 번 일어났기 때문입니다.

> **그렇다고 뮤텍스를 빼면 안 됩니다.** 빠른 오답보다 느린 정답이 낫습니다. 대신 **잠그는 횟수를 줄이는 것**이 옳은 해법입니다. 실습문제 6에서 800만 번을 4번으로 줄여 봅니다. 이 주제는 8강에서 더 깊이 다룹니다.
{: .prompt-tip }

## 제7절. 조건 변수

### 7.1 "기다렸다가 깨어나기"

뮤텍스는 **"들어가도 되는가"** 를 다루지만, **"조건이 갖춰질 때까지 기다린다"** 는 다른 문제입니다.

저장고가 가득 찼을 때 생산자는 어떻게 해야 할까요?

```c
while (count == CAP)
    ;                       /* 계속 확인 — CPU 를 태운다 */
```

이것을 **바쁜 대기**라 하며, 나쁜 방법입니다. 조건 변수를 쓰면 **자면서** 기다립니다.

```c
pthread_cond_t cv = PTHREAD_COND_INITIALIZER;

int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);      /* 하나 깨우기 */
int pthread_cond_broadcast(pthread_cond_t *cond);   /* 모두 깨우기 */
```

### 7.2 `pthread_cond_wait`이 하는 세 가지

이 함수는 겉보기와 달리 **세 동작을 하나로 묶은 것**입니다.

| 순서 | 하는 일 |
|---|---|
| 1 | **뮤텍스를 푼다** |
| 2 | 잠들어 신호를 기다린다 |
| 3 | 깨어나면 **뮤텍스를 다시 잠근다** |

**뮤텍스를 잠근 채로 불러야 하고, 돌아왔을 때도 잠겨 있습니다.** 이 성질 덕분에 "확인하고 기다린다" 사이에 틈이 생기지 않습니다.

### 7.3 반드시 `while`로 감싸십시오

```c
        while (count == CAP)                    /* if 가 아니라 while */
            pthread_cond_wait(&not_full, &lock);
```

> **`if`가 아니라 `while`입니다.**
>
> | 이유 | 설명 |
> |---|---|
> | **가짜 깨어남**(spurious wakeup) | 신호가 없었는데 깨어날 수 있다 |
> | 먼저 깬 다른 스레드 | 내가 깨어났을 때 조건이 이미 다시 깨졌을 수 있다 |
> | `broadcast` | 여럿이 깨어나도 자리는 하나뿐 |
>
> **깨어난 뒤 조건을 다시 확인**해야 안전합니다.
{: .prompt-danger }

### 7.4 생산자·소비자

```c
static void *producer(void *arg)
{
    ...
        pthread_mutex_lock(&lock);

        while (count == CAP)
            pthread_cond_wait(&not_full, &lock);

        buf[in] = i;
        in = (in + 1) % CAP;
        count++;
        ...
        pthread_cond_signal(&not_empty);        /* 소비자를 깨운다 */
        pthread_mutex_unlock(&lock);
```

```c
static void *consumer(void *arg)
{
    ...
        while (count == 0 && !done)
            pthread_cond_wait(&not_empty, &lock);

        if (count == 0 && done) {               /* 더 올 것이 없다 */
            pthread_mutex_unlock(&lock);
            break;
        }
        ...
        pthread_cond_signal(&not_full);         /* 생산자를 깨운다 */
        pthread_mutex_unlock(&lock);
```

```bash
./prodcons
```

```text
  생산  1 (저장고 1/4)
      소비자0 가  1 를 가져감 (저장고 0/4)
  생산  2 (저장고 1/4)
      소비자1 가  2 를 가져감 (저장고 0/4)
  ...
  생산  9 (저장고 1/4)
  생산 10 (저장고 2/4)
      소비자0 가  9 를 가져감 (저장고 1/4)
  ...
  소비자0 종료 — 6개 처리
  소비자1 종료 — 6개 처리
모두 끝났습니다. 저장고에 남은 개수 = 0
```

**12개를 만들어 6개씩 나누어 처리했고, 저장고가 정확히 비었습니다.**

### 7.5 끝냄을 알리는 방법

```c
    pthread_mutex_lock(&lock);
    done = 1;
    pthread_cond_broadcast(&not_empty);         /* 기다리는 모두를 깨운다 */
    pthread_mutex_unlock(&lock);
```

**`signal`이 아니라 `broadcast`** 입니다. 소비자가 여럿이라 **모두 깨워야** 각자 종료 조건을 확인하고 나갈 수 있습니다. `signal`을 쓰면 하나만 깨어나고 나머지는 영원히 잠듭니다.

| 언제 | 무엇을 |
|---|---|
| 자리 하나가 생겼다 | **`signal`** — 하나만 깨우면 충분 |
| 상태가 근본적으로 바뀌었다(끝남 등) | **`broadcast`** |

### 7.6 이 구조가 서버의 뼈대입니다

생산자·소비자는 **작업 대기열**의 기본 형태입니다.

| 이 예제 | 실제 서버 |
|---|---|
| 생산자 | 접속을 받는 스레드 |
| 저장고 | 처리 대기열 |
| 소비자 | 일꾼 스레드 여러 개 |

10강 다중 접속 서버와 17강 종합 과제에서 다시 만납니다.

## 제8절. `errno`의 정체

**1강 10.6절에서 미뤄 둔 이야기입니다.**

### 8.1 확인해 보기

```c
static void *fail_open(void *arg)
{
    long id = (long) arg;
    const char *path = (id == 0) ? "/없는파일" : "/etc/shadow";

    errno = 0;
    if (open(path, (id == 0) ? O_RDONLY : O_WRONLY) == -1) {
        sleep(1);                   /* 다른 스레드도 실패하도록 시간을 준다 */
        printf("[스레드 %ld] %s -> errno=%d (%s)\n",
               id, path, errno, strerror(errno));
    }
    printf("[스레드 %ld] &errno = %p\n", id, (void *) &errno);
    return NULL;
}
```

```bash
./errno_thread
```

```text
[주 스레드] &errno = 0x7abcb77dc6c8
[스레드 1] /etc/shadow -> errno=13 (Permission denied)
[스레드 1] &errno = 0x7abcb6bfe648
[스레드 0] /없는파일 -> errno=2 (No such file or directory)
[스레드 0] &errno = 0x7abcb73ff648
```

### 8.2 두 가지가 증명됩니다

| 관찰 | 뜻 |
|---|---|
| **`&errno`가 셋 다 다르다** | `errno`는 **스레드마다 따로 존재한다** |
| 1번이 13, 0번이 2를 **각자 유지** | 서로 덮어쓰지 않았다 |

**두 스레드가 1초 동안 함께 실패한 상태로 있었는데도** 각자의 값을 그대로 지켰습니다.

### 8.3 어떻게 그런가

`errno`는 변수가 아니라 **매크로**입니다.

```c
#define errno (*__errno_location())
```

`__errno_location()`은 **지금 스레드의 `errno` 자리**를 돌려주는 함수입니다. 그래서 `&errno`가 스레드마다 다른 값이 나옵니다.

> **만약 `errno`가 진짜 전역 변수였다면**, 스레드 A가 `open`에 실패한 직후 스레드 B가 다른 실패를 하면 **A의 오류 번호가 사라집니다.** 오류 처리가 근본적으로 불가능해집니다.
{: .prompt-info }

### 8.4 그래서 pthread 함수는 다릅니다

2.2절에서 pthread 함수가 `errno` 대신 반환값을 쓴다고 했습니다. 이유가 여기 있습니다. **`errno` 방식은 스레드마다 저장소가 필요한 번거로운 구조**이므로, 나중에 만들어진 pthread API는 처음부터 **반환값으로 알리는 더 단순한 방식**을 골랐습니다.

## 제9절. 스레드와 프로세스, 무엇을 고를까

### 9.1 판단표

| 상황 | 고를 것 | 이유 |

| 자료를 많이 주고받는다 | **스레드** | 공유하므로 복사가 없다 |
| 서로 독립적인 일 | **프로세스** | 하나가 죽어도 안전 |
| 다른 프로그램을 실행 | **프로세스** | `exec`이 필요하다 |
| 안정성이 최우선 | **프로세스** | 격리 |
| 만드는 횟수가 아주 많다 | **스레드** | 비용이 싸다 |
| 신뢰할 수 없는 코드를 돌린다 | **프로세스** | 권한도 낮출 수 있다 |

### 9.2 실제 사례

| 프로그램 | 방식 | 왜 |
|---|---|---|
| Apache(prefork) | 프로세스 | 안정성 — 하나가 죽어도 서비스는 계속 |
| nginx | 프로세스 + 이벤트 | 10강의 방식 |
| Chrome | **탭마다 프로세스** | **보안 격리** |
| 데이터베이스 | 대개 스레드 | 캐시를 공유해야 한다 |

> **"하나가 죽으면 전부 죽는다"** 는 스레드의 성질을 기억하십시오. 스레드 하나에서 `SIGSEGV`가 나면 **프로세스 전체가 끝납니다.** 1부 10강에서 배운 버퍼 오버플로 하나가 서버 전체를 무너뜨릴 수 있다는 뜻입니다.
{: .prompt-warning }

### 9.3 오늘날의 선택

실무에서는 **섞어 씁니다.** 프로세스 몇 개를 띄우고 각 프로세스가 스레드를 여러 개 두는 구조가 흔합니다. 격리와 효율을 함께 얻기 위해서입니다.

### 문제 3. 경쟁 상태 재현

**정답 및 해설**

5.1·5.2절의 코드와 결과가 답입니다.

```text
기대값 400000 | 실제값 341132
기대값 400000 | 실제값 397599
기대값 400000 | 실제값 394382
```

### 문제 6. 병렬 합계

1부터 1000만까지의 합을 여러 스레드로 나누어 구하십시오. **잠그는 횟수를 최소로** 하십시오.

**정답 및 해설**

**각자 지역 변수에 모으고 마지막에 한 번만 합칩니다.**

```c
static void *partial(void *arg)
{
    struct range *r = arg;
    long i, local = 0;              /* 지역 변수 — 잠글 필요가 없다 */

    for (i = r->from; i <= r->to; i++)
        local += i;

    pthread_mutex_lock(&lock);      /* 한 번만 잠근다 */
    total += local;
    pthread_mutex_unlock(&lock);
    return NULL;
}
```

```bash
for t in 1 2 4 8; do ./psum $t 10000000; done
```

```text
스레드  1 | 1~10000000 의 합 = 50000005000000 | 공식값 50000005000000 | 일치
스레드  2 | 1~10000000 의 합 = 50000005000000 | 공식값 50000005000000 | 일치
스레드  4 | 1~10000000 의 합 = 50000005000000 | 공식값 50000005000000 | 일치
스레드  8 | 1~10000000 의 합 = 50000005000000 | 공식값 50000005000000 | 일치
```

- **잠그는 횟수가 1000만 번에서 스레드 수만큼으로 줄어듭니다.** 6.5절에서 잰 12배의 차이가 여기서 사라집니다.
- 지역 변수는 스레드마다 따로이므로(3.2절) **보호할 필요가 없습니다.** 공유하는 것만 지키면 됩니다.
- 검산이 쉽습니다. 1~n의 합은 `n(n+1)/2`이므로 1000만이면 50000005000000입니다. **정답을 아는 문제로 시험하는 것**이 좋은 검증입니다.
- `long`으로 충분한지 확인하십시오. 1부 10강의 정수 넘침이 여기서도 적용됩니다.

### 문제 7. 조건 변수

크기가 정해진 저장고로 생산자·소비자를 구현하십시오.

**정답 및 해설**

7.4절의 코드와 결과가 답입니다.

| 확인 | 기대 |
|---|---|
| 저장고가 `CAP`을 넘지 않는가 | 출력의 `n/4`가 4를 넘지 않음 |
| 모든 항목이 처리되는가 | 소비자들의 합 = `ITEMS` |
| 끝에 남는 것이 없는가 | 마지막 줄이 0 |
| 프로그램이 멈추지 않는가 | 정상 종료 |

- **`while`로 조건을 확인**했는지 확인하십시오(7.3절). `if`로 바꾸면 드물게 깨집니다.
- 끝낼 때 **`broadcast`** 를 썼는지 보십시오. `signal`이면 소비자 하나가 영원히 잠듭니다(7.5절).
- 소비자를 3개, 4개로 늘려도 동작해야 합니다.
- `usleep` 값을 바꾸어 생산이 소비보다 빠르게 하면, 저장고가 가득 차 생산자가 기다리는 모습을 볼 수 있습니다.

### 문제 8. `errno` 확인

두 스레드가 서로 다른 이유로 실패하게 하고, `errno`가 섞이지 않는지 확인하십시오.

**정답 및 해설**

8.1절의 코드와 결과가 답입니다.

```text
[스레드 1] /etc/shadow -> errno=13 (Permission denied)
[스레드 0] /없는파일 -> errno=2 (No such file or directory)
```

- **`&errno`를 출력한 것**이 결정적 증거입니다. 세 값이 모두 다릅니다.
- `sleep(1)`을 넣어 **두 스레드가 동시에 실패 상태에 있도록** 만든 것이 시험 설계의 핵심입니다. 그러지 않으면 순차 실행되어 아무것도 증명하지 못합니다.
- 1강 10.6절에서 "매크로로 구현되어 있다"고만 말한 것을 이제 눈으로 확인했습니다.

### 문제 9. 스레드 안전한 카운터 모듈

증가·감소·읽기를 제공하는 카운터를 **스레드 안전하게** 만들어 헤더와 소스로 분리하십시오.

**정답 및 해설**

```c
/* counter.h */
#ifndef COUNTER_H
#define COUNTER_H

struct counter;                     /* 속을 감춘다 — 1부 11강 6.1절 */

struct counter *counter_new(void);
void            counter_free(struct counter *c);
void            counter_inc(struct counter *c);
long            counter_get(struct counter *c);

#endif
```

```c
/* counter.c */
struct counter {
    long value;
    pthread_mutex_t lock;
};

void counter_inc(struct counter *c)
{
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}

long counter_get(struct counter *c)
{
    long v;

    pthread_mutex_lock(&c->lock);   /* 읽기도 잠가야 한다 */
    v = c->value;
    pthread_mutex_unlock(&c->lock);
    return v;
}
```

```bash
for i in 1 2 3; do ./counter_test; done
```

```text
기대값 400000 | 실제값 400000 | 일치
기대값 400000 | 실제값 400000 | 일치
기대값 400000 | 실제값 400000 | 일치
```

- **구조체 안에 뮤텍스를 함께 넣은 것**이 핵심입니다. 자료와 그것을 지키는 자물쇠는 붙어 있어야 합니다.
- **읽기에도 잠금이 필요합니다.** `long` 읽기가 원자적일 것 같지만 보장되지 않습니다.
- **속을 헤더에 노출하지 않았습니다**(1부 11강 6.1절). 사용자가 `c->value`를 직접 건드리면 보호가 무너집니다. 이런 방식을 불투명 자료형이라 합니다.
- 이 모듈은 **잠금을 안에 숨겼으므로** 쓰는 쪽이 실수할 여지가 없습니다. 좋은 인터페이스 설계입니다.

### 문제 10. `fork`와 스레드 비교

같은 일을 `fork`와 스레드로 각각 구현하고, **전역 변수의 동작**과 **만드는 시간**을 비교하십시오.

**정답 및 해설**

| 항목 | `fork` | 스레드 |
|---|---|---|
| 자식이 전역을 바꾸면 | 부모는 **그대로**(4강 3.2절) | **함께 바뀐다**(3.2절) |
| 만드는 비용 | 페이지 표 복사 등 | **더 싸다** |
| 통신 | 파이프 필요(6강) | 변수로 바로 |

```bash
time ./make_procs 1000 ; time ./make_threads 1000
```

```text
--- fork 1000개 ---
real	0m0.149s
--- 스레드 1000개 ---
real	0m0.053s
```

- **스레드가 약 세 배 빠릅니다.** 다만 `fork`도 쓸 때 복사 덕분에 생각만큼 느리지는 않습니다(4강 3.4절). "프로세스는 무겁다"는 말이 리눅스에서는 생각보다 과장입니다.
- 시간보다 중요한 것은 **격리 여부**입니다. 9.1절의 판단표로 고르십시오.
- 두 프로그램의 전역 변수 동작 차이를 **한 줄로 설명**할 수 있어야 합니다. 이 강의를 이해했는지 가늠하는 기준입니다.

## 정리

| 구분 | 핵심 |
|---|---|
| 스레드 | 같은 주소 공간의 여러 흐름. **스택만 따로** |
| `fork`와 대비 | 전역이 `fork`는 복사, 스레드는 **공유** |
| 오류 알림 | **`errno`가 아니라 반환값**. `strerror(rc)` |
| 컴파일 | **`-pthread`**(glibc 2.34+는 링크만은 되지만 붙일 것) |
| 인자 | **반복문 변수 주소 금지.** 배열 칸이나 값으로 |
| 반환값 | 지역 변수 주소 금지 |
| 거두기 | `pthread_join` 또는 `pthread_detach` |
| **경쟁 상태** | `counter++`는 **세 단계**. 매번 다르고 가끔 맞는다 |
| 뮤텍스 | 임계 구역은 **짧게**, 모든 경로에서 `unlock` |
| 조건 변수 | `wait`은 **풀고-자고-다시 잠근다**. 반드시 **`while`** |
| `signal`/`broadcast` | 자리 하나면 `signal`, 상태 변화면 `broadcast` |
| `errno` | **스레드마다 따로.** `&errno`가 다르다 |
| 고르기 | 자료 공유는 스레드, **격리·안정성은 프로세스** |

## 부록 A. 이번 강의 함수 요약

| 하려는 일 | 함수 |
|---|---|
| 스레드 만들기 | `pthread_create(&th, NULL, fn, arg)` |
| 기다리고 거두기 | `pthread_join(th, &ret)` |
| 거두지 않겠다고 선언 | `pthread_detach(th)` |
| 자기 자신 | `pthread_self()` |
| TID(리눅스) | `syscall(SYS_gettid)` — `_GNU_SOURCE` 필요 |
| 뮤텍스 정적 초기화 | `PTHREAD_MUTEX_INITIALIZER` |
| 뮤텍스 동적 | `pthread_mutex_init` · `pthread_mutex_destroy` |
| 잠그기·풀기 | `pthread_mutex_lock` · `pthread_mutex_unlock` |
| 기다리지 않고 시도 | `pthread_mutex_trylock` (`EBUSY`) |
| 조건 변수 | `pthread_cond_wait` · `pthread_cond_signal` · `pthread_cond_broadcast` |
| 스택 크기 | `pthread_attr_getstacksize` · `pthread_attr_setstacksize` |
| 오류 메시지 | **`strerror(rc)`** — `errno`가 아니다 |
| 컴파일 | `gcc -Wall -Wextra -std=gnu17 -pthread` |

**본문의 주장과 근거**

| 주장 | 근거 |
|---|---|
| PID는 같고 TID만 다르다(2.3절) | `thread1` — PID 432 고정, TID 432·433·434·435 |
| **전역·힙은 공유, 스택은 따로**(3.2절) | `thread_share` — 전역/힙 주소가 모든 스레드에서 동일, 지역은 전부 다름 |
| **스레드 스택 8 MiB**(3.3절) | `pthread_attr_getstacksize` 8388608 = `ulimit -s` 8192 KiB, 두 스택 주소 차 `0x800000` |
| glibc 2.34+는 `-pthread` 없이도 링크(2.4절) | glibc 2.39에서 링크 성공, `ldd` 결과 동일. `-pthread`는 **`_REENTRANT`** 를 추가 |
| **경쟁 상태가 실제로 일어난다**(5.2절) | 4스레드×10만: 341132·397599·394382·383602·359398 — **5회 모두 다르고 모두 부족** |
| 스레드가 많을수록 심하다(5.4절) | 2스레드 334027, 8스레드 230646, 16스레드 305178 |
| **뮤텍스로 정확해진다**(6.2절) | 5회 모두 400000 |
| 인자 실수는 값이 겹친다(4.1절) | `bad`: `1 3 4 1 1` / `3 4 3 3 4`, `good`: `0 3 1 2 4` |
| **`errno`는 스레드마다 따로**(8.1절) | `&errno` 세 값이 모두 다름, 13과 2가 섞이지 않음 |
| 조건 변수가 동작한다(7.4절) | 12개 생산, 소비자 6+6개 처리, 저장고 0 |
| **뮤텍스는 약 12배 느리다**(6.5절) | 4스레드×200만: 0.029초 vs **0.359초** |
| 잠금을 줄이면 비용이 사라진다(문제 6) | `psum` 1·2·4·8스레드 모두 50000005000000 = `n(n+1)/2` |
| 스레드 안전 모듈이 정확하다(문제 9) | `counter_test` 3회 모두 400000 |
| **스레드 생성이 `fork`보다 약 3배 싸다**(문제 10) | 1000개 생성·회수: `fork` 0.149초 vs 스레드 **0.053초** |
