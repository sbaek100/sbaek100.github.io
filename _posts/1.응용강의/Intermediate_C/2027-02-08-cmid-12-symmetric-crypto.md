## 제1절. 대칭키 암호란

### 1.1 하나의 열쇠

> **대칭키 암호**: 잠그는 열쇠와 여는 열쇠가 **같은** 방식.

```text
   평문 ──[암호화: 키 K]──▶ 암호문 ──[복호화: 키 K]──▶ 평문
```

| 성질 | |
|---|---|
| 빠르다 | 공개키보다 **수백~수천 배** |
| 키가 하나 | 양쪽이 **같은 키**를 알아야 한다 |
| **문제** | **그 키를 어떻게 전달하는가**(13강) |

### 1.2 무엇을 지켜 주는가

암호화만으로는 **비밀성**만 얻습니다. **무결성**은 따로 챙겨야 합니다.

| 공격 | 비밀성만으로 |
|---|---|
| 읽기 | 막힌다 |
| **바꿔치기** | **막히지 않는다** |
| 다시 보내기 | 막히지 않는다 |
| 순서 바꾸기 | 막히지 않는다 |

**오늘 쓸 GCM은 둘을 한꺼번에 해 줍니다.** 이런 방식을 **인증 암호**(AEAD, Authenticated Encryption with Associated Data)라 합니다.

### 1.3 직접 만들지 마십시오

> **암호 알고리즘을 직접 구현하지 마십시오.**

| 이유 | |
|---|---|
| 미묘한 실수가 **전부를 무너뜨린다** | IV 하나, 비교 한 줄 |
| **시간 차 공격** | 비교하는 시간만으로 키가 새어 나간다 |
| 검증에 수년이 걸린다 | 수많은 전문가의 공격을 견뎌야 한다 |

**검증된 라이브러리를 바르게 쓰는 것**이 우리가 할 일입니다. 이번 강의에서 배우는 것은 알고리즘이 아니라 **바르게 쓰는 법**입니다.

## 제2절. 블록 암호와 운영 모드

### 2.1 AES는 16바이트만 다룹니다

**AES**(Advanced Encryption Standard)는 **블록 암호**입니다. 한 번에 **정확히 16바이트**를 다룹니다.

| 이름 | 키 길이 | 블록 |
|---|---|---|
| AES-128 | 16바이트 | 16바이트 |
| **AES-256** | **32바이트** | 16바이트 |

**그러면 100바이트는 어떻게 암호화합니까?** 그것을 정하는 것이 **운영 모드**입니다.

### 2.2 운영 모드

| 모드 | 성질 | 쓸 만한가 |
|---|---|---|
| **ECB** | 블록마다 따로 암호화 | **절대 금지** |
| CBC | 앞 블록과 엮는다 | 무결성 없음 |
| CTR | 흐름 암호처럼 | 무결성 없음 |
| **GCM** | **CTR + 인증 태그** | **권장** |
| ChaCha20-Poly1305 | AES가 느린 기기에서 | 권장 |

### 2.3 ECB가 왜 금지인가

같은 평문 블록은 **언제나 같은 암호문 블록**이 됩니다. 그림을 암호화하면 **윤곽이 그대로 보입니다.**

| 모드 | 같은 평문 두 번 |
|---|---|
| **ECB** | **같은 암호문** — 무늬가 드러난다 |
| CBC·CTR·GCM | 다른 암호문 — IV가 다르므로 |

**"같은 입력에 같은 출력"** 이 암호에서는 치명적입니다.

### 2.4 왜 GCM인가

| GCM이 주는 것 | |
|---|---|
| **비밀성** | CTR 방식의 암호화 |
| **무결성** | 인증 태그 |
| **덧붙인 자료 보호**(AAD) | 암호화하지 않지만 변조는 잡는다 |
| 빠르다 | 하드웨어 가속 |

**TLS 1.3이 쓰는 방식**이기도 합니다(14강).

## 제3절. AES-256-GCM 쓰기

### 3.1 OpenSSL의 EVP 인터페이스

OpenSSL은 알고리즘마다 다른 함수를 쓰지 않고 **EVP**라는 공통 인터페이스를 제공합니다.

| 순서 | 함수 |
|---|---|
| 1 | `EVP_CIPHER_CTX_new` — 작업 상자를 만든다 |
| 2 | `EVP_EncryptInit_ex` — 알고리즘·키·IV 설정 |
| 3 | `EVP_EncryptUpdate` — 자료를 넣는다(여러 번 가능) |
| 4 | `EVP_EncryptFinal_ex` — 마무리 |
| 5 | `EVP_CIPHER_CTX_ctrl(..., GET_TAG, ...)` — **태그를 꺼낸다** |
| 6 | `EVP_CIPHER_CTX_free` — 반납 |

**1부에서 배운 자원 관리 원칙 그대로**입니다. `new`가 있으면 `free`가 있어야 합니다.

### 3.2 암호화

```c
    if (EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, NULL, NULL) != 1)
        goto fail;
    if (EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, IVLEN, NULL) != 1)
        goto fail;
    if (EVP_EncryptInit_ex(ctx, NULL, NULL, key, iv) != 1)
        goto fail;

    /* 덧붙인 자료(AAD): 암호화하지는 않지만 무결성은 지킨다 */
    if (aad != NULL && aadlen > 0)
        if (EVP_EncryptUpdate(ctx, NULL, &len, aad, aadlen) != 1)
            goto fail;

    if (EVP_EncryptUpdate(ctx, ct, &len, pt, ptlen) != 1)
        goto fail;
    total = len;

    if (EVP_EncryptFinal_ex(ctx, ct + len, &len) != 1)
        goto fail;
    total += len;

    if (EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, TAGLEN, tag) != 1)
        goto fail;
```

**`EncryptInit_ex`를 두 번 부르는 것**에 주목하십시오. 알고리즘을 먼저 정하고, IV 길이를 설정한 뒤, 키와 IV를 넣습니다. 순서가 정해져 있습니다.

**AAD는 `out`을 `NULL`로 주고 넣습니다.** 암호화하지 않기 때문입니다.

### 3.3 복호화

```c
    /* 검사할 태그를 알려 준다 */
    if (EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_TAG, TAGLEN,
                            (void *) tag) != 1)
        goto fail;

    /* 여기서 태그를 검사한다. 맞지 않으면 1 이 아닌 값이 온다 */
    rc = EVP_DecryptFinal_ex(ctx, pt + len, &len);
    EVP_CIPHER_CTX_free(ctx);

    if (rc != 1)
        return -1;                  /* 위조되었다 */
```

> **`EVP_DecryptFinal_ex`의 반환값을 반드시 검사하십시오.**
> 이 한 줄이 **무결성 검사의 전부**입니다. 검사하지 않으면 위조된 자료를 그대로 쓰게 됩니다. 앞의 `DecryptUpdate`는 태그를 보지 않으므로, **평문은 이미 나와 있지만 믿을 수 없는 상태**입니다.
{: .prompt-danger }

## 제4절. 인증 태그가 지키는 것

### 4.1 실험

`tamper.c`는 **네 가지 변조**를 시도합니다.

```c
    /* ① 암호문 한 비트를 뒤집는다 */
    memcpy(bad_ct, ct, (size_t) ctlen);
    bad_ct[0] ^= 0x01;
```

```bash
./tamper
```

```text
원문: 송금액은 1000원입니다 (29바이트)

⓪ 손대지 않음        : 통과 "송금액은 1000원입니다"
① 암호문 1비트 변조  : 거절 — 태그 불일치
② 태그 1비트 변조    : 거절 — 태그 불일치
③ AAD 변조           : 거절 — 태그 불일치
④ 다른 키           : 거절

인증 태그가 없었다면 ①③ 은 조용히 통과했을 것입니다.
```

### 4.2 무엇이 중요한가

| 변조 | 태그가 없었다면 |
|---|---|
| **암호문 1비트** | **평문의 그 자리 1비트가 바뀐 채 통과** |
| AAD | **바뀐 채로 통과** |

**CTR 방식에서는 암호문의 한 비트를 뒤집으면 평문의 같은 자리 비트가 뒤집힙니다.** 공격자가 내용을 몰라도 **특정 자리를 조작**할 수 있습니다.

> **예를 들어 `"송금액은 1000원"` 이 어디쯤 있는지 짐작하면**, 숫자 부분의 비트를 뒤집어 금액을 바꿀 수 있습니다. **키를 몰라도 됩니다.** 이것이 무결성이 필요한 이유입니다.
{: .prompt-danger }

### 4.3 AAD의 쓸모

**암호화하고 싶지 않지만 변조는 막고 싶은 것**에 씁니다.

| 예 | 왜 암호화하지 않나 |
|---|---|
| 메시지 순번 | 중간 장비가 봐야 할 수도 |
| 수신자 주소 | 배달에 필요하다 |
| 프로토콜 판 번호 | 복호화 전에 알아야 한다 |

**③에서 AAD만 바꿨는데도 거절되었습니다.** 암호문은 손대지 않았는데 태그가 맞지 않습니다.

### 4.4 태그를 비교할 때

우리는 OpenSSL에 맡겼지만, 직접 비교해야 할 때가 있습니다.

```c
if (memcmp(tag1, tag2, 16) == 0)    /* 위험 */
```

**`memcmp`는 다른 바이트를 만나는 즉시 돌아옵니다.** 걸리는 시간이 **앞에서 몇 바이트가 맞았는지**를 알려 줍니다. 이것으로 태그를 한 바이트씩 알아내는 공격이 가능합니다.

```c
if (CRYPTO_memcmp(tag1, tag2, 16) == 0)     /* 안전 — 시간이 일정하다 */
```

**비밀값 비교에는 언제나 시간이 일정한 함수**를 쓰십시오.

## 제5절. 세 가지 재료 — 키·IV·태그

| 재료 | 크기(AES-256-GCM) | 비밀인가 | 재사용 가능한가 |
|---|---|---|---|
| **키** | 32바이트 | **그렇다** | 그렇다(한동안) |
| **IV** | 12바이트 | 아니다 | **절대 안 된다** |
| **태그** | 16바이트 | 아니다 | (결과값) |

| 오해 | 사실 |
|---|---|
| IV는 비밀이어야 한다 | **아니다.** 그대로 보내도 된다 |
| IV는 무작위여야 한다 | 겹치지만 않으면 된다. **계수기도 좋다** |
| 태그는 숨겨야 한다 | 아니다 |
| 키는 자주 바꿔야 한다 | 한 키로 아주 많은 메시지를 처리할 수 있다 |

**IV의 유일한 규칙은 "같은 키로 절대 두 번 쓰지 않는다"** 입니다. 다음 절에서 어기면 어떻게 되는지 봅니다.

## 제6절. IV를 재사용하면

**이 절이 이번 강의에서 가장 중요합니다.**

### 6.1 실험

`iv_reuse.c`는 **같은 키와 같은 IV로 두 메시지**를 암호화합니다.

```c
    n1 = gcm_encrypt(key, iv, (const unsigned char *) m1, (int) strlen(m1),
                     ct1, tag1);
    n2 = gcm_encrypt(key, iv, (const unsigned char *) m2, (int) strlen(m2),
                     ct2, tag2);   /* 같은 iv — 절대 하면 안 되는 일 */
```

그리고 **공격자 입장에서 두 암호문을 XOR** 합니다.

```c
    /* 공격자는 키를 모른다. 두 암호문만 가지고 XOR 한다 */
    for (i = 0; i < minlen; i++)
        x[i] = ct1[i] ^ ct2[i];
```

### 6.2 결과

```bash
./iv_reuse
```

```text
=== 같은 키, 같은 IV 로 두 메시지를 암호화합니다 ===
메시지 1: "ATTACK AT DAWN!!"
메시지 2: "송금액은 1000원"

암호문 1:          89a2095de6ae7b8b59b277bdf9b09e84
암호문 2:          2470fcf61d6db75fac7eae7c8ecf8f95fae2532b

암호문1 XOR 암호문2:add2f5abfbc3ccd4f5ccd9c1777f1111
평문1  XOR 평문2 :add2f5abfbc3ccd4f5ccd9c1777f1111

두 줄이 같습니까? 예 — 완전히 같습니다

=== 공격자가 메시지 1 을 알고 있다고 가정하면 ===
복구한 메시지 2: "송금액은 100"
키는 한 번도 쓰지 않았습니다.
```

### 6.3 무슨 일이 일어난 것인가

CTR 계열의 암호화는 이렇습니다.

```text
   암호문 = 평문 XOR 흐름(키, IV)
```

키와 IV가 같으면 **흐름도 같습니다.** 그래서

```text
   암호문1 XOR 암호문2
 = (평문1 XOR 흐름) XOR (평문2 XOR 흐름)
 = 평문1 XOR 평문2          ← 흐름이 지워진다
```

**키가 완전히 사라집니다.** 공격자는 두 평문의 XOR을 손에 넣고, **한쪽을 알면 다른 쪽을 그대로 얻습니다.**

> **위 실행에서 메시지 2가 그대로 복구되었습니다.** 키를 한 번도 쓰지 않았습니다. **IV 하나를 재사용한 것만으로** 암호화가 통째로 무너졌습니다.
{: .prompt-danger }

### 6.4 GCM에서는 더 나쁩니다

비밀성만 무너지는 것이 아닙니다. **인증 키가 노출되어 위조까지 가능해집니다.** GCM에서 IV 재사용은 **가장 치명적인 실수**로 꼽힙니다.

### 6.5 겹치지 않게 하는 두 방법

| 방법 | 설명 | 주의 |
|---|---|---|
| **계수기** | 0, 1, 2, … 순서대로 | **재시작할 때 이어져야 한다** |
| 무작위 | `RAND_bytes` | 12바이트면 충분히 안전하다 |

**계수기 방식이 확실합니다.** 다만 프로그램이 다시 시작될 때 **0부터 다시 세면 안 됩니다.**

### 6.6 방향도 나누어야 합니다

양쪽이 같은 키를 쓰면서 각자 계수기를 0부터 세면 **곧바로 겹칩니다.**

```c
/* make_iv: 방향과 순번으로 IV 를 만든다 — 절대 겹치지 않는다 */
static void make_iv(unsigned char *iv, int is_client, uint64_t seq)
{
    memset(iv, 0, SC_IVLEN);
    iv[0] = (unsigned char) (is_client ? 0x01 : 0x02);  /* 방향 구분 */
    iv[4]  = (unsigned char) (seq >> 56);
    ...
}
```

**첫 바이트로 방향을 나눈 것**이 핵심입니다. 클라이언트의 0번과 서버의 0번이 서로 다른 IV가 됩니다.

## 제7절. 암호 문구에서 키 만들기

### 7.1 문구를 그대로 쓰면 안 됩니다

```c
memcpy(key, "우리끼리만 아는 문구", 32);      /* 위험 */
```

| 문제 | |
|---|---|
| 길이가 안 맞는다 | 32바이트가 아니다 |
| **추측하기 쉽다** | 사람이 만든 문구는 무작위가 아니다 |
| 사전 공격 | 흔한 문구 목록으로 시도 |

### 7.2 키 유도 함수

> **일부러 느리게** 만들어 대량 시도를 어렵게 하는 함수를 씁니다.

```c
    /* 암호 문구를 그대로 키로 쓰면 안 된다 — 느린 유도 함수를 거친다 */
    if (PKCS5_PBKDF2_HMAC(passphrase, (int) strlen(passphrase),
                          salt, (int) saltlen,
                          200000,               /* 반복 횟수 */
                          EVP_sha256(),
                          SC_KEYLEN, sc->key) != 1)
        return -1;
```

| 인자 | 하는 일 |
|---|---|
| **소금(salt)** | 같은 문구라도 **다른 키**가 되게 한다 |
| **반복 횟수** | 클수록 느리다 — **공격자도 느려진다** |
| 해시 | SHA-256 |

**소금은 비밀이 아닙니다.** 함께 저장하거나 보내도 됩니다. 목적은 **미리 계산해 둔 표를 무용지물로 만드는 것**입니다.

### 7.3 오늘날의 권장

| 함수 | 평가 |
|---|---|
| PBKDF2 | 널리 쓰인다. 반복 횟수를 충분히(수십만) |
| **scrypt** | 메모리도 많이 쓰게 한다 — 더 낫다 |
| **Argon2** | 오늘날 가장 권장 |

OpenSSL 3.0에는 `EVP_KDF` 인터페이스로 셋 다 있습니다. 이번 강의는 배우기 쉬운 PBKDF2를 씁니다.

### 7.4 그런데 이것도 근본 해결이 아닙니다

**문구 자체를 양쪽이 어떻게 나누어 가졌습니까?**

| 방법 | 문제 |
|---|---|
| 미리 만나서 | 상대가 백만 명이면? |
| 전화로 | 도청될 수 있다 |
| 메일로 | 그 메일은 안전한가 |

**이것이 대칭키의 근본 한계**이며, 13강의 주제입니다.

## 제8절. 암호 채널 만들기

### 8.1 어디에 얹는가

11강에서 만든 프레이밍 **위에** 암호를 얹습니다.

```text
   응용 프로그램
        │  sc_send / sc_recv        ← 오늘 만드는 것
   ┌────▼─────────────────┐
   │  AES-256-GCM         │
   └────┬─────────────────┘
        │  msg_send / msg_recv      ← 11강
   ┌────▼─────────────────┐
   │  길이 앞머리 프레이밍   │
   └────┬─────────────────┘
        │  write / read             ← 2·9강
   [        소켓          ]
```

**층이 쌓이는 것**을 보십시오. 각 층은 아래층만 알면 됩니다. 1부 정리편에서 말한 "계층을 만들어라"가 여기서 완성됩니다.

### 8.2 한 메시지의 형식

```text
     +--------+------------------+
     | 태그 16 | 암호문 (길이 가변) |
     +--------+------------------+
   IV 는 보내지 않는다 — 양쪽이 계수기로 똑같이 만든다
```

**IV를 보내지 않아도 됩니다.** 양쪽이 같은 규칙(6.6절)으로 만들기 때문입니다. 12바이트를 아낄 수 있고, **순서가 어긋나면 복호화가 실패**하므로 재전송 공격도 막힙니다.

### 8.3 채널 구조체

```c
struct schan {
    int      fd;
    unsigned char key[SC_KEYLEN];
    uint64_t send_seq;              /* 내가 보낸 메시지 수 */
    uint64_t recv_seq;              /* 내가 받은 메시지 수 */
    int      is_client;             /* 방향마다 IV 공간을 나눈다 */
};
```

**7강 문제 9에서 만든 카운터 모듈처럼**, 자료와 그것을 다루는 함수를 한 묶음으로 두었습니다.

### 8.4 보내기와 받기

```c
    make_iv(iv, sc->is_client, sc->send_seq);
    ...
    EVP_CIPHER_CTX_free(ctx);
    sc->send_seq++;

    return msg_send(sc->fd, out, (size_t) ctlen + SC_TAGLEN);
```

```c
    make_iv(iv, !sc->is_client, sc->recv_seq);   /* 상대 방향의 IV */
    ...
    if (rc != 1) {                      /* 위조되었거나 순서가 틀렸다 */
        errno = EBADMSG;
        return -1;
    }
    sc->recv_seq++;
```

**받을 때는 `!sc->is_client`** 입니다. 상대가 만든 IV를 그대로 재현해야 하기 때문입니다.

### 8.5 동작 확인

```bash
./secserv 5200 &
./seccli c-srv 5200
```

```text
c-srv:5200 에 연결했습니다
비밀번호는 admin1234 입니다
echo: 비밀번호는 admin1234 입니다
계좌번호 110-123-456789
echo: 계좌번호 110-123-456789
quit
```

서버 쪽입니다.

```text
암호화 서버가 포트 5200 에서 기다립니다
접속: 127.0.0.1:42714
  복호화한 내용: 비밀번호는 admin1234 입니다
  복호화한 내용: 계좌번호 110-123-456789
  복호화한 내용: quit
연결 종료
```

**9강의 서버와 겉보기가 똑같습니다.** 달라진 것은 **선 위를 흐르는 것**뿐입니다.

### 8.6 문구가 다르면

```bash
./seccli c-srv 5202 wrong
```

```text
c-srv:5202 에 연결했습니다 (틀린 문구로!)
서버가 연결을 닫았습니다
```

```text
접속: 127.0.0.1:50962
  sc_recv 실패: 위조되었거나 키가 다릅니다
연결 종료
```

**첫 메시지부터 거절되었습니다.** 태그가 맞지 않기 때문입니다.

> **이것이 "인증"이라고 착각하기 쉽습니다.**
> 키를 아는 상대만 통과하니 인증처럼 보입니다. 그러나 **키를 아는 사람이면 누구든** 통과합니다. 키가 새어 나가면 끝이고, **상대가 진짜 그 서버인지**는 여전히 알 수 없습니다. 13·14강에서 이 문제를 다룹니다.
{: .prompt-warning }

| 증상 | 원인 | 해결 |
|---|---|---|
| **암호화가 통째로 무너짐** | **IV 재사용** | 계수기 + 방향 구분(6.6절) |

| 무늬가 드러남 | ECB 모드 | **GCM** |

| 메모리가 샘 | `CTX_free` 누락 | 모든 경로에서 |

| 키가 소스에 박혀 있음 | 하드코딩 | 설정·환경 변수·키 저장소 |

| 순서가 바뀐 메시지가 통과 | 순번 미사용 | 계수기 IV가 자동으로 막는다 |

### 문제 1·2. 암호화 왕복과 변조 탐지

AES-256-GCM으로 암호화·복호화하고, **네 가지 변조**가 모두 거절되는지 확인하십시오.

**정답 및 해설**

3.2·3.3절의 코드와 4.1절의 결과가 답입니다.

```text
⓪ 손대지 않음        : 통과
① 암호문 1비트 변조  : 거절 — 태그 불일치
② 태그 1비트 변조    : 거절 — 태그 불일치
③ AAD 변조           : 거절 — 태그 불일치
④ 다른 키           : 거절
```

- **`EVP_DecryptFinal_ex`의 반환값을 검사하지 않으면** ①③이 통과합니다. 일부러 검사를 빼고 실행해 보십시오. **평문이 한 비트 바뀐 채로 나옵니다.**
- 암호문 길이가 평문과 같은지 확인하십시오. GCM에는 패딩이 없습니다.
- `goto fail`로 정리 경로를 하나로 모은 것은 1부 10강 6.3절의 원칙입니다.

### 문제 3. AAD 활용

메시지 순번을 AAD로 넣어, **순서를 바꾸면 거절**되게 하십시오.

**정답 및 해설**

```c
char aad[32];
int len = snprintf(aad, sizeof aad, "seq:%llu", (unsigned long long) seq);

gcm_encrypt(key, iv, (unsigned char *) aad, len, pt, ptlen, ct, tag);
```

- **AAD는 암호화되지 않지만 태그에 반영됩니다.** 받는 쪽이 다른 순번으로 검사하면 실패합니다.
- 순번을 암호문 안에 넣어도 되지만, **복호화 전에 알아야 하는 값**은 AAD가 알맞습니다.
- 우리 `securechan.c`는 AAD 대신 **IV에 순번을 넣어** 같은 효과를 얻었습니다(8.2절). 두 방법의 차이를 설명할 수 있어야 합니다.

### 문제 4. IV 재사용 재현

같은 IV로 두 메시지를 암호화하고, **키 없이 평문을 복구**하십시오.

**정답 및 해설**

6.1·6.2절의 코드와 결과가 답입니다.

```text
암호문1 XOR 암호문2:add2f5abfbc3ccd4f5ccd9c1777f1111
평문1  XOR 평문2 :add2f5abfbc3ccd4f5ccd9c1777f1111
두 줄이 같습니까? 예 — 완전히 같습니다

복구한 메시지 2: "송금액은 100"
```

- **두 줄이 완전히 같다는 것**이 증명입니다. 흐름이 지워졌기 때문입니다(6.3절).
- 복구한 메시지가 짧은 이유는 두 평문의 길이가 달라 **짧은 쪽까지만** XOR 했기 때문입니다.
- **이것을 직접 해 보는 것이 중요합니다.** "IV를 재사용하지 마세요"라는 말보다 이 화면 하나가 훨씬 오래 기억에 남습니다.
- 서로 다른 IV로 바꾸면 두 줄이 전혀 달라집니다. 확인해 보십시오.

### 문제 5. 키 유도

같은 문구라도 **소금이 다르면 다른 키**가 나오는 것을 보이십시오.

**정답 및 해설**

```c
    PKCS5_PBKDF2_HMAC(phrase, len, salt1, s1len, 200000, EVP_sha256(), 32, k1);
    PKCS5_PBKDF2_HMAC(phrase, len, salt2, s2len, 200000, EVP_sha256(), 32, k2);
    printf("두 키가 같은가: %s\n", memcmp(k1, k2, 32) == 0 ? "예" : "아니오");
```

- **소금이 다르면 완전히 다른 키**가 나옵니다. 이것이 미리 계산한 표를 무력화합니다.
- 반복 횟수를 1000과 200000으로 바꾸어 **시간을 재어 보십시오.** 사람에게는 0.2초, 공격자에게는 200배의 벽입니다.
- 소금은 **매번 새로** 만들어 자료와 함께 저장합니다. 비밀이 아닙니다.

| | 9강 | 12강 |
|---|---|---|
| 엿들은 내용 | `"비밀번호는 admin1234 입니다\n"` | `"\x00\x00\x004 ..."` |

### 문제 8. 파일 암호화 도구

파일을 통째로 암호화·복호화하는 명령을 만드십시오.

**정답 및 해설**

**형식을 먼저 정해야 합니다.**

```text
   +---------+--------+--------+--------------+
   | 소금 16  | IV 12  | 태그 16 | 암호문        |
   +---------+--------+--------+--------------+
```

```c
    RAND_bytes(salt, 16);
    RAND_bytes(iv, 12);
    PKCS5_PBKDF2_HMAC(pass, plen, salt, 16, 200000, EVP_sha256(), 32, key);
    /* ... 암호화 ... */
    write_full(fd, salt, 16);
    write_full(fd, iv, 12);
    write_full(fd, tag, 16);
    write_full(fd, ct, ctlen);
```

- **소금과 IV를 파일에 함께 저장**합니다. 비밀이 아니므로 문제없습니다(5절 표).
- 큰 파일은 조각으로 나누어 `EVP_EncryptUpdate`를 여러 번 부릅니다. **조각마다 다른 IV가 필요하지는 않습니다** — 하나의 암호화 작업이기 때문입니다.
- 복호화할 때 **태그 검사가 실패하면 결과를 쓰지 마십시오.** 이미 쓴 뒤에 실패를 알면 늦습니다.
- 다 쓴 키는 지우십시오.

```c
OPENSSL_cleanse(key, sizeof key);
```

### 문제 9. 시간이 일정한 비교

`memcmp`와 `CRYPTO_memcmp`의 차이를 설명하고, 왜 후자를 써야 하는지 쓰십시오.

**정답 및 해설**

| | `memcmp` | `CRYPTO_memcmp` |
|---|---|---|
| 다른 바이트를 만나면 | **즉시 돌아온다** | 끝까지 본다 |
| 걸리는 시간 | **맞은 바이트 수에 따라 다르다** | 일정하다 |
| 비밀값 비교에 | **부적합** | 적합 |

- 공격자가 태그를 바꿔 가며 **응답 시간을 재면**, 앞에서 몇 바이트가 맞았는지 알 수 있습니다. 한 바이트씩 맞춰 나가면 16바이트를 알아낼 수 있습니다.
- **비밀번호 비교에도 같은 원칙**이 적용됩니다.
- 이것을 **부채널 공격**이라 합니다. 알고리즘이 아니라 **구현의 부산물**에서 정보가 새는 것입니다. 1.3절에서 "직접 만들지 말라"고 한 이유가 이것입니다.

### 문제 10. `openssl` 명령과 맞춰 보기

우리 프로그램이 만든 암호문을 **`openssl` 명령으로 복호화**해 보십시오.

**정답 및 해설**

```bash
openssl enc -aes-256-cbc -pbkdf2 -in plain.txt -out enc.bin -k "문구"
```

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -in enc.bin -out out.txt -k "문구"
```

- **`openssl enc`는 GCM을 지원하지 않습니다.** CBC로만 시험할 수 있습니다. 무결성이 없는 모드이므로 실무에는 쓰지 마십시오.
- 대신 **`openssl` 명령으로 무작위 키를 만들어** 우리 프로그램에 넘길 수 있습니다.

```bash
openssl rand -hex 32
```

- **정답이 있는 것과 맞춰 보는 검증**은 1부 12강부터 계속 써 온 방식입니다. 암호에서는 **시험 벡터**(test vector)라 하며, [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)에 GCM의 공식 시험 벡터가 실려 있습니다. 그것으로 맞춰 보는 것이 가장 확실합니다.

## 정리

| 구분 | 핵심 |
|---|---|
| 대칭키 | 잠그는 열쇠와 여는 열쇠가 같다. **빠르다** |
| 직접 구현 | **하지 말 것.** 검증된 라이브러리를 바르게 쓴다 |
| 블록 암호 | AES는 16바이트씩. **운영 모드**가 나머지를 정한다 |
| ECB | **절대 금지** — 무늬가 드러난다 |
| **GCM** | 비밀성 + **무결성** + AAD. TLS 1.3이 쓴다 |
| 태그 검사 | **`EVP_DecryptFinal_ex`의 반환값**이 전부다 |
| 세 재료 | 키(비밀) · IV(공개, **재사용 금지**) · 태그(결과) |
| **IV 재사용** | **암호화가 통째로 무너진다.** 키 없이 평문 복구 |
| IV 만들기 | 계수기 + **방향 구분** |
| 키 유도 | 문구를 그대로 쓰지 말 것. **PBKDF2 + 소금 + 많은 반복** |
| 층 구조 | 응용 → **암호** → 프레이밍 → 소켓 |
| **성과** | 9강의 엿듣기가 **무력해졌다** |
| 남은 것 | 메타데이터는 여전히 보인다. **키를 어떻게 나누는가** |
