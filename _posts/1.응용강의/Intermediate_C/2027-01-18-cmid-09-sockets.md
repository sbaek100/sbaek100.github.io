## 제1절. 소켓이란

### 1.1 소켓도 파일 서술자입니다

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);
```

**돌려주는 것은 그냥 `int`입니다.** 2강에서 `open`이 돌려준 것과 같은 종류이며, 같은 서술자 표에 들어갑니다(2강 9.1절).

| 소켓에 쓸 수 있는 것 | 3강에서 배운 것 |
|---|---|
| `read`·`write` | 그대로 |
| `close` | 그대로 |
| `poll`·`select` | 10강 |
| **`lseek`** | **불가**(2강 6.4절) — `ESPIPE` |

**`ls -l /proc/self/fd`로 보면 `socket:[12345]` 형태**로 나타납니다. 3강 3.1절의 `S_ISSOCK`이 이것입니다.

### 1.2 파일과 다른 점

| | 파일 | 소켓 |
|---|---|---|
| 대상 | 디스크의 자료 | **다른 컴퓨터의 프로그램** |
| 되감기 | 가능 | **불가** |
| 크기 | 정해져 있다 | **끝이 언제인지 모른다** |
| 실패 | 드물다 | **일상** — 끊김·지연·거부 |
| 상대 | 없다 | **상대가 있다** — 언제든 사라질 수 있다 |

**마지막 줄이 네트워크 프로그래밍의 본질**입니다. 파일은 사라지지 않지만 **상대는 언제든 사라집니다.**

### 1.3 세 가지 인자

```c
int socket(int domain, int type, int protocol);
```

| 인자 | 값 | 뜻 |
|---|---|---|
| `domain` | `AF_INET` | IPv4 |
| | `AF_INET6` | IPv6 |
| | `AF_UNIX` | **같은 컴퓨터 안**(6강 `socketpair`) |
| `type` | **`SOCK_STREAM`** | **TCP** — 순서 보장, 빠짐없이 |
| | `SOCK_DGRAM` | UDP — 11강 |
| `protocol` | 0 | 알아서 고른다 |

이번 강의는 **`AF_INET` + `SOCK_STREAM`**, 곧 TCP만 다룹니다.

### 1.4 TCP가 해 주는 것

| TCP가 보장하는 것 | 보장하지 않는 것 |
|---|---|
| 보낸 순서대로 도착한다 | **메시지 경계** |
| 빠뜨리지 않는다 | 언제 도착하는지 |
| 깨진 것은 다시 보낸다 | **상대가 살아 있는지** |

> **"메시지 경계가 없다"** 는 것이 6강 1.2절의 파이프와 똑같습니다. `write`를 세 번 나누어 해도 상대는 한 번에 받을 수 있고, 그 반대도 마찬가지입니다. **제6절에서 이것을 눈으로 확인합니다.**
{: .prompt-warning }

## 제2절. 서버의 네 단계

### 2.1 순서

| 단계 | 함수 | 하는 일 |
|---|---|---|
| 1 | `socket` | 소켓을 만든다 |
| 2 | **`bind`** | **주소와 포트를 붙인다** |
| 3 | **`listen`** | 받을 준비를 한다 |
| 4 | **`accept`** | 손님을 받는다 — **새 서술자가 생긴다** |

```text
   listen_fd (듣기 전용, 계속 산다)
       │
       │ accept
       ▼
   conn_fd (손님 하나와의 연결, 끝나면 닫는다)
```

**서술자가 둘이라는 점**이 처음 배울 때 가장 헷갈립니다. `listen_fd`로는 자료를 주고받지 않습니다.

### 2.2 코드

```c
    /* ① 소켓을 만든다 */
    listen_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (listen_fd == -1)
        die("socket");

    /* 끝낸 직후 다시 띄울 수 있게 한다 */
    if (setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on) == -1)
        die("setsockopt");

    /* ② 주소를 붙인다 */
    memset(&addr, 0, sizeof addr);
    addr.sin_family      = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);   /* 모든 주소에서 받는다 */
    addr.sin_port        = htons(port);         /* 바이트 순서 변환 */

    if (bind(listen_fd, (struct sockaddr *) &addr, sizeof addr) == -1)
        die("bind(포트 %u)", port);

    /* ③ 듣기 시작 */
    if (listen(listen_fd, BACKLOG) == -1)
        die("listen");
```

```c
        /* ④ 손님을 받는다 — 새 서술자가 생긴다 */
        peerlen = sizeof peer;
        conn_fd = accept(listen_fd, (struct sockaddr *) &peer, &peerlen);
        if (conn_fd == -1) {
            if (errno == EINTR)
                continue;
            die("accept");
        }

        inet_ntop(AF_INET, &peer.sin_addr, ipstr, sizeof ipstr);
        printf("접속: %s:%u\n", ipstr, ntohs(peer.sin_port));
```

### 2.3 `SO_REUSEADDR`를 반드시 넣으십시오

**이것을 빠뜨리면** 서버를 껐다 곧바로 켤 때 이렇게 됩니다.

```text
bind(포트 5000): Address already in use
```

아무도 그 포트를 쓰고 있지 않은데도 그렇습니다. **방금 닫은 연결이 `TIME_WAIT` 상태로 몇십 초 남아 있기** 때문입니다. `SO_REUSEADDR`는 그 상태의 주소를 다시 쓸 수 있게 해 줍니다.

> 개발 중에 서버를 자주 껐다 켜므로, **이 한 줄이 없으면 실습이 대단히 답답해집니다.**
{: .prompt-tip }

### 2.4 `listen`의 두 번째 인자

```c
listen(listen_fd, 16);
```

**아직 `accept` 하지 못한 손님을 몇 명까지 줄 세울지**입니다. 이 줄이 가득 차면 새 접속은 거부됩니다.

```bash
ss -tln | grep 5003
```

```text
State  Recv-Q Send-Q  Local Address:Port Peer Address:Port
LISTEN 0      16            0.0.0.0:5003      0.0.0.0:*
```

**`Send-Q`의 16이 우리가 준 값**입니다. `Recv-Q`는 지금 줄 서 있는 수입니다.

## 제3절. 클라이언트의 두 단계

### 3.1 순서

| 단계 | 함수 |
|---|---|
| 1 | `socket` |
| 2 | **`connect`** |

**`bind`가 없습니다.** 클라이언트의 포트는 커널이 알아서 고릅니다(임시 포트).

### 3.2 코드

```c
    /* ② 돌려받은 후보를 차례로 시도한다 */
    for (rp = res; rp != NULL; rp = rp->ai_next) {
        fd = socket(rp->ai_family, rp->ai_socktype, rp->ai_protocol);
        if (fd == -1)
            continue;
        if (connect(fd, rp->ai_addr, rp->ai_addrlen) == 0)
            break;                      /* 성공 */
        close(fd);
        fd = -1;
    }
    freeaddrinfo(res);

    if (fd == -1)
        die("%s:%s 에 연결할 수 없습니다", host, port);
```

**실패한 소켓은 반드시 닫고 새로 만듭니다.** 한 번 `connect`에 실패한 소켓은 다시 쓸 수 없습니다.

### 3.3 실행

**`c-cli`에서:**

```bash
./tcpcli c-srv 5000
```

```text
c-srv:5000 에 연결했습니다. 한 줄씩 입력하십시오 (quit 로 종료)
안녕하세요
echo: 안녕하세요
두 번째 줄
echo: 두 번째 줄
quit
```

**서버 쪽에는 이렇게 남습니다.**

```text
포트 5000 에서 기다립니다 (Ctrl+C 로 종료)
접속: 192.168.56.61:36658
  받음: 안녕하세요
  받음: 두 번째 줄
  받음: quit
연결 종료
```

**클라이언트의 포트 번호(36658)는 커널이 고른 것**입니다. 실행할 때마다 달라집니다.

### 3.4 실패하는 방식을 구분하십시오

| 오류 | `errno` | 뜻 |
|---|---|---|
| `Connection refused` | `ECONNREFUSED` | **그 포트에 아무도 없다** |
| `Connection timed out` | `ETIMEDOUT` | **방화벽이 조용히 버렸다** |
| `No route to host` | `EHOSTUNREACH` | 네트워크 경로가 없다 |
| `Network is unreachable` | `ENETUNREACH` | 설정 문제 |

**1강 4.7절에서 예고한 그 구분**입니다. 실습 중 접속이 안 되면 이 표로 원인을 좁히십시오.



## 제4절. 바이트 순서

### 4.1 왜 필요한가

컴퓨터마다 **여러 바이트짜리 수를 메모리에 놓는 순서**가 다릅니다.

| 방식 | 0x1388(5000)을 |
|---|---|
| **리틀 엔디언**(x86) | `88 13` — 작은 자리부터 |
| **빅 엔디언** | `13 88` — 큰 자리부터 |

**네트워크는 하나로 정해 두었습니다.** 빅 엔디언을 쓰며, 이를 **네트워크 바이트 순서**라 합니다.

### 4.2 확인

```c
    nport = htons(port);
    naddr = htonl(addr);

    show_bytes("  메모리에 있는 그대로", &port, sizeof port);
    show_bytes("  htons 를 거친 뒤", &nport, sizeof nport);
```

```bash
./byteorder
```

```text
이 컴퓨터의 바이트 순서 : 리틀 엔디언 (작은 자리부터)

포트 5000 (0x1388)
  메모리에 있는 그대로 88 13
  htons 를 거친 뒤       13 88

주소 0xc0a8383c (192.168.56.60)
  메모리에 있는 그대로 3c 38 a8 c0
  htonl 를 거친 뒤       c0 a8 38 3c

되돌리면: ntohs=5000, ntohl=0xc0a8383c
inet_ntop 결과: 192.168.56.60
```

**바이트가 정확히 뒤집혔습니다.** 그리고 `c0 a8 38 3c`는 십진수로 **192.168.56.60** 그 자체입니다.

| 십육진수 | 십진수 |
|---|---|
| `c0` | 192 |
| `a8` | 168 |
| `38` | 56 |
| `3c` | 60 |

**IP 주소를 적는 방식이 곧 네트워크 바이트 순서**입니다.

### 4.3 네 함수

| 함수 | 뜻 |
|---|---|
| `htons` | **h**ost **to** **n**etwork **s**hort (16비트) — **포트** |
| `htonl` | host to network long (32비트) — **IPv4 주소** |
| `ntohs` | 되돌리기 (16비트) |
| `ntohl` | 되돌리기 (32비트) |

> **규칙: 소켓 구조체에 넣는 수는 `hton*`, 꺼내 읽는 수는 `ntoh*`.**
> 빅 엔디언 컴퓨터에서는 이 함수들이 아무것도 하지 않습니다. 그래도 **반드시 쓰십시오.** 안 쓰면 x86에서만 도는 프로그램이 됩니다.
{: .prompt-warning }

### 4.4 자료에도 적용됩니다

주소와 포트뿐 아니라 **우리가 보내는 자료**에도 같은 문제가 있습니다.

```c
int count = 1000;
write(fd, &count, sizeof count);        /* 위험 — 상대 컴퓨터가 다르면 깨진다 */
```

| 해법 | 설명 |
|---|---|
| `htonl`로 변환해 보낸다 | 정수에는 이 방법 |
| **문자열로 보낸다** | 사람이 읽을 수 있고 안전하다 |
| 정해진 형식을 쓴다 | 11강 프로토콜 설계 |

**11강에서 이 문제를 정면으로 다룹니다.** 이번 강의에서는 문자열만 주고받습니다.

## 제5절. 주소 다루기 — `getaddrinfo`

### 5.1 이름을 주소로

```c
#include <netdb.h>

int getaddrinfo(const char *node, const char *service,
                const struct addrinfo *hints, struct addrinfo **res);
void freeaddrinfo(struct addrinfo *res);
```

```c
    memset(&hints, 0, sizeof hints);
    hints.ai_family   = AF_UNSPEC;      /* IPv4 든 IPv6 든 */
    hints.ai_socktype = SOCK_STREAM;

    rc = getaddrinfo(host, port, &hints, &res);
    if (rc != 0) {                      /* errno 가 아니다 */
        fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(rc));
        return 1;
    }
```

### 5.2 오류 알림 방식이 또 다릅니다

| 함수 계열 | 오류를 알리는 방식 |
|---|---|
| 시스템 호출 | `-1` + `errno`(1강) |
| pthread | 반환값이 오류 번호(7강 2.2절) |
| **`getaddrinfo`** | **반환값이 전용 오류 번호**, `gai_strerror`로 풀어 읽는다 |

**세 번째 방식**입니다. `strerror`가 아니라 **`gai_strerror`** 를 써야 합니다.

### 5.3 왜 이 함수를 쓰는가

| 옛 방식 | `getaddrinfo` |
|---|---|
| `gethostbyname` | IPv4 전용, **`MT-Unsafe`**(8강 5.2절) |
| `inet_addr` | IPv4 전용, 오류 처리 애매 |
| 주소 구조체를 직접 채움 | **알아서 채워 준다** |

**`getaddrinfo`는 IPv4와 IPv6를 함께 다루고 스레드 안전합니다.** 오늘날 유일하게 권장되는 방법입니다.

### 5.4 후보를 차례로 시도한다

`getaddrinfo`는 **여러 후보를 목록으로** 돌려줍니다. 이름 하나에 주소가 여럿일 수 있기 때문입니다(IPv4·IPv6, 여러 서버).

```bash
getent hosts localhost
```

```text
::1             localhost
```

**연결 코드에서 반복문을 돌린 이유**가 이것입니다(3.2절). 첫 후보가 실패해도 다음을 시도합니다.

> **`freeaddrinfo`를 잊지 마십시오.** `getaddrinfo`가 목록을 `malloc`으로 만들어 주므로 반납해야 합니다. 1부 8강의 원칙 그대로입니다.
{: .prompt-warning }

## 제6절. 부분 전송은 일상이다

**2강 4.1절에서 예고한 것이 여기서 현실이 됩니다.**

### 6.1 실험

`partial_io.c`는 **4 MiB를 한 번의 `write`로** 보내려 합니다. 받는 쪽도 **4 MiB를 한 번에** 달라고 합니다.

```c
    /* 보내는 쪽 버퍼를 작게 줄여 실제 상황을 흉내 낸다 */
    setsockopt(sv[0], SOL_SOCKET, SO_SNDBUF, &sndbuf, sizeof sndbuf);
```

```c
    /* 막히지 않게 해 두면 '보낼 수 있는 만큼만' 보내고 돌아온다 */
    if (fcntl(sv[0], F_SETFL, O_NONBLOCK) == -1)
        perror("fcntl");

    {
        ssize_t first = write(sv[0], buf, SIZE);

        printf("  [보내는 쪽] 4 MiB 를 한 번에 write 요청\n");
        printf("  [보내는 쪽] 실제로 보낸 양 = %zd 바이트 (%.2f%%)\n",
               first, 100.0 * (double) first / SIZE);
```

### 6.2 결과

```bash
./partial_io
```

```text
  [보내는 쪽] 4 MiB 를 한 번에 write 요청
  [보내는 쪽] 실제로 보낸 양 = 32640 바이트 (0.78%)
  [보내는 쪽] → 나머지는 직접 되풀이해서 보내야 합니다
  [보내는 쪽] 모두 보내는 데 write 124회
  [받는 쪽] 1번째 read: 4 MiB 를 요청했는데 32640 바이트
  [받는 쪽] 2번째 read: 4 MiB 를 요청했는데 32640 바이트
  [받는 쪽] 3번째 read: 4 MiB 를 요청했는데 32640 바이트
  [받는 쪽] 4번째 read: 4 MiB 를 요청했는데 32640 바이트
  [받는 쪽] 5번째 read: 4 MiB 를 요청했는데 32640 바이트
  [받는 쪽] 모두 134회 read 로 4194304 바이트
```

**4 MiB를 요청했는데 0.78%인 32,640바이트만 보냈습니다.** 나머지를 마저 보내는 데 `write`가 **124회** 더 걸렸습니다.

받는 쪽도 마찬가지입니다. 4 MiB를 달라고 했는데 매번 **32,640바이트씩** 돌아왔습니다.

### 6.3 그래서 `_full` 함수가 필요합니다

2강 4.2절에서 만든 그 함수가 **네트워크에서는 선택이 아니라 필수**입니다.

```c
int write_full(int fd, const void *vbuf, size_t n)
{
    const char *buf = vbuf;
    size_t done = 0;

    while (done < n) {
        ssize_t w = write(fd, buf + done, n - done);

        if (w < 0) {
            if (errno == EINTR)
                continue;               /* 시그널에 끊겼을 뿐 (5강 7절) */
            return -1;
        }
        done += (size_t) w;
    }
    return 0;
}
```

> **`write`의 반환값을 무시하면 자료가 조용히 잘립니다.**
> 파일에서는 거의 드러나지 않다가 **네트워크에서 곧바로 터집니다.** 위 실험에서 반환값을 무시했다면 4 MiB 중 32 KiB만 보내고 "다 보냈다"고 착각했을 것입니다.
{: .prompt-danger }

### 6.4 읽는 쪽은 더 어렵습니다

**얼마나 읽어야 하는지 미리 알 수 없습니다.**

| 방법 | 설명 | 배우는 곳 |
|---|---|---|
| **개행까지** | 한 줄 단위 프로토콜 | 이번 강의 `read_line` |
| **길이를 먼저 보낸다** | 4바이트 길이 + 자료 | **11강** |
| 연결을 닫아 끝을 알린다 | HTTP/1.0 방식 | 제7절 |
| 정해진 크기 | 고정 길이 레코드 | 드물다 |

이번 강의의 `read_line`은 **한 바이트씩** 읽습니다. 단순하지만 느립니다. 11강에서 버퍼를 둔 방식으로 개선합니다.

## 제7절. 연결이 끝나는 방식

### 7.1 정상 종료

한쪽이 `close`하면 상대의 `read`가 **0을 돌려줍니다.**

| `read`의 반환값 | 뜻 |
|---|---|
| 양수 | 그만큼 받았다 |
| **0** | **상대가 정상적으로 닫았다** |
| −1 | 오류 |

**2강 3.1절의 "0은 파일 끝"이 여기서는 "상대가 끊었다"** 가 됩니다.

### 7.2 이미 닫힌 곳에 쓰면

| 시점 | 결과 |
|---|---|
| 첫 번째 `write` | 성공할 수도 있다(커널이 아직 모름) |
| 그다음 `write` | **`SIGPIPE`** → 기본 동작은 **종료** |
| `SIGPIPE`를 무시하면 | `-1` + **`EPIPE`** |

```c
signal(SIGPIPE, SIG_IGN);           /* 5강 2.3절 */
```

> **서버 프로그램의 첫 줄에 넣으십시오.**
> 클라이언트가 먼저 끊는 일은 늘 일어납니다. 브라우저에서 새로 고침만 눌러도 그렇습니다. 그때마다 서버가 죽으면 안 됩니다. 5강 문제 10에서 종료 상태 141(=128+13)을 확인했던 그 문제입니다.
{: .prompt-danger }

### 7.3 절반만 닫기

```c
shutdown(fd, SHUT_WR);              /* "더 보낼 것은 없다" 고 알린다 */
```

| 인자 | 뜻 |
|---|---|
| `SHUT_WR` | **쓰기만 닫는다** — 읽기는 계속 |
| `SHUT_RD` | 읽기만 닫는다 |
| `SHUT_RDWR` | 둘 다 |

**"내 말은 끝났으니 네 대답을 기다린다"** 를 표현할 때 씁니다. `close`와 달리 서술자는 살아 있으므로 응답을 계속 받을 수 있습니다.

### 7.4 상대가 살아 있는지는 알 수 없습니다

**케이블이 뽑히거나 상대 컴퓨터가 꺼지면** TCP는 한동안 알아채지 못합니다. 아무것도 보내지 않는 연결은 몇 시간이고 그대로 남아 있을 수 있습니다.

| 방법 | 설명 |
|---|---|
| **응용 계층 신호** | 주기적으로 "살아 있나" 메시지 — **가장 확실** |
| `SO_KEEPALIVE` | TCP가 확인해 준다. 다만 기본 간격이 **2시간** |
| 시간 제한 | 일정 시간 조용하면 끊는다 |

**17강 종합 과제에서 이 문제를 다룹니다.**

## 제8절. 평문은 그대로 보인다

**이 절이 이 과정 전체의 전환점입니다.**

### 8.1 우리가 만든 것의 문제

지금까지 만든 서버와 클라이언트는 잘 동작합니다. 그런데 **오가는 자료가 어떤 모습으로 흐르는지** 확인해 본 적이 없습니다.

### 8.2 중간에 끼어들기

`wiretap.c`는 **클라이언트와 서버 사이에 앉아** 자료를 그대로 넘기면서 내용을 찍습니다.

```text
  클라이언트 ──▶ [ 엿듣기 ] ──▶ 서버
             ◀──          ◀──
```

핵심은 두 서술자를 함께 지켜보는 부분입니다.

```c
            for (i = 0; i < 2 && running; i++) {
                if (!(pfd[i].revents & (POLLIN | POLLHUP | POLLERR)))
                    continue;

                n = read(pfd[i].fd, buf, sizeof buf);
                if (n <= 0) {
                    running = 0;
                    break;
                }
                dump(i == 0 ? "  클라이언트 → 서버" : "  서버 → 클라이언트",
                     buf, (size_t) n);

                if (write_full(pfd[1 - i].fd, buf, (size_t) n) < 0)
                    running = 0;
            }
```

**`poll`로 두 쪽을 동시에 기다립니다.** 어느 쪽에서 자료가 오든 반대쪽으로 넘기면서 내용을 찍습니다. 10강에서 배울 방식을 미리 쓴 것입니다.

### 8.3 실행

터미널 셋을 씁니다.

```bash
./tcpserv 5000
```

```bash
./wiretap 6000 c-srv 5000
```

```bash
./tcpcli c-cli 6000
```

**클라이언트는 6000번(엿듣기)에 연결합니다.** 클라이언트 입장에서는 아무것도 달라지지 않습니다.

```text
비밀번호는 admin1234 입니다
echo: 비밀번호는 admin1234 입니다
계좌번호 110-123-456789
echo: 계좌번호 110-123-456789
quit
```

**정상적으로 동작합니다.** 그런데 엿듣기 쪽에는 이렇게 남습니다.

```text
=== 엿듣기 시작: 포트 6000 → 127.0.0.1:5000 ===
--- 새 연결 ---
  클라이언트 → 서버 36바이트: "비밀번호는 admin1234 입니다\n"
  서버 → 클라이언트 42바이트: "echo: 비밀번호는 admin1234 입니다\n"
  클라이언트 → 서버 28바이트: "계좌번호 110-123-456789\n"
  서버 → 클라이언트 34바이트: "echo: 계좌번호 110-123-456789\n"
  클라이언트 → 서버 5바이트: "quit\n"
--- 연결 끝 ---
```

> **비밀번호와 계좌번호가 그대로 읽힙니다.**
> 암호를 풀 필요도, 무엇을 알아낼 필요도 없었습니다. **그냥 지나가는 것을 읽었을 뿐**입니다.
{: .prompt-danger }

### 8.4 이것이 특별한 공격이 아닙니다

| 오해 | 사실 |
|---|---|
| "해킹 도구가 필요하다" | **200줄짜리 프로그램**이면 된다 |
| "서버를 뚫어야 한다" | 뚫을 필요 없다. **지나가는 것을 볼 뿐** |
| "우리 회사망은 안전하다" | 같은 망의 누구나, 공유기, 통신 장비, ISP |
| "중요한 것만 조심하면 된다" | **무엇이 중요한지 공격자가 고른다** |

**중간에 있을 수 있는 곳**을 헤아려 보십시오.

| 위치 | 예 |
|---|---|
| 같은 랜 | 카페·공항 무선망의 다른 손님 |
| 공유기 | 감염된 가정용 공유기 |
| 통신 경로 | 중간의 라우터·스위치 |
| 통신사 | ISP, 국가 |

### 8.5 서버 안에서도 평문입니다

`strace`로 서버가 다루는 자료를 보면 이렇습니다.

```bash
strace -f -e trace=read,write -o st.log ./tcpserv 5002
```

```bash
grep -a "admin1234" st.log
```

```text
write(4, "echo: \353\271\204\353\260\200\353\262\210\355\230\270\353\212\224 admin1234 "..., 42) = 42
```

**서버의 메모리에도 평문 그대로** 들어 있습니다.

### 8.6 그래서 무엇이 필요한가

우리가 만든 통신에는 **세 가지가 전혀 없습니다.**

| 없는 것 | 뜻 | 어디서 배우나 |
|---|---|---|
| **비밀성** | 남이 못 읽게 | **12강** 대칭키 암호 |
| **무결성** | 중간에서 못 바꾸게 | 12강 인증 태그 |
| **인증** | 상대가 진짜인지 | **13·14강** 공개키와 인증서 |

> **셋 다 필요합니다.**
> 비밀성만 있으면 중간에서 **내용을 바꿔치기**할 수 있습니다. 무결성만 있으면 **읽힙니다.** 인증이 없으면 **엉뚱한 상대와 안전하게 통신**하게 됩니다 — 오늘 만든 엿듣기 프로그램이 바로 그 상황입니다. 클라이언트는 자기가 서버와 통신한다고 믿었습니다.
{: .prompt-warning }

**12강부터 이 셋을 하나씩 채워 갑니다.** 그리고 14강에서 그 전부를 묶은 것이 TLS임을 보게 됩니다.

### 8.7 `tcpdump`로도 확인하십시오

프록시 없이 **네트워크를 흐르는 그대로** 보려면 `tcpdump`를 씁니다. 관리자 권한이 필요합니다.

**`c-cli`에서 잡으면서:**

```bash
sudo tcpdump -i enp0s8 -A -n 'tcp port 5000'
```

| 옵션 | 뜻 |
|---|---|
| `-i enp0s8` | 실습망 인터페이스(1강 2.3절) |
| `-A` | **내용을 글자로 보여 준다** |
| `-n` | 이름 풀이를 하지 않는다 |
| `'tcp port 5000'` | 그 포트만 |

**주고받은 글자가 그대로 보입니다.** 프록시를 거치지 않았는데도 그렇습니다.

> 14강에서 **TLS 핸드셰이크를 같은 방법으로** 들여다봅니다. 그때는 자료가 암호문으로 보일 것입니다. **오늘의 화면과 그때의 화면을 나란히 두고 비교**하면 암호화가 무엇을 했는지 한눈에 들어옵니다. **오늘 캡처한 화면을 저장해 두십시오.**
{: .prompt-tip }

## 제9절. 관찰 도구

### 9.1 `ss` — 연결 상태

```bash
ss -tln
```

```text
State  Recv-Q Send-Q  Local Address:Port Peer Address:Port
LISTEN 0      16            0.0.0.0:5003      0.0.0.0:*
```

| 옵션 | 뜻 |
|---|---|
| `-t` | TCP |
| `-l` | 듣고 있는 것만 |
| `-n` | 숫자 그대로(이름 풀이 안 함) |
| `-p` | 어느 프로세스인지(권한 필요) |
| `-a` | 전부 |

### 9.2 연결 상태 읽기

| 상태 | 뜻 |
|---|---|
| `LISTEN` | 손님을 기다리는 중 |
| `ESTAB` | 연결되어 있음 |
| **`TIME_WAIT`** | **닫은 뒤 잠시 남아 있음**(2.3절의 그 원인) |
| `CLOSE_WAIT` | **상대는 닫았는데 우리가 안 닫음** — 버그 신호 |

> **`CLOSE_WAIT`가 쌓이면 `close`를 빠뜨린 것입니다.** 2강 5.2절의 서술자 누수가 네트워크에서 이런 모습으로 나타납니다.
{: .prompt-warning }

### 9.3 그 밖의 도구

| 도구 | 쓰임 |
|---|---|
| `ss -tn state established` | 지금 연결된 것만 |
| `ls -l /proc/PID/fd` | 그 프로세스의 소켓(2강 9.2절) |
| `strace -e trace=network` | 소켓 관련 시스템 호출만(1강 11.4절) |
| **`nc`(netcat)** | **서버·클라이언트 흉내** — 시험에 아주 유용 |

`nc`로 우리 서버를 시험할 수 있습니다.

```bash
printf '시험\nquit\n' | nc c-srv 5000
```

**우리 클라이언트 없이도 동작해야** 프로토콜이 제대로 된 것입니다.

## 제10절. 자주 나오는 실수

| 증상 | 원인 | 해결 |
|---|---|---|
| `Address already in use` | `TIME_WAIT` | **`SO_REUSEADDR`**(2.3절) |
| `Connection refused` | 서버가 없다 | 서버 실행 확인 |
| `Connection timed out` | **방화벽** | `ufw status`(1강 4.7절) |
| 밖에서 접속이 안 됨 | `127.0.0.1`에 `bind` | **`INADDR_ANY`** |
| 포트가 엉뚱함 | `htons` 누락 | 포트·주소는 **반드시 변환** |
| 자료가 잘림 | `write` 반환값 무시 | **`write_full`**(6.3절) |
| 자료가 뭉쳐서 옴 | 메시지 경계 없음 | 개행이나 길이 앞머리(11강) |
| 서버가 갑자기 죽음 | `SIGPIPE` | `SIG_IGN` + `EPIPE` |
| `accept`가 `EINTR` | 시그널 | 재시도(5강 7절) |
| `CLOSE_WAIT` 누적 | `close` 누락 | 모든 경로에서 닫기 |
| 서술자 고갈 | 같은 원인 | `ulimit -n`(2강 5.2절) |
| `gethostbyname`이 이상함 | `MT-Unsafe` | **`getaddrinfo`**(5.3절) |
| `getaddrinfo` 오류가 이상함 | `strerror` 사용 | **`gai_strerror`** |
| 메모리가 샘 | `freeaddrinfo` 누락 | 반드시 반납 |

### 문제 5. 부분 전송 재현

`write`가 요청한 만큼 보내지 않는 것을 실험으로 보이십시오.

**정답 및 해설**

6.1·6.2절의 코드와 결과가 답입니다.

```text
  [보내는 쪽] 실제로 보낸 양 = 32640 바이트 (0.78%)
  [보내는 쪽] 모두 보내는 데 write 124회
```

- **두 가지 장치가 필요했습니다.** ① `SO_SNDBUF`로 버퍼를 줄이고 ② `O_NONBLOCK`으로 막히지 않게 했습니다.
- 막히는 소켓(기본값)에서는 커널이 다 보낼 때까지 기다려 주므로 짧은 쓰기가 잘 드러나지 않습니다. **그래도 시그널에 끊기면 짧게 돌아올 수 있으므로** `write_full`은 여전히 필요합니다.
- 받는 쪽이 4 MiB를 요청했는데 32,640바이트씩 받은 것도 함께 확인하십시오. **읽기와 쓰기 양쪽 모두** 부분 처리가 일어납니다.

### 문제 6. `SIGPIPE` 다루기

클라이언트가 먼저 끊었을 때 서버가 죽지 않게 하십시오.

**정답 및 해설**

```c
signal(SIGPIPE, SIG_IGN);
```

```c
if (write_full(conn_fd, reply, len) < 0) {
    if (errno == EPIPE)
        fprintf(stderr, "  상대가 먼저 끊었습니다\n");
    break;                          /* 이 손님만 포기하고 다음 손님을 받는다 */
}
```

- **재현하는 법**: 클라이언트를 실행한 뒤 곧바로 Ctrl+C로 죽이고, 서버가 응답을 보내게 하십시오.
- `SIG_IGN`을 빼면 서버가 **종료 상태 141**로 죽습니다(5강 문제 10).
- **한 손님의 문제로 서버 전체가 끝나면 안 됩니다.** `break`로 그 연결만 정리하고 반복문을 계속 도는 것이 핵심입니다.

### 문제 7. 엿듣기 프로그램

**정답 및 해설**

8.2·8.3절의 코드와 결과가 답입니다.

### 문제 8. `tcpdump`로 확인

프록시 없이 네트워크를 흐르는 자료를 캡처하십시오.

**정답 및 해설**

```bash
sudo tcpdump -i enp0s8 -A -n 'tcp port 5000'
```

- **인터페이스를 바르게 골라야** 합니다. 실습망은 `enp0s8`입니다(1강 2.3절). `lo`로 잡으면 두 VM 사이 통신이 보이지 않습니다.
- `-A` 대신 `-X`를 쓰면 십육진수와 글자를 함께 보여 줍니다.
- 파일로 저장해 두면 나중에 다시 볼 수 있습니다.

```bash
sudo tcpdump -i enp0s8 -w plain.pcap 'tcp port 5000'
```

- **이 파일을 지우지 마십시오.** 14강에서 TLS 캡처와 나란히 비교합니다.
- 권한이 없어 실행되지 않으면, 사용자에게 캡처 권한을 주는 방법도 있습니다.

```bash
sudo setcap cap_net_raw,cap_net_admin=eip $(which tcpdump)
```

### 문제 9. 여러 손님 받기 (맛보기)

지금 서버는 **한 번에 한 손님**만 받습니다. 4강의 `fork`로 여러 손님을 받게 고치십시오.

**정답 및 해설**

```c
        conn_fd = accept(listen_fd, ...);
        ...
        pid = fork();
        if (pid == 0) {                 /* 자식이 이 손님을 맡는다 */
            close(listen_fd);           /* 자식은 듣기 소켓이 필요 없다 */
            handle(conn_fd);
            close(conn_fd);
            _exit(0);
        }
        close(conn_fd);                 /* 부모는 이 연결을 놓는다 */
```

**닫기가 전부입니다.** 6강 3.1절의 파이프와 같은 이야기입니다.

| 누가 | 무엇을 닫나 | 안 닫으면 |
|---|---|---|
| 자식 | `listen_fd` | 서술자 낭비 |
| **부모** | **`conn_fd`** | **연결이 끝나도 안 닫힘** → `CLOSE_WAIT` 누적 |

손님 셋을 동시에 붙여 확인한 결과입니다.

```text
포트 5210 — 여러 손님을 받습니다
접속: 127.0.0.1:49960
접속: 127.0.0.1:49962
  [127.0.0.1:49960] 받음: 손님1 입니다
  [127.0.0.1:49962] 받음: 손님2 입니다
  [127.0.0.1:49960] 받음: quit
  [127.0.0.1:49962] 받음: quit
접속: 127.0.0.1:49966
  [127.0.0.1:49966] 받음: 손님3 입니다
  [127.0.0.1:49966] 받음: quit
```

```bash
ps -eo stat | grep -c '^Z'
```

```text
0
```

- **49960과 49962의 처리가 서로 겹쳐 있습니다.** 이것이 동시에 처리되고 있다는 증거입니다. 원래 서버였다면 앞 손님이 `quit` 할 때까지 다음 손님은 접속조차 되지 않았습니다.
- **좀비가 0개**입니다. 5강 8절의 `SIGCHLD` 처리기를 넣었기 때문입니다. 빼고 다시 세어 보면 접속 수만큼 쌓입니다.
- `accept`가 `EINTR`로 깨어나는 것도 처리해야 합니다. `SIGCHLD`가 올 때마다 `accept`가 중단되기 때문입니다(5강 7절).
- 이 방식은 접속마다 프로세스를 만들어 **비쌉니다.** 10강에서 `epoll`로 훨씬 효율적인 방법을 배웁니다.
- 그래도 **한 손님의 문제가 다른 손님에게 번지지 않는다**는 장점이 있습니다. 7강 9.2절의 Apache prefork 방식입니다.

### 문제 10. `nc`로 시험하기

우리 클라이언트 없이 `nc`만으로 서버를 시험하십시오.

**정답 및 해설**

```bash
printf '시험\nquit\n' | nc c-srv 5000
```

```bash
nc -l 5000
```

```text
echo: 시험
```

서버 쪽 기록입니다.

```text
포트 5211 에서 기다립니다 (Ctrl+C 로 종료)
접속: 127.0.0.1:33378
  받음: 시험
  받음: quit
연결 종료
```

- **`nc`로도 동작해야** 프로토콜이 제대로 정의된 것입니다. 우리 클라이언트에서만 되는 것은 우연히 맞은 것일 수 있습니다.
- `nc -q1`은 입력이 끝난 뒤 1초 더 기다렸다 끊으라는 뜻입니다. 없으면 응답을 받기 전에 끊길 수 있습니다.
- `nc -l`로 가짜 서버를 띄워 **우리 클라이언트를 시험**할 수도 있습니다. 양쪽을 따로 시험할 수 있어야 문제를 좁힐 수 있습니다.
- 1부 12강의 "정답이 있는 것과 맞춰 본다"는 검증 방식이 네트워크에서도 그대로 적용됩니다.

## 정리

| 구분 | 핵심 |
|---|---|
| 소켓 | **파일 서술자**다. `read`·`write`·`close` 그대로 |
| 서버 | `socket` → **`bind`** → `listen` → **`accept`**(새 서술자) |
| 클라이언트 | `socket` → `connect`. `bind`는 없다 |
| 필수 설정 | **`SO_REUSEADDR`**, `signal(SIGPIPE, SIG_IGN)` |
| 바이트 순서 | 포트는 **`htons`**, 주소는 **`htonl`** |
| 이름 풀이 | **`getaddrinfo`** + `gai_strerror` + `freeaddrinfo` |
| **부분 전송** | 4 MiB 요청에 **0.78%만** 전송됨. `write_full` 필수 |
| 메시지 경계 | **없다.** 개행이나 길이 앞머리로 직접 정한다 |
| 끝남 | `read`가 **0**이면 상대가 닫은 것 |
| 실패 구분 | `refused`=없음, `timed out`=**막힘** |
| **평문** | **중간에서 그대로 읽힌다.** 200줄이면 충분하다 |
| 없는 세 가지 | **비밀성·무결성·인증** → 12~14강 |

**본문의 주장과 근거**

| 주장 | 근거 |
|---|---|
| 리틀 엔디언에서 바이트가 뒤집힌다(4.2절) | `byteorder` — 포트 `88 13` → `13 88`, 주소 `3c 38 a8 c0` → `c0 a8 38 3c` |
| `c0a8383c`가 곧 192.168.56.60(4.2절) | `inet_ntop` 결과 |
| **4 MiB 요청에 0.78%만 전송된다**(6.2절) | `partial_io` — 32,640바이트, 완료까지 `write` 124회 |
| 읽기도 부분 처리된다(6.2절) | 4 MiB 요청에 매번 32,640바이트, 모두 134회 |
| `listen`의 backlog가 `Send-Q`에 보인다(2.4절) | `ss -tln` → `LISTEN 0 16` |
| **평문이 중간에서 그대로 읽힌다**(8.3절) | `wiretap` — 비밀번호·계좌번호가 문자 그대로 출력 |
| 서버 메모리에도 평문이 있다(8.5절) | `strace` 로그에 `admin1234`가 그대로 |
| 서버·클라이언트가 동작한다(3.3절) | 두 프로그램 실행 — `echo:` 응답과 서버 쪽 기록 |
| `fork` 서버가 동시에 처리한다(문제 9) | 손님 셋의 처리가 **서로 겹쳐** 기록됨, 좀비 **0개** |
| `nc`로도 동작한다(문제 10) | `printf … \| nc` → `echo: 시험` |
| 없는 포트는 즉시 거부된다(문제 4) | `Connection refused` |

> 값은 모두 **Ubuntu 24.04에서 실제로 실행한 결과**입니다. 8.3절의 엿듣기와 3.3절의 통신은 **검증 환경에서 같은 컴퓨터의 루프백으로 실행**했으므로 주소가 `127.0.0.1`로 나왔습니다. **여러분의 VM 두 대에서는 `192.168.56.60`·`192.168.56.61`로 나타나며, 그 밖의 동작과 출력은 같습니다.**
