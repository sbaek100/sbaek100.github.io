## 제1절. UDP란

### 1.1 연결이 없습니다

| | TCP(`SOCK_STREAM`) | UDP(`SOCK_DGRAM`) |
|---|---|---|
| 연결 | **필요**(`connect`·`accept`) | **없다** |
| 순서 | 보장 | **보장 없음** |
| 도착 | 보장(다시 보냄) | **보장 없음** |
| 중복 | 없음 | **있을 수 있음** |
| **메시지 경계** | **없다** | **있다** |
| 흐름 조절 | 있다 | 없다 |
| 머리말 크기 | 20바이트 이상 | **8바이트** |

### 1.2 함수가 다릅니다

| TCP | UDP |
|---|---|
| `connect` / `accept` | **없다** |
| `read` / `write` | **`recvfrom` / `sendto`** |
| 상대를 한 번 정하면 끝 | **매번 주소를 지정** |

```c
ssize_t sendto(int fd, const void *buf, size_t len, int flags,
               const struct sockaddr *dest, socklen_t addrlen);
ssize_t recvfrom(int fd, void *buf, size_t len, int flags,
                 struct sockaddr *src, socklen_t *addrlen);
```

**`recvfrom`이 보낸 사람의 주소를 채워 줍니다.** 그래서 답장을 보낼 수 있습니다.

### 1.3 하나의 소켓이 모두를 상대합니다

```text
   TCP                        UDP
   ┌─────────┐                ┌─────────┐
   │listen_fd│                │   fd    │──── 손님 A
   └────┬────┘                │         │──── 손님 B
        │ accept              │         │──── 손님 C
   ┌────┴────┬────────┐       └─────────┘
   │ conn_fd │conn_fd │        서술자 하나로 전부
   └─────────┴────────┘
```

**UDP는 서술자가 하나뿐**입니다. 10강에서 배운 다중화가 필요 없습니다. 대신 **누가 보낸 것인지 매번 확인**해야 합니다.

## 제2절. UDP 서버와 클라이언트

### 2.1 서버

```c
    fd = socket(AF_INET, SOCK_DGRAM, 0);        /* STREAM 이 아니라 DGRAM */
    ...
    if (bind(fd, (struct sockaddr *) &addr, sizeof addr) == -1) {
        perror("bind");
        return 1;
    }

    /* listen 도 accept 도 없다 */
```

```c
        peerlen = sizeof peer;
        n = recvfrom(fd, buf, sizeof buf - 1, 0,
                     (struct sockaddr *) &peer, &peerlen);
        ...
        /* 답장은 보낸 곳으로 — 주소를 직접 지정한다 */
        if (sendto(fd, buf, (size_t) n, 0,
                   (struct sockaddr *) &peer, peerlen) < 0)
            perror("sendto");
```

**`bind` 다음에 곧바로 `recvfrom`입니다.** `listen`도 `accept`도 없습니다.

### 2.2 클라이언트

```c
    /* 답장을 영원히 기다리지 않도록 시간 제한을 둔다 */
    tv.tv_sec = 1;
    tv.tv_usec = 0;
    setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof tv);
```

```c
        /* connect 없이 보낸다 — 받는 곳을 그때그때 지정 */
        if (sendto(fd, msg, (size_t) len, 0, res->ai_addr, res->ai_addrlen) < 0) {
            perror("sendto");
            continue;
        }

        n = recvfrom(fd, buf, sizeof buf - 1, 0, NULL, NULL);
        if (n < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK)
                printf("  %d번째: 답장이 없습니다(시간 초과)\n", i);
```

> **시간 제한이 반드시 필요합니다.**
> TCP라면 상대가 없을 때 `connect`가 실패해 알려 줍니다. **UDP는 그냥 보내고 끝**이므로, 답장을 기다리는 쪽이 스스로 포기할 줄 알아야 합니다. `SO_RCVTIMEO`가 없으면 영원히 멈춥니다.
{: .prompt-danger }

### 2.3 실행

```bash

  2번째 답장: 2번째 데이터그램
  3번째 답장: 3번째 데이터그램
보낸 3개 중 3개의 답장을 받았습니다
```

서버 쪽입니다.

```text
UDP 포트 5100 에서 기다립니다
  127.0.0.1:59744 에서 24바이트: 1번째 데이터그램
  127.0.0.1:59744 에서 24바이트: 2번째 데이터그램
  127.0.0.1:59744 에서 24바이트: 3번째 데이터그램
```

**세 번 모두 같은 포트에서 왔습니다.** 클라이언트가 소켓 하나를 계속 썼기 때문입니다. 그러나 **서버는 그 셋이 같은 상대인지 스스로 판단해야** 합니다. 연결이라는 개념이 없기 때문입니다.

### 2.4 상대가 없으면

```bash
./udpcli c-srv 5199 2
```

```text
  1번째: 답장이 없습니다(시간 초과)
  2번째: 답장이 없습니다(시간 초과)
보낸 2개 중 0개의 답장을 받았습니다
```

**`sendto` 자체는 성공했습니다.** 아무도 없는 곳에 보내도 UDP는 오류를 내지 않습니다. **답장이 없다는 것으로만 알 수 있습니다.**

> TCP였다면 `connect`가 곧바로 `Connection refused`였습니다(9강 3.4절). **이 차이가 UDP를 쓸 때 가장 조심해야 할 점**입니다.
{: .prompt-warning }

## 제3절. 언제 UDP를 쓰는가

### 3.1 알맞은 곳

| 쓰임 | 왜 UDP인가 |
|---|---|
| **DNS** | 질의 하나, 답 하나. 연결 비용이 아깝다 |
| **실시간 음성·영상** | **늦게 온 자료는 쓸모없다.** 다시 보내느니 버린다 |
| 게임 | 위치 정보는 최신 것만 의미가 있다 |
| 로그 수집(syslog) | 몇 개 빠져도 괜찮다 |
| 방송·다중 전송 | TCP로는 불가능 |

**핵심 판단**: **"늦게 도착한 자료가 가치가 있는가?"** 없다면 UDP가 낫습니다.

### 3.2 알맞지 않은 곳

| 쓰임 | 왜 TCP인가 |
|---|---|
| 파일 전송 | 한 바이트도 빠지면 안 된다 |
| 로그인·결제 | 순서와 도착이 중요 |
| 명령 주고받기 | 명령이 사라지면 곤란하다 |

### 3.3 "UDP가 빠르다"는 오해

| 오해 | 사실 |
|---|---|
| UDP가 언제나 빠르다 | **손실이 없을 때만** 그렇다 |
| TCP는 무겁다 | 연결 수립 이후에는 거의 차이가 없다 |
| UDP를 쓰면 지연이 준다 | **다시 보내기를 직접 만들면** TCP와 같아진다 |

**필요한 보장을 직접 만들다 보면 결국 TCP를 다시 만들게 됩니다.** 그래서 "TCP를 쓰되 정말 필요할 때만 UDP"가 기본 원칙입니다.

> 오늘날의 QUIC(HTTP/3)은 UDP 위에 신뢰성과 암호화를 새로 얹은 것입니다. **TCP를 대체하려고 만든 것이지 UDP가 간단해서 고른 것이 아닙니다.**
{: .prompt-info }

## 제4절. 메시지 경계 문제

**이 절이 이번 강의에서 가장 중요합니다.**

### 4.1 실험

`boundary.c`는 **세 번 나누어 보내고 받는 쪽이 몇 번에 받는지** 봅니다.

```c
    write(sv[0], "AAA", 3);
    write(sv[0], "BBBBB", 5);
    write(sv[0], "CC", 2);
```

```bash
./boundary tcp
```

```text
=== SOCK_STREAM (TCP 계열) ===
  보내는 쪽: 3바이트, 5바이트, 2바이트를 따로 보냈습니다
  1번째 read: 10바이트 "AAABBBBBCC"
  → 모두 1번 읽었습니다
```

```bash
./boundary udp
```

```text
=== SOCK_DGRAM (UDP 계열) ===
  보내는 쪽: 3바이트, 5바이트, 2바이트를 따로 보냈습니다
  1번째 read: 3바이트 "AAA"
  2번째 read: 5바이트 "BBBBB"
  3번째 read: 2바이트 "CC"
  → 모두 3번 읽었습니다
```

### 4.2 결과

| | 보낸 횟수 | 받은 횟수 | 경계 |
|---|---|---|---|
| **TCP** | 3 | **1** | **사라졌다** |
| **UDP** | 3 | **3** | **지켜졌다** |

**TCP에서 `"AAABBBBBCC"` 한 덩어리로 합쳐졌습니다.** 받는 쪽은 이것이 원래 몇 개였는지 알 방법이 없습니다.

### 4.3 반대도 일어납니다

9강 6.2절에서 본 것이 그것입니다. **한 번에 보낸 4 MiB가 134번에 나뉘어 도착**했습니다.

| 방향 | 일어나는 일 |
|---|---|
| 여러 번 보냄 → 한 번에 받음 | **합쳐짐**(이번 실험) |
| 한 번 보냄 → 여러 번 받음 | **쪼개짐**(9강 6.2절) |

**둘 다 정상입니다.** TCP는 **바이트의 흐름**만 보장하고 덩어리는 보장하지 않습니다.

### 4.4 UDP에는 EOF도 없습니다

위 실험에서 UDP 쪽은 **"끝"을 알 방법이 없어** 시간 제한으로 멈추게 했습니다.

```c
        /* UDP 계열에는 '끝'이 없다. 조용해지면 그만두도록 시간 제한을 둔다 */
        tv.tv_sec = 1;
        tv.tv_usec = 0;
        setsockopt(sv[1], SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof tv);
```

| | 끝을 아는 방법 |
|---|---|
| TCP | **`read`가 0**(9강 7.1절) |
| UDP | **없다** — 직접 정해야 한다 |

### 4.5 그래서 프레이밍이 필요합니다

> **프레이밍(framing)**: 바이트의 흐름에서 **하나의 메시지가 어디서 시작해 어디서 끝나는지** 정하는 방법.

| 방법 | 설명 | 예 |
|---|---|---|
| **구분자** | 특별한 바이트까지 | 개행(HTTP 머리말, SMTP) |
| **길이 앞머리** | 길이를 먼저 보낸다 | **대부분의 이진 프로토콜** |
| 고정 길이 | 언제나 같은 크기 | 드물다 |
| 연결 종료 | 닫으면 끝 | HTTP/1.0 |

지금까지 쓴 `read_line`은 **구분자 방식**이었습니다. 이제 **길이 앞머리** 방식을 만듭니다.

### 4.6 구분자 방식의 한계

| 문제 | 설명 |
|---|---|
| **자료에 구분자가 들어갈 수 없다** | 이진 자료에 개행이 있으면 깨진다 |
| 탈출 처리가 필요 | 복잡해진다 |
| **길이를 미리 모른다** | 버퍼를 얼마나 잡을지 알 수 없다 |
| 한 바이트씩 읽게 되기 쉽다 | 느리다 |

1부 12강의 CSV에서 **"제목에 쉼표를 금지"** 했던 것이 같은 문제였습니다. 그때는 금지로 피했지만, 이진 자료에서는 그럴 수 없습니다.

## 제5절. 길이 앞머리 방식

### 5.1 형식 정하기

```text
   +--------+--------+----------------+
   | 길이(4바이트, 네트워크 순서)      | 내용 |
   +--------+--------+----------------+
```

```c
#define MSG_MAX 65536           /* 바깥에서 온 길이의 상한 — 반드시 둔다 */

/* msg_send: 내용을 한 메시지로 보낸다. 성공하면 0, 실패하면 -1 */
int msg_send(int fd, const void *buf, size_t len);

/* msg_recv: 메시지 하나를 받는다.
   돌려주는 값은 받은 바이트 수, 0 이면 상대가 닫음, -1 은 오류. */
ssize_t msg_recv(int fd, void *buf, size_t cap);
```

### 5.2 보내기

```c
int msg_send(int fd, const void *buf, size_t len)
{
    uint32_t netlen;

    if (len > MSG_MAX) {
        errno = EMSGSIZE;
        return -1;
    }
    netlen = htonl((uint32_t) len);     /* 9강 4절 — 바이트 순서 */

    if (write_full(fd, &netlen, sizeof netlen) < 0)
        return -1;
    if (len > 0 && write_full(fd, buf, len) < 0)
        return -1;
    return 0;
}
```

**보내는 쪽에서도 상한을 검사합니다.** 실수로 거대한 값을 보내면 상대가 거절할 것이므로, 여기서 미리 막는 편이 낫습니다.

### 5.3 정확히 n바이트 읽기

```c
/* read_exact: n 바이트를 정확히 채운다. 1 성공, 0 상대가 닫음, -1 오류 */
static int read_exact(int fd, void *vbuf, size_t n)
{
    char *buf = vbuf;
    size_t done = 0;

    while (done < n) {
        ssize_t r = read(fd, buf + done, n - done);

        if (r < 0) {
            if (errno == EINTR)
                continue;
            return -1;
        }
        if (r == 0)
            return done == 0 ? 0 : -1;  /* 도중에 끊긴 것은 오류다 */
        done += (size_t) r;
    }
    return 1;
}
```

**세 가지 경우를 구분한 것**이 중요합니다.

| 상황 | 반환값 | 뜻 |
|---|---|---|
| 다 채웠다 | 1 | 정상 |
| **한 바이트도 못 읽고 끝** | **0** | **정상 종료** |
| **읽다가 끊김** | **−1** | **비정상** — 메시지가 잘렸다 |

세 번째를 0으로 처리하면 **잘린 메시지를 정상으로 오해**하게 됩니다.

### 5.4 확인

```bash
./framing_test good
```

```text
  보내는 쪽: 3·5·2바이트짜리 메시지 3개를 보냈습니다
  1번째 메시지: 3바이트 "AAA"
  2번째 메시지: 5바이트 "BBBBB"
  3번째 메시지: 2바이트 "CC"
  → 모두 3개의 메시지를 받았습니다
```

**4.1절에서 하나로 합쳐졌던 것이 셋으로 정확히 나뉘었습니다.** 같은 TCP 소켓인데도 그렇습니다.

## 제6절. 정수를 안전하게 주고받기

**9강 4.4절에서 미뤄 둔 이야기입니다.**

### 6.1 그대로 보내면 안 됩니다

```c
int count = 1000;
write(fd, &count, sizeof count);        /* 위험 */
```

| 무엇이 문제인가 |
|---|
| **바이트 순서**가 컴퓨터마다 다르다(9강 4절) |
| **크기**가 다를 수 있다(`long`은 32비트일 수도 64비트일 수도) |
| **패딩**이 구조체마다 다르다(1부 8강) |
| 부호 있는 정수의 표현 |

### 6.2 두 가지 방법

| 방법 | 장점 | 단점 |
|---|---|---|
| **고정 크기 + 네트워크 순서** | 작고 빠르다 | 사람이 못 읽는다 |
| **문자열** | 사람이 읽고 디버그하기 쉽다 | 크고 느리다 |

**이진 방법**은 이렇게 씁니다.

```c
#include <stdint.h>

uint32_t v = htonl((uint32_t) count);
msg_send(fd, &v, sizeof v);
```

| 반드시 지킬 것 |
|---|
| **`<stdint.h>`의 고정 크기 자료형**(`uint32_t` 등) |
| `hton*` / `ntoh*` 로 변환 |
| 구조체를 통째로 보내지 **않는다** |

### 6.3 구조체를 그대로 보내지 마십시오

```c
struct msg { uint8_t type; uint32_t value; };
write(fd, &m, sizeof m);            /* 위험 */
```

1부 8강 5절에서 배운 **패딩** 때문입니다. `sizeof(struct msg)`가 5가 아니라 8일 수 있고, 그 값은 컴파일러와 아키텍처마다 다릅니다.

**항목을 하나씩 정해진 순서로 쌓는 것**이 옳습니다.

```c
static size_t pack(unsigned char *out, uint8_t type, uint32_t value)
{
    uint32_t nv = htonl(value);

    out[0] = type;                  /* 1바이트 */
    memcpy(out + 1, &nv, 4);        /* 4바이트, 네트워크 순서 */
    return 5;                       /* 언제나 5바이트 */
}
```

**직렬화**(serialization)라 부르며, 실무에서는 Protocol Buffers·MessagePack 같은 라이브러리를 쓰기도 합니다.

### 6.4 64비트는 어떻게 하나

`htonll`은 표준이 아닙니다. 직접 만들거나 두 개의 32비트로 나눕니다.

```c
static void put_u64(unsigned char *p, uint64_t v)
{
    p[0] = (unsigned char) (v >> 56);   /* 큰 자리부터 — 네트워크 순서 */
    p[1] = (unsigned char) (v >> 48);
    p[2] = (unsigned char) (v >> 40);
    p[3] = (unsigned char) (v >> 32);
    p[4] = (unsigned char) (v >> 24);
    p[5] = (unsigned char) (v >> 16);
    p[6] = (unsigned char) (v >>  8);
    p[7] = (unsigned char) v;
}
```

**시프트와 마스크로 직접 쌓으면** 이 컴퓨터의 바이트 순서와 무관해집니다. 가장 확실한 방법입니다.

## 제7절. 길이를 믿으면 안 된다

**1부 10강의 신뢰 경계가 네트워크에서 어떻게 나타나는지 보는 절입니다.**

### 7.1 순진한 구현

```c
uint32_t len;

read_exact(fd, &len, 4);
len = ntohl(len);

buf = malloc(len);              /* 상대가 말한 대로 */
read_exact(fd, buf, len);
```

**무엇이 잘못되었습니까?**

### 7.2 공격

```c
        /* 공격자 흉내: 길이만 거대하게 적어 보낸다 */
        uint32_t huge = htonl(4000000000u);     /* 40억 바이트라고 주장 */

        if (write(sv[0], &huge, sizeof huge) < 0)
            perror("write");
```

**내용은 한 바이트도 보내지 않습니다.**

| 순진한 서버에 일어나는 일 |
|---|
| `malloc(4000000000)` — **4 GB를 요청** |
| 성공하면 메모리가 바닥난다 |
| 실패하면 `NULL`인데 검사를 안 했다면 **충돌** |
| 성공했어도 `read_exact`가 **영원히 기다린다** |

**4바이트를 보내는 것만으로 서버를 무너뜨릴 수 있습니다.**

### 7.3 방어

```c
    len = ntohl(netlen);

    /* 바깥에서 온 길이를 절대 믿지 않는다 — 1부 10강 신뢰 경계 */
    if (len > MSG_MAX || len > cap) {
        errno = EMSGSIZE;
        return -1;
    }
```

```bash
./framing_test evil
```

```text
  보내는 쪽: "내용이 40억 바이트" 라고만 적어 보냈습니다
  (내용은 한 바이트도 보내지 않았습니다)
  받는 쪽: 거절 — 길이가 한계를 넘습니다(EMSGSIZE)
  → 모두 0개의 메시지를 받았습니다
```

**두 줄의 검사로 막혔습니다.**

### 7.4 검사해야 할 것들

| 항목 | 검사 |
|---|---|
| **길이** | 상한(`MSG_MAX`)과 **내 버퍼 크기(`cap`)** 둘 다 |
| 종류·명령 번호 | 아는 값인가 |
| 문자열 | **끝 표시가 있는가**, 길이가 맞는가 |
| 숫자 | 범위 안인가 |
| 개수 | **곱셈이 넘치지 않는가**(1부 10강 5.2절) |

> **`len > MSG_MAX`만으로는 부족합니다.**
> 받는 쪽 버퍼가 `MSG_MAX`보다 작을 수 있습니다. **`len > cap`도 함께 검사**해야 합니다. 1부 10강의 "크기를 아는 자가 안전하다"가 그대로입니다.
{: .prompt-danger }

### 7.5 이것이 실제 취약점입니다

| 사례 유형 | 무슨 일 |
|---|---|
| 길이를 그대로 믿고 `malloc` | 메모리 고갈 |
| 길이를 그대로 믿고 `memcpy` | **버퍼 오버플로**(1부 10강) |
| 길이가 음수(부호 있는 형) | **거대한 값으로 변환**(1부 10강 5.1절) |
| 길이만 보내고 내용을 안 보냄 | 연결 자원 고갈 |

**세 번째가 특히 잘 숨습니다.** `int len`으로 받으면 `-1`이 `size_t`로 변환되며 거대한 값이 됩니다. **반드시 `uint32_t`로 받으십시오.**

## 제8절. 프로토콜 설계의 원칙

### 8.1 먼저 정해야 할 것들

| 항목 | 질문 |
|---|---|
| **프레이밍** | 하나의 메시지가 어디서 끝나는가 |
| **메시지 종류** | 어떤 명령이 있는가 |
| **인코딩** | 이진인가 글자인가 |
| **순서** | 누가 먼저 말하는가 |
| **오류** | 잘못을 어떻게 알리는가 |
| **판(version)** | 나중에 바꿀 수 있는가 |
| **한계** | 최대 크기·최대 개수 |

### 8.2 여섯 가지 원칙

**① 길이를 먼저, 그리고 상한을 둔다** (제5·7절)

**② 판 번호를 처음부터 넣는다**

```text
   +------+--------+--------+---------+
   | 판(1)| 종류(1)| 길이(4)| 내용     |
   +------+--------+--------+---------+
```

나중에 형식을 바꿔야 할 때, 판 번호가 없으면 **옛 프로그램과 새 프로그램을 구분할 수 없습니다.**

**③ 모르는 것은 거절한다**

```c
if (type > TYPE_MAX) {
    send_error(fd, "알 수 없는 종류");
    return -1;
}
```

"모르면 무시하고 넘어간다"는 관대함이 **보안 구멍**이 됩니다.

**④ 상태를 명확히 한다**

| 상태 | 허용되는 메시지 |
|---|---|
| 접속 직후 | 인사·인증만 |
| 인증 후 | 명령 |
| 종료 중 | 없음 |

**인증 전에 명령을 받아 처리하는 실수**가 흔합니다.

**⑤ 사람이 읽을 수 있으면 좋다**

디버깅이 훨씬 쉬워집니다. 성능이 정말 문제일 때만 이진으로 가십시오.

**⑥ 이미 있는 것을 먼저 찾는다**

HTTP·MQTT·gRPC 등 검증된 프로토콜이 많습니다. **직접 만드는 것은 마지막 선택**입니다.

### 8.3 우리 프로토콜의 한계

이번 강의의 `proto.c`에는 **판 번호도 종류도 없습니다.** 길이와 내용뿐입니다.

| 없는 것 | 왜 지금은 괜찮은가 |
|---|---|
| 판 번호 | 배우는 단계 |
| 메시지 종류 | 에코만 한다 |
| **인증** | **12~14강에서 넣는다** |
| **암호화** | **12강부터** |

**17강 종합 과제에서 이 모두를 갖춘 프로토콜을 완성합니다.**

## 제9절. 자원 고갈 막기

### 9.1 공격자가 노리는 것

| 자원 | 고갈시키는 법 | 방어 |
|---|---|---|
| **메모리** | 큰 길이를 주장 | **상한**(제7절) |
| **서술자** | 연결만 열고 아무것도 안 함 | **시간 제한**(10강 문제 8) |
| **연결 수** | 수만 개 접속 | **동시 접속 제한**(10강 문제 9) |
| CPU | 비싼 요청을 반복 | 요청 빈도 제한 |
| 대역폭 | 큰 자료를 요구 | 응답 크기 제한 |

### 9.2 최소한의 방어 목록

| 방어 | 어떻게 |
|---|---|
| 메시지 크기 상한 | `MSG_MAX` |
| **읽기 시간 제한** | `SO_RCVTIMEO` 또는 `epoll` 시간 제한 |
| 유휴 연결 정리 | 마지막 활동 시각 기록(10강 문제 8) |
| 동시 접속 상한 | 세어서 거절(10강 문제 9) |
| 주소별 연결 수 제한 | 한 곳에서 몰아치는 것을 막는다 |

```c
struct timeval tv = { 30, 0 };      /* 30초 안에 아무 말도 없으면 */

setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof tv);
```

### 9.3 느린 공격

> **한 바이트씩 아주 느리게 보내는 것**만으로 연결을 오래 붙들 수 있습니다.

`SO_RCVTIMEO`는 "아무것도 안 올 때"만 잡습니다. **조금씩 보내면 계속 갱신**됩니다.

| 추가 방어 | |
|---|---|
| **전체 시간 제한** | 요청 하나에 몇 초까지 |
| 최소 전송 속도 | 너무 느리면 끊는다 |

**17강에서 이 방어를 넣습니다.**

### 문제 3. 경계 소실 재현

세 번 나누어 보낸 것이 TCP에서는 한 번에, UDP에서는 세 번에 도착하는 것을 보이십시오.

### 문제 5. 길이 공격 막기

길이만 거대하게 적어 보내는 공격을 재현하고 막으십시오.

**정답 및 해설**

7.2·7.3절의 코드와 결과가 답입니다.

```text
  받는 쪽: 거절 — 길이가 한계를 넘습니다(EMSGSIZE)
```

- **검사를 지우고 실행해 보십시오.** `malloc(4000000000)`이 어떻게 되는지 직접 보십시오. 성공할 수도, `NULL`을 돌려줄 수도 있습니다. **어느 쪽이든 서버는 정상이 아닙니다.**
- `len > cap`도 함께 검사했는지 확인하십시오(7.4절).
- 길이를 `int`로 받아 음수를 넣어 보십시오. 1부 10강 5.1절의 부호 문제가 그대로 재현됩니다.

### 문제 6. 정수 주고받기

정수와 문자열이 섞인 메시지를 이식성 있게 주고받으십시오.

**정답 및 해설**

6.3절의 `pack` 방식이 답입니다.

```c
static size_t pack(unsigned char *out, uint8_t type, uint32_t value)
{
    uint32_t nv = htonl(value);

    out[0] = type;
    memcpy(out + 1, &nv, 4);
    return 5;                       /* 언제나 5바이트 */
}
```

- **`sizeof(struct)`를 쓰지 않은 것**이 핵심입니다. 패딩 때문에 값이 달라질 수 있습니다.
- 푸는 쪽에서도 같은 순서로 꺼내야 합니다. **보내는 코드와 받는 코드를 나란히 두고** 확인하십시오.
- 64비트가 필요하면 6.4절의 시프트 방식을 쓰십시오.

### 문제 7. 판 번호와 종류 넣기

`proto.c`를 확장해 **판 번호·메시지 종류**를 넣으십시오.

**정답 및 해설**

```text
   +------+--------+--------+---------+
   | 판(1)| 종류(1)| 길이(4)| 내용     |
   +------+--------+--------+---------+
```

```c
#define PROTO_VERSION 1

enum msg_type { MSG_HELLO = 1, MSG_DATA = 2, MSG_BYE = 3, MSG_ERROR = 4 };
```

```c
    if (hdr[0] != PROTO_VERSION) {
        errno = EPROTO;
        return -1;                  /* 모르는 판은 거절 */
    }
    if (hdr[1] < MSG_HELLO || hdr[1] > MSG_ERROR) {
        errno = EPROTO;
        return -1;                  /* 모르는 종류도 거절 */
    }
```

- **모르는 것은 거절**해야 합니다(8.2절 ③). 무시하고 넘어가면 나중에 형식을 바꿀 때 옛 프로그램이 이상하게 동작합니다.
- 판 번호를 **처음부터** 넣는 것이 중요합니다. 나중에 추가할 수는 없습니다.
- `EPROTO`는 프로토콜 오류를 뜻하는 `errno` 값입니다.

### 문제 8. 시간 제한 방어

아무 말 없이 연결만 붙들고 있는 상대를 끊으십시오.

**정답 및 해설**

```c
struct timeval tv = { 30, 0 };

setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof tv);
```

```c
    n = msg_recv(fd, buf, sizeof buf);
    if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
        fprintf(stderr, "30초 동안 아무 말이 없어 끊습니다\n");
        close(fd);
    }
```

- **`nc`로 접속만 하고 가만히 두어** 시험하십시오. 30초 뒤 끊겨야 합니다.
- 이 방어만으로는 **느린 공격을 못 막습니다**(9.3절). 한 바이트씩 29초마다 보내면 영원히 유지됩니다.
- 전체 시간 제한을 더하면 완전해집니다. 요청 하나를 받는 데 몇 초까지 허용할지 정하십시오.

### 문제 9. 프로토콜 문서 쓰기

만든 프로토콜을 **남이 구현할 수 있을 정도로** 문서화하십시오.

**정답 및 해설**

다음이 모두 있어야 합니다.

| 항목 | 내용 |
|---|---|
| 형식 그림 | 바이트 배치 |
| 각 항목의 크기와 **바이트 순서** | `uint32_t`, 네트워크 순서 |
| **한계값** | 최대 길이 65536 |
| 메시지 종류 표 | 번호와 뜻 |
| 대화 순서 | 누가 먼저, 어떤 순서로 |
| 오류 처리 | 잘못된 값을 받으면 무엇을 하는가 |
| 예시 | **실제 바이트 열** |

- **예시 바이트 열이 특히 중요합니다.** 글로만 쓰면 반드시 다르게 구현됩니다.

```text
"AAA" 를 보내는 메시지:
  00 00 00 03 41 41 41
  ^^^^^^^^^^^ ^^^^^^^^
  길이 3      "AAA"
```

- 1부 11강 6절에서 배운 **헤더가 곧 문서**라는 원칙이 프로토콜에도 적용됩니다.
- RFC를 한 편 훑어보십시오. 14강에서 읽을 [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846)이 좋은 본보기입니다.

### 문제 10. `nc`로 프로토콜 시험

우리 프로그램 없이 **손으로 만든 바이트**를 보내 서버를 시험하십시오.

**정답 및 해설**

```bash
printf '\x00\x00\x00\x03AAA' | nc -q1 c-srv 5000
```

**길이를 거짓으로 적어** 보십시오.

```bash
printf '\xff\xff\xff\xffAAA' | nc -q1 c-srv 5000
```

- 서버가 **거절하고 살아남아야** 합니다. 죽거나 멈추면 방어가 부족한 것입니다.
- 길이만 보내고 내용을 안 보내는 것도 시험하십시오.

```bash
printf '\x00\x00\x00\xff' | nc -q1 c-srv 5000
```

- **이것이 가장 기본적인 보안 시험**입니다. 정상 클라이언트만으로 시험하면 이런 경우를 영영 만나지 않습니다. 1부 12강 10.4절에서 CSV를 일부러 망가뜨려 시험한 것과 같은 방식입니다.

## 정리

| 구분 | 핵심 |
|---|---|
| UDP | 연결 없음·보장 없음·**경계 있음**. `sendto`/`recvfrom` |
| UDP의 함정 | 상대가 없어도 `sendto`는 성공한다 → **시간 제한 필수** |
| 고르는 기준 | **"늦게 온 자료가 가치가 있는가"** |
| **TCP 경계** | **없다.** 3번 보낸 것이 1번에 온다 |
| 프레이밍 | 구분자 / **길이 앞머리** / 고정 길이 / 연결 종료 |
| 길이 앞머리 | `uint32_t` + `htonl`, `read_exact`로 정확히 |
| `read_exact` | **0(정상 종료)과 −1(잘림)을 구분** |
| 정수 | 고정 크기 자료형 + 네트워크 순서. **구조체 통째로 금지** |
| **신뢰 경계** | **길이는 `MSG_MAX`와 `cap` 둘 다 검사** |
| 설계 원칙 | 길이 먼저·판 번호·모르는 것 거절·상태 관리 |
| 자원 방어 | 크기 상한·시간 제한·접속 수 제한 |
