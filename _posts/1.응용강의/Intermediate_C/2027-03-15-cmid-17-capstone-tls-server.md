## 제1절. 요구사항

### 1.1 만들 것

> **여러 명이 동시에 붙어도, 하나가 끊겨도, 신호를 받아도 무너지지 않는 TLS 서버.**

| 요구 | 확인 방법 |
|---|---|
| ① 동시 접속 **100대** 이상 | 100개를 한꺼번에 띄워 전원 성공 |
| ② **한 스레드**로 처리 | 스레드를 만들지 않는다 |
| ③ TLS 1.3만 허용 | 로그의 협상 결과 |
| ④ **메시지 경계 유지** | 길이 앞머리 프레이밍 |
| ⑤ 잘못된 프레임 **거절** | 길이 `0xFFFFFFFF` 를 보내 본다 |
| ⑥ 검증 실패 클라이언트 **차단** | 다른 CA로 접속 |
| ⑦ **우아한 종료** | `SIGTERM`에 정리 후 통계 출력 |
| ⑧ 자원 누수 없음 | `/proc/PID/fd` 개수(16강 7.4절) |

### 1.2 왜 스레드를 쓰지 않는가

7강에서 스레드를 배웠습니다. 접속마다 스레드를 만들면 코드가 단순해집니다. **그런데도 `epoll`을 쓰는 이유**는 10강에서 배웠습니다.

| | 접속마다 스레드 | **`epoll` 한 스레드** |
|---|---|---|
| 접속 1만 개 | 스택만 80GB | **문제없다** |
| 문맥 교환 | 많다(16강 8.2절) | 적다 |
| 경쟁 상태 | **걱정해야 한다**(8강) | **없다** |
| 코드 | 단순 | **복잡** |

**오늘은 복잡한 쪽을 택합니다.** 실무의 고성능 서버가 이 구조이기 때문입니다.

## 제2절. 설계 — 계층과 상태

### 2.1 계층

```text
   응용 (에코)
        │  handle_frame
   ┌────▼──────────────────┐
   │  프레이밍 (11강)        │  try_frames / queue_out
   └────┬──────────────────┘
        │  SSL_read / SSL_write
   ┌────▼──────────────────┐
   │  TLS (15강)            │  SSL_accept
   └────┬──────────────────┘
        │  논블로킹 소켓
   ┌────▼──────────────────┐
   │  epoll (10강)          │  epoll_wait
   └───────────────────────┘
```

**12강 8.1절에서 그린 층 구조와 같습니다.** 그때 손으로 만든 암호 계층 자리에 TLS가 들어갔습니다.

### 2.2 연결마다 상태가 필요합니다

**블로킹 방식이라면** 이렇게 쓸 수 있습니다.

```c
SSL_accept(ssl);            /* 끝날 때까지 기다린다 */
SSL_read(ssl, ...);
SSL_write(ssl, ...);
```

**논블로킹에서는 불가능합니다.** 각 단계가 **"아직"** 을 돌려주고 나갔다가 다시 들어옵니다.

> **그래서 "지금 어디까지 했는지"를 연결마다 기억**해야 합니다. 이것이 **상태 기계**입니다.
>
> 10강에서 `epoll`을 배울 때는 자료를 그냥 되돌려 보내면 되었습니다. **TLS가 들어오면 훨씬 복잡해집니다.** 핸드셰이크 자체가 여러 번에 나뉘기 때문입니다.
{: .prompt-warning }

### 2.3 상태 두 가지

```c
/* ---- 연결 상태 ---- */
enum st { ST_HANDSHAKE, ST_READY };
```

```text
   접속 ──▶ ST_HANDSHAKE ──(SSL_accept 성공)──▶ ST_READY ──▶ 종료
                │                                   │
                └────(실패)────▶ 종료 ◀─────────────┘
```

**핸드셰이크가 여러 번에 걸쳐 진행되는 동안 `ST_HANDSHAKE`에 머뭅니다.**

## 제3절. 연결 상태 구조체

```c
struct conn {
    int      fd;
    SSL     *ssl;
    enum st  state;
    char     peer[64];

    /* 들어오는 프레임 (11강: 4바이트 길이 앞머리) */
    unsigned char inbuf[4 + MSG_MAX];
    size_t   inlen;

    /* 나가는 자료 — 한 번에 다 못 보낼 때를 위해 (11강 3절) */
    unsigned char out[OUTBUF];
    size_t   outlen;
    size_t   outoff;
    int      want_write;        /* SSL 이 쓰기 대기를 요구했는가 */
    int      closing;
};
```

### 3.1 각 항목이 왜 필요한가

| 항목 | 왜 |
|---|---|
| `inbuf`/`inlen` | **프레임이 한 번에 안 온다**(11강 2절) |
| `outbuf`/`outlen`/`outoff` | **한 번에 다 못 보낸다**(11강 3절) |
| `want_write` | TLS가 **쓰기 준비**를 기다릴 수 있다(15강 8.2절) |
| `closing` | 상대가 끝냈지만 **보낼 것이 남았다** |
| `peer` | 로그용 |

### 3.2 서술자로 찾습니다

```c
static struct conn *conns[MAX_CONN];
```

**서술자 번호가 배열의 색인**입니다. 2강 3절의 **"가장 작은 빈 번호"** 규칙 덕분에 번호가 촘촘하게 유지되어 이 방식이 통합니다.

```c
                    if (cfd >= MAX_CONN) { close(cfd); continue; }
```

**한계를 반드시 검사하십시오.** 배열 밖을 쓰면 1부 8강에서 배운 그 사고가 납니다.

## 제4절. 상태 기계 — 어려운 부분

**이 절이 이번 과제의 핵심입니다.**

### 4.1 하나의 함수로 모읍니다

```c
static void drive(struct conn *c)
```

**"이 연결을 할 수 있는 데까지 진행시켜라"** 라는 뜻입니다. `epoll`이 깨울 때마다 이 함수를 부릅니다.

### 4.2 ① 핸드셰이크

```c
    if (c->state == ST_HANDSHAKE) {
        int r = SSL_accept(c->ssl);

        if (r == 1) {
            c->state = ST_READY;
            printf("  [%s] 핸드셰이크 완료 — %s / %s\n", c->peer,
                   SSL_get_version(c->ssl), SSL_get_cipher(c->ssl));
            fflush(stdout);
        } else {
            switch (SSL_get_error(c->ssl, r)) {
            case SSL_ERROR_WANT_READ:
                ep_mod(c, 1, 0);
                return;
            case SSL_ERROR_WANT_WRITE:
                ep_mod(c, 0, 1);
                return;
            default:
                printf("  [%s] 핸드셰이크 실패\n", c->peer);
                ...
```

| 반환 | 뜻 | 할 일 |
|---|---|---|
| 1 | 완료 | `ST_READY`로 |
| `WANT_READ` | **상대의 자료를 더 기다린다** | 읽기 대기 등록 |
| `WANT_WRITE` | **보낼 자리가 없다** | **쓰기 대기 등록** |
| 그 외 | 실패 | 끊는다 |

> **`SSL_accept`를 여러 번 부르게 됩니다.**
> 14강 6.2절에서 본 핸드셰이크 메시지가 여러 번 오갑니다. 논블로킹에서는 **한 번에 다 진행되지 않습니다.** `WANT_READ`가 오면 나갔다가, `epoll`이 다시 깨우면 **같은 자리에서 이어서** 진행합니다. OpenSSL이 내부 상태를 기억해 줍니다.
{: .prompt-tip }

### 4.3 ② 밀린 출력 먼저

```c
    /* 먼저 밀린 출력을 내보낸다 */
    if (c->outlen > c->outoff) {
        int f = flush_out(c);

        if (f < 0) { conn_close(c); return; }
        if (f > 0) { ep_mod(c, 1, c->want_write); return; }
    }
```

**읽기 전에 쓰기를 먼저** 합니다. 안 그러면 출력 대기열이 계속 쌓입니다.

### 4.4 ③ 읽고 프레임 꺼내기

```c
        n = SSL_read(c->ssl, c->inbuf + c->inlen,
                     (int) (sizeof c->inbuf - c->inlen));
        if (n > 0) {
            c->inlen += (size_t) n;
            if (try_frames(c) != 0) {
                printf("  [%s] 잘못된 프레임 — 끊습니다\n", c->peer);
                ...
            }
            continue;
        }
```

**`n > 0`이면 계속 반복**합니다. 논블로킹에서는 **`WANT_READ`가 나올 때까지 다 읽어야** 합니다. 남겨 두면 `epoll`이 다시 안 깨워 줄 수 있습니다.

### 4.5 ④ 프레임 꺼내기 — 11강 그대로

```c
/* try_frames: inbuf 에서 완성된 프레임을 모두 꺼낸다 */
static int try_frames(struct conn *c)
{
    for (;;) {
        uint32_t nl, len;

        if (c->inlen < 4)
            return 0;
        memcpy(&nl, c->inbuf, 4);
        len = ntohl(nl);
        if (len > MSG_MAX)                  /* 11강 5절: 반드시 검사 */
            return -1;
        if (c->inlen < 4 + len)
            return 0;                       /* 아직 덜 왔다 */

        if (handle_frame(c, c->inbuf + 4, len) != 0)
            return -1;

        memmove(c->inbuf, c->inbuf + 4 + len, c->inlen - (4 + len));
        c->inlen -= 4 + len;
    }
}
```

| 검사 | 왜 |
|---|---|
| `inlen < 4` | **길이조차 안 왔다** |
| **`len > MSG_MAX`** | **공격자가 큰 수를 보낼 수 있다**(11강 5절) |
| `inlen < 4 + len` | 몸통이 덜 왔다 |

> **`len > MSG_MAX` 검사가 없으면 어떻게 되겠습니까?**
> `0xFFFFFFFF`(약 42억)를 보내면 프로그램이 그만큼 기다리거나, 계산이 넘쳐 엉뚱한 곳을 읽습니다. **1부 10강에서 배운 "입력을 믿지 말라"** 가 여기 있습니다. 제6절에서 실제로 시험합니다.
{: .prompt-danger }

### 4.6 ⑤ 부분 전송 처리

```c
/* flush_out: 쌓인 것을 내보낸다. 0=다 보냄, 1=더 있음, -1=오류 */
static int flush_out(struct conn *c)
{
    while (c->outoff < c->outlen) {
        int n = SSL_write(c->ssl, c->out + c->outoff,
                          (int) (c->outlen - c->outoff));

        if (n > 0) {
            c->outoff += (size_t) n;
            continue;
        }
        switch (SSL_get_error(c->ssl, n)) {
        case SSL_ERROR_WANT_WRITE:
            c->want_write = 1;
            return 1;
        case SSL_ERROR_WANT_READ:
            /* 논블로킹 TLS 에서는 쓰기 중에도 읽기가 필요할 수 있다 */
            c->want_write = 0;
            return 1;
        default:
            return -1;
        }
    }
    c->outlen = c->outoff = 0;
    c->want_write = 0;
    return 0;
}
```

**`SSL_write`가 `WANT_READ`를 돌려줄 수 있습니다.** 쓰는 중인데 읽기를 기다린다는 뜻입니다. 이상해 보이지만 TLS에서는 정상입니다(15강 8.2절).

### 4.7 ⑥ 다음에 무엇을 기다릴지 등록

```c
        ep_mod(c, 1, c->want_write || (c->outlen > c->outoff));
```

**읽기는 항상, 쓰기는 필요할 때만** 기다립니다.

> **쓰기를 늘 기다리면 안 됩니다.**
> 보낼 것이 없는데 `EPOLLOUT`을 등록하면, 소켓이 거의 항상 쓸 수 있으므로 `epoll_wait`가 **쉬지 않고 깨어납니다.** CPU를 100% 먹는 흔한 실수입니다.
{: .prompt-warning }

### 4.8 버퍼 설정

```c
    /* 논블로킹에서 같은 버퍼가 아니어도 되도록 (15강 8.2절 참고) */
    SSL_CTX_set_mode(ctx, SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER |
                          SSL_MODE_ENABLE_PARTIAL_WRITE);
```

| 설정 | 뜻 |
|---|---|
| `ACCEPT_MOVING_WRITE_BUFFER` | 재시도할 때 **버퍼 주소가 달라도 된다** |
| `ENABLE_PARTIAL_WRITE` | **일부만 보내고 돌아와도 된다** |

**둘 다 없으면** 15강 8.2절의 제약을 엄격히 지켜야 합니다. 우리는 `outoff`로 진행 위치를 관리하므로 켜는 편이 편합니다.

## 제5절. 시그널과 우아한 종료

### 5.1 자기 파이프 기법

**5강에서 배운 방법**입니다.

```c
static void on_signal(int sig)
{
    int saved = errno;
    char c = (char) sig;

    stop_flag = 1;
    /* 처리기 안에서는 async-signal-safe 한 것만 (5강 6절) */
    if (write(sigpipe[1], &c, 1) < 0) {
        /* 처리기 안에서는 보고할 방법이 없다. stop_flag 로 충분하다 */
    }
    errno = saved;
}
```

| 지킨 것 | 어디서 |
|---|---|
| `volatile sig_atomic_t` | 5강 4절 |
| **`errno` 저장·복원** | 5강 6절 |
| `write`만 사용 | 5강 6절 — 안전한 함수 |
| **파이프로 주 반복문에 알림** | 5강 8절 |

### 5.2 `epoll`이 파이프를 감시합니다

```c
    ev.data.fd = sigpipe[0];
    epoll_ctl(epfd, EPOLL_CTL_ADD, sigpipe[0], &ev);
```

```c
            if (fd == sigpipe[0]) {
                char c;

                while (read(sigpipe[0], &c, 1) > 0)
                    ;
                stop_flag = 1;
                break;
            }
```

> **왜 `stop_flag`만으로 안 되는가?**
> `epoll_wait`가 `-1`(무한 대기)로 자고 있으면, 깃발만 세워서는 깨어나지 않습니다. **시그널이 `epoll_wait`를 `EINTR`로 깨우기는 하지만**, 파이프에 써 두면 확실하고 **어느 시그널이었는지도** 알 수 있습니다.
{: .prompt-tip }

### 5.3 `EINTR` 처리

```c
        if (n < 0) {
            if (errno == EINTR) continue;       /* 5강 */
            break;
        }
```

**5강 3절에서 배운 그것**입니다.

### 5.4 `SIGPIPE` 무시

```c
    signal(SIGPIPE, SIG_IGN);           /* 9강: 끊긴 소켓에 쓰면 죽는다 */
```

**이 한 줄이 없으면** 상대가 먼저 끊었을 때 서버가 조용히 죽습니다. 9강에서 배운 함정입니다.

### 5.5 정리

```c
    printf("\n종료 신호를 받았습니다. 정리합니다...\n");
    {
        int i;

        for (i = 0; i < MAX_CONN; i++)
            if (conns[i] != NULL) conn_close(conns[i]);
    }
    close(lfd);
    ...
    printf("총 접속 %ld건, 메시지 %ld개를 처리했습니다.\n",
           total_accepted, total_msgs);
```

**모든 연결에 `SSL_shutdown`을 보내고 닫습니다.** 상대가 "잘렸다"고 오해하지 않게 하기 위해서입니다(15강 8.4절).

## 제7절. 성능과 한계

### 7.1 무엇이 병목인가

| 자원 | 한계 |
|---|---|
| **서술자** | `ulimit -n`(10강·16강 8.4절) |
| 메모리 | 연결마다 `struct conn` ≈ 80KB |
| **CPU** | **TLS 핸드셰이크**(13강 8절) |
| 대역폭 | |

**우리 구조체는 크기가 큽니다.**

```c
    unsigned char inbuf[4 + MSG_MAX];   /* 16KB */
    unsigned char out[OUTBUF];          /* 64KB */
```

**연결 1만 개면 800MB**입니다. 실무에서는 필요할 때만 버퍼를 잡습니다(실습문제 3).

### 7.2 핸드셰이크가 비쌉니다

13강 8.1절에서 **공개키 연산이 초당 수만 회**임을 측정했습니다. 접속이 몰리면 여기가 먼저 막힙니다.

| 완화 | |
|---|---|
| **세션 재개** | 이미 한 연결의 결과 재사용 |
| 연결 유지 | 한 연결로 여러 요청 |
| 여러 프로세스 | `SO_REUSEPORT` |

### 7.3 한 스레드의 약점

**한 연결의 처리가 오래 걸리면 나머지가 전부 멈춥니다.**

| 위험 | 예 |
|---|---|
| 오래 걸리는 계산 | |
| **블로킹 호출** | 파일 읽기, DNS 조회 |
| 큰 자료 처리 | |

**해결**은 무거운 일을 **작업자 스레드 풀**(7강)로 보내는 것입니다. `epoll` 반복문은 **절대 막히면 안 됩니다.**

### 7.4 실무의 구조

| 구조 | 예 |
|---|---|
| `epoll` + 작업자 풀 | 대부분의 서버 |
| **CPU마다 `epoll` 반복문** | `SO_REUSEPORT` |
| 비동기 프레임워크 | libuv, libevent |

**우리가 만든 것이 그 뼈대**입니다.

### 문제 3. 버퍼를 필요할 때만 잡기

`struct conn`이 80KB나 됩니다. **줄이십시오.**

**정답 및 해설**

```c
struct conn {
    ...
    unsigned char *inbuf;
    size_t incap, inlen;
```

```c
/* need_in: 필요한 만큼 늘린다 */
static int need_in(struct conn *c, size_t want)
{
    unsigned char *n;

    if (c->incap >= want) return 0;
    if (want > 4 + MSG_MAX) return -1;      /* 한계는 그대로 */
    n = realloc(c->inbuf, want);
    if (n == NULL) return -1;
    c->inbuf = n; c->incap = want;
    return 0;
}
```

- 처음에는 **작게**(예: 4KB) 잡고, 큰 프레임이 오면 늘립니다.
- **한계 검사는 그대로 두어야** 합니다. 늘릴 수 있다고 무제한이 되면 안 됩니다.
- `free`를 `conn_close`에 추가하십시오. **valgrind로 확인**하십시오.
- 16강에서 배운 대로 **잡는 것과 쓰는 것은 다릅니다.** 그래도 구조체가 작아지면 관리가 쉬워집니다.

### 문제 4. 한가한 연결 끊기

일정 시간 아무것도 안 보내는 연결을 끊으십시오.

**정답 및 해설**

```c
    time_t last_active;
```

```c
    /* epoll_wait 에 시간 제한을 준다 */
    int n = epoll_wait(epfd, evs, MAX_EVENTS, 1000);
```

```c
    /* 주기적으로 훑는다 */
    now = time(NULL);
    for (i = 0; i < MAX_CONN; i++)
        if (conns[i] != NULL && now - conns[i]->last_active > IDLE_SEC)
            conn_close(conns[i]);
```

- **`-1`(무한 대기)을 시간 제한으로 바꾸어야** 주기적인 일을 할 수 있습니다.
- **이것이 없으면 자원 고갈 공격에 취약**합니다. 연결만 열어 두고 아무것도 안 보내는 공격이 있습니다.
- 연결이 많으면 매번 전체를 훑는 것은 비효율입니다. **시간순 목록**을 두면 낫습니다.

### 문제 5. 명령 프로토콜

에코 대신 간단한 명령을 처리하게 하십시오.

**정답 및 해설**

```text
   PING            → PONG
   TIME            → 현재 시각
   ECHO <내용>      → <내용>
   STAT            → 접속 수·메시지 수
   QUIT            → 연결 종료
```

- **11강에서 배운 대로** 프레임 안의 내용을 해석합니다.
- **알 수 없는 명령은 오류를 돌려주고 끊지 마십시오.** 다만 **너무 많으면** 끊는 것이 좋습니다.
- `STAT`은 `total_accepted`·`total_msgs`를 돌려줍니다.
- **입력 검사를 잊지 마십시오.** 길이, 문자, 인자 개수.

### 문제 6·7. 접속 제한과 작업자 풀

동시 접속 수를 제한하고, 무거운 일을 **작업자 스레드**로 넘기십시오.

**정답 및 해설**

```c
    if (live >= MAX_LIVE) {
        close(cfd);                 /* 또는 거절 메시지를 보내고 닫는다 */
        continue;
    }
```

작업자 풀은 7강의 방식을 씁니다.

```text
   epoll 반복문 ──(작업 큐)──▶ 작업자 스레드 N개
        ▲                              │
        └──────(eventfd 로 알림)────────┘
```

- **결과를 어떻게 돌려주는가**가 어려운 부분입니다. `eventfd`나 파이프로 `epoll` 반복문을 깨웁니다.
- **작업 큐는 여러 스레드가 만지므로** 뮤텍스와 조건 변수가 필요합니다(7강 6절).
- **8강의 도구로 검사하십시오.**

```bash
gcc -Wall -Wextra -std=gnu17 -fsanitize=thread tlsmux.c -o tlsmux_tsan -lssl -lcrypto
```

- WSL에서 TSan이 실패하면 `setarch $(uname -m) -R`를 앞에 붙이십시오(8강 문제 10, 16강 3.3절).
- **`SSL` 객체를 여러 스레드가 동시에 만지면 안 됩니다.** 한 연결은 한 스레드만 다루도록 하십시오.

## 정리

| 구분 | 핵심 |
|---|---|
| 구조 | `epoll` 한 스레드 + 연결마다 **상태 기계** |
| 계층 | 응용 → 프레이밍 → TLS → 소켓 |
| 상태 | `ST_HANDSHAKE` → `ST_READY` |
| **핸드셰이크** | **`SSL_accept`를 여러 번 부른다** |
| `WANT_READ/WRITE` | **어느 쪽을 기다릴지** `epoll`에 등록 |
| 읽기 | **`WANT_READ`가 나올 때까지** 반복 |
| 프레임 | 11강 그대로. **길이 검사 필수** |
| 부분 전송 | `outoff`로 진행 위치 관리 |
| **쓰기 등록** | **필요할 때만.** 늘 켜면 CPU 100% |
| 시그널 | **자기 파이프** + `EINTR` + `SIGPIPE` 무시 |
| 종료 | 모든 연결 정리 후 통계 |
| **검증 결과** | 동시 **100대**, 메시지 **500개**, 누락 0 |
| 안전 | **검증 실패 차단**, **잘못된 프레임 차단** |
| 한계 | 서술자·메모리·**핸드셰이크 CPU** |
| 주의 | **반복문이 막히면 전부 멈춘다** |
| **과정 전체** | **9강의 평문에서 시작해 여기까지 왔다** |
