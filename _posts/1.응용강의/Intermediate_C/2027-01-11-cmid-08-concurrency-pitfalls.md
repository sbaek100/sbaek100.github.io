## 제1절. 교착 상태를 만들어 본다

### 1.1 서로가 서로를 기다린다

> **교착 상태(deadlock)**: 두 흐름이 각자 상대가 가진 것을 기다리며 **영원히 멈추는** 상태.

자물쇠가 둘이고 스레드가 둘이면 곧바로 만들 수 있습니다.

| 시각 | 1번 스레드 | 2번 스레드 |
|---|---|---|
| 1 | **A를 잡는다** | |
| 2 | | **B를 잡는다** |
| 3 | B를 기다린다 → **막힘** | |
| 4 | | A를 기다린다 → **막힘** |

**둘 다 상대가 놓기를 기다리는데, 상대도 나를 기다립니다.**

### 1.2 코드

```c
/* lock_two: 두 자물쇠를 순서대로 잠그고 일한 뒤 푼다 */
static void lock_two(pthread_mutex_t *first, pthread_mutex_t *second,
                     const char *name)
{
    pthread_mutex_lock(first);
    printf("  [%s] 첫 번째 자물쇠를 잡았습니다\n", name);
    fflush(stdout);
    usleep(100000);                 /* 상대가 끼어들 틈을 만든다 */

    pthread_mutex_lock(second);
    printf("  [%s] 두 번째 자물쇠도 잡았습니다 — 일을 마칩니다\n", name);
    fflush(stdout);

    pthread_mutex_unlock(second);
    pthread_mutex_unlock(first);
}
```

```c
static void *worker1(void *arg) { ... lock_two(&A, &B, "1번"); ... }   /* A → B */
static void *worker2(void *arg) { ... lock_two(&B, &A, "2번"); ... }   /* B → A */
```

**두 함수는 같은 코드이고, 인자 순서만 다릅니다.**

### 1.3 실행

```bash
gcc -Wall -Wextra -std=gnu17 -pthread deadlock.c -o deadlock
```

```bash
./deadlock bad
```

```text
bad  판: 1번은 A→B, 2번은 B→A (역순)
  [1번] 첫 번째 자물쇠를 잡았습니다
  [2번] 첫 번째 자물쇠를 잡았습니다
>> 3초가 지나도 끝나지 않았습니다 — 교착 상태입니다
>> (1번 완료 0, 2번 완료 0)
```

**"두 번째 자물쇠도 잡았습니다"가 한 번도 나오지 않았습니다.** 둘 다 첫 번째만 잡은 채 멈췄습니다.

> **영원히 기다리지 않도록 3초 감시를 넣었습니다.**
> 그러지 않으면 시험 자체가 끝나지 않습니다. 6강 3.2절에서 파이프 실험에 `alarm`을 걸었던 것과 같은 설계입니다. **멈추는 것을 보여 주는 실험에는 반드시 탈출구가 필요합니다.**
{: .prompt-tip }

### 1.4 관찰하는 법

교착이 의심되면 프로세스를 들여다봅니다.

```bash
./deadlock bad & sleep 1 ; cat /proc/$!/task/*/stack 2>/dev/null | head
```

더 쉬운 방법은 `gdb`로 붙는 것입니다.

```bash
gdb -p <PID> -batch -ex "thread apply all bt" 2>/dev/null | head -30
```

**모든 스레드가 `pthread_mutex_lock`에서 멈춰 있으면** 교착입니다.

| 증상 | |
|---|---|
| CPU 사용률이 **0%** | 바쁘게 도는 것이 아니라 자고 있다 |
| 아무 진전이 없다 | 로그가 멈춘다 |
| 스택이 전부 `lock`에 있다 | 결정적 증거 |

**CPU가 0%인 것이 중요합니다.** 무한 반복(CPU 100%)과 교착(CPU 0%)은 증상이 정반대입니다.

## 제2절. 교착의 네 조건

### 2.1 넷이 모두 갖춰져야 일어난다

| 조건 | 뜻 | 깨는 방법 |
|---|---|---|
| **상호 배제** | 한 번에 하나만 쓸 수 있다 | 자물쇠를 안 쓴다(제7절 원자적 연산) |
| **점유하고 기다림** | 하나를 쥔 채 다른 것을 기다린다 | **한꺼번에 잡거나, 못 잡으면 놓는다** |
| **뺏을 수 없음** | 남이 쥔 것을 강제로 못 뺏는다 | `trylock`으로 스스로 놓는다 |
| **순환 대기** | A→B→…→A 로 고리가 생긴다 | **잠금 순서를 정한다**(제3절) |

**넷 중 하나만 깨면 교착은 일어나지 않습니다.** 실무에서 가장 널리 쓰는 것은 **순환 대기를 없애는 것**입니다.

### 2.2 방법 ① 순서를 통일한다

```c
static void *worker2(void *arg) { ... lock_two(&A, &B, "2번"); ... }   /* A → B 로 통일 */
```

```bash
./deadlock good
```

```text
good 판: 1번은 A→B, 2번은 A→B (같은 순서)
  [1번] 첫 번째 자물쇠를 잡았습니다
  [1번] 두 번째 자물쇠도 잡았습니다 — 일을 마칩니다
  [2번] 첫 번째 자물쇠를 잡았습니다
  [2번] 두 번째 자물쇠도 잡았습니다 — 일을 마칩니다
>> 둘 다 끝났습니다
```

**코드 한 글자만 바뀌었는데 교착이 사라졌습니다.**

### 2.3 방법 ② 못 잡으면 물러선다

```c
/* lock_two_try: 두 번째를 못 잡으면 첫 번째도 놓고 다시 시도한다 */
static void lock_two_try(pthread_mutex_t *first, pthread_mutex_t *second,
                         const char *name)
{
    int tries = 0;

    for (;;) {
        pthread_mutex_lock(first);
        if (pthread_mutex_trylock(second) == 0)
            break;                  /* 둘 다 잡았다 */

        pthread_mutex_unlock(first);    /* 물러선다 */
        tries++;
        usleep(10000 + (unsigned) (tries * 1000));
    }
    ...
}
```

```bash
./deadlock try
```

```text
try  판: 1번은 A→B, 2번은 B→A 지만 물러선다
  [1번] 0번 물러선 뒤 둘 다 잡았습니다
  [2번] 0번 물러선 뒤 둘 다 잡았습니다
>> 둘 다 끝났습니다
```

**순서가 여전히 반대인데도 교착이 없습니다.** 못 잡으면 쥔 것을 놓기 때문입니다.

> **이 실행에서는 "0번 물러선" 것으로 나왔습니다.** 마침 경합이 일어나지 않은 것입니다. 여러 번 실행하거나 스레드를 늘리면 물러서는 횟수가 올라갑니다. **동시성 실험은 한 번의 결과로 판단하면 안 됩니다**(7강 문제 3의 그 원칙).
{: .prompt-info }

### 2.4 두 방법의 비교

| | 순서 통일 | `trylock` 물러서기 |
|---|---|---|
| 성능 | **좋다** | 물러선 만큼 낭비 |
| 구현 | 규칙만 지키면 된다 | 다시 시도 논리가 필요 |
| 한계 | **순서를 정할 수 없을 때** 못 쓴다 | 언제나 쓸 수 있다 |
| 위험 | — | **활동 정지**(livelock) |

> **활동 정지(livelock)**: 둘 다 계속 물러섰다 다시 잡기를 반복하며 **아무도 전진하지 못하는** 상태. 교착과 달리 CPU는 바쁘게 돕니다. 그래서 위 코드에서 물러설 때마다 기다리는 시간을 **조금씩 늘렸습니다**(`tries * 1000`). 이를 지수 후퇴라 하며, 11강 네트워크 재시도에서도 같은 기법을 씁니다.
{: .prompt-warning }

## 제3절. 잠금 순서 통일

### 3.1 규칙을 정합니다

> **모든 코드가 자물쇠를 **같은 순서**로 잡는다.**

순서를 정하는 방법은 여러 가지입니다.

| 방법 | 예 |
|---|---|
| **이름순** | `account_a` 다음 `account_b` |
| **주소순** | 포인터 값이 작은 것부터 |
| 계층 번호 | 자물쇠마다 등급을 매기고 낮은 것부터 |

### 3.2 주소순으로 잡기

대상이 실행 중에 정해지면(계좌 이체 등) 주소를 기준으로 삼는 것이 편합니다.

```c
/* transfer: 두 계좌를 안전하게 잠근다 — 주소가 작은 쪽을 먼저 */
static void lock_ordered(pthread_mutex_t *x, pthread_mutex_t *y)
{
    if (x == y) {                   /* 같은 자물쇠면 한 번만 */
        pthread_mutex_lock(x);
        return;
    }
    if (x < y) {
        pthread_mutex_lock(x);
        pthread_mutex_lock(y);
    } else {
        pthread_mutex_lock(y);
        pthread_mutex_lock(x);
    }
}
```

**`x == y`를 먼저 걸러 내야 합니다.** 같은 자물쇠를 두 번 잠그면 자기 자신을 기다려 멈춥니다. 이것을 **자기 교착**이라 합니다.

### 3.3 잠금 계층

큰 프로그램에서는 자물쇠마다 등급을 정해 둡니다.

| 등급 | 자물쇠 | 규칙 |
|---|---|---|
| 1 | 전체 목록 | |
| 2 | 항목별 자물쇠 | **1을 쥔 채 2를 잡는 것은 허용** |
| 3 | 통계 | **낮은 등급을 쥔 채 높은 등급을 잡는 것만 허용** |

**역방향(3을 쥔 채 1을 잡기)이 금지**됩니다. 이 규칙만 지키면 순환이 생길 수 없습니다.

### 3.4 도구의 도움

```bash
gcc -Wall -Wextra -std=gnu17 -pthread -fsanitize=thread deadlock.c -o dl_tsan
```

**ThreadSanitizer**는 경쟁 상태와 잠금 순서 위반을 실행 중에 잡아 줍니다. 1부 10강 9.2절에서 배운 위생 검사기의 스레드용 판입니다.

| 검사기 | 잡는 것 |
|---|---|
| `-fsanitize=thread` | **경쟁 상태**, 잠금 순서 뒤바뀜 |
| `-fsanitize=address` | 메모리 오류(1부 10강) |

> 두 검사기는 **함께 쓸 수 없습니다.** 따로 빌드해 각각 돌려야 합니다. 속도가 크게 느려지므로 개발·시험 중에만 켭니다.
{: .prompt-info }

## 제4절. 재진입과 스레드 안전성

### 4.1 두 개념은 다릅니다

| 용어 | 뜻 | 언제 문제인가 |
|---|---|---|
| **재진입 가능**(reentrant) | 실행 도중 **다시 불려도** 괜찮다 | 시그널 처리기(5강 5절) |
| **스레드 안전**(thread-safe) | **여러 스레드가 동시에** 불러도 괜찮다 | 이번 강의 |

**둘은 겹치지만 같지 않습니다.** 뮤텍스로 지킨 함수는 스레드 안전하지만 재진입 가능하지는 않습니다. 시그널 처리기에서 부르면 자기 자신이 쥔 자물쇠를 기다려 멈추기 때문입니다.

| 함수의 성질 | 스레드에서 | 시그널 처리기에서 |
|---|---|---|
| 둘 다 아님(`strtok`) | 위험 | 위험 |
| 스레드 안전(뮤텍스로 보호) | 안전 | **위험**(자기 교착) |
| 재진입 가능(`write`) | 안전 | 안전 |

### 4.2 왜 안전하지 않은가

**함수가 상태를 기억하면** 위험합니다.

```c
char *tok = strtok(line, " ");      /* 첫 호출 */
while ((tok = strtok(NULL, " ")))   /* NULL — "이어서" 라는 뜻 */
    ...
```

`strtok(NULL, ...)`은 **"지난번에 어디까지 했는지"** 를 기억하고 있어야 합니다. 그 기억을 **함수 안의 정적 변수** 하나에 두었기 때문에, 스레드 둘이 동시에 쓰면 서로의 위치를 덮어씁니다.

### 4.3 실험

`strtok_race.c`는 각 스레드가 `"0-a 0-b 0-c"`처럼 **자기 번호가 붙은** 낱말을 나누고, 다른 번호가 섞여 나오면 오류로 셉니다.

```c
        if (use_safe) {
            char *save = NULL;

            for (tok = strtok_r(line, " ", &save); tok != NULL;
                 tok = strtok_r(NULL, " ", &save)) { ... }
        } else {
            for (tok = strtok(line, " "); tok != NULL;
                 tok = strtok(NULL, " ")) { ... }
        }
```

```bash
./strtok_race bad ; ./strtok_race bad ; ./strtok_race bad
```

```text
strtok   | 스레드 4 × 2000회 | 잘못 나뉜 횟수 = 3684
strtok   | 스레드 4 × 2000회 | 잘못 나뉜 횟수 = 3403
strtok   | 스레드 4 × 2000회 | 잘못 나뉜 횟수 = 3068
```

```bash
./strtok_race good ; ./strtok_race good ; ./strtok_race good
```

```text
strtok_r | 스레드 4 × 2000회 | 잘못 나뉜 횟수 = 0
strtok_r | 스레드 4 × 2000회 | 잘못 나뉜 횟수 = 0
strtok_r | 스레드 4 × 2000회 | 잘못 나뉜 횟수 = 0
```

**3천 번 넘게 틀렸습니다.** 각 스레드는 자기 문자열만 다루고 있는데도 그렇습니다. **자료를 공유하지 않아도 함수가 상태를 공유하면 깨집니다.**

> **이 결과가 특히 무서운 이유**는, 코드만 보아서는 공유가 전혀 없어 보이기 때문입니다. `line`은 지역 변수이고 각자의 것입니다. 문제는 **`strtok` 안에** 있습니다.
{: .prompt-danger }

## 제5절. `_r` 함수들

### 5.1 상태를 밖으로 꺼낸다

해법은 단순합니다. **함수가 기억하던 것을 호출하는 쪽이 들고 있게** 합니다.

```c
char *save = NULL;                          /* 내 몫의 기억 자리 */

for (tok = strtok_r(line, " ", &save); tok != NULL;
     tok = strtok_r(NULL, " ", &save))
    ...
```

**`save`가 지역 변수이므로 스레드마다 따로입니다**(7강 3.2절). 이것이 `_r`(reentrant) 함수들의 공통 설계입니다.

### 5.2 바꿔 써야 할 함수들

| 위험한 함수 | 안전한 대체 | 무엇을 기억했나 |
|---|---|---|
| `strtok` | **`strtok_r`** | 다음 위치 |
| `asctime`·`ctime` | `asctime_r`·`ctime_r` | 결과 문자열 버퍼 |
| `localtime`·`gmtime` | **`localtime_r`**·`gmtime_r` | `struct tm` 버퍼 |
| `getpwnam`·`getpwuid` | `getpwnam_r`·`getpwuid_r` | 결과 구조체 |
| `rand` | **`rand_r`** 또는 `random_r` | 난수 씨앗 |
| `readdir` | 요즘 glibc는 안전 | 항목 버퍼 |
| `gethostbyname` | **`getaddrinfo`**(9강) | 결과 구조체 |

**3강에서 `statinfo.c`를 만들 때 이미 `localtime_r`를 썼습니다.** 그때는 이유를 말하지 않았는데, 이것이 이유입니다.

```c
    localtime_r(&ts->tv_sec, &tm);
    strftime(buf, sizeof buf, "%Y-%m-%d %H:%M:%S", &tm);
```

### 5.3 판별하는 법

> **"이 함수가 돌려주는 포인터는 어디를 가리키는가?"**

| 답 | 판정 |
|---|---|
| 내가 준 버퍼 | 안전 |
| **함수 안의 정적 버퍼** | **위험** |

`man` 페이지에 **ATTRIBUTES** 절이 있고, 거기에 스레드 안전성이 적혀 있습니다.

```bash
man 3 strtok | sed -n '/ATTRIBUTES/,/^$/p' | head -20
```

```text
ATTRIBUTES
       For an explanation of the terms used in this section, see
       attributes(7).
       ┌───────────────┬───────────────┬───────────────────────┐
       │ Interface     │ Attribute     │ Value                 │
       ├───────────────┼───────────────┼───────────────────────┤
       │ strtok()      │ Thread safety │ MT-Unsafe race:strtok │
       ├───────────────┼───────────────┼───────────────────────┤
       │ strtok_r()    │ Thread safety │ MT-Safe               │
       └───────────────┴───────────────┴───────────────────────┘
```

**두 함수가 나란히 실려 있습니다.** `race:strtok`의 `race:` 뒤는 **무엇을 두고 경쟁하는지**를 밝힌 것입니다.

**`MT-Unsafe`가 보이면 스레드에서 쓰면 안 됩니다.** `MT-Safe`면 안전합니다. 자세한 표기법은 [`attributes(7)`](https://man7.org/linux/man-pages/man7/attributes.7.html)에 있습니다.

## 제6절. 스레드를 늘려도 빨라지지 않는다

**7강 6.5절에서 예고한 측정입니다.**

### 6.1 실험 설계

`scaling.c`는 **전체 일의 양을 고정**하고 스레드 수만 바꿉니다. 그리고 그중 몇 %를 임계 구역에서 하는지 조절합니다.

```c
    for (i = 0; i < per_thread; i++) {
        if ((i % 100) < pct) {      /* 이만큼은 잠그고 한다 */
            pthread_mutex_lock(&lock);
            shared++;
            spin();
            pthread_mutex_unlock(&lock);
        } else {                    /* 나머지는 혼자 한다 */
            spin();
        }
    }
```

```c
    per_thread = TOTAL / nth;       /* 전체 일의 양은 고정 */
```

**일의 양이 같으므로**, 완벽히 병렬이라면 스레드가 2배면 시간이 절반이 되어야 합니다.

### 6.2 측정 결과

```bash
for pct in 0 10 50 100; do for t in 1 2 4 8; do ./scaling $t $pct; done; done
```

```text

임계 구역  0% | 스레드  2 |  0.051초
임계 구역  0% | 스레드  4 |  0.029초
임계 구역  0% | 스레드  8 |  0.023초

임계 구역 10% | 스레드  1 |  0.102초
임계 구역 10% | 스레드  2 |  0.063초
임계 구역 10% | 스레드  4 |  0.072초
임계 구역 10% | 스레드  8 |  0.075초

임계 구역 50% | 스레드  1 |  0.111초
임계 구역 50% | 스레드  2 |  0.160초
임계 구역 50% | 스레드  4 |  0.214초

```

### 6.3 읽는 법

| 임계 구역 비율 | 1→8 스레드 | 해석 |
|---|---|---|
| **0%** | 0.100 → **0.023초** (4.3배 빨라짐) | 거의 이상적 |
| **10%** | 0.102 → 0.075초 | **2스레드가 최적**, 그 뒤로 나빠진다 |
| **50%** | 0.111 → 0.216초 | **늘릴수록 느려진다** |
| **100%** | 0.112 → **0.343초** (3배 느려짐) | 완전히 손해 |

**임계 구역이 절반만 되어도 스레드를 늘리는 것이 손해입니다.**

> **이것이 암달의 법칙(Amdahl's law)입니다.**
> 프로그램에서 **병렬로 할 수 없는 부분의 비율**이 전체 속도의 상한을 정합니다. 병렬 불가 부분이 10%라면 스레드를 무한히 늘려도 최대 10배까지만 빨라집니다.
>
> 게다가 실제로는 **더 나쁩니다.** 잠금 경합 자체가 비용이라 위 표처럼 **오히려 느려질 수 있습니다.**
{: .prompt-warning }

### 6.4 그래서 무엇을 해야 하나

| 원칙 | 방법 |
|---|---|
| **임계 구역을 줄인다** | 7강 문제 6처럼 지역에 모았다가 한 번만 합친다 |
| 자물쇠를 쪼갠다 | 해시 표의 칸마다 자물쇠(잠금 분할) |
| 읽기는 함께 | 읽기·쓰기 자물쇠(`pthread_rwlock_t`) |
| **아예 공유하지 않는다** | 스레드마다 자기 자료 |
| 원자적 연산 | 제7절 |

**가장 좋은 것은 마지막에서 둘째입니다.** 공유하지 않으면 지킬 것도 없습니다.

### 6.5 CPU 개수도 확인하십시오

```bash
nproc
```

```text
8
```

**CPU 개수보다 많은 스레드는 대개 도움이 되지 않습니다.** 위 표에서 4→8이 거의 나아지지 않은 이유 중 하나입니다. 다만 **입출력을 기다리는 스레드**는 CPU를 쓰지 않으므로 개수보다 많아도 괜찮습니다. 10강 서버에서 이 구분이 중요해집니다.

## 제7절. 원자적 연산

### 7.1 자물쇠 없이 안전하게

7강에서 `counter++`가 **읽고·더하고·쓰는 세 단계**라 위험하다고 배웠습니다. CPU는 이 셋을 **한 동작으로 처리하는 명령**을 가지고 있고, C11부터 표준으로 쓸 수 있습니다.

```c
#include <stdatomic.h>

atomic_long counter = 0;

atomic_fetch_add(&counter, 1);      /* 나눌 수 없는 한 동작 */
```

`counter++`처럼 써도 됩니다. `_Atomic` 자료형에는 연산자가 원자적으로 동작합니다.

### 7.2 세 방식 비교

```bash
./atomic_cmp none ; ./atomic_cmp mutex ; ./atomic_cmp atomic
```

```text
보호없음 |  0.010초 | 기대  4000000 | 실제  1142637 | 틀림
뮤텍스 |  0.215초 | 기대  4000000 | 실제  4000000 | 정확
원자적 |  0.076초 | 기대  4000000 | 실제  4000000 | 정확
```

| 방식 | 시간 | 정확한가 |
|---|---|---|
| 보호 없음 | **0.010초** | **틀림**(400만 중 114만) |
| 뮤텍스 | 0.215초 | 정확 |
| **원자적** | **0.076초** | **정확** |

**원자적 연산이 뮤텍스보다 2.8배 빠르면서 똑같이 정확합니다.**

> 보호 없는 판이 400만 중 **114만**밖에 세지 못했습니다. 7강 5.2절에서는 40만 중 34만이었는데, **경합이 심할수록 더 많이 잃습니다.**
{: .prompt-danger }

### 7.3 그런데 만능은 아닙니다

| 원자적 연산이 되는 것 | 안 되는 것 |
|---|---|
| 정수 하나 증감 | **여러 변수를 함께** 바꾸기 |
| 포인터 하나 교체 | 자료 구조 전체 수정 |
| 깃발 설정·검사 | 조건을 보고 기다리기 |

```c
/* 이것은 원자적으로 만들 수 없다 — 두 계좌를 함께 바꿔야 한다 */
from->balance -= amount;
to->balance   += amount;
```

**둘 이상을 한꺼번에 일관되게 바꿔야 하면 뮤텍스가 필요합니다.**

### 7.4 메모리 순서

`atomic_fetch_add`는 기본적으로 **가장 강한 순서 보장**을 씁니다. 더 느슨한 것을 고를 수도 있습니다.

```c
atomic_fetch_add_explicit(&counter, 1, memory_order_relaxed);
```

| 순서 | 뜻 |
|---|---|
| `memory_order_seq_cst` | 기본값. 모든 스레드가 같은 순서로 본다 |
| `memory_order_relaxed` | **개수만 맞으면 될 때** — 통계 카운터 등 |
| `acquire`/`release` | 자물쇠를 직접 만들 때 |

> **초보 단계에서는 기본값을 쓰십시오.** 느슨한 순서는 빠르지만, 잘못 쓰면 **재현되지 않는 버그**를 만듭니다. 성능을 재어 정말 병목일 때만 손대십시오.
{: .prompt-warning }

## 제8절. 다중 스레드에서 시그널

### 8.1 규칙이 달라집니다

5강에서 시그널을 배웠지만, 스레드가 여럿이면 새 문제가 생깁니다.

| 항목 | 스레드 사이에서 |
|---|---|
| 시그널 **처리기** | **공유한다** — 프로세스에 하나뿐 |
| 시그널 **마스크** | **각자 갖는다**(7강 3.4절) |
| 프로세스에 온 시그널 | **막지 않은 스레드 아무나** 하나가 받는다 |

> **"아무나 하나"가 문제입니다.**
> 어느 스레드가 받을지 정해져 있지 않습니다. 하필 자물쇠를 쥔 스레드가 받아 처리기 안에서 멈추면 프로그램 전체가 굳습니다.
{: .prompt-danger }

### 8.2 올바른 방법 — 전용 스레드

> **모든 스레드가 시그널을 막고, **전용 스레드 하나**가 `sigwait`으로 받는다.**

```c
    /* ① 주 스레드에서 미리 막는다 — 이후 만들어지는 스레드가 물려받는다 */
    sigemptyset(&set);
    sigaddset(&set, SIGINT);
    sigaddset(&set, SIGTERM);
    sigaddset(&set, SIGUSR1);

    rc = pthread_sigmask(SIG_BLOCK, &set, NULL);
```

```c
/* 시그널 전용 스레드: 여기서만 시그널을 받는다 */
static void *sig_thread(void *arg)
{
    sigset_t *set = arg;
    int signo, rc;

    for (;;) {
        rc = sigwait(set, &signo);      /* 막아 둔 시그널을 골라 받는다 */
        ...
        if (signo == SIGTERM || signo == SIGINT) {
            stop = 1;
            break;
        }
        printf("  [시그널 스레드] 진행: %ld / %ld / %ld\n",
               done[0], done[1], done[2]);
        ...
    }
    return NULL;
}
```

**`sigwait`은 처리기가 아니라 보통 함수 호출입니다.** 그래서 5강 5.2절의 제약(`printf` 금지 등)이 **전혀 적용되지 않습니다.** 원하는 것을 마음껏 할 수 있습니다.

### 8.3 실행

```bash
./sigthread &
SPID=$!
sleep 0.7; kill -USR1 $SPID
sleep 0.7; kill -USR1 $SPID
sleep 0.5; kill -TERM $SPID
wait $SPID
```

```text
PID 556 — SIGUSR1 로 상태를 묻고, SIGTERM 으로 끝내십시오
  [시그널 스레드] 10(User defined signal 1) 를 받았습니다
  [시그널 스레드] 진행: 14 / 14 / 14
  [시그널 스레드] 10(User defined signal 1) 를 받았습니다
  [시그널 스레드] 진행: 28 / 28 / 28
  [시그널 스레드] 15(Terminated) 를 받았습니다
  일꾼 1 종료 (38회 처리)
  일꾼 0 종료 (38회 처리)
  일꾼 2 종료 (38회 처리)
모두 정리했습니다
```

**일꾼 스레드들은 시그널을 전혀 신경 쓰지 않았습니다.** 깃발 하나만 보면 됩니다.

### 8.4 순서가 중요합니다

| 순서 | 하는 일 | 빠뜨리면 |
|---|---|---|
| 1 | **주 스레드에서 `pthread_sigmask`로 막는다** | 뒤에 만든 스레드가 시그널을 받아 버린다 |
| 2 | 전용 스레드를 만든다 | |
| 3 | 일꾼 스레드들을 만든다 | |

**막는 것이 반드시 먼저입니다.** 스레드는 만들어질 때 **부모의 마스크를 물려받기** 때문입니다.

> `sigprocmask`가 아니라 **`pthread_sigmask`** 를 쓰십시오. 다중 스레드 프로그램에서 `sigprocmask`의 동작은 규정되어 있지 않습니다.
{: .prompt-warning }

### 8.5 이 구조의 장점

| 장점 | |
|---|---|
| 처리기 제약이 없다 | `printf`·`malloc`·자물쇠 모두 가능 |
| 어느 스레드가 받을지 확실하다 | 전용 스레드 하나뿐 |
| 정리 순서를 통제할 수 있다 | 5강 6절의 우아한 종료가 그대로 |

**10강 이후의 서버 프로그램은 대부분 이 구조를 씁니다.**

## 제9절. 그 밖의 함정

### 9.1 뮤텍스의 종류

```c
pthread_mutexattr_t attr;

pthread_mutexattr_init(&attr);
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);
pthread_mutex_init(&lock, &attr);
```

| 종류 | 같은 스레드가 두 번 잠그면 |
|---|---|
| `NORMAL`(기본) | **자기 교착** — 영원히 멈춘다 |
| **`ERRORCHECK`** | **`EDEADLK` 오류를 돌려준다** |
| `RECURSIVE` | 허용한다(푸는 것도 같은 횟수) |

직접 확인해 보십시오.

```c
    pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);
    pthread_mutex_init(&m, &attr);

    pthread_mutex_lock(&m);
    rc = pthread_mutex_lock(&m);            /* 같은 스레드가 두 번 */
    printf("두 번째 lock 의 반환값 = %d (%s)\n", rc, strerror(rc));
```

```text
두 번째 lock 의 반환값 = 35 (Resource deadlock avoided)
```

**35가 `EDEADLK`입니다.** 기본 뮤텍스였다면 이 줄에서 영원히 멈췄을 것입니다. 7강 2.2절에서 배운 대로 **`errno`가 아니라 반환값**으로 알려 준다는 점도 확인하십시오.

> **개발 중에는 `ERRORCHECK`를 쓰십시오.** 자기 교착을 오류로 잡아 주므로 원인을 즉시 알 수 있습니다.
> `RECURSIVE`는 편해 보이지만 **설계가 잘못되었다는 신호**인 경우가 많습니다. "이 함수가 자물쇠를 쥔 상태로 불리는가?"를 알 수 없게 만들기 때문입니다.
{: .prompt-tip }

### 9.2 스레드마다 따로 두기

```c
static _Thread_local int my_count;      /* C11 표준 */
```

`_Thread_local`(또는 `thread_local`)을 붙이면 **전역처럼 보이지만 스레드마다 따로 존재**하는 변수가 됩니다. 1강 10.6절과 7강 8절에서 본 `errno`가 바로 이 방식입니다.

| 쓰임 | 예 |
|---|---|
| 스레드별 통계 | 각자 세고 나중에 합친다 |
| 스레드별 버퍼 | 매번 `malloc` 하지 않으려고 |
| 스레드별 난수 씨앗 | `rand_r`의 씨앗 |

**공유하지 않으므로 잠글 필요가 없습니다**(6.4절의 그 원칙).

### 9.3 거짓 공유

```c
struct {
    long a;         /* 스레드 1이 쓴다 */
    long b;         /* 스레드 2가 쓴다 */
} counters;
```

`a`와 `b`는 **다른 변수인데도** 성능이 나빠질 수 있습니다. 둘이 **같은 캐시 줄**(보통 64바이트)에 들어 있으면, 한쪽이 쓸 때마다 다른 쪽의 캐시가 무효화되기 때문입니다.

**해결**은 떨어뜨려 놓는 것입니다.

```c
struct padded {
    long value;
    char pad[64 - sizeof(long)];    /* 캐시 줄을 채워 분리한다 */
};
```

> **이것은 정확성 문제가 아니라 성능 문제입니다.** 결과는 언제나 맞지만 느려집니다. 원인을 모르면 "왜 스레드를 늘렸는데 안 빨라지지?"에서 헤매게 됩니다.
{: .prompt-info }

### 9.4 `fork`와 스레드를 섞지 마십시오

> **다중 스레드 프로그램에서 `fork`를 부르면, 자식에는 **부른 스레드 하나만** 존재합니다.**

| 결과 | |
|---|---|
| 다른 스레드가 쥐고 있던 자물쇠 | **영원히 잠긴 채로 복사된다** |
| 그 자물쇠를 쓰는 함수 | 자식에서 **멈춘다** |
| `malloc` 내부 자물쇠 | 자식에서 `malloc`이 멈출 수 있다 |

**그래서 `fork` 뒤에는 async-signal-safe 함수만 써야 하고, 사실상 곧바로 `exec` 하는 것 말고는 안전한 방법이 없습니다.**

| 하고 싶은 일 | 방법 |
|---|---|
| 다른 프로그램 실행 | `fork` 직후 곧바로 `exec` — 안전 |
| 자식에서 일 시키기 | **스레드를 만드는 편이 낫다** |

`posix_spawn`은 이 문제를 피해 만들어진 함수입니다.

### 문제 1. 교착 상태 만들기

자물쇠 두 개와 스레드 두 개로 교착을 재현하고, **탈출 장치**를 넣으십시오.

**정답 및 해설**

- **`usleep`으로 틈을 만든 것**이 재현의 열쇠입니다. 없으면 한쪽이 너무 빨리 끝나 교착이 잘 일어나지 않습니다.
- 3초 감시 후 `_exit(2)`로 빠져나갔습니다. `pthread_join`을 부르면 그 자리에서 함께 멈춥니다.
- CPU 사용률을 확인해 보십시오. `top`에서 **0%** 여야 합니다. 100%라면 교착이 아니라 다른 문제입니다.

### 문제 2. 순서 통일로 풀기

### 문제 3. `trylock`으로 물러서기

순서를 바꿀 수 없다고 가정하고, `trylock`으로 교착을 피하십시오.

**정답 및 해설**

2.3절의 코드가 답입니다.

- **물러설 때 쥔 것을 반드시 놓아야** 합니다. `pthread_mutex_unlock(first)`를 빠뜨리면 교착이 그대로입니다.
- **기다리는 시간을 조금씩 늘린 것**이 활동 정지를 막습니다. 둘이 같은 간격으로 물러서면 계속 부딪칩니다.
- `trylock`의 반환값은 **0이 성공**입니다. 실패는 `EBUSY`입니다. 7강 2.2절의 반환값 규약 그대로입니다.
- 여러 번 실행해 "물러선 횟수"가 달라지는지 보십시오. 0이 나올 수도 있습니다.

### 문제 4. 주소순 잠금 — 계좌 이체

두 계좌 사이에 돈을 옮기는 함수를 교착 없이 만드십시오. 어느 계좌든 인자로 올 수 있습니다.

**정답 및 해설**

3.2절의 `lock_ordered`가 답입니다.

```c
static void transfer(struct account *from, struct account *to, long amount)
{
    if (from == to)
        return;

    lock_ordered(&from->lock, &to->lock);

    if (from->balance >= amount) {
        from->balance -= amount;
        to->balance   += amount;
    }

    pthread_mutex_unlock(&from->lock);
    pthread_mutex_unlock(&to->lock);
}
```

- **주소 비교로 순서를 정한 것**이 핵심입니다. 어느 방향으로 이체하든 잠그는 순서는 같습니다.
- `from == to`를 걸러야 자기 교착을 막습니다(3.2절).
```bash
for i in 1 2 3; do ./transfer | tail -1; done
```

```text
총합 4000 (기대 4000) — 일치
총합 4000 (기대 4000) — 일치
총합 4000 (기대 4000) — 일치
```

- **여러 스레드가 서로 반대 방향으로 이체하도록** 시험하십시오. 위 프로그램은 8스레드가 각각 2만 번씩, 계좌를 무작위로 골라 이체합니다. 순서 규칙이 없으면 곧바로 멈춥니다.
- **잔액의 총합이 변하지 않는지**가 검산입니다. 7강 문제 6에서 `n(n+1)/2`로 검산한 것과 같은 방식입니다.
- 계좌를 고를 때 **`rand`가 아니라 `rand_r`** 를 썼습니다. `rand`는 `MT-Unsafe`입니다(5.2절). 이 프로그램에서 배운 두 가지가 함께 쓰였습니다.

### 문제 5·6. `strtok`의 위험과 `_r` 판

`strtok`을 여러 스레드에서 쓰면 어떻게 되는지 보이고, `strtok_r`로 고치십시오.

**정답 및 해설**

4.3절의 결과가 답입니다.

| 함수 | 잘못 나뉜 횟수 |
|---|---|
| `strtok` | **3684 / 3403 / 3068** (매번 다름) |
| `strtok_r` | **0 / 0 / 0** |

- **각 스레드가 자기 문자열만 다루는데도 깨집니다.** 공유한 것은 `strtok` 안의 정적 변수뿐입니다.
- `strtok_r`의 세 번째 인자 `save`가 **지역 변수**라는 점이 전부입니다. 상태가 스레드마다 따로 있게 됩니다.
- `man 3 strtok`의 ATTRIBUTES에서 **`MT-Unsafe race`** 를 확인하십시오(5.3절).
- 자기 코드에서 `localtime`·`ctime`·`rand`를 쓰고 있다면 모두 같은 문제입니다. 5.2절의 표로 점검하십시오.

### 문제 7. 확장성 측정

임계 구역 비율을 0·10·50·100%로 바꾸어 가며 스레드 1·2·4·8개의 시간을 재고, 표로 정리하십시오.

**정답 및 해설**

6.2절의 결과가 답입니다.

| 비율 | 1스레드 | 8스레드 | 판정 |
|---|---|---|---|
| 0% | 0.100초 | **0.023초** | 4.3배 빨라짐 |
| 10% | 0.102초 | 0.075초 | 2스레드가 최적 |
| 50% | 0.111초 | 0.216초 | **느려짐** |
| 100% | 0.112초 | **0.343초** | 3배 느려짐 |

- **전체 일의 양을 고정한 것**이 실험 설계의 핵심입니다(`per_thread = TOTAL / nth`). 그러지 않으면 무엇을 비교하는지 알 수 없습니다.
- `spin()` 안의 변수를 `volatile`로 둔 이유는 **컴파일러가 통째로 지워 버리지 않게** 하기 위해서입니다. 최적화가 실험을 무너뜨리는 흔한 사례입니다.
- 자기 환경에서는 다른 숫자가 나옵니다. **`nproc`을 먼저 확인**하고, 그 값을 넘는 지점에서 어떻게 되는지 보십시오.
- 결론을 한 문장으로 쓸 수 있어야 합니다. **"병렬로 할 수 없는 부분이 전체 속도를 결정한다."**

### 문제 9. 시그널 전용 스레드

일꾼 스레드 여럿과 시그널 전용 스레드 하나로 이루어진 프로그램을 만드십시오.

**정답 및 해설**

8.2·8.3절의 코드와 결과가 답입니다.

| 확인 | 기대 |
|---|---|
| `SIGUSR1` | 진행 상황 보고, 계속 실행 |
| `SIGTERM` | 모든 일꾼이 정리하고 종료 |
| 일꾼 스레드 | 시그널 코드가 **한 줄도 없다** |

- `pthread_sigmask`를 썼는지 확인하십시오. `sigprocmask`는 다중 스레드에서 동작이 규정되어 있지 않습니다.

### 문제 10. ThreadSanitizer 써 보기

**정답 및 해설**

## 정리

| 구분 | 핵심 |
|---|---|
| 교착 | 서로가 서로를 기다림. **CPU 0%** 로 멈춘다 |
| 네 조건 | 상호 배제·점유 후 대기·뺏을 수 없음·**순환 대기** |
| 가장 쉬운 해법 | **잠금 순서 통일**(이름순·주소순·계층) |
| `trylock` | 순서를 못 정할 때. **물러설 때 기다리는 시간을 늘린다** |
| 재진입 ≠ 스레드 안전 | 뮤텍스로 지킨 함수는 **처리기에서 위험** |
| `MT-Unsafe` | `strtok`·`localtime`·`rand` → **`_r` 판** |
| 확장성 | **임계 구역 50%면 늘릴수록 느려진다.** 암달의 법칙 |
| 가장 좋은 최적화 | **공유하지 않기** |
| 원자적 연산 | 변수 하나면 뮤텍스보다 **3배 빠르다** |
| 시그널 | 전부 막고 **전용 스레드 + `sigwait`**. `pthread_sigmask` |
| `fork` | 다중 스레드에서는 **곧바로 `exec`** 말고는 안전하지 않다 |
| 도구 | `-fsanitize=thread`, `ERRORCHECK` 뮤텍스 |
