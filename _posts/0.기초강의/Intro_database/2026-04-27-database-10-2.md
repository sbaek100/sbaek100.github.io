# 10-2 처음부터 안전하게 만드는 계정과 권한

> 이번 시간 학습 목표
> - 실습용 DB를 처음부터 만들고 보안 요구사항을 정리한다.
> - 사용자 계정을 역할별로 분리한다.
> - `GRANT`, `REVOKE`, `SHOW GRANTS`로 권한을 부여, 회수, 검증한다.
> - 민감한 열은 직접 공개하지 않고 `VIEW`로 안전하게 제공한다.
> - 프로그램이 `root` 계정으로 DB에 접속하면 왜 위험한지 설명할 수 있다.
{: .prompt-tip }

---

## 1. 오늘의 핵심 질문

데이터베이스 보안은 "누가 무엇을 할 수 있는가?"를 정확히 정하는 일에서 시작한다.

예를 들어 학교 성적 시스템이 있다고 하자.

- 웹 프로그램은 학생 목록을 조회하고 일부 정보를 수정해야 한다.
- 담임 교사는 자기 업무에 필요한 학생 정보와 성적을 봐야 한다.
- 보고서 담당자는 통계와 공개 가능한 정보만 봐야 한다.
- 방문자는 민감 정보에 접근하면 안 된다.
- 어떤 계정도 필요 없이 `DROP TABLE`을 할 수 있으면 안 된다.

이 요구사항을 MySQL 권한으로 구현하는 것이 이번 실습의 목표다.

---

## 2. 권한 관리 용어 정리

| 용어 | 의미 |
|---|---|
| **계정(User Account)** | MySQL에 로그인할 수 있는 사용자. MySQL에서는 `'사용자명'@'호스트'` 형태로 구분한다. |
| **호스트(Host)** | 해당 계정이 어디에서 접속할 수 있는지 나타낸다. `localhost`는 현재 PC에서만 접속 가능하다는 뜻이다. |
| **인증(Authentication)** | 사용자가 누구인지 확인하는 과정. 보통 비밀번호로 확인한다. |
| **권한(Privilege)** | 특정 DB나 테이블에 대해 할 수 있는 작업. 예: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `DROP`. |
| **객체(Object)** | 권한을 적용할 대상. 예: 데이터베이스, 테이블, 뷰, 열. |
| **DCL** | Data Control Language. 권한을 부여하거나 회수하는 SQL 분류. 대표 명령어는 `GRANT`, `REVOKE`. |
| **최소 권한 원칙** | 사용자나 프로그램에 필요한 권한만 주고, 필요 없는 권한은 주지 않는 보안 원칙. |
| **VIEW** | 실제 테이블을 바탕으로 만든 가상의 조회용 테이블. 민감한 열을 숨기거나 필요한 행만 보여 줄 때 사용한다. |
| **Deny by Default** | 기본적으로 아무 권한도 주지 않고, 필요한 권한만 명시적으로 허용하는 방식. |

> 실무에서 가장 위험한 습관은 "일단 잘 되게 하려고 모든 권한을 준다"이다. 보안은 필요한 권한을 찾는 과정이지, 모든 권한을 준 뒤 나중에 줄이는 과정이 아니다.
{: .prompt-warning }

## 3. 실습 시나리오

이번 시간에는 `secure_school`이라는 DB를 만든다.

### 3-1. 보호해야 할 데이터

| 테이블 | 내용 | 보안 관점 |
|---|---|---|
| `students` | 학생 기본 정보 | 전화번호와 보호자 연락처가 포함되어 민감하다. |
| `scores` | 과목별 점수 | 성적 정보이므로 접근 범위를 제한해야 한다. |
| `login_audit` | 로그인 기록 | 운영 계정만 입력하고 일반 계정은 수정하면 안 된다. |

### 3-2. 만들 계정

| 계정 | 역할 | 허용할 작업 |
|---|---|---|
| `school_app` | 웹 애플리케이션 계정 | 공개 VIEW 조회, 로그인 기록 입력 |
| `school_teacher` | 교사용 계정 | 학생 공개 정보 조회, 성적 조회와 수정 |
| `school_reporter` | 보고서 계정 | 공개 VIEW 조회만 가능 |
| `school_guest` | 방문자 계정 | 학생 이름과 학년만 조회 |

어떤 계정에도 `DROP`, `ALTER`, `CREATE` 같은 구조 변경 권한은 주지 않는다.

## 4. 실습 DB 처음부터 만들기

Workbench에서 `root`로 접속한 뒤 아래 SQL을 순서대로 실행한다.

```sql
DROP DATABASE IF EXISTS secure_school;
CREATE DATABASE secure_school
    DEFAULT CHARACTER SET utf8mb4
    DEFAULT COLLATE utf8mb4_0900_ai_ci;
USE secure_school;
```

학생 테이블을 만든다.

```sql
CREATE TABLE students (
    student_id INT PRIMARY KEY AUTO_INCREMENT,
    student_no VARCHAR(10) NOT NULL UNIQUE,
    name VARCHAR(30) NOT NULL,
    grade INT NOT NULL,
    class_room VARCHAR(10) NOT NULL,
    phone VARCHAR(30),
    guardian_phone VARCHAR(30),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

성적 테이블을 만든다.

```sql
CREATE TABLE scores (
    score_id INT PRIMARY KEY AUTO_INCREMENT,
    student_id INT NOT NULL,
    subject VARCHAR(30) NOT NULL,
    score INT NOT NULL,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT fk_scores_students
        FOREIGN KEY (student_id) REFERENCES students(student_id)
);
```

로그인 기록 테이블을 만든다.

```sql
CREATE TABLE login_audit (
    audit_id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(30) NOT NULL,
    login_result VARCHAR(20) NOT NULL,
    client_ip VARCHAR(45),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 6. 민감 정보 보호용 VIEW 만들기

### 6-1. 왜 VIEW가 필요한가?

`students` 테이블에는 전화번호와 보호자 연락처가 있다. 모든 계정에게 원본 테이블을 보여 주면 필요 이상으로 개인정보가 노출된다.

그래서 공개 가능한 열만 골라 `VIEW`를 만든다.

### 6-2. 보고서용 공개 VIEW

```sql
CREATE OR REPLACE VIEW v_student_public AS
SELECT
    student_id,
    student_no,
    name,
    grade,
    class_room
FROM students;
```

### 6-3. 방문자용 최소 정보 VIEW

```sql
CREATE OR REPLACE VIEW v_student_guest AS
SELECT
    name,
    grade
FROM students;
```

### 6-4. 교사용 성적 VIEW

```sql
CREATE OR REPLACE VIEW v_teacher_scores AS
SELECT
    s.student_no,
    s.name,
    s.grade,
    s.class_room,
    sc.subject,
    sc.score
FROM students s
JOIN scores sc ON s.student_id = sc.student_id;
```

확인한다.

```sql
SELECT * FROM v_student_public;
SELECT * FROM v_student_guest;
SELECT * FROM v_teacher_scores;
```

## 7. 계정 만들기

계정을 만들기 전, 이전 실습 흔적이 있으면 삭제한다.

```sql
DROP USER IF EXISTS 'school_app'@'localhost';
DROP USER IF EXISTS 'school_teacher'@'localhost';
DROP USER IF EXISTS 'school_reporter'@'localhost';
DROP USER IF EXISTS 'school_guest'@'localhost';
```

새 계정을 만든다.

```sql
CREATE USER 'school_app'@'localhost'
IDENTIFIED BY 'App_pw_1234!';

CREATE USER 'school_teacher'@'localhost'
IDENTIFIED BY 'Teacher_pw_1234!';

CREATE USER 'school_reporter'@'localhost'
IDENTIFIED BY 'Reporter_pw_1234!';

CREATE USER 'school_guest'@'localhost'
IDENTIFIED BY 'Guest_pw_1234!';
```

현재 계정 목록을 확인한다.

```sql
SELECT user, host
FROM mysql.user
WHERE user LIKE 'school_%'
ORDER BY user;
```

예상 결과:

```text
+-----------------+-----------+
| user            | host      |
+-----------------+-----------+
| school_app      | localhost |
| school_guest    | localhost |
| school_reporter | localhost |
| school_teacher  | localhost |
+-----------------+-----------+
```

> 계정 생성과 권한 부여는 별개의 단계이다. 계정만 만들면 기본적으로 아무 테이블도 조회할 수 없다. 이것이 Deny by Default의 출발점이다.

## 8. 권한 설계표 만들기

SQL을 실행하기 전에 권한 설계표를 먼저 만든다.

| 계정 | `students` 원본 | `scores` 원본 | `login_audit` | VIEW |
|---|---|---|---|---|
| `school_app` | 접근 금지 | 접근 금지 | `INSERT` | `v_student_public` 조회 |
| `school_teacher` | 공개 열만 `SELECT` | `SELECT`, `UPDATE(score)` | 접근 금지 | `v_teacher_scores` 조회 |
| `school_reporter` | 접근 금지 | 접근 금지 | 접근 금지 | `v_student_public` 조회 |
| `school_guest` | 접근 금지 | 접근 금지 | 접근 금지 | `v_student_guest` 조회 |

이 표에 없는 권한은 주지 않는다.

## 9. GRANT로 필요한 권한만 부여

### 9-1. 웹 애플리케이션 계정

웹 프로그램은 공개 학생 정보를 조회하고 로그인 기록만 입력할 수 있다.

```sql
GRANT SELECT ON secure_school.v_student_public
TO 'school_app'@'localhost';

GRANT INSERT ON secure_school.login_audit
TO 'school_app'@'localhost';
```

### 9-2. 교사용 계정

교사는 공개 학생 정보와 성적을 조회하고 점수만 수정할 수 있다.

```sql
GRANT SELECT (student_id, student_no, name, grade, class_room)
ON secure_school.students
TO 'school_teacher'@'localhost';

GRANT SELECT ON secure_school.scores
TO 'school_teacher'@'localhost';

GRANT UPDATE (score)
ON secure_school.scores
TO 'school_teacher'@'localhost';

GRANT SELECT ON secure_school.v_teacher_scores
TO 'school_teacher'@'localhost';
```

`UPDATE (score)`는 `scores` 테이블의 모든 열을 수정할 수 있다는 뜻이 아니다. `score` 열만 수정할 수 있다는 뜻이다.

### 9-3. 보고서 계정

```sql
GRANT SELECT ON secure_school.v_student_public
TO 'school_reporter'@'localhost';
```

### 9-4. 방문자 계정

```sql
GRANT SELECT ON secure_school.v_student_guest
TO 'school_guest'@'localhost';
```

MySQL 8에서는 `GRANT`가 바로 반영된다. 그래도 수업에서는 권한 변경을 명확히 하기 위해 다음 명령을 함께 실행한다.

```sql
FLUSH PRIVILEGES;
```

## 10. SHOW GRANTS로 검증하기

권한을 주는 것보다 중요한 것은 제대로 주어졌는지 확인하는 것이다.

```sql
SHOW GRANTS FOR 'school_app'@'localhost';
SHOW GRANTS FOR 'school_teacher'@'localhost';
SHOW GRANTS FOR 'school_reporter'@'localhost';
SHOW GRANTS FOR 'school_guest'@'localhost';
```

예상 결과 예시:

```text
-- school_app
GRANT USAGE ON *.* TO `school_app`@`localhost`
GRANT SELECT ON `secure_school`.`v_student_public` TO `school_app`@`localhost`
GRANT INSERT ON `secure_school`.`login_audit` TO `school_app`@`localhost`

-- school_teacher
GRANT USAGE ON *.* TO `school_teacher`@`localhost`
GRANT SELECT (`student_id`, `student_no`, `name`, `grade`, `class_room`) ON `secure_school`.`students` TO `school_teacher`@`localhost`
GRANT SELECT, UPDATE (`score`) ON `secure_school`.`scores` TO `school_teacher`@`localhost`
GRANT SELECT ON `secure_school`.`v_teacher_scores` TO `school_teacher`@`localhost`

-- school_reporter
GRANT USAGE ON *.* TO `school_reporter`@`localhost`
GRANT SELECT ON `secure_school`.`v_student_public` TO `school_reporter`@`localhost`

-- school_guest
GRANT USAGE ON *.* TO `school_guest`@`localhost`
GRANT SELECT ON `secure_school`.`v_student_guest` TO `school_guest`@`localhost`
```

확인할 점은 다음과 같다.

- `school_app`에 `DROP`, `ALTER`, `DELETE`가 없어야 한다.
- `school_reporter`는 원본 `students`를 볼 수 없어야 한다.
- `school_guest`는 `v_student_guest`만 볼 수 있어야 한다.
- `school_teacher`는 `scores.score`만 수정할 수 있어야 한다.

## 11. 실제 접속 테스트

Workbench에서 새 연결을 만들어 각 계정으로 접속해 본다.

### 11-1. `school_reporter` 테스트

성공해야 하는 명령:

```sql
USE secure_school;
SELECT * FROM v_student_public;
```

실패해야 하는 명령:

```sql
SELECT * FROM students;
DELETE FROM students WHERE student_id = 1;
DROP TABLE students;
```

예상 결과:

```text

|          2 | 2026002    | 이서연 |     3 | 3-2        |
|          3 | 2026003    | 박지호 |     2 | 2-1        |
|          4 | 2026004    | 최하은 |     1 | 1-1        |

-- SELECT * FROM students;

-- DELETE FROM students WHERE student_id = 1;
```

## 12. REVOKE로 권한 회수하기

실무에서는 계정의 업무가 바뀌거나, 권한을 잘못 줬거나, 보안 사고가 의심될 때 권한을 회수해야 한다.

예를 들어 보고서 계정의 조회 권한을 잠시 회수한다.

```sql
REVOKE SELECT ON secure_school.v_student_public
FROM 'school_reporter'@'localhost';

SHOW GRANTS FOR 'school_reporter'@'localhost';
```

예상 결과:

```text
GRANT USAGE ON *.* TO `school_reporter`@`localhost`
```

다시 부여한다.

```sql
GRANT SELECT ON secure_school.v_student_public
TO 'school_reporter'@'localhost';
```

모든 권한을 한 번에 회수하려면 다음을 사용한다.

```sql
REVOKE ALL PRIVILEGES, GRANT OPTION
FROM 'school_reporter'@'localhost';
```

> `REVOKE`는 없는 권한을 회수하려고 하면 오류가 날 수 있다. 먼저 `SHOW GRANTS`로 현재 권한을 확인하는 습관을 들인다.

## 17. 정리

- DB 보안의 출발점은 "누가 무엇을 할 수 있는가"를 정하는 것이다.
- 계정은 역할별로 분리하고, 프로그램은 `root`로 접속하지 않는다.
- `GRANT`는 필요한 권한만 부여하고, `REVOKE`는 필요 없어진 권한을 회수한다.
- `SHOW GRANTS`로 실제 권한을 반드시 검증한다.
- 민감한 열은 원본 테이블을 직접 열어 주지 말고 `VIEW`로 공개 범위를 줄인다.
- 다음 10-3에서는 권한을 줄여 놓은 상태에서 SQL Injection이 어떻게 발생하고, 어떻게 막는지 독립 실습으로 확인한다.
