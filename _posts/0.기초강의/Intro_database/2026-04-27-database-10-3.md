# 10-3 처음부터 구성하는 SQL Injection 방어 실습

## 1. SQL Injection 용어 정리

| 용어 | 의미 |
|---|---|
| **SQL Injection** | 사용자가 입력한 문자열이 SQL 문장의 일부로 해석되어, 개발자가 의도하지 않은 SQL이 실행되는 취약점. |
| **쿼리(Query)** | DB에 보내는 SQL 문장. 예: `SELECT * FROM users WHERE username = 'admin'`. |
| **문자열 리터럴(String Literal)** | SQL 안에서 작은따옴표로 감싼 문자열 값. 예: `'admin'`. |
| **조건식(Boolean Condition)** | 참 또는 거짓이 되는 식. 예: `role = 'ADMIN'`, `'1'='1'`. |
| **주석(Comment)** | SQL에서 뒤쪽 내용을 무시하게 하는 표기. MySQL에서는 `#` 또는 `-- `를 사용할 수 있다. |
| **문자열 연결(String Concatenation)** | 프로그램에서 `+`로 문자열을 이어 붙이는 방식. SQL을 만들 때 이 방식을 쓰면 위험하다. |
| **파라미터 바인딩(Parameter Binding)** | SQL 구조와 입력값을 분리해 DB에 전달하는 방식. Python MySQL Connector에서는 `%s`와 튜플을 사용한다. |
| **Prepared Statement** | SQL 구조를 미리 준비하고 값만 나중에 안전하게 전달하는 방식. SQL Injection 방어의 핵심이다. |
| **최소 권한 원칙** | 계정에 필요한 권한만 부여해 사고가 나도 피해 범위를 줄이는 원칙. |

SQL Injection을 한 문장으로 정리하면 다음과 같다.

> 사용자 입력을 SQL 문장에 그대로 이어 붙이면, 입력값이 데이터가 아니라 SQL 명령처럼 해석될 수 있다.
{: .prompt-info }

## 3. 실습 DB 처음부터 만들기

Workbench에서 `root`로 접속한 뒤 실행한다.

```sql
DROP DATABASE IF EXISTS injection_secure_lab;
CREATE DATABASE injection_secure_lab
    DEFAULT CHARACTER SET utf8mb4
    DEFAULT COLLATE utf8mb4_0900_ai_ci;
USE injection_secure_lab;
```

사용자 테이블을 만든다.

```sql
CREATE TABLE users (
    user_id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(30) NOT NULL UNIQUE,
    password_hash CHAR(64) NOT NULL,
    role VARCHAR(20) NOT NULL,
    is_active TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

로그인 기록 테이블을 만든다.

```sql
CREATE TABLE login_audit (
    audit_id INT PRIMARY KEY AUTO_INCREMENT,
    username_input VARCHAR(100),
    login_result VARCHAR(20) NOT NULL,
    client_ip VARCHAR(45),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 3-1. 비밀번호 해시란?

실제 서비스에서는 비밀번호를 그대로 저장하면 안 된다. 비밀번호가 유출되면 사용자의 실제 비밀번호가 바로 노출되기 때문이다.

**해시(Hash)**는 원본 값을 고정 길이 문자열로 바꾸는 함수이다. 이번 실습에서는 MySQL의 `SHA2(값, 256)`을 사용한다.

> 실무에서는 단순 SHA-256보다 `bcrypt`, `Argon2`, `PBKDF2`처럼 비밀번호 저장용으로 설계된 방식과 salt를 사용한다. 이번 실습에서는 SQL Injection 흐름을 단순하게 보기 위해 SHA-256을 사용한다.
{: .prompt-warning }

실습 데이터를 입력한다.

```sql
INSERT INTO users (username, password_hash, role)
VALUES
    ('admin',  SHA2('Admin_pw_1234!', 256), 'ADMIN'),
    ('minjun', SHA2('Minjun_pw_1234!', 256), 'USER'),
    ('seoyeon', SHA2('Seoyeon_pw_1234!', 256), 'USER'),
    ('guest',  SHA2('Guest_pw_1234!', 256), 'GUEST');
```

확인한다.

```sql
SELECT user_id, username, password_hash, role, is_active
FROM users;
```

예상 결과:

```text
+---------+----------+------------------------------------------------------------------+-------+-----------+
| user_id | username | password_hash                                                    | role  | is_active |
+---------+----------+------------------------------------------------------------------+-------+-----------+
|       1 | admin    | 64자리 SHA-256 해시값                                             | ADMIN |         1 |
|       2 | minjun   | 64자리 SHA-256 해시값                                             | USER  |         1 |
|       3 | seoyeon  | 64자리 SHA-256 해시값                                             | USER  |         1 |
|       4 | guest    | 64자리 SHA-256 해시값                                             | GUEST |         1 |
+---------+----------+------------------------------------------------------------------+-------+-----------+
```

`password_hash`는 긴 영문/숫자 문자열로 표시된다. 평문 비밀번호가 보이면 안 된다.

## 4. 프로그램용 제한 계정 만들기

Python 프로그램이 `root`로 접속하면 안 된다. 공격을 당했을 때 피해가 너무 커지기 때문이다.

먼저 이전 실습 계정을 정리한다.

```sql
DROP USER IF EXISTS 'inj_app'@'localhost';
```

프로그램용 계정을 만든다.

```sql
CREATE USER 'inj_app'@'localhost'
IDENTIFIED BY 'Inj_app_pw_1234!';
```

로그인 검증에 필요한 최소 권한만 준다.

```sql
GRANT SELECT (user_id, username, password_hash, role, is_active)
ON injection_secure_lab.users
TO 'inj_app'@'localhost';

GRANT INSERT ON injection_secure_lab.login_audit
TO 'inj_app'@'localhost';

FLUSH PRIVILEGES;
```

권한을 확인한다.

```sql
SHOW GRANTS FOR 'inj_app'@'localhost';
```

예상 결과:

```text
GRANT USAGE ON *.* TO `inj_app`@`localhost`
GRANT SELECT (`user_id`, `username`, `password_hash`, `role`, `is_active`) ON `injection_secure_lab`.`users` TO `inj_app`@`localhost`
GRANT INSERT ON `injection_secure_lab`.`login_audit` TO `inj_app`@`localhost`
```

`inj_app`에는 `DROP`, `ALTER`, `DELETE`, `UPDATE` 권한이 없어야 한다.

> 최소 권한은 SQL Injection 자체를 없애지는 못한다. 하지만 취약점이 발생했을 때 테이블 삭제, 데이터 수정 같은 피해를 줄여 준다.

## 6. 취약한 로그인 코드: 문자열 연결

`login_bad.py`를 만든다.

```python
import hashlib
import mysql.connector


def sha256_hex(text):
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


conn = mysql.connector.connect(
    host="localhost",
    user="inj_app",
    password="Inj_app_pw_1234!",
    database="injection_secure_lab"
)

cursor = conn.cursor(dictionary=True)

username = input("아이디: ")
password = input("비밀번호: ")
password_hash = sha256_hex(password)

# 취약점: 사용자 입력값을 SQL 문자열에 직접 이어 붙인다.
sql = (
    "SELECT user_id, username, role "
    "FROM users "
    "WHERE username = '" + username + "' "
    "AND password_hash = '" + password_hash + "' "
    "AND is_active = 1"
)

print("\n[실행될 SQL]")
print(sql)

cursor.execute(sql)
user = cursor.fetchone()

if user:
    print(f"\n[로그인 성공] {user['username']} / {user['role']}")
    result = "SUCCESS"
else:
    print("\n[로그인 실패]")
    result = "FAIL"

cursor.execute(
    "INSERT INTO login_audit (username_input, login_result, client_ip) "
    "VALUES (%s, %s, %s)",
    (username, result, "127.0.0.1")
)
conn.commit()

cursor.close()
conn.close()
```

### 6-1. 정상 로그인 테스트

```text
아이디: minjun
비밀번호: Minjun_pw_1234!
```

예상 출력:

```text
[실행될 SQL]
SELECT user_id, username, role FROM users WHERE username = 'minjun' AND password_hash = '...' AND is_active = 1

[로그인 성공] minjun / USER
```

비밀번호 해시값은 64자리 문자열로 출력된다. 예시에서는 길어서 `...`로 줄였다.

정상 계정과 비밀번호를 넣으면 로그인 성공이 출력된다.

## 7. SQL Injection으로 로그인 우회 확인

이번에는 비밀번호를 몰라도 로그인되는 취약점을 확인한다.

```text
아이디: admin' #
비밀번호: 아무거나
```

예상 출력:

```text
[실행될 SQL]
SELECT user_id, username, role FROM users WHERE username = 'admin' #' AND password_hash = '...' AND is_active = 1

[로그인 성공] admin / ADMIN
```

출력되는 SQL을 보면 다음과 비슷하다.

```sql
SELECT user_id, username, role
FROM users
WHERE username = 'admin' #' AND password_hash = '...'
AND is_active = 1
```

MySQL에서 `#`은 주석 시작이다. 따라서 `#` 뒤의 비밀번호 검사 부분이 무시된다. 결과적으로 DB는 아래 조건만 검사하게 된다.

```sql
WHERE username = 'admin'
```

그래서 비밀번호를 몰라도 `admin` 사용자로 로그인된다.

> 비밀번호를 해시로 저장해도 SQL Injection이 자동으로 막히지는 않는다. 해시는 비밀번호 유출 피해를 줄이는 방어이고, SQL Injection 방어는 파라미터 바인딩으로 해야 한다.
{: .prompt-warning }

## 8. 안전한 로그인 코드: 파라미터 바인딩

`login_safe.py`를 만든다.

```python
import hashlib
import mysql.connector


def sha256_hex(text):
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


conn = mysql.connector.connect(
    host="localhost",
    user="inj_app",
    password="Inj_app_pw_1234!",
    database="injection_secure_lab"
)

cursor = conn.cursor(dictionary=True)

username = input("아이디: ")
password = input("비밀번호: ")
password_hash = sha256_hex(password)

sql = """
SELECT user_id, username, role
FROM users
WHERE username = %s
  AND password_hash = %s
  AND is_active = 1
"""

cursor.execute(sql, (username, password_hash))
user = cursor.fetchone()

if user:
    print(f"\n[로그인 성공] {user['username']} / {user['role']}")
    result = "SUCCESS"
else:
    print("\n[로그인 실패]")
    result = "FAIL"

cursor.execute(
    """
    INSERT INTO login_audit (username_input, login_result, client_ip)
    VALUES (%s, %s, %s)
    """,
    (username, result, "127.0.0.1")
)
conn.commit()

cursor.close()
conn.close()
```

다시 같은 공격 입력을 넣어 본다.

```text
아이디: admin' #
비밀번호: 아무거나
```

예상 출력:

```text
[로그인 실패]
```

이번에는 로그인 실패가 나와야 한다.

### 8-1. 왜 안전한가?

취약한 코드는 입력값을 SQL 문장에 붙였다.

```python
"WHERE username = '" + username + "'"
```

안전한 코드는 SQL 구조를 먼저 고정하고, 값은 따로 전달한다.

```python
sql = "WHERE username = %s AND password_hash = %s"
cursor.execute(sql, (username, password_hash))
```

이 방식에서는 `admin' #` 전체가 SQL 문법이 아니라 **그냥 아이디 문자열 값**으로 처리된다. 그래서 주석 기호 `#`도 SQL 주석으로 동작하지 않는다.

## 9. 취약한 검색 코드

로그인뿐 아니라 검색 기능에서도 SQL Injection이 자주 발생한다.

`search_bad.py`를 만든다.

```python
import mysql.connector

conn = mysql.connector.connect(
    host="localhost",
    user="inj_app",
    password="Inj_app_pw_1234!",
    database="injection_secure_lab"
)

cursor = conn.cursor(dictionary=True)

keyword = input("검색어: ")

sql = (
    "SELECT username, role "
    "FROM users "
    "WHERE username LIKE '%" + keyword + "%' "
    "AND is_active = 1"
)

print("\n[실행될 SQL]")
print(sql)

cursor.execute(sql)

for row in cursor.fetchall():
    print(row)

cursor.close()
conn.close()
```

정상 검색:

```text
검색어: min
```

예상 출력:

```text
[실행될 SQL]
SELECT username, role FROM users WHERE username LIKE '%min%' AND is_active = 1
{'username': 'minjun', 'role': 'USER'}
```

공격 입력:

```text
검색어: %' OR '1'='1' #
```

예상 출력:

```text
[실행될 SQL]
SELECT username, role FROM users WHERE username LIKE '%%' OR '1'='1' #%' AND is_active = 1
{'username': 'admin', 'role': 'ADMIN'}
{'username': 'minjun', 'role': 'USER'}
{'username': 'seoyeon', 'role': 'USER'}
{'username': 'guest', 'role': 'GUEST'}
```

이 입력은 조건을 항상 참으로 만들어 전체 사용자 목록을 조회하게 만든다.

## 10. 안전한 검색 코드

`search_safe.py`를 만든다.

```python
import mysql.connector

conn = mysql.connector.connect(
    host="localhost",
    user="inj_app",
    password="Inj_app_pw_1234!",
    database="injection_secure_lab"
)

cursor = conn.cursor(dictionary=True)

keyword = input("검색어: ")

sql = """
SELECT username, role
FROM users
WHERE username LIKE %s
  AND is_active = 1
"""

cursor.execute(sql, (f"%{keyword}%",))

for row in cursor.fetchall():
    print(row)

cursor.close()
conn.close()
```

같은 공격 입력을 넣어도 전체 목록이 나오지 않아야 한다.

```text
검색어: %' OR '1'='1' #
```

예상 출력:

```text
-- 결과 없음
```

안전한 코드에서는 공격 문자열 전체가 검색어 값으로 처리된다. 실제로 `%' OR '1'='1' #`라는 이름을 가진 사용자가 없으므로 아무 행도 나오지 않는 것이 정상이다.

## 11. 입력 검증 추가하기

파라미터 바인딩이 가장 중요한 방어이지만, 입력 검증도 함께 사용하면 더 안전하다.

예를 들어 아이디는 영문자, 숫자, 밑줄만 허용한다고 정할 수 있다.

```python
import re

username = input("아이디: ")

if not re.fullmatch(r"[A-Za-z0-9_]{3,30}", username):
    print("아이디 형식이 올바르지 않습니다.")
    raise SystemExit
```

입력 검증의 목적은 다음과 같다.

- 잘못된 형식의 값을 일찍 거부한다.
- 예상하지 못한 값이 DB까지 전달되지 않게 한다.
- 오류 메시지와 로그를 관리하기 쉽게 만든다.

하지만 입력 검증만 믿으면 안 된다. SQL Injection 방어의 핵심은 여전히 **파라미터 바인딩**이다.

## 12. 최소 권한이 실제로 막아 주는 것

`inj_app` 계정에는 `DROP` 권한이 없다. 따라서 문자열 연결 취약점이 있더라도 다음과 같은 피해는 권한 단계에서 차단되어야 한다.

```text
아이디: admin'; DROP TABLE users; #
비밀번호: 아무거나
```

예상 결과:

```text
-- 보통은 여러 문장 실행 제한 또는 권한 부족으로 실패한다.
-- users 테이블은 삭제되지 않아야 한다.
```

`mysql-connector-python`은 기본적으로 한 번의 `execute()`에서 여러 SQL 문장을 실행하지 않도록 제한한다. 설령 여러 문장 실행이 가능한 환경이라도, `inj_app`에게 `DROP` 권한이 없기 때문에 테이블 삭제는 실패해야 한다.

> 최소 권한은 마지막 안전망이다. 취약한 코드를 그대로 둬도 된다는 뜻이 아니라, 실수나 공격이 발생했을 때 피해를 줄이는 방어층이다.
{: .prompt-info }

## 13. 로그인 기록 확인

다시 Workbench의 `root` 접속으로 돌아와 로그인 기록을 확인한다.

```sql
USE injection_secure_lab;

SELECT *
FROM login_audit
ORDER BY created_at DESC;
```

예상 결과:

```text
+----------+----------------+--------------+-----------+---------------------+
| audit_id | username_input | login_result | client_ip | created_at          |
+----------+----------------+--------------+-----------+---------------------+
|        4 | admin' #       | FAIL         | 127.0.0.1 | 2026-.. ..:..:..    |
|        3 | admin' #       | SUCCESS      | 127.0.0.1 | 2026-.. ..:..:..    |
|        2 | minjun         | SUCCESS      | 127.0.0.1 | 2026-.. ..:..:..    |
+----------+----------------+--------------+-----------+---------------------+
```

실습한 순서와 횟수에 따라 행 개수와 `audit_id`는 달라질 수 있다. 중요한 점은 공격처럼 보이는 입력값과 성공/실패 결과가 기록된다는 것이다.

로그는 보안 분석에 중요하다.

| 로그 항목 | 의미 |
|---|---|
| `username_input` | 사용자가 입력한 아이디 |
| `login_result` | 성공 또는 실패 |
| `client_ip` | 접속 위치 |
| `created_at` | 시각 |

실무에서는 로그인 실패가 짧은 시간에 반복되는지, 이상한 특수문자가 포함된 입력이 많은지, 관리자 계정 대상 시도가 많은지 등을 감시한다.

## 14. 방어 방법 정리

| 방어 방법 | 막는 대상 | 한계 |
|---|---|---|
| 파라미터 바인딩 | SQL Injection의 직접 원인 | 동적 테이블명, 정렬 컬럼명 등은 별도 검증 필요 |
| 최소 권한 | 사고 발생 시 피해 확대 | 취약점 자체를 제거하지는 못함 |
| 입력 검증 | 비정상 형식의 값 | 검증 누락 가능성이 있음 |
| 비밀번호 해시 | 비밀번호 원문 유출 | SQL Injection 자체를 막지는 못함 |
| 로그 기록 | 공격 시도 탐지와 사후 분석 | 공격을 직접 차단하지는 못함 |

가장 중요한 순서는 다음과 같다.

1. SQL은 문자열 연결로 만들지 않는다.
2. `cursor.execute(sql, values)` 형태로 파라미터 바인딩을 사용한다.
3. 프로그램 계정에는 필요한 권한만 준다.
4. 민감 정보는 원본 그대로 저장하거나 보여 주지 않는다.
5. 실패 로그와 이상 입력을 기록한다.

## 15. 연습 문제

### 문제 1

다음 코드가 위험한 이유를 설명하시오.

```python
username = input("아이디: ")
sql = "SELECT * FROM users WHERE username = '" + username + "'"
cursor.execute(sql)
```

**정답 예시**

사용자 입력값을 SQL 문자열에 직접 이어 붙였기 때문에 입력값 안의 작은따옴표, 주석, 조건식이 SQL 문법으로 해석될 수 있다. 따라서 SQL Injection 취약점이 생긴다.

### 문제 2

문제 1의 코드를 안전하게 바꾸시오.

**정답**

```python
username = input("아이디: ")
sql = "SELECT * FROM users WHERE username = %s"
cursor.execute(sql, (username,))
```

### 문제 3

`search_bad.py`에서 전체 사용자 목록이 나오게 하는 공격 입력을 작성하시오.

**정답 예시**

```text
%' OR '1'='1' #
```

단, 이 입력은 반드시 본인 PC의 실습용 DB에서만 사용한다.

### 문제 4

비밀번호 해시와 파라미터 바인딩은 각각 어떤 문제를 막는가?

**정답 예시**

비밀번호 해시는 DB가 유출되었을 때 비밀번호 원문이 바로 드러나는 것을 막는다. 파라미터 바인딩은 사용자 입력이 SQL 문법으로 해석되는 것을 막아 SQL Injection을 방어한다.

### 문제 5

`inj_app` 계정에 `DROP` 권한을 주지 않는 이유를 최소 권한 원칙으로 설명하시오.

**정답 예시**

로그인 기능을 수행하는 프로그램 계정은 사용자 조회와 로그인 기록 입력만 필요하다. 테이블 삭제 권한은 업무에 필요하지 않으므로 부여하면 안 된다. 그래야 SQL Injection 같은 취약점이 발생해도 테이블 삭제 피해를 줄일 수 있다.

## 16. 정리

- SQL Injection은 사용자 입력이 SQL 문장 구조로 해석될 때 발생한다.
- 문자열 연결로 SQL을 만들면 취약해진다.
- 파라미터 바인딩은 입력값을 SQL 구조가 아니라 데이터 값으로 전달한다.
- 비밀번호 해시는 필요하지만 SQL Injection 방어를 대신하지 않는다.
- 프로그램 계정은 `root`가 아니라 제한 계정이어야 한다.
- 최소 권한, 입력 검증, 로그 기록은 파라미터 바인딩과 함께 사용하는 방어층이다.

다음 11주차에서는 보안 사고나 실수로 데이터가 손상되었을 때 복구할 수 있도록 백업과 복구를 실습한다.
