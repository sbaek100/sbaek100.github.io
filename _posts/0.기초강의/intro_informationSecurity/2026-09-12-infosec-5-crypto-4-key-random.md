# 현대 암호 #3: 키 관리와 난수

> 아무리 강한 알고리즘(AES·RSA)이라도 **키를 잘못 만들고·나누고·보관하면** 보안은 무너진다. 또 키·IV·nonce·솔트는 모두 **좋은 난수**에서 출발한다. 이 글은 암호학의 마지막 퍼즐인 **키 관리와 난수**를 다룬다.  
> 관련 글: **[대칭키 암호(키·IV·nonce)](/posts/infosec-5-crypto-2/)**, **[해시 함수와 응용](/posts/infosec-5-crypto-3-2-hash/)**, **[접근통제 ① 인증(패스워드·솔트·PBKDF)](/posts/infosec-9-auth-1-1-authentication/)**.
{: .prompt-info }

## 1. 키(Key)

### 1.1 개요

- 대칭키 암호·공개키 암호·메시지 인증 코드(MAC)·전자서명 등 모든 암호기술을 쓰려면 **키(key)라 불리는 대단히 큰 수**가 반드시 필요하다.
- **키 공간(Key-Space)**의 크기, 즉 "가능한 키의 총 수"는 **크면 클수록 무차별 공격에 강하다.** 키 공간의 크기는 **키의 비트 길이**로 정해진다. (예: 128비트 키 → $2^{128}$가지)
- **키는 평문과 같은 가치를 갖는다.** 암호문을 도청한 이브에게 "키가 넘어가는 것"은 "평문이 넘어가는 것"과 똑같다.

> **🐴 당나귀의 열쇠가게 (키 관리의 교훈)**  
> 옛날에 당나귀가 열쇠가게를 열고 "내 자물쇠는 튼튼해서 도둑이 못 뚫어"라고 선전했다. 마을의 모두가 자물쇠를 맡겼다. 자물쇠는 확실히 튼튼했지만, **열쇠가 모두 같은 모양**이었다. 그래서 도둑이 **한 집 열쇠만 손에 넣자 모든 집이 뚫려** 버렸다. → 알고리즘(자물쇠)이 튼튼해도 **키 관리가 허술하면** 전체가 무너진다.
{: .prompt-tip }

## 2. 다양한 키

### 2.1 세션키와 마스터 키

- `https://`로 시작하는 페이지에 접속하면 웹 서버와 브라우저 사이에서 **SSL/TLS**로 암호화 통신이 이뤄진다.
- 이때 쓰는 키는 **해당 통신에만 한 번** 쓰고, 다음 통신엔 다른 키를 쓴다. 이렇게 통신 때마다 한 번만 쓰는 키를 **세션키(session key)**라 한다.
- 세션키와 달리 **반복적으로 쓰는 키**를 **마스터 키(master key)**라 한다.

> **세션키**: 사용자 간 통신 **세션이 개시될 때 할당**되고 **종료되면 폐기**되는 동적 대칭키. 다음에 쓰려고 유지할 필요가 없다. (앞 [하이브리드 암호](/posts/infosec-5-crypto-3-1-publickey/#6-하이브리드-암호)의 "세션키 교환"이 바로 이것)
{: .prompt-info }

### 2.2 CEK와 KEK

- **CEK(Contents Encrypting Key)**: 사용자가 직접 쓰는 정보(콘텐츠)를 암호화하는 키.
- **KEK(Key Encrypting Key)**: **"키를 암호화하는 키"**. 즉 CEK를 보호하기 위해 한 번 더 암호화하는 데 쓴다.

```
[CEK로 콘텐츠 암호화]                 [KEK로 CEK(키) 자체를 암호화]
 콘텐츠 ──암호화(CEK)──▶ 암호문         CEK ──암호화(KEK)──▶ 암호화된 CEK
 암호문 ──복호화(CEK)──▶ 콘텐츠         암호화된 CEK ──복호화(KEK)──▶ CEK
```

> **🍼 쉬운 설명**  
> CEK는 "금고 안 물건을 잠그는 열쇠", KEK는 "그 열쇠를 다시 넣어 두는 더 안전한 작은 금고의 열쇠"다. 키를 그냥 두지 않고 **키로 키를 또 감싸서** 보관하면, 키가 새도 한 겹 더 막힌다.
{: .prompt-tip }

## 3. 패스워드 기반 키 — PBKDF와 PBE

사람이 외우는 **패스워드**는 키로 쓰기엔 너무 짧고 엔트로피가 낮다. 그래서 패스워드로부터 **안전한 키를 유도(derive)**하는 표준이 필요하다.

### 3.1 PBKDF (Password-Based Key Derivation Function)

- **입력**: 비밀번호(P), 반복횟수(C), 솔트(S), 생성할 비밀키 길이(klen) → **출력**: 비밀키(mk)
- **솔트(SALT)**: 난수발생기로 생성하며 **최소 128비트 이상** 권고. **반복횟수는 최소 1,000번 이상** 권고.
- 아래는 **SHA-256 기반 HMAC**을 이용한 **PBKDF2**의 일반 구조다.

```
   비밀번호(P) ──┐   반복횟수(C) ──┐
                 ▼                  ▼
 U = SALT(S)||000…001 ─▶ [ SHA-256 HMAC ] ─▶ 비밀키(mk)
                          ▲
   생성할 비밀키 길이(klen) ┘
```

> **⚠️ 주의**: 취약한 해시(MD2·MD5·SHA-1)를 쓰는 표준 변형은 **사용하지 말 것**을 권고한다. 또한 PBKDF는 일부러 **느리게**(반복횟수↑) 만들어 대량 대입을 막는다 — 이는 [인증 글의 bcrypt/Argon2](/posts/infosec-9-auth-1-1-authentication/)와 같은 철학이다.
{: .prompt-warning }

### 3.2 PBE(패스워드 기반 암호)에서 솔트의 역할

- **솔트(Salt)**는 "소금"이라는 뜻이다. 요리에 소금을 뿌려 맛을 바꾸듯, 솔트는 **의사난수 생성기로 만든 랜덤 값**으로, 키(KEK)를 만들 때 **패스워드와 함께 일방향 해시함수에 입력**된다.
- 솔트는 **사전공격(Dictionary Attack)·레인보우 테이블 공격**을 막기 위해 존재한다.

```
[솔트 없음 → 사전공격 가능]
 패스워드 ─▶ 일방향 해시 ─▶ KEK      공격자가 패스워드별 KEK를 미리 계산해 둘 수 있음
   abc   → 02E32913…                 (abc, abcd, pass … 표를 만들어 비교만 하면 끝)

[솔트 있음 → 사전공격 불가]
 의사난수 생성기 ─▶ 솔트(salt) ─┐
                                ├─▶ 일방향 해시 ─▶ KEK
                     패스워드 ──┘
   솔트가 다르면 "패스워드가 같아도" KEK가 달라짐 → 미리 만든 표가 무용지물
```

> **솔트 운용 원칙**
> - 사용자마다 **랜덤하게** 생성한다.
> - 비밀번호와 **분리**해 안전한 장소에 저장한다.
> - 솔트 노출 위협을 줄이려 서버 프로그램은 솔트를 **외부에서 호출**해 쓰는 형태로 구현하기도 한다.
{: .prompt-info }

> 솔트가 레인보우 테이블을 어떻게 무력화하는지의 자세한 예시는 [인증 글 §6.4 Salt](/posts/infosec-9-auth-1-1-authentication/)에서도 다룬다.
{: .prompt-tip }

## 4. 암호키 저장 방법

- 암호키는 **서버** 또는 **하드웨어 토큰**에 저장할 수 있다.
  - **서버 저장**: 웹 서버·DB 서버일 수도 있으나, **물리적으로 분리된 서버**에 두는 것을 권고한다.
  - **하드웨어 토큰**: 저장 정보가 **위·변조·외부 노출이 어려운** 장치. 스마트카드·USB 토큰 등의 보안토큰, 즉 **HSM(Hardware Security Module)**을 의미한다.

> **🍼 쉬운 설명**  
> 키를 일반 서버 파일에 두는 건 "현관 비밀번호를 현관문에 붙여 두는" 격이다. **HSM**은 "비밀번호를 절대 안 꺼내 주는 금고" — 키를 안에 넣어 두고 **암·복호화 연산만 대신** 해 주므로 키 자체가 밖으로 나오지 않는다.
{: .prompt-tip }

## 5. 난수(Random Number)

키·IV·nonce·솔트·OTP 씨앗 등 암호의 거의 모든 "비밀의 출발점"은 **난수**다. 난수가 예측되면 그 위에 쌓은 보안 전체가 무너진다.

### 5.1 난수의 용도

| 용도 | 어디서 쓰나 |
|---|---|
| **키 생성** | 대칭키 암호, 메시지 인증 코드(MAC) |
| **키쌍 생성** | 공개키 암호, 전자서명 |
| **초기화 벡터(IV) 생성** | 블록 암호 모드 CBC·CFB·OFB |
| **비표(nonce) 생성** | 재전송 공격 방지, 블록 암호 CTR 모드 |
| **솔트 생성** | 패스워드 기반 암호(PBE) |
| **일회용 패드/패딩** | 패딩에 쓰는 열 생성 |

### 5.2 난수의 성질 (3가지)

난수의 성질은 다음 3가지로 분류하며, **위에서 아래로 갈수록 더 엄격한 조건**이 된다.

```
┌───────────────────────────────────────────┐
│ 무작위성 (Randomness)                        │  통계적 편중 없이 무작위
│  ┌───────────────────────────────────────┐ │
│  │ 예측 불가능성 (Unpredictability)         │ │  과거 수열로 다음 수 예측 불가
│  │  ┌─────────────────────────────────┐  │ │
│  │  │ 재현 불가능성 (Irreproducibility)  │  │ │  같은 수열을 재현 불가
│  │  └─────────────────────────────────┘  │ │
│  └───────────────────────────────────────┘ │
└───────────────────────────────────────────┘
```

| 성질 | 의미 |
|---|---|
| **무작위성** | 통계적인 편중 없이 수열이 무작위로 되어 있는 성질 |
| **예측 불가능성** | 과거의 수열로부터 다음 수를 예측할 수 없는 성질 |
| **재현 불가능성** | 같은 수열을 재현할 수 없는 성질 (재현하려면 수열 자체를 보존하는 수밖에 없음) |

> **🍼 쉬운 설명**: 주사위가 "무작위"여도, 굴리는 패턴을 알면 다음이 "예측"될 수 있다. 암호용 난수는 **예측·재현까지 불가능**해야 진짜 안전하다. (그래서 "통계적으로 고르다"만으로는 부족하다)
{: .prompt-tip }

### 5.3 의사난수 생성기 (PRNG)

- **RNG(Random Number Generator, 난수생성기)**: 하드웨어로 **열·음(소리)의 변화**처럼 예측·재현이 사실상 불가능한 **자연 현상을 센서로 감지**해 난수를 생성한다.
- **PRNG(Pseudo Random Number Generator, 의사난수 생성기)**: 난수(실제로는 **의사난수**)를 생성하는 **소프트웨어**. 소프트웨어만으로는 진정한 난수를 만들 수 없어 "**의사**"가 붙는다.

**PRNG의 구조**: 내부에 **「내부상태」**(관리하는 메모리 값)를 가지며, 외부에서 받은 **「종자(seed)」**를 기초로 의사난수열을 생성한다.

```
 종자(Seed) ──▶ [내부 상태 초기화] ──▶ 내부 상태 ──▶ 의사난수열(pseudo random number)
```

> **🔑 핵심**: PRNG는 **같은 seed면 같은 수열**이 나온다(재현 가능!). 그래서 암호에서는 **seed 자체가 예측 불가능한 양질의 난수**여야 하고, **절대 노출되면 안 된다.** seed가 새면 이후 모든 "난수"가 공격자에게 뻔히 보인다 → 키·IV·OTP가 전부 위험해진다.
{: .prompt-warning }

## 6. 난수가 무너뜨린 실제 사건들

"난수가 예측되면 그 위의 보안 전체가 무너진다"는 5장의 명제는 과장이 아니다. 역사가 세 번 증명했다.

> **📜 역사 한 토막 — 난수 잔혹사 3연발**
>
> **1995년, 넷스케이프 SSL.** 버클리의 대학원생 Goldberg와 Wagner는 넷스케이프 브라우저가 SSL 세션키의 seed를 **현재 시각과 프로세스 번호**로 만든다는 사실을 리버스 엔지니어링으로 알아냈다. 둘 다 공격자가 추측할 수 있는 값이라, 128비트 키가 **수십 초에서 수 분 만에** 복원되었다. 암호 알고리즘은 멀쩡했다 — seed가 문제였다.
>
> **2008년, 데비안 OpenSSL.** 리눅스 배포판 Debian의 관리자가 메모리 검사 도구의 경고를 없애려고 **코드 두 줄을 주석 처리**했는데, 하필 그 줄이 난수 풀에 엔트로피를 섞는 핵심부였다. 그 결과 약 2년 동안 이 배포판에서 생성된 모든 SSH·SSL 키의 경우의 수가 **사실상 32,768가지**로 줄었고, 전 세계 서버가 키를 재발급해야 했다.
>
> **2013년, Dual_EC_DRBG.** NIST 표준 난수 생성기 중 하나였던 이 알고리즘은 2007년부터 "특정 상수를 만든 자는 출력을 예측할 수 있다"는 백도어 가능성이 지적되어 왔는데, 스노든이 공개한 문서로 **NSA가 표준화에 개입한 정황**이 드러났다. 보안 회사 RSA Security가 이를 자사 제품의 기본값으로 채택하는 대가로 1,000만 달러를 받았다는 보도까지 나오며 파문이 커졌고, NIST는 사용 중단 권고를 거쳐 개정판(SP 800-90A Rev.1, 2015)에서 이 알고리즘을 최종 삭제했다.
>
> 세 사건의 공통점: **깨진 것은 암호 알고리즘이 아니라 언제나 난수였다.** ([④ ECC 편의 PS3 사건](/posts/infosec-5-crypto-3-4-ecc/)도 같은 계보다.)
>
> *근거: I. Goldberg·D. Wagner, "Randomness and the Netscape Browser"(Dr. Dobb's Journal, 1996년 1월호); Debian 보안 권고 DSA-1571-1 / CVE-2008-0166(2008); D. Shumow·N. Ferguson의 CRYPTO 2007 럼프 세션 발표, New York Times(2013.9)·Reuters(2013.12) 보도, NIST SP 800-90A Rev.1(2015).*
{: .prompt-tip }
