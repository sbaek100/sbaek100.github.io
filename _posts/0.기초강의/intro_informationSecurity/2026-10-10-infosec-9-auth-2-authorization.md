# 인가(Authorization)

> 앞 글 인증 **[① 지식 기반](/posts/infosec-9-auth-1-1-authentication/)** · **[② 소유·생체 기반](/posts/infosec-9-auth-1-2-possession-biometric/)** 에서 "당신이 누구인지"를 확인했다면, 이 글은 인증을 통과한 사용자가 **"무엇을 할 수 있는가"**를 정하는 **인가(Authorization)**를 다룬다.
{: .prompt-info }

접근통제 4단계(식별 → 인증 → **인가** → 책임추적성) 중 세 번째 단계다.

- 인증(Authentication): "Who are you?" (누구인가?)
- 인가(Authorization): "What permissions do you have?" (어떤 권한을 가졌는가?)

---

## 1. 인가 개요

**인가(authorization)** 는 인증된 사용자의 행동을 제한하는 것으로, 접근제어의 일부다.  
이미 인증된 사람이 **할 수 있는 것에 제한을 두는 것**이다.

### 1.1 접근통제 실현 구조

접근통제 실현은 다음 세 요소의 관계로 구성된다.

![560](/assets/img/posts/2026-06-01-infosec-9-auth-1-1780301491676.png)

| 요소 | 설명 | 예시 |
|---|---|---|
| **주체(Subject)** | 접근을 요청하는 주체 | 사람, 프로그램, 프로세스 |
| **객체(Object)** | 보호되어야 할 자원 | 파일, DB, 컴퓨터 |
| **접근(Access)** | 주체가 객체에 가하는 행위 | Read, Write, Delete |

#### 1. 정책 (Policy) — _무엇을(What)_

자원에 접근하는 **제한 조건(규칙)을 정의**하는 단계. "직원은 자기 부서 문서만 본다" 같은 **상위 원칙**이에요.

|종류|의미|예|
|---|---|---|
|**MAC** (강제적)|시스템(관리자)이 정한 등급에 따라 강제 통제. 사용자가 못 바꿈|군사·기밀 시스템 (1급/2급 비밀)|
|**DAC** (임의적)|자원 **소유자**가 권한을 직접 부여|내 파일을 친구에게 공유 (구글 드라이브)|
|**RBAC** (역할기반)|사람이 아니라 **역할(직책)** 에 권한 부여|"팀장" 역할이면 결재 권한 부여|

#### 2. 모델 (Model) — _어떻게 표현(How to express)_

정책을 **수학적·논리적으로 엄밀하게 표현**한 설계도. 사람 말("기밀은 보호한다")을 컴퓨터가 검증 가능한 **규칙**으로 바꾼 것입니다.

|모델|보호 목표|핵심 규칙 (쉽게)|
|---|---|---|
|**Bell-LaPadula**|**기밀성**(Confidentiality)|"위로 못 읽고, 아래로 못 쓴다" — 낮은 등급이 높은 비밀을 못 읽고, 높은 등급이 낮은 곳에 비밀을 흘리지 못함|
|**Biba**|**무결성**(Integrity)|벨-라파듈라의 **반대** — "아래로 못 읽고, 위로 못 쓴다" — 신뢰도 낮은 데이터가 중요 데이터를 오염시키지 못함|

💡 **외우는 팁:** Bell-LaPadula는 **기밀**(비밀이 새지 않게), Biba는 **무결성**(데이터가 오염되지 않게). 둘은 정확히 **거울처럼 반대** 규칙입니다.

#### 3. 메커니즘 (Mechanism) — _실제 구현(How to enforce)_

모델의 규칙대로 **실제 요청을 검사하고 허용/차단**하는 구체적 도구·기술.

|메커니즘|의미|비유|
|---|---|---|
|**ACL** (Access Control List)|**자원** 입장에서 "누가 접근 가능한지" 목록으로 관리|파일에 붙은 "출입 허가자 명단"|
|**CL** (Capability List)|**사용자** 입장에서 "내가 접근 가능한 자원" 목록으로 관리|사람이 들고 다니는 "출입증(열쇠 꾸러미)"|

💡 **ACL vs CL 차이:** 같은 정보를 **누구 기준으로 보느냐**의 차이예요.

- **ACL** = 문(자원)에 명단을 붙임 → "이 파일에 접근 가능한 사람: A, B"
- **CL** = 사람(주체)에게 열쇠를 줌 → "A가 가진 권한: 파일1 읽기, 파일2 쓰기"

## 2. 접근통제 정책 3종: MAC · DAC · RBAC

앞의 정책 표(§1.1)에서 살펴본 **MAC · DAC · RBAC** 는 "권한을 **누가, 무엇을 기준으로** 정하느냐"가 서로 다르다.  
한 줄로 요약하면 — **MAC은 시스템(관리자)이**, **DAC은 자원 소유자가**, **RBAC은 역할(직책)이** 권한을 정한다.

### 2.1 DAC (임의적 접근통제, Discretionary Access Control)

**개요.** 자원의 **소유자(Owner)** 가 자기 **재량(discretion)** 으로 다른 사용자에게 권한을 주거나 회수하는 방식이다. "내 파일이니 내가 누구에게 공유할지 정한다"가 핵심이며, **사용자 신원(ID) 기반**으로 동작한다.

- **권한 결정 주체:** 자원의 **소유자(사용자)**
- **판단 기준:** 주체의 **신원(Identity)** — 보통 ACL로 표현
- **특징:** 가장 널리 쓰임. 소유자가 권한을 **다른 사용자에게 넘겨줄(전파)** 수 있다. 대부분의 OS 파일 권한(Windows·Linux), 구글 드라이브 공유가 이 방식.

| 장점 | 단점 |
|---|---|
| 유연하고 **사용·구현이 쉬움** | 권한이 **전파**되면 관리자가 흐름을 통제하기 어려움 |
| 소유자가 직접 공유 → **협업에 편리** | **트로이목마·악성코드**가 소유자 권한을 도용하면 그대로 유출 |
| 일반 상용 환경(OS 등)에 적합 | 중앙 통제가 약해 **일관성·보안 수준이 낮음** |

### 2.2 MAC (강제적 접근통제, Mandatory Access Control)

**개요.** **시스템(보안 관리자)** 이 정한 **보안 등급/라벨(label)** 에 따라 접근을 **강제로(mandatory)** 통제하는 방식이다. 주체와 객체 모두에 보안 등급(예: 극비·비밀·기밀·일반)을 부여하고, 그 등급 관계로만 접근을 허용한다. **소유자라도 권한을 임의로 바꿀 수 없다.**

- **권한 결정 주체:** **시스템 / 중앙 보안 관리자**
- **판단 기준:** 주체·객체에 붙은 **보안 등급(라벨)**
- **특징:** **BLP(기밀성)·Biba(무결성)** 같은 모델로 구현(§4). **정보 흐름 자체를 통제**해 유출을 막는다. 군사·정부 기밀 시스템이 대표적.

| 장점 | 단점 |
|---|---|
| **가장 강력하고 엄격한** 보안 | **유연성이 낮고** 일반 업무 환경에 부적합 |
| 중앙 통제 → **정책이 일관됨** | 라벨 설계·운영이 **복잡하고 비용이 큼** |
| 내부자·소유자도 못 바꿔 **정보 유출 차단** | 사용자가 **불편**하게 느낄 수 있음 |

### 2.3 RBAC (역할기반 접근통제, Role-Based Access Control)

**개요.** 권한을 **사용자 개인이 아니라 조직의 '역할(Role, 직책)'에 부여**하고, 사용자는 그 역할을 할당받아 권한을 얻는 방식이다. 구조는 **사용자 → 역할 → 권한** 의 2단계 연결이다. 예: "팀장" 역할에 결재 권한을 주고, 김 과장을 "팀장" 역할에 배정.

- **권한 결정 주체:** **관리자**(역할을 정의하고 권한을 매핑)
- **판단 기준:** 사용자에게 부여된 **역할(직무)**
- **특징:** 사용자가 바뀌어도 **역할만 갈아 끼우면** 되어 관리가 단순. **최소권한·직무분리(SoD)** 원칙을 적용하기 좋다. 기업 ERP, 클라우드 권한 관리(AWS IAM 등)에서 표준처럼 쓰인다.

| 장점 | 단점 |
|---|---|
| 대규모 조직에서 **관리가 효율적** | 초기 **역할 설계가 어렵다** |
| 인사이동 시 **역할만 변경** → 실수↓ | 역할이 지나치게 늘어나는 **역할 폭증(role explosion)** |
| **최소권한·직무분리** 적용 용이 | 시간·위치 같은 **상황 기반 통제는 부족** (→ ABAC로 보완) |

### 2.4 세 정책 비교

| 비교 기준 | **DAC** (임의적) | **MAC** (강제적) | **RBAC** (역할기반) |
|---|---|---|---|
| **권한 결정 주체** | 자원 **소유자** | **시스템(관리자)** | **관리자**(역할 정의) |
| **판단 기준** | 주체의 **신원(ID)** | 보안 **등급(라벨)** | 사용자의 **역할** |
| **유연성** | 높음 | 낮음(엄격) | 중간 |
| **보안 수준** | 낮음 | **가장 높음** | 중간~높음 |
| **관리 부담** | 작음(소규모) / 큼(대규모) | 큼 | **작음**(대규모에 유리) |
| **권한 전파** | 가능(소유자가 위임) | 불가 | 역할 통해 통제 |
| **대표 사용처** | 일반 OS, 구글 드라이브 | 군사·정부 기밀 | 기업 ERP, 클라우드 IAM |

> **한 줄 정리.** **DAC**는 *"내 것은 내가 공유"*(편하지만 약함), **MAC**은 *"등급대로 강제"*(강력하지만 빡빡함), **RBAC**은 *"직책대로 부여"*(조직 운영에 현실적). 그래서 군·정부는 MAC, 일반 PC는 DAC, 기업은 RBAC을 주로 쓴다.

## 3. 접근제어 행렬(Access Control Matrix)

인가에 대한 전통적인 관점은 **램슨(Lampson)의 접근제어 행렬**에서 시작한다.  
인가의 두 가지 기본 구조는 **접근제어 목록(ACL)** 과 **권한 목록(C-list)** 이다.

### 3.1 접근제어 행렬 예시

| | OS | 회계 프로그램 | 회계 데이터 | 보험 데이터 | 월급 데이터 |
|---|---|---|---|---|---|
| 밥 | rx | rx | r | — | — |
| 앨리스 | rx | rx | r | rw | rw |
| 샘 | rwx | rwx | r | rw | rw |
| 회계 프로그램 | rx | rx | rw | rw | r |

### 3.2 접근제어 목록 (ACL)

접근제어 행렬을 **열(Column) 단위로** 나누어, 각 열을 상응하는 객체와 함께 저장한다.

- 객체에 대해 접근할 때마다 접근제어 행렬의 열을 확인하여 특정 연산을 허락할지 여부를 결정
- 예: 보험 데이터에 상응하는 ACL = `(밥, --), (앨리스, rw), (샘, rw), (회계 프로그램, rw)`

### 3.3 권한 목록 (C-list)

접근제어 행렬을 **행(Row) 단위로** 저장하는 것.

- 각 행은 상응하는 주체와 함께 저장됨
- 어떤 주체가 연산을 수행하려고 할 때마다 접근제어 목록에 있는 열을 확인
- 앨리스의 권한 목록 = `(OS, rx), (회계 프로그램, rx), (회계 데이터, r), (보험 데이터, rw), (월급 데이터, rw)`

## 4. 접근통제 보안 모델(Security Models)

> 보안 모델은 정책을 **수학적·논리적 규칙으로 엄밀하게 표현한 설계도**다(§1.1 참고).  
> 크게 **기밀성** 모델(BLP), **무결성** 모델(Biba·Clark-Wilson), **이해충돌 방지** 모델(Chinese Wall)로 나뉜다.  
> 아래에서 각 모델의 *개요 → 보안규칙 → 장단점* 을 살펴보고, 마지막 §4.7에서 한 표로 비교한다.
{: .prompt-info }

### 4.1 다단계 보안(MLS; Multi Level Security) 개요

- 주체가 사용자이며 객체는 보호되어야 할 데이터
- 취급 등급은 주체에게 적용되지만 기밀 등급은 객체에 적용
- 미국 국방성의 4단계 기밀 등급: **극비 > 비밀 > 기밀 > 일반 평문**
- 다단계 보안의 응용 프로그램으로 네트워크 방화벽이 있음


---

### 4.2 벨-라파둘라 모델 (BLP; Bell-LaPadula) — 기밀성

**개요.** 1970년대 미국 국방성을 위해 만들어진 **최초의 수학적 보안 모델**로, **기밀성(Confidentiality)** 보호가 목표다. 주체·객체에 보안 등급(라벨)을 부여하는 **MAC** 환경에서, *높은 등급의 비밀이 낮은 등급으로 새어 나가지 않도록* 정보 흐름을 통제한다.

**목적**: 다단계 보안 시스템이 만족시켜야 하는 최소한의 기밀 요구사항을 캡처하는 것.

**두 가지 규칙:**

| 규칙 | 조건 | 의미 |
|---|---|---|
| **단순 보안 조건** (No Read Up) | $L(O) \leq L(S)$일 경우에만 주체 $S$는 객체 $O$를 읽을 수 있다 | 낮은 등급의 주체는 높은 등급의 객체를 읽을 수 없음 |
| **\*-특성 (스타 특성)** (No Write Down) | $L(S) \leq L(O)$일 경우에만 주체 $S$는 객체 $O$를 쓸 수 있다 | 높은 등급의 주체는 낮은 등급의 객체에 쓸 수 없음 |

**결과적으로 BLP는 '상향 읽기 금지 및 하향 쓰기 금지'로 명확하게 기술된다.**

![568](/assets/img/posts/2026-06-01-infosec-9-auth-1-1780301531605.png)

| 행위 | 허용 | 금지 |
|---|---|---|
| READ | 하위 레벨 문서 읽기 허락 (Read Down) | 상위 레벨 문서 읽기 금지 (No Read Up) |
| WRITE | 상위 레벨 문서 쓰기 허락 (Write Up) | 하위 레벨 문서 쓰기 금지 (No Write Down) |

**장점과 단점**

| 장점 | 단점 |
|---|---|
| 기밀성 보호를 **수학적으로 엄밀하게** 보장 | **기밀성만** 다루고 **무결성은 보호하지 못함**(낮은 등급이 위로 쓰는 건 허용 → 데이터 오염 가능) |
| 군사·정부 등 **등급 기반 환경에 적합** | 등급이 고정적이라 **현실의 유연한 업무**엔 부적합 |
| 정보 유출(하향 흐름)을 원천 차단 | "위로 쓰기 허용"이 **블라인드 쓰기**(못 읽는 곳에 쓰기) 같은 비현실적 상황을 낳음 |

> **한계 메모.** BLP는 *"비밀이 새지 않게"* 만 신경 쓴다. 그래서 **낮은 신뢰도 사용자가 중요한 파일을 오염시키는 무결성 문제**는 못 막는다 — 이걸 보완하려고 나온 것이 다음의 **Biba**다.
{: .prompt-warning }

### 4.3 비바 모델 (Biba's Model) — 무결성

**개요.** BLP가 기밀성을 다루는 데 반해, **비바 모델은 무결성(Integrity)을 다룬다.** *신뢰도(무결성 등급)가 낮은 데이터·주체가 중요한(높은) 데이터를 오염시키지 못하도록* 막는 것이 목표다. 규칙이 BLP와 정확히 **거울처럼 반대**라는 점이 특징이다.

BLP는 기밀성을 다루는 데 반해, **비바 모델은 무결성을 다룬다.**

$I(O)$를 객체 $O$의 무결성, $I(S)$를 주체 $S$의 무결성이라고 하자.

| 규칙 | 조건 | 의미 |
|---|---|---|
| **쓰기 접근 규칙** | $I(O) \leq I(S)$인 경우에만 주체 $S$는 객체 $O$를 쓸 수 있다 | No Write Down (하향 쓰기 금지) |
| **읽기 접근 규칙** | $I(S) \leq I(O)$인 경우에만 주체 $S$는 객체 $O$를 읽을 수 있다 | No Read Down (하향 읽기 금지) |

![567](/assets/img/posts/2026-06-01-infosec-9-auth-1-1780301546892.png)


| 행위    | 허용                          | 금지                            |
| ----- | --------------------------- | ----------------------------- |
| READ  | 상위 레벨 문서 읽기 허락 (Read Up)    | 하위 레벨 문서 읽기 금지 (No Read Down) |
| WRITE | 하위 레벨 문서 쓰기 허락 (Write Down) | 상위 레벨 문서 쓰기 금지 (No Write Up)  |

$S$가 더 낮은 무결성 수준의 객체를 보지 않도록 방지하기 때문에 비바 모델은 실제적으로 아주 엄격하다.

**저수위 원칙**: 주체 $S$가 객체 $O$를 읽으면 $I(S) = \min(I(S), I(O))$이다.

**장점과 단점**

| 장점 | 단점 |
|---|---|
| **무결성**(데이터 오염 방지)을 수학적으로 보장 | **기밀성은 다루지 못함**(BLP와 상호 보완 관계) |
| BLP와 **대칭 구조**라 함께 적용하기 쉬움 | "하향 읽기 금지"가 지나치게 엄격해 **실무에서 비현실적** |
| 멀웨어·저신뢰 입력의 상향 오염을 차단 | 무결성을 *등급*으로만 봐서 **상업적 무결성(거래 절차)** 은 표현 못 함 |

> **BLP ↔ Biba 핵심 대비.** BLP = *위로 못 읽고 아래로 못 쓴다(기밀)* / Biba = *아래로 못 읽고 위로 못 쓴다(무결)*. 둘 다 **등급 기반**이라, "거래 절차의 정당성" 같은 **상업적 무결성**은 다음의 **Clark-Wilson**이 맡는다.
{: .prompt-tip }

### 4.4 구획 (Compartment)

일반적으로 보안 등급의 간단한 계층적 구조는 대부분의 상황을 다루기에 유연하지 못하다.  
실제적으로는 보안 등급에 '걸쳐서' 정보 흐름을 더 제한하도록 **구획(Compartment)** 을 사용할 필요가 있다.

**표기법**: `보안 등급 {구획명}`

예: 극비 등급 내에 '고양이'와 '개' 구획이 있음
- `극비{고양이}`, `극비{개}`, `극비{고양이,개}`

구획은 **지식 한정 원칙(Need to Know)** 을 실현하는 일을 담당한다.

### 4.5 클락-윌슨 모델 (Clark-Wilson) — 상업용 무결성

**개요.** BLP·Biba가 **군사용 등급(라벨)** 에 초점을 맞췄다면, 클락-윌슨은 **은행·기업 같은 상업 환경의 무결성**을 위해 만들어졌다. "등급" 대신 **잘 짜인 거래 절차**와 **직무 분리**로 데이터의 정확성과 일관성을 지킨다. 핵심 아이디어는 *사용자가 데이터를 직접 주무르지 못하게 하고, 검증된 프로그램(절차)을 통해서만 바꾸게 한다*는 것이다.

**핵심 구성 요소**

| 요소 | 의미 |
|---|---|
| **CDI** (Constrained Data Item) | 무결성을 **보호해야 하는** 데이터 (예: 계좌 잔액) |
| **UDI** (Unconstrained Data Item) | 보호 대상이 아닌 일반 데이터 (예: 사용자 입력 원본) |
| **TP** (Transformation Procedure) | CDI를 바꾸는 **잘 정의된 거래 절차**(트랜잭션) |
| **IVP** (Integrity Verification Procedure) | CDI가 유효한 상태인지 **검증**하는 절차 |
| **접근 3요소(Access Triple)** | 주체는 CDI에 직접 못 가고 **`사용자 → TP → CDI`** 형태로만 접근 |

**두 가지 보안 규칙**

| 규칙 | 의미 |
|---|---|
| **잘 구성된 거래** (Well-formed Transaction) | 사용자가 데이터를 임의로 못 바꾸고, **정해진 절차(TP)로만** 변경 → 절차마다 로그가 남아 **감사 추적** 가능 |
| **직무 분리** (Separation of Duty) | 하나의 거래를 **여러 사람이 나눠** 수행 (예: 입력자 ≠ 승인자) → 한 사람의 단독 부정 차단 |

**장점과 단점**

| 장점 | 단점 |
|---|---|
| **실제 상거래·회계 환경에 가장 적합** | 절차(TP)·검증(IVP)을 일일이 정의해야 해 **구현이 복잡** |
| 감사 추적·직무 분리로 **내부 부정 방지** | 운영·관리 **부담이 큼** |
| 데이터의 **정확성·일관성** 보장 | 등급 기반 모델보다 **이론이 덜 단순** |

### 4.6 차이니즈 월 모델 (Chinese Wall / Brewer-Nash) — 이해충돌 방지

**개요.** **이해충돌(Conflict of Interest)** 방지를 목표로 하는 모델로, 컨설팅·법률·금융처럼 한 사람이 **경쟁 관계인 두 고객의 정보를 동시에 보면 안 되는** 환경을 위해 만들어졌다. 가장 큰 특징은 **동적 접근통제** — *과거에 무엇을 봤느냐에 따라 앞으로 접근할 수 있는 대상이 달라진다*. 한 번 한쪽 벽 안으로 들어가면 반대편(경쟁사)으로는 벽이 생겨 막힌다.

**핵심 개념**

- **회사 데이터셋(Company Dataset):** 같은 회사에 속한 객체들의 묶음
- **이해충돌 클래스(CoI Class):** **서로 경쟁하는 회사**들을 묶은 그룹 (예: `{A은행, B은행}`)
- 사용자가 A은행 데이터를 한 번 열람하면, **같은 CoI 클래스의 B은행**(경쟁사)은 이후 접근이 **차단**된다.

**두 가지 보안 규칙**

| 규칙 | 의미 |
|---|---|
| **읽기 규칙** (단순 보안) | 같은 CoI 클래스에서 **아직 아무 회사도 접근하지 않았을 때만** 읽기 허용 |
| **쓰기 규칙** (*-속성) | 다른 회사 정보가 **간접적으로 새어 나가지 않도록** 쓰기를 제한 |

**장점과 단점**

| 장점 | 단점 |
|---|---|
| **이해충돌을 원천 차단** (컨설팅·금융에 현실적) | 접근할수록 **벽이 쌓여** 접근 가능 범위가 점점 좁아짐 |
| 과거 이력을 반영하는 **동적·유연한** 통제 | 이력 추적이 필요해 **구현이 복잡** |
| 기밀성 + 무결성 요소를 **함께** 고려 | 한 번 정해진 벽은 **되돌리기 어려움** |

### 4.7 보안 모델 비교 분석

| 모델 | 보호 목표 | 핵심 규칙 | 적용 분야 | 장점 | 단점 |
|---|---|---|---|---|---|
| **Bell-LaPadula** | **기밀성** | No Read Up / No Write Down (위로 못 읽고, 아래로 못 씀) | 군사·정부 기밀 | 기밀 유출 원천 차단, 수학적으로 엄밀 | 무결성 미보호, 경직됨 |
| **Biba** | **무결성** | No Read Down / No Write Up (아래로 못 읽고, 위로 못 씀) | 데이터 오염 방지 | 저신뢰 오염 차단, BLP와 대칭 | 기밀성 미보호, 지나치게 엄격 |
| **Clark-Wilson** | **상업적 무결성** | 잘 구성된 거래 + 직무 분리 (`사용자→TP→CDI`) | 은행·회계·기업 | 실무 적합, 감사·내부부정 방지 | 절차 정의 복잡, 관리 부담 |
| **Chinese Wall** | **이해충돌 방지** | 같은 CoI 클래스 접근 이력에 따라 동적 차단 | 컨설팅·법률·금융 | 이해충돌 차단, 동적·유연 | 접근 제약 누적, 구현 복잡 |

> **큰 그림.** **BLP**(기밀)와 **Biba**(무결)는 *군사용·등급 기반*의 고전 모델로 서로 거울 관계다.  
> **Clark-Wilson**(거래 무결성)과 **Chinese Wall**(이해충돌)은 *상업 환경의 현실 문제*를 풀기 위해 등장했다.  
> 즉 **"무엇을 지키려는가"** — 기밀이냐, 무결이냐, 거래 절차냐, 이해충돌이냐 — 가 모델 선택의 기준이다.

![547](/assets/img/posts/2026-06-01-infosec-9-auth-1-1780301588574.png)

- 은닉 채널은 정보가 흘러가는 또 다른 길을 제공
- 몇몇 해킹 도구는 네트워크상에서의 은닉 채널을 악용

## 6. CAPTCHA

### 6.1 튜링 테스트 (Turing Test)

컴퓨터 개척자이자 이니그마의 해독자인 **앨런 튜링(Alan Turing)** 이 1950년에 제안한 테스트.

![518](/assets/img/posts/2026-06-01-infosec-9-auth-1-1780301608057.png)


- 이 테스트에서는 한 사람이 다른 사람과 컴퓨터에게 질문을 던짐
- 질문자는 오직 키보드로만 질문을 던질 수 있고, 응답도 컴퓨터 스크린에만 나타남
- 질문자는 어느 쪽이 컴퓨터인지 사람인지 모르며, 목표는 오직 질문과 답변으로만 구별해내는 것
- 만약 사람 질문자가 추측하는 것 이상의 확률로 이 퍼즐을 풀 수 없다면 컴퓨터는 튜링 테스트를 통과한 것 — **어떤 컴퓨터도 아직 튜링 테스트를 통과하지 못함**

### 6.2 CAPTCHA

**CAPTCHA** = **C**ompletely **A**utomated **P**ublic **T**uring test to tell **C**omputers and **H**umans **A**part

- 컴퓨터와 사람을 구별 짓는 완전히 자동화된 공개 튜링 테스트
- 사람은 통과할 수 있지만 컴퓨터는 확률상 통과할 수 없음 (**역튜링 테스트**)
- 캡차는 사람이 아닌 컴퓨터가 자원에 접근하는 것을 막기 위해 설계되었기 때문에 **접근제어의 한 형태**

![573](/assets/img/posts/2026-06-01-infosec-9-auth-1-1780301629282.png)


### 6.3 보안에서 CAPTCHA가 중요한 이유

| 역할 | 설명 |
|---|---|
| **자동화된 봇 공격 방지** | 자동화된 봇이 대량으로 계정을 생성하거나, 로그인을 시도하거나, 스팸을 게시하는 공격 차단 |
| **서비스 남용 방지** | 티켓 예매, 설문 조사, 투표 시스템 등에서 자동화된 프로그램이 시스템을 조작하거나 과부하를 일으키는 것을 방지 |
| **무차별 대입 공격 방지** | 로그인 시도 횟수를 제한하고 자동화된 비밀번호 크래킹을 어렵게 만듦 |
| **데이터 스크래핑 방지** | 웹 크롤러가 대량으로 데이터를 수집하는 것을 제한 |
| **DDoS 공격 완화** | 자동화된 요청을 필터링하여 웹사이트의 과부하를 방지 |
