# 암호제품 평가체계 — CC·EAL·CCRA와 암호모듈 검증

---

앞 글에서는 암호가 **이론적으로** 안전한가를 다루었음. 공격 모델을 정하고 안전성 목표를 정의하는 학술적 층위였음.

그러나 실무에서 제품을 도입하는 사람은 다른 질문을 함. **"이 제품에 들어간 암호가 제대로 만들어졌다는 것을 누가 보증하는가?"** 논문으로 증명된 알고리즘이라도, 그것을 구현한 소스 코드에 버그가 있거나 키를 하드코딩해 두었다면 아무 소용이 없음.

그래서 **신뢰기관이 검증·인정하는 제도**가 필요함. 이 장은 그 제도를 다룸.

> **두 층위를 혼동하지 말 것**
>
> | 층위 | 질문 | 다루는 곳 |
> |---|---|---|
> | **학술적 안전성** | 이 알고리즘은 어떤 공격 모델 하에서 무엇을 보장하는가 | 앞 글 (COA·KPA·CPA·CCA / OW·IND·NM) |
> | **제도적 검증** | 이 제품을 신뢰기관이 어떤 기준으로 확인했는가 | **이 글** (CC·EAL·CCRA·CMVP) |
>
> 둘 다 "암호 알고리즘의 안전성 평가"라고 불리지만 전혀 다른 이야기임. 시험에서도 자주 섞여 출제됨.
{: .prompt-warning }

## Part 1. 평가체계의 전체 구조

### 1.1 기본 선택 기준은 신뢰기관의 평가 결과임

- 정보보호제품의 안전한 선택·사용을 위한 기본 선택기준은 **신뢰기관의 안전성 평가 결과**임. 가장 대표적인 것이 **CC(Common Criteria)** 기반의 정보보호제품 평가임.
- 단, CC 기반 평가기준에서는 핵심기술인 **암호 알고리즘에 대한 평가기준을 따로 명시하지 않고**, 각국이 **독자적으로** 하도록 규정함. 이를 구현한 **암호모듈**에 대한 평가 또한 독자적으로 하도록 규정함.
- 암호모듈에 대한 안전성 평가로 가장 널리 참조되는 것은 미국 **NIST**가 수행하는 **CMVP(Cryptographic Module Validation Program)** 이며, 세계적으로 인정받음.

> **FIPS(Federal Information Processing Standards Publication)**
> NIST가 발행하는 정보처리 관계 출판물("핍스"). 예: 암호모듈 **FIPS 140-2**, 암호알고리즘(AES) **FIPS 197**.
{: .prompt-info }

### 1.2 평가는 동심원 계층으로 이루어짐

평가는 **암호 알고리즘 → 암호모듈 → 정보보호제품 → 응용시스템**의 동심원 계층으로 이루어짐.

```
┌───────────────────────────────────────────────┐
│ 응용 시스템 (Application System)                 │  ← 항공관제센터 등 (Common Criteria)
│  ┌─────────────────────────────────────────┐  │
│  │ 정보보호제품 (Security Product)            │  │  ← 침입차단/탐지시스템 (Common Criteria)
│  │  ┌───────────────────────────────────┐  │  │
│  │  │ 암호모듈 (Crypto Module)            │  │  │  ← FIPS 140-2 / CMVP · KCMVP
│  │  │  ┌─────────────────────────────┐  │  │  │
│  │  │  │ 암호알고리즘 (Crypto Algorithm) │  │  │  │  ← AES / FIPS 197
│  │  │  └─────────────────────────────┘  │  │  │
│  │  └───────────────────────────────────┘  │  │
│  └─────────────────────────────────────────┘  │
└───────────────────────────────────────────────┘
```

| 평가 종류 | 대상 | 설명 |
|---|---|---|
| ① 암호 알고리즘 평가 | 탑재된 암호 알고리즘 | 알고리즘 **자체만** 평가 → 제품·시스템과 **독립적**으로 평가 가능. 일반적으로 알고리즘의 **이론적 안전성**만 평가 |
| ② 암호모듈 평가 | 암호서비스(기밀성·무결성 기능 모듈) | 이론적 안전성과는 **별도로**, 암호서비스 기능을 제공하는 **모듈의 안전성** 평가 |
| ③ 정보보호제품 평가 | 암호모듈 탑재 제품 | 예) 침입차단시스템(IPS), 침입탐지시스템(IDS) |
| ④ 응용시스템 평가 | 제품을 상호 연동한 시스템 | 예) 국가기관망 네트워크 보안성, 항공관제센터 안전성 |

> ①의 "이론적 안전성"이 바로 앞 글에서 다룬 **공격 모델과 안전성 개념(IND-CCA2 등)** 임. 두 글이 여기서 만남.
{: .prompt-info }

### 1.3 평가 순서

- 응용시스템의 안전성을 직접 평가하는 것이 가장 바람직하나, 평가 기준·방법·체계를 마련하고 탑재 기술을 개별적으로 평가하기가 **상당히 어려움**.
- 따라서 응용시스템의 **가장 기본이 되는 암호 알고리즘**에 대한 안전성 평가가 **우선**되어야 함.
- 결국 다음 순서로 평가를 수행하는 것이 바람직함.

$$
\text{암호 알고리즘(이론적 안전성)} \;\rightarrow\; \text{검증된 암호모듈 탑재 정보보호 제품} \;\rightarrow\; \text{제품으로 구성된 응용시스템}
$$

## Part 2. CC — 공통평가기준

> **CC(Common Criteria, 공통평가기준)**
> 선진 각국이 서로 다른 평가 기준으로 평가를 시행하여 초래되던 시간·비용 낭비 등 제반 문제점을 없애기 위해 개발됨. **1998년** 미국·캐나다·영국·프랑스·독일 간에 **상호인정협정(CCRA)** 이 체결됨. CC는 평가 원칙·평가 모델, 보안 기능 요구사항(11개), 7등급 평가를 위한 보증 요구사항(8개)으로 구성됨.
{: .prompt-info }

### 2.1 CC는 왜 만들어졌는가 — 세 기준의 통합

CC 이전에는 나라마다 서로 다른 평가 기준이 존재했음. 대표적으로 미국의 **TCSEC**(1985, 오렌지 북), 유럽의 **ITSEC**(1991), 캐나다의 **CTCPEC**(1993)이 있었음.

문제는 명확했음. 같은 제품을 미국에 팔려면 TCSEC으로, 유럽에 팔려면 ITSEC으로 **각각 다시 평가**받아야 했음. 평가 비용과 기간이 나라 수만큼 늘어나는 구조였음.

그래서 이들 기준을 하나로 합쳐 만든 것이 **CC**임. 1996년 CC 1.0이 발표되었고, 1999년 국제표준 **ISO/IEC 15408**로 채택됨. 이후 CC 3.1(2006, 개정 5판은 2017)을 거쳐 **CC:2022**로 이어지고 있음.

> **한 번 평가받아 여러 나라에서 인정받자.** 이것이 CC의 목적임. 기술 기준을 새로 발명한 것이 아니라, **흩어진 기준을 통합하여 중복 평가를 없애려는 시도**였다는 점이 핵심임.
{: .prompt-tip }

### 2.2 CC의 구성

CC는 세 부분과 별도의 평가방법론으로 이루어짐.

| 문서 | 내용 |
|---|---|
| **CC Part 1** | 소개 및 일반 모델. 평가의 개념과 용어를 정의함 |
| **CC Part 2** | **보안기능요구사항(SFR)** — 제품이 "무엇을 하는가" |
| **CC Part 3** | **보증요구사항(SAR)** — "그것을 믿을 수 있는 근거가 얼마나 되는가" |
| **CEM** | 공통평가방법론(Common Evaluation Methodology). 평가자가 실제로 어떻게 평가하는지의 절차 |

Part 2의 보안기능요구사항은 **11개 클래스**로 구성됨.

| 클래스 | 내용 | 클래스 | 내용 |
|---|---|---|---|
| **FAU** | 보안감사 | **FPR** | 프라이버시 |
| **FCO** | 통신(부인방지) | **FPT** | TSF 보호 |
| **FCS** | 암호 지원 | **FRU** | 자원 활용 |
| **FDP** | 사용자 데이터 보호 | **FTA** | TOE 접근 |
| **FIA** | 식별 및 인증 | **FTP** | 안전한 경로/채널 |
| **FMT** | 보안 관리 | | |

Part 3의 보증요구사항은 **8개 클래스**로 구성됨.

| 클래스 | 내용 | 클래스 | 내용 |
|---|---|---|---|
| **APE** | 보호프로파일(PP) 평가 | **ALC** | 생명주기 지원 |
| **ASE** | 보안목표명세서(ST) 평가 | **ATE** | 시험 |
| **ADV** | 개발 | **AVA** | 취약성 평가 |
| **AGD** | 설명서(지침서) | **ACO** | 구성(composition) |

각 클래스는 **클래스(Class) → 패밀리(Family) → 컴포넌트(Component) → 엘리먼트(Element)** 의 계층으로 세분화됨.

### 2.3 반드시 구분해야 할 세 용어 — TOE · PP · ST

| 용어 | 우리말 | 의미 |
|---|---|---|
| **TOE** (Target of Evaluation) | 평가대상 | 실제로 평가를 받는 제품 또는 시스템과 그 설명서 |
| **PP** (Protection Profile) | 보호프로파일 | **특정 제품군**에 요구되는 보안 요구사항을 **구현과 무관하게** 정리한 문서. "방화벽이라면 이 정도는 갖추어야 한다"는 **수요자·발주자 관점**의 요구사항 명세 |
| **ST** (Security Target) | 보안목표명세서 | **특정 TOE 하나**에 대해 그 제품이 무엇을 어떻게 만족하는지 기술한 **구현 종속적** 문서. **개발자 관점**의 답안지 |

```
   [ PP ]  "방화벽 제품이라면 이런 보안 기능을 갖출 것"   ← 수요자가 요구 (제품 독립적)
      │
      │  (참조)
      ▼
   [ ST ]  "우리 제품 X는 그 요구를 이렇게 만족함"        ← 개발자가 제출 (제품 종속적)
      │
      │  (기술)
      ▼
   [ TOE ] 실제 평가 대상 제품 X                        ← 평가기관이 검증
```

> **암기 포인트** — **PP는 문제지, ST는 답안지, TOE는 답안을 낸 제품**임. 시험에서 PP와 ST를 바꾸어 놓는 문제가 자주 출제됨. 구분 기준은 **구현 독립성**임(PP = 독립적, ST = 종속적).
{: .prompt-tip }

### 2.4 EAL — 평가보증등급 7단계

**EAL(Evaluation Assurance Level, 평가보증등급)** 은 "이 제품을 얼마나 믿을 수 있는가"를 나타내는 등급임. **EAL1부터 EAL7까지 7단계**로 구분됨.

| 등급 | 명칭 | 의미 |
|---|---|---|
| **EAL1** | 기능시험 (Functionally Tested) | 문서와 기능 동작만 확인. 가장 낮은 수준 |
| **EAL2** | 구조시험 (Structurally Tested) | 개발자가 제공한 설계 정보까지 검토 |
| **EAL3** | 방법론적 시험 및 점검 (Methodically Tested and Checked) | 개발 과정의 체계성까지 확인 |
| **EAL4** | 방법론적 설계·시험·검토 (Methodically Designed, Tested and Reviewed) | **상용 제품이 현실적으로 도달 가능한 최고 수준**으로 통용됨 |
| **EAL5** | 준정형적 설계 및 시험 (Semiformally Designed and Tested) | 설계를 준정형적 방법으로 기술 |
| **EAL6** | 준정형적 검증 설계 및 시험 (Semiformally Verified Design and Tested) | 고위험 환경용 |
| **EAL7** | 정형적 검증 설계 및 시험 (Formally Verified Design and Tested) | **수학적으로 정형 검증**. 극히 제한된 소규모 제품에만 적용 가능 |

![](/assets/img/posts/2026-09-26-infosec-7-crypto-evaluation-1786235399456.png)

> **혼동 주의 — EAL은 "제품이 얼마나 안전한가"가 아님.**
> EAL은 **보증(assurance)의 깊이**, 즉 "얼마나 꼼꼼히 확인했는가"를 나타내는 등급임. EAL7을 받은 제품이 EAL2를 받은 제품보다 반드시 안전한 것은 아님. **무엇을(ST에 명시된 보안 기능) 어느 깊이로(EAL) 검증했는지를 함께 보아야** 의미가 있음.
>
> 또한 EAL이 높을수록 평가 기간과 비용이 급격히 늘어남. 그래서 실무에서는 **EAL4**가 상용 제품의 사실상 상한선으로 쓰이며, EAL5 이상은 스마트카드·보안칩처럼 대상이 작고 정형 검증이 가능한 제품에 주로 적용됨.
{: .prompt-warning }

## Part 3. CCRA — 국제상호인정협정

**CCRA(Common Criteria Recognition Arrangement)** 는 한 회원국에서 발급한 CC 인증서를 **다른 회원국이 추가 평가 없이 인정**하도록 한 국제 협정임. 1998년 미국·캐나다·영국·프랑스·독일 간에 체결된 뒤 참여국이 확대되었음.

### 3.1 두 가지 참여 자격

| 자격 | 영문 | 권한 |
|---|---|---|
| **인증서 발행국** | CAP (Certificate Authorising Participant) | 자국에서 CC 평가를 수행하고 **인증서를 발행**할 수 있음. 물론 타국 인증서도 인정함 |
| **인증서 수용국** | CCP (Certificate Consuming Participant) | 인증서를 발행하지는 못하고, 타국 인증서를 **인정만** 함 |

한국은 **인증서 발행국(CAP)** 으로 참여하고 있음.

### 3.2 2014년 개정 — 상호인정 범위의 축소

여기가 실무에서 가장 자주 오해되는 지점임. **2014년 9월 비준된 개정 CCRA**는 상호인정의 범위를 다음과 같이 **좁혔음**.

- **cPP(collaborative Protection Profile) 기반 평가** 결과
- cPP를 쓰지 않은 경우에는 **EAL2 이하**(결함 보완 ALC_FLR 포함)

즉 개정 이전에는 **EAL4까지** 국제적으로 상호인정되었으나, 개정 이후에는 **EAL3 이상은 자동으로 상호인정되지 않음**. 높은 등급을 받아도 그 효력이 인증서를 발급한 나라 안에 머물 수 있다는 뜻임.

```
   [ 2014년 개정 전 ]                    [ 2014년 개정 후 ]

   EAL1 ~ EAL4  → 국제 상호인정          cPP 기반 평가        → 국제 상호인정
   EAL5 ~ EAL7  → 발급국 내에서만        EAL1 ~ EAL2         → 국제 상호인정
                                        EAL3 이상 (cPP 미사용) → 발급국 내에서만
```

> **왜 범위를 줄였는가** — 나라마다 EAL의 실제 평가 엄격도에 차이가 있다는 문제 제기가 있었고, 높은 EAL 평가는 비용과 기간이 과도하다는 비판도 있었음. 그래서 **"등급을 높이 받는 경쟁"에서 "제품군별로 합의된 요구사항(cPP)을 충족했는가"** 로 무게중심을 옮긴 것으로 볼 수 있음.
>
> **cPP**는 국제 기술 커뮤니티(iTC)가 제품군별로 공동 개발한 보호프로파일임. 여러 나라 전문가가 함께 만들었으므로 해석 차이가 줄어듦.
{: .prompt-info }

### 3.3 국내 평가 체계

한국의 CC 평가·인증 체계는 **KECS(Korea Evaluation and Certification Scheme)** 라 부르며, 국가정보원 산하의 **IT보안인증사무국**이 인증 업무를 수행함. 평가는 지정된 평가기관이 담당함.

국내에서는 공공기관에 정보보호제품을 납품할 때 CC 인증을 요구하는 경우가 많으므로, 국내 보안 업체에게 CC 인증 취득은 **사업의 전제 조건**에 가까움.

---

## Part 4. 암호모듈의 안전성 평가 — CMVP와 KCMVP

### 4.1 CMVP

- **CMVP**는 1995년 7월 미국 **NIST**와 캐나다 **CSE(Communications Security Establishment)** 가 공동 개발한, **암호 모듈의 안전성 검증**을 위한 프로그램임.
- CMVP가 요구하는 암호모듈 안전성 평가는 크게 세 가지로 나뉘며, 각 항목에 **안전성 등급**을 설정하여 기준을 마련함.
  - ㉠ 암호기술의 **구현 적합성** 평가
  - ㉡ 암호키 **운용 및 관리**
  - ㉢ **물리적 보안**

> 세 번째 항목인 **물리적 보안**이 왜 필요한지는 앞 글에서 이미 답이 나왔음. **부채널 공격**(타이밍·전력 분석 등) 때문임. 수학적으로 완벽한 알고리즘이라도 구현에서 물리적 정보가 새면 키가 노출됨. 알고리즘 평가와 모듈 평가가 별개인 이유가 이것임.
{: .prompt-tip }

### 4.2 KCMVP

국내에도 대응하는 제도가 있음. **KCMVP(한국 암호모듈 검증제도)** 는 국가·공공기관에서 사용하는 암호모듈의 안전성과 구현 적합성을 검증하는 제도로, 국가정보원이 주관함. 공공 부문에 납품되는 제품이 암호 기능을 포함하면 KCMVP 검증필 암호모듈을 탑재해야 하는 경우가 많음.

### 4.3 CC와 암호모듈 평가의 관계

앞서 언급했듯 CC는 **암호 알고리즘 자체에 대한 평가 기준을 규정하지 않음**. CC의 FCS(암호 지원) 클래스는 "적절한 암호 알고리즘을 규격대로 사용하는가"를 볼 뿐, 그 알고리즘이 수학적으로 안전한지는 판단하지 않음.

따라서 다음과 같이 **역할이 나뉨**을 기억해야 함.

| 대상 | 평가 체계 |
|---|---|
| 암호 알고리즘 | 각국의 독자 검증 체계 (예: 국내 검증대상 암호 알고리즘, 미국 FIPS 197 등) |
| 암호 모듈 | **CMVP** (FIPS 140 계열), 국내는 **KCMVP** |
| 정보보호제품 · 응용시스템 | **CC** (ISO/IEC 15408) |

---

## 시험에 나오는 핵심 3가지

> **① CC의 세 용어와 EAL의 의미**
> **PP**(제품군 요구사항, 구현 독립) / **ST**(특정 제품의 명세, 구현 종속) / **TOE**(평가 대상). **EAL1~7**은 안전도가 아니라 **보증의 깊이**이며, 상용 제품은 통상 **EAL4**가 상한선임.
>
> **② CCRA와 2014년 개정**
> 한 나라의 CC 인증서를 다른 나라가 인정하는 협정임. 참여 자격은 **CAP**(발행국)와 **CCP**(수용국)로 나뉨. **2014년 개정으로 상호인정 범위가 cPP 기반 평가 또는 EAL2 이하로 축소**되었음.
>
> **③ 세 체계의 역할 분담**
> **알고리즘**(각국 독자 기준·FIPS 197) → **암호모듈**(CMVP·KCMVP, 구현 적합성·키 운용·물리적 보안) → **제품/시스템**(CC, ISO/IEC 15408). **CC는 암호 알고리즘 자체의 안전성을 평가하지 않음.**
{: .prompt-tip }

## 용어 정리

| 용어 | 영문(약어) | 정의 |
|---|---|---|
| 공통평가기준 | Common Criteria (CC) | 정보보호제품의 보안성을 평가하는 국제 표준(ISO/IEC 15408) |
| 평가대상 | Target of Evaluation (TOE) | 실제로 평가를 받는 제품·시스템과 그 설명서 |
| 보호프로파일 | Protection Profile (PP) | 제품군에 요구되는 보안 요구사항을 구현과 무관하게 기술한 문서 |
| 공동 보호프로파일 | collaborative PP (cPP) | 국제 기술 커뮤니티(iTC)가 제품군별로 공동 개발한 PP |
| 보안목표명세서 | Security Target (ST) | 특정 TOE가 요구사항을 어떻게 만족하는지 기술한 구현 종속 문서 |
| 보안기능요구사항 | Security Functional Requirements (SFR) | CC Part 2의 요구사항. 제품이 무엇을 하는가 |
| 보증요구사항 | Security Assurance Requirements (SAR) | CC Part 3의 요구사항. 그것을 믿을 근거가 얼마나 되는가 |
| 평가보증등급 | Evaluation Assurance Level (EAL) | 보증의 깊이를 나타내는 EAL1~EAL7의 등급 |
| 공통평가방법론 | Common Evaluation Methodology (CEM) | 평가자가 따라야 할 실제 평가 절차 |
| 국제상호인정협정 | Common Criteria Recognition Arrangement (CCRA) | 회원국 간 CC 인증서를 상호 인정하는 협정 |
| 인증서 발행국 | Certificate Authorising Participant (CAP) | 자국에서 CC 인증서를 발행할 수 있는 회원국 |
| 인증서 수용국 | Certificate Consuming Participant (CCP) | 타국 인증서를 인정만 하는 회원국 |
| 국내 평가·인증 체계 | KECS | 한국의 CC 평가·인증 체계. IT보안인증사무국이 인증 수행 |
| 암호모듈 검증 프로그램 | Cryptographic Module Validation Program (CMVP) | 미국 NIST와 캐나다 CSE가 공동 운영하는 암호모듈 검증 제도 |
| 한국 암호모듈 검증제도 | KCMVP | 국가·공공기관용 암호모듈을 검증하는 국내 제도(국가정보원 주관) |
| 연방정보처리표준 | FIPS | NIST가 발행하는 표준. FIPS 140(암호모듈), FIPS 197(AES) 등 |
