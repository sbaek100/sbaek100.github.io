## 1.1 프로그램과 프로세스의 구분

**프로그램(program)** 은 디스크에 저장된 실행 파일이다. 기계어 명령과 초기 데이터를 담은 **정적인 파일**일 뿐이므로, 저장되어 있는 동안에는 CPU도 메모리도 소비하지 않는다.

**프로세스(process)** 는 그 프로그램이 메모리에 적재되어 실행 중인 상태, 즉 **실행 중인 프로그램의 인스턴스**이다. 프로세스는 자신만의 주소 공간과 실행 문맥(프로그램 카운터, 레지스터 값, 스택 등)을 가지며, CPU 시간과 메모리를 실제로 점유한다. 커널은 이 프로세스를 단위로 자원을 배분하고 상태를 관리한다.

**데몬(daemon)** 은 제어 터미널 없이 배경에서 상주하며 특정 서비스를 제공하는 프로세스를 가리킨다. 부팅 시 기동되어 시스템이 종료될 때까지 동작하는 경우가 많다.

| 용어             | 정의                             | 존재 형태 | 자원 소비       |
| -------------- | ------------------------------ | ----------------- | ------------- |
| **프로그램**       | 디스크에 저장된 실행 파일(정적)             | 파일      | 없음         |
| **프로세스**       | 메모리에 적재되어 실행 중인 프로그램의 인스턴스(동적) | 메모리 상의 실행 단위    | CPU·메모리    |
| **데몬(Daemon)** | 제어 터미널 없이 배경에서 상주하는 프로세스       | 메모리 상의 실행 단위    | 상시 소비      |


![](/assets/img/posts/2026-09-22-linuxintro-week4-2-process-package-1787475656566.png)

프로그램과 프로세스는 **일대다 관계**이다. 하나의 실행 파일을 세 번 실행하면 **서로 독립적인 세 개의 프로세스**가 생성되며, 각 프로세스는 고유한 식별 번호와 별개의 주소 공간을 가진다. 웹 브라우저 창을 여러 개 띄운 뒤 하나만 닫아도 나머지가 영향을 받지 않는 것이 이 독립성의 결과이다.

> **비유로 보면** 프로그램은 조리법이 적힌 문서이고, 프로세스는 그 조리법에 따라 실제로 진행 중인 조리 작업이다. 문서 한 장으로 여러 사람이 동시에 조리할 수 있듯, 실행 파일 하나에서 여러 프로세스가 생성될 수 있다.
{: .prompt-tip }

> **이 구분이 갖는 실무적 의미**
> 시스템 관리에서 조회·제어의 대상은 언제나 **프로세스**이다. 자원을 점유하고 있는 것도, 종료 명령을 받는 것도 디스크 위의 파일이 아니라 실행 중인 인스턴스이기 때문이다. 따라서 대상을 특정하려면 개별 인스턴스를 가리키는 식별자가 필요하며, 그것이 다음 절에서 다루는 **PID**이다.
{: .prompt-info }

## 1.2 프로세스의 속성 — PID와 PPID

커널은 생성되는 모든 프로세스에 **고유한 식별 번호**를 부여한다. 같은 프로그램에서 생성된 프로세스라도 이름은 동일할 수 있으나 번호는 중복되지 않으므로, 프로세스를 지목하는 유일한 기준은 이 번호이다.

| 속성 | 의미 | 비고 |
|---|---|---|
| **PID** | **P**rocess **ID**entifier. 프로세스 식별 번호 | 시스템 전체에서 유일함 |
| **PPID** | **P**arent **PID**. 부모 프로세스의 식별 번호 | 생성 계보를 나타냄 |
| STAT | 현재 상태 | 실행·대기·정지·좀비 등 |
| TTY | 연결된 터미널 | `?`이면 제어 터미널이 없음(데몬) |

**프로세스의 생성 — 부모와 자식**

리눅스에서 새 프로세스는 **기존 프로세스의 복제를 통해서만** 생성된다. 실행 중인 프로세스가 `fork()` 시스템 호출로 자신과 거의 동일한 사본을 만들고, 그 사본이 `exec()` 계열 호출로 다른 프로그램의 이미지로 교체되는 방식이다. 이때 복제를 수행한 쪽을 **부모 프로세스**, 생성된 쪽을 **자식 프로세스**라 한다.

자식 프로세스는 자신의 PID와 함께 부모의 PID를 **PPID**로 보유한다. 따라서 임의의 프로세스에서 PPID를 따라 거슬러 올라가면 반드시 상위 프로세스에 도달하며, 이 과정을 반복하면 최종적으로 **PID 1번**에 이른다. 즉 시스템의 모든 프로세스는 **PID 1을 뿌리로 하는 하나의 트리 구조**를 이룬다. Ubuntu 24.04에서 PID 1은 `systemd`이다.

```
 systemd (PID 1)             모든 프로세스의 최상위 부모
   ├── sshd                  원격 접속 관리
   ├── cron                  예약 작업 관리
   └── bash                  사용자의 셸
         └── ps              사용자가 실행한 명령
```

따라 하기 4-1의 2단계에서 `ps -f`를 실행하면 **`ps`의 PPID가 `bash`의 PID와 일치**함을 확인할 수 있다. 셸이 명령을 실행할 때마다 위의 `fork()`–`exec()` 과정이 수행되기 때문이다.

**STAT(상태) 값의 의미**

프로세스는 대부분의 시간을 입출력 완료나 이벤트 발생을 기다리며 보낸다. 따라서 `ps`로 조회하면 **대다수 프로세스가 `S`(대기) 상태**로 표시되는 것이 정상이다.

| 값 | 의미 | 설명 |
|---|---|---|
| **R** | **R**unning | CPU에서 실행 중이거나 실행 대기열에 있음 |
| **S** | **S**leeping | 이벤트를 기다리는 중단 가능 대기 상태(**대다수가 이 상태**) |
| **T** | s**T**opped | 시그널을 받아 실행이 중단된 상태 |
| **Z** | **Z**ombie | 실행은 종료되었으나 종료 상태가 회수되지 않은 상태 |

**좀비 프로세스의 정확한 의미**

명칭과 달리 좀비는 **이미 실행이 종료된 프로세스**이다. 주소 공간과 열린 파일 등 자원은 모두 반환된 상태이므로 CPU와 메모리를 소비하지 않는다. 남아 있는 것은 **프로세스 테이블의 항목 하나와 종료 상태(exit status)** 뿐이다.

자식 프로세스가 종료되면 커널은 그 종료 상태를 보존하고, 부모 프로세스가 `wait()` 계열 시스템 호출로 이를 **회수(reap)** 할 때 비로소 테이블 항목을 제거한다. 부모가 이 호출을 수행하지 않으면 항목이 계속 남으며, 이 상태를 좀비라 한다. 좀비가 대량으로 누적되면 프로세스 테이블과 PID 공간을 잠식하여 새 프로세스 생성이 실패할 수 있다는 점이 실질적 문제이다.

> **자주 출제되는 함정**
> "좀비 프로세스는 `kill -9`로 제거할 수 있다"는 진술은 **거짓**이다.
>
> 시그널은 **실행 중인 프로세스에 전달되어 그 동작에 영향을 주는** 수단이다. 좀비는 이미 실행이 종료된 상태이므로 전달할 실행 문맥 자체가 없고, 따라서 어떤 시그널도 효과를 갖지 못한다.
>
> 좀비를 해소하는 경로는 두 가지이다.
> 1. **부모가 종료 상태를 회수한다.** 부모 프로세스가 `wait()`를 정상 수행하면 즉시 소멸한다.
> 2. **부모를 종료한다.** 부모가 사라진 고아 프로세스는 PID 1(`systemd`)에 재양육(reparenting)되며, `systemd`는 종료 상태를 즉시 회수하도록 구현되어 있으므로 좀비가 곧 소멸한다.
>
> 즉 조치 대상은 좀비 자신이 아니라 **회수를 수행하지 않는 부모 프로세스**이다.
{: .prompt-danger }

## 1.3 프로세스 조회 — `ps`

`ps`는 **p**rocess **s**tatus의 약어로, 명령을 실행한 **그 시점의 프로세스 목록을 한 번 출력**하는 명령이다.

`ps`에는 하이픈이 없는 문법과 있는 문법이 함께 존재한다. 이는 계통이 다른 두 유닉스(BSD와 System V)의 옵션 체계를 리눅스의 `ps`가 모두 수용하였기 때문이다. **두 형식 모두 전체 프로세스를 조회한다는 목적은 같으나, 출력하는 열의 구성이 다르다.**

| 형식 | 명령 | 옵션의 뜻 | 대표 특징 |
|---|---|---|---|
| BSD 스타일(하이픈 없음) | **`ps aux`** | `a` 모든 터미널, `u` 사용자 중심 형식, `x` 터미널 없는 프로세스 포함 | **CPU·메모리 사용률을 보여 준다** |
| System V 스타일(하이픈 사용) | **`ps -ef`** | `-e` 모든 프로세스, `-f` 전체 형식 | **부모 번호(PPID)를 보여 준다** |

| 명령 | 용도 |
|---|---|
| `ps` | 현재 터미널의 프로세스만 |
| `ps aux` | 전체 프로세스(사용률 포함) |
| `ps -ef` | 전체 프로세스(부모 번호 포함) |
| `ps aux --sort=-%mem` | 메모리 사용량 내림차순 정렬 |
| `pgrep -a bash` | 이름으로 PID 검색(**p**rocess **grep**) |

---

### 1.3.1 `ps aux`의 출력 읽기

메모리를 많이 쓰는 순서로 상위 5개를 뽑아 본 화면이다. 값은 환경에 따라 다르며, **열의 구성과 순서만 동일**하다.

```text
student@ubuntu-y1:~/lab04$ ps aux --sort=-%mem | head -6
USER       PID %CPU %MEM     VSZ    RSS TTY      STAT START   TIME COMMAND
student   3197  0.6  9.5 3924740 384308 ?        Ssl  07:49   0:20 /usr/bin/gnome-shell
student   4102  2.1  7.8 2915640 315224 ?        Sl   08:02   0:47 /usr/lib/firefox/firefox
student   3355  0.3  2.4 1283416  97180 ?        Sl   07:49   0:05 /usr/libexec/gnome-terminal-server
root       892  0.0  1.1  412308  45120 ?        Ssl  07:48   0:02 /usr/lib/snapd/snapd
root         1  0.0  0.3  167344  13208 ?        Ss   07:48   0:02 /sbin/init splash
```

> `head -6`을 붙였으므로 **머리행 1줄 + 프로세스 5줄**이 나온다. `--sort=-%mem`의 앞에 붙은 `-`가 내림차순을 뜻하므로, 메모리를 가장 많이 쓰는 프로세스가 맨 위에 온다.
{: .prompt-tip }

**열별 의미**

| 열 | 의미 | 해석상 유의점 |
|---|---|---|
| `USER` | 프로세스 소유자 | `root`는 시스템 권한으로 기동된 프로세스임 |
| `PID` | 프로세스 식별 번호 | **`kill` 등으로 대상을 지정할 때 사용함** |
| `%CPU` | CPU 사용률(%) | 순간값이므로 조회 시점마다 달라짐 |
| `%MEM` | **물리 메모리** 사용률(%) | `RSS`를 전체 물리 메모리로 나눈 백분율 |
| `VSZ` | **가상 주소 공간** 크기(KiB) | 실제 점유량이 아님(아래 참조) |
| `RSS` | **물리 메모리 점유량**(KiB) | **메모리 부족 여부 판단의 기준값** |
| `TTY` | 연결된 제어 터미널 | **`?`는 제어 터미널이 없음을 의미하며 데몬에 해당함** |
| `STAT` | 프로세스 상태 | 첫 글자가 상태, 이후 문자는 부가 정보(아래 참조) |
| `START` | 프로세스 시작 시각 | 24시간이 경과하면 날짜 형식으로 표시됨 |
| `TIME` | **누적 CPU 사용 시간** | 경과 시간이 아니라 실제로 CPU를 점유한 시간의 합 |
| `COMMAND` | 실행된 명령 | `ps aux`는 실행 경로와 인자를 함께 표시함 |

> **`VSZ`와 `RSS`의 구분 — 가장 자주 혼동되는 부분**
>
> | 열 | 정식 명칭 | 의미 |
> |---|---|---|
> | `VSZ` | **V**irtual **S**i**Z**e | 프로세스가 **예약한 가상 주소 공간 전체**의 크기 |
> | `RSS` | **R**esident **S**et **S**ize | 그중 **실제로 물리 메모리에 올라가 있는 부분**의 크기 |
>
> 프로세스는 실행 파일·공유 라이브러리·힙·스택 등을 가상 주소 공간에 매핑해 두지만, 그 전부가 물리 메모리를 점유하지는 않는다. 아직 접근하지 않은 영역이나 스왑으로 내려간 영역은 `VSZ`에 포함되되 `RSS`에는 포함되지 않는다. 위 출력에서 `gnome-shell`의 `VSZ`는 약 3.9GB이나 `RSS`는 약 384MB인 것이 그 예이다.
>
> 따라서 **물리 메모리 부족 여부를 판단할 때는 `VSZ`가 아니라 `RSS`(및 이를 백분율로 환산한 `%MEM`)를 기준으로 삼는다.** 또한 공유 라이브러리는 여러 프로세스의 `RSS`에 중복 계상되므로, `RSS`의 단순 합계가 실제 총 사용량과 일치하지는 않는다.
{: .prompt-danger }

**`STAT` 열이 `Ssl`처럼 여러 글자인 이유**

`STAT`의 **첫 글자만이 제1.2절에서 배운 상태**(`R`·`S`·`T`·`Z`)이고, 뒤에 붙는 소문자·기호는 부가 정보이다. 즉 `Ssl`은 "`S`(대기 중)이면서 `s`(세션 리더)이고 `l`(멀티스레드)"이라는 뜻이다.

| 뒤에 붙는 문자 | 의미 |
|---|---|
| `s` | **세션 리더**(session leader). 해당 세션을 대표하는 프로세스 |
| `l` | **멀티스레드**. 둘 이상의 스레드로 구성된 프로세스 |
| `+` | **포그라운드** 프로세스 그룹에 속함(제2절에서 학습) |
| `<` | 우선순위가 높음 |
| `N` | 우선순위가 낮음(**N**ice) |
| `L` | 메모리 일부를 물리 메모리에 고정해 둠(**L**ocked) |

> 따라서 `Ssl`·`Sl`·`Ss`·`R+`는 모두 **서로 다른 상태가 아니라 같은 `S`·`R` 상태에 부가 정보가 덧붙은 것**이다. 상태를 판단할 때는 **첫 글자만** 보면 된다.
{: .prompt-tip }

### 1.3.2 `ps -ef`의 출력 읽기

같은 시스템을 `ps -ef`로 조회한 화면이다.

```text
student@ubuntu-y1:~/lab04$ ps -ef | head -6
UID        PID  PPID  C STIME TTY          TIME CMD
root         1     0  0 07:48 ?        00:00:02 /sbin/init splash
root       892     1  0 07:48 ?        00:00:02 /usr/lib/snapd/snapd
student   3197  3102  0 07:49 ?        00:00:20 /usr/bin/gnome-shell
student   3421  3355  0 07:50 pts/0    00:00:00 bash
student   4530  3421  0 08:11 pts/0    00:00:00 ps -ef
```

**열별 의미**

| 열 | 의미 | 해석상 유의점 |
|---|---|---|
| `UID` | 프로세스 소유자 | `ps aux`의 `USER`에 대응함 |
| `PID` | 프로세스 식별 번호 | — |
| **`PPID`** | **부모 프로세스의 식별 번호** | **`ps aux`에는 없는 열로, 생성 계보 추적에 사용함** |
| `C` | CPU 사용률의 정수 근사값 | `%CPU`보다 정밀도가 낮음 |
| `STIME` | 프로세스 시작 시각 | `ps aux`의 `START`에 대응함 |
| `TTY` | 연결된 제어 터미널 | `?`는 제어 터미널 없음, `pts/N`은 의사 터미널 |
| `TIME` | 누적 CPU 사용 시간 | `시:분:초` 형식으로 표시됨 |
| `CMD` | 실행된 명령 | `ps aux`의 `COMMAND`에 대응함 |

> **출력에서 부모-자식 관계를 확인하는 방법**
>
> 마지막 두 행을 보면 `ps -ef`(PID 4530)의 `PPID`가 **3421**이고, 3421은 바로 위 행의 `bash`이다. 제1.2절에서 설명한 `fork()`–`exec()` 과정이 출력에 그대로 반영된 것이다. 같은 방식으로 `bash`(3421)의 `PPID` 3355는 터미널 에뮬레이터에 해당한다.
>
> 첫 행의 PID 1은 `PPID`가 **0**으로 표시된다. 커널이 직접 생성한 최초의 프로세스이므로 부모가 존재하지 않음을 의미한다.
{: .prompt-tip }

### 1.3.3 두 형식의 열 구성 차이

동일한 프로세스를 조회하더라도 **출력되는 열의 구성이 다르다.** 아래 표에서 "없음"으로 표시된 항목은 그 형식이 제공하지 않는 정보이다.

| 정보 | `ps aux` | `ps -ef` |
|---|---|---|
| 소유자 | `USER` | `UID` |
| 프로세스 번호 | `PID` | `PID` |
| **부모 번호** | **없음** | **`PPID`** |
| CPU 사용률 | `%CPU`(소수점) | `C`(정수 근사) |
| **메모리 사용률** | **`%MEM`** | **없음** |
| **메모리 크기** | **`VSZ`, `RSS`** | **없음** |
| **상태** | **`STAT`** | **없음** |
| 시작 시각 | `START` | `STIME` |
| 누적 CPU 시간 | `TIME` | `TIME` |
| 터미널 | `TTY` | `TTY` |
| 명령 | `COMMAND` | `CMD` |

핵심 차이는 두 가지로 정리된다.

1. **`ps aux`에만 있는 것 — 자원 사용량과 상태**(`%MEM`·`VSZ`·`RSS`·`STAT`)
2. **`ps -ef`에만 있는 것 — 부모 번호**(`PPID`)

> **목적에 따른 선택 기준**
>
> | 확인 목적 | 사용할 명령 | 근거 |
> |---|---|---|
> | 메모리 과다 점유 프로세스 식별 | **`ps aux --sort=-%mem`** | 정렬 기준인 `%MEM`·`RSS`가 이 형식에만 있음 |
> | CPU 과다 점유 프로세스 식별 | **`ps aux --sort=-%cpu`** | 위와 동일 |
> | 좀비 프로세스 존재 확인 | **`ps aux`** | 상태 열 `STAT`이 이 형식에만 있음 |
> | 프로세스의 생성 주체 확인 | **`ps -ef`** | `PPID`가 이 형식에만 있음 |
> | 종료 가능 여부 판단 | **`ps -ef`** | PPID를 거슬러 올라가 소속과 역할을 확인함 |
>
> 요약하면 **자원 사용량은 `ps aux`, 생성 계보는 `ps -ef`** 로 조회한다.
{: .prompt-info }

> **두 문법을 섞어 쓰지 않는다**
> `ps -aux`처럼 하이픈을 붙여도 실제로는 `ps aux`와 같은 결과가 나오는 경우가 많다. 그러나 이는 `ps`가 사용자의 실수를 짐작해 바로잡아 주는 것일 뿐, **규격상 `-aux`는 "`x`라는 이름의 사용자"를 뜻하는 `-u x`로 해석될 수 있다.** `x`라는 계정이 실제로 있는 시스템에서는 전혀 다른 결과가 나온다.
>
> 시험에서도 두 문법의 구분을 묻는 경우가 있으므로, **`ps aux`(하이픈 없음)와 `ps -ef`(하이픈 있음)** 를 각각 통째로 외워 두는 편이 안전하다.
{: .prompt-warning }

## 1.4 실시간 감시 — `top`과 `htop`

`ps`가 한순간의 상태를 한 번 출력하는 데 비해, **`top`** 은 시스템 자원 사용 현황을 실시간으로 갱신하여 표시한다. `top`은 대부분의 리눅스에 기본 설치되어 있다.

| 키 | 동작 |
|---|---|
| **`P`** | CPU 사용률순 정렬(**P**rocessor) |
| **`M`** | 메모리 사용률순 정렬(**M**emory) |
| `k` | 프로세스에 시그널 전송(**k**ill) |
| **`q`** | **종료**(**q**uit) |

**[그림 4-3] `top` 실행 화면 — 예상 화면**

아래는 `top`을 실행하였을 때 나타나는 화면의 예시이다. 숫자 값은 환경에 따라 달라지며, 화면 구성만 동일하다. 오른쪽의 `←` 표시는 설명을 위해 덧붙인 것이며 실제 화면에는 나타나지 않는다.


**요약부(화면 위쪽 5행)의 각 항목**

| 표시 | 행 | 의미 |
|---|---|---|
| ① | 1행 | 현재 시각, 가동 시간(`up 1:45` = 1시간 45분), 로그인 사용자 수, **부하 평균(1분·5분·15분)** |
| ② | 2행 | 전체 작업 수와 상태별 개수. **`zombie` 값이 0보다 크면 좀비 프로세스가 존재**한다 |
| ③ | 3행 | CPU 사용 비율. `us`=사용자 프로그램, `sy`=커널, `id`=유휴, `wa`=입출력 대기 |
| ④ | 4·5행 | 물리 메모리(`Mem`)와 스왑(`Swap`)의 전체·여유·사용량(MiB 단위) |
| ⑤ | 머리행 | 아래 프로세스 목록의 열 이름 |

**목록부의 각 열**

| 열 | 의미 |
|---|---|
| `PID` | 프로세스 식별 번호 |
| `USER` | 프로세스 소유자 |
| `PR` / `NI` | 스케줄링 우선순위 / nice 값 |
| `VIRT` / `RES` / `SHR` | 가상 / 실제(물리) / 공유 메모리 크기(KiB) |
| `S` | 상태. 제1.2절의 `R`·`S`·`T`·`Z`와 같은 값 |
| `%CPU` / `%MEM` | CPU 사용률 / 물리 메모리 사용률 |
| `TIME+` | 누적 CPU 사용 시간 |
| `COMMAND` | 명령 이름(길면 끝이 `-`로 잘려 표시됨) |

> 화면이 갱신되는 도중 `P`를 누르면 목록이 `%CPU` 내림차순으로, `M`을 누르면 `%MEM` 내림차순으로 다시 정렬된다. 위 예시는 `%CPU` 기준으로 정렬된 상태이다. `q`를 누르면 종료되어 프롬프트로 돌아온다.
{: .prompt-tip }

`top`을 개선하여 색상과 마우스 조작, 스크롤을 지원하는 도구가 **`htop`** 이다. `htop`은 기본 설치되어 있지 않으므로 제3절에서 학습할 `apt`로 설치한 뒤 사용한다.

```bash
sudo apt install htop     # 설치(제3절에서 상세히 다룸)
htop                      # 실행. F10 또는 q 로 종료
```

> **부하 평균(load average)의 해석**
> `top`과 `htop` 상단에 표시되는 부하 평균은 최근 1분·5분·15분 동안 실행을 대기한 프로세스의 평균 개수를 의미한다. **CPU 코어 수보다 큰 값이 지속되면 과부하 상태**로 판단한다.
{: .prompt-tip }

> ### 따라 하기 4-1. 프로세스 조회
>
> **목적** 여러 방식으로 프로세스를 조회하고 각 출력 형식의 차이를 파악한다.
{: .prompt-tip }

**1단계.** 실습 디렉터리를 생성하고 이동한다.

```bash
mkdir -p ~/lab04 && cd ~/lab04
```

**2단계.** 현재 터미널의 프로세스를 조회한다.

```bash
ps
```

> `bash`와 `ps` 두 개만 출력된다. 옵션 없는 `ps`는 현재 터미널에 연결된 프로세스만 표시한다.

```bash
ps -f
```

> PPID 열이 추가된다. **`ps`의 부모가 `bash`임을 확인한다.**

**3단계.** 두 가지 문법으로 전체 프로세스를 조회한다.

```bash
ps aux | head -10
```

> `%CPU`·`%MEM`·`VSZ`·`RSS`·`STAT` 열이 포함된다. **`STAT`의 첫 글자**만이 상태이고 뒤의 `s`·`l`은 부가 정보라는 점을 제1.3.1절에서 확인한다.

```bash
ps -ef | head -10
```

> **`PPID` 열이 포함되는 대신 `%MEM`·`STAT` 열이 사라진다.** 두 형식의 열 구성 차이는 제1.3.3절의 대조표로 확인한다.

두 형식의 머리행을 나란히 놓고 직접 대조해 본다.

```bash
ps aux | head -2
```

```bash
ps -ef | head -2
```

> 두 명령 모두 **PID 1번(`systemd`) 한 행**을 출력하지만 **열의 이름과 개수가 서로 다르다.** `ps aux`에만 `%MEM`·`RSS`·`STAT`이, `ps -ef`에만 `PPID`가 포함되어 있음을 확인한다.

**4단계.** PID 1번을 확인한다.

```bash
ps -p 1 -o pid,ppid,user,comm
```

> `systemd`가 출력된다. 모든 프로세스의 최상위 부모이다.

**5단계.** 자원 사용량 기준으로 정렬한다.

```bash
ps aux --sort=-%mem | head -6
```

> 앞의 `-`는 내림차순을 의미한다. 메모리를 많이 사용하는 프로세스가 위에 표시된다.

**6단계.** `top`을 실행하여 조작한다.

```bash
top
```

> 화면 내에서 다음을 순서대로 수행한다.
> 1. `P` — CPU 사용률순 정렬
> 2. `M` — 메모리 사용률순 정렬
> 3. `q` — 종료

> **확인 사항** `ps aux`와 `ps -ef`의 열 구성 차이를 설명할 수 있고, `top`을 실행·정렬·종료할 수 있다면 성공이다.
{: .prompt-tip }

## 2.1 포그라운드와 백그라운드

| 구분 | 정의 |
|---|---|
| **포그라운드(foreground)** | 터미널을 점유하며 실행. 종료될 때까지 다른 명령을 입력할 수 없다. |
| **백그라운드(background)** | 터미널을 반환하고 배경에서 실행. 명령 끝에 `&`를 붙인다. |

**"터미널을 점유한다"는 말의 의미**

셸이 명령을 포그라운드로 실행하면, 키보드 입력을 받는 통로(표준 입력)와 `Ctrl+C`·`Ctrl+Z` 같은 키를 수신할 권한이 모두 그 프로세스에게 넘어간다. 입력 통로가 자식에게 넘어가 있으므로 셸은 명령이 끝날 때까지 다음 프롬프트를 표시하지 못한다.

백그라운드 실행(`&`)은 이 제어권을 셸이 그대로 쥔 채 자식을 띄우는 방식이다. 그래서 프롬프트가 즉시 돌아오고, 셸은 다음 명령을 받을 수 있다.

![](/assets/img/posts/2026-09-22-linuxintro-week4-2-process-package-1787476386190.png)

| 명령 | 동작 |
|---|---|
| `명령 &` | 백그라운드로 실행 |
| `jobs` | 현재 셸의 작업 목록(`-l`은 PID 포함) |
| `fg %1` | 1번 작업을 포그라운드로 전환(**f**ore**g**round) |
| `bg %1` | 정지된 1번 작업을 백그라운드에서 재개(**b**ack**g**round) |
| `Ctrl + Z` | 포그라운드 작업을 정지 |

**작업 번호(%1)와 PID는 다르다**

| 구분 | 예시 | 부여 주체 | 유효 범위 |
|---|---|---|---|
| **PID** | 12847 | **커널** | 시스템 전체에서 유일 |
| **작업 번호** | `%1`, `%2` | **셸** | 해당 셸(터미널) 안에서만 유효 |

```
[1]+  12847 Running     sleep 300 &
 └┬┘   └─┬─┘
 작업번호  PID
```

터미널을 하나 더 열면 그 셸은 자기만의 `%1`, `%2`를 새로 매긴다. 따라서 **다른 터미널의 프로세스는 `%N`으로 제어할 수 없고 PID로 지정**해야 한다.

**작업 상태 전이 한눈에 보기**

![](/assets/img/posts/2026-09-22-linuxintro-week4-2-process-package-1787476512764.png)

핵심 규칙 세 가지:

1. **`Ctrl+Z`는 정지만 시킨다.** 종료가 아니므로 반드시 `fg`·`bg`·`kill` 중 하나로 뒤처리해야 한다.
2. **`bg`의 대상은 "정지된" 작업이다.** 실행 중인 포그라운드 작업을 곧바로 백그라운드로 보내는 방법은 없으며, 반드시 `Ctrl+Z` → `bg` 순서를 따른다.
3. **포그라운드 → 백그라운드 전환은 `Ctrl+Z` → `bg`, 그 반대는 `fg` 한 번**이다.

> **터미널을 닫으면 백그라운드 작업도 함께 종료된다**
>
> 터미널이 닫히면 셸은 자식 프로세스들에게 "연결이 끊겼다"는 시그널(SIGHUP)을 전달하며, 이를 받은 프로세스는 기본적으로 종료된다. `&`로 실행했더라도 마찬가지다.
>
> 터미널을 닫아도 계속 실행되게 하려면 `nohup`(**no** **h**ang **up**)을 사용한다.
>
> ```bash
> nohup ./backup.sh &
> ```
>
> 출력은 자동으로 `nohup.out` 파일에 기록된다. 원격 서버에서 오래 걸리는 작업을 걸어 두고 접속을 끊을 때 필수적인 명령이다.
{: .prompt-warning }

**실무 활용 예**

| 상황 | 실행 방식 | 이유 |
|---|---|---|
| 대화형 명령(vim, top) | 포그라운드 | 사용자의 키보드 입력이 필요함 |
| 오래 걸리는 압축·복사 | `명령 &` | 진행 중에도 다른 명령 수행 |
| 원격 서버의 야간 배치 | `nohup ./batch.sh &` | 접속을 끊어도 계속 실행 |

## 2.2 시그널의 개념

**시그널(signal)** 은 커널 또는 다른 프로세스가 특정 프로세스에 전달하는 **비동기 통지 수단**이다. 프로세스의 실행을 중단·정지·재개시키거나, 예외 상황의 발생을 알리는 데 사용한다.

시그널의 가장 중요한 특성은 **전달되는 정보가 시그널 번호 하나뿐**이라는 점이다. 임의의 데이터를 함께 실어 보낼 수 없으며, 수신 측은 "몇 번 시그널이 도달하였다"는 사실만을 인지한다. 따라서 발신 의도나 맥락은 전달되지 않고, 그 번호에 어떻게 반응할 것인가는 전적으로 **수신 프로세스의 구현**에 달려 있다.

`kill` 명령은 이름과 달리 종료 전용 명령이 아니라 **임의의 시그널을 전달하는 명령**이다. 정지(SIGSTOP)나 재개(SIGCONT) 역시 동일한 방식으로 전달된다.

![](/assets/img/posts/2026-09-22-linuxintro-week4-2-process-package-1787476993279.png)

**시그널에 대한 프로세스의 세 가지 처리 방식**

각 시그널에는 커널이 정한 **기본 동작(default action)** 이 있으나, 프로세스는 이를 변경할 수 있다.

| 처리 방식 | 설명 | 예 |
|---|---|---|
| **기본 동작 수행** | 시그널별로 정해진 기본 반응을 따른다. 대부분 종료 또는 정지이다. | `sleep 60`에 `Ctrl+C` → 종료 |
| **무시(ignore)** | 시그널을 수신하되 아무 동작도 수행하지 않는다. | 중단되면 안 되는 처리 구간 |
| **직접 처리(catch)** | 미리 등록해 둔 **시그널 처리기(signal handler)** 를 실행한다. | `vim`에 `Ctrl+C` → 종료되지 않음 |

`vim`이 `Ctrl+C`로 종료되지 않는 것은 SIGINT에 대한 처리기를 등록해 두었기 때문이며, 편집 중인 내용의 손실을 방지하려는 설계이다. 반면 `sleep 60`은 별도의 처리기가 없으므로 기본 동작인 종료가 수행된다.

**주요 시그널**

| 번호 | 이름 | 의미 | 기본 동작 | 무시 가능 여부 |
|---|---|---|---|---|
| 1 | SIGHUP | 제어 터미널과의 연결 단절(**H**ang **UP**) | 종료 | 가능 |
| 2 | SIGINT | 인터럽트 요청(`Ctrl + C`, **INT**errupt) | 종료 | 가능 |
| **15** | **SIGTERM** | **종료 요청(**TERM**inate). `kill`의 기본값** | 종료 | 가능 |
| **9** | **SIGKILL** | **강제 종료** | 종료 | **불가능** |
| 19 | SIGSTOP | 실행 정지 | 정지 | **불가능** |
| 18 | SIGCONT | 정지된 프로세스의 재개(**CONT**inue) | 재개 | 처리는 가능하나 재개 자체는 막지 못함 |

`SIG`는 **sig**nal의 약어이다.

**키보드 입력과 시그널의 대응**

터미널에서 아래 키를 입력하면, 터미널 드라이버가 해당 시그널을 **포그라운드 프로세스 그룹**에 전달한다.

| 키 | 시그널 | 기본 결과 |
|---|---|---|
| `Ctrl + C` | SIGINT(2) | 종료 |
| `Ctrl + Z` | SIGTSTP(20) | 정지 |

> `Ctrl+Z`가 전달하는 SIGTSTP(20)는 SIGSTOP(19)과 동일하게 프로세스를 정지시키지만, **SIGTSTP는 무시하거나 처리기로 가로챌 수 있고 SIGSTOP은 불가능**하다는 차이가 있다. SIGTSTP는 사용자의 정지 요청이므로, 프로그램이 정리 작업을 수행하거나 정지를 거부할 여지를 남겨 둔 것이다.

**SIGKILL(9)과 SIGSTOP(19)만 무시할 수 없는 이유**

다른 시그널은 수신 프로세스에 전달되어 그 처리 방식에 따라 동작이 결정되므로 무시나 가로채기가 가능하다. 그러나 **SIGKILL과 SIGSTOP은 수신 프로세스에 전달되지 않고 커널이 직접 처리**한다. 프로세스는 이 두 시그널에 대해 처리기를 등록할 수도, 무시하도록 설정할 수도 없다.

이러한 설계는 **제어 불능 상태의 프로세스를 강제로 종료하거나 정지시킬 수단을 보장**하기 위한 것이다. 모든 시그널이 무시 가능하다면 무한 루프에 빠진 프로세스나 악의적으로 작성된 프로그램을 관리자가 제어할 방법이 없어진다. 따라서 **종료 수단 하나(SIGKILL)와 정지 수단 하나(SIGSTOP)** 만은 프로세스가 거부할 수 없도록 규정되어 있다.

> **그 대가 — `kill -9`를 함부로 쓰면 안 되는 까닭**
>
> SIGKILL을 받은 프로세스는 **정리 코드를 한 줄도 실행하지 못한 채 즉시 소멸**한다. 그 결과 다음과 같은 부작용이 발생할 수 있다.
>
> - 임시 파일·잠금 파일이 삭제되지 않고 잔존함
> - 버퍼에만 존재하던 데이터가 디스크에 기록되지 못하고 유실됨
> - 공유 자원(세마포어, 공유 메모리 등)이 해제되지 않은 채 남음
>
> 데이터베이스 서버처럼 쓰기 작업이 진행 중인 프로세스를 `kill -9`로 종료하면 데이터 정합성이 깨질 수 있는 것이 대표적인 사례이다. 이것이 SIGKILL을 최후의 수단으로만 사용해야 하는 이유이다.
{: .prompt-info }

---

## 2.3 프로세스 종료 명령 — `kill`과 `killall`

| 명령 | 동작 |
|---|---|
| `kill PID` | SIGTERM(15) 전송 — 정상 종료 요청 |
| `kill -9 PID` | SIGKILL(9) 전송 — 강제 종료 |
| `kill -l` | 시그널 목록 조회(**l**ist) |
| `killall 프로세스명` | 동일한 이름의 **모든 프로세스**에 전송 |
| `pkill -f "패턴"` | 명령행에서 패턴이 일치하는 프로세스에 전송 |

`kill`은 PID를 지정하여 하나의 프로세스에, `killall`은 이름을 지정하여 같은 이름의 모든 프로세스에 시그널을 보낸다.

> **`kill -9`를 우선 사용해서는 안 되는 이유**
>
> | 구분 | SIGTERM(15) | SIGKILL(9) |
> |---|---|---|
> | 의미 | 정리 후 종료할 것을 요청 | 즉시 강제 종료 |
> | 프로세스의 대응 | 임시 파일 삭제, 버퍼 기록 등 정리 작업 수행 | **아무 작업도 수행하지 못함** |
> | 결과 | 정상 종료 | 데이터 손상 가능 |
>
> **먼저 `kill`(SIGTERM)을 전송하고, 일정 시간이 지나도 응답이 없을 때에만 `kill -9`를 사용한다.**
{: .prompt-danger }

---

> ### 따라 하기 4-2. 작업 제어와 프로세스 종료
>
> **목적** 백그라운드 작업을 제어하고, `kill`과 `killall`로 프로세스를 종료한다.
{: .prompt-tip }

**1단계.** 포그라운드 실행을 확인한다.

```bash
sleep 60
```

> 60초 동안 다른 명령을 입력할 수 없다. `Ctrl + C`로 중단한다. 이때 전달되는 시그널이 SIGINT이다.

**2단계.** 백그라운드로 실행한다.

```bash
sleep 300 &
```

```bash
sleep 400 &
```

```bash
jobs -l
```

> `[1]`, `[2]`는 작업 번호이며 그 옆의 숫자가 PID이다. 명령 끝의 `&`가 백그라운드 실행을 지시한다.

**3단계.** 포그라운드와 백그라운드를 전환한다.

```bash
fg %1
```

> 1번 작업이 포그라운드로 전환되어 터미널을 점유한다. 이때 **`Ctrl + Z`** 를 누른다.

```bash
jobs
```

> 상태가 `Stopped`(정지)로 표시된다.

```bash
bg %1
```

```bash
jobs
```

> 상태가 `Running`(실행 중)으로 복귀한다.

**4단계.** 작업 번호로 종료한다.

```bash
kill %1
```

```bash
jobs
```

> 1번 작업이 종료된다.

**5단계.** 이름으로 여러 프로세스를 한 번에 종료한다.

```bash
sleep 500 &
```

```bash
sleep 600 &
```

```bash
pgrep -a sleep
```

> 실행 중인 `sleep` 프로세스의 PID가 모두 출력된다.

```bash
killall sleep
```

```bash
pgrep -a sleep || echo "모두 종료되었습니다"
```

> `killall`은 이름이 `sleep`인 모든 프로세스에 시그널을 전송하므로, 여러 프로세스를 한 번에 종료할 수 있다.

**6단계.** SIGTERM과 SIGKILL의 차이를 관찰한다.

```bash
sleep 700 &
```

```bash
PID=$! && echo "PID = $PID"
```

> `$!`는 가장 최근에 백그라운드로 실행한 프로세스의 PID를 담은 특수 변수이다.

```bash
kill $PID
```

```bash
ps -p $PID -o pid,stat,comm || echo "정상 종료되었습니다"
```

> 대부분의 프로세스는 SIGTERM(기본값)만으로 정상 종료된다. 응답하지 않는 경우에 한하여 `kill -9 $PID`(SIGKILL)를 사용한다.

> **확인 사항** `fg`·`Ctrl+Z`·`bg`로 작업 상태를 전환하였고, `kill`과 `killall`의 차이(하나 대 이름 전체)를 설명할 수 있다면 성공이다.
{: .prompt-tip }

# 제3절. 소프트웨어 설치와 패키지 관리

---

## 3.1 패키지 관리자의 역할

윈도우에서 프로그램을 설치하려면 설치 파일을 검색·내려받기·실행하는 절차를 거쳐야 하며, 필요한 구성 요소도 개별적으로 확인해야 한다.

리눅스의 **패키지 관리자(package manager)** 는 이 과정을 자동화한다. 명령 한 줄로 저장소(repository)에서 검색하고, 내려받고, 의존 관계에 있는 다른 패키지까지 함께 설치한다. Ubuntu가 사용하는 고수준 패키지 관리 도구가 **`apt`** 이며, 이는 **A**dvanced **P**ackaging **T**ool의 약어이다.

> **GUI 소프트웨어 센터**
> Ubuntu Desktop에는 **App Center(소프트웨어 센터)** 라는 그래픽 도구가 기본 포함되어 있어, 목록에서 프로그램을 검색하고 버튼을 눌러 설치할 수 있다. 이는 초보자에게 편리하나, 서버 관리와 자동화에는 명령행 도구가 필수적이다. 본 강의는 명령행 `apt`를 중심으로 다룬다.
{: .prompt-info }

---

## 3.2 `apt`는 인터넷 연결과 관리자 권한이 필요하다

`apt`로 소프트웨어를 설치하려면 두 가지 조건이 충족되어야 한다.

- **인터넷 연결.** 저장소는 인터넷상의 서버에 있으므로, 목록을 갱신하고 패키지를 내려받으려면 네트워크에 연결되어 있어야 한다.
- **관리자 권한(sudo).** 소프트웨어 설치는 시스템 전체에 영향을 미치므로 일반 사용자 권한으로는 수행할 수 없다. 명령 앞에 `sudo`를 붙여 관리자 권한으로 실행하며, 실행 시 `student` 계정의 암호를 요구한다.

```bash
sudo apt install tree
```

---

## 3.3 `apt` 주요 명령

| 명령 | 기능 |
|---|---|
| **`sudo apt update`** | **저장소의 패키지 목록 정보만 갱신** |
| **`sudo apt upgrade`** | **설치된 패키지를 실제로 최신 버전으로 갱신** |
| `sudo apt install 이름` | 설치 |
| `sudo apt remove 이름` | 제거(**설정 파일은 잔존**) |
| **`sudo apt purge 이름`** | **설정 파일까지 완전 제거** |
| `apt search 키워드` | 검색(관리자 권한 불필요) |
| `apt show 이름` | 상세 정보 |
| `apt list --installed` | 설치된 패키지 목록 |
| `sudo apt autoremove` | 불필요한 의존 패키지 정리 |

> **혼동하기 쉬운 두 쌍의 명령**
>
> **① `update`와 `upgrade`**
> - `apt update` : 저장소의 **목록 정보만** 갱신한다. 패키지 자체는 변경되지 않는다.
> - `apt upgrade` : 실제로 패키지를 최신 버전으로 갱신한다.
>
> 따라서 항상 `update`를 먼저 실행하고 `upgrade`를 수행한다.
>
> **② `remove`와 `purge`**
> - `remove` : 프로그램만 제거하고 **설정 파일은 남긴다.**
> - `purge` : 설정 파일까지 완전히 제거한다.
{: .prompt-danger }

---

## 3.4 `dpkg` — 저수준 도구

`apt`가 인터넷 저장소를 다루는 고수준 도구라면, **`dpkg`** 는 개별 `.deb` 패키지 파일을 직접 다루는 저수준 도구이다(**d**ebian **pkg**). 주로 설치된 패키지와 그 파일을 조회하는 데 사용한다.

| 명령 | 기능 |
|---|---|
| `dpkg -l` | 설치된 패키지 목록 조회(**l**ist) |
| `dpkg -L 이름` | 해당 패키지가 설치한 파일 목록 |
| `dpkg -S 경로` | 해당 파일이 속한 패키지 조회 |
| `sudo dpkg -i 파일.deb` | 로컬 `.deb` 파일 설치(**의존성을 자동 해결하지 않음**) |

`dpkg -i` 실행 후 의존성 오류가 발생하면 `sudo apt install -f`로 해결한다(`-f`는 **f**ix).

> **참고 — 다른 계열의 대응 명령**
> 레드햇 계열(CentOS, Fedora 등)에서는 `.deb` 대신 `.rpm` 패키지를 사용하며, `apt`에 대응하는 도구는 `dnf`, `dpkg`에 대응하는 도구는 `rpm`이다. 시험에서는 `rpm -qa`(전체 목록 조회)가 `dpkg -l`에 대응한다는 점 등을 함께 묻는다.
{: .prompt-warning }

---

> ### 따라 하기 4-3. 패키지 관리
>
> **목적** `apt`와 `dpkg`로 패키지를 설치·조회·삭제하고, `remove`와 `purge`의 차이를 확인한다.
{: .prompt-tip }

**1단계.** 패키지 목록을 갱신한다.

```bash
sudo apt update
```

> 저장소의 최신 목록 정보를 내려받는다. 인터넷 연결과 `sudo` 암호가 필요하다.

**2단계.** 패키지를 검색하고 정보를 조회한다.

```bash
apt search "^tree$" 2>/dev/null
```

```bash
apt show tree 2>/dev/null | head -12
```

**3단계.** 패키지를 설치한다.

```bash
sudo apt install -y tree htop
```

> `-y`는 설치 확인 질문에 자동으로 "예"라고 답하는 옵션이다.

```bash
tree -L 2 ~/lab04
```

> `tree`는 디렉터리 구조를 나무 모양으로 표시하는 프로그램이다. 방금 설치하여 사용할 수 있게 되었다.

**4단계.** 설치된 파일과 소속 패키지를 조회한다.

```bash
dpkg -L tree | head
```

> 해당 패키지가 설치한 파일 목록이다.

```bash
which tree
```

```bash
dpkg -S $(which tree)
```

> `which`는 명령의 실제 경로를, `dpkg -S`는 그 파일이 어느 패키지에 속하는지 조회한다.

**5단계.** 설치 목록을 확인한다.

```bash
dpkg -l | grep -E "tree|htop"
```

> `ii`는 정상 설치 상태를 의미한다.

**6단계.** `htop`을 실행한다.

```bash
htop
```

> 색상으로 구분된 실시간 프로세스 감시 화면이 표시된다. `q` 또는 `F10`으로 종료한다.

**7단계.** `remove`와 `purge`의 차이를 확인한다.

설정 파일을 남기는 패키지에서 두 명령의 차이가 드러난다. 설정 파일을 포함하는 `at` 패키지로 확인한다.

```bash
sudo apt install -y at
```

```bash
sudo apt remove -y at
```

```bash
ls -l /etc/at.deny
```

> 프로그램은 삭제되었으나 **설정 파일은 그대로 남아 있다.** 재설치 시 기존 설정을 이어서 사용할 수 있도록 보존한 것이다.

```bash
sudo apt purge -y at
```

```bash
ls -l /etc/at.deny 2>/dev/null || echo "설정 파일까지 삭제되었습니다"
```

> `purge`는 설정 파일까지 완전히 제거한다.

**8단계.** 실습에 설치한 패키지를 정리한다.

```bash
sudo apt purge -y htop tree && sudo apt autoremove -y
```

> **확인 사항** `apt update` → `apt install` → `dpkg`로 조회 → `apt remove`/`purge`의 흐름을 수행하였고, `remove`와 `purge`의 차이를 설명할 수 있다면 성공이다.
{: .prompt-tip }

# 제5절. 자주 발생하는 오류와 대응 방법

---

| 화면에 출력된 메시지 / 증상 | 원인 | 대응 방법 |
|---|---|---|
| `No such process` (kill) | 해당 PID가 존재하지 않음 | `ps` 또는 `pgrep`으로 다시 확인한다. |
| `Operation not permitted` (kill) | 타 사용자의 프로세스 | `sudo kill`을 사용한다. |
| 좀비 프로세스가 사라지지 않음 | 부모가 회수하지 않음 | 부모 프로세스를 종료한다. `kill -9`는 효과가 없다. |
| `E: Unable to locate package` | 패키지 목록이 오래됨 | `sudo apt update`를 먼저 실행한다. |
| `Unable to acquire the dpkg lock` | 다른 apt 프로세스가 실행 중 | 종료를 기다린 후 재시도한다. |
| `Could not resolve host` (apt) | 인터넷 연결 문제 | 네트워크 연결 상태를 확인한다. |
| `Permission denied` (apt) | `sudo` 누락 | 명령 앞에 `sudo`를 붙인다. |
| `htop: command not found` | 미설치 | `sudo apt install htop`으로 설치한다. |

# 제6절. 요약

---

## 6.1 핵심 개념 정리

| 구분 | 요점 |
|---|---|
| 프로세스 | 메모리에 적재되어 실행 중인 프로그램의 인스턴스이다. `fork()`–`exec()`로 생성되어 부모-자식 계층을 이루며, 각 프로세스는 고유한 PID와 부모의 PPID를 가진다. 트리의 뿌리는 PID 1의 `systemd`이다. |
| 좀비 | 실행은 종료되었으나 부모가 종료 상태를 회수하지 않아 프로세스 테이블 항목만 남은 상태이다. 시그널이 듣지 않으므로 **부모를 조치**해야 한다. |
| 조회 | `ps aux`(BSD)와 `ps -ef`(System V) 두 문법이 있다. **사용량(`%MEM`·`RSS`·`STAT`)은 `ps aux`에만, 부모 번호(`PPID`)는 `ps -ef`에만** 나온다. 실시간 감시는 `top`, 색상 지원 도구는 `htop`을 사용한다. |
| 출력 읽기 | `VSZ`는 예약한 가상 메모리, **`RSS`가 실제 점유량**이다. `STAT`은 **첫 글자만 상태**이고 뒤의 `s`·`l`·`+`는 부가 정보이다. `TTY`가 `?`이면 데몬이다. |
| 작업 제어 | 명령 끝의 `&`로 백그라운드 실행, `jobs`로 목록 조회, `fg`/`bg`로 전환, `Ctrl+Z`로 정지한다. |
| 시그널과 종료 | `kill`은 PID 하나에, `killall`은 이름이 같은 전체에 시그널을 보낸다. SIGTERM(15)을 먼저 시도하고 응답이 없을 때만 SIGKILL(9)을 사용한다. |
| 패키지 관리 | `apt`는 인터넷 저장소를 다루는 고수준 도구로 `sudo`가 필요하다. `update`(목록 갱신) → `upgrade`(실제 갱신) 순으로 실행하며, `remove`는 설정 파일을 남기고 `purge`는 완전히 제거한다. |
| dpkg | 개별 `.deb`를 다루는 저수준 도구로, `-l`(목록)·`-L`(파일)·`-S`(소속) 조회에 사용한다. |
