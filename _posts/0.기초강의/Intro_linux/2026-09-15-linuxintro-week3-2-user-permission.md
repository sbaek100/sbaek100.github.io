본 강의는 리눅스 기초 과정에서 가장 중요한 내용을 다룬다.

리눅스는 여러 사용자가 하나의 시스템을 함께 사용하는 **다중 사용자 운영체제**이다. 이러한 환경에서 발생하는 문제의 대부분은 "누가 무엇에 접근할 수 있는가"라는 설정이 잘못된 데에서 비롯된다. 따라서 계정과 권한을 정확히 이해하는 것이 안전한 시스템 운영의 출발점이다.

> **실습 환경에 관한 주의**
> 본 강의의 실습은 실제로 계정을 생성하고 파일 권한을 변경한다. 반드시 **학습용 시스템**에서만 수행하여야 하며, 운영 중인 컴퓨터에서 실행해서는 안 된다. 각 실습 말미의 정리 절차를 반드시 수행한다. 모든 실습은 터미널(`Ctrl + Alt + T`)에서 진행하며, 프롬프트는 `student@ubuntu-y1:~$` 형태이다.
{: .prompt-danger }

# 제1절. 다중 사용자와 관리자

---

## 1.1 다중 사용자 운영체제의 이해

리눅스는 여러 사용자가 하나의 시스템을 이용할 수 있도록 설계되었다. 이러한 환경에서는 각 사용자의 자료를 서로 격리하고, 시스템의 중요 파일을 일반 사용자로부터 보호하는 장치가 필요하다.

이를 **공동주택**에 비유하면 다음과 같이 대응시킬 수 있다.

| 공동주택 | 리눅스 시스템 |
|---|---|
| 입주민 | 사용자(user) |
| 세대 열쇠 | 비밀번호 |
| 각 세대 | 홈 디렉터리(`/home/사용자명`) |
| 관리사무소장 | 관리자(root) |
| 동별 자치회 | 그룹(group) |
| 공용 공간 출입 권한 | 그룹 권한 |
| 세대별 출입 통제 | 파일 접근 권한 |

이러한 구조가 제대로 설정되지 않으면 다른 사용자가 타인의 파일을 열람하거나, 일반 사용자가 관리자 권한을 획득하거나, 공용 디렉터리의 자료를 타인이 삭제하는 문제가 발생한다.

---

## 1.2 UID와 GID

사용자는 `student`, `alice`와 같은 이름으로 식별되지만, 리눅스 내부에서는 **숫자**로 관리된다.

| 용어 | 약어 풀이 | 의미 |
|---|---|---|
| **UID** | **U**ser **ID**entifier | 사용자 식별 번호 |
| **GID** | **G**roup **ID**entifier | 그룹 식별 번호 |

`ls -l`이 화면에 표시하는 소유자 이름은, 실제로는 파일에 저장된 숫자(UID)를 계정 목록과 대조하여 이름으로 바꾸어 보여 준 결과이다.

우분투에서 UID는 다음과 같이 구획되어 있다.

| UID 범위 | 구분 | 예시 |
|---|---|---|
| **0** | **관리자(root)** | root |
| 1 ~ 999 | 시스템이 사용하는 계정 | daemon, www-data |
| **1000 이상** | **일반 사용자 계정** | student, alice |

> **매우 중요한 보안 개념**
> 리눅스는 **UID가 0이면 계정 이름과 무관하게 관리자 권한을 부여한다.** 즉 관리자를 결정하는 것은 이름이 아니라 UID 0이라는 숫자이다.
>
> 그러므로 시스템을 점검할 때 "UID가 0인 계정이 root 하나뿐인가"를 확인하는 것은 기본적인 보안 점검 항목이다.
{: .prompt-warning }

---

## 1.3 관리자(root)와 `sudo`

일반 사용자는 시스템 전체에 영향을 주는 작업(계정 생성, 다른 사용자의 파일 접근, 설정 변경 등)을 수행할 수 없다. 이러한 작업은 **관리자(root)** 만 수행할 수 있다.

우분투는 보안을 위해 root 계정으로 직접 로그인하는 것을 막아 두고, 대신 **`sudo`** 명령을 통해 필요한 순간에만 관리자 권한을 빌려 쓰도록 한다.

| 항목 | 설명 |
|---|---|
| `sudo` | **s**uper**u**ser **do**의 약어. 뒤에 오는 **한 명령만** 관리자 권한으로 실행 |
| 필요한 비밀번호 | root의 비밀번호가 아니라 **자기 자신의 비밀번호** |
| 사용 자격 | `sudo` 그룹에 소속된 사용자만 사용 가능 |
| 기록 | 실행한 명령이 로그에 남아 나중에 추적할 수 있음 |

```bash
sudo useradd -m alice      # 계정 생성 (관리자 권한 필요)
sudo -l                    # 자신에게 허용된 sudo 명령 조회
```

관리자 권한이 필요한 명령 앞에는 `sudo`를 붙인다. 계정을 만들거나 다른 사용자의 파일을 다루는 작업은 시스템 전체에 영향을 미치므로 관리자 권한이 요구되기 때문이다.

> **[그림 3-4] 필요**
> 일반 사용자 `student`가 `sudo` 명령을 통해 관리자(root) 권한을 잠시 빌려 작업을 수행하고 다시 일반 권한으로 돌아오는 과정을, 권한 상승과 복귀를 화살표로 표현한 개념도.
{: .prompt-tip }

---

> ### 따라 하기 2-1. 사용자와 그룹 정보 확인
>
> **목적** 현재 시스템의 사용자와 그룹 정보를 확인하고, UID 체계를 실제 데이터로 검증한다.
{: .prompt-tip }

**1단계.** 자신의 UID와 소속 그룹을 확인한다.

```bash
id
```

> 출력에서 `uid=`(사용자 번호), `gid=`(기본 그룹), `groups=`(전체 소속 그룹)를 각각 확인한다.

```bash
groups
```

> 소속 그룹의 이름만 간략히 출력한다.

**2단계.** 계정 목록 파일에서 일반 사용자를 조회한다.

```bash
grep "bash$" /etc/passwd
```

> `/etc/passwd`는 시스템에 등록된 모든 계정 정보를 담은 파일이다. 로그인 셸이 `bash`로 끝나는 계정, 즉 사람이 로그인하여 사용하는 계정을 확인한다.

**3단계.** 자신의 sudo 권한을 확인한다.

```bash
sudo -l
```

> 처음 `sudo`를 사용할 때 자기 자신의 비밀번호를 입력한다. 자신에게 허용된 명령의 범위가 출력된다.

> **확인 사항** 자신의 UID가 1000 이상이고, `groups`에 `sudo`가 포함되어 있으며, `sudo -l`이 정상 실행되었다면 성공이다.
{: .prompt-tip }

# 제2절. 사용자와 그룹 관리

---

## 2.1 계정 생성 — `useradd`

`useradd`는 계정을 생성하는 표준 명령이며, 관리자 권한이 필요하므로 항상 `sudo`와 함께 사용한다.

```bash
sudo useradd -m -s /bin/bash alice
sudo passwd alice
```

| 옵션 | 약어 풀이 | 기능 |
|---|---|---|
| **`-m`** | **m**ake home | **홈 디렉터리 생성 (항상 지정)** |
| **`-s`** | **s**hell | 로그인 셸 지정 |
| `-c` | **c**omment | 실명 등 설명 정보 |
| `-G` | **G**roups | 보조 그룹 지정 |

> **`-m` 옵션을 생략하는 경우의 문제**
> 홈 디렉터리가 생성되지 않아, 해당 계정으로 로그인하면 정상적인 작업이 어렵다. **`useradd`에는 항상 `-m`을 지정하여야 한다.**
{: .prompt-warning }

계정 생성 직후에는 비밀번호가 설정되어 있지 않다. `passwd`(**passw**or**d**의 약어) 명령으로 비밀번호를 부여하여야 로그인이 가능해진다.

```bash
sudo passwd alice          # 다른 사용자의 비밀번호 설정
passwd                     # 자신의 비밀번호 변경
```

---

## 2.2 계정 수정과 삭제

| 명령 | 약어 풀이 | 기능 |
|---|---|---|
| **`usermod -aG 그룹 사용자`** | **user mod**ify | **보조 그룹 추가** |
| `usermod -L 사용자` / `-U 사용자` | | 계정 잠금 / 해제 |
| `userdel -r 사용자` | **user del**ete | 계정과 홈 디렉터리까지 삭제 |

> **`-aG`에서 `-a`를 생략할 경우의 위험**
>
> - `usermod -aG devteam alice` → 기존 보조 그룹을 **유지**하면서 devteam을 추가한다.
> - `usermod -G devteam alice` → 기존 보조 그룹을 **모두 제거**하고 devteam만 남긴다.
>
> `-a`는 **a**ppend(추가)의 약어이다. 그룹을 추가할 때는 **반드시 `-aG` 형태**로 사용하여야 한다.
{: .prompt-danger }

---

## 2.3 그룹 관리 — `groupadd`

동일한 권한을 여러 사용자에게 부여할 때, 사용자마다 개별 설정하는 것은 비효율적이다. 대신 **그룹**에 권한을 부여하고 사용자를 그룹에 소속시킨다.

| 명령 | 약어 풀이 | 기능 |
|---|---|---|
| `groupadd 그룹명` | **group add** | 그룹 생성 |
| `groupdel 그룹명` | **group del**ete | 그룹 삭제 |

우분투는 사용자 `alice`를 생성하면 동명의 그룹 `alice`를 함께 만들어 이를 **기본 그룹**으로 지정한다. 사용자가 생성한 파일은 이 기본 그룹의 소유가 된다. 이와 별도로 여러 사용자가 공유하는 그룹을 **보조 그룹**이라 하며, `usermod -aG`로 추가한다.

---

> ### 따라 하기 2-2. 계정 생성과 그룹 배정
>
> **목적** `useradd`로 계정을 만들고, 그룹을 생성하여 사용자를 배정한다.
{: .prompt-tip }

**1단계.** 실습용 그룹을 생성한다.

```bash
sudo groupadd devteam
```

```bash
grep devteam /etc/group
```

> `/etc/group`은 그룹 정보를 담은 파일이다. `devteam` 그룹이 생성되었는지 확인한다.

**2단계.** 옵션을 갖추어 계정을 생성한다.

```bash
sudo useradd -m -s /bin/bash -c "Alice Kim" -G devteam alice
```

```bash
sudo useradd -m -s /bin/bash -c "Bob Lee" -G devteam bob
```

**3단계.** 생성 결과를 확인한다.

```bash
id alice
```

> `uid`, `gid`와 함께 보조 그룹 `devteam`이 표시되는지 확인한다.

```bash
grep devteam /etc/group
```

> `devteam:x:1001:alice,bob` 형태로 두 사용자가 소속되었음을 확인한다.

**4단계.** 홈 디렉터리가 생성되었는지 확인한다.

```bash
ls -ld /home/alice
```

> 권한이 `750`으로 설정되어 다른 일반 사용자가 내용을 조회할 수 없음을 확인한다.

**5단계.** 비밀번호를 설정한다.

```bash
sudo passwd alice
```

```bash
sudo passwd bob
```

> 실습용 비밀번호로 `Linux#2026`을 사용한다. 입력 시 화면에 문자가 표시되지 않는 것은 정상이다.

**6단계.** 이미 만든 계정을 나중에 그룹에 추가하는 방법을 확인한다.

```bash
sudo useradd -m -s /bin/bash -c "Dev One" dev1
```

```bash
sudo usermod -aG devteam dev1
```

```bash
id dev1
```

> **`-a`를 반드시 포함하였는지 확인한다.** `id dev1`에 `devteam`이 표시되어야 한다.

> **확인 사항** `id alice`와 `id dev1`에 `devteam`이 표시되고, `/home/alice`가 생성되어 있다면 성공이다.
{: .prompt-tip }

# 제3절. 파일 접근 권한

---

## 3.1 권한의 3×3 구조

`ls -l`로 파일을 조회하면 맨 앞에 열 개의 문자가 표시된다. 첫 글자는 종류(파일은 `-`, 디렉터리는 `d`)를 나타내고, 나머지 아홉 글자가 권한이다. 이 아홉 글자는 **세 주체**에 대하여 **세 종류의 권한**을 부여하는 방식으로 구성된다.

```
     -     rwx     r-x     r--
     │      │       │       │
     │      │       │       └── others : 기타 사용자
     │      │       └────────── group  : 소유 그룹의 구성원
     │      └────────────────── user   : 소유자
     └───────────────────────── 파일 종류
```

| 주체 | 의미 |
|---|---|
| **user** | 파일의 소유자 |
| **group** | 소유 그룹에 속한 구성원 |
| **others** | 그 외의 모든 사용자 |

> **[그림 3-5] 필요**
> `ls -l` 출력에서 권한 표기(`-rwxr-xr--`)의 각 자리를 소유자(user)/그룹(group)/기타(others)로 구분하여 화살표로 설명한 다이어그램.
{: .prompt-tip }

---

## 3.2 파일과 디렉터리에서 `rwx`의 의미 차이

**본 강의에서 가장 중요한 내용이다.** 권한 학습에서 가장 많이 혼동하는 지점이다.

| 권한 | 숫자 | **일반 파일**에서의 의미 | **디렉터리**에서의 의미 |
|---|---|---|---|
| `r` (**r**ead) | **4** | 파일 내용을 읽을 수 있다 | **내부 항목의 이름 목록을 조회할 수 있다(`ls`)** |
| `w` (**w**rite) | **2** | 파일 내용을 수정할 수 있다 | **내부에 항목을 생성·삭제·이름 변경할 수 있다** |
| `x` (e**x**ecute) | **1** | 파일을 프로그램으로 실행할 수 있다 | **디렉터리를 통과할 수 있다(`cd`, 내부 파일 접근)** |

디렉터리를 **도서관**에 비유하면 다음과 같이 이해할 수 있다.

- **`r`** = 장서 목록표를 열람할 권리
- **`x`** = 서가 안으로 들어갈 권리
- **`w`** = 책을 꽂거나 빼낼 권리

목록표만 볼 수 있고 서가에 들어갈 수 없다면 실제로 책을 꺼낼 수 없듯이, **`x` 권한이 없는 디렉터리 내부의 파일에는 접근할 수 없다.**

> **본 강의에서 가장 중요한 귀결**
> **파일의 삭제 가능 여부는 파일 자신의 권한이 아니라, 그 파일이 위치한 디렉터리의 `w` 권한이 결정한다.**
>
> 파일을 삭제하는 행위는 "파일 내용을 수정하는 일"이 아니라 "디렉터리에 등록된 항목을 제거하는 일"이기 때문이다. 따라서 읽기 전용 파일도 상위 디렉터리에 쓰기 권한이 있으면 삭제될 수 있다.
{: .prompt-danger }

![](/assets/img/posts/2026-09-15-linuxintro-week3-2-user-permission-1787465918239.png)
---

## 3.3 숫자(8진수) 표기법

읽기 4, 쓰기 2, 실행 1을 합산하여 표기한다.

| 기호 | 계산 | 숫자 |
|---|---|---|
| `rwx` | 4+2+1 | **7** |
| `rw-` | 4+2 | **6** |
| `r-x` | 4+1 | **5** |
| `r--` | 4 | **4** |
| `---` | 0 | **0** |

세 주체의 값을 나란히 적으면 세 자리 숫자가 된다. 실무에서 자주 사용하는 조합은 다음과 같다.

| 숫자 | 기호 | 용도 |
|---|---|---|
| **644** | `rw-r--r--` | 일반 문서·설정 파일 |
| **755** | `rwxr-xr-x` | 실행 파일, 공개 디렉터리 |
| **700** | `rwx------` | 개인 전용 디렉터리 |
| **600** | `rw-------` | 개인 키 등 민감한 파일 |
| **777** | `rwxrwxrwx` | 모두에게 전권 부여. **사실상 사용 금지** |

---

## 3.4 권한 변경 — `chmod`

`chmod`는 **ch**ange **mod**e(모드를 변경하다)의 약어이다. 두 가지 방식으로 사용할 수 있다.

**방식 1: 숫자(8진수) 모드**

```bash
chmod 644 report.txt
chmod 755 script.sh
```

**방식 2: 기호 모드**

| 구분 | 기호 | 의미 |
|---|---|---|
| 대상 | `u` / `g` / `o` / `a` | user / group / others / all |
| 연산자 | `+` / `-` / `=` | 추가 / 제거 / 지정(나머지 제거) |
| 권한 | `r` / `w` / `x` | 읽기 / 쓰기 / 실행 |

```bash
chmod u+x script.sh          # 소유자에게 실행 권한 추가
chmod go-w shared.txt        # 그룹·기타의 쓰기 권한 제거
chmod a=r public.txt         # 모두에게 읽기 권한만 부여
```

---

## 3.5 소유권 변경 — `chown`, `chgrp`

| 명령 | 약어 풀이 | 기능 |
|---|---|---|
| `chown` | **ch**ange **own**er | 소유자 변경 |
| `chgrp` | **ch**ange **gr**ou**p** | 소유 그룹 변경 |

```bash
sudo chown alice file              # 소유자를 alice로 변경
sudo chown alice:devteam file      # 소유자와 그룹 동시 변경
sudo chgrp devteam file            # 그룹만 변경
```

> **`chown`이 관리자 전용인 이유**
> 일반 사용자가 자신의 파일을 타인에게 마음대로 넘길 수 있다면, 저장 공간 제한을 회피하거나 책임 소재를 흐리는 등의 문제가 생긴다. 이러한 이유로 `chown`은 관리자만 실행할 수 있으며 `sudo`가 필요하다.
{: .prompt-warning }

---

## 3.6 기본 생성 권한 — `umask`

새로 생성되는 파일과 디렉터리의 권한은 **기준값에서 umask 값을 제거**하여 결정된다.

| 대상 | 기준값 | 이유 |
|---|---|---|
| **일반 파일** | **666** (`rw-rw-rw-`) | 생성 시점에는 실행 권한을 부여하지 않는다 |
| **디렉터리** | **777** (`rwxrwxrwx`) | 진입을 위해 실행 권한이 필요하다 |

우분투의 기본 umask는 **022**이며, 이때 파일은 **644**, 디렉터리는 **755**로 생성된다.

> **자주 혼동하는 함정**
> "umask가 022일 때 새로 생성되는 **파일**의 권한은?"의 정답은 **644**이며, 755가 아니다. 755는 디렉터리의 답이다. 파일의 기준값(666)과 디렉터리의 기준값(777)이 서로 다르다는 점이 핵심이다.
{: .prompt-danger }

>
> **목적** 숫자 방식과 기호 방식으로 권한을 설정하고, 권한 변경이 실제 동작에 미치는 영향을 확인한다.
{: .prompt-tip }

**1단계.** 실습 디렉터리와 파일을 준비한다.

```bash

```

```bash
echo "일반 문서입니다." > doc.txt
```

```bash

```

```bash
ls -l
```

> 두 파일 모두 실행 권한(`x`)이 없음을 확인한다.

**2단계.** 실행 권한이 없는 스크립트를 실행해 본다.

```bash

```

> `Permission denied` 오류가 발생한다. 내용이 스크립트이더라도 실행 권한이 없으면 실행할 수 없다.

**3단계.** 기호 모드로 실행 권한을 부여한다.

```bash
chmod u+x run.sh
```

```bash

```

> 소유자 자리에 `x`가 추가된 것을 확인한다.

```bash
./run.sh
```

> 정상적으로 실행된다.

**4단계.** 숫자 모드로 동일한 조작을 수행한다.

```bash
chmod 644 run.sh
```

```bash
ls -l run.sh
```

> 실행 권한이 다시 제거되었다.

```bash
chmod 755 run.sh
```

**5단계.** 기호 모드의 여러 형태를 사용한다.

```bash
chmod go-r doc.txt
```

```bash
chmod a=r doc.txt
```

```bash
ls -l doc.txt
```

> `a=r`은 모든 주체에게 읽기 권한만 부여하고 나머지는 제거한다. 결과가 `-r--r--r--`임을 확인한다.

> **확인 사항** 두 방식으로 동일한 권한을 설정할 수 있고, 실행 권한 유무에 따라 스크립트 실행 여부가 달라지는 것을 확인하였다면 성공이다.

> ### 따라 하기 2-4. 디렉터리 권한과 삭제 권한 확인 ★핵심 실습
>
> **목적** 디렉터리에서 `r`과 `x`가 각각 무엇을 허용하는지 확인하고, 파일 삭제 권한이 어디에 있는지 실증한다.
>
> **본 실습은 본 강의에서 가장 중요한 내용이다.**
{: .prompt-tip }

**1단계.** 실험용 디렉터리와 파일을 준비한다.

```bash

```

```bash

```

```bash
echo "공개 내용" > secret_dir/public.txt
```

```bash

```

> 다른 사용자 alice가 홈 디렉터리를 통과할 수 있도록 통과 권한(`x`)만 부여하였다.

**2단계.** 디렉터리에 읽기 권한만 있고 실행 권한이 없는 경우를 확인한다.

```bash

```

```bash

```

> **이름 목록은 출력된다.** 디렉터리의 `r`(읽기) 권한이 목록 조회를 허용하기 때문이다.

```bash
sudo -u alice cat ~/lab03/perm/secret_dir/public.txt
```

> **실패한다.** 파일에 도달하려면 디렉터리를 통과(`x`)해야 하는데, 실행 권한이 없기 때문이다.

**3단계.** 디렉터리에 실행 권한을 부여한다.

```bash
chmod 755 secret_dir
```

```bash
sudo -u alice cat ~/lab03/perm/secret_dir/public.txt
```

> **이번에는 성공한다.** 디렉터리의 `r`과 `x`가 모두 있어야 내부 파일을 정상적으로 활용할 수 있다. 이것이 디렉터리에 통상 `755`나 `750`을 부여하는 이유이다.

**4단계.** 파일 삭제 권한의 소재를 확인한다.

```bash
chmod 444 secret_dir/public.txt
```

```bash
ls -l secret_dir/public.txt
```

> `-r--r--r--`이다. 누구도 쓸 수 없는 읽기 전용 파일이다.

```bash
rm -f secret_dir/public.txt
```

```bash
ls secret_dir
```

> **삭제되었다.** 쓰기 권한이 전혀 없는 파일임에도 삭제된 것이다.

> **핵심 결론**
> 파일을 삭제하는 행위는 "디렉터리에 등록된 항목을 제거하는 일"이므로, 삭제 가능 여부는 파일 자신의 권한이 아니라 **그 파일이 위치한 디렉터리의 `w` 권한**이 결정한다.
{: .prompt-danger }

**5단계.** 원상 복구한다.

```bash
chmod 750 ~
```

> **확인 사항**
> 다음 세 문장을 자신의 표현으로 설명할 수 있다면 성공이다.
> 1. 디렉터리의 `r`은 목록 조회, `x`는 통과를 허용한다.
> 2. `x` 권한이 없는 디렉터리 내부의 파일에는 접근할 수 없다.
> 3. 파일의 삭제 가능 여부는 상위 디렉터리의 `w` 권한이 결정한다.
{: .prompt-tip }

# 제4절. 특수 권한(SetUID·SetGID·Sticky Bit)

---

앞서 학습한 아홉 개의 기본 권한(`rwx` × 3주체)만으로는 해결하기 어려운 상황이 있다. 예컨대 일반 사용자가 자신의 비밀번호를 변경하려면 관리자만 접근할 수 있는 `/etc/shadow` 파일을 수정해야 한다. 이처럼 **필요한 최소한의 권한만 일시적으로 부여**하기 위하여, 리눅스는 기본 권한 위에 세 가지 **특수 권한(Special Permission)** 을 제공한다.

![](/assets/img/posts/2026-09-15-linuxintro-week3-2-user-permission-1787465942278.png)

## 4.1 SetUID — 실행 시 소유자의 권한으로

**SetUID(Set User ID, 8진수 4000)** 가 설정된 실행 파일은, 그 파일을 **누가 실행하든 파일 소유자의 권한으로 동작**한다.

대표적인 예가 비밀번호 변경 명령 `passwd`이다.

```bash
ls -l /usr/bin/passwd
```

```
-rwsr-xr-x 1 root root 59640 ... /usr/bin/passwd
```

> 소유자 권한 자리의 `x`가 있어야 할 위치에 **`s`** 가 표시되어 있다. 이것이 SetUID이다. `passwd`의 소유자는 root이므로, 일반 사용자가 `passwd`를 실행하면 **일시적으로 root의 권한을 빌려** `/etc/shadow`에 접근하여 자신의 비밀번호를 안전하게 변경할 수 있다.

## 4.2 SetGID — 실행 시 그룹의 권한으로

**SetGID(Set Group ID, 8진수 2000)** 는 실행 시 파일 소유 **그룹**의 권한으로 동작하게 한다. 특히 **디렉터리에 설정하면, 그 안에서 새로 생성되는 모든 파일이 디렉터리의 소유 그룹을 자동으로 상속**한다. 팀 프로젝트 디렉터리에서 모든 산출물이 동일한 그룹 소유권을 갖도록 할 때 유용하다.

```bash
ls -ld /path/to/team_dir
```

```
drwxr-sr-x 2 root project_team 4096 ... team_dir
```

> 그룹 권한 자리의 `x` 위치에 **`s`** 가 표시된다.

## 4.3 Sticky Bit — 공유 디렉터리의 삭제 제한

**Sticky Bit(8진수 1000)** 는 여러 사용자가 공유하는 디렉터리에서, **파일을 만든 사람(소유자)과 root만 그 파일을 삭제**할 수 있도록 제한한다. 대표적인 예가 모든 사용자가 임시 파일을 쓰는 `/tmp` 디렉터리이다.

```bash
ls -ld /tmp
```

```
drwxrwxrwt 10 root root 4096 ... /tmp
```

> 기타(others) 권한 자리의 `x` 위치에 **`t`** 가 표시된다. 이 덕분에 `/tmp`는 누구나 파일을 생성할 수 있지만, 타인의 파일은 삭제할 수 없다. 3.2절에서 학습한 "삭제 권한은 상위 디렉터리의 `w`가 결정한다"는 원칙의 예외를 만들어, 공유 공간을 안전하게 유지하는 장치이다.

## 4.4 특수 권한의 부여

`chmod`의 숫자 모드에서 기존 세 자리 앞에 특수 권한 자리를 하나 더 붙이거나, 기호 모드에서 `s`·`t`를 사용한다.

| 특수 권한 | 숫자 | 기호 방식 | 표기 문자 |
|---|---|---|---|
| SetUID | 4000 | `chmod u+s 파일` | `s`(소유자 자리) |
| SetGID | 2000 | `chmod g+s 디렉터리` | `s`(그룹 자리) |
| Sticky Bit | 1000 | `chmod +t 디렉터리` | `t`(기타 자리) |

```bash
chmod 4755 program      # SetUID + rwxr-xr-x
chmod 2775 team_dir     # SetGID + rwxrwxr-x
chmod 1777 shared_dir   # Sticky Bit + rwxrwxrwx
```

> **특수 권한은 보안의 양날이다**
> 특수 권한은 편리하지만, 잘못 설정하면 심각한 취약점이 된다. 예컨대 소유자가 root인 일반 실행 파일에 불필요하게 SetUID가 걸려 있으면, 공격자가 그 파일을 통해 root 권한을 탈취할 수 있다. 따라서 **불필요한 SetUID/SetGID 파일이 있는지 주기적으로 점검**하여야 한다. 이 점검은 제6절과 다음 시간의 시나리오 실습에서 다룬다.
{: .prompt-danger }

> ### 따라 하기 3-1. 시스템의 특수 권한 확인하기
>
> **목적** 실제 시스템에서 SetUID와 Sticky Bit가 설정된 파일·디렉터리를 확인한다.
{: .prompt-tip }

**1단계.** `passwd`의 SetUID를 확인한다.

```bash
ls -l /usr/bin/passwd
```

> 소유자 권한 자리에 `s`가 보이면 SetUID가 설정된 것이다.

**2단계.** `/tmp`의 Sticky Bit를 확인한다.

```bash
ls -ld /tmp
```

> 기타 권한 자리에 `t`가 보이면 Sticky Bit가 설정된 것이다.

**3단계.** 시스템 전체에서 SetUID가 설정된 파일을 검색한다.

```bash
find /usr/bin -perm -4000 -type f
```

> `-perm -4000`은 SetUID가 설정된 파일을 찾는 조건이다. `passwd`, `sudo` 등 관리자 권한이 필요한 명령들이 출력된다. 이 목록에 낯선 파일이 있다면 침해를 의심하여야 한다.

> **확인 사항** `passwd`에서 `s`, `/tmp`에서 `t`를 확인하고, `find`로 SetUID 파일 목록을 조회하였다면 성공이다.
{: .prompt-tip }

# 제5절. 확장 파일 속성과 파일 보안

---

기본 권한과 특수 권한 외에도, 리눅스는 파일을 보호하기 위한 여러 기능을 제공한다.

## 5.1 확장 파일 속성 — `chattr`

`chattr`(**ch**ange **attr**ibute, 속성 변경)는 소유자나 root조차 실수로 파일을 변경·삭제하지 못하도록 잠그는 확장 속성을 부여한다.

| 속성 | 의미 | 용도 |
|---|---|---|
| `i`(immutable) | 변경 불가 | 중요 설정 파일을 수정·삭제·이름 변경으로부터 보호 |
| `a`(append-only) | 추가만 가능 | 로그 파일이 덮어써지지 않고 뒤에 추가만 되도록 보호 |

```bash
sudo chattr +i /etc/passwd       # 계정 파일을 변경 불가로 잠금
sudo chattr +a /var/log/audit.log  # 감사 로그를 추가 전용으로 설정
lsattr /etc/passwd               # 설정된 속성 확인
```

> `+i`가 설정된 파일은 root라도 삭제할 수 없다. 해제하려면 `sudo chattr -i 파일`을 먼저 실행해야 한다. 이는 악성코드나 실수에 의한 핵심 파일 변조를 막는 강력한 수단이다.

## 5.2 파일 암호화 — `gpg`

권한만으로는 디스크를 직접 분리하여 읽는 공격을 막을 수 없다. 민감한 파일은 **암호화**하여 보관한다. `gpg`(GNU Privacy Guard)는 파일을 대칭키 방식으로 암호화한다.

```bash
gpg -c 중요문서.pdf    # 비밀번호를 입력하면 중요문서.pdf.gpg 가 생성된다
```

> 암호화된 `.gpg` 파일은 올바른 비밀번호 없이는 열 수 없으므로, 파일이 유출되어도 내용이 보호된다.

## 5.3 파일 변경의 추적 — 로깅

시스템은 중요한 변경을 로그로 기록한다. 로그를 통하여 "누가, 언제, 어떤 명령으로" 파일을 변경하였는지 추적할 수 있다.

```bash
tail -f /var/log/syslog | grep 파일명
```

> `tail -f`는 로그가 기록되는 즉시 화면에 이어서 출력한다. 관리자는 이를 통하여 파일 변경을 실시간으로 감시한다. 접근 통제(권한)가 사전 예방이라면, 로깅은 사후 추적의 수단이다.

# 제6절. 접근 권한 취약점과 대응

---

지금까지 학습한 권한 관리는 모두 **취약점을 예방**하기 위한 것이다. 실무에서 접근 권한과 관련하여 자주 발생하는 취약점과 그 대응을 정리한다.

| 구분 | 대표적 보안 취약점 | 리눅스에서의 대응 |
|---|---|---|
| **권한 설정 오류** | 과도한 권한 부여(`777`), 불필요한 실행 권한, 잘못된 SetUID | 기본 권한 체계(`rwx`)를 최소로, SetUID/SetGID 점검, Sticky Bit 활용 |
| **중요 파일 노출** | 설정 파일·인증 정보·백업 파일(`.bak`, `.old`)의 과도한 공개 | `chmod 600`으로 접근 제한, `chattr +i`로 보호, 암호화 |
| **악성코드 감염** | 실행 파일 변조, 시스템 파일 감염 | inode 기반 파일 관리, 확장 속성으로 변경 차단, 무결성 점검 |
| **무단 접근** | 인증 우회, 권한 상승 공격 | 파일 소유권 관리, 로깅을 통한 추적, 최소 권한 원칙 준수 |

> **최소 권한 원칙(Principle of Least Privilege)**
> 접근 권한 관리의 핵심 원칙은 **"각 사용자와 프로그램에게 작업에 필요한 최소한의 권한만 부여한다"** 는 것이다. 권한이 넓을수록 그것이 탈취되었을 때의 피해도 커진다. `777`처럼 모두에게 전권을 주는 설정을 피하고, 필요한 주체에게 필요한 권한만 부여하는 습관이 보안의 출발점이다.
{: .prompt-danger }

본 강의에서 학습한 권한 관리를 실제 상황에 적용하는 훈련은 다음 시간의 **접근 권한 시나리오 실습**에서 수행한다. 그곳에서는 취약하게 설정된 시스템을 직접 진단하고 바로잡는다.

# 제7절. 자주 발생하는 오류와 대응 방법

---

| 화면에 출력된 메시지 | 원인 | 대응 방법 |
|---|---|---|
| `Permission denied` | 권한 부족 | `ls -l`로 권한을 확인한 뒤 `chmod` 또는 `sudo`를 적용한다. |
| `Operation not permitted` | 관리자 전용 작업 시도 | `sudo`를 붙인다(`chown` 등). |
| `is not in the sudoers file` | `sudo` 그룹에 속하지 않음 | 관리자가 `sudo usermod -aG sudo 사용자`로 추가한다. |
| `useradd: user 'alice' already exists` | 이미 존재하는 계정 | `id alice`로 확인한다. 필요 시 `userdel`로 정리한다. |
| `group does not exist` | 그룹이 없음 | `groupadd`로 먼저 생성한다. |
| 디렉터리 목록은 보이나 파일이 열리지 않음 | 디렉터리에 `x` 권한 없음 | `chmod +x 디렉터리` |
| 그룹에 추가했으나 권한이 적용되지 않음 | 세션에 반영되지 않음 | **로그아웃 후 재로그인**한다. |

> **가장 빈번한 혼란 사례**
> `usermod -aG`로 그룹에 추가하였음에도 권한이 적용되지 않는 경우가 있다. **그룹 소속은 로그인 시점에 결정되므로** 이미 로그인해 있는 세션에는 즉시 반영되지 않는다. 로그아웃 후 재로그인하면 해결된다.
{: .prompt-warning }

# 제8절. 요약

---

## 8.1 핵심 개념 정리

| 구분 | 요점 |
|---|---|
| 사용자 식별 | 리눅스는 사용자를 UID로 식별하며, **UID 0은 계정 이름과 무관하게 관리자**이다. |
| 관리 권한 | 시스템 전체에 영향을 주는 작업은 `sudo`로 관리자 권한을 빌려 수행한다. |
| 계정 관리 | 생성은 `useradd -m -s`, 비밀번호는 `passwd`, 보조 그룹 추가는 반드시 `usermod -aG`로 한다. |
| 소유권 | `chown`은 소유자, `chgrp`는 소유 그룹을 변경하며 관리자 권한이 필요하다. |
| **권한의 의미** | **파일과 디렉터리에서 `rwx`의 의미가 다르다.** 디렉터리의 `r`은 목록 조회, `x`는 통과, `w`는 항목 생성·삭제이다. |
| **삭제 권한** | **파일의 삭제 가능 여부는 상위 디렉터리의 `w` 권한이 결정한다.** |
| umask | 기준값은 파일 666, 디렉터리 777이다. umask 022이면 파일 644, 디렉터리 755가 된다. |

---

## 8.2 본 강의에서 학습한 명령어

| 명령어 | 약어 풀이 | 기능 |
|---|---|---|
| `id` / `groups` | — | 소속 확인 |
| `sudo` | superuser do | 관리자 권한으로 명령 실행 |
| `useradd -m -s` | user add | 계정 생성 |
| `usermod -aG` | user modify | 계정 수정·그룹 추가 |
| `userdel -r` | user delete | 계정 삭제 |
| `passwd` | password | 비밀번호 설정 |
| `groupadd` / `groupdel` | group add / delete | 그룹 생성·삭제 |
| `chmod` | change mode | 권한 변경(기본·특수 권한) |
| `chown` | change owner | 소유자 변경 |
| `chgrp` | change group | 소유 그룹 변경 |
| `umask` | — | 기본 생성 권한 설정 |
| `find -perm` | — | 특정 권한(예: SetUID 4000) 파일 검색 |
| `chattr` / `lsattr` | change / list attribute | 확장 속성 부여·확인(`+i`, `+a`) |
| `gpg -c` | GNU Privacy Guard | 파일 암호화 |

---

## 8.3 특수 권한과 파일 보호 요약

| 구분 | 요점 |
|---|---|
| SetUID (4000) | 실행 시 파일 **소유자**의 권한으로 동작한다(예: `passwd`, `-rwsr-xr-x`). |
| SetGID (2000) | 실행 시 파일 **그룹**의 권한으로 동작하며, 디렉터리에 걸면 그룹 소유권을 상속한다. |
| Sticky Bit (1000) | 공유 디렉터리에서 **소유자와 root만** 파일을 삭제할 수 있다(예: `/tmp`, `drwxrwxrwt`). |
| `chattr +i` / `+a` | 변경 불가·추가 전용 속성으로 핵심 파일을 보호한다. |
| 최소 권한 원칙 | 필요한 최소한의 권한만 부여한다. `777`을 피한다. |

---

## 8.4 반드시 기억해야 할 네 가지

| 번호 | 내용 |
|---|---|
| 1 | **UID 0은 관리자이다.** 계정 이름과 무관하다. |
| 2 | **디렉터리의 `r`은 목록 조회, `x`는 통과이다.** 둘 다 있어야 정상적으로 활용할 수 있다. |
| 3 | **파일 삭제 권한은 상위 디렉터리의 `w`가 결정한다.** (단, Sticky Bit는 예외를 만든다) |
| 4 | **umask 022 → 파일 644, 디렉터리 755.** 파일과 디렉터리의 기준값이 서로 다르다. |
