> **이 실습에서 하는 일**
> 하나의 네트워크를 서브넷으로 나누고, 계획한 IP(마지막 사용 가능 주소 포함)를 PC에 할당합니다. 그런 다음 같은 서브넷과 다른 서브넷의 통신이 어떻게 다른지 확인하고, ping을 보낼 때 ARP가 먼저 동작하는 모습을 시뮬레이션으로 관찰합니다.
{: .prompt-info }

## 실습 2-1. 서브넷을 계획하고 IP 할당하기

> **실습 목표** `192.168.1.0/24`를 `/26` 서브넷 4개로 나누고, 계획한 IP를 PC에 할당해 같은/다른 서브넷의 통신 차이를 확인한다.
> **주소 계획** 아래 표를 직접 완성해 본 뒤 실습에 사용한다.
{: .prompt-tip }

**먼저 계산해 봅시다.** `192.168.1.0/24`를 4개로 나누면 `/26`(마스크 255.255.255.192, 블록 크기 64)이 됩니다. 각 서브넷의 네 가지 주소를 채워 보세요.

| 서브넷 | 네트워크 주소 | 첫 사용 가능 | 마지막 사용 가능 | 브로드캐스트 |
|---|---|---|---|---|
| 부서 A | 192.168.1.0 | 192.168.1.1 | 192.168.1.62 | 192.168.1.63 |
| 부서 B | 192.168.1.64 | 192.168.1.65 | 192.168.1.126 | 192.168.1.127 |

_표 2-9. 실습에 사용할 서브넷 계획(부서 A·B만 사용)_

**실습 절차**

**1단계 — 장치 배치.** 스위치(2960) 2대와 PC 4대를 놓습니다. 부서 A의 PC 두 대(PC-A1, PC-A2)는 스위치 SW1에, 부서 B의 PC 두 대(PC-B1, PC-B2) 역시 스위치 SW1에 다이렉트 케이블로 연결합니다.

![](/assets/img/posts/2026-08-25-netintro-02b-lab-subnetting-1786426015200.png)

**2단계 — IP 할당.** 각 PC를 클릭 → `[Desktop] > [IP Configuration] > [Static]`에서 아래 표대로 입력합니다. 서브넷 마스크는 네 대 모두 `255.255.255.192`입니다. 이때 **부서 A의 두 번째 PC에는 그 서브넷의 ‘마지막 사용 가능 주소’를 일부러 배정**해, 계산이 맞았는지 확인해 봅니다.

| PC | 소속 | IP 주소 | 서브넷 마스크 |
|---|---|---|---|
| PC-A1 | 부서 A | 192.168.1.1 | 255.255.255.192 |
| PC-A2 | 부서 A | 192.168.1.62 (마지막 사용 가능 주소) | 255.255.255.192 |
| PC-B1 | 부서 B | 192.168.1.65 | 255.255.255.192 |
| PC-B2 | 부서 B | 192.168.1.126 (마지막 사용 가능 주소) | 255.255.255.192 |

_표 2-10. PC별 IP 배정표_

![](/assets/img/posts/2026-08-25-netintro-02b-lab-subnetting-1786425693839.png)

**3단계 — 같은 서브넷 통신 확인.** PC-A1의 `[Desktop] > [Command Prompt]`에서 같은 부서(같은 서브넷)인 PC-A2로 ping을 보냅니다. 성공해야 합니다.

```text
PC-A1> ping 192.168.1.62

Reply from 192.168.1.62: bytes=32 time<1ms TTL=128
Reply from 192.168.1.62: bytes=32 time<1ms TTL=128
...
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss),
```

**4단계 — 다른 서브넷 통신 확인.** 이번에는 PC-A1에서 다른 부서(다른 서브넷)인 PC-B1로 ping을 보냅니다. **실패**할 것입니다.

```text
PC-A1> ping 192.168.1.65

Request timed out.
Request timed out.
...
    Packets: Sent = 4, Received = 4, Lost = 4 (100% loss),
```

> **왜 실패할까요?** PC-A1(192.168.1.0/26 소속)과 PC-B1(192.168.1.64/26 소속)은 IP 앞부분이 비슷해 보여도 **서로 다른 서브넷**입니다. 다른 서브넷끼리 통신하려면 그 사이를 이어 주는 **라우터**가 있어야 하는데, 지금 구성에는 라우터가 없습니다. 이 ‘다른 서브넷을 잇는 일’이 바로 6강(라우팅)에서 배울 내용입니다. 즉 서브넷은 곧 ‘통신의 경계’인 셈입니다.
{: .prompt-info }

> **결과 확인** 같은 서브넷(PC-A1↔PC-A2)은 성공, 다른 서브넷(PC-A1↔PC-B1)은 실패하면 완료입니다. 마지막 사용 가능 주소(.62, .126)를 배정한 PC도 정상 통신되는 것으로, 계산이 맞았음을 확인할 수 있습니다.
{: .prompt-tip }

> **생각해 보기 — 마스크를 바꾸면 어떻게 될까?**
> 실습이 끝났다면, PC-A1과 PC-B1의 서브넷 마스크만 `255.255.255.0`(/24)으로 바꿔 보세요. 그러면 방금까지 실패하던 두 PC의 ping이 성공할 것입니다. IP 주소는 하나도 바꾸지 않았는데 왜 결과가 달라질까요? 마스크가 ‘어디까지가 같은 네트워크인가’의 경계를 정하기 때문입니다. 확인한 뒤에는 반드시 원래 값(`255.255.255.192`)으로 되돌려 두세요.
{: .prompt-info }

## 실습 2-2. ARP와 ICMP 관찰하기

> **실습 목표** ping(ICMP)을 보내기 전에 ARP가 먼저 동작하는 것을 시뮬레이션으로 눈으로 확인한다.
{: .prompt-tip }

### 관찰하기 전에 — ARP와 ICMP는 왜 짝을 이룰까

우리가 `ping`을 실행하면 실제로 오가는 것은 **ICMP** 메시지입니다. ping은 상대에게 ‘살아 있나요?’라고 묻는 **에코 요청(Echo Request)** 을 보내고, 상대가 ‘네, 살아 있어요’라고 **에코 응답(Echo Reply)** 을 돌려주는 과정입니다(2강 이론 8절). 그런데 여기에는 한 가지 숨은 문제가 있습니다.

데이터가 실제로 케이블 위를 지나가려면, 3계층의 IP 주소만으로는 부족하고 2계층의 **MAC 주소**가 반드시 있어야 합니다(1강·2강). 편지에 비유하면 IP 주소는 ‘받는 사람 이름’, MAC 주소는 ‘실제 집 주소’입니다. 이름만 알고 집 주소를 모르면 편지를 부칠 수 없습니다. 그래서 PC-A1은 PC-A2에게 ICMP를 보내기 **전에**, 먼저 ‘192.168.1.62의 MAC 주소’를 알아내야 합니다. 이 일을 하는 것이 **ARP**입니다(2강 이론 7절).

정리하면, ARP 캐시가 비어 있을 때 `ping 192.168.1.62`를 실행하면 다음 순서로 동작합니다.

| 순서 | 동작 | 종류 |
|---|---|---|
| ① | PC-A1이 자기 ARP 캐시를 확인 → 비어 있음 | — |
| ② | PC-A1: “192.168.1.62 쓰는 분, MAC 알려 주세요” | ARP 요청(브로드캐스트) |
| ③ | PC-A2: “제 MAC은 …입니다” | ARP 응답(유니캐스트) |
| ④ | PC-A1이 IP–MAC을 캐시에 저장한 뒤, 비로소 ICMP 전송 | ICMP 에코 요청 |
| ⑤ | PC-A2가 응답 | ICMP 에코 응답 |

_표 2-11. ping 한 번에 숨어 있는 ARP → ICMP 순서_

여기서 ②번 ARP 요청이 **브로드캐스트**(네트워크 전체에게)인 이유는, 아직 상대의 MAC을 몰라 특정 대상을 콕 집어 보낼 수 없기 때문입니다. 반대로 ③번 응답은 이미 물어본 상대(PC-A1)의 MAC을 알기에 **유니캐스트**(그 한 대에게만)로 돌아옵니다. 이번 실습에서 시뮬레이션으로 눈으로 확인할 것이 바로 이 **‘ARP(브로드캐스트) 먼저, ICMP(유니캐스트) 나중’** 의 순서입니다.

**실습 절차**

**1단계 — ARP 캐시 초기화.** 실습 2-1 구성을 **그대로 이어서** 사용합니다. 스위치나 PC를 다시 만들 필요는 없습니다. 다만 실습 2-1에서 이미 통신을 했기 때문에, PC-A1의 ARP 캐시에는 학습된 항목이 이미 남아 있습니다. ARP가 처음부터 동작하는 모습을 관찰하려면 이 캐시를 먼저 비워야 합니다. PC-A1의 `[Command Prompt]`에서 `arp -d`로 캐시를 지운 뒤, `arp -a`로 비었는지 확인합니다.

```text
PC-A1> arp -d
PC-A1> arp -a
No ARP Entries Found
```

> **왜 캐시를 지워야 하나요?** ARP는 한 번 알아낸 IP–MAC 짝을 캐시에 저장해 두고 재사용합니다(2강 이론 7절). 그래서 실습 2-1처럼 이미 통신한 뒤에는 캐시가 차 있어, 다시 ping을 해도 ARP 요청이 새로 나가지 않습니다. `arp -d`로 캐시를 비우면(또는 몇 분간 통신 없이 두면 자동으로 만료됩니다) ARP가 처음부터 다시 동작하는 것을 관찰할 수 있습니다.
{: .prompt-info }

![](/assets/img/posts/2026-08-25-netintro-02b-lab-subnetting-1786426216693.png)

**2단계.** 오른쪽 아래 `[Simulation]` 버튼을 눌러 시뮬레이션 모드로 바꿉니다.

**3단계.** PC-A1의 Command Prompt에서 `ping 192.168.1.62`를 입력한 뒤, 화면 오른쪽 시뮬레이션 패널의 `[Capture / Forward]` 버튼을 눌러 패킷을 한 단계씩 진행시킵니다. **먼저 ARP(브로드캐스트)가 오간 뒤, 그 다음에 ICMP가 전달되는 순서**를 색깔 봉투로 확인합니다.
(이 단계 전에 Filter 를 확인합시다.)

![](/assets/img/posts/2026-08-25-netintro-02b-lab-subnetting-1786426260513.png)


![](/assets/img/posts/2026-08-25-netintro-02b-lab-subnetting-1786426363872.png)

**4단계.** 움직이는 봉투를 클릭하면 `[PDU Information]` 창이 열려 계층별 헤더(Ethernet·ARP·ICMP)를 볼 수 있습니다. ARP 봉투와 ICMP 봉투의 내용을 각각 열어 비교해 봅니다.

![](/assets/img/posts/2026-08-25-netintro-02b-lab-subnetting-1786426419372.png)

**5단계.** `[Realtime]`으로 돌아와 다시 `arp -a`를 입력하면, 이번에는 방금 학습한 IP–MAC 매핑이 캐시에 들어 있는 것을 볼 수 있습니다.

```text
PC-A1> arp -a
  Internet Address      Physical Address      Type
  192.168.1.62          00d0.58c1.a201        dynamic
```

> **결과 확인** 시뮬레이션에서 ARP가 ICMP보다 먼저 나타나고, 실습 뒤 `arp -a`에 IP–MAC 매핑이 생기면 완료입니다. IP(3계층)는 ‘누구에게’ 보낼지를 정하고, ARP는 그 IP에 해당하는 MAC(2계층)을 찾아 줍니다. 두 계층이 협력하는 지점을 직접 확인한 것입니다.
{: .prompt-tip }

## 잘 안 될 때 점검 순서

| 증상 | 점검할 것 |
|---|---|
| 같은 서브넷인데 ping 실패 | 두 PC의 서브넷 마스크가 `255.255.255.192`로 정확한지, IP 오타는 없는지 |
| 다른 서브넷인데 ping 성공 | 마스크를 `255.255.255.0`으로 잘못 넣었을 가능성(그러면 둘이 같은 네트워크가 됨). 표대로 `.192`인지 확인 |
| `arp -a`에 아무것도 없음 | ping을 한 번도 보내지 않았거나 통신이 실패한 경우. 성공한 통신 뒤에 다시 확인 |
