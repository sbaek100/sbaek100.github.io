앞 편에서 네트워크 계층이 ‘컴퓨터(호스트)까지’ 데이터를 날라 주었다면, **전송 계층**은 그 컴퓨터 안의 정확한 ‘프로그램(프로세스)까지’ 데이터를 전달합니다. TCP/IP의 전송 계층에는 성격이 완전히 다른 두 프로토콜, UDP와 TCP가 있습니다. 이어서 사용자와 맞닿은 **응용 계층**의 주요 프로토콜까지 살펴봅니다.

## 1. 포트 번호의 구조

두 프로토콜을 보기 전에, 이들이 공통으로 쓰는 포트 번호의 구조부터 정리합니다. 포트 번호는 용도에 따라 세 구간으로 나뉘며, 1장에서 본 대표 포트들은 ‘잘 알려진 포트’에 속합니다.

| 구간 | 범위 | 용도 |
|---|---|---|
| 잘 알려진 포트(Well-known) | 0 ~ 1023 | HTTP(80)·DNS(53) 등 표준 서비스가 예약해 사용 |
| 등록된 포트(Registered) | 1024 ~ 49151 | 특정 응용 프로그램이 등록해 사용 |
| 동적 포트(Dynamic) | 49152 ~ 65535 | 클라이언트가 통신할 때 임시로 사용 |

## 2. UDP

**UDP**(User Datagram Protocol)는 연결을 맺지 않고 데이터를 즉시 보내는 단순하고 빠른 프로토콜입니다. 헤더가 8바이트에 불과할 만큼 가볍지만, 그 대가로 신뢰성 기능은 거의 제공하지 않습니다.

![그림 2-11. UDP 세그먼트 구조](/assets/img/posts/2026-03-09-netintro-c2-31.png)
_그림 2-11. UDP 세그먼트 구조_

| 서비스 | UDP의 제공 여부 |
|---|---|
| 프로세스 대 프로세스 통신 | 제공 — 포트 번호로 송·수신 프로세스 식별 |
| 비연결형 서비스 | 제공 — 연결 설정 없이 각 데이터그램을 독립 전송 |
| 흐름 제어 | 미제공 — 수신자 속도를 고려하지 않음 |
| 오류 제어 | 검출만 — 체크섬으로 확인하되, 손상 시 재전송 없이 폐기 |
| 혼잡 제어 | 미제공 — 네트워크 혼잡을 고려하지 않음 |
| 다중화·역다중화 | 제공 — 여러 프로세스가 하나의 UDP를 공유 |

_표 2-14. UDP가 제공하는 서비스_

UDP는 약간의 손실보다 속도·실시간성이 더 중요한 곳에 적합합니다. 인터넷 전화(VoIP)와 실시간 영상 스트리밍, 짧은 요청-응답으로 끝나는 DNS 질의, IP를 자동 할당하는 DHCP 등이 대표적입니다. UDP 기반 프로토콜로는 인증 없이 단순하게 파일을 주고받는 **TFTP**(69번, 장비 부팅 이미지 전송 등)와 장비 상태를 수집·관리하는 **SNMP**(161·162번)가 있습니다.

## 3. TCP

**TCP**(Transmission Control Protocol)는 UDP와 달리 연결을 맺고 신뢰성을 보장합니다. 포트 번호로 두 프로세스를 식별하고, 데이터를 경계 없는 연속된 바이트 흐름(스트림)으로 다루며, 송·수신 버퍼를 두어 흐름 조절·재전송을 준비합니다. 순서 번호와 확인 응답(ACK), 재전송을 통해 데이터가 손실·순서 뒤바뀜 없이 도착하도록 보장하고, 양쪽이 동시에 주고받는 전이중 통신을 지원합니다.

| 통신 방식 | 설명 | 예 |
|---|---|---|
| 단방향(Simplex) | 한 방향으로만 전송 | 라디오 방송 |
| 반이중(Half-duplex) | 양방향이지만 한 번에 한쪽만 | 무전기 |
| 전이중(Full-duplex) | 양방향 동시 전송 | 전화 통화, TCP |

_표 2-15. 통신 방식의 비교_

| 구분 | TCP | UDP |
|---|---|---|
| 연결 방식 | 연결형(연결 설정 후 전송) | 비연결형(바로 전송) |
| 신뢰성 | 높음(순서·재전송 보장) | 낮음(보장 없음) |
| 속도 | 상대적으로 느림 | 빠름 |
| 헤더 크기 | 20~60바이트 | 8바이트 |
| 대표 용도 | 웹·메일·파일 전송 | 실시간 스트리밍·DNS |

_표 2-16. TCP와 UDP의 비교_

둘 중 무엇을 쓸지는 ‘정확함’과 ‘빠름’ 중 무엇이 더 중요한가로 갈립니다. 파일 다운로드·웹처럼 한 글자라도 틀리면 안 되는 통신은 재전송으로 정확성을 보장하는 TCP를, 실시간 영상 통화·게임처럼 조금 끊겨도 흐름이 이어지는 것이 더 중요한 통신은 빠른 UDP를 씁니다. 즉 TCP는 ‘느려도 정확하게’, UDP는 ‘조금 잃어도 빠르게’입니다.

### (1) 세그먼트와 제어 플래그

TCP가 전송하는 데이터 단위를 **세그먼트(Segment)** 라 합니다. 세그먼트는 헤더와 데이터로 이루어지며, 헤더는 기본 20바이트에서 옵션을 더해 최대 60바이트까지 늘어납니다.

![그림 2-12. TCP 세그먼트 헤더 형식](/assets/img/posts/2026-03-09-netintro-c2-32.png)
_그림 2-12. TCP 세그먼트 헤더 형식_

| 필드 | 기능 |
|---|---|
| 출발지·목적지 포트 | 통신하는 두 프로세스를 식별(각 16비트) |
| 순서 번호(Seq) | 보내는 바이트 스트림에서 이 세그먼트의 위치 |
| 확인 응답 번호(Ack) | 다음에 받기를 기대하는 바이트 번호(수신 확인) |
| 데이터 오프셋 | 헤더의 크기 |
| 제어 플래그 | 연결·전송을 제어하는 6개 비트 |
| 윈도우 크기 | 한 번에 받을 수 있는 데이터 양(흐름 제어) |
| 체크섬 | 오류 검출 |
| 긴급 포인터 | URG 플래그와 함께 긴급 데이터의 끝 위치 표시 |

_표 2-17. TCP 세그먼트의 주요 필드_

특히 중요한 부분이 **제어 플래그**입니다. 6개 비트가 켜지고 꺼짐에 따라 연결 설정·데이터 전송·연결 종료 등 TCP의 동작이 결정됩니다. 패킷을 분석하거나 공격 기법을 이해할 때 이 플래그를 읽을 줄 아는 것이 핵심입니다.

| 플래그 | 이름 | 의미 |
|---|---|---|
| URG | Urgent | 긴급 데이터가 있으며 긴급 포인터가 유효함 |
| ACK | Acknowledgment | 확인 응답 번호가 유효함(연결 중 대부분 켜짐) |
| PSH | Push | 버퍼에 쌓지 말고 즉시 응용 계층으로 전달 |
| RST | Reset | 연결을 강제로 끊거나 비정상 연결을 거부 |
| SYN | Synchronize | 연결을 설정하고 순서 번호를 동기화 |
| FIN | Finish | 더 보낼 데이터가 없으니 연결을 종료 |

_표 2-18. TCP 제어 플래그 6종_

### (2) 3-way 핸드셰이크

TCP는 데이터를 보내기 전에 먼저 연결을 맺습니다. 이 과정을 **3-way 핸드셰이크**라 하며, SYN과 ACK가 핵심 역할을 합니다. 순서 번호(Seq)로 대화의 기준점을 맞추는 과정으로 이해하면 쉽습니다. ① 클라이언트가 `Seq=100`인 SYN을 보내면(연결 요청), ② 서버는 ‘100번 잘 받았고 다음엔 101번을 기대한다’는 뜻으로 `Ack=101`을 담고 자기 기준점 `Seq=500`인 SYN·ACK를 보냅니다. ③ 클라이언트가 `Ack=501`로 응답하면 연결이 성립합니다. 이렇게 서로의 시작 번호를 교환해 두면, 이후 데이터가 순서대로 왔는지·빠진 것은 없는지 번호로 확인할 수 있습니다.

![그림 2-13. TCP 3-way 핸드셰이크](/assets/img/posts/2026-03-09-netintro-c2-33.png)
_그림 2-13. TCP 3-way 핸드셰이크_

> **보안 — SYN 플러딩 공격** 3-way 핸드셰이크의 허점을 노린 공격이 SYN 플러딩입니다. 공격자가 SYN만 대량으로 보내고 마지막 ACK를 보내지 않으면, 서버는 완성되지 않은 ‘반열림(half-open)’ 연결을 계속 큐에 쌓아 둡니다. 이 대기 큐가 가득 차면 정상 사용자의 접속까지 거부되는 서비스 거부(DoS) 상태가 됩니다. 대응책으로는 연결 정보를 미리 할당하지 않는 **SYN 쿠키**, 대기 시간 단축, 방화벽·IPS를 통한 비정상 SYN 차단 등이 있습니다.
{: .prompt-warning }

연결이 맺어지면 송신 측은 각 바이트에 순서 번호를 붙여 보내고, 수신 측은 확인 응답(ACK)으로 어디까지 잘 받았는지 알립니다. 윈도우 크기로 흐름을 조절하며, 즉시 처리가 필요한 데이터에는 PSH 플래그를 씁니다. 참고로 TCP는 수신자의 형편(흐름 제어)만이 아니라 네트워크 전체의 혼잡도 살핍니다. 전송량을 조금씩 늘려 가다가(슬로 스타트) 손실이 감지되면 급격히 줄이는 방식으로, 인터넷 전체가 무너지지 않도록 스스로 속도를 조절합니다.

### (3) 연결 종료

전송이 끝나면 연결을 종료합니다. TCP는 양방향 연결이므로 각 방향을 따로 닫아야 하며, 보통 FIN과 ACK를 주고받는 4-way 방식으로 종료합니다. 상황에 따라 응답이 합쳐지면 3-way로 끝나기도 하고, 한쪽 방향만 닫고 다른 방향은 계속 데이터를 보내는 하프클로즈(half-close)도 가능합니다. 연결이 비정상 상태에 빠지거나 더는 유효하지 않을 때는 RST 플래그로 강제로 끊으며, 존재하지 않는 포트로의 접속 시도에 대한 거부 응답에도 RST가 쓰입니다.

![그림 2-14. TCP 종료 방식 비교](/assets/img/posts/2026-03-09-netintro-c2-34.png)
_그림 2-14. TCP 종료 방식 비교_

| 종료 방식 | 설명 |
|---|---|
| 4-way 종료 | 양쪽이 각각 FIN·ACK를 주고받아 두 방향을 차례로 닫는 표준 방식 |
| 3-way 종료 | 한쪽의 FIN에 대한 ACK와 자신의 FIN이 하나로 합쳐질 때 |
| 하프클로즈 | 한 방향만 종료하고 반대 방향은 계속 데이터를 전송 |

_표 2-19. TCP 연결 종료 방식_

> **실습 2-5. 전송 계층 — 포트 번호와 TCP/UDP**  
> **실습 목표** 하나의 서버가 포트 번호로 여러 서비스를 구분함을 확인하고, 웹 접속이 TCP 3-way 핸드셰이크로 시작함을 관찰한다.

**실습 절차**

1. 구성에 Server를 하나 추가하고 IP를 위와 같이 설정한다.
2. 서버의 `[Services] > [HTTP]`가 On인지 확인한다.
3. PC0의 `[Desktop] > [Web Browser]`에서 `http://192.168.10.100`에 접속한다.
4. `[Simulation]` 모드에서 이 접속의 첫 패킷을 열어, TCP 플래그가 `SYN → SYN,ACK → ACK`로 이어지고 목적지 포트가 `80`임을 확인한다(ACL filter를 Port 80으로 설정하면 편하다).

## 4. 애플리케이션 계층

애플리케이션 계층(Application Layer)은 TCP/IP의 가장 위 계층으로, 사용자와 응용 프로그램에 직접 네트워크 서비스를 제공합니다. OSI 상위 세 계층(세션·표현·응용)의 역할을 하나로 통합한 것으로 볼 수 있으며, 이 계층의 프로토콜들은 전송 계층(TCP/UDP) 위에서 동작합니다.

| 프로토콜 | 포트 | 전송 계층 | 기능 |
|---|---|---|---|
| HTTP | 80(HTTPS 443) | TCP | 웹 페이지 요청·응답 |
| FTP | 20·21 | TCP | 파일 전송 |
| TELNET | 23 | TCP | 원격 접속(평문) |
| DNS | 53 | UDP/TCP | 도메인 이름 ↔ IP 변환 |

_표 2-20. 대표적인 애플리케이션 계층 프로토콜_

- **HTTP**(HyperText Transfer Protocol): 웹의 근간으로, 클라이언트가 요청하면 서버가 응답하는 구조이며 각 요청이 서로 독립적인 무상태(Stateless) 방식입니다. 암호화를 더한 것이 HTTPS(443).
- **FTP**(File Transfer Protocol): 제어용(21번)과 데이터용(20번) 두 연결을 나누어 쓰며, 능동(Active)·수동(Passive) 두 모드가 있습니다.
- **TELNET**: 원격지 장비에 접속해 명령을 실행하지만 모든 데이터를 평문으로 주고받아 도청에 취약하므로, 오늘날은 암호화된 SSH로 대체하는 것이 원칙입니다.
- **DNS**: 사람이 읽는 도메인 이름을 IP 주소로 바꿔 주는 계층적 분산 데이터베이스로, 짧은 질의는 UDP(53), 영역 전송처럼 큰 데이터는 TCP로 처리합니다.

### (1) 이메일 프로토콜 — SMTP·POP3·IMAP

이메일은 보내는 프로토콜과 받는 프로토콜이 다릅니다. 보낼 때는 SMTP를, 받을 때는 POP3나 IMAP 중 하나를 씁니다.

| 프로토콜 | 포트 | 역할 |
|---|---|---|
| SMTP | 25 | 메일 발송과 서버 간 전달 |
| POP3 | 110 | 메일을 단말로 내려받고 서버에서 지우는 수신 방식 |
| IMAP | 143 | 메일을 서버에 둔 채 여러 단말에서 동기화하는 수신 방식 |

_표 2-21. 이메일 프로토콜의 비교_

### (2) DHCP — IP 주소 자동 할당

**DHCP**(Dynamic Host Configuration Protocol)는 네트워크에 새로 연결된 단말에 IP 주소·서브넷 마스크·기본 게이트웨이·DNS 서버 주소를 자동으로 배부하는 프로토콜입니다. UDP 67·68번을 쓰며, 네 단계의 머리글자를 따 **DORA**라 부릅니다.

| 단계 | 동작 |
|---|---|
| ① Discover | 단말이 ‘DHCP 서버가 있나요?’를 네트워크 전체에 브로드캐스트 |
| ② Offer | 서버가 사용 가능한 IP 주소를 제안 |
| ③ Request | 단말이 제안받은 IP를 쓰겠다고 요청 |
| ④ Ack | 서버가 확정하고 임대 기간(Lease Time)을 부여 |

_표 2-22. DHCP의 4단계(DORA)_

> **보안 유의 — DHCP 스푸핑** DHCP는 요청과 응답의 진위를 검증하지 않습니다. 공격자가 가짜 DHCP 서버를 세워 자신을 기본 게이트웨이로 배부하면 트래픽을 가로챌 수 있고(DHCP 스푸핑), 가짜 요청을 대량으로 보내 주소 풀을 고갈시키는 공격(DHCP Starvation)도 있습니다. 스위치의 DHCP 스누핑 기능으로 방어합니다.
{: .prompt-warning }

### (3) 원격 접속 — Telnet과 SSH

원격지 장비에 접속해 관리할 때 쓰는 두 프로토콜은 보안에서 극명하게 갈립니다.

| 구분 | Telnet | SSH |
|---|---|---|
| 포트 | 23 | 22 |
| 암호화 | 없음(전 구간 평문) | 전 구간 암호화 |
| 인증 | ID/패스워드가 평문 노출 | 패스워드 또는 공개키 인증 |
| 사용 원칙 | 사용 금지(실습·폐쇄망 한정) | 원격 관리의 표준 |

_표 2-23. Telnet과 SSH의 비교_

> **실습 2-6. 응용 계층 — DHCP·DNS·웹 서비스**  
> **실습 목표** 서버에 DHCP·DNS·HTTP를 구성해, PC가 IP를 자동으로 받고 도메인 이름으로 웹에 접속하게 한다.
{: .prompt-tip }

**실습 절차**

1. Server0의 `[Services] > [DHCP]`를 켜고, 시작 주소 `192.168.10.101`·서브넷 마스크·기본 게이트웨이를 넣어 주소 풀을 만든다.
2. `[DNS]`를 켜고 `www.test.com → 192.168.10.100` A 레코드를 추가한다.
3. `[HTTP]`는 기본 페이지를 그대로 둔다.
4. 각 PC의 `[IP Configuration]`을 Static에서 DHCP로 바꾸고, 주소가 자동으로 할당되는지 확인한다.
5. PC의 웹 브라우저에서 `http://www.test.com`으로 접속한다(DNS가 이름을 IP로 바꿔 준다).

> **결과 확인** PC가 DHCP로 IP를 받고, 도메인 이름만으로 웹 페이지가 열리면 성공.  
> **계층 짚기** 사용자는 이름만 알면 되고 DHCP·DNS·HTTP가 그 뒤에서 협력한다 — 응용 계층(7계층)의 모습이다. 여기까지가 스위치 하나로 묶인 하나의 LAN이다. 3장에서는 서로 다른 네트워크를 잇는다.
{: .prompt-tip }
