물리·데이터링크 계층이 ‘같은 동네 안’ 전달을 맡았다면, **네트워크 계층**은 서로 다른 네트워크에 있는 출발지와 목적지 사이에서 패킷을 종단 간(End-to-End)으로 전달합니다. 이를 위해 소프트웨어로 부여하는 논리 주소(IP 주소)를 쓰고, 수많은 경로 중 가장 알맞은 길을 골라 패킷을 내보내는 라우팅을 수행합니다. 핵심은 IP이며, 이를 보조하는 ARP·ICMP가 함께 동작합니다.

## 1. 라우팅과 포워딩

라우팅(Routing)과 포워딩(Forwarding)은 자주 혼동되지만 다릅니다. 라우팅은 목적지까지 가는 최적 경로를 미리 계산해 라우팅 테이블을 만드는 ‘계획’ 단계이고, 포워딩은 실제로 패킷이 도착했을 때 그 테이블을 보고 알맞은 출력 포트로 내보내는 ‘실행’ 단계입니다. 라우팅은 출발 전에 지도를 보고 갈 길을 정하는 것, 포워딩은 실제 교차로에서 그 계획대로 방향을 트는 것에 비유할 수 있습니다. 라우팅은 제어 평면(Control Plane), 포워딩은 데이터 평면(Data Plane)에서 이루어집니다.

## 2. IP 주소 체계

### (1) 클래스 기반 주소 지정

IPv4 주소는 32비트로, 네트워크를 식별하는 네트워크부와 그 안의 호스트를 식별하는 호스트부로 나뉩니다. 인터넷 초기에는 이 경계를 A부터 E까지 다섯 개의 고정된 클래스로 나누어 정했는데, 이를 클래스 기반(Classful) 주소 지정이라 합니다.

이 방식은 인터넷 초창기인 1980년대 초, 한정된 IP 주소를 기관의 규모에 맞춰 효율적으로 분배하기 위해 도입되었습니다. 전 세계 국가·대기업을 위한 A 클래스, 중규모 대학·기업을 위한 B 클래스, 소규모 연구소를 위한 C 클래스로 등급을 나눈 것입니다. 여기에는 기술적 이유도 있었습니다. 1980년대의 라우터는 성능·메모리가 부족했고 라우팅 프로토콜이 서브넷 마스크 정보를 함께 전송하지 못했기 때문에, IP 주소의 맨 앞 비트 패턴(0, 10, 110…)만 보고도 별도 연산 없이 네트워크 길이(8·16·24비트)를 즉시 판별해 빠르게 포워딩하도록 주소 자체에 고정된 경계선을 심어 둔 것입니다.

| 클래스 | 첫 옥텟 범위 | 선행 비트 | 네트워크/호스트 비트 | 용도 |
|---|---|---|---|---|
| A | 0 ~ 127 | 0 | 8 / 24 | 대형 네트워크(호스트 약 1,600만) |
| B | 128 ~ 191 | 10 | 16 / 16 | 중형 네트워크(호스트 약 6.5만) |
| C | 192 ~ 223 | 110 | 24 / 8 | 소형 네트워크(호스트 254) |
| D | 224 ~ 239 | 1110 | — | 멀티캐스트용 |
| E | 240 ~ 255 | 1111 | — | 연구·예약용 |

_표 2-6. IPv4 주소 클래스 A~E 비교_

문제는 주소 낭비가 심하다는 점이었습니다. 호스트 300개가 필요한 기관이 C 클래스(254개)로는 부족해 B 클래스(6.5만 개)를 받으면 약 6.4만 개가 고스란히 낭비됩니다. 이런 비효율이 쌓이며 IPv4 주소 고갈이 빠르게 앞당겨졌고, 결국 1990년대 들어 서브넷 마스크를 활용하는 클래스 없는 주소 지정(CIDR)으로 전환되었습니다.

### (2) 서브네팅·CIDR·VLSM

고갈을 완화하기 위해 여러 기법이 등장했습니다. **서브네팅(Subnetting)** 은 하나의 큰 네트워크를 여러 작은 서브넷으로 쪼개는 것으로, 호스트부의 일부를 서브넷 식별에 쓰며 어디까지가 네트워크부인지 알려 주는 것이 서브넷 마스크입니다. 반대로 **슈퍼네팅(Supernetting)** 은 여러 작은 네트워크를 하나로 묶어 라우팅 정보를 줄이는 주소 집약 기법입니다. **CIDR**(Classless Inter-Domain Routing)은 A·B·C 클래스 구분을 없애고 `192.168.1.0/24`처럼 프리픽스 길이(/n)로 네트워크 크기를 자유롭게 지정하며, **VLSM**(Variable Length Subnet Mask)은 같은 네트워크 안에서도 서브넷마다 다른 크기의 마스크를 적용해 낭비를 최소화합니다.

서브넷 마스크를 이해하는 열쇠는 ‘1의 개수’입니다. 마스크에서 1인 부분이 네트워크를, 0인 부분이 호스트를 나타냅니다. `/24`는 앞 24비트가 1(255.255.255.0)이라 호스트가 8비트(256개), `/26`은 앞 26비트가 1(255.255.255.192)이라 호스트가 6비트(64개)입니다. 서브넷을 하나 더 잘게 쪼갤 때마다 네트워크 비트를 1씩 빌려 오고, 그만큼 호스트 수는 절반으로 줄어듭니다.

예로 `192.168.10.0/24`를 4개(=2²)의 서브넷으로 나누면 호스트부에서 2비트를 빌려 `/26`이 되고, 각 서브넷은 256÷4=64개 주소, 그중 네트워크·브로드캐스트 주소를 뺀 62대를 수용합니다.

|---|---|---|---|

_표 2-7. 192.168.10.0/24를 /26 서브넷 4개로 분할한 결과_

> **계산 팁 — 서브넷의 크기와 경계** 블록 크기 = 256 − 마스크의 마지막 옥텟 값으로 빠르게 구합니다. `/26`의 마스크는 255.255.255.192이므로 블록 크기는 256−192=64. 그래서 경계가 0·64·128·192로 64칸씩 떨어집니다. 필요한 호스트 수로 마스크를 정할 때는 ‘2^(호스트비트)−2 ≥ 필요 대수’를 만족하는 가장 작은 호스트 비트를 고릅니다. 예: 100대가 필요하면 2⁷−2=126 ≥ 100이므로 호스트 7비트(/25)가 답입니다.

| 특수 주소 | 범위/형태 | 용도 |
|---|---|---|
| 네트워크 주소 | 호스트 비트 모두 0 | 네트워크 자체를 식별(예: 192.168.1.0) |
| 브로드캐스트 주소 | 호스트 비트 모두 1 | 네트워크 내 전체 호스트에 전송(예: 192.168.1.255) |
| 루프백 주소 | 127.0.0.0/8 (127.0.0.1) | 자기 자신을 가리킴(통신 테스트) |
| 사설 주소 | 10/8, 172.16/12, 192.168/16 | 내부망 전용(인터넷에서 라우팅 안 됨) |
| 제한 브로드캐스트 | 255.255.255.255 | 자신이 속한 로컬 네트워크 전체 |

## 3. 인터넷 프로토콜(IP)

**IP**(Internet Protocol)는 네트워크 계층의 핵심으로, 패킷(데이터그램)을 출발지에서 목적지까지 전달합니다. 두 가지 중요한 특징은 **비연결형(Connectionless)** 과 **비신뢰성(Best-Effort)** 입니다. 즉 연결을 미리 맺지 않고 각 패킷을 독립적으로 보내며, 전달을 ‘최선을 다해’ 시도할 뿐 도착이나 순서를 보장하지 않습니다. 신뢰성은 상위의 전송 계층(TCP)이 책임집니다. 참고로 TCP·UDP·ICMP·IGMP가 모두 IP 데이터그램에 실려 전송됩니다.

![그림 2-8. IP 데이터그램의 위치](/assets/img/posts/2026-03-09-netintro-c2-21.png)
_그림 2-8. IP 데이터그램의 위치_

IP가 전송하는 패킷을 데이터그램(Datagram)이라 부릅니다. IPv4 데이터그램은 헤더와 데이터로 구성되며, 헤더는 기본 20바이트에 옵션을 더해 최대 60바이트까지 커질 수 있습니다.

![그림 2-9. IPv4 데이터그램 헤더 형식](/assets/img/posts/2026-03-09-netintro-c2-22.jpeg)
_그림 2-9. IPv4 데이터그램 헤더 형식_

| 필드 | 기능 |
|---|---|
| 버전(Version) | IP 버전(IPv4=4) |
| 헤더 길이(IHL) | 헤더의 크기(4바이트 단위) |
| 서비스 종류(ToS/DSCP) | 우선순위·서비스 품질(QoS[^qos]) 표시 |
| 전체 길이 | 헤더+데이터 전체 바이트 수 |
| 식별자(Identification) | 단편화된 조각들이 원래 어느 데이터그램인지 식별 |
| 플래그(DF/MF) | DF=단편화 금지, MF=뒤에 조각 더 있음 |
| 단편 오프셋 | 조각이 원본에서 차지하는 위치 |
| TTL(Time To Live) | 패킷 수명(라우터마다 1씩 감소, 0이면 폐기 → 무한 루프 방지) |
| 프로토콜(Protocol) | 상위 프로토콜 번호(ICMP=1, TCP=6, UDP=17) |
| 헤더 체크섬 | 헤더 오류 검출 |
| 출발지/목적지 IP | 송신자·수신자의 논리 주소(각 32비트) |

_표 2-9. IPv4 헤더의 주요 필드_

**TTL**은 잘못된 경로로 패킷이 영원히 도는 것을 막는 안전장치이며, traceroute가 경로를 추적하는 원리로도 쓰입니다. TTL은 8비트라 최댓값이 255인데, 실제로 전 세계 인터넷망을 거치는 라우터 수(홉 수)는 보통 20~30개를 넘지 않으므로 초기값이 64나 128만 되어도 목적지 도달에 문제가 없습니다. 흥미롭게도 보안 관점에서는, 공격자가 받은 패킷의 TTL 값을 역산해 상대방의 OS 환경(Windows인지 Linux인지)이나 거쳐 온 라우터 수를 추정하는 **핑거프린팅**에 활용되기도 합니다. 또한 프로토콜 필드 값(1·6·17)을 알아 두면 패킷 분석 시 IP 안에 무엇이 실렸는지 바로 알 수 있습니다.

### IPv6 — 등장 배경과 특징

IPv6가 등장한 가장 직접적인 배경은 IPv4 주소의 고갈입니다. IPv4는 32비트라 약 43억 개만 표현할 수 있었는데, 스마트폰·IoT·AI 서버가 폭증하며 주소가 바닥을 드러냈습니다. IPv6는 주소 공간을 128비트로 늘려 약 340간[^gan] 개라는 사실상 무한대에 가까운 주소를 제공합니다. 지구상의 모래알 하나하나에 고유 IP를 부여하고도 남는 수준입니다.

주소 확장 외에도 IPv6는 구조를 혁신했습니다. 가변 크기였던 IPv4 헤더와 달리 **헤더를 40바이트로 고정**해, 라우터가 헤더 끝을 일일이 계산할 필요가 없어 처리 속도가 크게 향상됐습니다. 가끔 쓰는 특수 기능은 고정 헤더 뒤에 필요할 때만 붙이는 확장 헤더로 분리했습니다. 데이터 전송 방식도 바뀌어, 모든 기기에 무조건 뿌리던 **브로드캐스트를 폐지**하고 특정 그룹에만 보내는 멀티캐스트를 강화했으며, 가장 가까운 하나에 전달하는 애니캐스트를 새로 도입했습니다. 나아가 별도의 DHCP 서버 없이도 단말이 스스로 고유 IP를 만들어 내는 **SLAAC**[^slaac](상태 비저장 주소 자동 구성)를 지원해, 랜선만 꽂으면 인터넷을 쓰는 ‘플러그 앤 플레이’ 환경을 제공합니다. 보안 측면에서는 패킷을 암호화·인증하는 **IPsec**을 설계 단계부터 기본 사양으로 포함했습니다. 다만 통로가 보호되어도 운영체제 취약점·악성코드 같은 상위 계층 위협은 여전하므로, 방화벽과 접근 통제는 필수입니다.

IPv6 주소는 128비트를 16비트씩 8개 그룹으로 나누고 각 그룹을 16진수로 표기해 콜론(:)으로 잇습니다(예: `2001:0db8:0000:0000:0000:ff00:0042:8329`). 각 그룹 앞쪽의 0은 생략하고, 연속된 0 그룹은 `::`로 한 번만 줄여 `2001:db8::ff00:42:8329`처럼 축약합니다.

![그림 2-10. IPv6 주소체계 축약의 예](/assets/img/posts/2026-03-09-netintro-c2-23.png)
_그림 2-10. IPv6 주소체계 축약의 예_

IPv4와 IPv6는 호환되지 않아, 두 체계가 공존하며 점진적으로 옮겨 가기 위해 **이중 스택**(한 장비가 둘 다 탑재), **터널링**(IPv6 패킷을 IPv4 안에 캡슐화), **헤더 변환**(NAT64 등)의 세 전략을 씁니다.

## 4. 논리 주소와 물리 주소의 변환 — ARP

같은 네트워크 안에서 실제로 프레임을 주고받으려면 물리 주소(MAC)가 필요합니다. 그런데 상위 계층은 논리 주소(IP)로 통신하므로, IP 주소를 MAC 주소로(또는 그 반대로) 바꾸는 과정이 반드시 필요합니다. 이 변환을 담당하는 것이 ARP·RARP·GARP입니다.

**ARP**(Address Resolution Protocol)는 IP 주소(논리)를 MAC 주소(물리)로 변환하며, 네트워크 계층과 데이터 링크 계층의 경계에서 동작합니다. 예를 들어 PC(`192.168.10.5`)가 게이트웨이(`192.168.10.1`)에 처음 통신하려 하면, ① PC는 ‘192.168.10.1을 쓰는 분, MAC 알려 주세요’를 네트워크 전체에 **브로드캐스트**합니다(ARP 요청). ② 해당 IP의 주인만 ‘제 MAC은 …입니다’라고 그 PC에게만 **유니캐스트**로 답합니다(ARP 응답). ③ PC는 이 IP-MAC 쌍을 ARP 캐시에 저장해 두고 재사용하므로 다음부터는 매번 묻지 않습니다.

> **보안 유의 — ARP 스푸핑** ARP는 응답의 진위를 검증하지 않습니다. 공격자가 위조된 ARP 응답을 보내 피해자의 캐시를 오염시키면, 트래픽이 공격자를 거쳐 가도록 만들 수 있습니다(중간자 공격, MITM[^mitm]). 이 ARP 스푸핑/포이즈닝은 보안 단원에서 자세히 다룹니다.
{: .prompt-warning }

이 밖에 **RARP**(Reverse ARP)는 반대로 MAC 주소를 IP 주소로 변환하며, 자기 IP를 모르는 초기 디스크리스 단말이 부팅 시 IP를 얻는 데 쓰였으나 오늘날 BOOTP·DHCP로 대체됐습니다. **GARP**(Gratuitous ARP)는 누가 묻지 않았는데도 자신의 IP에 대한 ARP를 스스로 브로드캐스트하는 것으로, IP 충돌 감지·캐시 갱신·이중화 장비의 장애 전환(Failover) 시 새 MAC 알림에 쓰입니다. 다만 공격자가 GARP로 거짓 매핑을 뿌려 캐시를 오염시키는 데 악용할 수도 있습니다.

## 5. ICMP

**ICMP**(Internet Control Message Protocol)는 IP의 오류를 보고하고 네트워크 상태를 진단하기 위한 보조 프로토콜입니다. IP는 비신뢰성이라 패킷이 사라져도 스스로 알리지 못하는데, ICMP가 그 빈틈을 메워 오류·상태 정보를 출발지에 통보합니다. 다만 ICMP 메시지 자체도 IP 데이터그램(프로토콜 번호 1)에 실려 전송되며 전달을 보장하지는 않습니다. 우리가 흔히 쓰는 `ping`은 질의 메시지인 에코 요청/응답을 이용한 것입니다.

| Type | 이름 | 의미 |
|---|---|---|
| 3 | Destination Unreachable | 목적지에 닿을 수 없음(코드로 세분) |
| 5 | Redirect | 더 나은 경로가 있으니 그 경로로 보내라는 안내 |
| 11 | Time Exceeded | TTL이 0이 되어 폐기(traceroute의 원리) |
| 12 | Parameter Problem | IP 헤더에 잘못된 값이 있음 |
| 4 | Source Quench(폐기됨) | 혼잡하니 천천히 보내라는 옛 메시지(현재는 TCP 혼잡 제어·ECN이 대신) |
| 8 / 0 | Echo Request / Reply | 질의 메시지. ping의 왕복 확인에 사용 |

_표 2-11. 주요 ICMP 메시지 Type_

> **보안 유의 — ICMP의 악용** ping·traceroute는 편리한 진단 도구지만, 공격자에게는 살아 있는 호스트와 경로를 파악하는 정찰 수단이 됩니다. 위조된 브로드캐스트 ping으로 트래픽을 증폭시키는 Smurf 공격, ICMP에 데이터를 숨겨 빼내는 ICMP 터널링 등이 있어 경계 구간에서는 ICMP를 선별적으로 제한하기도 합니다.
{: .prompt-warning }

## 6. NAT

**NAT**(Network Address Translation)는 내부에서 쓰는 사설 IP 주소를 외부로 나갈 때 공인 IP 주소로 바꿔 주는 기술입니다. IPv4 주소 고갈을 늦춘 일등 공신으로, 가정의 공유기부터 기업망까지 어디에나 있습니다. 내부 호스트가 밖으로 패킷을 보내면 NAT 장비가 출발지 주소를 자신의 공인 IP로 바꾸고 그 매핑을 변환 테이블에 기록하며, 응답이 돌아오면 테이블을 보고 원래의 내부 주소로 되돌려 전달합니다.

| 종류 | 설명 |
|---|---|
| 정적 NAT | 사설 IP 하나와 공인 IP 하나를 1:1 고정 매핑(내부 서버 공개용) |
| 동적 NAT | 공인 IP 풀에서 그때그때 하나를 골라 매핑 |
| PAT(NAPT) | 공인 IP 하나를 포트 번호로 구분해 여러 내부 호스트가 공유(가정용 공유기 방식) |

_표 2-12. NAT의 종류_

> **참고 — NAT와 보안** NAT는 내부 주소 구조를 외부에서 볼 수 없게 감추므로 부수적인 보안 효과가 있습니다. 그러나 NAT는 방화벽이 아니며, 접근 통제를 대신하지 못한다는 점에 유의해야 합니다.
{: .prompt-info }

## 7. 실습

> **실습 2-3. 네트워크 계층 — IP·ARP·ICMP 관찰**  
> **실습 목표** ping(ICMP)이 나가기 전에 ARP가 먼저 동작함을 시뮬레이션으로 확인하고, 서브넷이 통신에 미치는 영향을 실험한다.
{: .prompt-tip }

**실습 절차**

1. PC0을 클릭 → `[Desktop] > [Command Prompt]`에서 `arp -a`를 입력해 캐시가 비어 있는지(No ARP Entries) 확인한다.
2. 오른쪽 아래 `[Simulation]` 버튼을 눌러 시뮬레이션 모드로 바꾼다.
3. Command Prompt에서 `ping 192.168.10.2`를 입력한 뒤, Simulation Panel의 `[Capture / Forward]` 버튼으로 패킷을 한 단계씩 진행한다. 먼저 ARP(브로드캐스트)가 오가고, 그 뒤 ICMP가 전달되는 순서를 색깔 봉투로 확인한다.
4. 움직이는 봉투를 클릭하면 `[PDU Information]` 창이 열려 계층별 헤더(Ethernet·ARP·ICMP)를 볼 수 있다.
5. `[Realtime]`으로 돌아와 `arp -a`로 학습된 IP–MAC 매핑을 확인한다. (실험) PC1의 IP를 `192.168.20.2`로 바꾸면 다른 서브넷이 되어 ping이 실패함을 확인하고 원래대로 되돌린다.

> **결과 확인** Simulation 이벤트에 ARP 다음 ICMP가 보이고, 같은 서브넷에서 ping이 성공하면 완료.  
> **계층 짚기** IP(3계층)는 ‘누구에게’ 보낼지를 정하고, ARP는 그 IP에 대응하는 MAC(2계층)을 찾아 준다. 두 계층이 협력하는 지점이다.
{: .prompt-tip }

> **실습 2-4. 서브네팅으로 IP 주소를 계획하고 할당하기**  
> **실습 목표** 하나의 네트워크(192.168.1.0/24)를 부서별 서브넷으로 나누고, 계획한 IP를 PC에 할당해 같은/다른 서브넷의 통신 차이를 확인한다.  
> **주소 계획** `192.168.1.0/24` → `/26` 4개로 분할, 마스크 255.255.255.192.
{: .prompt-tip }

**실습 절차**

1. 먼저 `192.168.1.0/24`를 `/26` 서브넷 4개로 나누고 표로 적는다. 부서A = `192.168.1.0/26`(사용 .1~.62), 부서B = `192.168.1.64/26`(사용 .65~.126), 나머지 둘(.128/26, .192/26)은 예비로 둔다.
2. 스위치(2960) 2대와 PC 4대를 놓고, 부서A PC 2대는 SW1에, 부서B PC 2대는 SW2에 자동 케이블로 연결한다.
3. 각 PC → `[Desktop] > [IP Configuration]`에서 `[Static]`을 고르고 계획한 IP와 마스크(255.255.255.192)를 넣는다. 부서A: PC3 `192.168.1.1`, PC4 `192.168.1.2` / 부서B: PC5 `192.168.1.65`, PC6 `192.168.1.66`.
4. 같은 부서(같은 서브넷)끼리 통신을 확인한다: PC3에서 `ping 192.168.1.2` (성공해야 한다).
5. 다른 부서(다른 서브넷)로 통신해 본다: PC5에서 `ping 192.168.1.1`. 라우터가 없으므로 실패한다. 왜 실패하는지(서로 다른 서브넷이라 라우터/게이트웨이가 필요) 생각해 본다.

> **결과 확인** 같은 서브넷 통신은 성공, 다른 서브넷 통신은 실패하면 완료. 서브넷이 곧 ‘통신의 경계’임을 확인한 것이다.  
> **계층 짚기** 서브넷 마스크(3계층)가 ‘어디까지가 같은 네트워크인가’를 정한다. 두 서브넷을 잇고 싶다면 3장처럼 라우터가 필요하다.
{: .prompt-tip }
