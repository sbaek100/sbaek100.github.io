앞 편에서 무선 LAN의 암호화·인증을 다뤘습니다. 이 편에서는 유·무선이 만나는 지점의 구조적 취약점을 보여 주는 **WAP·WTLS·WAP2**, 기기 자체를 식별하는 **디바이스 인증**과 **RFID**, 그리고 iOS·안드로이드와 **BYOD** 같은 모바일 보안·통제 기술을 살펴봅니다.

## 1. WAP (Wireless Application Protocol)

**WAP**은 1990년대 후반 피처폰 시절, 좁은 대역폭·작은 화면·제한된 연산 능력을 가진 무선 단말에서도 인터넷을 이용하도록 설계된 통신 프로토콜 스택입니다. PC 웹의 HTML 대신 경량 마크업 언어를 쓰고, 유선 인터넷과 무선 단말 사이를 **WAP 게이트웨이**가 중계한다는 점이 큰 특징입니다. 지금은 스마트폰과 고속 무선망 보급으로 쓰이지 않지만, 유선 프로토콜을 무선에 맞게 변형하는 과정에서 생긴 구조적 보안 문제(WAP Gap)를 잘 보여 주는 사례라 자격시험에도 자주 등장합니다.

WAP 단말은 화면·기능을 최소화한 마이크로브라우저를 탑재합니다. 사용자가 페이지를 요청하면 ① 단말이 무선 구간으로 WAP 게이트웨이에 요청을 보내고, ② 게이트웨이가 이를 유선 규격(HTTP)으로 변환해 웹 서버에 전달하며, ③ 서버 응답(WML)을 게이트웨이가 다시 무선 규격으로 압축·변환해 단말로 돌려줍니다. 즉 WAP 게이트웨이는 무선과 유선 두 세계를 잇는 번역기이자 프록시이며, 이 중계 구조가 WAP Gap의 근본 원인입니다.

WAP은 HTML·JavaScript 대신 무선 최적화 응용 환경 **WAE**를 정의합니다. **WML**(Wireless Markup Language)은 좁은 화면에 맞춰 카드(Card)·데크(Deck) 단위로 화면을 구성하는 XML 기반 경량 마크업(HTML의 무선판), **WMLScript**는 간단한 클라이언트 로직을 위한 경량 스크립트(JavaScript의 무선판), **WTAI**는 통화·문자 등 전화 기능을 웹 콘텐츠에서 호출하는 인터페이스입니다.

| WAP 계층 | 프로토콜 | 대응 TCP/IP 계층 | 역할 |
|---|---|---|---|
| 응용 | WAE(WML·WMLScript) | 응용(HTTP+HTML) | 무선 콘텐츠 표현 |
| 세션 | WSP | 응용(HTTP) | 세션 관리·데이터 압축 |
| 트랜잭션 | WTP | 전송(TCP) | 요청·응답의 신뢰성 전달 |
| 보안 | WTLS | 전송(TLS/SSL) | 인증·암호화 |
| 전송 | WDP | 인터넷(IP)+전송(UDP) | 다양한 무선 베어러 위 데이터그램 전달 |

## 2. WTLS (무선 전송 계층 보안)

**WTLS**는 유선 인터넷의 TLS/SSL을 좁은 대역폭·높은 지연·불안정한 무선 회선에 맞게 경량화한 보안 프로토콜입니다. TLS처럼 기밀성(암호화)·무결성(변조 탐지)·인증을 제공하되, 낮은 연산 능력을 고려해 더 짧은 키와 가벼운 절차를 쓰고 TCP가 아닌 데이터그램(WDP) 위에서 동작합니다.

WTLS도 TLS처럼 여러 하위 프로토콜로 구성됩니다. **Handshake**(암호 알고리즘·세션 키 협상), **ChangeCipherSpec**(협상된 규격 적용 시작 통지), **Alert**(오류·종료 통지), **Record**(실제 데이터 암호화 전송). 또한 인증 수준에 따라 클래스 1(인증 없이 암호화만), 클래스 2(서버만 인증), 클래스 3(서버·클라이언트 상호 인증)으로 나뉩니다.

> **보안 유의 — WAP Gap 취약점** 유선망(TLS)과 무선망(WTLS)이 만나는 WAP 게이트웨이에서는 데이터가 일시적으로 복호화되어 평문으로 노출됩니다. 게이트웨이가 공격당하면 종단 간 암호화가 무너지는 구조적 결함입니다.
{: .prompt-warning }

## 3. WAP2 (End-to-End Security)

**WAP2**는 WAP Gap을 근본적으로 해결하기 위한 차세대 표준입니다. 게이트웨이에서 이루어지던 WTLS↔TLS 변환을 없애고, 단말이 TCP/IP와 표준 TLS를 직접 지원해 웹 서버와 **종단 간(End-to-End)** 암호화 통신을 합니다. 단말의 마이크로브라우저가 사실상 축소된 PC 브라우저처럼 HTTP/TLS를 그대로 쓰고, 필요할 때만 WAP 프로필로 콘텐츠를 압축하므로, 게이트웨이가 평문을 들여다보는 구간 자체가 사라집니다.

## 4. 디바이스 인증

**디바이스 인증**은 “이 사용자가 맞는가”를 확인하는 사용자 인증과 달리, “이 기기가 접속을 허용받은 정당한 단말인가”를 확인하는 절차입니다. 무선은 전파가 닿는 범위의 누구나 접속을 시도할 수 있어 사용자 인증만으로는 부족하고, 기기 자체를 식별·인증해야 합니다. BYOD·IoT 확산으로 접속 기기가 폭증하면서 비인가·복제 단말의 우회 접속을 막는 데 필수가 되었지만, 인증 정보가 기기 안에 저장되므로 분실·탈취 시 유출 위험과 등록·갱신·폐기의 운영 부담이 따릅니다.

- **ID/패스워드 인증**: 고유 계정·비밀번호로 인증. 구현이 쉽지만 기기 분해·복제 시 그대로 노출.
- **MAC 주소 인증**: 허용 MAC 목록에 있는 단말만 접속. 간편하지만 MAC이 평문 노출되어 스푸핑에 취약.
- **암호 프로토콜 인증**: 인증서·사전 공유 키로 암호학적으로 신원 증명(EAP-TLS, FIDO 등). 위조·복제에 강함.
- **Challenge/Response 인증**: 매번 값이 바뀌는 질의(Challenge)를 서버가 던지고, 단말이 자신만 아는 비밀 키로 연산해 응답. 비밀 키 자체는 전송되지 않고 매번 다른 값을 주고받아 **재전송(Replay) 공격에 강함**(802.1X/EAP·4-Way Handshake도 이 원리).

| 기술 | 장점 | 단점 |
|---|---|---|
| ID/패스워드 | 간단·저비용 | 기기 분해·복제 시 노출 |
| MAC 주소 | 간편한 필터링 | 평문 노출로 스푸핑에 취약 |
| 암호 프로토콜 | 위조·복제 어려움 | 인증서 발급·관리 부담 |
| Challenge/Response | 재전송 공격에 강함 | 매 세션 연산 부담 |

_표 6-11. 기기 인증 기술의 장단점 비교_

**FIDO**는 패스워드 없이 지문·홍채 같은 바이오 인증이나 하드웨어 보안 키로 인증하는 글로벌 표준입니다. 생체 정보가 기기 밖으로 나가지 않고 서버에는 공개키 기반 인증 결과만 전달됩니다. UAF(패스워드 완전 대체), U2F(2차 인증용 하드웨어 키 추가), FIDO2/WebAuthn(W3C 웹 표준 연계 패스워드리스)으로 나뉩니다.

## 5. RFID

**RFID**는 전파로 태그(Tag)에 저장된 정보를 리더(Reader)가 비접촉으로 읽는 식별 기술입니다. 태그는 리더의 전파에서 전력을 얻는 수동형(Passive)과 자체 전원으로 더 먼 거리까지 신호를 보내는 능동형(Active)으로 나뉩니다. 교통카드·출입 통제·물류에 널리 쓰이지만, 무선 구간이 암호화되지 않은 경우가 많아 도청·복제·위조에 취약합니다.

RFID 보안 대책은 태그가 암호 연산을 할 수 있는지에 따라 나뉩니다. **암호 기술 사용**: 해시 잠금(Hash-Lock, 올바른 키로 잠금 해제), 챌린지-응답(재사용 방지), 경량 암호(저전력용). **암호 기술 미사용**: 킬 태그(계산대 통과 후 영구 무력화), 패러데이 케이지(금속으로 전파 차단 — 전파 차단 여권 케이스), 블로커 태그(무의미한 응답 대량 발생), 거리 제한·사용자 인지.

## 6. 모바일 보안 — iOS와 안드로이드

스마트폰은 항상 켜진 채 네트워크에 연결되고 민감 정보가 한곳에 집중되며 분실·도난이 잦습니다. 반면 앱이 공식 마켓으로 배포되고 OS가 앱을 강하게 격리하는 등 구조적으로는 PC보다 앞선 보안 모델을 갖추기도 했습니다.

**iOS**는 하드웨어부터 OS·앱 마켓까지 애플이 전 과정을 통제하는 **폐쇄형** OS로, 그 통제력 자체를 보안 무기로 삼습니다. 부팅 각 단계가 애플 서명 코드인지 검증하는 **시큐어 부트 체인**, 생체 정보·키를 전용 보안 프로세서에 보관하는 **시큐어 엔클레이브**, 애플 서명 앱만 실행하는 **코드 서명·앱스토어 검수**, 파일마다 잠금 암호 연동 키를 부여하는 **데이터 보호**, 앱마다 독립 영역만 쓰게 하는 **앱 샌드박스**가 핵심입니다. 취약 경로로는 보호 장치를 스스로 무력화하는 **탈옥(Jailbreak)**, 커널·WebKit의 **제로데이**, 기업용 인증서 악용, 그리고 플랫폼 무관하게 통하는 피싱·사회공학이 있습니다.

**안드로이드**는 리눅스 커널 위에 만든 **개방형** OS로, 보안 핵심은 **격리와 권한**입니다. 앱마다 고유 UID를 부여해 격리하는 샌드박스(SELinux가 한 번 더 감쌈), 민감 자원을 실제 사용 시점에 묻는 **런타임 권한 모델**, 개발자 키 서명과 **Play Protect** 검사가 있습니다. 특히 모든 앱은 **매니페스트(AndroidManifest.xml)** 로 자신을 OS에 “선언”하는데, 여기 선언되지 않은 권한·컴포넌트는 실행 중 쓸 수 없어 앱 보안 점검에서 가장 먼저 열어 봅니다.

| 구성 요소 | 설명 |
|---|---|
| 패키지명 | 앱을 고유하게 식별하는 이름 |
| 컴포넌트 선언 | Activity·Service·Broadcast Receiver·Content Provider를 OS에 등록 |
| 권한 선언 | 카메라·위치 등 민감 권한을 `uses-permission`으로 명시(런타임 권한의 출발점) |
| API 레벨 지정 | minSdkVersion·targetSdkVersion으로 호환성·보안 정책 결정 |

_표 6-14. 매니페스트의 주요 구성 요소_

안드로이드 취약점으로는 공식 마켓 밖 설치를 허용하는 **사이드로딩**, 패치가 늦거나 끊기는 **단편화(Fragmentation)**, 샌드박스·서명 검증을 스스로 해제하는 **루팅(Rooting)**, 그리고 `exported` 컴포넌트 오설정·과도한 권한 요청 같은 **매니페스트 설정 오류**가 있습니다.

| 구분 | 안드로이드 | iOS |
|---|---|---|
| 생태계 | 개방형(오픈소스) | 폐쇄형(애플 단일 통제) |
| 앱 배포 | 플레이 스토어 + 사이드로딩 | 앱스토어 검수(단일 경로) |
| 격리 구조 | UID 샌드박스 + SELinux | 샌드박스 + 코드 서명 강제 |
| 하드웨어 보안 | 제조사별 상이(Knox 등) | Secure Enclave로 일원화 |
| 보안 패치 | 제조사·통신사 경유(단편화) | 애플이 직접 신속 배포 |
| 무력화 행위 | 루팅(Rooting) | 탈옥(Jailbreak) |

_표 6-15. 안드로이드와 iOS의 보안 구조 비교_

> **보안 유의 — 루팅과 탈옥** 루팅·탈옥은 OS의 격리와 서명 검증을 사용자가 스스로 해제하는 행위로, 악성코드에 관리자 권한을 내주는 것과 같습니다. 금융 앱과 기업 보안 솔루션(MDM 등)은 루팅·탈옥된 단말을 탐지해 실행·접속을 차단합니다.
{: .prompt-warning }

플랫폼 무관 공통 위협으로는 문자 메시지 악성 링크(스미싱), 정상 앱 위장 악성 앱, 공용 Wi-Fi 도청(OWE가 이를 막는 표준), 분실·도난이 있습니다. 이런 개인 기기가 회사 업무에 들어올 때의 대응이 BYOD 보안입니다.

## 7. BYOD 보안 기술

**BYOD(Bring Your Own Device)** 는 임직원이 개인 소유 단말을 업무에 쓰는 방식입니다. 비용·편의는 좋아지지만 회사가 통제하지 않는 기기가 내부 데이터에 접근하므로 전통적 보안 경계가 무너집니다(분실·도난, 개인·업무 데이터 혼재, 악성 앱·루팅 단말, 비인가 접속, 퇴사 시 데이터 회수 곤란).

> **참고 — BYOD·CYOD·COPE** 기기의 소유·선택 방식에 따라, 개인 기기를 쓰는 BYOD, 회사가 정한 목록에서 고르는 CYOD, 회사 소유 기기를 개인 용도로도 쓰는 COPE로 나뉩니다. 소유가 회사 쪽에 가까울수록 통제는 쉬워지고 자율성은 줄어듭니다.
{: .prompt-info }

- **MDM(Mobile Device Management)**: 단말 전체를 중앙에서 통제. 자산·구성 관리, 정책 강제(잠금·암호·카메라 차단), 분실 대응(원격 잠금·초기화), 루팅·탈옥 탐지. 통제력은 강하지만 개인 소유 기기에 적용하면 개인 영역까지 통제되어 프라이버시와 충돌합니다.
- **컨테이너화(Containerization)**: 단말 안에 암호화된 업무 전용 영역을 만들어 개인 영역과 격리(삼성 Knox, 안드로이드 Work Profile). 회사는 컨테이너 안쪽만 통제해 프라이버시 충돌이 크게 줄어듭니다.
- **모바일 가상화**: 하이퍼바이저 위에 업무용·개인용 OS를 통째로 분리 실행. 격리 수준 최고이나 성능·배터리 부담이 커 국방·금융 등 고보안 환경 중심.
- **MAM(Mobile Application Management)**: 기기 전체가 아니라 업무용 앱과 데이터만 관리. 앱 데이터 암호화·복사 제한, 퇴사 시 업무 앱만 지우는 선택적 와이프(Selective Wipe)가 가능해 BYOD와 궁합이 좋습니다.
- **NAC(Network Access Control)**: 네트워크 입구에서 통제. 인가 단말인지·보안 상태(백신·패치·루팅 여부)가 기준을 충족하는지 검사해 허용·차단·격리합니다. 802.1X를 기반으로 단말 무결성 검사를 더한 것으로, 비인가 BYOD를 걸러 내는 마지막 관문입니다.

| 기술 | 통제 대상 | 특징 |
|---|---|---|
| MDM | 기기 전체 | 통제력 최강, 프라이버시와 충돌 |
| 컨테이너화 | 단말 내 업무 영역 | 암호화 격리, 개인·업무 공존 |
| 모바일 가상화 | 운영체제 전체 | 격리 최고, 성능 부담 큼 |
| MAM | 업무 앱·데이터 | 선택적 와이프, BYOD 친화적 |
| NAC | 네트워크 접속 | 802.1X 기반, 비인가·비정상 단말 차단 |

_표 6-18. BYOD 보안 기술의 비교_

다섯 기술은 경쟁이 아니라 통제 지점이 다른 상호 보완 관계입니다. 실제 기업은 ‘NAC로 네트워크 입구를 지키고, 등록된 단말에는 MDM 또는 컨테이너·MAM을 적용’하는 식으로 조합합니다.

---

여기까지 유·무선이 만나는 WAP·WTLS·WAP2, 디바이스 인증과 RFID, 모바일 플랫폼과 BYOD 보안을 살펴보았습니다. 다음 편에서는 패킷 트레이서로 무선 네트워크를 직접 구성하고 암호화·접근제어를 적용하는 실습을 진행합니다.
