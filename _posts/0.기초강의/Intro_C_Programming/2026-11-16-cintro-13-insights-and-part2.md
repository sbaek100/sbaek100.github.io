# 제1부. 강의별 인사이트

각 강의에서 **문법이 아니라 관점**으로 남아야 할 것입니다.

## 1강 — 컴파일은 번역이 아니라 네 단계다

**인사이트: 오류 메시지는 어느 단계에서 났는지부터 읽는다.**

`gcc hello.c -o hello.exe` 한 줄 뒤에는 **전처리 → 컴파일 → 어셈블 → 링크** 네 단계가 숨어 있습니다. 이것을 알면 오류 메시지의 절반이 저절로 해석됩니다.

| 메시지 | 단계 | 뜻 |
|---|---|---|
| `No such file or directory` | 전처리 | 헤더를 못 찾았다 |
| `expected ';' before` | 컴파일 | 문법이 틀렸다 |
| `undefined reference to` | **링크** | 함수 본체가 없다 |

**초심자가 가장 오래 헤매는 이유는 "어디서 잘못됐는지 모르기 때문"입니다.** 단계를 아는 것만으로 이 헤맴이 사라집니다. 11강에서 `-I`·`-L`·`-l`을 배울 때 이 인사이트가 그대로 재활용되었습니다.

## 2강 — C는 작은 언어다

**인사이트: 언어는 작고, 힘은 라이브러리와 조합에서 나온다.**

K&R 1장을 한 바퀴 돌면서 확인한 것은, **C의 문법이 놀랄 만큼 적다**는 사실입니다. 예약어는 30여 개뿐이고, 문자열조차 언어의 일부가 아니라 **약속(끝에 `'\0'`)** 일 뿐입니다.

이것이 C의 성격입니다.

| C가 주는 것 | C가 주지 않는 것 |
|---|---|
| 자료형, 연산자, 제어 흐름, 함수, 포인터 | 문자열 자료형, 배열 크기 검사, 메모리 자동 회수 |

**주지 않는 것들은 모두 "직접 하라"는 뜻입니다.** 그래서 자유롭고, 그래서 위험합니다. 10강 전체가 이 한 문장의 결과였습니다.

## 3강 — 자료형은 "메모리를 어떻게 해석할까"의 약속이다

**인사이트: 같은 비트도 자료형에 따라 다른 값이 된다.**

`int`와 `unsigned int`는 **같은 32비트를 다르게 읽는** 두 가지 방식일 뿐입니다. 그래서 `-1 < 1u`가 거짓이 되고, `(short) 70000`이 4464가 됩니다.

이 관점은 나중에 결정적으로 쓰입니다.

| 어디서 | 어떻게 |
|---|---|
| 10강 | 부호 혼용 비교가 길이 검사를 무력화한다 |
| 8강 | `union` — 같은 자리를 여러 자료형으로 읽는다 |
| 2부 | 네트워크 바이트 순서, 이진 프로토콜 해석 |

**"변수에 값이 들어 있다"가 아니라 "메모리의 그 자리를 이 자료형으로 읽는다"** 로 생각을 바꾸는 것이 3강의 진짜 소득입니다.

## 4강 — 제어 흐름은 적을수록 좋다

**인사이트: 읽기 어려운 코드는 대개 흐름이 복잡한 코드다.**

`if`·`switch`·`while`은 어렵지 않습니다. 정작 어려운 것은 **언제 쓰지 않을지**입니다.

| 배운 것 | 남은 교훈 |
|---|---|
| 매달린 `else` | 중괄호를 아끼면 나중에 값을 치른다 |
| `switch` 폴스루 | 의도한 것과 실수한 것이 똑같이 생겼다 |
| `break`·`continue` | 편하지만, 남용하면 흐름을 못 쫓아간다 |
| `goto` | 배웠지만 거의 쓰지 않는다 |

12강 `cmd_add`에서 **잘못된 입력을 만나면 곧바로 `return`** 한 것이 이 인사이트의 적용입니다. 중첩을 깊게 만드는 대신 일찍 빠져나갔습니다.

## 5강 — 함수는 나누는 도구가 아니라 감추는 도구다

**인사이트: 중요한 것은 무엇을 공개하고 무엇을 감추는가이다.**

함수를 "긴 코드를 자르는 방법"으로만 이해하면 절반만 이해한 것입니다. 진짜 가치는 **경계를 만드는 것**에 있습니다.

| 도구 | 하는 일 |
|---|---|
| 함수 | 안쪽 구현을 감추고 이름만 노출한다 |
| `static` | 파일 밖에서 보이지 않게 한다 |
| 헤더 | **공개하기로 한 것만** 적는다 |

12강에서 `next_field`를 `static`으로 감추고 `book_from_csv`만 공개한 것이 그 예입니다. **감출 수 있어야 나중에 바꿀 수 있습니다.**

여기서 배운 **스택 프레임**이 7강 버퍼 오버플로의 토대가 되었다는 점도 기억해 두십시오. "함수가 끝나면 돌아갈 주소가 메모리에 적혀 있다"는 사실 하나가 보안의 절반입니다.

## 6강 — 배열은 포인터가 아니다. 다만 그렇게 행세할 뿐이다

**인사이트: 배열의 이름은 대부분의 자리에서 첫 원소의 주소로 바뀐다. 하지만 배열은 배열이다.**

이 구분을 못 하면 평생 헷갈립니다.

| 상황 | 배열 이름의 정체 |
|---|---|
| `sizeof a` | **배열 전체 크기**. 주소로 바뀌지 않는다 |
| `f(a)` | 첫 원소의 **주소**로 바뀐다 |
| `a[i]` | `*(a + i)`와 같다 |
| 함수 인자 `int a[]` | 사실은 `int *a`다 |

여기서 **"함수에 배열을 넘기면 크기 정보가 사라진다"** 는 결론이 나옵니다. 그래서 크기를 함께 넘겨야 하고, 그래서 10강의 안전 규칙이 존재합니다. **6강의 문법 하나가 C 보안 문제의 뿌리**입니다.

## 7강 — 포인터는 주소가 아니라 "접근 권한"이다

**인사이트: 포인터를 가진다는 것은 그 메모리를 마음대로 할 수 있다는 뜻이다.**

포인터를 "주소를 담는 변수"로만 보면 왜 위험한지 알 수 없습니다. **포인터는 그 자리를 읽고 쓸 권리**입니다. 그리고 C는 그 권리가 정당한지 **검사하지 않습니다.**

`bof_demo.c`에서 `authorized`가 `0x41414141`이 된 장면이 이 인사이트를 눈으로 보여 주었습니다. 아무도 그 변수를 건드리지 않았는데 값이 바뀌었습니다. **옆 배열에 대한 쓰기 권한이 그 변수에까지 미쳤기 때문**입니다.

함수 포인터도 같은 관점으로 보십시오. **"실행할 코드를 가리키는 권한"** 입니다. 그래서 `qsort`가 동작하고(12강), 그래서 함수 포인터를 덮어쓰는 공격이 존재합니다.

## 8강 — 자료 구조는 문제의 모양을 코드로 옮긴 것이다

**인사이트: 좋은 자료 구조를 고르면 코드가 저절로 단순해진다.**

구조체·배열·연결 리스트·트리·해시 표를 배웠지만, 핵심은 문법이 아니라 **선택**입니다.

| 문제의 성질 | 알맞은 구조 |
|---|---|
| 순서대로 훑고 정렬한다 | 배열 |
| 자주 넣고 뺀다, 순서만 중요 | 연결 리스트 |
| 크기 순서로 찾는다 | 트리 |
| 이름으로 즉시 찾는다 | 해시 표 |

12강에서 **연결 리스트를 배웠음에도 배열을 고른 것**이 이 인사이트의 실천입니다. 배운 것 중 최신·최고급을 쓰는 것이 아니라, **요구사항에 맞는 것**을 고르는 것이 설계입니다.

또 하나. 이 강의에서 처음으로 **메모리를 직접 빌렸습니다.** 그 순간부터 "누가 반납할 책임이 있는가"라는 질문이 모든 함수에 따라붙게 되었습니다. C 프로그래머의 사고방식은 여기서 갈립니다.

## 9강 — 입출력은 운영체제와의 대화다

**인사이트: `printf`는 화면에 쓰는 것이 아니라 스트림에 쓰는 것이다.**

버퍼가 있고, `stdout`과 `stderr`가 나뉘어 있고, 파일과 화면이 같은 방식으로 다루어진다는 사실 — 이것들은 모두 **운영체제가 만들어 준 추상화**입니다.

| 겉보기 | 실제 |
|---|---|
| `printf`가 화면에 쓴다 | 버퍼에 모았다가 나중에 커널에 넘긴다 |
| 파일과 화면이 다르다 | 둘 다 `FILE *`, 둘 다 스트림 |
| `fclose`는 마무리다 | **여기서 처음 오류가 드러날 수 있다** |

**이 인사이트가 2부의 출발점입니다.** 2부 2강에서 `FILE *`의 아래에 **파일 서술자(정수 하나)** 가 있고, 그 아래에 `read`·`write` 시스템 호출이 있음을 보게 됩니다. 9강은 그 추상화의 **가장 위층**을 배운 것이었습니다.

## 10강 — 안전은 기능이 아니라 습관이다

**인사이트: "이 값의 크기를 나는 알고 있는가?"**

10강의 모든 규칙은 이 한 질문의 변형입니다.

| 규칙 | 사실은 같은 질문 |
|---|---|
| `gets` 대신 `fgets` | 담을 곳의 크기를 아는가 |
| `sprintf` 대신 `snprintf` | 결과가 들어갈 크기를 아는가 |
| 곱셈 넘침 검사 | 계산 결과의 크기를 아는가 |
| `strtol` + 범위 검사 | 들어온 값의 범위를 아는가 |
| `printf("%s", s)` | 서식을 내가 정했는가 |

그리고 **신뢰 경계**. 바깥에서 온 값은 적대적일 수 있다고 가정하는 것. 이 태도는 2부 네트워크 프로그래밍에서 **선택이 아니라 필수**가 됩니다. 지구 반대편의 낯선 사람이 보낸 바이트를 다루게 되기 때문입니다.

## 11강 — 코드는 부품이 되어야 다시 쓰인다

**인사이트: 복사해 붙여 넣는 순간, 고쳐야 할 곳이 두 곳으로 늘어난다.**

라이브러리와 `Makefile`은 편의 도구가 아니라 **코드를 오래 살리는 방법**입니다.

| 없을 때 | 있을 때 |
|---|---|
| 소스를 복사한다 | 라이브러리를 링크한다 |
| 버그를 여러 곳에서 고친다 | 한 곳만 고친다 |
| 매번 전체를 다시 빌드한다 | 바뀐 것만 빌드한다 |
| 헤더를 고쳐도 반영 안 된다 | `-MMD -MP`가 알아서 처리한다 |

`-I`·`-L`·`-l`을 이해했다는 것은 곧 **남이 만든 것을 쓸 수 있게 되었다**는 뜻입니다. 2부에서는 이 능력으로 `pthread`·소켓 라이브러리를 붙이게 됩니다.

## 12강 — 설계는 자료에서 시작한다

**인사이트: 무엇을 다루는지 정하면 무엇을 할지는 따라온다.**

기능 목록부터 만들면 코드가 엉킵니다. **자료 → 구조 → 함수 → 화면** 순서로 가면 각 부분이 제자리를 찾습니다.

그리고 하나 더. **좋은 `main`은 짧습니다.** 줄거리만 보이고 세부는 각 함수에 있습니다. `main`이 길어지고 있다면 그것은 설계가 무너지고 있다는 신호입니다.

마지막으로 **시험 계획**. 만들고 나서 시험하는 것이 아니라 **만들기 전에 무엇을 확인할지 정해 두는 것**입니다. 정상·경계·오류·자원 네 갈래로 나누어 보는 습관은 앞으로 모든 프로젝트에서 쓰입니다.

# 제2부. 전체를 관통하는 여덟 줄기

강의를 가로질러 반복해서 나타난 것들입니다.

## 줄기 1. C는 검사하지 않는다

이 한 문장에서 다음이 모두 파생됩니다.

| 파생된 것 | 강의 |
|---|---|
| 배열 밖 접근이 조용히 통과한다 | 2 · 6 · 7 |
| 크기를 함께 넘겨야 한다 | 6 |
| 버퍼 오버플로가 존재한다 | 7 · 10 |
| 메모리를 직접 반납해야 한다 | 8 |
| 안전 규칙이 필요하다 | 10 |

**C를 안다는 것은 "C가 해 주지 않는 일이 무엇인지" 아는 것**입니다.

## 줄기 2. 크기를 아는 자가 안전하다

| 상황 | 크기를 아는 방법 |
|---|---|
| 배열 | `sizeof a / sizeof a[0]` |
| 함수 인자로 온 배열 | **알 수 없다.** 함께 받아야 한다 |
| 문자열 | `'\0'`까지 세거나 `strlen` |
| 빌린 메모리 | 내가 요청한 크기를 기억해야 한다 |
| 파일에서 읽은 줄 | `fgets`에 크기를 넘겼으므로 안다 |

**크기를 모르는 채로 쓰는 순간이 사고가 나는 순간**입니다.

## 줄기 3. 미정의 동작은 "지금 잘 돌아감"이 가장 위험하다

| 흔한 오해 | 실제 |
|---|---|
| "실행해 보니 되던데요" | 지금 그 컴파일러, 그 최적화 옵션에서만 |
| "값이 이상하지만 프로그램은 살아 있다" | 이미 메모리를 침범했을 수 있다 |
| "경고는 무시해도 된다" | 경고는 미래의 오류다 |

그래서 **경고 0개**를 규칙으로 삼았고, 위생 검사기를 소개했습니다.

## 줄기 4. 이름·주소·값을 구분하라

C를 배우는 사람의 혼란은 대부분 이 셋이 섞여서 생깁니다.

| 표현 | 무엇인가 |
|---|---|
| `x` | 값 |
| `&x` | 주소 |
| `p` | 주소를 담은 값 |
| `*p` | 그 주소에 있는 값 |
| `a` (배열) | 첫 원소의 주소로 바뀌는 이름 |
| `f` (함수) | 코드의 주소로 바뀌는 이름 |

`scanf("%d", &x)`의 `&`가 왜 필요한지, `strcpy(d, s)`에는 왜 `&`가 없는지 — 같은 원리입니다.

## 줄기 5. 실패는 예외가 아니라 정상적인 결과다

| 함수 | 실패를 알리는 방법 |
|---|---|
| `malloc`·`realloc`·`fopen` | `NULL` |
| `fgets` | `NULL` |
| `scanf` | 읽은 개수 |
| `strtol` | `end` 포인터와 `errno` |
| 우리가 만든 함수 | 0 / 1 |

**실패를 검사하지 않는 코드는 완성된 코드가 아닙니다.** 그리고 실패했을 때 **이미 잡은 자원을 정리하는 것**까지가 처리입니다(10강 6.3절, 12강 5.2절).

## 줄기 6. 계층을 만들어라

좋은 C 코드는 **얇은 층이 여러 개** 쌓인 모양입니다.

| 층 | 예 (12강) |
|---|---|
| 아래 | `read_line` — 안전하게 읽기만 |
| 가운데 | `parse_int` — 변환과 검증만 |
| 위 | `ask_int` — 둘을 묶어 대화 |
| 맨 위 | `cmd_add` — 업무 흐름 |

각 층은 **아래층만 알고 위층은 모릅니다.** 그래서 따로 시험할 수 있고 따로 재사용할 수 있습니다.

## 줄기 7. 컴퓨터는 메모리다

C를 배우는 진짜 이유입니다. 강의를 거치며 메모리의 지도가 완성되었습니다.

| 영역 | 무엇이 있는가 | 배운 곳 |
|---|---|---|
| 코드 | 실행할 명령, 함수 | 7강 함수 포인터 |
| 전역/정적 | 전역 변수, `static` 변수, 문자열 상수 | 5강 |
| 힙 | `malloc`으로 빌린 것 | 8강 |
| 스택 | 지역 변수, 인자, **돌아갈 주소** | 5강 · 7강 |

**2부에서는 이 지도가 그대로 확장됩니다.** 가상 메모리, 프로세스마다 따로 있는 주소 공간, 커널 공간과 사용자 공간의 경계 — 모두 이 그림 위에 그려집니다.

## 줄기 8. 도구가 사람보다 정확하다

| 도구 | 잡아 주는 것 |
|---|---|
| `-Wall -Wextra` | 흔한 실수 대부분 |
| `-Wconversion`·`-Wsign-compare` | 자료형 함정 |
| 위생 검사기 | 실행 중 메모리 사고 |
| 정적 분석기 | 실행 없이 찾는 결함 |
| `make` | 빌드 누락과 순서 |
| 디버거 | 실제로 무슨 일이 일어나는지 |

**사람은 잊지만 도구는 잊지 않습니다.** 도구를 켜 두는 것이 실력의 일부입니다.

# 제4부. 시스템 프로그래밍으로 가는 다리

## 4.1 지금 여러분이 서 있는 자리

1부에서 만든 프로그램은 모두 **혼자 돌아가는 프로그램**이었습니다.

| 1부의 프로그램 | 상대한 것 |
|---|---|
| 계산기, 정렬 | 자기 메모리뿐 |
| 도서 관리 | 화면과 파일 하나 |

그런데 실제 세상의 프로그램은 그렇지 않습니다.

| 실제 프로그램 | 상대하는 것 |
|---|---|
| 웹 서버 | 수천 개의 동시 접속 |
| 셸 | 다른 프로그램을 만들고 기다린다 |
| 데이터베이스 | 디스크, 잠금, 여러 사용자 |
| 백신 | 파일 시스템 전체, 다른 프로세스 |

**그 차이를 메우는 것이 시스템 프로그래밍입니다.**

## 4.2 이미 여러분은 시스템 호출을 쓰고 있었다

`printf` 한 줄을 다시 봅시다.

| 층 | 무엇이 일어나는가 | 누가 |
|---|---|---|
| 1 | `printf("%d\n", x)` — 서식을 문자열로 만든다 | 표준 라이브러리 |
| 2 | 버퍼에 쌓는다 | 표준 라이브러리 |
| 3 | 버퍼가 차거나 개행을 만나면 `write(1, buf, n)` | **시스템 호출** |
| 4 | 사용자 모드 → 커널 모드 전환 | CPU |
| 5 | 커널이 터미널 드라이버에 넘긴다 | **커널** |
| 6 | 화면에 글자가 나타난다 | 하드웨어 |

**1부는 1~2층을 배운 것입니다. 2부는 3층부터 내려갑니다.**

## 4.3 1부의 개념이 2부에서 이렇게 바뀝니다

| 1부에서 배운 것 | 2부에서 만나는 형태 |
|---|---|
| `FILE *fp` | **파일 서술자** `int fd` — 정수 하나 |
| `fopen`·`fread`·`fclose` | `open`·`read`·`close` 시스템 호출 |
| `stdin`·`stdout`·`stderr` | 서술자 **0·1·2** |
| 함수 호출과 스택 프레임 | 프로세스 생성(`fork`)과 주소 공간 |
| 전역 변수 | 스레드 사이의 **경쟁 상태** |
| `malloc`의 힙 | `brk`·`mmap`, 가상 메모리 |
| 구조체 | `struct stat`, `struct sockaddr` 등 커널의 자료형 |
| 반환값으로 실패를 알림 | `-1`과 **`errno`** |
| 신뢰 경계(10강) | 네트워크에서 오는 바이트 |
| 라이브러리 링크(11강) | `-lssl -lcrypto` 등 시스템 라이브러리 |
| 12강의 설계 방법 | 그대로, 더 큰 규모로 |

**새로 배우는 것은 문법이 아니라 인터페이스입니다.** C 문법은 이미 다 배웠습니다.

## 4.4 실습 환경이 리눅스로 바뀝니다

| 이유 | 설명 |
|---|---|
| **시스템 호출이 표준화되어 있다** | POSIX. 윈도우는 다른 API를 쓴다 |
| **C와 UNIX는 함께 태어났다** | K&R 8장이 UNIX 인터페이스인 것도 그래서다 |
| **도구가 갖추어져 있다** | `strace`, `gdb`, `valgrind`, 위생 검사기 |
| **서버의 사실상 표준** | 실무에서 만나는 환경 |

> 걱정하지 않아도 됩니다. **`gcc`·`make`·헤더·라이브러리·포인터·구조체 — 배운 것이 전부 그대로 통합니다.** 오히려 원래 있던 자리로 돌아가는 것에 가깝습니다. 리눅스 기본 사용법은 별도 과정 「리눅스 기초」에서 다루며, 2부 1강에서도 필요한 만큼 정리합니다.
{: .prompt-info }

# 제5부. 2부 「중급 C 프로그래밍」 로드맵

**주제: 프로그램이 운영체제·다른 프로세스·네트워크와 대화한다.**

## 5.1 전체 구성

2부의 기준 교재는 **APUE**(Stevens · Rago, *Advanced Programming in the UNIX Environment*, 3판, 2013)입니다. 1부가 K&R의 장 구성을 따랐던 것과 같은 방식입니다.

| 부 | 강 | 주제 | 핵심 | APUE | 실습 |
|---|---|---|---|---|---|
| **1부** | 1강 | 실습 환경 구축과 시스템 호출 | 사용자·커널 공간, `man` 2절, `strace`, `errno` | 1·2장 | **VM 2대** |
| 기초 | 2강 | 저수준 파일 입출력 | `open`·`read`·`write`·`lseek`, `FILE *`와의 관계 | 3·5장 | VM 1대 |
| | 3강 | 파일 시스템과 메타데이터 | `stat`, 권한, 디렉터리 순회, 링크, 원자적 갱신 | 4장 | VM 1대 |
| **2부** | 4강 | 프로세스 | `fork`·`exec`·`wait`, 좀비와 고아, 프로세스 트리 | 8·9장 | VM 1대 |
| 프로세스 | 5강 | 시그널 | `sigaction`, 안전한 처리기, `SIGCHLD`, `EINTR` | 10장 | VM 1대 |
| | 6강 | 파이프와 IPC | `pipe`·`dup2`, **작은 셸 만들기**, FIFO, `mmap` | 15·17장 | VM 1대 |
| **3부** | 7강 | 스레드 | `pthread`, 공유 자료, 경쟁 상태, 뮤텍스·조건 변수 | 11장 | VM 1대 |
| 동시성 | 8강 | 동시성의 함정 | 교착 상태, 재진입, 스레드 안전성, 성능 측정 | 12장 | VM 1대 |
| **4부** | 9강 | 소켓 프로그래밍 | TCP 서버·클라이언트, 바이트 순서, **평문이 그대로 보인다** | 16장 | **VM 2대** |
| 네트워크 | 10강 | 다중 접속 서버 | `select`·`poll`·`epoll`, 논블로킹 | 14·16장 | **VM 2대** |
| | 11강 | UDP와 프로토콜 설계 | 메시지 경계, 길이 앞머리, 입력 검증 | 16장 | **VM 2대** |
| **5부** | 12강 | 대칭키 암호 | AES-GCM, 키·IV·인증 태그, **직접 만드는 암호 채널** | **—** | **VM 2대** |
| **암호화** | 13강 | 공개키·키 교환·서명 | X25519 키 교환, Ed25519 서명, **중간자 공격** | **—** | **VM 2대** |
| **통신** | 14강 | TLS 핸드셰이크 완전 분해 | 인증서·CA, 자체 CA 구축, **핸드셰이크 메시지로 확인** | **—** | **VM 2대** |
| | 15강 | OpenSSL로 TLS 구현 | `SSL_CTX`, **검증을 켜는 세 줄**, 흔한 실수 | **—** | **VM 2대** |
| **6부** | 16강 | 커널의 시각 | 가상 메모리, 스케줄링, `/proc`, 관찰 도구 | 7장 | VM 1대 |
| 마무리 | 17강 | 종합 과제 | **TLS 동시 접속 서버** — 전체를 결합 | — | **VM 2대** |

**5부의 APUE 장이 비어 있는 것이 중요합니다.** APUE도, 더 두꺼운 TLPI도 **암호화는 다루지 않습니다.** 운영체제 인터페이스와 암호학은 별개의 영역이기 때문입니다. 그 부분은 *Serious Cryptography*·*Bulletproof TLS and PKI*, 그리고 무료 자료인 [The Illustrated TLS 1.3 Connection](https://tls13.xargs.org/)과 표준 원문 [**RFC 9846**](https://www.rfc-editor.org/rfc/rfc9846)으로 채웁니다.

> TLS 1.3은 2018년 [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446)으로 처음 나왔고, 지금은 **RFC 9846**이 이를 대체한 현행 표준입니다. 인터넷의 설명 글 대부분은 아직 8446을 인용하므로 둘 다 알아 두어야 합니다.
{: .prompt-info }

**5부 네 강의가 2부의 중심**입니다. 앞의 강의들은 모두 그곳에 도달하기 위한 준비입니다. 9강에서 두 컴퓨터 사이에 오가는 문자열을 **직접 가로채어 읽어 본 뒤**, 12강부터 그것을 막는 방법을 하나씩 만들어 갑니다.

## 5.2 2부에서 얻게 될 것

| 능력 | 구체적으로 |
|---|---|
| 운영체제와 직접 대화 | 시스템 호출을 읽고 쓰고, `man` 2절을 스스로 찾는다 |
| 프로그램을 만드는 프로그램 | 셸이 어떻게 동작하는지 만들어 보며 이해한다 |
| 동시성 | 여러 흐름이 같은 자료를 다룰 때 무엇이 깨지는지 안다 |
| 네트워크 | 소켓으로 통신하는 서버와 클라이언트를 만든다 |
| 커널의 관점 | 프로그램이 실행된다는 것이 실제로 무엇인지 안다 |
| 보안 | 원격 입력을 다루는 코드에 방어를 넣는다 |
| **암호화 통신** | **TLS 안에서 무슨 일이 일어나는지 설명하고, 직접 구현한다** |

## 5.3 2부를 시작하기 전에 갖추어야 할 것

| 항목 | 확인 방법 |
|---|---|
| 포인터를 그림으로 설명할 수 있다 | 6강·7강 실습문제를 다시 풀어 본다 |
| 구조체와 동적 메모리를 쓸 수 있다 | 8강 연결 리스트를 백지에서 |
| 파일 입출력을 할 수 있다 | 9강 파일 복사 프로그램 |
| 안전 규칙을 적용한다 | 10강 점검 목록 |
| 여러 파일로 나누어 빌드한다 | 11강 `libcstudy` |
| **12강 과제를 완성했다** | 가장 확실한 기준 |

> **12강 종합 과제를 스스로 완성했다면 2부를 시작할 준비가 된 것입니다.** 아직이라면 그것부터 마치십시오. 2부는 1부의 능력을 전제로 진행됩니다.
{: .prompt-warning }

# 제6부. 자가 점검과 다음 걸음

## 6.1 스스로 확인해 보십시오

각 항목을 **누군가에게 설명할 수 있는지**로 판단하십시오. 코드를 짤 수 있는 것과 설명할 수 있는 것은 다릅니다.

**기초**

- [ ] `int`와 `unsigned int`의 차이를 비트 수준에서 설명할 수 있다
- [ ] `for`와 `while`이 왜 같은 것인지 설명할 수 있다
- [ ] 지역 변수와 전역 변수가 메모리 어디에 있는지 말할 수 있다

**포인터**

- [ ] `int *p`와 `int p[]`가 함수 인자에서 왜 같은지 설명할 수 있다
- [ ] `sizeof(배열)`과 `sizeof(포인터)`가 왜 다른지 설명할 수 있다
- [ ] `char *s = "abc"`를 왜 수정하면 안 되는지 안다
- [ ] 함수 포인터로 `qsort`를 쓸 수 있다

**메모리**

- [ ] `malloc`한 것을 언제 누가 `free` 할지 설계 단계에서 정한다
- [ ] `realloc`의 결과를 원래 포인터에 바로 넣으면 안 되는 이유를 안다
- [ ] 스택과 힙의 차이를 설명할 수 있다

**안전**

- [ ] 버퍼 오버플로가 어떻게 흐름을 빼앗는지 설명할 수 있다
- [ ] `strncpy`가 왜 안전하지 않은지 설명할 수 있다
- [ ] 정수 넘침이 어떻게 버퍼 오버플로가 되는지 설명할 수 있다

**구성**

- [ ] 헤더에 무엇을 넣고 무엇을 빼는지 판단할 수 있다
- [ ] `-I`·`-L`·`-l`을 구분해 쓸 수 있다
- [ ] `Makefile`을 읽고 고칠 수 있다
- [ ] 프로그램을 파일로 나눌 때 기준을 말할 수 있다

## 6.2 실력을 굳히는 방법

**① 읽으십시오.** 남의 C 코드를 읽는 것이 가장 빠릅니다. 작은 오픈 소스 프로젝트의 소스를 내려받아 `Makefile`부터 읽어 보십시오. 11강을 마친 지금이라면 읽힙니다.

**② 다시 만드십시오.** 이미 있는 것을 직접 만들어 보는 것이 최고의 연습입니다.

| 난이도 | 만들어 볼 것 |
|---|---|
| 쉬움 | `wc`, `head`, `cat` |
| 보통 | `grep`(간단한 형태), CSV 정렬 도구 |
| 어려움 | 간단한 인터프리터, 텍스트 편집기 |

**③ 자신의 옛 코드를 다시 보십시오.** 2강에서 쓴 코드를 지금 보면 고칠 곳이 보일 것입니다. **그 차이가 여러분이 성장한 양**입니다.
