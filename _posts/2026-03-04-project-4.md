# 4부. 보안 요구사항 도출

---

## 1. 요구사항(Requirements)이란?

### 정의

> **요구사항(Requirements)** 이란, 시스템이 **무엇을 해야 하는지(What)** 를 명확하게 정의한 명세(Specification)임. '어떻게(How)'가 아니라 '무엇을(What)'에 집중함.

```
[요구사항의 역할]

비즈니스 목표
(Business Goal)
      ↓
요구사항 도출
(Requirements Elicitation)
      ↓
시스템 설계
(System Design)
      ↓
구현(Implementation)
      ↓
테스트(Testing)  ← 요구사항을 기준으로 검증
```

### 요구사항의 중요성

나쁜 요구사항이 프로젝트 실패의 가장 큰 원인임.

|원인|비율 (Standish CHAOS Report 기준)|
|---|---|
|불완전한 요구사항|13%|
|사용자 참여 부족|12%|
|자원 부족|11%|
|비현실적 기대|6%|

## 2. 기능적 vs 비기능적 보안 요구사항

### 기능적 요구사항(Functional Requirements)

> 시스템이 **수행해야 하는 기능**을 명세함.

**형식**: "시스템은 [주체]가 [조건]일 때 [행동]을 수행해야 한다."

|예시|설명|
|---|---|
|"시스템은 사용자가 로그인 5회 실패 시 계정을 잠가야 한다"|브루트포스 방어 기능|
|"시스템은 사용자 데이터를 저장할 때 AES-256으로 암호화해야 한다"|암호화 기능|
|"시스템은 모든 관리자 작업에 대해 감사 로그를 생성해야 한다"|로깅 기능|
|"시스템은 비밀번호를 bcrypt로 해싱하여 저장해야 한다"|비밀번호 보호 기능|

### 비기능적 요구사항(Non-Functional Requirements)

> 시스템이 **얼마나 잘** 수행하는지, 시스템의 **품질 속성**을 명세함.

**형식**: "시스템은 [품질 속성]이 [측정 가능한 기준]을 만족해야 한다."

|예시|품질 속성|
|---|---|
|"시스템은 악성 요청을 100ms 이내에 차단해야 한다"|성능(Performance)|
|"시스템은 연간 99.9% 이상의 가용성을 유지해야 한다"|가용성(Availability)|
|"시스템은 취약점 발견 시 48시간 이내에 패치해야 한다"|유지보수성(Maintainability)|
|"시스템은 OWASP Top 10 취약점을 포함하지 않아야 한다"|보안성(Security)|

### 기능적 vs 비기능적 보안 요구사항 비교

|구분|기능적 보안 요구사항|비기능적 보안 요구사항|
|---|---|---|
|**초점**|무엇을 하는가 (기능)|얼마나 잘 하는가 (품질)|
|**측정**|기능 동작 여부 (O/X)|수치로 측정 (수치, %)|
|**예시**|"2FA 기능 구현"|"로그인 응답 시간 500ms 이내"|
|**테스트**|기능 테스트|성능 테스트, 보안 테스트|

## 3. 위협에서 요구사항 도출하기 (역방향 설계)

### 역방향 설계란?

> **역방향 설계(Backward Design)** 란, 3부에서 도출한 **위협(Threat)을 기반으로**, 그 위협을 제거·완화하기 위한 **보안 요구사항을 역방향으로 도출**하는 방법임.

```
[순방향 vs 역방향 설계]

순방향 (일반적):
기능 구현 → 테스트 → 보안 검토  (보안이 마지막)

역방향 (보안 우선):
위협 식별 → 보안 요구사항 → 기능 설계 → 구현  (보안이 먼저)
```

### STRIDE 위협 → 보안 요구사항 도출 매핑

|STRIDE 위협|대응 보안 메커니즘|도출되는 요구사항 예시|
|---|---|---|
|**스푸핑(Spoofing)**|인증(Authentication)|"시스템은 모든 API 요청에 JWT 토큰 인증을 요구해야 한다"|
|**변조(Tampering)**|무결성 검증|"시스템은 파일 업로드 시 SHA-256 해시를 저장하고 검증해야 한다"|
|**부인(Repudiation)**|감사 로그|"시스템은 모든 사용자 행위를 타임스탬프와 함께 불변 로그에 저장해야 한다"|
|**정보 유출(Info Disclosure)**|암호화·접근 제어|"시스템은 민감 데이터를 AES-256으로 암호화하여 저장해야 한다"|
|**서비스 거부(DoS)**|가용성 보호|"시스템은 동일 IP에서 분당 100회 이상 요청 시 차단해야 한다"|
|**권한 상승(EoP)**|권한 부여(Authorization)|"시스템은 RBAC을 적용하여 역할별 접근 가능한 기능을 제한해야 한다"|

### 실습 예시 — 병원 환자 관리 시스템

**3부에서 식별된 위협** → **4부에서 도출된 요구사항**

```
[위협] 외부 공격자가 환자 DB에 무단 접근 (STRIDE: I - 정보유출)
  ↓
[요구사항 1] 환자 개인정보는 AES-256으로 암호화하여 저장해야 한다 (기능적)
[요구사항 2] 의사/간호사/행정직 역할별 데이터 접근 범위를 분리해야 한다 (기능적)
[요구사항 3] DB 접근 시도 실패는 3회 초과 시 IP를 30분간 차단해야 한다 (기능적)

[위협] 의료진이 처방 데이터를 변조 (STRIDE: T - 변조)
  ↓
[요구사항 4] 모든 처방 데이터 수정 이력은 변경 불가능한 로그로 저장해야 한다 (기능적)
[요구사항 5] 처방 데이터 변경 시 상위 관리자의 디지털 서명이 필요해야 한다 (기능적)
```

## 4. 보안 요구사항 작성 방법

### 좋은 요구사항의 조건 — SMART 원칙

|조건|설명|나쁜 예|좋은 예|
|---|---|---|---|
|**S**pecific (구체적)|모호하지 않음|"보안을 강화한다"|"비밀번호는 8자 이상, 특수문자 포함"|
|**M**easurable (측정 가능)|수치 또는 기준 존재|"빠르게 탐지한다"|"1초 이내에 탐지한다"|
|**A**chievable (달성 가능)|기술적으로 구현 가능|"모든 공격을 막는다"|"알려진 OWASP Top 10 공격을 차단한다"|
|**R**elevant (관련성)|실제 위협과 연관됨|"UI를 예쁘게 만든다"|"로그인 페이지에 CSRF 토큰 적용"|
|**T**ime-bound (기간)|구현 일정이 있음|"언젠가 추가한다"|"Sprint 2 종료 전 구현한다"|

### 요구사항 우선순위 결정 — MoSCoW 기법

> **MoSCoW** 는 요구사항을 4가지 우선순위로 분류하는 방법임.

|등급|의미|설명|보안 예시|
|---|---|---|---|
|**M**ust have|반드시 필요|없으면 시스템 동작 불가|로그인 인증, 데이터 암호화|
|**S**hould have|있어야 함|없으면 불편하지만 동작은 가능|2FA, 감사 로그|
|**C**ould have|있으면 좋음|있으면 품질 향상|보안 대시보드, 위협 알림|
|**W**on't have|이번엔 제외|현재 범위 밖, 다음 버전에|AI 기반 이상 탐지|

### 보안 요구사항 분류 체계

```
보안 요구사항
├── 인증(Authentication)
│   ├── 사용자 인증
│   └── 시스템/API 인증
├── 인가(Authorization)
│   ├── RBAC(역할 기반 접근 제어)
│   └── ABAC(속성 기반 접근 제어)
├── 기밀성(Confidentiality)
│   ├── 저장 데이터 암호화
│   └── 전송 데이터 암호화
├── 무결성(Integrity)
│   ├── 입력값 검증
│   └── 데이터 해시 검증
├── 가용성(Availability)
│   ├── DDoS 방어
│   └── 장애 복구(Failover)
└── 감사(Auditing)
    ├── 로그 수집
    └── 로그 보호
```

## 5. 보안 요구사항 명세서(SRS) 작성

### SRS(Software Requirements Specification)란?

> **SRS(소프트웨어 요구사항 명세서, Software Requirements Specification)** 는 소프트웨어 시스템의 모든 요구사항을 체계적으로 기술한 공식 문서임.

### SRS 작성 양식 (보안 프로젝트용)

```markdown
# 보안 요구사항 명세서 (SRS)

## 1. 프로젝트 개요
- 프로젝트명:
- 버전:
- 작성일:
- 작성자:

## 2. 시스템 개요
- 목적:
- 범위:
- 주요 이해관계자:

## 3. 위협 요약 (3부 결과 참조)
| 위협 ID | STRIDE 유형 | 위협 설명 | 위험 등급 |
|---------|-----------|---------|---------|
| T-001 | I (정보유출) | SQL 인젝션으로 DB 탈취 | 매우 높음 |

## 4. 기능적 보안 요구사항
| 요구사항 ID | 연관 위협 | 요구사항 내용 | 우선순위 | 담당자 |
|-----------|---------|------------|--------|------|
| SR-F-001 | T-001 | 모든 DB 쿼리는 매개변수화 쿼리를 사용해야 한다 | Must | |
| SR-F-002 | T-001 | 입력값은 화이트리스트 방식으로 검증해야 한다 | Must | |

## 5. 비기능적 보안 요구사항
| 요구사항 ID | 품질 속성 | 요구사항 내용 | 측정 기준 |
|-----------|---------|------------|---------|
| SR-NF-001 | 성능 | 위협 탐지 응답 시간 | 1초 이내 |
| SR-NF-002 | 가용성 | 서비스 가동률 | 99.9% 이상 |

## 6. 컴플라이언스 요구사항
| 법규/기준 | 관련 조항 | 요구사항 |
|---------|---------|---------|
| 개인정보보호법 | 제29조 | 개인정보 암호화 저장 의무 |
| OWASP Top 10 | A01~A10 | 상위 10개 취약점 방어 |

## 7. 수용 기준(Acceptance Criteria)
각 요구사항이 완료되었다고 판단할 수 있는 기준을 명시함.
```

### 실제 요구사항 ID 부여 방식

```
SR - F - 001
 ↑    ↑    ↑
보안  기능  번호
요구  적
사항  (F: Functional
      NF: Non-Functional
      C: Compliance)
```

## 핵심 용어 정리

|용어|영문|설명|
|---|---|---|
|요구사항|Requirements|시스템이 무엇을 해야 하는지 정의한 명세|
|기능적 요구사항|Functional Requirements|시스템이 수행해야 하는 기능 명세|
|비기능적 요구사항|Non-Functional Requirements|시스템 품질 속성 명세|
|SRS|Software Requirements Specification|소프트웨어 요구사항 명세서|
|MoSCoW|MoSCoW|요구사항 우선순위 분류 기법|
|SMART|SMART|좋은 요구사항의 5가지 조건|
|RBAC|Role-Based Access Control|역할 기반 접근 제어|
|ABAC|Attribute-Based Access Control|속성 기반 접근 제어|
|수용 기준|Acceptance Criteria|요구사항 완료 판단 기준|
