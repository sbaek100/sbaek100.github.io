## 1. 프로젝트란 무엇인가

### 정의

> **프로젝트(Project)** 란, **명확한 목표**를 달성하기 위해 **정해진 기간** 동안 **한정된 자원**을 활용하는 **일시적(Temporary)인 활동**임.

#### 핵심 키워드 4가지

|키워드|설명|
|---|---|
|목표(Goal)|달성해야 할 명확한 결과물이 존재함|
|기간(Duration)|시작일과 종료일이 정해져 있음|
|자원(Resource)|사람, 예산, 도구가 제한되어 있음|
|일시성(Temporary)|반복되지 않는 고유한 활동임|

#### 예시

- 일반 업무: "매일 서버 로그를 모니터링한다" → 반복적, 지속적
- **프로젝트: "6개월 안에 침입 탐지 시스템(IDS, Intrusion Detection System)을 구축한다" → 목표, 기간, 자원이 명확함**

## 2. 일반 업무(Operation)와의 차이

### 비교표

|구분|프로젝트(Project)|일반 업무(Operation)|
|---|---|---|
|**목적**|새로운 결과물 창출|기존 업무 유지·반복|
|**기간**|한시적 (시작~종료)|지속적 (끝이 없음)|
|**결과**|고유한 산출물|표준화된 반복 산출물|
|**팀 구성**|프로젝트 기간만 운영|고정 조직|
|**변화**|변화를 만들어냄|현상 유지|
|**위험(Risk)**|불확실성이 높음|상대적으로 예측 가능|

### 정보보안 분야 예시

|일반 업무|프로젝트|
|---|---|
|바이러스 백신 업데이트|제로 트러스트(Zero Trust) 아키텍처 도입|
|방화벽 룰 관리|SIEM(보안 정보 이벤트 관리) 시스템 구축|
|사용자 계정 관리|통합 IAM(Identity and Access Management) 시스템 개발|
|보안 패치 적용|취약점 자동화 스캐닝 플랫폼 개발|

## 3. 애자일(Agile) 방법론

### 배경: 왜 애자일이 등장했나?

기존의 **폭포수 모델(Waterfall Model)** 은 요구사항 분석 → 설계 → 개발 → 테스트 → 배포를 순차적으로 진행함.
![](/assets/img/posts/2026-03-04-project-1-1772542789580.png)

**문제점**: 프로젝트 막바지에 요구사항이 바뀌면 전체를 다시 해야 함 → 비용과 시간 낭비가 극심함.

```
[폭포수 모델 흐름]
요구사항 분석 → 설계 → 개발 → 테스트 → 배포
      (변경 불가) ← 한 단계 실패 시 전체 재작업
```

### 애자일 선언(Agile Manifesto, 2001)의 핵심 가치

> **애자일(Agile)** 이란 "민첩한"이라는 뜻으로, **짧은 반복 주기(Iteration)** 를 통해 **지속적으로 개선**해 나가는 소프트웨어 개발 방법론임.

| 더 중요하게 생각하는 것 | 상대적으로 덜 중요한 것 |
| ------------- | ------------- |
| 개인과 상호작용      | 프로세스와 도구      |
| 작동하는 소프트웨어    | 포괄적인 문서       |
| 고객과의 협력       | 계약 협상         |
| 변화에 대응        | 계획 준수         |

![](/assets/img/posts/2026-03-04-project-1-1772542853803.png)
### 애자일의 대표 프레임워크

|프레임워크|특징|
|---|---|
|**스크럼(Scrum)**|스프린트 단위 반복, 역할 분담 명확|
|**칸반(Kanban)**|작업 흐름 시각화, 유연한 일정|
|**XP(Extreme Programming)**|코드 품질 강조, 페어 프로그래밍|
|**SAFe(Scaled Agile Framework)**|대규모 조직에 적용|

## 4. 스프린트(Sprint)

### 정의

> **스프린트(Sprint)** 란, 스크럼(Scrum) 방법론에서 **일정한 짧은 기간(보통 1~4주)** 동안 정해진 작업을 완료하는 **반복 개발 주기**임.

### 스프린트 구조

```
[스프린트 사이클]

프로덕트 백로그       스프린트 백로그        스프린트 결과물
(Product Backlog) → (Sprint Backlog)  →  (Increment)
전체 할 일 목록       이번 스프린트 할 일      실제 동작하는 산출물

↑_________________피드백(Feedback)_____________________↑
```

#### 1) 프로덕트 백로그 (Product Backlog)

> **"우리가 만들고 싶은 최종 결과물의 모든 꿈과 계획"**

- **의미:** 프로젝트가 끝날 때까지 완성해야 할 **모든 기능과 요구사항의 우선순위 목록**입니다.    
- **학생들이 해야 할 일:** 팀원들과 브레인스토밍을 통해 '있으면 좋을 것 같은 기능'을 전부 적습니다. 그 후, **가장 중요한 순서**대로 줄을 세웁니다.
    
- **예시 (주제: 학교 매점 예약 앱):**    
    1. 로그인 기능 (필수)        
    2. 상품 목록 보기 (필수)        
    3. 장바구니 담기 (중요)        
    4. 실시간 재고 알림 (나중에)        
    5. 리뷰 작성 기능 (선택 사항)        

#### 2) 스프린트 백로그 (Sprint Backlog)

> **"딱 요만큼만! 이번 주에 끝낼 목표"**
- **의미:** 프로덕트 백로그 중 **'이번 스프린트(예: 1~2주)' 안에 하기로 약속한 일들**입니다.    
- **학생들이 해야 할 일:** 전체 목록에서 이번 주에 현실적으로 할 수 있는 양만큼만 가져옵니다. 그리고 그 일을 더 작게 쪼개서 **누가 언제까지 할지** 정합니다.    
- **예시 (1주 차 스프린트 목표):**    
    - **목표:** "사용자가 상품을 볼 수 있게 만들자!"        
    - **할 일(To-do):**        
        - 민수: 상품 데이터베이스(DB) 만들기            
        - 지수: 상품 목록 화면 디자인하기            
        - 영희: 클릭하면 상세 페이지로 넘어가는 기능 구현하기            

#### 3) 스프린트 결과물 (Increment / 제품 증분)

> **"말만 하지 말고, 보여줘! 진짜 작동하는 조각"**

- **의미:** 스프린트가 끝났을 때 나오는 **실제로 눈에 보이고 작동하는 결과물**입니다. 단순한 문서가 아니라 '실행 가능한 코드'나 '동작하는 프로토타입'을 의미합니다.    
- **학생들이 해야 할 일:** 계획했던 기능이 실제로 돌아가는지 확인합니다. 그리고 선생님이나 친구들에게 보여주고 **피드백**을 받습니다.
    
- **예시 (1주 차 결과):**    
    - 비록 결제는 안 되지만, 핸드폰에서 앱을 켰을 때 빵과 우유 목록이 예쁘게 보이고 클릭이 되는 상태.
### 스프린트 구성 이벤트

|이벤트|설명|시점|
|---|---|---|
|**스프린트 계획(Sprint Planning)**|이번 스프린트에서 할 일 결정|스프린트 시작|
|**데일리 스크럼(Daily Scrum)**|매일 15분 진행 상황 공유|매일|
|**스프린트 리뷰(Sprint Review)**|결과물 시연 및 피드백|스프린트 종료|
|**회고(Retrospective)**|팀 개선점 논의|스프린트 종료 후|

### 정보보안 프로젝트 스프린트 예시 — IDS 구축 프로젝트

```
Sprint 1 (1~2주): 요구사항 수집 및 환경 구성
Sprint 2 (3~4주): 네트워크 트래픽 수집 모듈 개발
Sprint 3 (5~6주): 이상 탐지(Anomaly Detection) 알고리즘 적용
Sprint 4 (7~8주): 대시보드 및 알람(Alert) 기능 구현
Sprint 5 (9~10주): 테스트 및 취약점 점검
Sprint 6 (11~12주): 최종 발표 및 문서화
```

## 5. 정보보안 프로젝트의 특수성

### 일반 SW 프로젝트와의 차이점

|구분|일반 SW 프로젝트|정보보안 프로젝트|
|---|---|---|
|**핵심 관심사**|기능 구현|기능 + 보안|
|**요구사항**|기능적 요구사항 중심|보안 요구사항 필수 포함|
|**위협 분석**|선택적|필수적|
|**법규 준수**|일반적|개인정보보호법, ISMS-P 등 필수|
|**테스트**|기능 테스트|기능 테스트 + 침투 테스트(Pentest)|

### 정보보안 3요소 — CIA 트라이어드(CIA Triad)

> 모든 보안 프로젝트는 아래 3가지를 기준으로 설계되어야 함.

|요소|설명|침해 사례|
|---|---|---|
|**기밀성(Confidentiality)**|인가된 사용자만 접근 가능|개인정보 유출, 도청|
|**무결성(Integrity)**|데이터가 변조되지 않음|SQL 인젝션, 파일 변조|
|**가용성(Availability)**|필요할 때 언제든 사용 가능|DDoS 공격, 랜섬웨어|

### 정보보안 프로젝트 필수 고려사항

1. **법규 및 컴플라이언스(Compliance)**: 개인정보보호법, 정보통신망법, ISMS-P 등
2. **위협 모델링(Threat Modeling)**: 개발 전 보안 위협 사전 식별
3. **보안 요구사항(Security Requirements)**: 기능 명세와 함께 보안 명세 작성
4. **시큐어 코딩(Secure Coding)**: 개발 단계부터 취약점 방지
5. **취약점 점검(Vulnerability Assessment)**: 배포 전 점검 필수
