## 이 글의 목적

01~10번 실습 포스트가 **"공격을 직접 해 보는"** 데 초점을 맞췄다면, 이 글은 그 실습들을 **정보보안기사(필기) 시험에서 묻는 이론 틀**로 다시 정리한 것입니다.

실습에서 다룬 SQLi·XSS·CSRF·파일 업로드·인클루전·명령 삽입은 시험에서 **"인젝션·접근통제·시큐어코딩"** 관점으로 다시 나오고, 실습에서 다루지 않은 **SSL/TLS 프로토콜 공격, 웹 서버 하드닝, 웹 로그 분석, 보안 솔루션 분류**가 추가로 출제됩니다. 이 글은 그 **빈 곳을 채우는 이론서**입니다.

> 이 글은 특정 문제집의 문항·정답을 옮기지 않습니다.  
> 대신 **"시험이 반복적으로 묻는 개념"** 을 ★ 표시로 강조해 이론으로 정리했습니다. 개념을 이해하면 어떤 변형 문제가 나와도 풀립니다.
{: .prompt-info }

> **★ 시험 포인트** 표시는 출제 빈도가 높아 반드시 짚고 넘어가야 할 핵심입니다.
{: .prompt-tip }

## 1. SSL/TLS 기초

### 1.1 SSL과 TLS의 관계

| 버전 | 발표 | 비고 |
|---|---|---|
| SSL 1.0 | 미발표 | 설계 결함으로 공개되지 않음 |
| SSL 2.0 | 1995 | Netscape. 메시지 인증에 MD5 사용 등 취약 → **사용 금지** |
| SSL 3.0 | 1996 | POODLE 공격에 취약 → **사용 금지** |
| TLS 1.0 | 1999 | SSL 3.0 기반, IETF 표준화(RFC 2246) |
| TLS 1.1 | 2006 | CBC 관련 보강 |
| TLS 1.2 | 2008 | SHA-256, AEAD(GCM) 지원 — 현재 최소 권고선 |
| TLS 1.3 | 2018 | 핸드셰이크 단순화·고속화, 취약 알고리즘 대거 제거 |

> **★ 시험 포인트**  
> - SSL은 **Netscape**가 만든 것이고, 표준화하면서 이름이 **TLS**로 바뀌었습니다.  
> - **SSL 2.0/3.0은 취약 → 더 이상 사용 금지**, 최소 **TLS 1.1 이상(실무는 1.2 이상)** 을 써야 합니다.  
> - HTTP/2는 **TLS 1.2 이상**을 요구합니다.  
> - SSL/TLS는 통신의 **기밀성·무결성·(서버)인증**을 보장합니다. "암호화하니 신용카드 번호를 그냥 보내도 된다"는 식의 단정은 **틀린 보기**입니다(서버 신뢰성·구현 취약점은 별개).
{: .prompt-tip }

### 1.2 SSL/TLS 프로토콜 구조

SSL/TLS는 여러 하위 프로토콜로 구성됩니다.

| 하위 프로토콜 | 역할 |
|---|---|
| **Handshake** | 암호 알고리즘 협상, 키 교환, 서버(·클라이언트) 인증 |
| **Record** | 실제 데이터를 암호화·무결성 보호하여 전송 |
| **ChangeCipherSpec** | "지금부터 협상된 암호 파라미터를 적용한다"는 신호 |
| **Alert** | 오류·경고 통지 |

**Record 프로토콜이 지원하는 암호 알고리즘 예**: IDEA, RC2-40, DES-40, DES, 3DES, Fortezza, RC4-40, RC4-128 등.

> WPKI(Wireless PKI)는 **무선 인터넷 공개키 기반구조**로, SSL Record의 암호 알고리즘과는 다른 범주입니다(혼동 주의).
{: .prompt-warning }

### 1.3 Handshake 메시지 순서와 내용

핸드셰이크는 대략 다음 순서로 진행됩니다.

```
ClientHello → ServerHello → Certificate → (ServerKeyExchange)
→ (CertificateRequest) → ServerHelloDone
→ (ClientCertificate) → ClientKeyExchange → ChangeCipherSpec → Finished ...
```

| 메시지 | 보내는 쪽 | 핵심 내용 |
|---|---|---|
| **ClientHello** | 클라이언트 | 지원 가능한 **최고 SSL/TLS 버전**, **32바이트 난수**, **세션 ID**, **지원 Cipher Suite 목록**, **압축 방식 목록** |
| **ServerHello** | 서버 | ClientHello가 제시한 것 중 **서버가 선택한** 알고리즘·버전 |
| **Certificate** | 서버 | 서버의 **X.509 인증서**(공개키 포함). 인증 요구 시 클라이언트도 전송 |
| **ServerKeyExchange** | 서버 | Certificate에 공개키가 없을 때, 키 교환용 공개키를 서버 인증서로 서명해 전달 |
| **CertificateRequest** | 서버 | 클라이언트 인증서를 요구할 때 |
| **ChangeCipherSpec** | 양쪽 | 협상된 암호 파라미터를 실제 적용 |

> **★ 시험 포인트**  
> - **ClientHello에 "클라이언트의 주소"는 들어가지 않습니다.** (난수·세션ID·버전·Cipher Suite·압축목록이 들어갑니다.)  
> - **Cipher Suite = "키 교환·인증 알고리즘" + "암호 명세(cipher spec)"** 구조입니다. 예: `TLS_RSA_WITH_AES_128_GCM_SHA256`.  
> - 상호인증(서버↔클라이언트 인증서)에는 **비대칭키(공개키) 암호**를 쓰고, 실제 데이터 기밀성(DES, RC4 등)에는 **대칭키 암호**를 씁니다.  
> - 서버 인증이 필요하면 서버는 **Certificate** 메시지로 X.509 인증서 목록을 보냅니다. 인증서가 필요 없는 응용에서는 ServerKeyExchange 대신 **Certificate**로 서버 인증서를 보내기도 합니다.
{: .prompt-tip }

## 2. SSL/TLS를 노리는 주요 공격 (★ 최다 출제 구간)

암호 자체가 아니라 **프로토콜·구현·다운그레이드**를 노리는 공격들입니다. 이름·한 줄 원리·대상 버전을 짝지어 외워야 합니다.

| 공격 | 한 줄 원리 | 주 대상 |
|---|---|---|
| **BEAST** | TLS 1.0 CBC 모드의 예측 가능 IV를 악용한 평문 복원 | TLS 1.0 |
| **CRIME / BREACH** | 압축 후 암호문 길이 변화로 비밀(쿠키) 추정 | TLS 압축 / HTTP 압축 |
| **POODLE** | SSL 3.0으로 **다운그레이드** 유도 후, CBC 패딩이 MAC으로 보호되지 않는 점을 악용 | SSL 3.0 |
| **Heartbleed** | OpenSSL **Heartbeat** 확장의 길이 미검증 → 서버 메모리(최대 64KB) 덤프 | OpenSSL 1.0.1 |
| **FREAK** | 약한 **수출용(Export) RSA** 스위트를 쓰게 강제 → 512비트 RSA 인수분해 | Export RSA |
| **Logjam** | Diffie-Hellman을 **DHE_EXPORT(512비트)** 로 다운그레이드 | DH 키교환 |
| **DROWN** | 살아있는 **SSLv2**를 이용해 같은 키를 쓰는 최신 연결의 RSA 복호 | SSLv2 |
| **SLOTH** | 약한 해시(MD5 등) 기반 서명에 대한 충돌 공격 | 약한 서명 해시 |
| **SSL Strip** | 중간자가 HTTPS를 HTTP로 벗겨 평문 통신 유도 | HTTP↔HTTPS 전환 |

### 2.1 꼭 구분해야 할 핵심

- **Heartbleed(CVE-2014-0160)**: 이름이 "심장출혈"인 이유 — Heartbeat(연결 유지용) 메시지에서 **요청한 데이터 길이를 검증하지 않아**, 실제보다 더 많은 메모리를 응답에 담아 보냅니다. 그 결과 개인키·세션·쿠키 등 **메모리 내용이 조금씩 새어 나옵니다**. → **암호 알고리즘 문제가 아니라 구현(코드) 버그**입니다.
- **POODLE**: SSL 3.0으로 **강제 다운그레이드**한 뒤, CBC 모드 **패딩이 MAC으로 보호되지 않는** 점을 이용합니다. → "SSL 3.0을 끄라"가 대책.
- **DROWN**("Decrypting RSA with Obsolete and Weakened eNcryption"): **SSLv2를 켜 둔 것** 자체가 다른(최신) 연결까지 위태롭게 만듭니다. → "SSLv2를 끄라".
- **SSL Strip**: 인증서 위조가 아니라 **HTTPS↔HTTP 전환 구간**을 노립니다. 클라이언트 화면에는 인증서 오류가 뜨지 않아 알아채기 어렵습니다. → **HSTS**로 방어.

> **★ 시험 포인트 — "SSL/TLS 취약점과 거리가 먼 것" 유형 대비**  
> - **Spectre / Meltdown**은 **CPU(명령어 실행) 취약점**으로, SSL/TLS 프로토콜 취약점과는 **거리가 멉니다.**  
> - **Ghost(glibc)** 와 **Shellshock(bash)** 도 TLS 자체 취약점이 아니라 **리눅스 라이브러리·셸 취약점**입니다(아래 2.2).
{: .prompt-tip }

### 2.2 같이 묶여 나오는 비-TLS 시스템 취약점

| 취약점 | 위치 | 원리 |
|---|---|---|
| **Shellshock** (CVE-2014-6271) | bash | 환경변수에 담긴 **함수 선언 뒤에 붙인 명령어**까지 bash가 실행 → CGI/HTTP 헤더 경유 RCE |
| **Ghost** (CVE-2015-0235) | glibc | `gethostbyname()` 류 함수의 버퍼 처리 결함 → 메모리 변조로 임의 코드 실행 |

이 둘은 "최근 알려진 심각한 취약점"으로 SSL/TLS 공격과 **함께 보기로 섞여** 나오므로, **"이건 TLS가 아니라 셸/라이브러리 취약점"** 으로 구분하는 것이 포인트입니다.

### 2.3 모바일 앱의 SSL Pinning

**SSL Pinning(인증서 고정)** 은 앱이 **신뢰할 서버 인증서(또는 공개키)를 앱 안에 미리 박아 두고**, 그 인증서 외에는 신뢰하지 않게 하는 기법입니다.

- 목적: 단말에 악성 CA가 설치되어도 **중간자(MITM) 공격을 차단**.
- 효과: 프록시(Burp 등)로 트래픽을 가로채려는 시도도 막힙니다.

> **★ 시험 포인트**: 안드로이드 앱에서 "CA 등록을 통한 중간자 공격을 막기 위해" 도입하는 기술 → **SSL Pinning**(App Signing·IDS·IPS와 혼동 주의).
{: .prompt-tip }

## 3. 웹 서버 보안 강화(하드닝)

### 3.1 서버 정보 노출 최소화 — ServerTokens (Apache)

`ServerTokens` 지시자는 응답 헤더 `Server:` 에 얼마나 많은 정보를 드러낼지 정합니다.

| 설정 | `Server:` 헤더 예시 |
|---|---|
| `Full` | `Apache/2.4.2 (Unix) PHP/4.2.2 MyMod/1.2` (전체 노출) |
| `OS` | `Apache/2.4.2 (Unix)` |
| `Minor` | `Apache/2.4` |
| `Major` | `Apache/2` |
| `Min` | `Apache/2.4.2` |
| `Prod` | `Apache` (보안상 권고) |

> **★ 시험 포인트**: OS·데몬의 **버전 정보 노출은 최소화**해야 하며, Apache에서는 `ServerTokens Prod`(=`Server: Apache`)가 권고입니다. 버전이 노출되면 공격자가 해당 버전의 알려진 취약점을 곧바로 노립니다.
{: .prompt-tip }

### 3.2 Apache 주요 파일 접근 권한

`root`만 실행·수정할 수 있어야 하는 파일을 일반 사용자가 수정할 수 있으면, **권한 도용·로그 위조·임의 코드 실행**으로 이어집니다.

| 파일 | 소유자 | 권장 권한(예) | 이유 |
|---|---|---|---|
| `httpd`(실행 바이너리) | root | `511` (실행 가능, 쓰기 불가) | 변조되면 임의 코드가 root로 실행 |
| `httpd.conf`(설정) | root | `644` 이하(쓰기는 root만) | 설정 변조로 보안정책 무력화 |
| 로그 파일 | root | 일반 사용자 쓰기 금지 | 심볼릭 링크/덮어쓰기로 시스템 파일 훼손·로그 위조 |

> 핵심 원칙: **소유자·그룹·퍼미션을 보안 가이드대로** 설정하고, 주요 디렉터리·파일은 **root만 쓰기 가능**하게 둡니다.
{: .prompt-warning }

### 3.3 관리자 페이지 노출

추측하기 쉬운 관리자 경로(`/admin`, `/manager`, `/master`, `/system` 등)나 포트(`7001`, `8080`, `8443`, `8888` 등)가 외부에 노출되면 공격 표면이 커집니다.

- **점검**: 흔한 경로·포트로 접근 시도, 기본 관리자 계정(`admin`/`administrator`/`manager`)·기본 비밀번호 점검, **인증 과정 없이 중간 페이지(예: `/admin/main.asp`)로 바로 접근**되는지 확인.
- **대책**: 관리자 로그인 페이지 주소를 **추측 어려운 이름**으로 변경, 중요 페이지는 **특정 사용자만** 접근하도록 제한.

### 3.4 불충분한 세션 만료

세션 만료 시간을 정하지 않거나 너무 길게 두면, 공격자가 **만료되지 않은 세션을 재활용**할 수 있습니다(특히 공용 PC).

- **점검**: 인증 후 발급된 페이지의 요청을 **일정 시간(예: 10분 이상) 경과 뒤 재전송**했을 때 정상 처리되는지 확인.
- **대책**: 세션 타임아웃을 **짧게(예: 10분)** 설정하고, 로그아웃 시 서버 세션을 파기. (06번 세션 보안 포스트와 연결)

### 3.5 robots.txt와 크롤러 제어

`robots.txt` 는 사이트 **루트**에 두어, 검색엔진 크롤러(스파이더)가 **수집하지 않기를 바라는 경로**를 표시하는 파일입니다(로봇 배제 표준).

> **★ 시험 포인트**  
> - 크롤러(crawler)가 사이트를 수집·등록하는 것을 제어하려고 쓰는 파일은 **`robots.txt`** (`httpd.conf`·`access.conf` 아님).  
> - 단, robots.txt는 **"권고"** 일 뿐 강제력이 없어, **민감 경로를 여기에 적으면 오히려 공격자에게 힌트**가 됩니다. 접근 통제는 별도로 해야 합니다.
{: .prompt-tip }

## 4. 웹 로그 보안과 침해사고 분석

### 4.1 access_log와 CLF(Common Log Format)

Apache 접근 로그의 기본 형식은 **CLF**입니다.

```
LogFormat "%h %l %u %t \"%r\" %>s %b"
```

예시 한 줄:

```
127.0.0.1 - frank [10/Oct/2000:13:55:36 -0700] "GET /apache_pb.gif HTTP/1.0" 200 2326
```

| 변수 | 의미 |
|---|---|
| `%h` | 요청한 클라이언트(원격 호스트)의 IP |
| `%l` | identd 신원(보통 `-`) |
| `%u` | HTTP 인증으로 알아낸 사용자 ID(userid) |
| `%t` | 서버가 요청 처리를 마친 시각 |
| `%r` | 요청 라인(메서드·자원·프로토콜) — 예: `GET /apache_pb.gif HTTP/1.0` |
| `%>s` | 서버가 클라이언트에 보낸 **상태 코드** |
| `%b` | 응답 헤더를 제외하고 **클라이언트에 보낸 본문 크기** |

> **★ 시험 포인트 — 흔한 함정**  
> - `%u`는 **원격 사용자(HTTP 인증 사용자)** 이지, "원격 클라이언트(호스트)"가 아닙니다. 클라이언트 IP/호스트는 **`%h`** 입니다.  
> - `%b`(=CLF의 마지막 항목)는 **"전송된 콘텐츠(본문)의 크기"** 이지, "서버에 전송된 콘텐츠 크기"가 아닙니다.  
> - **`%m`** = 요청 메서드(GET/POST), **`%H`** = 요청 프로토콜.
{: .prompt-tip }

### 4.2 access_log vs error_log

- **access_log**: 일반적으로 **요청 방식·요청 내용(URL)·상태 코드** 등이 기록됩니다. 예) `400 Bad Request` 같은 상태코드는 요청 URL과 함께 **access_log**에 남습니다.
- **error_log**: 서버 처리 중 발생한 **오류** 정보.
- 로그가 너무 커지면(예: 하루 2GB) 서버가 느려지므로 **로그 분할(rotation)** 기능을 사용합니다.

> **침해 흔적의 예**: `GET /default.ida?XXXX...` 같은 요청이 로그에 보이면 **코드레드(Code Red) 웜** 류의 버퍼 오버플로우 공격 시도일 수 있습니다. 즉 로그 한 줄로 공격 시도를 식별할 수 있어, **로그 보안·정기 분석**이 중요합니다.
{: .prompt-warning }

### 4.3 침해사고 시 전자우편(헤더) 분석

메일 헤더 분석은 보안기사 단골입니다(이메일 보안 단원과 연계).

- `From:` — 발신자의 전자우편 주소.
- `Received:` 줄 — 메일이 **경유한 서버(메일서버) 정보와 IP, 시각**이 누적 기록됩니다. (발송 IP, 사용 메일서버, 수신자 주소 등 확인 가능)

> **★ 시험 포인트**: 메일 헤더로는 **"메일이 경유한 라우터 목록"** 은 알 수 없습니다(라우터가 아니라 **메일서버** 경유 정보가 남습니다).
{: .prompt-tip }

## 5. ModSecurity (Apache용 WAF 모듈)

ModSecurity는 Apache에 **웹 공격 침입 탐지/차단**을 추가하는 모듈로, 클라이언트와 웹 서버 사이에서 요청을 검사합니다. SQL 인젝션·XSS·버퍼 오버플로우 등 OWASP 대부분의 취약점에 대응합니다.

| 주요 기능 | 설명 |
|---|---|
| 요청(request) 필터링 | 웹 서버가 처리하기 **전에** 요청 내용을 분석·필터링 |
| 우회 방지 정규화 | `//`, `\`, `.`, `%00` 등 **우회용 문자열 제거 + 인코딩 디코드** 후 검사 |
| HTTP 프로토콜 이해 | HTTP를 이해하므로 정밀 필터링 |
| POST 페이로드 분석 | GET뿐 아니라 **POST 본문**도 검사 |
| 감사 로깅 | 요청의 상세 부분까지 로깅(탐지전용 운영 가능) |
| HTTPS 필터링 | 엔진이 웹서버에 임베디드되어 **복호화된 요청 데이터**에 접근 → HTTPS 공격도 필터링 |

**주요 환경설정 지시자**

| 지시자 | 값 | 의미 |
|---|---|---|
| `SecRuleEngine` | `On` / `Off` / `DetectionOnly` | **기능 활성화(차단)** / 비활성화 / **탐지만(차단 안 함)** |
| `SecAuditEngine` | `On` / `Off` / `RelevantOnly` | 감사 로깅: 전체 / 안 함 / 관련 트랜잭션만 |

> **★ 시험 포인트**  
> - ModSecurity의 **기능을 켜는(활성화) 지시자는 `SecRuleEngine`** 입니다(`SecAuditLog`·`SecDefaultAction` 아님).  
> - "요청 URL을 정규식으로 수정"하는 목적은 **서버 처리 편의가 아니라**, WAF 필터링을 우회하려는 문자열을 **정규화해 탐지·차단**하기 위함입니다.
{: .prompt-tip }

## 6. HTTP 기반 공격 (인젝션 외)

### 6.1 HTTP 응답 분할(HTTP Response Splitting)

사용자 입력값이 **HTTP 응답 헤더(예: `Set-Cookie`, `Location`)에 그대로 포함**될 때, 입력에 **CR(`%0d`)·LF(`%0a`) 개행 문자**가 있으면 응답이 **2개 이상으로 분리**됩니다.

- 공격자는 첫 응답을 끝내고 **두 번째 응답을 위조**해 **XSS·캐시 포이즈닝**을 수행합니다.
- **대책**: 헤더에 들어갈 입력값에서 **CR·LF 제거** 또는 적절한 인코딩.

### 6.2 HTTP 요청 스머글링(HTTP Request Smuggling / Desync)

프런트엔드–백엔드 서버 구조에서, `Content-Length` 와 `Transfer-Encoding: chunked` 헤더를 **모순되게 조작**하면, 두 서버가 요청 경계를 **다르게 해석**합니다. 그 틈에 **하나의 패킷 안에 또 다른 요청을 숨겨(smuggling)** 백엔드로 직접 보내, 일반 사용자가 닿을 수 없는 자원 접근·XSS 유도 등을 수행합니다.

> **★ 시험 포인트**: `Content-Length` + `Transfer-Encoding: chunked` 를 동시에 조작해 패킷 안에 다른 요청을 포함시키는 것은 **HTTP Request Smuggling(HTTP Desync)** 입니다(SSRF·CSRF와 혼동 주의).
{: .prompt-tip }

### 6.3 그 밖의 응용 공격

| 공격 | 원리 |
|---|---|
| **Struts(스트럿츠) 공격** | 안전하지 않은 구조로 역직렬화/표현식이 처리되어 RCE로 이어짐. 구버전 사용 시 홈페이지 변조·DoS·DB 유출 |
| **Format String** | `printf` 류에 사용자 입력이 **포맷 문자열로** 들어가 메모리 읽기/쓰기 |
| **Buffer Overflow** | 폼 핸들링·중복 폼 등 경계 검사 미흡으로 버퍼를 넘겨 임의 코드 실행 |

## 7. 인젝션 변종 총정리 (실습 01·02·08과 연계)

### 7.1 SQL Injection — 종류

| 유형 | 핵심 |
|---|---|
| **Form SQL Injection** | 폼 기반 인증의 조건문을 조작해 인증 우회 |
| **Union SQL Injection** | `UNION SELECT`로 다른 쿼리 결과를 덧붙여 추출 |
| **Stored Procedure SQLi** | 저장 프로시저를 함수처럼 실행하는 쿼리 집합 악용 |
| **Error-Based SQLi** | DB **오류 메시지**를 단서로 단계적으로 정보 획득 |
| **Blind SQLi** | 오류 메시지가 없을 때, 결과의 **참/거짓**으로 정보 유추 |
| **Mass SQL Injection** | 다수 사이트를 자동화로 한 번에 감염 |

> **★ 시험 포인트**: **Blind SQLi** = 흔히 **content(참/거짓) 기반** 또는 **time(시간) 기반**으로 DB 정보를 판단합니다. **오류 메시지를 이용하면 Error-Based**, **참/거짓·시간이면 Blind**로 구분합니다.
{: .prompt-tip }

### 7.2 SQL Injection — 특수문자와 주석

| 특수문자 | 용도 |
|---|---|
| `'` | 문자 데이터 구분 기호 |
| `;` | 쿼리 구분 기호 |
| `--`, `#` | 해당 줄 주석 |
| `/* */` | 블록 주석 |
| `\|\|`, `+` | 문자열 연결(DBMS에 따라) |

**주석은 DBMS마다 다릅니다.**

| DBMS | 한 줄 주석 |
|---|---|
| MSSQL / Oracle | `--` |
| MySQL | `#`(또는 `-- `) |
| MS Access | `%00` 등 |

> **★ 시험 포인트**  
> - `&`(앰퍼샌드)는 **SQL이 아니라 XSS·HTTP 파라미터**에서 의미 있는 문자입니다. "SQLi에서 허용하지 말아야 할 특수문자"를 고를 때 **`&`는 SQLi 문맥과 거리가 멉니다.**  
> - 주석(`--`, `#`)은 **인증 부분을 무력화**하려고 자주 쓰입니다(뒤 조건을 잘라냄).
{: .prompt-tip }

### 7.3 SQL Injection 방어 — 시험이 강조하는 항목

- **준비된 명령문(Prepared Statement)** 사용 → 입력을 **데이터로 바인딩**(가장 근본적).
- **화이트리스트** 입력 검증(블랙리스트보다 안전 — 블랙리스트는 우회가 쉬움).
- **저장 프로시저** 사용(웹을 통한 SQLi 방지 맥락에서 **DB 확장 프로시저가 아닌 내장/저장 프로시저**).
- **원시 ODBC 에러를 사용자에게 노출 금지**, DB 계정은 **최소 권한**.
- **테이블·컬럼명·SQL 구조가 외부 HTML에 노출되지 않게** 설정.

### 7.4 그 밖의 인젝션

| 인젝션 | 원리 |
|---|---|
| **SSI Injection** | HTML에 입력값이 들어가 서버에서 처리될 때 `<!--#exec ...-->`·`<!--#echo var="DOCUMENT_ROOT"-->` 같은 **SSI 지시문**이 실행되어 서버 데이터 유출/명령 실행 |
| **LDAP Injection** | LDAP 쿼리에 입력을 주입해 디렉터리(개인정보 등) 유출 |
| **XPath Injection** | 검사 없이 XPath 질의문에 입력을 넣어 쿼리 의미·구조 변경 → 인가되지 않은 데이터 열람 |
| **XML Injection** | XML 쿼리(XQuery 등)에 입력을 주입해 구조 변경 |

> **★ SSI 인젝션 점검 포인트**  
> - `<!--#echo var="DOCUMENT_ROOT"-->` 를 입력해 반환 페이지에 **서버의 홈 디렉터리(웹 루트)** 가 표시되면 취약.  
> - `<!--#exec cmd="ls -al"-->` 가 실행되어 **디렉터리 파일 목록**이 나오면 명령 실행 가능.
{: .prompt-tip }

> **★ 인젝션 공통 방어(시험 단골)**: **화이트리스트** 입력 검증이 핵심. XPath/XML은 입력값을 **바인딩**하고 특수문자(`(`, `)`, `[`, `]`, `'`, `/`, `=`, `@` 등)를 필터링/치환. **출력값 검증이 아니라 입력값 필터링**이 정답인 경우가 많습니다.
{: .prompt-tip }

### 7.5 XSS 방어 — 문자 치환과 화이트리스트

사용자 입력의 `<`, `>`, `&`, `"` 등을 **HTML 엔티티로 치환**합니다.

| 문자 | 치환 |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `&` | `&amp;` |
| `"` | `&quot;` |

> **★ 시험 포인트**: HTML 태그를 허용해야 하는 게시판이라면, **허용 태그 목록(White List)** 을 정하고 그 태그만 허용합니다(모두 막거나 모두 허용이 아니라 **화이트리스트**).
{: .prompt-tip }

### 7.6 CSRF 방어 — 시험이 강조하는 구성

- 입력 폼은 **GET보다 POST** 사용.
- 폼과 처리 프로그램 사이에 **토큰** 사용 → 공격자의 직접적인 URL 사용이 동작하지 않도록.
- 중요 기능은 **사용자 세션 검증 + 재인증** 요구.
- CSRF 공격 코드는 **XSS와 마찬가지로 자바스크립트 형태**로 삽입될 수 있습니다(둘 다 입력값 검증 미흡이 원인).

### 7.7 OS 명령어 삽입 — 특수문자 조합

| 기호 | 동작 |
|---|---|
| `;` | 앞 명령 성공 여부와 무관하게 **순차 실행** |
| `\|` | 앞 명령의 **출력**을 뒤 명령의 **입력**으로 |
| `\|\|` | 앞 명령이 **실패해야** 뒤 명령 실행 |
| `&&` | 앞 명령이 **성공해야** 뒤 명령 실행 |

> **★ 시험 포인트 — 흔한 함정**: "`ls && pwd` → `ls`가 **실패해야** `pwd` 실행"은 **틀린** 설명입니다. `&&`는 **성공해야** 뒤가 실행됩니다. 반대로 `||`는 **실패해야** 뒤가 실행됩니다.
{: .prompt-tip }

## 8. 파일 업로드·인클루전 시험 포인트 (실습 09·10과 연계)

### 8.1 파일 업로드 취약점 판단

- 게시판 등에 **글쓰기 권한**이 있는지, **파일 첨부 권한**이 있는지, **스크립트 확장자(`jsp`·`php`·`asp`) 업로드가 가능**한지 점검합니다.
- 핵심 발생 조건: ① **실행 가능한 형태의 파일을 업로드**할 수 있고, ② 업로드 파일이 **URL로 접근 가능**하며, ③ 저장 디렉터리에서 **서버 측 스크립트가 실행 가능**해야 합니다.

> **★ 시험 포인트**: "게시판에 **스크립트 태그 입력**이 가능한지"는 **XSS** 판단 항목이지, 파일 업로드 취약점 판단과는 거리가 멉니다.
{: .prompt-tip }

### 8.2 웹셸(WebShell)

`<% eval request("cmd") %>` 같은 짧은 ASP 코드(또는 `<?php system($_GET['cmd']); ?>`)는 **웹셸**입니다. `eval`/`execute`로 외부에서 전달한 코드를 실행합니다.

- `eval(expression)`: expression을 **평가**해 결과(True/False 등) 반환.
- `execute(expression)`: expression을 **실행**.

### 8.3 파일 삽입(File Inclusion)

- 공격자가 악성 스크립트를 서버에 포함시켜 실행 → 삽입 위치가 **로컬이면 LFI, 원격이면 RFI**.
- PHP의 외부 사이트 소스 실행 기능(`allow_url_fopen`)을 악용한 변조 사고가 많습니다.

> **★ 시험 포인트**: PHP에서 **원격 파일의 명령 실행(RFI)** 대책 → `php.ini`에서 **`allow_url_fopen`(및 `allow_url_include`)을 `Off`** 로 설정.
{: .prompt-tip }

### 8.4 부적절한 파라미터 조작

가격·수량·주문 정보 등 **클라이언트와 서버 사이에 교환되는 파라미터**를 조작해 권한·자격을 상승시키는 공격입니다.

- 대응: **데이터 유형 검증, 허용 문자셋 검증, 최대/최소 길이 검증, Null 허용 여부 검증, 값/패턴 검증**.

> **★ 시험 포인트**: 파라미터 조작 대응으로 **"무차별 대입(brute force) 검증"** 은 적절하지 않습니다(파라미터 *값 검증*이 핵심).
{: .prompt-tip }

## 9. 보안 솔루션 분류 (혼동 주의 구간)

### 9.1 한눈에 비교

| 솔루션 | 한 줄 정의 |
|---|---|
| **WAF**(Web Application Firewall) | 일반 네트워크 방화벽과 달리 **웹 애플리케이션 보안에 특화**된 방화벽 |
| **IDS**(Intrusion Detection System) | 악의적 활동을 **탐지·기록·보고** |
| **IPS**(Intrusion Prevention System) | 공격 신호를 탐지해 **자동으로 능동 차단** |
| **UTM**(Unified Threat Management) | 여러 보안 기능을 **하나의 장비로 통합** |
| **NGFW**(차세대 방화벽) | IP 헤더뿐 아니라 **패킷 데이터(애플리케이션 계층, L7)** 까지 검사 |
| **SIEM** | 기업 내 모든 자원의 정보·보안 이벤트를 **통합 관리**(예: QRadar, ArcSight, Splunk, enVision) |
| **SOAR** | 보안 대응 프로세스를 **자동화**해 사람 개입 없이 표준 절차로 대응(Gartner 2017) |
| **MDM**(Mobile Device Management) | 개인 소유 모바일 **기기 전체**를 중앙에서 제어 |
| **MAM**(Mobile Application Management) | 모바일에 설치된 **앱·데이터만 선택적**으로 관리 |

### 9.2 자주 나오는 짝 맞추기

- "응용 프로그램의 입력·출력·접근을 제어하는 방화벽" → **WAF**.
- "스마트폰·태블릿·노트북 같은 **모바일 장치를 관리**하는 기술" → **MDM**.
- "악의적 활동을 식별·기록·보고하고 **능동 차단**" → **IPS**(탐지·기록·보고만 하면 IDS).

> **★ 시험 포인트**: SIEM 대표 제품(QRadar·ArcSight·enVision·Splunk)과 SOAR(자동화·Gartner 2017 용어)를 구분하세요. MDM(기기 전체) vs MAM(앱만)도 단골입니다.
{: .prompt-tip }

## 10. 시큐어코딩 — 정적 분석 vs 동적 분석

| 구분 | 정적분석(SAST) | 동적분석(DAST) |
|---|---|---|
| 실행 여부 | **실행하지 않고** 소스코드 수준 분석 | **실행 환경에서** 분석 |
| 사용 시점 | 주로 **개발 단계** | 주로 **시험(테스트) 단계** |
| 장점 | 개발 초기 발견 → **수정비용 절감** | **소스코드 불필요**, 정확도·커버리지 향상 |
| 단점 | 설계·구조 관점/컴포넌트 간 통합 취약점 발견 **제한적** | 도구·사용자 수준에 의존, **구조 관점 취약점 발견 못함** |
| 예 | compile-time·source 수준 코드/ API 점검 | **stress test, penetration test** |

> **★ 시험 포인트**  
> - **stress test·penetration test는 "동적 분석"** 입니다. "정적 분석의 예"로 나오면 **틀린 보기**입니다.  
> - 정적분석은 **실행 결과보다 실행 전 구현**에 초점, 동적분석은 **구현보다 실행 과정·결과**에 초점.  
> - 둘은 **상호 보완**적입니다.
{: .prompt-tip }

## 11. 입력값 검증 — 화이트리스트 vs 블랙리스트 (전 단원 관통 원리)

| 방식 | 정의 | 보안성 |
|---|---|---|
| **블랙리스트** | 금지 문자/패턴만 차단, 나머지 허용 | 낮음 — **우회가 쉬움**(빠뜨린 패턴 존재) |
| **화이트리스트** | 허용 문자/패턴만 통과, 나머지 차단 | 높음 — 통과 기준이 좁아 우회 어려움 |

- 개별 문자를 일일이 나열하기보다 **정규식으로 범주/패턴을 지정**하면 유지·보수에 유리.
- 신뢰할 수 없는 출처에서 받은 값은 모두 화이트리스트로 검증.

> **★ 시험 포인트**: SQLi·XSS·명령 삽입·파일 인클루전·파라미터 조작 등 **거의 모든 인젝션 방어의 정답은 "블랙리스트가 아니라 화이트리스트"** 입니다. 블랙리스트는 보조 수단입니다.
{: .prompt-tip }

## 12. 마무리 — 시험 직전 1분 점검표

- SSL은 **Netscape**, 표준화하면서 **TLS**. SSL 2/3 금지, 최소 TLS 1.1↑.
- ClientHello에 **클라이언트 주소 없음**. Cipher Suite = 키교환·인증 + 암호명세.
- **Heartbleed=구현버그(메모리 누출), POODLE=SSL3 다운그레이드, DROWN=SSLv2, FREAK/Logjam=Export 다운그레이드, SSL Strip=HTTPS 벗기기**.
- **Spectre/Meltdown·Shellshock·Ghost는 TLS 취약점 아님**.
- **SSL Pinning** = 모바일 MITM(CA 등록) 방어.
- Apache **ServerTokens Prod** 권고. 주요 파일은 **root만 쓰기**.
- **robots.txt** = 크롤러 제어(권고일 뿐, 민감정보 적지 말 것).
- CLF: `%h`(클라IP) `%u`(인증사용자) `%b`(본문크기) — **`%u`≠호스트**.
- 메일 헤더로 **라우터 목록은 못 봄**(메일서버 경유 정보).
- ModSecurity 활성화 = **`SecRuleEngine On`**.
- **HTTP Response Splitting**(CR/LF) vs **HTTP Request Smuggling**(CL+TE).
- **Blind SQLi = content/time 기반**, Error-Based = 오류 메시지.
- 명령 삽입: `&&`=성공해야 다음, `||`=실패해야 다음.
- RFI 대책 = `allow_url_fopen Off`.
- **stress/penetration test = 동적분석**.
- 모든 인젝션 방어의 기본 = **화이트리스트**.

> 이 글은 01~10번 실습과 짝을 이룹니다. 공격을 **손으로 해 본 경험** 위에 이 이론을 얹으면, 시험의 변형 문제도 **원리로** 풀 수 있습니다.
{: .prompt-tip }
