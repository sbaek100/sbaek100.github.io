## 1. SQL Injection이란?

**공격자가 입력창에 "SQL 문장 조각"을 집어넣어, 원래 개발자가 의도하지 않은 쿼리를 실행시키는 공격.**

- 주로 **로그인 창, 검색창, URL 파라미터** 등 사용자 입력이 그대로 SQL에 들어가는 곳에서 발생한다.
- OWASP(웹 취약점 통계 단체) 에서 수십 년째 "Top 10" 에 들어 있는 **가장 고전적이고 가장 치명적인** 공격 중 하나다.

> 💡 한마디로 요약하면:  
> **"사용자 입력을 문자열로 그대로 이어 붙여 SQL을 만들면 뚫린다."**
{: .prompt-info }

## 2. 실습 환경 준비 (Windows 11)

### 2-1. 실습용 DB

```sql
DROP DATABASE IF EXISTS injection_lab;
CREATE DATABASE injection_lab;
USE injection_lab;

CREATE TABLE users (
    id       INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(30) NOT NULL UNIQUE,
    password VARCHAR(100) NOT NULL,
    role     VARCHAR(20)
);

INSERT INTO users (username, password, role) VALUES
('admin',  'admin1234', 'ADMIN'),
('minjun', 'abcdefg',   'USER'),
('seoyeon','qwerty',    'USER');
```

> ⚠️ 실제 서비스라면 비밀번호는 반드시 **해시(SHA-256, bcrypt 등)** 로 저장한다.

> "계정부터 덜컥 만들지 않고, 먼저 표로 정의한다" 는 습관이 이번 단원의 핵심이다.

## 3. 접근통제 설계 — 권한 매트릭스부터 그린다

**"공격 실습을 시작하기 전에, 누가 무엇을 할 수 있는지 표로 먼저 정의한다."**

DB 보안 설계의 정석 순서는 다음과 같다.

1. 시스템에 어떤 **주체(Subject)** 가 있는가? — 사용자/애플리케이션/역할
2. 어떤 **객체(Object)** 가 있는가? — 테이블, 뷰, 컬럼
3. 각 주체가 각 객체에 대해 어떤 **동작(Action)** 을 할 수 있는가? — SELECT / INSERT / UPDATE / DELETE

이 셋의 관계를 한 장의 표로 정리한 것이 **접근통제 매트릭스(Access Control Matrix)** 다.

### 3-1. 접근통제의 세 가지 유형

| 유형 | 약자 | 설명 |
|---|---|---|
| 임의적 접근통제 | DAC | 객체 소유자가 권한을 직접 부여 (MySQL `GRANT` 기본 방식) |
| 강제적 접근통제 | MAC | 시스템이 보안 등급·라벨에 따라 강제 적용 (군·정부 시스템) |
| 역할 기반 접근통제 | RBAC | **역할(Role)** 에 권한을 묶고, 사용자에게 역할을 부여 |

MySQL 8.0은 DAC를 기본으로 쓰고, `CREATE ROLE` 로 RBAC도 지원한다. 이번 실습은 DAC 방식이다.

### 3-2. 이번 실습용 권한 매트릭스

`injection_lab` 안에서 세 가지 주체를 가정한다.

- **`injlab_app`** — 웹 로그인 기능이 쓰는 애플리케이션 계정 (가장 권한이 적어야 함)
- **`injlab_admin`** — 관리자. 사용자 관리까지 가능
- **`injlab_guest`** — 외부 방문자. 공개된 정보만 볼 수 있음

먼저 공개용으로 쓸 **뷰**를 하나 정의한다. (민감 컬럼 `password` 를 제외한다.)

| 객체 | 종류 | 설명 |
|---|---|---|
| `users` | 테이블 | 원본. `password` 컬럼 포함 |
| `v_users_public` | 뷰 | `id`, `username`, `role` 만 공개 |

이제 매트릭스를 그린다.

| 주체 \ 객체 | `users` (원본) | `users.password` (민감 컬럼) | `v_users_public` (공개 뷰) |
|---|---|---|---|
| `injlab_app`   | SELECT(id, username, password, role) | ✅ (로그인 검증용) | — |
| `injlab_admin` | SELECT / INSERT / UPDATE | ✅ | SELECT |
| `injlab_guest` | ❌ 접근 금지 | ❌ 접근 금지 | SELECT |

> 💡 `injlab_app` 는 로그인 검증 때문에 `password` 컬럼 **읽기**는 허용하지만,  
> **UPDATE/DELETE/DROP 같은 변경 권한은 없다.** 이것이 SQL Injection 피해를 "정보 노출" 선에서 막아 주는 장치다.
{: .prompt-info }

### 3-3. 표를 SQL로 옮기기 — 작성 통제 5단계

접근통제 매트릭스를 SQL로 옮길 때는 **정해진 순서**를 지킨다.  
이 순서를 지키지 않으면 "지금은 되는데 누가 뭘 할 수 있는지 아무도 모르는 상태" 가 된다.

#### 단계 1. 민감 컬럼을 가린 공개 뷰부터 만든다

```sql
USE injection_lab;

CREATE OR REPLACE VIEW v_users_public AS
SELECT id, username, role          -- password 컬럼 제외
FROM users;
```

#### 단계 2. 계정을 만든다 (아직 권한은 주지 않는다)

```sql
-- 기존 실습 잔여가 있다면 깨끗이 지운다
DROP USER IF EXISTS 'injlab_app'@'localhost';
DROP USER IF EXISTS 'injlab_admin'@'localhost';
DROP USER IF EXISTS 'injlab_guest'@'localhost';

CREATE USER 'injlab_app'@'localhost'   IDENTIFIED BY 'injlab_pw_1234';
CREATE USER 'injlab_admin'@'localhost' IDENTIFIED BY 'admin_pw_1234';
CREATE USER 'injlab_guest'@'localhost' IDENTIFIED BY 'guest_pw_1234';
```

> 💡 **"계정 생성"과 "권한 부여"는 반드시 분리한다.**  
> 계정만 먼저 만들어 두면 잠시 **아무것도 못 하는 무권한 상태**가 된다.  
> 이 상태가 곧 "명시적 거부(Deny-by-default)" 원칙의 출발점이다.
{: .prompt-info }

#### 단계 3. 표에 따라 권한을 정확히 부여한다

```sql
-- injlab_app: 로그인 검증에 필요한 컬럼만 SELECT
GRANT SELECT (id, username, password, role) ON injection_lab.users
    TO 'injlab_app'@'localhost';

-- injlab_admin: users 전체 조작 + 공개 뷰 조회
GRANT SELECT, INSERT, UPDATE ON injection_lab.users
    TO 'injlab_admin'@'localhost';
GRANT SELECT ON injection_lab.v_users_public
    TO 'injlab_admin'@'localhost';

-- injlab_guest: 공개 뷰만
GRANT SELECT ON injection_lab.v_users_public
    TO 'injlab_guest'@'localhost';

FLUSH PRIVILEGES;
```

> ⚠️ **매트릭스에 없는 권한은 절대로 추가하지 않는다.**  
> "편의상" 주는 권한이 나중에 사고의 근원이 된다.
{: .prompt-warning }

#### 단계 4. 표 외의 권한이 남아 있지 않은지 확인한다

이번 실습은 단계 2에서 `DROP USER IF EXISTS` 후 계정을 새로 만들었으므로 과거 권한이 남아 있지 않다.  
계정을 삭제하지 않고 재사용한 경우에는 `SHOW GRANTS` 로 현재 권한을 확인한 뒤, 표에 없는 권한만 정확히 `REVOKE` 한다.

#### 단계 5. 매트릭스대로 되었는지 반드시 검증한다

```sql
SHOW GRANTS FOR 'injlab_app'@'localhost';
SHOW GRANTS FOR 'injlab_admin'@'localhost';
SHOW GRANTS FOR 'injlab_guest'@'localhost';
```

각 계정의 결과를 **3-2의 표와 한 줄씩 맞춰 본다.** 한 항목이라도 다르면 표를 수정하든 GRANT를 고치든 둘 중 하나.

### 3-4. 검증 실습 — 매트릭스가 실제로 지켜지는가?

Workbench에서 각 계정으로 새 연결을 만들고 아래를 시도해 결과를 표에 기록한다.

| 시도 | `injlab_app` | `injlab_admin` | `injlab_guest` |
|---|---|---|---|
| `SELECT * FROM users` | ? | ? | ? |
| `SELECT * FROM v_users_public` | ? | ? | ? |
| `UPDATE users SET role='ADMIN'` | ? | ? | ? |
| `DROP TABLE users` | ? | ? | ? |

정답 예시:

| 시도 | app | admin | guest |
|---|---|---|---|
| `SELECT * FROM users` | ✅ | ✅ | ❌ |
| `SELECT * FROM v_users_public` | ❌(권한 없음) | ✅ | ✅ |
| `UPDATE users SET role='ADMIN'` | ❌ | ✅ | ❌ |
| `DROP TABLE users` | ❌ | ❌ | ❌ |

`DROP` 은 **어떤 계정도 불가** 다. 이 설계는 이미 "10-3의 공격 실습"을 견디도록 되어 있다.

> 💡 이 표를 먼저 설계했기 때문에,  
> 뒤(6절)에서 보는 `'; DROP TABLE users; #` 공격이 **원천적으로 막히는 이유**를 구조적으로 설명할 수 있다.
{: .prompt-info }

### 3-5. 이후 공격 실습은 가장 제한된 계정 `injlab_app` 으로 진행

지금부터의 모든 Python 스크립트는 **`injlab_app`** 로만 접속한다.  
관리자 권한으로 공격 실습을 하면 **사고가 실제로 일어난다.** 순서와 계정을 꼭 지키자.

## 5. 공격 시연 — 비밀번호 없이 로그인

다시 `login_bad.py` 를 실행하고, 아래처럼 입력한다.

```
아이디: admin
비밀번호: ' OR '1'='1
```

### 무슨 일이 일어났는가?

`sql` 변수의 값은 이렇게 된다:

```sql
SELECT * FROM users
 WHERE username = 'admin' AND password = '' OR '1'='1'
```

- `'1'='1'` 은 **항상 참** 이다.
- `OR` 로 연결되었으므로 **전체 WHERE 조건이 항상 참** 이 된다.
- 결과: **비밀번호가 틀려도 admin 으로 로그인된다.**

> ⚠️ 이 한 줄의 실수로 관리자 계정이 그대로 넘어간다.  
> 이것이 실제 뉴스에 나오는 "개인정보 유출 사고" 의 전형적인 첫 단계다.
{: .prompt-warning }

## 6. 또 다른 공격 — 원하는 결과 뽑아내기

```
아이디: minjun' #
비밀번호: 아무거나
```

`#` 는 MySQL 주석이라 그 뒤가 모두 무시된다. 실제 실행되는 쿼리:

```sql
SELECT * FROM users WHERE username = 'minjun' # ' AND password = '아무거나'
```

→ **비밀번호 확인을 생략**하고 `minjun` 으로 로그인된다.

> 💡 `--` 도 SQL 주석으로 많이 쓰이지만, MySQL에서는 `--` 뒤에 공백이 필요하다.  
> 실습에서는 헷갈리지 않도록 `#` 주석을 사용한다.
{: .prompt-info }

### 더 심한 공격 (그래서 최소 권한이 중요하다)

만약 이 계정이 `DROP` 권한까지 있고, 실행 환경이 여러 SQL 문장을 한 번에 실행하도록 허용한다면 다음 입력으로 테이블을 날려버릴 수 있다.

```
아이디: admin'; DROP TABLE users; #
```

→ 쿼리는 다음처럼 해석된다.

```sql
SELECT * FROM users WHERE username = 'admin'; DROP TABLE users; # ...
```

> 💡 실습 계정 `injlab_app` 은 `SELECT` 만 갖고 있기 때문에 `DROP TABLE` 이 실행되지 않는다.  
> **10-2 최소 권한 원칙의 방어 효과**를 직접 볼 수 있다.
{: .prompt-info }

## 7. 근본 해결 — 파라미터 바인딩 (Prepared Statement)

**취약했던 이유**: 사용자 입력을 "문장의 일부" 로 취급했다.  
**해결**: 사용자 입력은 **"데이터 값"** 으로만 넘기고, SQL 구조는 **미리 고정**한다.

### 7-1. 안전한 코드 — `login_safe.py`

```python
# login_safe.py
import mysql.connector

conn = mysql.connector.connect(
    host="localhost",
    user="injlab_app",
    password="injlab_pw_1234",
    database="injection_lab"
)
cursor = conn.cursor(dictionary=True)

username = input("아이디: ")
password = input("비밀번호: ")

# ✅ %s 자리에 값이 "데이터로" 들어간다 (안전)
sql = "SELECT * FROM users WHERE username = %s AND password = %s"
cursor.execute(sql, (username, password))

result = cursor.fetchone()

if result:
    print(f"[로그인 성공] 환영합니다, {result['username']}님 ({result['role']})")
else:
    print("[로그인 실패]")

cursor.close()
conn.close()
```

### 7-2. 이번엔 공격이 안 통한다

아까 뚫렸던 입력을 다시 해 보자.

```
아이디: admin
비밀번호: ' OR '1'='1
```

결과:

```
[로그인 실패]
```

이유: `' OR '1'='1` 이 **그냥 "비밀번호라는 이름의 문자열 값"** 으로만 취급된다.  
DB는 이 값을 **password 컬럼과 있는 그대로 비교**할 뿐, SQL 구조를 바꾸지 않는다.

---

## 8. 파라미터 바인딩을 "시각적으로" 비교

| 구분 | 취약한 코드 | 안전한 코드 |
|---|---|---|
| SQL 작성 | `"... WHERE name = '" + x + "'"` | `"... WHERE name = %s"` |
| 값 전달 | 문자열 연결 | `execute(sql, (x,))` |
| 값 해석 | SQL 구조의 일부로 해석 | 반드시 "데이터" 로 해석 |
| 결과 | 뚫린다 | 안전하다 |

> 💡 외우기: **“문자열로 `+` 하지 말고, `%s` 와 튜플로 넘긴다.”**
{: .prompt-info }

## 9. 검색 기능에서의 SQL Injection

로그인뿐 아니라 **검색창** 도 자주 뚫리는 지점이다.

### 취약한 검색

```python
# search_bad.py
import mysql.connector

conn = mysql.connector.connect(
    host="localhost", user="injlab_app",
    password="injlab_pw_1234", database="injection_lab"
)
cursor = conn.cursor(dictionary=True)

keyword = input("검색어: ")
sql = "SELECT username, role FROM users WHERE username LIKE '%" + keyword + "%'"
cursor.execute(sql)
for row in cursor.fetchall():
    print(row)

cursor.close()
conn.close()
```

공격 입력:

```
검색어: %' OR '1'='1' #
```

→ 전체 사용자 목록이 유출된다.

### 안전한 검색

```python
# search_safe.py
import mysql.connector

conn = mysql.connector.connect(
    host="localhost", user="injlab_app",
    password="injlab_pw_1234", database="injection_lab"
)
cursor = conn.cursor(dictionary=True)

keyword = input("검색어: ")

sql = "SELECT username, role FROM users WHERE username LIKE %s"
cursor.execute(sql, (f"%{keyword}%",))   # %는 파이썬 쪽에서 붙인다
```

## 10. 추가 방어 수단 (다층 방어)

실무에서는 **한 가지 방어에만** 의존하지 않는다. 여러 겹으로 막는다.

0. **접근통제 매트릭스 설계** (오늘 3단원) — 공격 이전에 "누가 무엇을 할 수 있는가"를 표로 정의.
1. **파라미터 바인딩** (가장 중요) — 오늘 배운 `%s` 방식.
2. **최소 권한 원칙** — 10-2에서 배운 GRANT 최소화. 뚫려도 피해를 줄인다.
3. **입력 검증(Validation)** — 숫자만 받아야 할 곳은 `int(user_input)` 으로 변환.
4. **ORM 사용** — SQLAlchemy, Django ORM 등은 내부적으로 파라미터 바인딩을 한다.
5. **웹 방화벽(WAF)** — 의심스러운 입력을 앞단에서 차단.
6. **민감 컬럼은 VIEW로 마스킹** — 9-1에서 배운 기법.

> 💡 **0번이 가장 앞에 온 이유**  
> 나머지 1~6번은 모두 "기술적 방어" 이지만, 0번은 **설계 단계의 방어** 다.  
> 설계가 틀리면 아무리 코드에서 막아도 권한 오용은 막을 수 없다.

## 12. 정리

- SQL Injection은 **입력 문자열을 쿼리의 일부로 해석**해 버려서 생기는 사고다.
- 공격 실습 전에 **접근통제 매트릭스** 를 먼저 표로 그린 뒤 `GRANT` 로 구현한다.
- 방어의 핵심은 **파라미터 바인딩** (`%s` + 튜플) 이다. 문자열 `+` 는 금지.
- 만에 하나 뚫려도 **최소 권한 원칙(10-2)** 이 피해 범위를 줄여 준다.
- **접근통제 매트릭스 설계 + VIEW 마스킹(9-1) + 최소 권한(10-2) + 파라미터 바인딩(10-3)** 이 네 겹 방어가 기본 세트다.

다음 주([11-1](/posts/database-11-1))에는 사고가 나도 복구할 수 있도록 **백업과 복구** 를 실습한다.
