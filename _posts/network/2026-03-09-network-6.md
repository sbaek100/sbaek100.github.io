# 캡슐화·역캡슐화 실습 & OSI 5~7계층 가볍게 보기

---

# 1장. OSI 5~7계층은 시험용보다 "감 잡기" 정도로 이해

---

## 1.1 왜 5, 6계층을 길게 하지 않는가?

고등학생 입장에서는 **OSI 1~4계층과 캡슐화 흐름**을 이해하는 것이 훨씬 중요함.  
실제 Packet Tracer 실습에서도 눈에 잘 보이는 것은 대부분 1~4계층임.

- **5계층(세션)**: 연결을 유지하고 끊는 흐름
- **6계층(표현)**: 인코딩, 암호화, 압축 같은 데이터 표현 방식
- **7계층(응용)**: 사용자가 실제로 쓰는 서비스(HTTP, DNS, FTP 등)

> 즉, 5·6계층은 "이런 역할이 있구나" 정도로만 알고,  
> 실제 시험과 실습에서는 **4계층 이하 + 캡슐화**에 집중하는 것이 효율적임.

---

## 1.2 5~7계층 한 번에 정리

| 계층 | 핵심 역할 | 쉬운 예시 |
|---|---|---|
| **7계층 응용** | 프로그램이 네트워크 기능 사용 | 웹 브라우저, 이메일 |
| **6계층 표현** | 데이터 형식 변환, 암호화, 압축 | UTF-8, HTTPS, ZIP |
| **5계층 세션** | 연결 시작, 유지, 종료 | 로그인 상태 유지, 화상회의 연결 |

**한 줄 요약**

```text
7계층: 무엇을 할지 정함
6계층: 어떤 형식으로 보낼지 정함
5계층: 얼마나 연결을 유지할지 관리
```

---

# 2장. 오늘 진짜 핵심 — 캡슐화와 역캡슐화

---

## 2.1 캡슐화란?

송신 측에서 데이터가 아래 계층으로 내려가면서 **헤더가 하나씩 붙는 과정**임.

```text
응용 데이터
→ 4계층: TCP/UDP 헤더 추가
→ 3계층: IP 헤더 추가
→ 2계층: MAC 헤더 + FCS 추가
→ 1계층: 비트 신호로 전송
```

| 계층 | 붙는 것 | PDU 이름 |
|---|---|---|
| 4계층 | TCP/UDP 헤더 | 세그먼트(Segment) |
| 3계층 | IP 헤더 | 패킷(Packet) |
| 2계층 | MAC 헤더, FCS | 프레임(Frame) |
| 1계층 | 전기신호/비트 | 비트(Bit) |

---

## 2.2 역캡슐화란?

수신 측에서 반대로 **헤더를 하나씩 벗겨내며 원래 데이터로 복원하는 과정**임.

```text
비트 수신
→ 2계층: 프레임 확인
→ 3계층: IP 확인
→ 4계층: 포트 / 통신 방식 확인
→ 응용 프로그램이 데이터 사용
```

---

## 2.3 가장 중요한 시험 포인트

```text
IP 주소 = 최종 목적지까지 거의 그대로 감
MAC 주소 = 장비를 한 번 건너갈 때마다 바뀔 수 있음
```

특히 **라우터를 지나면 MAC 주소는 새로 작성됨**.  
이 장면을 Packet Tracer에서 직접 보는 것이 오늘 실습 목표임.

---

# 3장. Packet Tracer로 캡슐화 확인 실습

---

## 3.1 이번 실습 목표

이번 실습에서는 아래 3가지를 직접 확인함.

1. PC에서 보낼 때 캡슐화가 어떻게 되는지
2. 스위치는 2계층까지만 보고 전달하는지
3. 라우터를 지나면서 **IP는 유지되고 MAC은 바뀌는지**

---

## 3.2 토폴로지 구성

이번에는 같은 LAN이 아니라, **라우터를 한 번 거치는 구조**로 만들어야 함.  
그래야 캡슐화와 MAC 주소 변경을 제대로 볼 수 있음.

```text
[PC0] --- [Switch0] --- [Router0] --- [Switch1] --- [PC1]
```

### 3.2.1 장비를 화면에 놓는 순서

1. Packet Tracer를 열고 새 작업 화면을 준비함
2. 하단에서 `End Devices`를 클릭함
3. `PC` 2대를 작업 화면으로 끌어다 놓음
   ![](/assets/img/posts/2026-03-09-network-6-1775288192012.png)
   
4. 하단에서 `Switches`를 클릭함
5. `2960` 스위치 2대를 작업 화면으로 끌어다 놓음
   
   ![](/assets/img/posts/2026-03-09-network-6-1775288242059.png)
   
6. 하단에서 `Routers`를 클릭함
7. `1941` 라우터 1대를 작업 화면으로 끌어다 놓음
   
   ![](/assets/img/posts/2026-03-09-network-6-1775288257463.png)
   
8. 왼쪽부터 `PC0 - Switch0 - Router0 - Switch1 - PC1`처럼 일렬로 배치함

### 3.2.2 케이블 연결 순서

1. 하단의 `Connections`를 클릭함
2. `Copper Straight-Through`를 선택함
3. `PC0` 클릭 → `FastEthernet0`
4. `Switch0` 클릭 → `FastEthernet0/1`
5. 다시 `Copper Straight-Through` 선택
6. `Switch0` 클릭 → `GigabitEthernet0/1`
7. `Router0` 클릭 → `GigabitEthernet0/0`
8. 다시 `Copper Straight-Through` 선택
9. `Router0` 클릭 → `GigabitEthernet0/1`
10. `Switch1` 클릭 → `GigabitEthernet0/1`
    
    ![](/assets/img/posts/2026-03-09-network-6-1775288360696.png)
    
    
    
11. 다시 `Copper Straight-Through` 선택
12. `Switch1` 클릭 → `FastEthernet0/1`
13. `PC1` 클릭 → `FastEthernet0`

### 3.2.3 연결 직후 확인

- 케이블 끝 점등이 잠깐 주황색일 수 있음  
  
  
  
- 잠시 뒤 초록색으로 바뀌면 정상임
  
  

- 계속 빨간색이면 포트나 케이블을 다시 확인함



- 라우터의 전원 반드시 확인
  
  ![](/assets/img/posts/2026-03-09-network-6-1775288545373.png)

## 3.3 주소 설정

### PC0

- IP 주소: `192.168.1.10`
- 서브넷 마스크: `255.255.255.0`
- 기본 게이트웨이: `192.168.1.1`

### Router0

- `G0/0`: `192.168.1.1 / 255.255.255.0`
- `G0/1`: `192.168.2.1 / 255.255.255.0`

### PC1

- IP 주소: `192.168.2.10`
- 서브넷 마스크: `255.255.255.0`
- 기본 게이트웨이: `192.168.2.1`

### 3.3.1 PC0 설정 클릭 순서

1. `PC0` 클릭
2. `Desktop` 클릭
3. `IP Configuration` 클릭
4. 아래 값을 입력함

```text
IP Address: 192.168.1.10
Subnet Mask: 255.255.255.0
Default Gateway: 192.168.1.1
```

### 3.3.2 PC1 설정 클릭 순서

1. `PC1` 클릭
2. `Desktop` 클릭
3. `IP Configuration` 클릭
4. 아래 값을 입력함

```text
IP Address: 192.168.2.10
Subnet Mask: 255.255.255.0
Default Gateway: 192.168.2.1
```

### 3.3.3 여기서 많이 틀리는 부분

- `Default Gateway`를 비워 두지 않기
- PC0의 게이트웨이는 `192.168.1.1`
- PC1의 게이트웨이는 `192.168.2.1`
- 두 PC의 서브넷 마스크는 모두 `255.255.255.0`

---

## 3.4 Router0 설정 방법

Router0를 클릭한 뒤 `CLI`에서 아래처럼 입력함.

```text
enable
configure terminal
interface g0/0
ip address 192.168.1.1 255.255.255.0
no shutdown
exit
interface g0/1
ip address 192.168.2.1 255.255.255.0
no shutdown
end
```

> `no shutdown`을 하지 않으면 인터페이스가 꺼진 상태라 통신이 안 됨.

### 3.4.1 입력 후 상태 확인

아래 명령으로 인터페이스 상태를 한 번 더 확인하면 좋음.

```text
show ip interface brief
```

정상이라면 `GigabitEthernet0/0`, `GigabitEthernet0/1`가 둘 다 `up`으로 보임.

![](/assets/img/posts/2026-03-09-network-6-1775288795942.png)


### 3.4.2 포트 이름이 다르게 보일 때

- 장비 종류에 따라 포트 이름이 조금 다를 수 있음
- 중요한 것은 PC0 쪽 인터페이스에 `192.168.1.1`
- PC1 쪽 인터페이스에 `192.168.2.1`을 넣는 것임

---

## 3.5 실습 전 확인

Realtime Mode에서 먼저 한 번 확인함.

1. `PC0` → `Desktop` → `Command Prompt`
2. 아래 명령어 입력

```text
ping 192.168.2.10
```

3. 응답이 오면 기본 설정 완료
4. 첫 번째 Ping이 실패해도 ARP 때문일 수 있으므로 2~3번 실행해 봄
   
   ![](/assets/img/posts/2026-03-09-network-6-1775288837353.png)

### 3.5.1 Ping이 안 될 때 점검 순서

1. PC0와 PC1의 IP, 서브넷 마스크, 기본 게이트웨이가 맞는지 확인
2. Router0의 IP 주소가 양쪽 인터페이스에 맞게 들어갔는지 확인
3. `no shutdown`을 했는지 확인
4. 케이블 연결 상태가 초록색인지 확인
5. 필요하면 `ping 192.168.1.1`, `ping 192.168.2.1`로 게이트웨이부터 따로 확인

> Realtime Mode에서 한 번 통신이 되는지 보고 넘어가면 Simulation Mode 해석이 훨씬 쉬움.

---

## 3.6 Simulation Mode 설정

1. Packet Tracer 우측 하단의 **`Simulation`** 클릭
2. 우측 Event List 패널이 열리면 **`Edit Filters`** 클릭
3. `Show All/None`으로 전체 해제
4. **`ARP`**, **`ICMP`**만 체크
   
   ![](/assets/img/posts/2026-03-09-network-6-1775289233212.png)
   
1. 창 닫기

> 처음에는 프로토콜을 적게 보는 것이 훨씬 이해하기 쉬움.

### 3.6.1 보기 편하게 만드는 팁

- Event List가 복잡하면 `Reset Simulation`으로 기록을 비움
- 자동 재생보다 `Capture/Forward`를 써서 한 칸씩 넘김
- 봉투를 클릭했을 때 `PDU Information` 창이 열리는지 확인

---

## 3.7 캡슐화 확인용 Ping 보내기

1. `PC0`의 `Command Prompt`에서 아래 명령 실행

```text
ping 192.168.2.10
```

2. Event List에 ARP와 ICMP 이벤트가 쌓이는지 확인
3. **`Capture/Forward`**를 눌러 한 단계씩 이동시킴

### 3.7.1 처음에 ARP가 먼저 보이는 이유

- PC0는 곧바로 ICMP를 보내지 않음
- 먼저 `192.168.1.1`의 MAC 주소를 알아내야 함
  
  ![](/assets/img/posts/2026-03-09-network-6-1775289416131.png)
  
- 그래서 ARP가 먼저 나오고, 그 다음 ICMP Echo Request가 진행됨

### 3.7.2 봉투를 클릭해서 볼 때 주로 확인할 탭

- `OSI Model`: 계층별로 무슨 일이 일어나는지 확인
- `Inbound PDU Details`: 들어오는 정보 확인
- `Outbound PDU Details`: 나가는 정보 확인

> 라우터에서는 `Inbound`와 `Outbound`를 비교하는 것이 핵심임.

---

## 3.8 반드시 보는 순서

### 1단계 — PC0에서 ARP 확인

처음에는 PC0가 **기본 게이트웨이 192.168.1.1의 MAC 주소**를 알아내야 함.

즉, PC0는 바로 PC1의 MAC을 찾지 않음.  
서로 다른 네트워크이기 때문에 "먼저 라우터한테 보내야지"라고 판단함.

**확인 포인트**

- ARP Request의 대상이 `192.168.1.1`인지
- ARP Reply를 Router0가 보내는지
- ARP Request가 브로드캐스트 형태로 나가는지
- ARP Reply를 받은 뒤 PC0가 게이트웨이 MAC을 알게 되는지

> 이것이 "원격지 목적지에 갈 때는 목적지 PC MAC이 아니라 게이트웨이 MAC을 사용한다"는 뜻임.

**직접 따라할 순서**

1. `PC0`에서 나온 첫 ARP 봉투를 클릭
2. `Outbound PDU Details`에서 Target IP가 `192.168.1.1`인지 확인
3. `Capture/Forward`를 눌러 `Switch0`로 이동
4. 다시 눌러 `Router0`까지 이동
5. Router0가 보내는 ARP Reply 봉투를 클릭
6. Reply가 다시 `PC0`로 돌아오는지 확인

---

### 2단계 — PC0에서 ICMP Echo Request 확인

PC0에서 출발하는 초록색 봉투를 클릭하고 **PDU Information**를 확인함.

**OSI Model 탭에서 볼 것**

- Layer 3:
  - Source IP = `192.168.1.10`
  - Destination IP = `192.168.2.10`
- Layer 2:
  - Source MAC = `PC0의 MAC`
  - Destination MAC = `Router0 G0/0의 MAC`

**직접 따라할 순서**

1. ARP가 끝난 뒤 생성된 ICMP 봉투 클릭
2. `OSI Model` 탭에서 Layer 3 값을 확인
3. 목적지 IP가 `192.168.2.10`인지 확인
4. Layer 2에서 목적지 MAC이 PC1이 아니라 Router0인지 확인
5. `Outbound PDU Details`에서 ICMP Echo Request인지 확인

즉, 이 시점의 핵심은 아래와 같음.

```text
IP 목적지 = 최종 목적지 PC1
MAC 목적지 = 지금 당장 보내야 하는 다음 장비 Router0
```

---

### 3단계 — Switch0에서 확인

패킷이 `Switch0`에 도착했을 때 봉투를 클릭함.

**확인 포인트**

- 스위치는 **2계층 장비**
- 목적지 MAC을 보고 어느 포트로 보낼지 결정
- IP 주소는 경로 판단 기준으로 사용하지 않음

**직접 따라할 순서**

1. `Switch0`에 도착한 봉투 클릭
2. `OSI Model`에서 2계층 중심으로 처리되는지 확인
3. 같은 IP 패킷이 그대로 전달되는지 확인
4. 스위치는 프레임을 전달할 뿐 IP를 바꾸지 않는다는 점을 연결해서 보기

즉, 스위치는 "최종 목적지가 누구인지"보다  
"이 프레임을 어느 포트로 내보낼지"를 MAC 주소로 판단함.

---

### 4단계 — Router0에서 확인

이번 실습의 가장 중요한 장면임.  
Router0에 도착한 봉투를 클릭해서 **In Layers / Out Layers**를 비교함.

**여기서 꼭 확인할 것**

1. 들어올 때의 목적지 MAC은 `Router0 G0/0 MAC`
2. 라우터는 2계층 헤더를 벗겨냄
3. 3계층 IP 주소를 보고 라우팅 결정
4. 나갈 때는 **새로운 2계층 헤더를 다시 붙임**

**직접 따라할 순서**

1. `Router0`에 들어온 봉투 클릭
2. `Inbound PDU Details`에서 목적지 MAC이 Router0 자신인지 확인
3. `OSI Model`에서 2계층 헤더가 제거되는 흐름 확인
4. 3계층에서 목적지 IP `192.168.2.10`을 보고 있는지 확인
5. `Outbound PDU Details`로 이동
6. Source MAC이 `Router0 G0/1`로 바뀌는지 확인
7. Destination MAC이 `PC1`로 바뀌는지 확인

즉, Router0를 지나고 나면:

```text
변하지 않는 것:
- Source IP = 192.168.1.10
- Destination IP = 192.168.2.10

바뀌는 것:
- Source MAC = Router0 G0/1의 MAC
- Destination MAC = PC1의 MAC
```

> 이 장면이 바로 **캡슐화 / 역캡슐화 / 재캡슐화**를 한 번에 보여주는 핵심 장면임.

---

### 5단계 — PC1에서 역캡슐화 확인

패킷이 `PC1`에 도착하면 봉투를 클릭함.

**확인 포인트**

- 2계층에서 MAC 확인 후 제거
- 3계층에서 목적지 IP 확인
- ICMP Echo Request 처리
- 이후 Echo Reply를 다시 생성해 반대로 보냄

**직접 따라할 순서**

1. `PC1`에 도착한 봉투 클릭
2. `OSI Model`에서 위 계층으로 올라가며 처리되는지 확인
3. Echo Request 처리가 끝난 뒤 Echo Reply 봉투가 생기는지 확인
4. Reply가 `Router0 → Switch0 → PC0`로 되돌아가는 것도 끝까지 확인

즉, 수신 측에서는 헤더를 벗기면서 위 계층으로 올라감.

### 3.8.1 최종 흐름 한 번 더 정리

```text
1. PC0가 게이트웨이 MAC을 ARP로 알아냄
2. PC0가 ICMP 패킷을 만들고 Router0 MAC을 붙여 전송
3. Switch0는 MAC만 보고 전달
4. Router0는 MAC 헤더를 벗기고 IP를 확인한 뒤 새 MAC 헤더를 붙여 전송
5. PC1은 역캡슐화 후 Echo Reply를 생성
6. Reply도 같은 원리로 반대 방향으로 이동
```

## 3.9 학생들이 가장 헷갈리는 부분 정리

### Q1. 왜 PC0는 처음부터 PC1의 MAC 주소를 안 쓰나?

PC1은 다른 네트워크에 있으므로 직접 도달 불가함.  
그래서 **같은 LAN 안에 있는 기본 게이트웨이(라우터)의 MAC 주소**를 사용함.

### Q2. 왜 IP 주소는 안 바뀌나?

IP 주소는 **최종 출발지와 최종 목적지**를 나타내기 때문임.  
중간 라우터는 경로만 바꿔 줄 뿐, 원래 목적지를 바꾸지 않음.

### Q3. 왜 MAC 주소는 바뀌나?

MAC 주소는 **한 구간(LAN) 안에서만 의미 있는 주소**이기 때문임.  
라우터를 넘어 새로운 LAN으로 들어가면 그 구간에 맞는 새 MAC 헤더가 필요함.

## 3.10 실습 체크리스트

| 확인 항목 | 직접 확인할 내용 |
|---|---|
| ARP 대상 | PC0가 `192.168.1.1`의 MAC을 찾는지 |
| PC0의 ICMP 패킷 | 목적지 IP는 `192.168.2.10`인지 |
| PC0의 프레임 | 목적지 MAC은 Router0의 MAC인지 |
| Switch0 동작 | 2계층만 보고 전달하는지 |
| Router0 동작 | IP는 유지, MAC은 재작성되는지 |
| PC1 도착 | 역캡슐화 후 Echo Reply를 생성하는지 |
